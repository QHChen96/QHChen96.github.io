    01 / 从问题出发

    模型给出下一步，Harness 让下一步真的发生。

    假设你让 AI：“检查一个项目，找出错误，修改代码，再运行测试。”一次模型请求只能根据输入生成输出。要完成整件事，还需要程序读取文件、执行工具、保存结果、再次调用模型，并在失败或取消时处理现场。

    Harness 就是承接这些工作的执行系统。在 DeepSeek Harness（DSH）里，模型适配、工具、会话、运行循环以及 UI 都通过插件组合。模型负责提出行动；运行时负责让行动按规则执行，并把观察结果送回下一次请求。[架构]

    输入与历史 → 模型判断 → 工具执行 → 结果入史 → 再次判断

    拿掉这个闭环，模型即使知道“应该运行测试”，也不代表测试已经运行。理解 Agent，首先要把生成一个行动请求与执行这个行动分开。

    先分清三个常被叫作“上下文”的东西

    名字实际含义你应问的问题
    LLM context本次发给模型的消息、系统指令与工具定义模型这一刻知道什么？
    Cordis Context / ctx运行时的服务容器、事件与插件生命周期接口代码这一刻能调用什么服务？
    Agent scope支持作用域的注册项在某个 Agent 下的可见范围这个 Agent 能看见哪些工具、提示词和技能？

    Session 是这次交互的事件账本；活着的 Agent 是当前驱动账本继续工作的运行对象。它们既不等于模型，也不等于同一个 ctx。[Session] [Cordis]

    02 / 对照系统架构图

    七个模块，承担七种责任。

    模块与入口它负责什么容易误会的边界
    Web / SDK / ACP接收输入、展示或传输结果入口有多种，底层可复用同一运行体系
    Agent registry
    ctx.agents    		创建、查找、恢复 Agent，提供统一交互接口接口与默认循环实现分离
    Agent loop
    ctx.agentLoop    		推进 turn / step，调用模型并处理工具续步默认循环本身也是插件
    Session
    ctx.sessions    		维护追加式事件历史，派生模型消息内存提交与存储 flush 是不同层次
    System prompt
    ctx.systemPrompt    		组装当前可见的提示词片段与工具定义不同 Agent 的可见贡献可以不同
    LLM
    ctx.llm    		准备调用、绑定模型适配器、统一流式协议模型服务可替换，能力差异仍需适配
    Tools
    ctx.tools    		工具注册、执行器与受策略约束的调用链需要模型据此继续判断的结果，须进入下一次请求

    这些模块借助 Cordis 组成插件树。官方架构把 core/agent 的接口与 core/agent-loop 的默认驱动明确分开，因此业务 UI 可以面向统一 Agent 接口，而不用耦合某个循环内部的私有方法。[架构] [Agent]

    Python SDK 也遵循同一结构：Python 客户端通过 JSON-RPC 驱动 DSH 运行时，不是用 Python 重写另一套 Agent 循环。[Python SDK]

    03 / 对照执行循环图

    跟着一条“读文件并总结”的请求走一遍。

    以下是教学情景，不是一次真实模型调用记录。假设模型先请求读文件，再给出总结。在这个情景中，我们把处理过程设为一个 Turn、两个 Step。Turn 是运行时的工作边界，不与每条用户消息或业务任务固定一一对应。每个 Step 包含一次模型请求以及这次请求产生的工具执行。实际还可能出现请求重试、输入拒绝、取消或追加指导。[Agent loop]

    1. 接收入队。用户消息进入 Agent inbox；followup() 排队启动后续 turn。
    2. 开启 Turn，领取输入。驱动记录开始事件，领取本轮输入。一个 Turn 可以在拒绝或取消时以零个 Step 结束。
    3. 组装工作条件。快照当前模型选择，解析当前可见工具，组装系统提示词。agent/pre-step 可接纳、改写或拒绝消息。
    4. 准备模型调用。prepareCall() 绑定适配器与实际能力；成功准备后，才按规则记录被接纳的输入、系统消息、请求头与上下文。
    5. 从日志派生请求。deriveMessages() 构建模型可见历史。模型请求使用冻结的消息快照，取消信号保持可用。
    6. 模型输出工具请求。模型生成工具名、参数和调用身份。此时文件尚未因为这段输出而被读取。
    7. 工具执行。运行时记录调用，经过策略与执行管线，读取文件并记录工具结果。Step 1 结束。
    8. 工具结果驱动下一步。工具调用通常留下“需要模型继续处理结果”的义务；Step 2 的请求带上刚才的结果。
    9. 模型给出总结。本次没有新工具调用，也没有待处理的新指导，运行时进入收尾检查。
    10. 关闭 Turn。记录结束。Agent 可以继续留在注册表中，等待下一条消息。

    真实实现的主要入口在 packages/core/agent-loop/src/agent.ts：ReactLoopAgent 管 inbox、turn 和 step。这里的名称指向 ReAct 式执行驱动，不是前端 React 组件。[循环源码]

    运行过程中怎样补充信息？

    方法语义典型用途
    followup()排到后续 Turn，并可唤醒 Agent“接下来再检查另一个目录”
    steer()进入最近的可用 Step 边界，并可唤醒 Agent“本次先不要改文件，只给诊断”
    inject()注入下一次接纳请求的上下文，本身不唤醒告知文件变动、业务状态或额外材料

    注入的信息需要等到下一次模型请求才会被模型看见，不能改变已经发出去的那次推理。[Agent]

    04 / 历史、状态与恢复

    Session 是事件账本，聊天记录是它的一种视图。

    DSH 的 Session 采用追加式事件模型。用户消息、模型输出、工具调用及结果、Turn / Step 边界等，按序进入同一份历史。模型消息由这些记录派生，避免另维护一份可能与界面脱节的对话数组。[Session]

    记录承担的作用直接进入模型消息？
    user/message用户输入及被接纳的上下文进入有效消息视图
    assistant/message已结算的助手消息及其紧凑流记录助手内容进入视图
    assistant/attempt保留失败、重试等已结算尝试的流记录属于日志记录，不直接加入模型历史
    tool/call / tool/result工具执行事实、调用与结果配对通过工具历史与消息投影形成请求
    turn/* / step/*运行阶段与结束原因属于生命周期记录

    重放的主要含义是重建状态与消息视图。重建出一条过去的工具调用记录，并不等于再执行一次那个工具。对于订单、发布、生成视频等外部操作，这个区别直接影响重复执行风险。

    界面流、日志提交、磁盘保存分成三层

    1. agent/assistant-stream 发送临时的 start / chunk / end 帧，让 UI 及时显示文字。
    2. 一次输出结算后，完整的紧凑流随 assistant/message 或 assistant/attempt 加入 Session。
    3. 持久化后端保存这些事件；checkpoint 策略在约定边界执行 flush。

    因此，“用户看见了部分文字”“事件已提交到内存账本”“存储确认已保存”是三件事。硬崩溃若发生在输出结算前，临时片段可能没有对应的持久流记录。本页以锁定提交的 assistant-stream.ts 为准。[流式源码] [Checkpoint]

    上下文变长，怎样继续工作？

    日志保留已提交的会话事件，模型一次请求却受上下文窗口约束。DSH 把 Compaction 设计为可替换能力：记录摘要与替换决策，从事件投影出缩短后的消息视图。保留日志不代表每次把全部日志发送给模型。摘要仍可能丢细节，所以业务硬规则、订单状态与素材索引应留在可查询的权威数据中。后一句是应用设计建议。[Compaction]

    请求成本取决于实际送入模型的消息和工具定义；保持稳定前缀有利于提供商支持的缓存复用，但缓存命中、计费和压缩效果需要实际测量。不能从“有 Session”推导出“无限记忆”或“零成本上下文”。[Agent loop]

    05 / 行动如何受控

    模型提出调用，工具管线执行并记录结果。

    一个工具至少要说明：叫什么、何时用、输入参数是什么、实际执行什么、返回怎样的结果。插件把定义注册到 ctx.tools 后，模型可见的 schema 参与请求组装。模型拿到的是调用说明，执行函数留在运行环境中。[工具开发]

    tool/call→pre-execute→guards→execute→post-execute→tool/result

    这是教学简化流程。真实管线还区分输出投影、最终内容约束和结果观察：前置策略可以允许、拒绝或请求审批；guard 提供不可被后续监听器取消的拒绝；执行包装可实现超时、指标等；后置阶段可转换结果；最后把权威结果记回 Session。tools/result 是运行时观察事件，tool/result 是 Session 事实记录。[工具管线]

    取消是协作机制，工具实现应响应 exec.signal。写一个“超时毫秒数”字段也不会让任意函数自动停止，仍需相应策略实现。注册项的生命周期清理，同样不会自动撤销已发送的消息或已创建的业务订单。[工具开发]

    Native 调用与 PTC

    Native 模式让模型直接提出具体工具调用。PTC（Programmatic Tool Calling）让模型提交代码，通过生成的工具 SDK 编排调用。PTC 内部子调用仍进入工具策略管线。需要对大量结果做过滤、聚合时，程序先处理再返回必要数据，可以减少把中间材料反复交给模型的需要；具体收益需实测。[工具管线]

    MCP 接在哪里？

    每个配置的 MCP server 由一个连接插件桥接：发现远端工具，再注册为普通 DSH 工具，因此仍受取消、权限和结果记录机制管理。资源按需发现读取，server instructions 可加入系统提示词。MCP client 不发布统一的 ctx.mcp 服务，图里也没有虚构这个中心模块。[MCP]

    06 / 对照插件装配图

    Everything is a Plugin，真正解决的是可组合性。

    在 Cordis 中，插件通过 apply(ctx) 或 Service 类挂载；服务通过稳定的 ctx.<key> 暴露；inject 声明依赖；事件提供扩展位置；ctx.effect()、ctx.on() 等注册跟随生命周期清理。由此，增加审批或新工具通常可以挂到现有扩展点，而不用复制一份 Agent 循环。[Cordis]

    借用熟悉的企业后端概念，ctx 的服务查找与依赖声明可以帮助你联想到依赖注入容器；around 事件可以帮助你联想到中间件。这只是理解类比，Cordis 的作用域、事件和卸载契约要按其自身规则使用。

    六个容易混淆的名词

    概念负责什么视频创作中心的设计示例
    Plugin可挂载的功能模块视频生成服务接入模块
    Service代码之间使用的能力接口自建的视频任务查询服务
    Tool模型可申请执行的动作提交生成任务、读取任务结果
    Skill按需加载的工作说明与资源分镜编写规范、角色一致性方法
    Agent Preset某类 Agent 的插件与能力组合编剧、分镜师、审核员岗位
    Profile / Bundle应用启动组合 / 可分发配置层视频工作台的宿主部署组合

    右列是应用设计示例，不是 DSH 内置业务功能。一个插件可以只提供 UI、存储或模型适配，不一定提供 Tool。Skill 通常先暴露名称与描述，模型需要时再读取正文；说明本身不授予工具或宿主权限。[Skills]

    启动时怎样组成产品？

    Profile 选择有序 Bundle；随后叠加 Profile 自己的 patch、Harness home 的 patch，以及命令行 --patch 覆盖，生成插件树。web、headless、sdk、sdk-minimal、acp 是已提供的启动组合。Patch 的替换有明确语义，不能默认所有字段都自动深合并。[应用启动]

    Agent Preset 则作用在 Agent 的工具、提示词、Skills 等组合上。同一宿主可以有多种岗位。已运行的 Agent 可继续持有旧组合 revision；重启后恢复通常按保存的 Preset ID 解析当前定义，并不自动保存和恢复旧插件代码。[Preset]

    Scope / Preset 控制能力可见性，不能充当多租户安全边界。普通服务要使用隔离 realm，还需要 provider 与消费者正确配置；操作系统权限、数据库租户条件和业务鉴权应在各自真实边界执行。[Preset]

    07 / 怎样替换能力而少改业务代码

    接口定义、能力实现、能力使用者分开。

    官方把这种边界称为 capability seam。它通常包括三部分：Service Definition 声明契约，Provider 实现契约，Consumer 调用契约。Consumer 可以是模型 Tool，也可以是其他插件。[架构]

    例如读取文件：调用者面向文件能力接口，底层 provider 决定读取本地文件还是远端执行环境。又如模型调用：循环面向 ctx.llm，适配器负责把统一请求与流协议转换成模型服务的格式。[LLM]

    可替换的前提是接口契约一致。换模型仍要确认工具调用、推理参数、上下文长度等能力；把运行环境换成远端 sandbox，也要让文件与子进程服务指向同一执行世界。架构只提供替换位置，不会自动消除服务语义差异。

    Hook 为什么不一定要修改主循环？

    如 tools/pre-execute、llm/stream 这样的 waterfall 是 around middleware。监听者调用 next() 把控制交给后续逻辑，也可以在拥有决策权时提前返回。这里“加一个插件”真正意味着“把行为挂到某个确定的执行边界”。[Cordis]

    插件不能随意把所有东西都写进一段系统提示词：需要在恢复后还存在的事实，应进入 Session 事件或权威业务存储；仅观察当前调用的数据，可以使用 live event；要让模型执行一个动作，应提供 Tool；要让人点击的命令直接生效，可以使用命令机制。[扩展指南]

    08 / 多 Agent 的层次

    单个循环、子 Agent、Workflow 与 Team 各管一层。

    机制负责的问题当前实现边界
    单 Agent loop一位执行者如何连续判断与行动同一 Agent 通过自己的 inbox 与 step 边界接工作
    Subagent把一个子任务委派出去本地可创建或 fork 子会话；外部 provider 的后续交互能力不同
    Workflow用 JavaScript 编排多个子任务的并行与依赖当前没有脚本与中间值的 checkpoint / resume
    Agent Teams持续维护队友、消息和共享任务 DAG实验性、按需启用；路径声明是协作提示，不是文件锁

    Subagent 的 provider 可以给出不同执行方式。本地子 Agent 有自己的 Session；fork 可以继承已完成的父会话前缀。外部运行器可能只提供一次执行，不应假定所有 provider 都支持续聊或冷恢复。[Subagent]

    Workflow 让脚本调用 agent()、parallel()、pipeline() 等组织工作，父调用等待整个 run 结束。当前的运行脚本、子任务进度与中间变量不做断点持久化，所以进程重启无法从原指令位置继续；也没有内置跨子 Agent 的 token budget 词汇。[Workflow]

    Agent Teams 维护 Lead 与队友、共享任务依赖以及带 revision 的更新。blockedBy 表达依赖，writeScopes 用于提示路径重叠。后者不会阻止两个 Agent 同时编辑同一文件，工程上仍需你选择任务边界、工作树或冲突处理方式。[Agent Teams]

    因此，“有 Graph / DAG”需要继续追问：它表达的是任务依赖、正在运行的执行流程，还是可恢复的工作状态？这些性质需要逐项确认。

    09 / 生产中最有价值的边界

    日志能证明发起过操作，结果未知时还需查询外部世界。

    DSH 将持久化后端与 checkpoint 策略拆开。前者负责存储；后者在模型请求前、顶层工具执行前和下一步边界 flush 已提交的相关事件。未完成持久化时，不放行对应的模型请求或顶层工具主体。[Checkpoint]

    教学案例：视频任务是否已经创建？

    1. DSH 将“准备调用生成工具”的记录持久保存。
    2. 生成服务成功创建任务，得到外部 job ID。
    3. 进程在把结果保存到 Session 前崩溃。
    4. 恢复后只看到调用，缺少结果；不能推断任务一定失败。

    这种情况会得到 TOOL_OUTCOME_UNKNOWN。正确的业务处理是使用幂等键、查询外部任务状态，再决定补记结果或重新执行。官方支持将工具调用身份 exec.callId 用于支持幂等的 provider；对于跨次重新发起的同一业务操作，还要定义稳定的业务幂等键。[Checkpoint]

    模型请求重试则是另一层机制：重试策略可以在同一 Step 里重新发模型请求，保留失败 attempt，避免把同一用户消息重复加入历史。重试推理与重试外部动作必须分别设计。[LLM retry]

    Session 恢复也不等于恢复任意 shell 进程、浏览器状态或 Workflow 的脚本位置。这些能力需要其所属运行环境或业务服务单独提供。

    分镜卡片与任务进度Session 业务事件 + Web renderer事件模型、可恢复投影与交互组件
    项目、素材、版本与长任务独立业务后端与任务服务权威状态、队列、权限、对账与长期保存

    例如一次“把这段小说做成 30 秒短片”的请求：导演 Agent 读取改编 Skill，调用检索工具获得人物设定，再委派分镜任务；生成工具把工作提交给你自己的任务服务，返回任务 ID；UI 根据业务事件显示状态。长视频渲染进度由任务服务持续维护，Agent Session 保存交互与决策经过。

    DSH 已提供 Web 会话节点与 keyed renderer 扩展位置。一般工具展示与专门的 Web 业务卡片是不同层，Host 工具实现不会凭空生成你的分镜工作台。[Conversation]

    你的 SCRM 或 OMS / WMS 项目也可按同样边界接入：工具负责访问已授权业务接口，数据库负责订单、库存与租户数据的真实状态。RAG 检索变成工具或上下文来源后，准确率仍需用召回命中、证据覆盖、回答忠实性等指标单独评估；框架可组合性本身不保证知识质量。

    11 / 三个验证原理的实验

    先看到插件树，再看到闭环，最后接入自己的能力。

    以下实验入口来自官方文档，未在本次讲解中发起真实模型请求。运行模型实验需要你配置可用 provider；模型是否使用工具、执行几步，以实际日志为准。

    实验 A：看见真实的产品组合

    npx @deepseek-ai/dsh --profile web --dump-config

    它显示最终插件配置，而不发起一个模型任务。查找模型、Session、工具、Agent loop、持久化策略与 Web 插件，验证“循环本身也是组合的一部分”。该 npm 命令会解析当时发布的包；本页源码分析固定在页首提交，二者版本可能不同。[应用启动]

    实验 B：观察一个工具闭环

    在单独的练习目录放一个 README，启动已配置好模型的 Web 或 SDK，要求：“请用工具读取 README，再用两句话总结。”查看实际事件，区分模型请求、tool/call、tool/result 与下一 Step。尝试运行中补充“只关注部署说明”，观察下一 Step 才吸收指导。

    实验 C：添加一个无副作用工具

    按官方首次工具教程，注册一个问候或时长估算工具：ctx.tools.register(defineTool(...))。准备输入参数与 output.schema / output.render，让执行函数返回结构化值；通过 patch 挂载插件，再让模型明确调用。[首次工具教程]

    验收点：模型能看到定义；调用参数通过校验；结果由你写的代码计算；执行结果回到下一次推理；移除插件后新组合不再提供该能力。这比先搭复杂多 Agent 团队更容易定位问题。

    展开：理解循环的教学伪代码 
    # 教学伪代码；不是可直接运行的 DSH API。
while 当前还有需要处理的工作:
    tools, prompt = 组装当前Agent的可见能力()
    接纳输入并写入Session()
    messages = 从Session派生模型历史()
    response = 请求模型(messages, tools, prompt)
    结算助手输出(response)
    if response.包含工具调用:
        results = 经过策略管线执行(response.工具调用)
        记录工具结果(results)
        continue
    if 没有新指导且收尾允许结束:
        break

# 压缩、flush屏障、作用域与资源释放。

    读源码的建议顺序：架构 → Agent 接口 → agent-loop 的 agent.ts → Session → Tools pipeline → Cordis → Preset → Workflow / Teams。沿一条调用路径阅读，再补支线，能把每个抽象和真实执行联系起来。
