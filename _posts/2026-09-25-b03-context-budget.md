**领导：**订单号和记录的区别我懂了。现在我把三本客服手册、两年聊天记录、所有旧 FAQ 都贴进去，它总不会说“不知道”了吧？

**小陈：**它可能先说“输入太长”，也可能在一堆话里漏掉客户最要紧的那句“我没收到”。您这是给人找签收记录，顺手把仓库钥匙、去年年会菜单和五版制度都压在记录上面。

**领导：**不是说模型上下文窗口很大吗？

**小陈：**大也有边。模型处理文字会把它切成 **token**；token 不是固定一个汉字，也不是固定一个词。一次请求的**上下文窗口**要装输入，也要给输出留地方；有些模型还要为内部推理占用空间。窗口大，不表示资料越多越准，也不表示这轮读过的内容会永久记住。[OpenAI 的上下文说明](https://developers.openai.com/api/docs/guides/conversation-state)把输入、输出与窗口限制分开讲得很清楚。

**领导：**我看采购表写的是“超长上下文”，够塞就算赢吧？

**小陈：**额度像会议室座位数，不是参会名单。三本手册都坐进来，客户原话也可能没人在意。还有个实际问题：如果输入占得太满，输出要写内部处理卡时留的空间不够，答案可能写到一半就停。具体上限、截断方式和计费要看所选模型与应用配置，不能只盯宣传页上的那个大数字。

**领导：**所以你要给三本手册做摘要？别一摘要把“先核实签收”给摘要没了。

**小陈：**不能凭感觉删。我先列**本轮上下文清单**：哪段为工单 0823 服务，谁提供的，为什么放进来。有效规则保留原文关键段落和版本，不把“可以退款”四个字摘得像免审批券。

| 材料 | 来源与用途 | 本轮处理 |
| --- | --- | --- |
| 任务卡：只写内部草稿，不承诺退款 | 产品、客服确认的任务边界 | 保留，放在明确的任务要求里 |
| 客户原话：“显示已签收，我没收到，能退款吗？” | 工单 0823；必须保留争议点 | 保留原句，不能只剩“问退款” |
| 本轮订单查询结果 | 订单系统；只说明系统记录 | 有结果才放入，并带查询时间；失败就标未知 |
| 签收争议的现行规则片段 | 已校验版本的规则库；回答处理步骤 | 只放相关段落、版本和生效信息 |
| 归档 FAQ：“签收异常可退款” | 旧版资料；可能误导 | 不作为现行依据送入本轮 |
| 其他品类的整本手册、两年前闲聊 | 对这张单没有直接用途 | 暂不放；需要时再找对应段落 |

**领导：**万一现行规则在没贴进去的第二本手册第 68 页呢？

**小陈：**那该解决的是**怎么找到相关段落**，不是把整本书硬塞给每个工单。应用先按问题找相关资料，核对版本与生效状态，再把原文片段和来源送进这一轮。找不到、找到两份互相冲突的“现行规则”，就停下来交人。检索怎么做，后面单独讲；今天先把“该给模型看什么”定清楚。

**领导：**那旧聊天记录一点用都没有？

**小陈：**有用时再拿，比如客户已经补充了门卫电话，当前处理确实需要核实这一句，就保留原话和时间。两年前另一位客户的长篇争执，对这张单没帮助。重要的是**按工单和本轮动作选材料**，并记下删掉什么；不是规定“历史记录一律不能看”。

**领导：**你这删删减减，能省多少费用？

**小陈：**不编一个“省 60%”来哄您。我们记录同一张模拟工单在同一模型下的**输入 token、输出 token、耗时与结果**，分别跑“全量材料”和“按清单材料”。少传无关文本通常会减少输入量，具体费用和耗时得按所用模型、计费方式和实测结果算。更要紧的是，两次都核对有没有保留“客户称未收到”、有没有误引旧规则。

**领导：**那今天交付什么？

**小陈：**一份可给开发照着装材料的上下文清单，加一张回放记录表：每段材料的来源、版本、用途、去留；每轮的 token 用量、耗时、所引依据、草稿和转人工原因。验收就三条：**客户诉求不丢，依据能追到有效版本，缺证据时不瞎补。**费用和耗时另看实测，不拿漂亮百分比当成绩。

**领导：**还要在表里记输出 token？我只管往里塞了多少。

**小陈：**要记。回答长短也占窗口和费用；内部卡写不全，就算输入省了一半也没用。同一工单回放先比答得对不对，再比用量和耗时。要是“精简版”漏了签收争议那条关键规则，省出来的全是返工费。

**领导：**还有一句：这轮看过的，下轮它记得吗？

**小陈：**别赌。下一轮要用的东西，应用得按需要再提供或从状态里取。上下文窗口是这一次开会的桌面，不是公司档案室。

## “窗口很大”为什么仍会答错

**领导：**我买的模型窗口够长，三本手册全放进去也没超过上限，为什么还要筛？

**小陈：**窗口上限只回答“这次请求能否装下”，不回答“模型能否从几十页里稳稳找到适用条款”。无关材料多会增加输入费、处理时长与相互矛盾的说法；过期条款若正好写得更像客户问题，模型可能引用错版本。即使没有硬截断，客户“已签收却未收到”的争议也可能被一堆退款入口说明淹没。上下文管理的目标是把当前任务必要的、可信且适用的材料送到位，而不是比赛谁的提示更长。

**领导：**既然你说 token 不是汉字，预算怎么估？

**小陈：**用实际所选模型的计数方法，对任务要求、会话、工具结果、检索片段和预期输出分别计量。不能拿“一个汉字等于一个 token”估价。窗口预算先预留输出和可能的推理空间，再分给固定规则、当前客户消息、工具回执、检索证据。具体比例不是写死的行业公式，而要看模型上限、输出格式和任务复杂度。若本轮需要一张完整处理卡，不能把输入塞满后只给它留下半句话的空间。

**领导：**要不要永远把系统提示放最前，客户消息放最后？

**小陈：**应用应按接口规定的角色与结构发送，不靠在纯文本里加几个“最高优先级”的大标题伪造角色。客户原话需要完整保留关键争议，规则片段要带来源和版本，工具结果按调用返回。排列可通过回放评估，但**顺序不能代替来源和权限**。把过期规则放在最显眼的位置，它仍然过期；把客户假装管理员的文字放在末尾，它仍只是客户文字。

## 哪些东西必须保留原文，哪些可以压缩

**领导：**我最怕你压缩政策，把一个“不”字压没了。

**小陈：**对决定业务资格的条款，保留原文关键句、条件、例外、版本和生效范围；可以删掉无关章节，却不能只抽“可退款”三个字。客户原话里“显示已签收，但我没收到”两半都重要，摘要若变成“咨询退款”就丢了争议根。订单查询结果可裁成必要字段，但不能丢查询时间和状态来源。过去几十轮客服寒暄可概括，不过客户新补充的门卫信息、承诺时间和已创建的核查任务要带可核查的记录。

**领导：**那让模型给长对话做摘要，不就省事了？

**小陈：**可以，但摘要是压缩产物，不是原始事实。存摘要时保留它覆盖的消息范围、生成时间、引用的关键消息 ID，以及仍未解决的问题；最好用结构化状态记录订单号、当前已核实事实和待办，而不是一句“客户问题已处理”。每次摘要更新要防止“可申请”被写成“已批准”、客户主张被写成公司事实。高风险承诺仍回到原消息或业务回执核对。摘要能帮模型接上话，不能代替审计档案。

**领导：**两年前聊天记录里客户曾说家里门牌变过，这次有没有用？

**小陈：**看是否与当前订单和处理动作有关，且客户当前身份有权让我们读取。旧地址可能已经失效，不能拿来自动更改配送。若客服需要核实历史地址，按权限查询并标明时间；不需要时别放进模型上下文。选材料的原则不是“越新越真”或“越多越保险”，而是**当前问题需要、来源可查、权限允许、时效合适**。涉及个人信息时，多给模型一页，等于多扩一页暴露面。

## 检索不是把手册缩小成随机三段

**领导：**你说从第二本手册第 68 页拿相关段落，搜索怎么保证没漏？

**小陈：**先有合格的知识库：文档版本、状态、生效时间、地区和业务线清楚；PDF 解析别把表格列错位；切分时保留标题、条件和例外。查询时从客户问题和订单状态提取关键词与语义，再按有效范围过滤，必要时结合关键词与向量召回并重排。候选进入模型前还要核它是否真的回答这张单。若找不到适用条款，诚实标缺证据，不因“窗口还空着”就塞一个看起来相近的旧 FAQ。

**领导：**检索结果只取前三条，不就控制住预算？

**小陈：**固定三条可能在简单题够用，在有例外条款的题里漏掉关键限制。数量要跟问题类型、条款结构和评测结果配合；有时一个完整段落比三段碎片更有用。重排分数只是找候选，不能把最高分等同于业务适用。我们在回放里看“正确条款有没有进来”“错误旧版有没有混进来”“答案每句能否被证据支持”，再调片段数与长度。预算是约束，不是闭着眼睛砍页数的理由。

**领导：**我把整本手册缓存给模型，以后每单都不用检索？

**小陈：**缓存能降低重复处理的开销，但要看供应商和应用的具体机制，并不自动保证旧政策失效时缓存会跟着更新。规则改版后，当前请求必须引用有效版本；缓存键或上下文构建应包含规则版本，失效和回滚要能追踪。客户与订单私有数据更不能因为“省钱”跨会话复用。技术缓存处理重复文本，业务授权与时效仍由应用判断。

## 窗口满了时，删什么，不能删什么

**领导：**假设客户聊了二十轮、工具查了八次，上下文真的快满了，你怎么取舍？

**小陈：**先保留任务边界、最新客户诉求、当前订单绑定、最新有效工具回执、适用规则和未完成待办。旧轮里可归档的寒暄、重复查询结果、已解决且与当前问题无关的话可以压缩或移出；但会影响现在承诺的事项要保留准确状态和回执引用。若仍装不下，就拆任务：先完成证据核对，再生成回复；或先让客服接手。不能悄悄截掉最早的退款审批信息，却继续使用“之前已经批准”的结论。

**领导：**把旧轮聊天删掉，模型会不会忘了已经问过客户什么？

**小陈：**所以该持久化的是状态，不是赌模型记忆。比如 `asked_for_signature_proof=true`、`customer_replied_at=...`、`pending_owner=after_sales`，并附原消息链接；下一轮按需要重新取出。若状态和聊天摘要冲突，以业务系统和原始消息核验。长对话压缩后做一次回放，检查它是否重复索取客户已经提供的材料、是否把待处理说成已完成。可恢复性比把所有对话塞在一个窗口里重要。

**领导：**若 API 报上下文超限，直接截最旧消息总行吧？

**小陈：**不要在生产里悄悄截，尤其不能只按时间切。最旧消息可能是客户最初的未收货陈述、正式授权或退款承诺。先由上下文构建器按重要性与可恢复来源选取，并在请求前计数；超限时给出明确降级：压缩可归档历史、减少无关候选、分步处理或转人工。记录删掉了哪些材料，排障时才知道模型为什么答偏。若输出被截断，也不能把半张卡送审核，标生成不完整并恢复。

## 同一张工单，怎么比较“全塞”和“精选”

**领导：**我们做两组测试，精选版更快，你就能说它更好吗？

**小陈：**先固定模型、温度、客户问题、订单回执与规则版本，只改变上下文构建策略。每条样本标出必须保留的事实与条款、禁止的结论，再看完整性、证据支持、过期规则误用、转人是否正确。记录输入与输出 token、生成耗时、工具调用、客服改稿。对同一工单重复运行几次，看是否稳定，但重复样本不当作新增业务场景。若精选版省钱却漏掉“先核查签收”的例外，不能算赢。

**领导：**具体有哪些试题？

**小陈：**至少五类：客户原话被长历史淹没；旧 FAQ 与新规则相似但冲突；订单状态刚更新，旧工具结果仍在对话里；政策条件跨表格和脚注；客户提到另一张订单，系统不能跨单拿历史记录。正常入口咨询也要有，防止精选策略把所有题都转人工。每条保存构建后的实际模型输入，光看原始资料库不够，因为问题可能出在“取对了却没送进去”。

**领导：**看到 token 数降了 40%，能不能写成成本降 40%？

**小陈：**不能直接写。模型费用可能区分输入、输出、缓存，工具检索和人工审核也有成本；精选版若输出更长、重试更多，账单不按输入比例下降。拿真实计费与试点人工耗时算完整成本，再按题型看收益。省下来的 token 若换来错误承诺，事故成本会把那点折扣吃掉。报告写实测条件、样本量和不确定性，别把一次演示的百分比复制进投资回报表。

## 上线后，旧规则突然冒出来怎么办

**领导：**假设今天政策改版，你们昨晚的精选上下文模板还带着旧片段，谁来发现？

**小陈：**每次请求记录文档 ID、版本、索引构建号和实际送入模型的片段。规则发布时触发相关索引更新与缓存失效，先做旧版不可被当前题召回、新版能被召回的回归；若新旧并存或检索异常，暂停该题型的自动结论，客服用受控规则库人工核查。已发出的历史回复保留当时证据版本以便追溯，当前回复不沿用。把“资料源已更新”当成“所有模型上下文已更新”，中间可能隔着索引、副本、缓存和正在处理的会话。

**领导：**如果当前规则确实缺失，Agent 可以借旧版先给个大概吗？

**小陈：**可说明“正在核对适用政策”，并安排有主待办；不能拿归档条款作为当前资格判断。客服内部可看到“旧版曾这样规定，仅供排查规则缺口”，但对客承诺必须依据现行有效规则。资料不足时回答范围缩窄，是诚实服务；把空白用旧文填满，看似积极，后面客服要花更多时间拆穿。

**领导：**最后给我一个面试版本：长上下文与 RAG 谁赢？

**小陈：**没有按名字分胜负。长窗口解决“能容纳多少当前相关材料”，检索解决“从大量材料里找到哪一段”；二者常配合。小而稳定的规则集可直接提供，庞大且常更新的知识库更需要检索和版本治理；高风险结论无论走哪条路，都要检查证据适用和动作回执。先用同一批工单比较正确性、遗漏、延迟和成本，再决定组合，而不是看宣传里的窗口数字决定系统架构。

**领导：**如果面试官继续问“为什么不能全靠摘要记忆”，怎么答？

**小陈：**摘要只保留生成时认为重要的信息，可能漏掉后来才变关键的一句，也可能把条件说满。当前订单状态、审批结果和退款执行必须回业务系统查；政策应回有效版本；客户承诺要能回到原消息。摘要适合帮助定位和续聊，不适合当不可变事实源。应用可以保存结构化状态和引用指针，按本轮需要重取原文或回执，这比让模型在多轮压缩的故事里猜哪句话还算数可靠。

**领导：**那怎么知道构建器没有悄悄删掉最关键的那句？

**小陈：**对每类工单列“不可丢字段”：本单客户诉求、当前绑定订单、最新业务状态与查询时间、适用规则和阻断条件、未完成待办。请求前做完整性检查，缺必需项就停止生成对客结论。回放时把实际送入模型的上下文与源材料逐项对照，标出保留、压缩、排除的原因。线上抽样检验“客户说没收到”是否仍出现，旧版 FAQ 是否被排除。指标不仅是平均 token 数，还有关键信息保留率与误用率。

**领导：**模型窗口升级变大，以前的清单是不是可以全扔？

**小陈：**不用。更大的窗口可让某些长条款或复杂案情少切分，但权限、时效、版本和来源问题不会因容量增加消失。升级时用同一批难单重测，看看是否能保留更多必要上下文、减少遗漏，同时关注费用与高分位延迟。若把全部旧资料重新塞回去，升级只会给过期政策换一张更大的桌子。

**领导：**精选上下文的清单谁维护？

**小陈：**产品与业务定义每类工单的不可丢事实，知识负责人维护文档版本，开发维护构建与计数，客服用改稿原因反馈遗漏。规则改版、工具字段变化或客户新增问法，都要带着回放更新清单。上下文预算不是一次裁掉几页的压缩技巧，而是随业务变化持续维护的输入契约。
