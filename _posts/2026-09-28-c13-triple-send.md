**领导：**发送接口报超时。重试两次，总有一次能发出去。

**小陈：**问题是第一次可能已经发出去了，只是“我收到了”的回执掉在路上。再试两次，客户手机一震三下，以为我们在催他给道歉信点赞。

**领导：**那不重试？

**小陈：**先分清“没执行”和“执行结果未知”。这单有两个坑：工单系统把同一个事件投递了三次；发送服务第一次成功，响应却超时。我们不能只在 Agent 提示词里写“请勿重复”，闸门得设在发送服务前。

**领导：**闸门怎么认？

**小陈：**工单事件有稳定的 `event_id`；发送动作另有业务唯一键，例如“工单 0823 + 草稿版本 4 + 客户确认回复”。数据库先原子地登记这个键和状态，再调用发送服务。重复事件命中旧键，就读取原状态，不再生成新发送。若渠道支持幂等键，重试带同一个键；[Stripe 的幂等请求文档](https://docs.stripe.com/api/idempotent_requests)说明了这类接口如何用键识别重复请求，但我们的短信、邮件供应商是否支持，要逐个核实，不能照搬。

**领导：**超时以后，到底谁去查？

**小陈：**照表办：

| 查到的状态 | 处理 |
| --- | --- |
| 渠道明确未接收，且本地无发送回执 | 用同一业务键按限次策略重试 |
| 渠道已接收／已发送 | 记录回执，不再发送 |
| 渠道查不到，结果仍不确定 | 标记“待核实”，人工核对；暂停自动外发 |

**领导：**上线验收？

**小陈：**故意投递三次同一事件，再让第一次发送成功但响应超时：客户侧最多收到一封，本地只有一个有效发送记录；查不到结果时必须停在“待核实”，客服能看到原键、次数和回执查询记录。补发若确属新业务动作，要由人明确创建新版本并说明原因，不能偷偷换个键绕过去。[微软的幂等消费者模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer)也把重复消息视为应由消费者处理的正常情况。

## 先把两种重复分开，闸门才装得对

**领导：**同一事件来三次、发送接口又重试，不都是重复吗？

**小陈：**发生位置不同。工单系统发出“草稿已批准”事件，消息队列可能至少投递一次，但因为确认丢失，消费者会收到两三次；这是**事件重复**。消费者调用邮件服务，服务已发出邮件但响应超时，消费者再调用；这是**外部动作重复**。只在消费端按 `event_id` 去重，挡不住调用邮件服务后的未知结果；只给邮件接口加幂等键，也挡不住同一业务动作被重复创建成三个不同请求。两道闸都要有。

事件消费端的键应是稳定的逻辑事件标识，而不是消息队列每次投递临时生成的编号。若同一“草稿已批准”事件重投，三个副本的 `event_id` 相同；它们可以有不同 `delivery_id`，那只是运输记录。消费者按 `consumer_name + event_id` 建唯一约束，避免两个消费者实例同时看到“还没有处理”便各自创建发送任务。先查再插两步之间有竞态，要让数据库唯一约束做裁判。

发送动作还需要独立业务键。`case_id + approved_draft_version + recipient + channel + purpose` 可以描述“这张工单、这版批准内容、发给这个收件人、通过这个渠道、为了这一项告知”的逻辑动作。实际可以把这些字段规范化后生成不含个人信息的随机或派生键，并保存字段快照。不要只用 `case_id`：一张单可能确实要发进度和最终结论两封；也不要每次重试都生成新 UUID：那样渠道根本看不出是同一动作。

**领导：**客服改了一个标点，要算新动作吗？

**小陈：**要看是否已批准、是否已发。发送前改稿会产生新草稿版本，旧待发任务要被取消或标过期，新版本重新审批；发送后改稿不能把同一封邮件“改掉”，要明确创建更正通知，记录它引用前一次发送回执。业务键不能因为模型又生成了一版就自动重置，否则一次超时可能被误当成“新内容”发第二封。客服在界面上要看到“旧版已发／新版拟补发”，由有权限的人决定是否需要纠正。

## 发送任务的状态，不能只有成功和失败

**领导：**设计状态机会不会比发邮件还费劲？

**小陈：**最少也要有 `待发送`、`发送中`、`已确认接收`、`明确失败`、`结果未知`、`待人工核对`、`取消`。外部接口调用之前，发送服务在本地登记业务键、消息内容的摘要哈希、审批回执和状态；登记与任务入队要保持一致。两个工作进程同时拿到任务，也只能一个拿到租约或条件更新成功。发完收到渠道回执，更新状态与渠道消息 ID。若请求超时，不写“失败”，写“未知”，随后按渠道能力查询。

“已确认接收”也不必冒充“客户已读”。邮件服务接受提交、SMTP 投递、最终送达、客户打开，是不同信号；短信网关亦然。本文要解决的是**不要重复外发**，还要知道客户是否收到、是否需要别的渠道告知。回执字段要写清来自哪个系统、代表哪个阶段。一个 `sent=true` 容易让客服以为客户已经看见，下一次争议就解释不清。

**领导：**如果发完邮件，更新本地状态前进程崩了？

**小陈：**这是经典的“外部副作用不能和本地数据库做同一笔事务”。恢复时看到 `发送中` 长时间不动，不能直接重发。先按渠道消息 ID、业务键或收件人时间窗查询渠道记录；查到已接收，就补本地回执；渠道明确未接收，才能用同一逻辑键重试；查询能力不足或结果矛盾，就进人工核对。客服看到的是“结果待核”，不能收到一个误导性的红色“发送失败”按钮，一点又发一封。

微软的幂等消费者模式特别指出：外部 API 这类不能加入本地事务的副作用，应先记处理中状态，再执行外部动作，重投时对陈旧的处理中记录做核对。它也提醒去重记录要保留足够久，覆盖消息可能重投的时间窗。不能每天凌晨把去重表清空，而死信队列里的旧消息下周还能重放；“清理存储”若没和重放窗口对齐，会把旧道歉信从坟里叫起来。

## 渠道不支持幂等键，就别吹“绝对只发一次”

**领导：**Stripe 都能用幂等键，邮件供应商照抄不行？

**小陈：**Stripe 的文档说明它自己的 API 会按幂等键返回首次请求结果，还会核对参数是否一致；这不能证明我们用的邮件或短信服务也有同样行为、同样保留窗口。接入时逐一查：是否接受调用方键、键保留多久、重复请求返回什么、状态能否查询、回调是否会重复、渠道消息 ID 在何时生成。若供应商不支持，系统只能靠本地去重和查询回执降低重复概率；一旦外部结果始终无法确认，就必须停止自动重试并交人工，而不是许诺数学意义上的“永远恰好一次”。

某些渠道可用可搜索的自定义元数据绑定我们的动作 ID；某些只能按时间和收件人查近似记录。后者要小心：同一客户一天可能合法收到两条不同通知，不能只因号码相同就认定已发。查询规则要结合内容摘要、业务目的和时间窗，仍不能确认就保留未知。未知状态不是工程师难堪的标志，是防止客户收到三封道歉信的必要停顿。

**领导：**那客服急着补发怎么办？

**小陈：**界面显示原动作 ID、提交时间、渠道查询记录、当前不确定之处，并提供“发起人工核对”，而不是直接给“重发”按钮。核对确认原邮件未送达后，沿同一业务动作重试；若原邮件已发但内容有误，则建立新的“更正告知”动作，关联原回执并走审批。人可以决定新业务动作，不能靠换幂等键绕过未知结果。所有例外留操作人和原因，后续能复盘。

## 同一张工单，故障从早到晚各来一次

**领导：**把时间线讲完整，我看看哪里会发三次。

**小陈：**09:00，客服批准草稿版本 4，工单系统提交 `draft_approved` 事件，事件 ID 为 `E-41`。09:01，消费者 A 收到第一次投递，原子插入 `consumer=mail, event=E-41` 和发送动作 `N-17`；消费者 B 同时收到第二次投递，唯一约束挡住它，读取到 `N-17` 并退出。09:02，A 调用邮件供应商，供应商接收并生成渠道消息 `M-99`，但响应在网络中丢失。A 将 `N-17` 标为结果未知。09:03，第三次投递来，消费者 C 看到事件已处理且动作未知，不新建 `N-18`。

09:05，核对任务按业务键或供应商查询能力找到 `M-99`，补录“供应商已接收”的回执；若最终送达回执晚到，再追加渠道状态，不改变“只有一个逻辑发送动作”的事实。若 09:05 查不到，而供应商查不到不代表没发，动作仍停在未知并派给值班客服。客户看到的要么是一封准确通知，要么是对外承诺暂缓；绝不能因为后台心急收到三封互相矛盾的答复。

**领导：**事件处理标志和动作状态要不要在一个事务里？

**小陈：**能在同库完成的部分尽量同事务：事件去重记录、发送动作、内部待办一起提交，避免“记了事件已处理，却没建发送动作”。外部邮件调用不在这个事务里，因此用动作状态与核对补齐。若系统使用事务性 outbox 发任务，也要检查写业务状态与写 outbox 是否同事务；否则“批准了草稿但事件没发”会成为另一类丢单。设计不能只防重复，还要防漏发。

## 上线测试：把每一种坏时机都试出来

**领导：**你给测试团队一张表，别只让他们投递三次。

**小陈：**要覆盖至少八种时机：批准事件重复投递；两个消费者并发处理；本地插入去重记录前崩溃；本地提交后、队列确认前崩溃；邮件服务明确拒绝；邮件服务成功但响应丢失；渠道回调重复且乱序；死信消息在去重记录清理后重放。每个场景都检查动作记录数、实际渠道消息数、客户收到的内容、状态是否可解释、是否有负责人的未知待办。测试用沙箱收件箱和虚构工单，不要向真实客户试发送。

成功指标不止“重复邮件为零”。要看未知状态积压多少、平均多久核清、人工补发比例、渠道回调缺失率、同一事件被检测到的重复次数、客户投诉的重复通知率。若重复率下降，但一堆未知状态没人核，系统只是把问题藏起来。值班页应按未知持续时间排序，超过承诺窗口升级；恢复渠道查询后批量对账，但每张单仍按原业务键处理。

**领导：**技术面试官最后问你：消息队列说支持 exactly once，还要这些吗？

**小陈：**要看“恰好一次”覆盖的边界。队列可能保证自己控制的消息写入或消费语义，却管不了外部邮件供应商已经发送、响应却丢失的事实。消费者按稳定事件 ID 去重，发送动作按业务键和回执核对，才能把实际副作用管起来。重试不是按按钮多按两次，而是用**同一个逻辑动作**在已知边界内继续；结果未知时先查证。客户只收到一封道歉信，比系统自称“重试成功三次”更像成功。

## 幂等键不是护身符，写错了照样翻车

**领导：**既然有键，为什么还会发重复？

**小陈：**键的**粒度**和**寿命**都可能错。若只用工单号，0823 第一次进度通知占了键，第二天真正的处理结论被当重复丢掉；若用当前时间戳，重试每次都不同，根本拦不住。应先定义“什么叫同一封业务通知”，再定键。相同内容不一定是同一动作：客户上午收到进度、下午又按约定收到进度，文字可能一样，但时间和目的不同；不同内容也不一定是新动作：同一封待发邮件在批准前改了错别字，不应让旧版与新版都进入发送队列。

键的保留期还要覆盖可能发生的重放。正常队列最多保留几天，死信队列可能被人工在几周后重投，供应商自己的幂等键却可能只保留更短时间。若本地记录已清、供应商也忘了旧键，历史消息会被当新动作。清理策略应按最长可重放窗口制定，或者在工单业务记录中长期保留已完成动作的唯一标识。需要清历史数据时，先封存重放入口并检查待处理死信。不要让存储优化变成客户的第二封道歉信。

参数也要绑定。假如重试时沿用同一个键，但收件人从客户 A 变成客户 B，系统必须拒绝，而不是把 A 的成功回执返回给 B，或把原内容发给 B。保存动作时记录收件人受控标识、渠道、批准草稿哈希；每次重试校验与原动作一致。真实邮箱、手机号不要直接放进幂等键或日志里，内部可以用受控关联 ID；需要核对时再走权限查询。Stripe 文档对重复键会比较参数，这给我们的是设计启发，不是邮件供应商已实现的保证。

**领导：**我能不能手动把状态从未知改成失败，然后重发？

**小陈：**不能把“不知道”改写成“没发生”。人工核对可以附供应商查询、发送记录或客户确认等证据，得出“明确未发”后改变状态；证据不足就保持未知。若客服确需向客户补充进度，可以创建新的**不同目的**的告知，如“我们正在核对上一条通知是否送达”，并避免重复承诺。状态变更要留操作者、证据和时间。用管理员权限手动涂改数据库是事故扩大器。

## 客户收到三封，说明闸门失守后还要会止血

**领导：**如果已经发出三封怎么办？别只告诉我以后加唯一索引。

**小陈：**先停止该路径的自动发送和队列重试，确认是否仍有待发送副本。用业务动作 ID、渠道消息 ID 和收件人范围找出受影响工单，检查三封是否内容一致、是否包含冲突承诺。客服负责人决定是否主动发一次清晰的更正说明；这次更正也是新业务动作，需要审批和自己的幂等键，不能由原故障路径自动补发。再按时间线定位重复从哪层进来：生产者发了三个不同 `event_id`，消费者没做唯一约束，还是外部超时被错误当失败。每层修法不同。

事故期间报表不要只写“邮件发送成功 300%”。要把独立客户数、逻辑动作数、供应商接收数和真实送达数拆开；重复外发归入服务质量与渠道成本。复盘加入永久回归用例，让下次发布故意重放相同事件、打断响应、并发消费。若系统后来补录了正确回执，也不能删除当时重复发送的历史；事实留着，修复才能被验证。

**领导：**如果供应商接口既不支持幂等，也不支持查消息呢？

**小陈：**这种渠道的未知状态无法安全自动重试。业务要么接受人工核对与更保守的发送策略，要么换具备回执能力的供应商，要么调整客户承诺，不能由工程师用“超时就重试”替业务承担重复外发风险。发票入口通知可能容忍一次遗漏后的人工补发，退款确认、法律通知等高后果消息要求更严格的渠道选择。技术架构要把渠道能力差异明确交给产品和业务决策。

上线前还有一道运营验收：让值班客服拿着一张 `结果未知` 的测试单，在不问工程师的情况下说清这条消息的原业务目的、原批准版本、首次提交时间、目前能查到的渠道证据、下一次核对时间和升级人。如果工作台只显示“发送异常，请重试”，技术上再漂亮的幂等表也会被人的点击绕过。系统应把“查询原发送结果”放在主要位置，把“创建新通知”做成明确的、有原因和审批的独立操作。

**领导：**同一事件重复投递本来就是队列正常现象，为什么客服要知道？

**小陈：**客服不必知道队列的每次投递，但要知道对客动作目前是否确定。工程面板看 `event_id`、重复次数、消费租约和渠道回调；客服面板看“这封通知是否已确认发出、要不要继续处理客户”。两边共享同一逻辑动作 ID，排障时才能对上。运营不需要被消息中间件的术语淹没，也不能被一个假的“失败”按钮诱导重复发。

对技术面试再补一句：幂等不是“操作只执行一次”的魔法，而是**相同逻辑请求重复出现时，最终效果仍按一次计算**。对于本地数据库，唯一约束与事务能守住边界；对于外部邮件，必须结合供应商能力、回执查询和未知状态处理。把边界说清，比背一句“加个 Redis 锁”更像真正做过线上系统。

小陈把这条规则贴在发送按钮旁：**不知道第一封是否发出时，先查第一封，别急着造第二封。**这不是拖延客户，而是把下一步交给能核对回执的人；核对有期限、有人负责，才算真正可靠。

**领导：**发送平台第一次回了超时，第二次回了成功，客户却收到三条，怎么追？

**小陈：**以稳定发送意图 ID 关联所有尝试、平台消息 ID 与客户收件记录，检查是否重试换了新键、队列是否重复投递、平台是否异步成功。先停止该渠道自动重试并核影响客户，再修去重和回执查询。只按“第二次成功”结案，会把第一次和第三次送达藏掉。
