**领导：**续约助手昨晚失败，今天重跑就好了。你怎么把发送按钮封起来了？

**小陈：**失败的是我们没拿到回执，邮件可能已经发出去。再跑一次如果从头发送，就是把一次不确定变成两次确定打扰。恢复得先认清现在处于什么状态，不能把“重新启动”当万用创可贴。

本文使用**教学虚构**的星河制造续约流程。原流程只生成内部草稿；为了讲外部结果不明，后半篇假设业务另外批准了一份具体草稿的发送，并有发送服务执行。批准、发送与续约准备分别记录，不能因为读到本篇示例就把前面三路研究的权限扩大。所有状态名与事故数据用于说明设计。

## 一、先把“失败”拆开，不同情况不能吃同一颗药

**领导：**错误码都是五百，哪里不一样？

**小陈：**模型请求失败、合同读取超时、证据不满足、权限拒绝、父流程取消、发送后回执丢失，恢复办法完全不同。HTTP 错误只是观察，不是业务结论。一个服务端五百可能发生在动作执行前，也可能发生在执行后生成回执时。

读取型任务如果暂时无法连到资料服务，可以有限重试；权限不足应返回阻断，不应该换模型继续尝试绕过；输出结构错误可以要求修正或按规则重试，但仍记入任务质量；来源存在冲突则需要补证据或人工确认，重跑同一查询未必增加信息。把这些统一叫`failed`，主流程就无法决定继续、暂停、回退还是求助。

外部动作更特殊。客户端超时只能证明我们没有在期限内收到完整响应，不能证明动作未执行。对“创建商机”“更新报价”“发送邮件”等请求，要有`unknown`这种明确状态。未知时先查业务回执或动作 ID，不能让一个重试框架无条件再次执行。真正安全的重试取决于幂等语义与受控动作账本，而非请求动词看起来像 POST 还是 GET。

失败分类应写进结果信封：错误类别、可否重试、已知副作用、缺失条件和建议恢复点。可重试标记不能由模型任意设定，而由工具适配器和业务规则判断。模型可以说明它看到的现象，运行时根据接口保证与动作记录作决定。

## 二、状态机比一句“已失败”更能救命

一项只读研究可以经历`pending→ready→running→succeeded`，也可以进入`retry_wait`、`blocked`、`timed_out`、`cancelled`等终态或等待态。执行完成之后还有验收：拿到输出不意味着进入`succeeded`。对于动作任务，额外有`authorized`、`submitted`、`unknown`、`confirmed`等状态。两类任务不应共用一个过于简单的成功字段。

**领导：**状态这么多，会不会把流程搞复杂？

**小陈：**实际情况本来就多。少写状态只会把复杂性藏进判断代码和人脑。每个状态要说明进入条件、允许的下一步、谁能迁移以及超时怎么处理。没有动作的“等待人工确认”与“正在执行外部发送”必须分开，否则重启后无法知道该通知人还是该去对账。

状态迁移要以持久事件或原子更新为依据。任务从就绪进入执行时，记录有效尝试与执行租约；结果通过验收后，提交工件引用和成功状态，再解锁下游。不能先告诉下游“成功”，后写证据文件；如果进程在中间倒下，下游会读到不存在的资料。数据库与对象存储不能天然跨服务原子提交时，要使用可验证的工件提交协议或重试协调，避免半份结果被看成完成。

业务总体状态与分支状态也分开。三个分支中两个成功，一个阻断，整体是“缺必要证据”；不是把成功数除以三，写“完成百分之六十七”就能交给销售。进度可以报告，业务条件仍需要满足。异常终态里应保留已经取得的合格资料，让后续只补缺口。

## 三、租约、尝试与 fencing：防止两个人都以为自己接了单

队列可能重复投递，工作进程可能在租约过期后仍活着，网络恢复后还会发回结果。只有任务 ID 不足以识别当前合法执行者。我们为同一逻辑任务建立递增尝试或租约代次，由持久任务服务签发。完成写入时检查代次是否仍有效，不接受已经被替换的执行者回传。

**领导：**旧执行者已经结束了，为什么还要拒绝？

**小陈：**我们只观察到它超时，不知道它真的死了。比如合同研究第一次卡住，第二次读到新版本并完成；第一次随后拿着旧合同回来。如果只看任务 ID，它会覆盖新结果。fencing 的作用是在提交端挡住失效执行者，让旧结果不能推进主流程。

下面是**任务提交伪代码**，真实实现需要在存储事务内完成条件检查与写入：

```python
def commit_result(task_id, lease_epoch, artifact):
    with transaction():
        task = load_for_update(task_id)
        if task.lease_epoch != lease_epoch:
            return "stale_attempt"
        if task.status != "running":
            return "not_accepting_results"
        validate_artifact(task, artifact)
        task.artifact_ref = artifact.ref
        task.status = "succeeded"
        persist(task)
        append_completion_event(task)
    return "accepted"
```

它解决的是应用结果提交一致性，不会自动取消已经发送到第三方的动作。如果失效执行者已经向邮件服务提交了请求，任务数据库拒绝回传也无法把邮件收回来。外部写入必须另有幂等键、授权与动作状态检查。不要把“我们有租约”解释成整个世界都遵守这把锁。

租约续期还需要明确允许时长。工作单元不停续租可能永久占住任务；父流程取消时，续租应被拒绝。任务恢复时检查已经保存的工件、有效租约和业务截止时间，不能只看进程列表。工作进程与业务状态由不同系统观察，判定依据必须落在可持久、可审计的任务记录上。

## 四、检查点保存的是运行状态，不是时间机器

**领导：**LangGraph 有 checkpoint，直接恢复就不会重复了？

**小陈：**它能保存图状态并支持继续，但没有承诺把数据库、邮件服务器和模型调用全部回到某一秒。检查点告诉我们图走到哪里、有哪些已保存结果；外部世界需要自己的账本和对账。

[LangGraph 的 Checkpointers 文档](https://docs.langchain.com/oss/python/langgraph/checkpointers)说明检查点按线程保存图状态，成功分支的 pending writes 可以帮助在同一超步失败后恢复时避免重跑已成功节点。持久化模式也有性能与耐久性的取舍。应用仍要选择合适的生产存储并验证恢复行为；内存 saver 仅留在进程内，断电后不会自动变成持久数据库。

恢复不能假定从 Python 某一行接着执行。框架可能从节点或步骤边界重进，节点中前面的代码因此有机会再次运行。读取资料可以按规则重做，创建业务记录则要能识别已发生动作。把副作用放进可识别、可幂等的工具边界，并记录回执，才能与检查点形成闭环。裸写“先发邮件，随后保存状态”的节点，最危险的窗口就是两步之间。

检查点至少关联运行 ID、状态版本、图版本、模型与提示版本、工件引用及审批绑定。原始资料未必都需要复制进状态，但引用必须能定位到这轮所用版本。依赖外部可变链接时，要知道恢复后能否读回相同证据；若不能，标记重新核验，并使受影响草稿失效。状态恢复成功不等于业务资料仍然有效。

## 五、局部重试，怎样保留已经做好的两路工作

假设客户事实与服务工单都完成并通过验收，合同服务暂时失败。恢复点应是合同任务，不是整项续约从头重跑。主状态保留两份证据及其版本，合同分支使用同一个逻辑任务 ID、新尝试编号和剩余预算。待其通过校验后再汇流。这样避免重复检索、重复花费和新旧资料混合。

**领导：**资料可能变了，要不要全部重查？

**小陈：**看快照与有效期。若恢复发生在同一短时间窗口且业务允许原证据继续适用，可保留；若工单已经关闭、合同变更或审批失效，就按依赖关系重新核验受影响分支。重用是带条件的，不是永远信任旧结果。更新后的证据可能触发重新写作与重新审核，不能把新资料偷偷塞进已经获批的稿件。

重试策略也要保留原因。网络瞬断可以有限退避；连续输出无来源，不一定靠五次同样提示解决，需要改任务输入或检查检索路径；权限拒绝不进入自动重试队列。重试次数、累计耗时和费用都属于原逻辑任务，不因新尝试清零。父任务已超时或取消时，不再启动重试，保留具体未完成项供人工处理。

我们可以为反复失败的任务设置隔离队列。它保留输入引用、错误类别、尝试历史、已完成工件和需要的恢复条件。人工修复资料或配置后，显式创建恢复尝试。隔离不是静悄悄丢弃，也不是每分钟自动敲一次坏接口；系统要让业务知道这项任务为什么不能继续以及谁可以解除阻断。

## 六、外部动作未知，先对账，再谈再次执行

**领导：**邮件工具超时，用户等着呢。重试一封总比没发好。

**小陈：**如果是报价承诺，多发一封旧版本可能比没发更麻烦。我们先看动作账：这个客户、这个草稿版本、这次批准对应哪项发送。有没有供应商动作 ID、幂等键、已受理记录或最终回执。不能把“没看到成功”写成“已确认失败”。

动作幂等键要表达业务身份，而不是每次随机生成。比如运行、动作类型、目标客户、批准的草稿版本共同确定这项逻辑动作。重试保持同一个键，并校验请求正文哈希；同一键下不能换成另一版报价。供应商若明确支持该范围与期限内的幂等请求，才按其保证使用；如果不支持，应用需要受控提交与权威查询，仍不能凭本地去重宣布跨系统 exactly-once。

一个常用辅助是 transactional outbox：在同一业务数据库事务里保存已授权动作与待投递事件，再由投递器发送。这样避免业务状态已写而消息没入队。但投递器仍可能重复发送，因此接收侧幂等或动作识别仍重要。outbox 改善本地事务与投递之间的可靠性，并不让所有外部系统自动只执行一次。

发送状态还可能有多个层次：本地待提交、供应商已受理、供应商已投递、用户是否收到或阅读。业务需要哪个证明，就记录哪个。不能拿“请求受理成功”宣布客户已看到，也不能在缺少最终回执时抹掉已经受理的事实。对账达到期限仍无法确认，转人工带出已知动作记录与推荐核对路径，不让人工也从头猜。

## 把事故按分钟走一遍，恢复记录才知道该补哪一步

**领导：**你拿这次超时从头走一下，别只说原则。

**小陈：**九点零一分，三路证据通过验收，草稿第六版进入审核；九点零五分，有权限的人批准该客户与该版本的邮件；九点零六分，动作账写入待提交，发送服务返回受理 ID，应用保存最终状态前掉线。这时业务任务恢复后应读取第六版的批准与动作记录，查询那个受理 ID，不能再创建第七版并沿用旧批准，也不能另造幂等键重新发送。

若查询确认已投递，记录外部状态和时间，再关闭该动作；若确认未受理，检查批准、正文哈希和接口幂等保证仍有效后重投同一逻辑动作；若查询仍无法确定，保持未知并按期限升级人工。人工拿到的是受理 ID、目标、已批准正文、最后观察时间和已做的核对，不是一句“请帮忙看看邮件发了没”。动作状态变化可以结束发送任务，但不会自动宣布客户已经接受续约。

在这个过程里，研究进度不用重来。若恢复时发现合同政策更新，系统先标记相关草稿不再适用；已经外发则进入更正评估，未发则撤销或重新审核。可见，一次恢复可能同时有“发送确认完成”和“内容需更正”两条状态。我们不能用一个绿色灯吞掉它们。准确恢复是在每个责任域里确认已有事实，再推进合法下一步。

## 七、补偿不是撤销键，已经发生的事要正面处理

如果错误草稿已经外发，技术上可能无法撤回。恢复需要业务更正：停止后续动作、定位受影响客户与版本、请有权限的人确认更正内容、按受控流程发送更正，并记录关联。补偿动作本身也需要幂等和回执，否则更正邮件又会重复发送。

**领导：**那 Saga 可以自动回滚？

**小陈：**Saga 的补偿通常是业务上的反向或修复动作，不是把所有服务恢复成从未发生。取消已创建任务、恢复可逆字段、通知错误承诺的更正，分别有不同前提。已经被客户读到的价格不能靠删一条 CRM 记录消失。补偿方案要由业务定义并经过审批，系统负责可追踪地执行。

每个可写动作在启用前，都该有失败与补偿说明：动作是否可撤销、如何判定执行结果、补偿是否需要人工、补偿失败怎样升级。不能等事故发生才问模型“请想一个办法”。跨系统动作越多，越需要把不可逆步骤放在明确验证与批准之后，减少需要补偿的范围。

补偿也可能只覆盖一部分。CRM 字段恢复成功，客户更正尚待审核，整体应标明“技术恢复完成、对客处理待完成”，不能一概写恢复成功。技术状态与业务损害处理分开记，后续复盘才能知道事件真正何时关闭。

## 八、取消后还回来的结果，不能偷偷复活任务

父流程取消时，发出取消信号只是第一步。我们还要停止新派发、停止租约续期、标记哪些任务的结果不再接收，并处理正在运行的工具。只读查询可以尝试停止；远程动作若已经提交，则进入结果确认流程。取消不能作为清空动作账的理由。

分支回传需要检查父运行的接收状态。已取消的续约草稿不应因为最后一项研究完成而自动转成待审；被新客户请求替代的旧运行也不能覆盖当前页面。晚到但有价值的只读资料可以作为历史工件保存，是否用于新运行要重新验证对象、时间和权限。保存历史与推进当前流程是两种操作。

**领导：**用户只是改了目标，比如不续约了，旧研究还用得上。

**小陈：**可以复用经验证的资料，不复用原任务的决策状态。目标变化相当于业务修订，新运行继承什么、重新查什么、原批准是否失效都要明示。系统不应把“研究客户”与“批准发送续约方案”混成同一个可继承状态。

## 九、更新代码后恢复旧任务，版本也可能来捣乱

长任务恢复时，图结构、协议字段、提示与工具都可能已更新。旧检查点的`risk`字段是字符串，新代码要求结构化风险列表；旧任务允许两类来源，新策略已经禁止其中一类。直接套用新代码读取旧状态，可能报错，也可能更危险地不报错但解释不同。

恢复策略可以是用兼容版本继续旧任务，或通过明确迁移将旧状态转换后再继续。迁移记录输入版本、输出版本、变更字段和失效判断；影响审批与证据含义的变更通常需要重新核验。模型版本升级也可能改变输出行为，不能把旧运行剩余部分自动换模型后继续沿用原质量结论。

部署时保留正在运行任务的版本归属，逐步将新任务导向新版本。旧版本退出前确保任务已完成、迁移或明确终止。工具凭证和权限策略有更高优先级：被撤销的权限不能因为旧代码仍在运行而继续有效。因此执行前和读取时都要核对当前授权，不把版本固定当绕过安全更新的理由。

## 十、恢复能力怎样验收

| 故障注入 | 应出现的结果 | 不能出现的结果 |
| --- | --- | --- |
| 合同分支断线 | 仅重试缺失分支，保留合格资料 | 全部任务重复派发 |
| 旧尝试晚到 | 记录失效回传，当前状态不变 | 旧合同覆盖新证据 |
| 写工件后进程退出 | 恢复时验证完整工件并继续 | 半文件被视为成功 |
| 发送受理后回执丢失 | 未知状态与权威对账 | 直接再发新请求 |
| 父流程取消 | 停派发，晚到结果不推进流程 | 已取消任务自行复活 |
| 协议升级后续跑 | 兼容恢复或明确迁移 | 静默误解旧字段 |

这些是测试预期，不是本文已在真实生产中取得的成绩。项目应在可控环境注入故障，核对任务表、工件、外部动作记录和最终业务产物。恢复测试不能只检查程序没有崩溃；要检查客户没有重复收到动作、合格证据没有丢、未知状态没有被冒充成功。

**领导：**最后一句，恢复到底恢复什么？

**小陈：**恢复的是完成目标所需的合法进度。我们保留已验证成果，重新取得失效资料，识别已经发生的动作，明确未知与需要人处理的部分。进程重新站起来只是开始，业务状态重新可信才算完成。

下一篇解决另一种更安静的事故：程序全部成功，几个审查 Agent 也全部通过，草稿却仍然引用了错价。权限、独立核验和端到端评测要一起上场。

## 长会话恢复的进一步实现

检查点恢复之外，历史太长需要压缩时还要保住目标、否定条件、工件版本与未完成事项。[长会话压缩与恢复]({{ '/posts/2026/09/30/me04-compaction-and-resume/' | relative_url }})把摘要、结构状态和动作账本分开保存，展开预算触发、快照发布与旧版本迁移。
