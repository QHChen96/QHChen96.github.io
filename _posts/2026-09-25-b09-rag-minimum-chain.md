**领导：**我已经把《售后规则.pdf》拖进去了，Agent 怎么还说“按一般经验可以退款”？

**小陈：**因为“上传成功”只说明文件到了某个地方，不说明它在回答这张工单时读到了哪一条。

**领导：**它不能自己打开看吗？

**小陈：**能不能打开、怎么找、找到了什么，得看我们给它接的检索流程。先拿虚构工单 0823：客户说订单显示已签收，但自己没收到，问能不能退款。我们要找的是**现行的签收争议条款**，不是 PDF 里出现“退款”两个字的任何段落。

## 领导：“RAG 到底干了什么？请说人话。”

**小陈：**RAG 可以理解成“先找资料，再拿资料回答”。就像您开会前让我查制度，我不能说“文件在公司网盘里，所以我肯定会背”。我得打开正确版本，找到管这件事的段落，把出处带回来，再写处理意见。

**领导：**所以把整本 PDF 塞给模型也行？

**小陈：**资料少、短的时候可以做对照。但制度多、常更新，还混着旧版，通常得先整理文档、拆成可检索的段落，建立索引；提问时检索相关段落，再把**少量带来源的证据**放进本轮上下文。检索可按关键词，也可按语义相近程度，必要时组合；“用向量”不是 RAG 的入场券，找对证据才是。

**领导：**有啥区别？搜到“退款”不就行了？

**小陈：**旧版 FAQ 写“签收异常可直接退款”，现行条款写“先核对签收记录，再由售后判断”。两段都有“退款”，只按字面搜可能把旧的排在前面。检索前要过滤失效版本；回答时还要看这段能不能支持结论。它只支持“交售后核实”，不支持“已退款”。

## 领导：“那你把这单的证据拿出来，别只讲流程。”

**小陈：**处理卡可以这样写。内容是教学用的虚构规则：

| 这一格 | 工单 0823 的内容 |
| --- | --- |
| 客户问题 | “显示已签收，我没收到，能退款吗？” |
| 订单事实 | 系统返回“已签收”；客户称“未收到”，两者构成待核实争议 |
| 命中依据 | 现行售后规则“签收争议需先核对签收记录，再由售后判断” |
| 来源信息 | 文件名、条款位置、生效版本、检索时间 |
| 允许的结论 | 可以说明会核实并交售后，不预先承诺退款 |
| 证据缺失时 | 标“规则未确认”，停止给退款判断，转人工 |

**领导：**模型引用了条款，是不是就一定答对？

**小陈：**也不是。它可能找对段落，却把“可申请”写成“已批准”。所以验收要两关：**检索是否找到了适用依据**，以及**答复有没有超出依据**。我们把现行条款从测试输入拿掉再跑一次，关键退款结论必须消失或转人工；如果它还说得斩钉截铁，问题就露出来了。

**领导：**那旧版、PDF 表格、跨部门资料呢？

**小陈：**这些都是下一层麻烦。今天这篇先把一条证据链打通；旧版过滤、解析错误、混合检索和跨库查询会各自单写。把“搜到一个片段”当“制度已落实”，那是给未来的售后同事埋彩蛋。

**小陈交付的证据链：**每条待审答复都能回到现行来源、适用段落和订单查询结果；任何一项缺失，草稿明确写“待核实”。验收不是看 PDF 有没有上传成功，而是看“问题—证据—结论”三段能否逐一对上。

## 上传 PDF 到客户听懂，中间有六道工序

**领导：**你说上传不等于会用，那文件进系统后到底还要做什么？

**小陈：**先确认文档是谁发布、哪一版、何时生效、适用哪个地区和商品；再解析文本与表格；按标题和条款边界切成可检索片段；建立关键词或语义索引；工单来了检索候选并过滤失效资料；最后让模型基于带来源的适用片段起草，验证结论是否被证据支持。每道都可能出错。文件上传成功只能证明第一步“收到文件”，不能证明表格没解析错、旧版没混进来，更不能证明客户的退款资格。

**领导：**听起来像给 PDF 办入职手续。

**小陈：**对，制度比新员工更需要标生效日期。旧 FAQ 与新政策可能都在知识库里，旧版依然用于历史审计，却不该回答今天的新工单。索引记录文档 ID、版本、状态、适用范围和生效时间；查询时按本单上下文过滤。若规则改了却只替换源文件、旧索引副本还在，Agent 仍会拿昨天的条款说今天的话。发布验证要从真实查询入口查到新版本，而不是只看“上传完成”的绿灯。

## PDF 被拆成段落时，条件最容易走丢

**领导：**把每页切成固定长度不就可以搜索了吗？

**小陈：**可以作为技术起点，但业务条件常跨页。第 12 页写“签收争议可申请售后处理”，第 13 页表格写“需核实签收凭证，例外情况需主管审批”；若只切出前一句，模型会把“可申请”说成“可直接退款”。切分应尽量保留章节标题、条件、例外与表格行列关系；片段可带父章节引用，需要时回取完整条款。过大片段会混入无关规则，过小片段会断掉语义。好坏用真实问题回放判断，不看切块大小是不是整齐。

**领导：**扫描版 PDF 没文字层，怎么办？

**小陈：**要 OCR，再抽样核对数字、否定词、表格列和页码。尤其“不可退款”的“不”如果识别丢了，就是把政策反过来。低质量解析片段要标置信或待人工复核，不进高风险自动答复；业务负责人确认后才上线。检索系统再高级，也无法从缺失或反向的文本里找出正确制度。内容准备是 RAG 的地基，不能只在模型端加一句“请谨慎”补救。

**领导：**那是不是所有 PDF 都要人逐字审核？

**小陈：**按风险分级。退款、资金和法律承诺相关条款需重点核对条件、例外与版本；普通操作入口可用抽样加回放。自动解析结果附原页预览，审核员能对照；变更记录写谁批准上线。若公司没有文档治理，先限定 RAG 回答低风险问题，把高风险结论交人，别用“文件已经入库”冒充制度已上线。

## 找到“退款”两个字，为何仍可能找错

**领导：**搜索引擎返回五段，分数最高的就给模型？

**小陈：**分数表示检索相关性的一种估计，不是业务裁决。客户问“显示已签收但没收到”，标题《退款入口》很可能高分，却只教他点哪里；《签收争议核查》可能分数低些，才管当前条件。先过滤版本、地区与业务线，再看问题类型、订单状态和条款适用性。关键词检索擅长精确词与编号，语义检索能覆盖同义问法，混合检索可结合两者；具体哪种更好，要用同一批工单看适用条款召回和错条款误入。

**领导：**如果检索到的段落里写“可退款”，模型为什么不能直接回答能退？

**小陈：**要看它的前置条件。也许只适用于未发货，也许需要签收凭证核查，还可能写的是“可申请”而非“保证批准”。检索候选只能提供规则证据，订单是否满足条件仍需订单与售后事实。对 0823，当前系统显示已签收、客户称未收到，结论是进入争议核查；是否最终退款还缺凭证与审批。RAG 把规则拿到桌上，不能替业务系统完成退款审批。

**领导：**RAG 是不是必须用向量数据库？

**小陈：**不是。小规模且有明确编号的规则，用关键词、目录或数据库过滤可能足够；语义问法变化大时，向量召回有帮助。也可两路召回后重排。核心是“从外部知识取回适用证据供回答”，不是某个存储品牌。评测看找对证据、版本过滤、延迟和维护成本；只说“我们用了向量”并不能解释客户为何收到错答。[OpenAI Retrieval 文档](https://developers.openai.com/api/docs/guides/retrieval)介绍了检索流程，但业务适用性仍要自己定义。

## 引用是真的，也可能撑不起这句话

**领导：**模型在“已为您退款”后面加了政策链接。是不是就有依据？

**小陈：**政策链接只能支持“什么情况下可以申请或审批”，不能证明公司已经执行退款。要对每个关键句做证据映射：订单状态引用订单回执，政策处理步骤引用有效条款，审批状态引用审批记录，退款执行引用支付回执。真实存在的链接若不支持该断言，仍是错引。比完全编造引用更危险，因为审核员容易被蓝色链接骗过。

**领导：**引用 ID 让模型自己写，能保证吗？

**小陈：**应用将检索返回的片段 ID 作为允许引用集合，生成后校验 ID 存在、属于有效版本、当前工单有权访问；不存在的拒绝。再看语义支持关系：入口条款不支持退款资格，签收争议条款不支持“已到账”。高风险句子让业务校验或人工复核。引用格式正确只说明“找得到这页”，不说明“这页同意这句话”。

**领导：**如果检索不到现行规则，模型可以按常识补一句吗？

**小陈：**可以解释目前在核查、告诉客户下一步与联系路径，不能凭通用经验给公司政策结论。内部卡标缺证据、查询过哪些版本、谁负责补知识。转人不是“RAG 失败就踢球”，要保留已查订单事实和文档缺口，让客服能继续。上线指标也要看无证据正确停答率；把它算成“回答失败”会诱导系统乱找一条凑上。

## 规则改版当天，RAG 最容易翻车

**领导：**政策负责人刚上传新版，客户问到这条，我们怎么知道系统用的是新的？

**小陈：**发布流程给文档版本和索引构建号，测试从对客查询路径检索，确认新条款进候选、旧版不再作为当前依据。缓存键包含版本或按发布失效；并行索引切换期间，运行记录实际使用哪版。若新旧都被标有效且冲突，先停止自动判断并交政策负责人，别让模型按相似分数选一个。旧版保留给历史审计，但当前工单只用现行有效集合。

**领导：**如果新版 PDF 的表格解析失败，回滚旧版是不是最快？

**小陈：**要看旧版是否仍被业务授权使用。技术回滚索引不等于政策可以回滚；政策已正式生效时，旧版即使容易检索也不能拿来对客。更稳妥的是暂停该题型自动结论，让客服通过原始正式文件核查，修解析并复测后恢复。系统恢复的目标是依据正确政策服务客户，而不是让搜索框先恢复绿色。

## 一张最小评测单，别让上传按钮充当验收

**领导：**给我六道题，明天让团队自己跑。

**小陈：**第一，问退款入口，入口文档应命中但不判断资格；第二，签收未收到，应命中争议条款；第三，未发货取消，不得误套签收争议；第四，旧版 FAQ 更像客户问法，仍须过滤；第五，PDF 表格的例外条件不能丢；第六，适用条款缺失，系统应停答并形成知识缺口。每道记录查询、候选、过滤原因、最终引用、草稿与人工结论。模型版本、索引构建号和政策版本都记上，才能回放。

**领导：**报告里只写“命中率 90%”行不行？

**小陈：**不行。要分检索效果与回答效果。检索看适用条款是否进入候选、过期或不适用条款是否误入；回答看每个关键断言是否被证据支持、是否遗漏限制、是否把申请说成执行。正确证据找到却答错，应修生成与校验；证据没找到，应修内容准备、查询或排序。按题型和样本量报告，别把十个入口题与一个资金争议混成漂亮平均。

**领导：**这次交付能不能比“PDF 已上传”多一句？

**小陈：**可以：客户问题能找到当前适用条款，条款能回到原文件版本，答复的每句关键结论能找到真正支持它的订单或规则证据；缺任何一段就停在明确的人工接手状态。这样客户问“能退款吗”，我们不会用一个上传进度条回答他。

## 检索没错，为什么仍要给客服看原文

**领导：**既然系统能找到段落，还要让客服点开 PDF 原页，岂不是回到手工时代？

**小陈：**不是每单逐页翻，而是高风险或冲突时能快速回到原文。检索片段可能漏标题、脚注或表格上下文；审核卡显示高亮片段，同时提供原文件版本、页码和前后文。客服需要判断“这句可申请”是否受上一段“仅未发货”限制，点一下就能核实。若只给模型转述的二手话，人工审核也会被模型的理解牵着走。对低风险入口咨询可抽检，对退款资格和金额要更严格。

**领导：**如果文档格式变了，页码不稳定怎么办？

**小陈：**用稳定的文档 ID、版本和条款编号，再保留原始文件快照；页码是辅助定位，不作唯一标识。切块时记父章节、字符范围或版面位置，检索片段能回到当时那版原文。新版本发布后，历史工单仍可解释“当时依据的是哪条”；当前工单则按生效版本检索。没有版本化的引用链接，过两周打开后可能已指向另一条内容，审计也跟着穿越。

**领导：**知识库同一问题有两份现行文件，谁优先？

**小陈：**先看职责与适用范围：总政策与地区细则、通用售后与特殊商品规则可能同时有效。文档治理要定义优先级和例外关系；若关系不明或互相冲突，系统列出两份及冲突点，交政策负责人裁决。不能让向量分数决定制度层级，也不能让模型凭篇幅选择“更像官方”的一篇。被裁决的结果要回写知识治理，不让下一个客户再遇到同一冲突。

**领导：**RAG 运行时到底存了哪些东西，出错后怎么查？

**小陈：**保留工单关联 ID、问题改写、过滤条件、索引版本、候选片段及分数、重排结果、最终送入模型的证据集合、输出引用和校验结论。敏感资料按权限存，不把完整客户信息扔进公开日志。排障时先看原文解析正确吗、适用片段进候选了吗、被哪个过滤条件排掉了、模型是否引用了它。这样可以把“搜不到”“搜到了没选”“选了但说错”分开，不会全怪一句“模型幻觉”。

**领导：**如果候选很多，模型读不过来，是不是给它前十条就行？

**小陈：**数量按任务和评测调。前十条可能让重复的退款入口占满上下文，关键例外仍排第十一；反过来只给一条可能缺前置条件。可先用业务过滤缩小集合，去重同一条款的重复切块，重排候选，再为模型提供完整但适量的条款。控制总 token 的同时给输出留空间，必要时分步检索。检索质量不是候选越多越好，而是适用证据和条件能否被模型看见。

## RAG 与“整本塞进窗口”，怎么选

**领导：**现在模型窗口越来越长，干脆把整本 PDF 放进去，省建索引？

**小陈：**若只有一份短而稳定的规则，可以把有效原文直接提供，拿同题回放比较；制度多且频繁更新时，整本放入会增加成本、延迟和旧版混入风险。长窗口解决能装多少，检索解决从大量文件中找到什么，两者并不互斥。即使整本都放了，仍需说明版本、适用范围和每句结论的来源；窗口大不自动把“可申请”变成“已批准”。采购架构前先量检索命中、答案支持、人工改稿和每单成本。

**领导：**向量检索、关键词 grep、混合检索，面试答哪个最好？

**小陈：**没有固定冠军。精确政策编号、商品型号和否定词，关键词常有优势；客户把“门卫代收”说成“保安签了字”，语义召回可能更好；混合方案可兼顾两路，但多一层配置和排序。用相同文档版本、查询集合与标注结果比较适用条款召回、错条款误入、延迟和维护成本。最关键的是先过滤失效文件、保留条件、检查答案支持；检索器名字不能替这些工作。

**领导：**如果模型已经学过通用售后知识，RAG 还必要吗？

**小陈：**公司当前政策、地区细则和临时改版不是可靠地存于模型训练参数里。通用知识可帮助理解“签收争议是什么意思”，不能替公司决定今天这笔单按哪个版本处理。RAG 给当前外部证据，业务系统给订单事实，模型把两者组织成建议；规则缺失或冲突时照样停答。若知识确实很小且稳定，应用也可直接提供受控规则，而不是为了叫 RAG 强装一个向量库。

**领导：**那下一次再有人上传 PDF，你会先问什么？

**小陈：**问这是什么版本、谁批准生效、适用哪些工单、旧版何时退出当前检索、表格和例外是否解析正确、哪组回放能证明客户问题真能找到它。回答不了这些，上传动作只能算资料入库，不能算客服 Agent 已学会制度。领导可以继续拖文件，我负责提醒它先过入职审核。

**领导：**如果解析和索引都对，客户仍投诉答错，下一步查什么？

**小陈：**查实际送入模型的片段、每句答复引用与订单状态。可能检索候选正确但重排丢了关键条款，也可能生成时漏了例外，或发送前没有校验“可申请”与“已执行”的差别。按工单追完整证据链，才能让错误落到可修的一环。

**领导：**这比“重新上传一次 PDF”有用多了。
