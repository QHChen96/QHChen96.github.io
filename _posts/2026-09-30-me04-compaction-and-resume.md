**领导：**它把三天聊天压缩成“客户很重视续约，沟通顺利”。我重启后让它继续，它又从介绍公司开始。顺利的是摘要，掉链子的是进度。

**小陈：**因为我们给它写了心得，没给它留交接。续约助手至少要知道目标、做过什么、证据在哪、什么没完成，以及哪些动作已经发出去。这几类内容可以一起恢复，不能都指望一句自然语言摘要。

本篇使用**教学虚构**的星河制造续约任务。联系人林女士工作沟通默认邮件，草稿第一版已完成，报表口径仍待确认，报价尚未批准。会话包含多次研究、工具调用和修改，超过预定输入预算后需要压缩，中途还可能发生重启。我们给出能缩短上下文、又能核对进度的完整办法。

## 一、先看“忘记”的三种不同现场

第一种是历史不在当前输入里，模型不知道早先的要求。第二种是历史在，但摘要丢了条件，例如把“尚未批准发送”压成“准备发送”。第三种是任务状态与外部系统不一致，模型记得自己计划发邮件，却没有真实回执。三种都可能表现成重复做事，修法却不同。

**领导：**换一个摘要更强的模型，能一起解决吗？

**小陈：**可以提高语言压缩质量，不能替代状态与回执。摘要器再强，也无法凭聊天确定网络超时后邮件到底有没有投递，更不能把不存在的审批补出来。先把程序能确定的东西存好，再让模型整理无法用固定字段表达的背景。

历史存档保留实际发生的输入输出，工作状态表示当前任务位置，动作账本记录具有外部影响的提交与结果。摘要只负责降低阅读成本，可以引用前三者。每层有自己的更新与验证方式，恢复时先读取可信状态，再加载必要背景；不能让摘要中的一句“已完成”覆盖账本里的未知。

还有一个容易被忽略的地方：工具调用消息有成对关系。只保留结果却删掉它对应的调用、只保留调用却没有结果，可能违反模型接口的消息格式或让后续语义混乱。压缩算法既要遵守目标接口协议，也要保持必要来源和因果关系，不能逐条随便截取最短的几条。

## 二、长会话里哪些东西应该常驻，哪些应当搬出去

常驻内容包括当前目标、身份与范围、硬限制、合法当前阶段、必须遵守的事实条件、必要未知。像“只能生成内部草稿”“报价未经批准”“报表口径待确认”都直接影响下一步，不能在预算紧张时删掉。当前联系偏好短而相关，可以放进有效记忆区，注明来源和修订。

大段合同、整页工单和多轮草稿不必反复常驻。把它们保存在可授权读取的工件中，常驻只留定位、版本与用途；下一步确实需要时展开相关部分。工件引用应稳定，不使用会随顺序变化的“上面第三段”。引用解决定位，不意味着工件永远正确，仍要检查来源版本与适用性。

**领导：**以前试过的失败方案呢？全删了会不会又踩坑？

**小陈：**保留会影响接下来选择的失败原因和前提。比如报表查询接口当前没有所需字段，不能只记“查过了”；要留工具版本、缺字段和可用替代路径。暂时网络抖动则记成可重试状态，不把一次超时变成永久工具禁用。

探索中的无关闲聊与已排除分支可以移出当前窗口，但完整历史是否留存仍按用途和保留策略决定。压缩不是偷偷删除数据，也不意味着所有存档都应永久保留。输入优化与资料治理两项工作互相联系，各自需要明确结果与负责人。

## 三、把“当前状态”写成字段，别把流程藏在一段作文里

下面是**教学状态结构**，省略真实业务字段。任务 ID与租户绑定，阶段来自应用允许的枚举，证据与草稿有独立版本。

```json
{
  "task_id": "renewal-42",
  "state_revision": 12,
  "goal": "prepare_internal_renewal_draft",
  "phase": "awaiting_evidence",
  "contact_id": "contact-17",
  "constraints": ["draft_only", "no_unapproved_price"],
  "evidence": {
    "contract": {"ref": "contract-8", "version": 3},
    "report_issue": {"ref": "ticket-19", "status": "needs_recheck"}
  },
  "draft": {"ref": "draft-42", "version": 2},
  "open_items": ["confirm_active_user_definition"],
  "action_ids": [],
  "summary_ref": "summary-42-rev12"
}
```

`state_revision`用于并发和快照一致性，不代表事实一定正确。`phase`只说明程序允许从哪里继续，`evidence`保存观测与定位；工单的当前状态需要恢复时核对。`action_ids`指向已登记外部动作，不能由摘要器根据句子“准备发出”随手填入。

未知项必须有类型。证据缺失、用户尚未决定、接口暂时不可用和权限不足需要不同下一步。全部写成“待确认”会让系统反复问用户本来应由工具查询的事；全部写成“失败”又会让可恢复任务被丢弃。可以在开放事项里保存负责人、原因、下一次读取入口和重试边界。

**领导：**字段越来越多，模型还能理解吗？

**小陈：**给模型的是清楚的任务视图，底层状态可以更完整。程序维护版本、动作和授权，生成阶段看到目标、已知、未知与允许下一步。别让模型替我们在十个数字里猜恢复顺序，也别让它改状态就能改变现实。

状态迁移由事件驱动：证据核验成功，更新相应状态；草稿验证通过，进入等待审核；审核绑定当前草稿版本，才能允许后续发送。模型可建议下一步，应用验证前提后迁移。压缩前后走同一套规则，避免“聊得久了”变成绕过状态机的通行证。

## 四、摘要应该保什么，怎样检查它没把事情压歪

背景摘要保留事件因果、用户明确要求、重要否定、已排除理由和待处理分歧，每条最好能指回来源范围。它不需要重复状态里全部字段，但不能改写状态含义。比如“客户希望本周获得方案”，必须同时保留“尚未批准对外报价”的限制，不能压成“本周发报价”。

**领导：**我给它写“不要遗漏关键信息”，够不够？

**小陈：**还要把关键项列成机器可检查的清单。目标、对象、截止条件、否定、未完成项、已作承诺与动作身份分别核对。摘要生成后和来源、结构状态比较，发现不一致就修正或回退。提示提升倾向，验证确定这次有没有做到。

检验可以包括固定字段比对与主张核验。固定字段如客户 ID、草稿版本和允许动作，不接受模糊改写；自然语言背景按来源检查，不能新增事实。模型审阅可辅助发现遗漏，关键程序条件仍由确定性代码验证。审阅模型可能同样漏掉否定，不能把“二审通过”当绝对正确。

摘要不应不停从上次摘要再总结。几次递归压缩会放大早先遗漏，后来只剩“沟通顺利”。增量整理应结合可访问原始来源和当前有效状态，定期重建重要段落；为每版摘要保存覆盖范围、生成规则版本与引用，使我们能定位丢失从哪一轮开始。

对矛盾不要为了字数删掉一边。写清当前已确认结果，保留尚未解决的分歧；已纠错的旧主张注明不成立或不再用于当前决定，按用途处理历史。摘要是降低理解成本，不是替事实选一个看起来最顺的剧情。

## 五、什么时候压缩，别等请求已经塞爆才抢救

实际预算从模型窗口、输出预留、系统与工具定义、当前状态、近期消息和预计工具结果共同计算。需要保留足够余量，工具返回很长文档时可以先落工件再选择片段，而不是让一条结果撑爆全部预算。压缩触发依据实际 token计量，中文字符数不直接等于 token数。

**领导：**每二十轮压缩一次，简单固定。

**小陈：**一轮可以只有一句，也可以带几万字合同。轮数可作提醒，真正发送前仍要预算检查。余量不足先整理，整理失败再缩减可选材料；必要约束放不下就暂停当前生成并交代原因，不从最老消息开始无差别删除。

压缩本身也有输入容量。很长历史可以按完整事件段整理，段间保留范围和引用，再从源记录生成当前任务视图。每段边界考虑调用结果配对和事件关系，避免把一句修正落到下一段，上一段却独立发布错误主张。分段只是降低处理规模，不降低事实验证要求。

压缩耗时也要管理。对于长期任务可以后台准备候选摘要，正式切换前核对状态修订与覆盖范围；对即将溢出的请求同步生成合格最小摘要。后台基于第十二版生成，第十三版已经改变批准条件，不能因为生成较慢就把第十二版重新设为当前。

## 六、切换摘要与检查点，要有一致的版本边界

把新摘要写好，却在保存状态之前崩溃，可能出现新摘要配旧阶段。先更新阶段，摘要还没生成，又可能旧背景配新决定。我们需要一个明确快照：状态修订、摘要引用、工件版本清单与消息覆盖范围共同说明恢复时读哪一组内容。

同库实现可以在事务内提交状态与摘要元数据；大工件放对象存储时，先保存不可变版本并检查可读，再把引用发布到正式快照。未发布的候选不作为恢复入口。跨服务故障保留可重试记录，不能声称三个远程写调用顺序执行就具有原子性。

**领导：**文件已经生成了，怎么还算没发布？

**小陈：**生成和成为当前恢复依据有区别。恢复入口只指向提交成功的快照，临时文件可以回收或重试。类似草稿写完不代表已经批准。清晰的发布点能避免重启时看见半套东西，误以为只是模型记性差。

下面是**压缩切换伪代码**，表示先读快照、生成候选、验证并按版本提交。`commit_if_revision`需要真实事务或等价并发协议。

```python
def compact(task_id, repo, model):
    base = repo.read_snapshot(task_id)
    sources = repo.load_allowed_sources(base.coverage)
    candidate = model.summarize(
        sources=sources,
        required=base.required_facts,
        open_items=base.open_items,
    )
    repo.validate_summary(candidate, base, sources)
    artifact = repo.save_immutable_summary(candidate)
    return repo.commit_if_revision(
        task_id=task_id,
        expected=base.revision,
        summary_ref=artifact.id,
        coverage=base.coverage,
    )
```

提交冲突后重新读取任务变化，判断是否需要重做摘要，不自动把预期修订换成最新再强写。若生成只是补背景且不涉及变化部分，可以按明确合并规则处理；涉及批准或当前条件则重新核验。冲突处理也是压缩工程的一部分，不能留给模型“自行判断大概没事”。

## 七、重启恢复顺序：先确认这是谁的任务，再确认世界变了没有

恢复入口先校验调用者、租户与任务权限，读取正式检查点及版本清单，验证结构和必要工件可用。过期授权不随检查点复活，联系人与合同关系可能变化，恢复时重新解析当前业务对象。只有这些前提成立，才构建模型继续工作的上下文。

然后核对外部动作账本。尚未提交的草稿可继续编辑；已经提交且有回执的动作按结果更新状态；提交后超时的动作先查外部状态或按原幂等键重试。若服务既无查询又无幂等能力，不能凭摘要里的“没发成”再次执行，应该进入人工确认或受限恢复路径。

**领导：**任务恢复一下，为什么还要查合同？

**小陈：**研究停了两天，合同或审批可能改了。检查点可以保留当时观测，但继续决策前按字段时效复核。稳定背景可复用，动态价格、当前联系关系、权限与工单状态更容易失效。复核范围按下一步依赖选择，不必每次重新做全部研究。

最后从结构状态、有效记忆、摘要与必要工件组装恢复包，明确合法下一步。我们这个案例仍在等待报表口径确认，草稿不能对外发送；恢复后查询待确认事项，再修订内部草稿，不从公司介绍重来，也不把旧计划当成已完成动作。

## 八、LangGraph 的检查点和 Store，为什么都需要但职责不同

[LangGraph Add memory 文档](https://docs.langchain.com/oss/python/langgraph/add-memory)区分线程内状态保存与跨会话长期信息；[Stores 文档](https://docs.langchain.com/oss/python/langgraph/stores)说明长期存储与检查点的用途。任务进度用检查点恢复，联系人偏好可以从长期 Store读取。放在哪个组件取决于范围与生命周期，不取决于哪一个名字更像记忆。

检查点机制可以保存框架运行状态，但工具已经产生的外部效果仍有各自一致性要求。检查点回到某个节点，不等于邮件系统回到过去，也不等于批准重新有效。节点重跑涉及外部动作时，要使用动作身份与幂等约束。框架的恢复能力是应用恢复的重要部分，不能覆盖所有外部事务。

**领导：**我只设一个`thread_id`，是不是能跨会话记住一切？

**小陈：**线程 ID是定位运行状态的键之一，不是身份认证。必须与租户和任务绑定，读取服务验证权限；新的任务也不该为了共享偏好强行沿用旧线程。跨会话的稳定信息用相应 Store范围，线程保留本次任务的进度，这样不会把上一单的批准带进下一单。

生产后端要确认持久性、故障行为、保留策略与升级兼容；开发内存示例不能证明重启可恢复。业务快照还要管理 schema版本。字段增加通常可以兼容，阶段语义改变则需要迁移或明确拒绝旧快照。不能给旧记录补个默认“已完成”，把兼容问题变成业务事故。

## 九、Letta 当前 MemFS，怎样理解“放进文件就记住”

本次核对的[Letta Agent SDK Memory 文档](https://docs.letta.com/agent-sdk/memory)描述基于 Agent记忆 Git仓库的 MemFS：云端备份的 Agent通过提交和推送同步记忆；`system/`下文件每轮进入系统上下文，其他文件按需要读取。这与旧版 memory blocks教程的接口组织不同，使用时必须锁定 SDK与文档版本。

这里的启发是区分少量常驻记忆与大量按需读取文件。常驻内容越多，每轮固定成本越高，也更容易把过期内容持续带入；按需文件减少输入，但需要可靠定位、权限与版本。仓库历史便于追踪，仍需业务事实有效性与撤销策略，Git提交成功不代表客户偏好还适用。

[MemFS 的详细文档](https://docs.letta.com/concepts/memfs)还区分云端备份与仅本地运行：本地 Agent提交到当前机器上的仓库，备份由使用方负责。换电脑要能恢复，不能只看这台机器已经提交。文档也介绍可选的 MemFS Search mod：关键词路径与需要额外索引的语义、混合路径有不同依赖；文件记忆与对话历史搜索是不同对象。检索能力可以扩展，仍要先决定搜哪些合法文件、怎样判断当前有效性。

**领导：**后台 dreaming能不能自动把所有经验整理好？

**小陈：**当前文档有后台整理近期会话的配置。它解决何时整理与如何触发，不保证总结必定可信。来源、主体、当前修订和发布权限仍要验证。个人习惯与组织规则尤其分开，不能让一份自动生成的心得进入全体 Agent的系统文件，变成公司新制度。

共享仓库还会引入并发和冲突。多个 Agent编辑相同文件，要有所有权、合并与发布流程；文件中的外部资料不能因为位于记忆仓库就取得高优先级。下一篇专门处理共享范围与删除传播，这里先明确文件记忆也需要完整工程责任。

## 十、从压缩后重复劳动，定位到具体缺口

**领导：**压缩后又问客户已经回答过的问题，应该看哪里？

**小陈：**先查源消息是否保存，已确认答复是否进入工作状态或有效偏好，再看摘要覆盖与恢复包是否包含。状态有值但模型仍问，是使用环节；摘要遗漏且来源可读，是整理环节；原始消息不存在，就不能靠摘要器复原，得补记录或明确重新确认。

恢复后动作重复执行，优先查动作 ID和回执，而不是调整摘要语气。恢复后用了旧联系人，查业务关系刷新与范围解析；草稿恢复版本错误，查工件清单和快照提交；未知被压成已解决，查主张校验。问题拆到这些环节，工程人员能拿具体记录复现，不靠猜模型心情。

压缩前后可以回放同一个下一步请求，比较关键事实覆盖、允许动作与实际输出。长窗口原始请求作为参照，也要验证它本身没有用旧事实；不能把“完整历史答案”默认当真值。明确真值来自任务状态与权威来源，压缩质量看是否保留这些必要信息。

测试还包括在候选摘要生成后、发布前、状态提交后人为中断，再恢复。预期恢复入口只指向完整发布的版本；外部动作未知进入核查；失效授权被拒绝。测试这几处具体故障即可证明主要一致性边界，不用为了显得严格把所有语言风格再重复测一遍。

## 十一、换了代码版本，旧交接单还能不能用

恢复服务首先读取快照的结构版本，再决定兼容读取、迁移或暂停。假设旧版阶段只有“准备中”，新版细分成“证据不足”和“等待审核”，不能直接把旧阶段映射到等待审核；必须根据证据完成标记、草稿验证结果和批准记录判断。迁移处理缺少依据时，保留待核验阶段，比补一个最方便的默认值稳妥。

**领导：**快照升级也要像数据库升级一样管理？

**小陈：**对，因为它决定接下来做什么。新增可选字段容易兼容，改变动作语义或批准绑定更需要显式迁移。迁移记录原快照引用、转换规则版本与结果，检查工件仍可读取；失败可回到旧运行或受限恢复，不要覆盖原快照再发现新代码读不懂。

摘要规则升级也不能直接使旧文字取得更高地位。新的摘要要求保留报价限制，而旧摘要没有这个字段，恢复时应从结构状态和原始依据补齐；源记录按策略已经不存在，就说明依据缺口并重新核验。不能为了让迁移顺利，让模型编一条看起来合理的限制，或把缺字段解释成没有限制。

工件引用还有完整性问题。草稿保存后如果可被原地修改，快照中的版本号可能指向已经变化的内容；使用不可变工件版本或内容校验值，读取发现不匹配则拒绝依赖该版本继续。外部业务对象无法固定时保留观测版本与时间，恢复重新核对当前值。这样一份交接单既能定位资料，也能发现资料已被替换。

升级验收选择一个确实会继续执行的旧任务，核对它的目标、未知、允许动作与下一步，而不是只测试 JSON解析成功。会读只是兼容的一半，会继续做对才是恢复的结果。相同快照在迁移前后关键约束一致，新增核验不会造成重复发送，才能开放新运行读取这批历史任务。

## 十二、给接手的人，也给接手的 Agent 一份合格交接

合格交接里当前目标明确、下一步可执行、未知有负责人、事实有出处、工件有版本、外部动作可查询。长篇聊天不再是唯一交接载体，摘要也不承担它无法证明的内容。恢复包可以对人显示简洁视图，对运行服务保持完整字段，双方读的是同一组正式状态。

**领导：**最后它还会不会说“沟通顺利”？

**小陈：**可以写感想，接着必须写事实：草稿第二版已验证，报表口径待确认，报价未批准，当前默认邮件联系，无已提交发送动作。这样领导一句“继续”下去，系统知道先核验报表再更新草稿，不会把“顺利”当成万能进度条。

这一篇交付的是结构状态、摘要校验、预算触发、快照发布与恢复顺序。我们已经解决压缩后丢进度的问题；下一篇把视角扩到多 Agent：研究员、写作员与审核员共用一份记忆时，怎样共享真正有效的事实，同时让私有资料不串客、撤回内容不反复复活。
