**领导：**订单接口偶尔超时，客户还在等。Agent 总得说点什么吧？

**小陈：**刚才它说“正在派送”，依据是接口超时。按这个逻辑，天气预报打不开，也能断言外面晴空万里。

**领导：**那只能回“系统忙”？太敷衍。

**小陈：**可以把**已知**说清，把**未知**标清，再给客户具体的下一步。工单 0823 的已知事实是“我们收到查询请求”；未知是“当前物流状态”；可说的话是“订单查询暂时不可用，我们已记录这次查询并转交客服，核实后在约定渠道回复”。绝不把“没查到”改写成“没发货”，也不编“正在派送”。

**领导：**系统可能一秒后就好了，转人工会不会太早？

**小陈：**只对**查询这种只读、可安全重复**的调用，在总响应时限内做有限重试，比如一次短重试；连续故障就停，避免所有工单一起挤爆订单系统。[微软的重试模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/retry)提醒我们要区分瞬时故障和持续故障，并控制重试策略。发消息、退款这类写操作不能套用“查单重试”规则。

**领导：**之后恢复了呢？

**小陈：**故障工单带 `order_lookup_unavailable` 标记、查询时间、请求关联 ID，进入补查队列。恢复后后台只读复查；若已经有客服接手，先更新内部卡片，不自行给客户补发一条可能重复或过时的消息。客服看到真实结果和故障期间那句承诺，再决定是否对外更新。

**领导：**今天给我一条验收线。

**小陈：**拔掉订单接口跑三种工单：未发货、已发货、状态未知。Agent 对三者都不能编具体物流；客户收到的是“查单暂不可用 + 已记录 + 后续渠道”，客服工作台能看见故障和待补查；接口恢复后只补事实，不自动重复外发。这样客户没有被晾着，也没有被我们瞎安慰。

## 超时是“我没听见”，不是“对方没干活”

**领导：**订单查询又不是退款，超时到底有什么好纠结的？

**小陈：**查询本身通常没有业务副作用，但它的**结果**仍不能瞎填。超时说明调用方在期限内没拿到可靠响应，可能请求没到订单系统，可能系统查完了但响应丢了，也可能还在排队。三种情况在客户端看起来都是“等太久”。所以 Agent 不能把超时解释成“订单不存在”“未发货”或“正在派送”。这些是订单状态，必须有对应的订单系统回执和查询时间。

在 0823 号工单里，Agent 已经知道客户说“显示签收但没收到”，也知道这是一张已核验身份的售后单；它不知道**当前**订单状态。已知和未知要分字段存，不要写成一段顺口的“系统正在查询，您的包裹应该正在派送”。这里的“应该”一旦被客户截图，就变成公司给了错误状态的证据。安全的答复也不能只说“系统忙”，因为客户还需要知道问题有没有被记录、谁继续查、何时有下次更新。

**领导：**如果昨天查过“已签收”，今天接口坏了，能不能先用昨天的数据？

**小陈：**可以说“昨日 16:02 的查询显示已签收”，前提是时间与来源清楚，并明确“当前状态暂时无法核实”。不能去掉时间，写成“订单已签收”。是否适合展示旧数据还要看问题：查询商品规格，昨天的结果可能仍有参考价值；查实时物流、退款或风控状态，过期一分钟都可能误导。缓存不是天然的兜底答案，它要带抓取时间、最大允许陈旧度和适用场景。超过限制，就只显示“上次记录”并转人或待补查。

## 重试预算要算总时间，不是每层都试三次

**领导：**你说“一次短重试”，为什么不是三次？

**小陈：**因为客户等的是整次答复，不是某个函数返回。假设对话服务愿意花五秒查证，其中模型判断已花一秒、工具调用第一次花两秒、生成答复还要留一秒，那剩余只有一秒，根本容不下三次两秒重试。把总截止时间从入口传到工具层，工具层只在剩余时间足够、故障像瞬时问题时重试。数字只是示意，实际预算要看生产延迟分布与服务承诺。

还要防“重试套娃”。模型调用层重试两次，工具 SDK 默认重试三次，网关又重试两次，看起来每层都很克制，最坏可能打出十几次请求。小陈要把重试职责放在明确的一层，或者至少把各层预算合在一起；请求带关联 ID，观测能看出一次客户问询到底打了订单系统多少次。订单系统本来就忙，Agent 集体重试会像一群人挤在坏电梯门口，不会让电梯修好得更快。

微软的重试模式也区分取消、立即重试和延迟重试；对持续故障，过度重试会增加负载。实现时按错误类型决定：明确的权限不足、订单号格式错误不重试；短暂网络断开或限流可在预算内退避；连续故障则熔断或快速失败，给客户准确的降级答复。每种工具有自己的策略，不能把查订单和申请退款放进同一个“自动重试三次”装饰器。

**领导：**熔断以后是不是所有客户都查不了了？

**小陈：**熔断不是关掉客服，而是订单接口连续失败时暂时停止无意义请求，过一段时间允许少量探测，成功后恢复。客服系统仍能收消息、建待办、查看此前有权限的记录；不能依赖实时查单的答复进入降级路径。不同租户、地区或接口可能故障范围不同，要按真实故障域熔断，不要一个地区慢就让全国都失明。技术面板看错误率和探测，客服面板看哪些工单待补查。

## 客户话术也要分三格：事实、限制、动作

**领导：**说“暂时查不到”会不会显得我们没能力？

**小陈：**比编状态强。对客话术可以是：“我们已收到您查询这笔订单的请求；订单系统当前未返回最新状态，所以我暂时不能确认是否派送或签收。工单已交由客服核查，我们会通过当前会话在今天服务时段内更新。”这段话有三部分：确认已发生的事，说明无法确认的边界，给出有人负责的下一步。最后的更新时间要来自公司的服务承诺与排班，不是模型现编。

如果客户问“那我现在能申请退款吗”，Agent 不能把查不到订单当成“可以退款”，也不能把故障当成“不能退款”。它可以解释“退款资格需核对订单和现行规则，目前查单不可用，已为您登记人工核实”，并保留客户明确提出的退款诉求。若客服系统有独立可用的退款申请入口，是否指引客户使用，要按业务规则和身份条件决定；不能假设所有接口同时坏，也不能假设另一个接口的结果能替代订单状态。

**领导：**客户连续催三次，系统要不要每次都建一张补查单？

**小陈：**不要。按 `case_id + lookup_purpose` 聚合仍未完成的补查动作，客户新消息追加到原工单并更新紧急程度；同一笔未解决的查单任务不因三次催问长出三张。客服能看到客户催了三次，不必重复查三次同样失败的接口。若客户换了订单或问题范围，再建新的补查动作，并保留与原案的关联。去重保证不淹没队列，客户催促的信息仍保留给负责人判断优先级。

## 恢复之后补查，最容易把旧承诺撞翻

**领导：**订单系统恢复了，后台批量补查并自动发结果，不就完了？

**小陈：**先补事实，再决定是否外发。恢复队列里的每条任务有工单 ID、查单目的、故障时间、客户当时的问题、已有客服负责人和最后一次客户消息。补查前重新核身份与工单权限，读当前工单版本；如果客服已经手动查完并回复，任务标“已由人工完成”，不再外发；如果客户改问另一订单，旧任务不能把旧订单结果塞进新对话；如果工单已结案，要看结案原因和是否仍欠一次更新。后台拿到订单状态只是证据更新，不是获得对客发送权。

恢复后的状态也可能与故障前的缓存不同。比如故障前缓存“待发货”，恢复后实时系统显示“已签收”；系统保留两个时间点，让客服解释变化，不要简单把旧值覆盖，导致客户问“你们昨天为什么说没发货”时无从回答。对客户最终回复应基于最新回执、有效政策和已经做出的承诺；若有争议，转人工核对，而不是模板自动说“系统现已正常，您的问题已解决”。

**领导：**补查队列也可能故障。谁发现？

**小陈：**队列每条任务都有负责人或值班组、创建时间、下次尝试时间、最后结果和到期动作。接口恢复后，队列积压应逐步消化，限速避免刚恢复又被洪峰打倒。超出约定更新时间的工单优先升级；重复失败记录原因，不能无限退避到没人看见。监控要看**故障期间产生多少待补查、恢复后完成多少、仍有多少无主或超时、客户承诺履行多少**，而不只是订单接口恢复了绿色。

## 故障桌面演练，领导负责挑最坏的分支

**领导：**我给你四张纸。第一张，查单接口返回 200，但内容是空的。

**小陈：**HTTP 成功只证明传输层返回，不证明有有效业务事实。订单 ID 不匹配、字段缺失、数据时间过旧，都应判为“证据不足”而非“无订单”。工具适配层要校验 schema、本单归属和更新时间，返回给 Agent 的是明确的 `known/unknown/error`，不要把空对象交给模型猜。

**领导：**第二张，模型说“我刚查到正在派送”，但轨迹里没有工具回执。

**小陈：**对实时订单状态的断言必须引用本次有效回执；发送前校验引用 ID 和时间。没有回执就拒绝自动外发，降级为“暂不能确认”或交客服审核。这不是审查模型文采，是防止它把语言概率当物流事实。

**领导：**第三张，订单接口恢复了，客户已经在电话里得到人工答复。

**小陈：**补查任务读取最新工单事件，发现人工已回复，就只更新内部证据与对账状态，不再发第二条。若电话答复没有录入工单，说明人工流程也要补记录，否则自动系统不知道自己该停。

**领导：**第四张，订单查询和退款提交都超时，你还敢说“只读查询可重试”？

**小陈：**两件事分开。只读查单可在预算内有限重试；退款提交属于有副作用的写操作，超时后可能已执行，要按业务键查询回执或交人工核对，不能重发新申请。工具接口必须声明 `read_only` 或 `write`，还要看真实行为，不能因为方法叫 `getRefundStatus` 就假设它无副作用。故障降级策略按动作性质制定，不按接口名字拍脑袋。

**领导：**第五张，接口持续错误两小时，客服队列挤满。

**小陈：**需要运营降级方案：暂停不必要的自动查单，统一给客户准确进度，按承诺到期、投诉风险和业务影响排序待补查；客服优先处理需要人工判断的争议，纯状态查询等待系统恢复后批量只读核对。经理能看到积压与预计处理能力，决定是否增派人手或调整对客更新时间。Agent 在这里负责分类、记录、提醒和草拟，不负责凭空恢复订单系统。

## 验收不是“接口好了能回答”，而是坏时也不会说谎

**小陈：**测试集要包括接口明确成功、超时、限流、权限拒绝、200 空响应、过期缓存、跨订单返回、恢复后状态变化、客服已接手、退款写操作结果未知。每例都检查工具调用次数、总响应时间、对客断言是否有回执、故障待办是否有主、恢复后是否重复回复。用故障注入打断不同时间点，再回放同一工单，确保不会出现“刚刚还说查不到，下一秒又宣称昨天已派送”这种时间线错误。

技术面试若问“重试、熔断、降级有什么区别”，小陈会答：**重试**处理可能很快恢复的单次故障，受总时间与动作性质约束；**熔断**在持续故障时减少无效调用并保护下游；**降级**保证核心服务还能诚实地接单、记录、交接和履约。三者是不同层的动作，不是一句“失败再试”可以概括。领导最想听的也不是术语，而是订单系统坏了之后，客户有没有得到可信的下一步。

## 工具返回值别只给模型一团文本

**领导：**如果 Agent 自己能理解超时，为什么还要改工具接口？

**小陈：**因为“工具返回空字符串”可能是无订单、无权限、超时、上游返回空值，也可能是适配器自己解析失败。让模型猜是哪一种，就是给它编故事的机会。工具适配层应返回结构化结果：`status` 区分 `ok`、`not_found`、`unauthorized`、`unavailable`、`invalid_response`；`order_id` 和已核验的本单引用用于防串单；`observed_at` 告诉我们状态何时有效；`source_receipt` 指向订单系统回执；`retryable` 只给程序参考，不由模型自行决定重试次数。对 `ok` 结果也要校验物流状态属于允许枚举、时间戳合理、订单归属一致。

`not_found` 也不能直接给客户说“您没有订单”。它只说明按当前查询条件未找到记录，可能是订单号输入错误、渠道不一致、身份不匹配或数据同步延迟。客服话术要根据具体错误码和核验步骤决定。`unauthorized` 更不能用反复重试解决；先停自动查询，交给身份流程。`unavailable` 才走短重试和补查队列。错误类型越清楚，Agent 越不需要用语言掩盖系统分不清的事实。

**领导：**这些状态一多，运营能看懂吗？

**小陈：**运营工作台把技术码翻成动作：“本单资料暂无法查询，已进入补查”；“身份未核验，需客户确认”；“订单号未匹配，请复核输入”。底层保留原错误码和回执，值班工程师能定位，客服看的是下一步。技术精度和操作易懂不是二选一。所有对客模板都要标明能说的事实范围，不能把 `unavailable` 翻译成“订单正在派送中”。

## 算一笔故障期间的容量账

**领导：**假设一分钟来一百张查单工单，订单系统已经慢了，你那“一次短重试”会怎样？

**小陈：**如果每张都立即重试一次，下游最多会接到两百次请求，故障更重。要结合全局重试预算、退避抖动、并发上限和熔断状态；不是每个用户都各自“再试一次”。试点可让少量探测请求验证恢复，其他工单先进入有主的补查队列。上游恢复时也限速消化积压，例如按容量分批处理，并优先满足已经承诺更新时间的案件。具体阈值要用压测和服务容量确定，不能凭文章给出一个万能数字。

客服看到的也不是“系统已恢复，所有工单完成”。假如积压一万张，每秒只能安全补查一百张，理论上至少还要约一百秒，现实还有限流和失败；运营应看到剩余量、处理速率和最早到期的承诺。恢复公告和实际清空队列是两件事。客户的每张单都要有可查询进度，避免故障结束后仍有角落里的一张单无人处理。

**领导：**如果订单系统间歇性好坏，熔断会不会来回跳？

**小陈：**探测成功一次不代表彻底恢复。熔断从开启到试探，再逐步放量；观察一段窗口内的成功率和延迟，失败就回到降级。状态切换要记录时间和原因，便于客服知道某条答复生成时系统处于什么阶段。频繁抖动时，宁可延长降级路径的诚实告知，也不要让客户在同一会话里一会儿“马上查到”、一会儿“暂不可用”。

发布前，小陈会把对客模板交给一位不了解技术故障的客服盲读。客服必须能从模板判断：公司目前确定知道什么、不知道什么、客户下一次何时从哪里收到更新、如果过时由谁接手。若只能读出“系统繁忙请稍后”，说明待办和承诺没落地；若读出“正在派送”，说明模板把未知偷换成结论。两种都退回改。

恢复验证还要看一张“最旧未完成工单”。工程师宣布接口成功率恢复后，抽出故障期间最早的一张待补查单，确认它有新的查询回执、负责人的处理动作和客户承诺的履行记录。看最旧的一张比只看平均恢复速度更能发现被队列遗忘的客户。若那张单仍无主，事故就还没结束。

**领导：**这回我懂了。订单系统睡着时，Agent 至少别替快递员宣布已经出门。

**小陈：**它还能把客户的问题稳稳接住，留下可查的待办，等证据回来再说准话。故障时不乱答，恢复后不漏单，才是客服 Agent 的基本功。

值班表上也要写清故障指挥人、客服通知人和补查队列负责人。没人负责的“稍后回复”，本质上还是一句漂亮的空话；客户等的是下一次真实更新。

小陈还要求每次补查都附原故障请求的关联 ID，让值班人能从客户追问一路查回订单接口的错误窗口。若补查仍失败，待办继续归属原负责人并按承诺时间升级，不能因自动任务结束就从客服工作台消失。
