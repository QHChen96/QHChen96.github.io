**领导：**小陈，我昨晚在 Dify 画了五个框：输入、查订单、Agent、审核、输出。看着像五站地铁，为什么日志里有十二次工具调用？模型供应商的账单还以为我们包了一辆车。

**小陈：**画布上的一个框，是工作流的一次节点执行；Agent 框内部可以反复让模型决定下一步，再调用工具，再把结果喂回模型。五个节点不等于五次模型请求，更不等于五次工具调用。您画的是站点图，Agent 节点里还藏着换乘图。先把两层轨迹展开，再看哪些往返该留，哪些应该改成固定节点。

**领导：**别又跟我讲“智能体很复杂”。客户就问“我买的耳机过了八天还能退吗”，把能退不能退答出来，今天上线。

**小陈：**这张工单刚好能测出系统是否真懂业务。订单号、客户身份、耳机类别、签收日期、政策生效版本、拆封例外都可能影响答案。我们的目标是生成待客服审核的解释和引用，不能自动退款。下面的订单和数字是教学示例；Dify 的节点行为以[官方 Workflow 与 Chatflow 说明](https://docs.dify.ai/en/cloud/use-dify/build/workflow-chatflow)和[Agent 节点文档](https://docs.dify.ai/en/cloud/use-dify/nodes/agent)为准。

## 外层画布一条路，里面却能跑好几圈

**领导：**那先说外层。Workflow 和 Chatflow 不就是名字不一样？

**小陈：**两者都用节点画布，交互方式不同。Workflow 从一次输入或触发开始，跑到结果；适合批处理、报告、事件处理。Chatflow 是每条对话消息触发设计好的流程，再由 Answer 节点回复，适合客服追问。领导的耳机问题如果是 CRM 新建工单后的夜间批处理，用 Workflow；如果客户在聊天窗口问完又补一句“我已经拆封了”，用 Chatflow。选错以后常见事故是把每条追问当成全新请求，丢掉经过验证的订单上下文；或者把一次批处理误写成依赖聊天记忆的暗箱。

外层可以这样做：输入客户消息和工单 ID；业务服务核对身份并读取订单；按订单时间查询有效政策；条件节点把资料完整与否分流；资料齐全才让生成节点写草稿；人工审核后由外部客服系统发送。Dify 的[编排文档](https://docs.dify.ai/en/cloud/use-dify/build/orchestrate-node)说节点可以串行或并行，前一节点的变量可供后续读取；并行分支彼此不能直接读对方变量，汇合后才有两边结果。这个限制不是界面小脾气，而是数据依赖：报价计算不能在订单信息尚未到手时假装已经算好。

**领导：**我们不是已经有“查订单”节点了吗？Agent 为什么还要查？

**小陈：**这就要看 Agent 能见到哪些工具。若它同时被配置了订单查询、政策检索和工单读取，且上游只传一句“订单 0823”，它会自己再查。上游查询没有以结构化、足够可信的字段传进去，Agent 可能觉得证据不完整；即使传进去了，工具说明含糊也会让它重复调用。重复查询不一定是“模型笨”，可能是我们把同一责任放在外层和里层两次。先记录每次调用的工具名、参数、耗时、返回摘要和原因，再决定是否移除重复能力。

## 点开 Agent 框，循环长什么样

Dify 的经典 Agent 节点给模型工具使用权，可以选择 Function Calling 或 ReAct 策略。前者利用模型原生的结构化工具调用；后者用结构化提示引导“思考、行动、观察”的循环。两者外观都可能是“一个 Agent 节点”，运行轨迹却包含多次模型与工具往返。[官方节点说明](https://docs.dify.ai/en/cloud/use-dify/nodes/agent)还给出 Max Iterations、Memory、工具配置与输出变量：最终答复、工具输出、推理轨迹、迭代数、成功状态和日志。领导只看最后一句话，自然看不到过程里的十二张小票。

小陈把一条虚构的异常轨迹打印出来：第 1 轮判断缺订单状态，查订单；第 2 轮发现政策字段只写了“售后规则”，查知识库；第 3 轮检索到旧政策和新政策，分别打开两段；第 4 轮再次查订单签收时间；第 5 轮查商品是否特殊品类；第 6 轮遇到模糊措辞，又换关键词检索；直到第 9 轮才写草稿。十二次工具调用与九轮模型推理并不是同一个计数，有的轮次可并发多个工具，有的轮次只分析结果不调工具。实际计费还包括输入、输出 token、工具服务费用和重试。拿“画布五格”当成本估算单位，相当于按厨房门数算一顿饭的食材。

**领导：**那我把 Max Iterations 调成二，不就省钱了吗？

**小陈：**能限制一部分循环，却不能保证任务完成，也不能单靠这一项保证固定账单。一次迭代里可能调用多个工具；工具本身会有外部服务费用和等待时间。把上限改得过低，模型可能拿不齐证据却仍产出一段语气笃定的草稿。把它调得过高，错误参数和低质量检索可能反复重演。正确办法是先给任务定义可验证的证据条件，再按它设置迭代上限、工具超时和总预算。上限命中时标记“未完成待人工处理”，不能把“跑满了”翻译成“验证通过”。

**领导：**你说证据条件，别写成一堆好听的话。

**小陈：**就这张耳机单，至少要求 `order_owner_verified=true`、签收时间不为空、政策版本的生效区间覆盖签收或申请日期（按企业实际条款决定）、商品类别与例外标记都有来源、草稿引用的政策 ID 与查询结果一致。还要明确“满足退货条件”和“退款已执行”是不同状态。Agent 只有在这些字段齐全后写解释；缺一个便生成“缺什么、由谁补、下一步去哪”的待处理结构，而不是自己填想象出来的日期。条件可在外层用 If-Else 节点检查；[Dify 的条件节点](https://docs.dify.ai/en/cloud/use-dify/nodes/ifelse)支持用变量比较并走 IF、ELIF、ELSE 分支。模型可以解释例外条款，布尔校验仍由流程做。

## “十二次”从哪来，按四个账本查

第一本是业务轨迹：工单 ID、客户身份校验结果、订单读取回执、政策版本、人工审核与外发回执。它回答“客户这件事办到哪”。第二本是画布轨迹：节点开始结束、输入输出变量、分支选择、错误、总耗时。它回答“外层哪一格卡住”。第三本是 Agent 轨迹：每轮模型决策、工具名、参数、工具结果摘要、迭代数、停止原因。它回答“框里为什么又查了一遍”。第四本是成本轨迹：模型 token、各工具计费、超时重试、并行调用与缓存命中。它回答“钱是在哪里花的”。四本账用同一个工单 ID 与运行 ID 关联，单看任意一本都会误判。

**领导：**记录全量工具结果不就行了？省得大家猜。

**小陈：**客服订单里可能有姓名、地址、手机号和内部备注。日志需要足够定位问题，但不能把完整敏感结果又存到一套人人可看的排障平台。保留工具名、参数字段名、脱敏参数、结果数量、版本号、哈希或受控引用；真正需要回看内容时按权限去原系统取。尤其检索结果若带恶意指令，原文要被标记为不可信资料，不能因为进了“Agent 观察”就变成系统命令。排查一次工具重复调用不需要复制整张客户订单到公开监控。

小陈做成本拆分：总延迟大致由外层串行节点耗时、Agent 多轮模型思考与工具等待、人工审核等待构成；并行分支需按最长分支计算关键路径，不是把所有时长简单相加。总成本可以先按“每轮模型输入输出 + 每次工具服务 + 检索与存储 + 重试”估，再用运行日志校准。数字不要直接从示例挪到生产，因为模型、上下文长度、工具价格和缓存策略会变。更关键的是每个成本项都要对应业务价值：重复查同一订单零价值，第二次核不同政策生效时间可能有价值。砍掉重复调用，保留必要查证，才是优化。

**领导：**既然外层能查订单和政策，Agent 还有什么必要？

**小陈：**对标准问题可能没有必要。输入字段完整且规则明确时，订单服务加条件分支、模板或普通 LLM 生成节点就够了。Agent 适合下一步无法事先完全写死的任务，例如客户上传了几种不同格式的购买证明，可能要依实际内容选择解析、交叉核验或查特殊条款。即便如此，也要把工具集缩到这一步确实需要的只读能力。把“查询”和“执行退款”同时交给同一个 Agent，只为省两个画布节点，是把价格风险、权限风险一起打包进去了。

## 经典 Agent 和新 Agent，不是一张设置页换皮

**领导：**我今天看到 Dify 又有个“新 Agent 节点”。是不是之前那些限制全过时了？

**小陈：**不能混在一起讲。发文时[官方文档](https://docs.dify.ai/en/cloud/use-dify/nodes/agent)把经典 Agent 与新 Agent 分开：经典节点是模型配工具和策略的循环；新 Agent 节点仍处于 beta，当前只用于 Workflow 应用，运行的是带自身能力与沙箱的完整 Agent。可以邀请已发布 Agent，也可以在节点里从头配置一个。两种节点都可能在画布上只占一格，但配置、状态、预算和可见轨迹的口径需要按所用版本核验。不能把经典节点的某个输出变量名字直接当成 beta 节点一定相同，也不能把 beta 的沙箱能力说成经典节点默认就有。

新节点还有个容易踩的流转点：两个节点即便邀请同一个已发布 Agent，也各自在独立沙箱运行；前一个节点写的文件不会自动飘到后一个。要让后续步骤拿到事实，应声明输出并引用它。官方文档还说明变量作为文本传入 Agent 时有长度截断，较长内容应以文件交接；文件输出也有大小限制。客服场景里，如果上游把一整份售后政策作为长文本直接塞进任务，关键条款可能没传完整。更稳的方式是传政策版本 ID 与受控文件引用，让 Agent 明确读取对应文件，再把“引用的条款 ID、草稿文件或结构化结果”作为输出交给审核节点。

**领导：**邀请的 Agent 后面更新了，旧流程会不会跟着变？

**小陈：**官方说明被邀请的已发布 Agent 更新后，使用它的工作流会跟着取得新能力；若这个节点只想保留当前配置，可以制作副本。生产里这是版本治理问题：不是“复用越多越好”，而是共享 Agent 的提示、工具或模型变化可能影响多个流程。上线前要记录邀请来源、发布版本或配置摘要、工具权限、回归样本。客服退货这一条若受法规或政策强约束，更新后必须回放旧单、新单、边界日期、工具失败四类样本。否则领导周三改了一个“更亲切”的回复风格，周四所有流程都变了，而客服只看见客户投诉。

## 失败和停止，不能被漂亮的草稿掩过去

工具失败至少分三类。订单 API 返回 403，通常是身份或权限不满足，必须停止订单事实判断；返回 404，可能订单不存在，也可能刻意隐藏跨用户订单，需按业务协议解释；返回超时，表示不知道读没读到，不能说订单不存在。检索节点找不到政策，也不等于“政策允许”，应进入知识缺口处理。模型多轮后没有足够证据，应标为待核实。三者对应的客服话术可以都很客气，但工单状态不同：无权访问走核身，资料缺失走补资料，系统失败走稍后重试或人工查证。

**领导：**那重试一次好了，别把问题推给客服。

**小陈：**只读查询可以在限次、短退避和同一工单关联下重试；绝不能把整个工作流从头到尾无脑重放，尤其未来如果里面有“创建退货申请”“发送邮件”这类副作用。每个外部动作要有业务幂等键和回执。若调用超时，先查对方系统是否已有申请，再决定重试；若审核拒绝，草稿留痕但不发送，不能让另一路自动化继续消费旧的“成功”变量。Agent 自己说“已完成”只是模型输出，业务完成看订单服务、发送系统和人工审核的真实回执。

小陈把外层输出定成结构化对象：`status` 只取 `ready_for_review`、`need_identity`、`need_policy`、`tool_failed`、`budget_exceeded`；`evidence` 列订单与政策引用；`draft` 只在证据够时非空；`stop_reason` 说明停在哪个关口。不要让一个空字符串兼任“暂未查到”“API 挂了”“模型没写完”。Dify 的 Agent 节点有成功状态和日志，但企业业务状态仍要单独映射。这样一条失败轨迹可由人工接手，客服看得懂下一步，不必盯着模型的思考记录猜。

**领导：**你这个结构看着挺整齐，可模型把 `status` 写成 `ready_for_review`，不还是它说了算？

**小陈：**正是不能让它独自说了算。Agent 输出可以提出状态候选，外层校验器要用可信工具结果重算关键条件：订单归属是否由业务服务确认、政策 ID 是否存在且有效、必要字段是否齐全、草稿引用是否包含没有在证据集中出现的条款。若 `draft` 写着“可退”，但 `evidence` 里没有有效政策，外层应改成 `need_policy`，并把这次矛盾记录成失败样本。模型负责表达与可选的查证路线，最终能否进入人工审核队列由可检查的字段决定。这不是不信模型，而是对所有会犯错的系统都设同一条验收线。

**领导：**我看执行日志里有一次政策工具调用成功，为什么你还说政策缺失？

**小陈：**“HTTP 200”只表示接口完成，不表示查到了适用条款。工具可能返回三个相似版本，可能返回一条已废止公告，也可能返回搜索摘要而不是原文。工具结果必须有结果类型、政策 ID、生效时间、来源位置和适用范围；没有这些，`tool_success=true` 也只能说明请求成功。反过来，找不到结果要区分“索引未覆盖”“权限不允许”“确无相关条款”。这三个空结果不能同样让模型自由发挥。我们用一张旧订单回放：如果它买在旧规则下，检索到今天的新政策不能直接引用；必须按业务规定的生效时点选择版本。所谓十二次调用，有时不是次数问题，而是每次拿回来的证据质量太差。

工具描述也会直接影响循环。把政策工具写成“搜索公司文档”，模型可能用它查订单、查退款进度、查所有模糊词；改成“按商品类别与申请日期返回有效售后政策及版本 ID，只读，不返回客户订单”，模型选择时边界清楚。参数要在业务端校验，`tenant_id` 从可信会话取得，不能由模型自行填；订单号可由用户陈述，但每次查询都重新核归属。即便 Dify 允许把工具挂到 Agent 上，真正防越权的是工具服务本身。限制工具数量可以减少选择噪声和误调用面，但不替代鉴权、速率限制与审计。

**领导：**如果它查两次同一订单，我们在工具层缓存一次就行吧？

**小陈：**只读缓存可以省接口负载，但要带租户、订单、权限范围和数据版本作键，不能把甲客户的订单缓存给乙客户。缓存还不能掩盖模型重复决策：模型每多转一轮，可能仍增加输入 token、延迟和错误机会。先修上游变量传递与工具说明，再视业务时效设短缓存。退款状态一旦变化，旧缓存会让草稿错过刚刚发起的申请；“相同参数”未必意味着“当前结果应相同”。因此日志里同时记录模型请求次数、工具实际访问次数和缓存命中次数，领导看到的十二与后端统计的八才有解释。

还有个常被漏掉的预算是人工时间。Agent 拖了四十秒给出一份缺引用的漂亮草稿，客服要再花三分钟翻政策；改成确定性节点加模板，十秒给出完整证据包，客服三十秒确认，整体成本反而更低。衡量时除了 token，还要看客服改写率、退回率、客户二次追问率和错判带来的补救时间。若一个 Agent 节点让人只得到一句“根据相关政策”，没有条款版本和订单事实，它的自动化程度只是把检索工作转嫁给客服，并没有解决领导最关心的处理效率。

## 一次改造，三组回放

小陈先复制工作流，在试运行环境里留住当前配置与十条脱敏工单。第一组是标准耳机单：核身、订单、现行政策都有明确结果；外层查一次订单和政策，Agent 若只负责把事实写成可读草稿，应没有多余工具调用。第二组是边界单：签收日期恰好跨政策版本或商品类别例外；若确需额外查证，就记录工具为何调用以及新证据改变了哪个判断。第三组是故障单：订单 API 超时、政策检索为空、迭代上限命中各一例；结果必须落到对应状态，不应产生“可以退”或“退款已发”的肯定句。每组把运行 ID、节点轨迹、模型轮次、工具次数、成本和最终审核结果放在一页。

**领导：**那十二次该降到几次，给个 KPI。

**小陈：**先不能凭空定“所有工单三次以下”。标准单若数据齐全，目标可以是零次重复订单查询；边界单允许额外政策查证，但每次都要有不同证据目的。我们用分层指标：标准样本的工具次数分布、边界样本证据正确率、失败样本误答率、每张工单的 95 分位延迟和单次成本。先确认没有越权查询和错误对客，再压无价值调用。若只追求最少次数，模型会更快地给出没核实的答案，这张账单便宜，售后纠纷可不便宜。

上线时的判断也很具体：固定校验留在画布；需要模型选择路径的部分才进 Agent；工具最小化；设轮次和时间预算；将“不足以判断”作为合法终态；外发仍经人工或明确授权的业务流程。领导想看“五个框”，可以继续看。小陈要看的则是每一格背后的调用明细、事实来源与失败出口。地铁站牌负责告诉人去哪，换乘记录负责解释为什么晚点，两张图缺一张都没法运营。
