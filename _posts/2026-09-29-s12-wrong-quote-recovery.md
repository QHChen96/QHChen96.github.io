**领导：**坏了。Agent 把未批准的八折报价发给客户了。赶紧撤回邮件，删掉旧报价，再发一份对的。

**小陈：**先别让它自动再发。客户是外部邮箱，撤回未必能做到；旧报价可能已被下载或转给采购。删掉内部文件只会把证据删没。先停同一价格模板的后续发送，查清谁实际收到了哪一版，再让有权的人决定逐户怎么说。

**领导：**你这不是拖时间吗？

**小陈：**是止血。乱发一封“请以新报价为准”，如果收件人名单还错，事故会从错价变成群发错价。今天要先圈出影响范围、固定证据、分层处理客户、对账下游，最后再重开报价流程。

下文客户、金额、审批和处置时间线均为教学虚构。真实报价争议及外部通知应由企业销售、财务、法务和相关负责人根据实际合同、地区规则与客户关系作决定；技术团队不替他们做法律结论。

## 错价已经出门，第一反应别是“再发一封”

虚构事故发生在上午九点：销售 Agent 读取了领导聊天里的“可以考虑八折”，把内部试算 PDF 标成正式报价，向十位潜在客户的联系人发出。九点零三分，财务发现订阅折扣未审批，接口开发费用也被一同打折。领导想让小陈点邮箱“撤回”。小陈先确认邮件系统与收件范围，提醒大家外部客户邮箱不能以内部撤回功能为保证。微软 [Outlook 的官方说明](https://support.microsoft.com/en-us/outlook/can-i-undo-recall-a-sent-email)明确指出，发往组织外部或个人邮箱的邮件不能按同组织的撤回条件处理。不同邮箱供应商还有短暂的延迟发送或撤销窗口，但事故发生数分钟后，不能凭一个按钮假设客户没有拿到文件。

**领导：**那我让销售挨个打电话，让客户别看。

**小陈：**先知道哪些人真的收到了，别给没收到的人主动补送一个错误价格。也别只看 CRM“已联系”，它可能在邮件 API 接受请求时就写入。调用受理、发件箱出现、投递回执、退信、客户回复是不同证据。我们将报价版本 ID、邮件发送意图 ID、邮件系统消息 ID、收件地址、附件指纹和回执关联起来。状态未知的列为待核，不能直接当成功，也不能重试再发。

第一道动作是停止同源任务：暂停这次批量活动、相关报价模板的自动外发、排队中的待发送项，以及会拿错误报价继续生成邮件的下游任务。暂停范围要以价格版本和活动 ID 为准，避免把所有正常客户沟通一锅端。已在邮箱系统受理的请求，技术上未必能取消，状态要继续追踪。暂停动作、操作人和时间记到事故台账；不能把“点击暂停”误认为“所有外发都停止”，得核对队列是否还有进行中的任务。

**领导：**先把 Agent 总开关关了，最省事。

**小陈：**总开关可以作为紧急兜底，但仍要知道它管到哪里。排队系统可能已经把任务交给邮件服务，关生成服务不影响已提交的外发；销售也可能继续从已下载的 PDF 手工发送。我们要同时冻结错误报价版本的“可发送”资格、停相关活动队列、在邮箱侧确认状态、通知账户经理暂勿引用旧文件。若总开关会中断其他正常客户的服务，就由事故负责人记录影响与恢复条件。暂停并非一个抽象按钮，是一组可核查的动作和回执。

小陈给事故定了统一编号，先按时间列出九点前价格规则是什么、九点整谁触发批量任务、九点零一分哪些发送请求被受理、九点零三分谁发现错误、九点零五分哪些队列被暂停。每一格附系统日志或人工确认，不用“应该”“大概”。时间线能帮团队辨认：同一批十位客户中，有三封可能还没出队列，有两封受理但回执迟到；若把发现时间当发送截止，影响清单就会漏人。事故负责人每隔固定时间发布已确认事实和仍未知状态，避免销售、财务各自用旧截图给客户解释。

## 影响清单不能从“生成了十份 PDF”倒推

**领导：**系统显示生成了十份报价，那就是十位客户。

**小陈：**生成记录不等于发出记录。一位客户可能对应多个联系人，一封邮件可能含抄送，还有两封可能在队列里没发。以发送意图为起点，查收件地址与消息 ID，关联原附件指纹和报价版本。对每一位客户标状态：草稿未发、排队已取消、邮箱 API 已受理但结果未明、发件箱可见、退信、客户回复、客户已引用报价推进合同。只有这样，销售联系客户时才不会把“我们发错了报价”告诉一个压根没收到的人，也不会漏掉真正抄送的采购人。

微软 [Graph sendMail 文档](https://learn.microsoft.com/en-us/graph/api/user-sendmail?tabs=http&view=graph-rest-1.0)说明 <code>202 Accepted</code> 是请求被接受，并非处理完成或最终投递。小陈因此把“受理但待核”留在清单里，继续查询邮箱系统或退信情况；不能把网络超时后的未知状态直接算作未发而重试。若 CRM 的活动记录与邮箱记录不一致，先保留两者，再用消息 ID、时间和地址对账。一个系统没有记录，不足以证明另一个系统的外发没发生。

证据固定包括当时的报价 PDF 原文件或内容指纹、内部试算依据、审批流状态、Agent 生成和发送轨迹、邮件正文与附件、客户回复、CRM 变化。保护访问权限，避免事故台账变成客户报价公开展板。错误文件可从可继续访问的公开链接中按授权流程下架，但已发附件与客户下载的副本不能靠改链接抹去。报价系统应标记该版有争议并禁止新外发，保留历史供处理和审计；不能把价格从八折悄悄改回原价，让回头看的人误以为客户当时收到的是正确版。

影响清单要能对账，不靠人工在微信群里数名字。小陈以报价版本为键查所有生成文档，再以文档指纹查邮件附件和分享链接，以发送意图查消息 ID、To/Cc/Bcc，以消息 ID 查发件箱与退信，以账户 ID 查 CRM 和合同草案。每条关系都可能断开，例如邮件服务只给异步受理回执、某销售手工转发旧 PDF。断开的不是自动判“无影响”，而是进入人工核查队列，写明负责人与最迟复核时间。清单有版本号，新增受影响客户时保留原版本和发现原因，让领导知道数字为何从七变十。

**领导：**客户把邮件转给别人，我们查得到吗？

**小陈：**通常无法完整知道外部转发链，所以影响范围分“已确认直接收件”和“可能被转发，需通过客户沟通确认”。技术日志不能证明客户没有保存或转发。也正因如此，对外沟通不能使用“您尚未查看旧版”这种未经证实的句子。销售只陈述自己确知的事实：某日期发送了某编号报价，发现其价格未经内部审批，正在由授权团队核对并提供准确版本。后续具体商务安排由负责人与客户谈，不让模型根据一个已读回执猜客户内部做了什么。

## 十位客户不是十封同样的道歉信

小陈和账户负责人把受影响客户分组。第一组邮件在队列里被取消，没有对客动作，只检查是否另有销售手动发送。第二组已外发但无回复，需尽快由账户负责人按批准口径说明报价有误、将提供核准版本，并确认客户是否已用于内部审批。第三组客户已回复“按此价推进”，情形更敏感，销售与财务、法务一起核对双方沟通和合同状态，再决定如何谈；不能由 Agent 擅自宣称“旧报价当然无效”。第四组可能已进入合同草案或采购订单，下游文件要一并排查。分组不是为了拖延，而是避免一个模板给不同事实的客户说同一句可能错误的话。

**领导：**“请以新报价为准”不能一封解决？

**小陈：**只有新报价经审批，且有权的人确认可以这样表达，才发。客户已经按旧报价开采购申请时，单方面一句“以新为准”可能制造更大争议。我们可以起草更正模板，但每户要带自己的旧报价编号、旧邮件时间、改正内容、当前可提供的正式方案和联系人；具体措辞由授权人批准。对于尚未看见旧报价的客户，轻率提到“八折”反而主动扩散错误信息。系统根据事实分组，但最终商务决策由人作。

客户沟通要能闭环：谁联系、何时、通过什么渠道、发了哪版更正、客户是否收到、是否有疑问、是否暂停后续合同动作。只给销售一个“已发送更正邮件”的勾不够；若邮件退信或客户要求电话确认，状态要继续。多位联系人同属一客户时，账户负责人决定沟通顺序和统一口径，避免采购收到新版、技术负责人仍拿旧版推实施。联系记录进 CRM，但不要用“客户未反对”当“客户接受新版”。明确同意、明确拒绝、待回复是三种状态。

新报价也不能因为事故紧急就抄近路。财务重新核产品行项、折扣范围、币种、税费、有效期；销售确认客户本次真正询价的配置；审批人批准具体版本；外发服务比对内容指纹与收件人，再由账户负责人发送。若客户提出“既然你们发了八折，为什么现在又变”，客服机器人不能套一段“系统错误，以新版为准”自动回应。它可以把已核实事实和对客口径提示给销售，客户关系和争议处理仍由人承担。紧急处置可以压缩排队时间，不能压缩事实与授权。

**领导：**如果客户已经回复接受旧价，新报价还要照发吗？

**小陈：**这类客户单独升级。先固定其回复所指的旧报价编号、时间与条件，再由商务和法务判断如何处理；不能以“我们系统里已把旧版设失效”作为唯一答案。新报价可以作为协商材料，但何时发、怎样说、是否另有安排，都需要批准。Agent 只能汇总事实和准备备选草稿，不得自动替公司承认或否认具体责任。对每户的状态卡要清楚标“争议处理中”，而不是为了让事故面板变绿，勉强归类为已更正。

## CRM 改回正确金额，合同草案可能还躺着旧价

事故处理中最容易漏的是下游复制。销售看到错价后把 CRM 金额改回原价，报表正常了；但法务系统里的合同草案已经从旧报价生成，客户采购系统也可能上传了旧 PDF。小陈按“报价版本 ID”反查邮件附件、CRM 商机、合同草案、订单申请、预测看板和交付准备事项。每个系统记录旧版本是只作历史证据、需暂停、需修订，还是已有客户接受待进一步处理。不能把所有状态一刀切改成“已解决”。

**领导：**能不能删掉那份错误合同草案？

**小陈：**可以按系统和企业规则取消或废止继续使用，但历史上它出现过这件事要留记录。若客户已收到草案，更不能靠内部删除假装从没发过。新草案要有修订来源、批准链和客户确认过程。微软的 [Dynamics 365 报价生命周期文档](https://learn.microsoft.com/en-us/dynamics365/sales/sales-transactions)展示了草稿、激活和修订版本的区别；我们借鉴“已对外版本可追、修改产生新修订”的原则，不宣称某平台能自动撤回外部客户手中的文件。

预测也要复核。错价八折可能让模型以为客户“接受报价”，把商机阶段提升，管理层资源已按错误毛利排了计划。S09 的证据门槛在这里继续适用：客户回复“按此价推进”只说明客户回应了错误版本，商业处理还在进行；系统不能简单记作正式报价被接受。小陈给看板加“受报价事故影响，金额待确认”，让管理层知道这单有现实沟通，不要拿旧价或新价任意一个当确定收入。

## 事故什么时候算结束，不以“新邮件已发”为准

小陈给每户建一条处置记录：错误版本和发送证据、新价格审批、对客联系、客户回应、相关合同与 CRM 更正、当前责任人和下一跟进时间。结案条件不是统一的“更正邮件已发”，而是当前可控动作完成、客户状态清楚、下游无仍在使用的错误版本、未知发送状态已核查或明确移交。若客户仍在谈旧价，事件可以转到商务争议处理，技术事故台账不能把它悄悄关成“系统已修复”。对内也发布影响范围和已采取动作，避免另一个销售同一天从旧文件夹继续发八折 PDF。

**领导：**客户会不会觉得我们管理混乱？

**小陈：**事故已经发生，藏得越久通常越难解释。我们现在能做的是准确、及时、由熟悉客户的人沟通，别再让第二封自动邮件把同一客户叫错名字。对外怎么说由授权团队判断；技术给他们完整事实、版本和状态。改价争议未必能用一封邮件解决，但每一步都知道下一位负责人是谁，至少不会发生“大家都以为别人已经解释过”。

事后修复也分层。S08 的报价审批状态机需要硬拦未批准 PDF；S07 的发送闸门检查收件人和附件指纹；S04 的 CRM 写入规则不得把内部试算当正式金额；预测汇总排除事故中有争议的版本。再用本次脱敏事故做回放：未批折扣、已批后附件被替换、网络超时、客户已回复、排队邮件取消失败、旧版仍被合同系统引用。每种情形的预期不是“模型道歉”，而是系统在正确关口停、能找到影响范围、能向人交接。错价不会因一次提示词修改而彻底消失，恢复能力要靠多道可观察的控制。

小陈还安排一次恢复演练。测试环境里放十个虚构账户和两版报价，故意让邮件 API 在五封受理后超时、两封进入队列、三封根本没发送。值班人拿不到“标准答案”，必须根据消息 ID、队列和发件箱核对，产出分层清单；商务负责人对“已回复接受”的虚构客户单独选口径；财务给出正确价并批准版本；最后检查 CRM、合同草案和销售待办是否全部指向准确状态。演练通过的标准是影响范围能解释、未知状态有人接、没有二次误发，而不是在培训会上把流程图背得很熟。

**领导：**什么时候可以重新打开自动报价？

**小陈：**先修根因，再回放，再限定范围开启。至少验证未审批折扣无法进入可发布状态，附件替换会使批准失效，发送工具只接受批准快照，超时不会盲目重试，错误版本在搜索和复用入口被拦。恢复后先让一小部分低风险报价走人工审查，观察实际日志和错发告警，再逐步扩大；每次扩大写明负责人、暂停阈值与回退入口。事故还没处理完时，系统可以恢复内部试算和资料整理，但正式外发权限不必同时恢复。让业务有事可做，也让下一轮客户不替我们再测一次。

领导最后没有按“撤回”按钮赌运气。他先批准暂停同源外发，销售负责人按客户清单逐户核实，财务完成正确报价，授权人决定每户更正口径。技术把旧版标为有争议、停止新引用，并对账邮件、CRM 和合同草案。十位客户的状态不再挤成一个“已处理”标签：三位未外发、五位已收到待回复、一位退信、一位正在讨论旧价，后者有明确负责人继续处理。这些数字仍是教学虚构，但处理逻辑是真正能拿去画事故台账的。

事故台账最后还要留一列“未解决风险”。五位待回复客户是否已经把旧价送内部审批，暂时不知道；退信地址是否有正确替代联系人，需要销售核查；讨论旧价的客户可能要求重新谈实施范围。这些不确定不妨碍技术团队修好发送闸门，却妨碍把商务事件粗暴结案。小陈让每项风险有主人、下一次检查时间和关闭依据。一个事件可拆成技术修复完成、客户沟通继续、合同争议待定几个并行状态，领导看板上不再只有一个“已修复”绿灯。这样既不让开发永远背着未解决的商务谈判，也不让商务问题在技术上线后失踪。

**小陈：**我们不能让客户忘记收到过那封邮件。能做的是先知道谁看到了什么，再让对的人把事情说清，最后确保系统不再把错价送出去。今天的胜利不是把事故记录删干净，而是没有人再凭猜测续发第二轮。

领导把这次事故的时间线和处置清单留给下次复盘。以后谁问“报价错发怎么办”，小陈不用回答“看情况”：先停同源发送，查真实回执，保护原始版本，逐户判断，授权纠正，对账下游，回放后恢复。具体商务话术会因客户而异，技术顺序不能乱。

事故面板上，所有待核状态都有责任人和下一次更新时间。第二天销售再打开客户记录，不会只看到一条“已发更正”，还能看到客户是否确认、哪版报价仍在谈、合同草案是否暂停。恢复的标准是下一位接手的人能继续正确处理，而不必重新猜昨天到底发生了什么。
