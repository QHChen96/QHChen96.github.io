**领导：**新模型榜单第一，我们把研发 Agent 的模型名换一下，下周效率翻倍。

**小陈：**模型换了，验证码 issue 的通过率反而掉了。旧 Harness 逼它“每一步都先写十项计划”，又在每次工具调用后把全仓说明塞回来。新模型本来能按需找文件，被我们安排成一边读万字会议纪要一边找螺丝。

**领导：**那是新模型不适合我们？

**小陈：**现在还不能下结论。你同时动了模型版本、提示模板、工具目录和压缩阈值。结果变差，到底是谁推的，账都算不清。先用同一组任务做“模型版本 × Harness 版本”的四格回放，再决定保留什么、改什么、怎么回滚。

文中模型 A/B、任务与数值均为教学虚构，不代表任何真实产品测评。实际产品配置与迁移建议需按发布当天官方文档核验。

## 先把“更聪明”翻译成这张 issue 的结果

领导说“更聪明”，小陈问：“对 #318 验证码乱序，是更快找到代码，还是更少误改文件，还是一次就把测试跑对？”研发 Agent 不是答选择题；它要读仓库、提出补丁、执行工具、处理失败、交可审 PR。一个模型在公开基准上表现更好，不自动保证它在我们老旧工具定义和长日志里更可靠。团队要列任务级结果：修复是否满足乱序验收、是否保留旧客户端兼容、是否越权调用、测试证据是否真实、PR 是否可评审；再看耗时、调用数和成本。

**领导：**那先用真实 issue 试一天？

**小陈：**可以灰度，但先有可重复的回放集。真实 issue 会被人改、依赖服务会波动、仓库主线会前进，同一任务今天和明天不是同一题。小陈从历史里挑三类样本：明确定位的小修、跨模块改动、工具失败恢复；每类含正常与刁钻样例。每张样本固定仓库提交、任务描述、允许工具、测试环境和验收条件。脱敏后离线回放，再在小流量真实任务上观察。没有固定输入的对比，很容易把“周二 CI 比周一快”当作模型升级成绩。

OpenAI 的[模型使用指导](https://developers.openai.com/api/docs/guides/latest-model)会随模型迭代更新迁移建议；较早一代的[迁移指引示例](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.4)明确建议先只切模型、固定推理配置、跑评测，再逐项调整。LangChain 的[Deep Agents profiles 文档](https://docs.langchain.com/oss/python/deepagents/profiles)展示按模型或提供方配置提示、工具可见性和中间件；这恰好说明模型配置与 Harness 配置可以分开版本化。小陈不会把某家示例 profile 当成通用最优参数，关键是把每个变量写清。

## 四格表：先看是谁变了，再看哪格值得上线

小陈定义 M0 是当前模型、M1 是候选模型；H0 是当前 Harness、H1 是按候选模型特性调整后的 Harness。第一格 M0/H0 是生产基线，必须能复现已知表现；第二格 M1/H0 只换模型，测新模型在旧框架里表现如何；第三格 M0/H1 只换 Harness，测新框架本身有没有改善或破坏；第四格 M1/H1 看组合效果。四格用同一组任务、同一仓库基线和工具模拟，重复多次并记录随机波动。若只做第一与第四格，任何变化都无法归因。

**领导：**H1 是什么？你还没知道问题就先造新 Harness？

**小陈：**先从轨迹找具体问题，再做最小修改。比如新模型在 H0 里被强制每轮写长计划，导致工具调用延后；H1 只把这个强制模板改成“复杂任务按需规划，短任务可直接定位”，其他权限、测试门禁不动。或者旧压缩阈值导致关键约束丢失，H1 只调整交接单。一次只改一个可解释环节，必要时再形成下一个 H2。四格不是一次性大改造的借口，它帮助我们拆出模型效应、Harness 效应和二者组合。

## 一个例子：旧提示词怎么把新模型带偏

H0 的系统提示写着：“收到任何 issue，先输出完整十步计划；每一步结束都复述全部仓库规则；若工具失败，原样重试三次。”旧模型在简单任务上也许需要强约束，新模型面对 #318 已能从 issue 找到模块，却仍得先填满十步计划；每轮复述推高上下文成本，错误重试让临时故障放大。小陈从轨迹看见它并不是不会找代码，而是在找到代码前被模板耗掉多轮。H1 把固定计划改成按任务复杂度选择，把重复规则换成可引用的仓库知识地图，把错误重试按类别处理。

**领导：**那以后提示越短越好？

**小陈：**不能一概而论。安全边界、业务禁止事项、交付证据要求不能为了省 token 删掉；冗长的重复解释可以改成清楚、可执行的规则与外部文档引用。具体模型对不同提示的反应要测。OpenAI 的不同模型指导会讨论提示迁移与精简，但团队不能把某篇文档的一组百分比直接搬到自己项目。我们关心的是同一 issue 是否更容易修对、是否减少误调用和无效轮次。

工具描述也有旧包袱。H0 里两个工具都叫“verify”，一个跑测试，一个查预发健康，新模型可能更积极调用工具，于是更容易碰到含糊命名；H1 把工具目录收窄、名字与失败语义写清。若 M1/H0 误选很多、M1/H1 好转，这是 Harness 与模型交互的问题，不能简单宣布 M1“工具能力弱”。相反，若四格里 M1 都在同一类型任务上错过关键根因，才更值得分析模型本身或任务输入是否不适配。

## 评测必须分层：任务通过率、过程质量、运营代价

第一层看最终结果：验收测试、代码评审、缺陷复现是否通过。第二层看过程风险：是否越权调用、是否重复外发、是否用旧测试证据、是否遗漏交接约束；即使最终答案对，过程触碰生产密钥也不能上线。第三层看运营代价：端到端耗时、模型与工具调用数、沙箱资源、人工纠错分钟数。只用“成功率”会把更贵、更慢、更难审的方案包装成进步；只用 token 费用则会把错误的便宜方案包装成节约。

**领导：**我就要一个总分，好做汇报。

**小陈：**先设硬门槛，再汇总可比较项。越权、无证据交付、重复 PR 是不能用更快速度抵消的；满足门槛后，再比较质量、时延与成本。对不同任务类型单独看，别让八十个简单小修盖住五个跨模块失败。报告给每格样本数、通过数、失败类别、分布而非只给平均值。模型输出有波动，必要时同一任务多次运行；一次成功不能证明稳定，一次失败也未必代表全部不行。

每次回放保留模型标识、Harness 版本、提示版本、工具目录版本、仓库提交、测试镜像、样本 ID、随机配置与运行轨迹。若候选方案质量突然变好，先排除是否测试环境变简单、工具多了一个捷径、验收用例被改弱。H11 的目标是把升级变成可复核实验，而不是把结果写成“领导觉得它今天挺聪明”。

## 样本怎么挑，才不会给候选模型出“开卷考”

**领导：**我们拿过去成功的四十条 issue 回放，模型看过这些代码，会不会天然占便宜？

**小陈：**历史仓库本身可以用，关键是样本不要只挑成功且简单的。小陈把过去的任务按根因与风险分层：定位明确的小改动、需要跨文件理解的改动、工具环境故障、权限被拒、需要停止交人的问题。每类保留成功与失败案例，并把任务描述、当时仓库提交和验收条件一起封存。若选的都是“修一个拼写错误”，所有组合都高分，根本测不出 H0 的工具问题。若只选极难怪题，又会误判日常收益。

回放还要防止答案泄露。模型若能读到原始 PR、提交历史中的修复补丁或评测答案，就不是在解题，而是在抄答案。可以固定仓库到修复前提交，按任务需要限制后续提交可见性；保留可供定位的真实业务资料，但隐藏验收用例的答案部分。环境要尽量接近真实：依赖可用、测试命令正确、工具权限与生产一致。把所有障碍都在评测里删掉，测出的只是理想世界里的选手。

同一任务多次运行时，随机性会让结果有波动。小陈不给领导看“最好的一次”，而是记录每个组合多次尝试的通过数、失败类型和耗时范围；特别关注原先稳定通过的任务是否变成偶尔失败。若候选组合只在某一轮运气好、另几轮把旧客户端错误码改坏，不能凭一次满分推广。评测样本还要留一组不参与调参的保留集，避免团队反复针对固定四十题修 Harness，最后只会做这四十题。

**领导：**失败任务是不是都算模型扣分？

**小陈：**先分根因。仓库依赖服务真的挂了，四格都失败，是环境样本；H1 工具返回误标，把测试失败写成成功，是 Harness 缺陷；M1 在同样工具与上下文下反复漏读关键断言，可能是模型与任务不适配；M1/H1 才失败，说明组合交互有问题。最终指标仍按用户得到的结果计，但诊断必须分层，才能决定是修工具、修上下文、换模型还是暂缓升级。

## 看轨迹时别只找“模型说错的那一句”

小陈把一条失败轨迹拆成四段：任务输入是否完整，模型当时看见了哪些上下文，工具真实返回什么，Harness 如何把返回送进下一轮。旧 Harness 把搜索结果截成前五条，恰好没包含验证码状态文件；M1 随后选择错误模块，并不是“它不懂代码”，而是它根本没得到候选文件。另一条轨迹里工具已返回 <code>exit_code=1</code>，模型仍说测试通过，这是模型解释和完成门禁双重问题。失败定位不能只截最后一句结论，要顺着输入与执行链找第一次偏航的地方。

**领导：**有时两个模型走法不同，一个先搜、一个先读说明，怎么公平比较？

**小陈：**不要求它们工具调用顺序一模一样。固定的是任务、可用工具、权限与验收，允许各自选择路径；比较最终结果和过程边界。若某个模型用两步找对文件，另一个用五步也找对，质量都算通过，时延与成本再比较。强迫新模型照旧模型每一步走，会把“模型能力”变成“遵守旧脚本能力”。安全约束和审计要相同，工作策略可以不同。

当 H1 调整工具目录时，更要确认没有把任务难度暗中降低。比如 H1 增加一个“直接告诉模型根因”的工具，M1/H1 高分不代表模型升级有效；若这工具在生产确实可用，它仍是合理系统改进，但应归因于 Harness，而不是写进模型成绩。四格表就是为这些“看起来都变好了”的差异找主人。领导若只想换模型，我们必须能回答不改系统时它的表现；若愿意改系统，则看组合是否值得维护成本。

## 版本矩阵不止两格：把影响行为的东西都锁住

小陈把“模型版本”定义到具体可调用标识和相关推理配置，而不是写“新版”；Harness 版本包含系统提示、任务模板、工具名称与 schema、工具搜索策略、压缩阈值、停止规则、沙箱镜像和交付门禁。仓库提交、测试数据、CI 工作流也要冻结或记录。若模型名字没变，后台实现可能更新，团队需要记录供应商提供的版本信息和回放日期，观察漂移。若平台无法钉住精确后端版本，就把这一限制写进结论，增加周期性回放。

**领导：**这张表会不会版本组合爆炸？

**小陈：**不会每个配置都做全排列。先用 M0/H0 建基线，M1/H0 看单换模型；遇到明确回归，再只改相关 Harness 环节形成 H1，补 M0/H1 与 M1/H1。对工具目录、压缩和提示分别做小实验，不把十个调整一次塞进 H1。每次保留配置快照和理由。矩阵是诊断工具，不是要求把所有宇宙平行线跑一遍。

版本锁也覆盖外部知识。仓库说明文件在评测期间被同事更新，Agent 可能因新文档少走弯路；如果没记录，团队会把文档改进归功于模型。测试镜像更新后修好了依赖，回放耗时下降，也不是模型更快。真实生产总会变化，离线阶段尽量固定，灰度阶段完整记录。两阶段回答不同问题：离线问“同条件下谁更稳”，灰度问“在真实变化里是否仍能交付”。

## 回滚要验证“能退回”，不能只保存旧配置文件

小陈把升级前的 M0/H0 配对打包：模型配置、Harness 配置、工具契约、任务策略、回放报告和回滚脚本。灰度中如果新组合误选部署工具，安全门会拦住，但还需要暂停新任务并切回已验证配对；若只是某类任务质量下降，可先路由回旧组合，保留其他灰度样本。回滚策略按严重程度分层，不能等事故发生时才讨论“是全部回退还是只退登录模块”。

**领导：**旧组合还能用，直接切回去就行。

**小陈：**先演练。旧模型是否仍可调用、旧工具 schema 是否已被新版本覆盖、旧提示引用的仓库说明是否还存在、旧任务检查点能否被当前执行器读取，都可能变。回滚演练要在测试环境启动一张旧任务，读工作区、跑测试、尝试交付到测试仓库；结果存档。若平台不允许完整回到旧模型，就准备人工接管与降级路径，而不是在上线方案里写一个实际上按不了的“撤回”按钮。

回滚后继续追踪已由新组合创建的 PR。PR 不会因为模型切回去自动消失；已写的代码、测试、评论与外部动作依旧需要按原任务键对账。新任务路由到旧组合，运行中的新组合任务按风险停机或完成，再决定如何处理其 PR。H07 的外部动作台账和 H08 的证据闸门在这里继续生效。升级与回滚改变谁来运行，不能抹掉已经发生的事实。

## 灰度不是把所有新任务都交给新模型

小陈先让 M1/H1 接少量低风险、小范围 issue，保留人工评审和完整证据门禁。灰度观察实际仓库分布、工具调用错误、CI 失败与人工改稿，不只看离线回放；一旦出现安全边界回归或无证据结案，立刻停新任务，原任务按检查点和工作区恢复。回滚要成对：模型版本与对应 Harness 配置一起回到已验证组合，不能只把模型切回 M0，却留下专为 M1 调的 H1，然后说“回滚了”。

**领导：**切回去会不会把正在跑的任务弄乱？

**小陈：**任务启动时固定配对版本与工具目录，运行中不热换。新任务用回滚组合；正在运行的任务若触发风险，安全停机并保留现场，再决定按原配对完成、迁移或人工接管。会话压缩、工作区与检查点都带版本，避免旧任务恢复时悄悄套上新提示。升级是系统版本变更，不是后台下拉框改个名字。

最后，小陈给领导的结论不是“新模型好”或“新模型差”，而是：“在 40 条教学回放里，M1/H0 的验证码类任务回归主要来自旧工具目录；调整工具命名后 M1/H1 通过安全门，耗时与成本仍需灰度确认。”这里数字是示例，不是真实测试成绩。领导终于有一张能问到底的表：哪格变了、为什么、哪条风险还未放行。换模型这件事，才从追榜单变成可交付的升级。

**领导：**能不能把这次升级结论写成一页我能签的单？

**小陈：**一页足够，但每行要能打开证据。第一行写候选配对版本和适用任务：M1/H1 只用于普通研发 issue，暂不处理生产事故。第二行写回放结果：样本组成、每类成功与失败、越权和误结案是否为零、耗时与成本范围，并附原始轨迹。第三行写未解决问题：旧安卓兼容类任务仍有回归，转回 M0/H0。第四行写灰度上限、负责人和观察期；第五行写回滚触发条件和已演练的操作路径。签字不是相信新模型会更努力，是确认这些边界与证据可接受。

小陈还把“成功率提高两个百分点”拆开问。如果四十条里从三十二条通过变成三十三条通过，差异可能只是一张任务的随机波动；如果新增通过的是高风险跨模块任务，同时旧的简单任务开始偶发越权，不能只看净增一条。要看逐题迁移表：哪些任务由错变对、哪些由对变错、错误严重度如何、是否有共同根因。预算若允许，再扩展样本或重复运行；预算不够就缩小结论范围，写“目前证据不足以证明整体更好”。没有必要为了汇报把统计不确定性磨成一句斩钉截铁的话。

灰度期间若供应商更新模型或工具平台配置，也要标记实验窗口。新旧组合同一天接到的任务难度不同，不能直接比较日均 PR 数；尽量按任务类型配对、看完成到可合并的时长与人工返工。领导想要的是团队效率，评测要覆盖从接 issue 到交付的整个链条。若新模型生成代码更快，却让评审人每张 PR 多花半小时纠错，所谓提速只是把工时从模型那边搬到小陈桌上。

这张升级单每次复盘都更新，保留旧版本和当时的判断依据。后来若发现遗漏的回归任务，团队能知道是样本覆盖不够、灰度观察不足，还是某个工具配置在上线后变了，再决定补评测或回滚。
