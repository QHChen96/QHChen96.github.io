**领导：**我在审批页点了一次“同意”，客户收到两份合同邮件。你不是说 LangGraph 有检查点，服务重启能接着跑吗？

**小陈：**能接着跑的是图的状态，外部邮件不自动跟着图状态组成同一个事务。第一次发送成功后，服务还没把“已发送”写进检查点就断电；恢复时发送节点重新执行。图里看着只走了一次箭头，邮箱里已经留下两次脚印。先查邮件服务的发送回执和请求键，停掉这条任务的自动重试，再把发送节点做成可对账、可去重。

**领导：**流程图上明明是“审批—发送—记录”，我只点一次，怎么能走两遍？

**小陈：**箭头说明先后关系，不保证外部副作用恰好一次。今天把 state、节点、边、检查点和人工暂停拆开，标出图能保存哪里、邮件系统真正执行哪里。随后做一次“发送后立刻杀进程”的回放，让同一合同最多产生一条有效外发记录；若邮件服务没给明确回执，停在待核，别重发赌运气。

合同、客户、发送数量和时间均为教学虚构。LangGraph 官方文档说明检查点、interrupt 和恢复的公开行为；本文的邮件幂等、审批版本与对账流程是企业应用层设计，不宣称框架自动保证外部邮件只发一次。

## 图画的是控制流，state 记的是图知道的事

小陈先用白板还原流程：起草合同邮件、展示给领导审批、领导修改收件人与附件、执行发送、记录回执。LangGraph 的节点可以分别实现这些步骤，边规定下一步去哪里；state 存合同版本、收件人、草稿、审批状态、发送请求键和回执。官方[Persistence 文档](https://docs.langchain.com/oss/python/langgraph/persistence)说明 checkpointer 按 thread 保存图状态快照，供续跑和故障恢复；store 则是跨 thread 的应用数据。它能帮助找回“图进行到哪里”，不代表外部邮件、CRM 和检查点在一个数据库事务里提交。

**领导：**那一个发送节点返回“成功”，检查点不应该立刻保存吗？

**小陈：**节点调用邮件 API 成功到状态持久化完成之间总有一段时间。进程、网络或检查点存储在这段时间坏掉，邮件已发而图还不知道。反过来，若先在 state 写“已发送”再真的调 API，调 API 前崩了，图会以为发过，客户其实没收到。无论先后，总有接缝。除非邮件系统与图状态共享强事务，通常做不到；所以用业务幂等键、回执查询与对账来处理“可能已经发生”。检查点让计算可恢复，业务幂等让副作用可安全重试，两者要配合。

小陈把 state 的五个字段按性质标颜色：<code>draft_version</code> 是待发内容版本，<code>approval_id</code> 证明这版内容和收件人已被批准，<code>send_key</code> 是这次业务动作的稳定去重键，<code>send_status</code> 是本地图里看到的状态，<code>provider_receipt</code> 是邮件平台可核的发送结果。<code>send_status=SUCCESS</code> 如果没有回执，只是本地说法；审批了 V3 草稿，不意味着恢复后模型重新生成 V4 还可以沿用同一个“同意”。收件人、标题、正文摘要、附件指纹任何一项变了，都应重新审批或确认既有批准范围。

## interrupt 让人插话，不会帮人记住没发生过的事

LangGraph 的[Interrupts 文档](https://docs.langchain.com/oss/python/langgraph/interrupts)说明：节点里调用 <code>interrupt()</code> 会暂停并通过检查点保存状态，之后用同一个 <code>thread_id</code> 与 <code>Command(resume=...)</code> 继续。小陈用它停在真正发送之前，让领导看待发内容，而不是邮件已经出门后才问同不同意。生产环境需要持久化的 checkpointer；文档提醒 <code>InMemorySaver</code> 只存在内存，重启会丢。若演示时只用内存存储，服务一重启，连“领导刚批了什么”都不一定找得回来。

**领导：**我点同意后，它不是从暂停的那一行继续吗？

**小陈：**要注意官方文档里的细节：恢复时包含 <code>interrupt()</code> 的节点会从节点开头重新执行，<code>interrupt()</code> 之前的代码也会再跑。若有人把“先发一封预告邮件”写在 <code>interrupt()</code> 前面，恢复时可能重复发。安全做法是把有副作用的动作放到批准之后的独立节点，或者让前置动作本身幂等；审批节点里只准备和校验可重复计算的数据。图能准确保存断点，不代表节点里的每行副作用都只运行一次。代码评审要看中断位置，不只看节点名字叫“审批”。

审批回执也要带版本。领导看到的页面显示客户 A、邮箱 a@example、合同 V3、附件哈希；点击同意应产生批准记录，绑定这些内容和领导身份。若恢复时 state 里的收件人变成客户 B，或者附件换了 V4，发送节点不能只看 <code>approved=True</code> 就放行。把批准对象写成“这一版具体内容”，才能防有人在暂停期间或恢复前改稿后借用旧签字。模型生成草稿可以重跑，但重跑结果要重新审；不把一次“同意”当未来所有版本的空白支票。

## 崩溃落在两条线之间，检查点自己跨不过去

小陈让测试环境在邮件服务返回成功后立刻杀掉进程，故意不给 LangGraph 保存下一份检查点。恢复器按 thread ID 读到的状态仍是“待发送”，于是准备再次执行发送节点。若发送请求带同一个业务键，邮件服务或企业发送网关可以识别重复，返回第一次的回执；若服务不支持去重，应用先查自己的发送登记或供应商回执，再决定是否能重试。若查不到且结果未知，暂停交人核对，不能因为图 state 还没写成功，就断定邮箱里没有那封邮件。

**领导：**发送服务不支持幂等键怎么办？

**小陈：**先看它有没有按客户端请求 ID 查询结果、有没有可可靠搜索的消息 ID，或者我们能否在企业发送网关建一个唯一发送登记。登记里的主键是“合同版本＋收件人＋业务发送意图”，并记录草稿指纹、审批 ID 与供应商回执。发送前先检查该键是否已有成功记录；发送后写回执。若供应商既不能去重也无法查询发信结果，网络超时时就无法自动安全重试，只能暂缓并人工查发件箱或供应商后台。框架不会凭空补出邮件平台没有的保证。给领导讲清“自动恢复”覆盖到哪一步，比拿一张漂亮流程图暗示绝对不重发更负责。

## 复跑与时光倒流，都可能让节点再执行

官方[LangGraph time travel 文档](https://docs.langchain.com/oss/python/langgraph/use-time-travel)说明，从过去检查点 replay 或 fork，后续节点会重新执行，包含模型调用和外部 API 请求。小陈提醒领导：“您看到时间旅行按钮，以为是看看历史；它其实可能让发送节点再跑一遍。”因此调查环境要隔离真实发送工具，或给动作加幂等保护与审批版本检查；不能拿生产 thread 回到“发送前”节点试图复现事故，然后无意又给客户补一封合同。检查点是可复演的状态，不是所有外部世界都能回到那个时间。

**领导：**可不可以直接在图里存 <code>sent=True</code>，省掉供应商查询？

**小陈：**它可以加速正常路径，但不能成为唯一真相。<code>sent=True</code> 可能在邮件服务受理但最终退信之前写入；<code>sent=False</code> 可能只是崩溃前没来得及写。需要区分“请求已提交”“平台受理”“已投递或退信”“结果未知”，业务回执的含义要与供应商文档对齐。合同外发更关注客户是否收到正确版本；平台受理不一定等于客户打开。Agent 回答“合同已发送”至少应有发送平台的受理回执，若业务要求确认送达，另设后续状态，不能让一个布尔值吞掉所有阶段。

## 一次完整的恢复演练，除了重启还要查错收件人

小陈在代码评审里把图拆成四个节点：<code>draft</code> 生成固定版本，<code>approve</code> 只做暂停与接收批准，<code>send</code> 检查批准、请求键和实际发送，<code>finalize</code> 记录回执并生成对客户或销售的说明。节点之间的边按批准或拒绝分流，拒绝直接进入停止分支。这样的图不保证万无一失，但能让人准确指出“外部动作在哪一个节点”；若草稿生成、审批和发送全塞进一个函数里，恢复时谁重跑、哪段可能重复，连开发者自己都难说清。节点边界的原则是把可重复计算与不可随意重复的副作用分开。

**领导：**state 里放回执不就行了，为什么还要一张发送账？

**小陈：**state 属于这个 thread 的运行进度，发送账属于跨重试、跨服务实例、甚至跨图版本都要可查的业务动作。领导审批页面可能重发一次 resume，请求队列也可能重复投递；两个工作进程若同时拿同一 thread 继续，不能各自认为“state 还没写已发，所以我来发”。发送账按稳定键建唯一约束，先争取该动作的执行权，其他工作进程看到已有处理中的记录就等待或对账。图检查点帮助续跑，不替数据库唯一约束处理并发重复。若只依赖内存里的锁，服务重启就像换班后把值班表撕了。

稳定键也不能随便拼。用“客户邮箱＋今天日期”会误把同一客户当天两份不同合同合并；用随机 UUID 每次重试都会换键，等于没有幂等。小陈把键定义为一次明确发送意图的 ID，绑定合同版本、收件人集合、附件指纹和审批 ID；同一意图重试复用同一键，改正文或收件人则创建新版本并重新审批。发送前比较键所绑定内容与当前草稿，发现不一致就拒绝，避免“键一样但邮件悄悄换了”。幂等键不是护身符，它要与业务上“同一件事”的定义一致。

邮件平台若支持提交时的幂等参数，发送网关传同一键最理想；若不支持，自己的发送账只能控制本方重复发起，网络超时后仍可能不知道供应商是否受理。小陈把状态写成 <code>PREPARED</code>、<code>SUBMITTED</code>、<code>CONFIRMED</code>、<code>UNKNOWN</code>、<code>FAILED</code>，每次变化有时间和证据。<code>SUBMITTED</code> 记录请求确实发出，<code>CONFIRMED</code> 要有供应商回执，<code>UNKNOWN</code> 需要查询或人工核实；不能把超时直接改成 <code>FAILED</code>。恢复器只对明确未提交或平台明确拒绝的动作重新发送，对未知先对账。这样同一流程可重跑，而外部世界不会被我们当成可随意撤销的沙盘。

**领导：**审批节点里放一个“发送预览”日志可以吧？

**小陈：**写日志通常可以重复，前提是日志有运行 ID、不会触发外部通知；若所谓“预览”其实会给销售发一封提醒，那就是副作用，放在 <code>interrupt()</code> 前可能恢复再发。官方文档明确提醒中断恢复时节点从头执行。小陈在代码评审里逐行标“纯计算”“可重复写入”“外部不可重复动作”。纯计算如渲染预览可以放节点前；可重复写入要有稳定键；外部动作放批准后且独立封装。这个划分比给节点取名“安全审批”更有效，名字不执行任何校验。

图的持久化存储也要选对。<code>InMemorySaver</code> 很适合本地演示，但重启便丢；生产使用持久 checkpointer，并设置存储备份、访问权限和保留策略。它保存的 state 可能含合同草稿、收件人等敏感信息，不能因为“只是 checkpoint”就不做权限管理；长期累积还会增加存储成本。thread ID 要稳定地映射到业务工单，不能让前端每次刷新生成新 thread，否则领导刚批完，系统又从头起一条新流程。恢复时用同一 thread 读取检查点，同时再从业务系统核查合同版本和审批状态，防止旧 state 在现实已变化后继续跑。

**领导：**如果两个人都打开审批页，一个点同意，一个点拒绝呢？

**小陈：**审批服务要有一条明确的状态机和并发规则，例如“首个有权限的终态决定，后续操作返回冲突”，或按组织流程要求双人审批。不能让两个浏览器各自给 LangGraph 发 <code>Command(resume=...)</code>，最后看哪个消息后到来。审批记录绑定操作者、时间、草稿版本和预期状态；状态从 <code>PENDING</code> 到 <code>APPROVED</code> 或 <code>REJECTED</code> 用条件更新。图接收的是已经由审批服务核实的结果，仍要确认与当前草稿一致。LangGraph 能暂停和恢复执行，谁有权批、两个决定冲突怎么办，是公司审批系统的责任。

小陈给“领导说同意”加了真实身份门。聊天里有人写“领导已经同意了”只是用户提供的一句话，不是 <code>approval_id</code>；一张截图也不能自动变成审批记录。审批页由登录身份确认操作者，批准结果存到业务系统，再作为 resume 的可信输入。若领导在审批后离职或权限被撤，尚未发送的动作要按当时制度重新核授权是否仍有效。审批结果可以被图保存，但审批的合法性和生命周期不应由模型文字推断。把暂停做出来只是第一步，把暂停期间谁能改什么说清才是完整流程。

## 一张“图状态／外部状态”对账表

小陈让值班人遇到重启时先看两列，而不是直接按“继续运行”。图列显示 checkpoint 在 <code>WAIT_APPROVAL</code>、<code>READY_TO_SEND</code> 或 <code>DONE</code>；外部列显示审批服务的终态、发送账的请求状态、邮件平台的回执。若图待发送而发送账已有确认回执，补图状态，不再发；若图已完成但邮件平台明确拒绝，标事故并处理客户沟通，不把图的 DONE 当事实；若图待审批但审批服务已有新批准，检查版本后恢复；若两边证据冲突，隔离该工单交人。每个组合有动作，避免值班同事只凭一个绿色节点判定世界正常。

**领导：**这张表听上去比那张图复杂。

**小陈：**因为它把图外的世界算进来了。流程图描述期望路径，对账表描述故障时实际可能留下的状态。若为了简洁删掉“邮件已发但图没记”的格子，系统恢复时就会把它变成第二封真实邮件。我们可以把多数格子自动化处理，人工只接结果未知和冲突；值班界面只显示需要人判断的几条。但在设计时必须把组合列全，不然自动化只能覆盖晴天。

小陈还给每次恢复设“最终一致”验收：同一发送意图在业务账只有一个有效发送键，供应商最多一条对应的有效邮件，图 state 指向那条回执；客户邮箱、合同版本和审批记录能互相核对。若邮件平台出现多条回执，不能靠把图改成 DONE 掩盖，必须进入重复外发事故处理。若回执无法查，保持 UNKNOWN 并有明确负责人和截止时间，不能无限卡在“系统正在恢复”。恢复完成的定义来自三本账一致，不是服务进程重新启动了。

**领导：**那能不能把邮件发送和检查点保存塞到同一个数据库事务里？

**小陈：**如果邮件只是写进公司自己的待发送表，写入表和图状态理论上可以在同一数据库里协调；真正把邮件交给外部供应商时，事务边界仍跨不出去。常用的办法是事务性 outbox：在本方数据库先以唯一业务键写待发送记录，再由发送工作进程投递，失败可重试，回执回填。即使这样，供应商受理后本方尚未记回执的窗口仍存在，仍需供应商幂等或可查询回执。outbox 能缩小“图说该发却没投递”的缝，不能神奇地让两个独立系统共享一次原子提交。

小陈给这个方案加一条操作边界：生产事故排查时，开发者可以在隔离环境复演图节点，但不能把真实邮件发送工具带进去；若必须在生产环境从旧 checkpoint 恢复，先核发送账并锁定相关意图，避免恢复器和人工操作同时发。图的时间旅行很适合查“如果当时拒绝会怎样”，前提是外部副作用被模拟或拦住。把回放安全当成测试环境配置的一部分，才能放心用框架给的调试能力。

值班交接时还要写明“这条合同现在谁持有处理权”：自动恢复器、客服人工，还是法务审核。交接给人后，自动任务应停在可见状态；人核实回执后再回填同一发送账。若自动和人工各自以为对方没处理，重复发送就会从软件故障升级成组织协作故障。恢复不仅要有机器的断点，也要有人的接手回执。

小陈的演练从审批前开始。领导拒绝，发送次数应为零；领导批准 V3，正常发一次，回执与附件哈希匹配；发送后杀进程并重启，同一 thread 继续，仍只保留一条有效外发记录；审批后把附件替换 V4，发送节点应拒绝旧批准；邮件平台超时但可能受理，恢复器先查 send_key，查不到时停待核。每条回放记录 state、checkpoint ID、审批版本、供应商消息 ID 与最终收件人。模型说“任务完成”不能代替邮箱回执。

**领导：**如果第一封发错了，幂等是不是会把错误固定住？

**小陈：**是，所以幂等只保证同一动作不会重做，不保证第一次动作一定正确。发错收件人或附件时，立刻停止后续自动发送，按公司通知与信息处理流程评估更正、撤回或联系客户；原发送记录不能删除重写成“没发生”，要保留事故事实。若需发一封更正邮件，那是新的业务动作和新的审批、发送键，不是拿旧键重试。恢复系统要能区分“未执行”“已执行正确”“结果未知”“已执行但错误”，每种后续处理都不同。图能把流程可视化，不能把已离开邮箱的内容收回来。

领导看完回放，终于问对问题：“检查点保存到哪、邮件回执在哪、失联时谁查？”小陈答：“图的 state 让我们知道续跑位置，发送账和供应商回执让我们知道外部实际结果，审批记录证明谁批准哪一版。三本账对齐，才能说一次点击只形成一条有效外发。”流程图还在，但这回每条箭头背后都有能被检查的凭据。
