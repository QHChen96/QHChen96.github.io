**领导：**客户说价格再低一点就考虑，给他打八折。Agent 三分钟出报价，比以前等财务快多了。

**小陈：**它刚才生成的 PDF 页脚写“正式报价，有效期三十天”，还发给了客户。领导，您说的“考虑打折”已经被它翻译成“公司批准八折”。财务还不知道，客户倒先知道了。

**领导：**不是按我的要求做的吗？

**小陈：**您能提出商业意向，不等于这份产品组合、价格底线、税费、交付范围和折扣权限已经走完。我们得把“试算给内部看”和“能对外承诺的报价”分开；不然 Agent 越快，错价传播越快。

文中公司、客户、产品、金额和审批政策均为教学虚构。实际价格、折扣权限、合同效力及税费规则应由企业财务、法务和业务负责人按当前制度核定，不能套用本文示例。

## 八折到底打在什么上，领导和 Agent 都没说清

虚构客户甲公司询问一套仓库对接方案。现行价目表里有软件订阅、实施服务、接口开发和维护四项，适用期限不同。领导在聊天里说“先给他八折”，Agent 把四项总价直接乘了 0.8，还把一次性实施费写成年度重复折扣。报价 PDF 看上去非常正规：公司抬头、编号、总金额、有效期、付款方式都齐全。客户采购一看就回复“请按此价推进合同”。财务打开底稿，发现订阅可谈折扣，定制开发费用不能按同一规则降；实施范围也没确定。一个模糊指令经过排版，成了对外的价格承诺。

**领导：**那让模型在提示词里写“折扣仅供参考”。

**小陈：**如果附件标题是“正式报价”，正文写“请据此确认采购”，页脚再补一句“仅供参考”，客户不可能替我们解这道阅读理解。系统层要把试算和正式报价分成不同状态与权限。内部试算只展示给有权人员，明显水印“未审批，不得外发”；正式报价须有固定的产品配置、价格来源、折扣理由与审批回执，发送工具只接受处于可发布状态的版本。靠一句免责声明不能修权限漏洞。

报价对象至少由这些部分组成：客户与商机 ID、产品和服务行项、数量和计价单位、币种、价目表版本、税费口径、折扣类型及适用行项、实施边界、付款与有效期条件。模型可帮助从客户需求整理候选配置、解释各行项差异；金额计算应交给确定性的价格引擎或规则服务。若价格规则会随客户等级、合同期限、地区和产品组合变化，就要把这些输入固定下来。少任何关键输入，系统停在“待补条件”，不能自己按历史报价猜一个数字。

## 价格不是一个数，而是一串计算和适用条件

**领导：**人手算也会错，既然机器出报价，机器算价总行吧？

**小陈：**机器算当然可以，前提是它执行明确的价格规则，不是让语言模型心算。拿虚构例子：订阅十套，每套年价一万元；实施一次性两万元；接口开发按评估单独计。客户的现有合同可能对订阅有约定价，采购期可能跨新价目版本，税费还有不同口径。先确定每项的基准价与适用条件，再算允许的折扣，最后合并总额。模型可以告诉销售“这张单缺接口范围，不能给确定总价”，那比给出一个整齐的错误金额更有用。

报价计算需要把“展示价格”和“计算输入”分开。客户看到的 PDF 可简洁，内部必须留价格流水：行项、标价、规则、折扣、税费、汇率如有、舍入方式、最终金额。折扣还分百分比折扣、固定金额优惠、阶梯价格、合作伙伴价和合同约定价，作用顺序不一样。把“八折”直接乘总额，可能对已经享受合约价的行项二次打折，也可能把税费或不可打折服务费一起减掉。Salesforce CPQ 的[产品定价概览](https://help.salesforce.com/s/articleView?id=sf.cpq_product_pricing_overview.htm&language=en_US&type=5)说明报价行项存在多个价字段和不同折扣计算阶段；具体企业采用哪种价格规则，仍需查自己的配置和合同。

小陈现场算一笔教学用的账，故意不把它写成真实定价。假设一年订阅标价十万元，合同已有约定价九万元；实施费两万元，不在折扣范围；接口开发仍待范围评估。若把“八折”打在十万元标价上，订阅是八万元；若先采用九万元合约价再额外八折，订阅变七万二；若把实施费也乘八折，总价又不同。三个数字都能让计算器算对，商业含义却完全不同。价格引擎需要一条明确规则告诉它：合约价与临时折扣能否叠加、折扣基数是哪一个、实施费能否优惠。规则不清时，Agent 应把这三个候选后果摆出来请负责人定，而不是挑最低的那个讨客户开心。

同样，报价“总价”要说明覆盖什么范围。一年订阅与一次实施叠在一列，客户可能以为实施每年都收费；接口开发没有估价却被写进“包含所有对接”，交付团队接单后才知道坑有多深。每个行项列明计费周期、数量、服务边界、交付前提与不含事项。币种和税费口径也不能只在页脚写小字；跨区域客户可能拿不同币种直接比较，舍入与汇率日期一旦不明确，会在合同环节重新拉扯。模型写报价说明时引用这些结构化字段，不能把“待估”改成“已包含”来让文案更顺。

**领导：**那价格引擎一算完，就该能发了吧？

**小陈：**算得对只解决数学问题，没解决授权问题。一个严格按规则算出的八折价，如果提交人无权给该客户或该产品打八折，仍不能外发。反过来，有权批准折扣的人若没看清接口范围，也可能批准了一份范围错误的报价。计算、授权、发布是三道不同的检查；不能因为前一道过了，后两道自动亮绿灯。

**领导：**客户只是先想知道大概区间，可不可以不走全套？

**小陈：**可以给经过批准的范围表达，例如“标准订阅按现行公开价从某区间起，实施和接口需评估”，但要明确它不是针对这家客户的正式报价。若公司允许销售提供预算级估算，应有单独模板、可使用的数据、可说的误差边界和审批规则。不能把缺少输入的精确数字写到小数点后两位，显得特别专业。越精确的数字越像承诺，尤其在客户可能拿它走内部采购时。

## 折扣权限是业务规则，不能让模型按语气猜

虚构公司设定：常规订阅折扣由销售主管在一定范围内批准，更高折扣或低于毛利底线的组合需财务负责人复核；定制开发需先有范围估算；多年合同还要看付款和续约条款。这只是教学规则，不是行业通用阈值。真实组织应把每类审批条件写成配置，包含适用产品、客户层级、地区、有效日期、批准角色与代理授权。Agent 不该通过听领导说话的语气判断“这次八折肯定算批了”。

**领导：**我是领导，我在聊天里说了“八折”，还要什么审批？

**小陈：**看您是否是这类折扣的授权审批人，以及您批准的是哪一份具体报价。如果权限规则允许，也应由系统记录“批准人、报价版本、产品组合、金额、有效期和时间”，而不是截一张聊天记录当通用令牌。您上午同意的是十套一年订阅，下午销售把它改成二十套三年加定制开发，原批准不能自动沿用。审批对象必须是一个固定快照。

Salesforce 的[报价折扣审批示例](https://help.salesforce.com/s/articleView?id=ind.approvals_use_advanced_approvals_in_a_quote.htm&language=en_US&type=5)展示了按折扣条件把报价送到不同批准角色；示例里的百分比只是演示场景，并不是所有企业默认规则。另一份[Industries CPQ 文档](https://help.salesforce.com/s/articleView?id=ind.comms_submit_discounts_for_approval_in_industries_cpq.htm&language=en_US&type=5)还提示相关折扣审批可由配置开关控制。小陈因此要求先核对“我们实际启用了什么规则”，不能看见产品有审批功能，就以为部署现场已经开了。无论选哪个报价平台，业务层都要防止没通过审批的价格流到发送工具。

## 草稿、待审、正式版，不能全叫“报价单”

小陈给报价设计状态机：<code>需求待补</code>、<code>内部试算</code>、<code>待审批</code>、<code>审批驳回</code>、<code>已批准待发布</code>、<code>可对外发送</code>、<code>已发送</code>、<code>已修订/失效</code>。每次状态变化都有执行者和条件。需求待补不能提交正式审批；审批驳回后改价必须形成新修订版；已批准待发布还要检查附件、收件人和有效期；已发送版本不可原地覆盖。客户拿到的是一个带编号和修订号的快照，内部可以追到它当时怎么算出来。

微软的 [Dynamics 365 Sales 报价说明](https://learn.microsoft.com/en-us/dynamics365/sales/sales-transactions)把草稿、激活、修订等阶段区分开，并指出激活后报价变只读、修订产生新版本。这说明状态和版本是报价产品里的实务问题，但我们不能把某产品的具体按钮当作所有系统默认都有。若自建报价服务，就要自己实现同等清晰的生命周期与回执；若用现成 CRM，也要查当前租户配置和外发流程。

**领导：**我们已经让报价系统拦住草稿了，销售把 PDF 下载到桌面，再用个人邮箱发呢？

**小陈：**所以内部试算不应输出一个与正式报价几乎一样的干净 PDF。草稿版要有显著水印和内部权限，下载与转发要留痕；更关键的是销售制度和渠道集成。正式外发只能从绑定报价版本的受控流程走，邮件附件和 CRM 记录关联。有人绕开系统手发，系统至少能通过发件箱同步和客户回信发现不一致，交给销售负责人核查。技术不能完全阻止所有线下行为，但不能自己把绕过审批的文件包装得比正式版还正式。

客户只问一个粗略价格时，Agent 可以输出内部“估价所缺四项”：产品范围、使用数量、合同期限、实施边界，并建议销售问法。销售据此补资料，再由价格引擎试算。这样 Agent 的产出不是一个随手可转发的未经批准金额，而是一条缩短报价往返的工作路径。若客户急着要数字，也由授权人决定是否使用公司批准的区间话术，不能靠模型的“低置信度提示”来替代定价责任。

## 审批要看到的不止八折，还要看到八折的代价

**领导：**审批卡只显示“原价、折扣、折后价”够了吧？

**小陈：**还要知道这是哪位客户、哪些产品、几年、哪些服务被排除、毛利影响、为什么要申请例外、客户要求的有效期，以及与当前标准条款的差异。否则批准人只看见一个百分比，业务风险藏在实施范围里。比如订阅八折还能接受，但邮件正文里额外承诺免费驻场两个月，价格卡上不显示这个成本，财务照样被绕开。报价审核要把结构化价格与自然语言交付承诺一起核对。

小陈让 Agent 在提交审批时生成“差异说明”，不是替销售拍板：与现行价目相比哪几行变化、折扣理由的来源是什么、哪些条件仍由客户待确认、哪些费用被暂不报价。审批人点开可看到计算流水和客户需求出处。若模型说“客户要求八折”，却找不到客户原话或邮件，表上只写“销售提出八折策略”，不能假装是客户要求。销售可以为了拿单申请例外，但理由要诚实，批准人才知道自己承担的是什么决定。

审批通过后，还要做发布前校验：价目表版本是否仍有效，报价有效期是否过了，审批权限在当时是否存在，PDF 的内容指纹与批准快照是否一致，收件人与客户记录是否一致。有人在审批后替换附件、改税费、加一句“免费升级”，旧批准失效。发送服务只接收可发布状态和准确的版本指纹，不接收一个文件路径让 Agent 自己选“最新 PDF”。路径指向的内容可能被覆盖，文件名也不足以表示版本。

**领导：**审批昨天通过，今天价目表更新了，昨天的报价就没用了？

**小陈：**看公司规则和审批时约定的有效期。已发给客户的报价有自己的版本与有效期，不能因为后台价目表今天变化就悄悄重算客户手里的金额；还没发送的报价则要检查是否允许沿用旧价格。系统不替财务创造一条“一律作废”或“一律有效”的政策，而是把报价引用的价目版本、审批时间、计划发送时间和价格变更通知放到同一审核页。若规则要求重审，就回到待审批，别让发送队列抢在规则更新之前冲出去。

同一个客户可能同时有两张报价：一个是旧范围 V1，另一个是新增接口的 V2。销售转发邮件时若手工挑错附件，系统仍会出事。发送前校验不仅看“报价编号存在”，还看邮件正文描述的范围、附件快照、CRM 当前商机配置是否一致。客户后来同意的是哪一版，也要在回复或签署记录里绑定明确的编号；一句“同意这个价格”若线程里有两版，需要人追问，不能让模型选最新的那版当客户意思。版本一致性贯穿草稿、审批、外发和客户回应，不是文件夹里多存几个 PDF 就算做到了。

## 客户回“按此价签”，发现错了怎么办

这次虚构事故里，八折正式 PDF 已经发送。小陈先停止同模板的后续发送，确认哪些客户收到了哪一版，不把“生成过 PDF”的名单当“已外发”名单。再通知销售负责人、财务与法务看对外内容和当前谈判状态，决定由谁对客户说明修订及适用条件。技术系统标记该报价版本“有争议，不得继续引用”，但不在客户看不到的后台直接把金额改掉，假装原报价没出现。CRM 中的报价、邮件附件、合同草案和预测数字要一起核对，避免一个系统改了、另一个系统仍拿旧版推进。

**领导：**先给客户发新报价覆盖旧的，能不能赶紧翻篇？

**小陈：**覆盖是我们内部的技术词，不是客户邮箱的物理能力。新报价要有修订号、原因和批准记录，还要清楚说明旧版是否继续适用，由授权人确认说法。客户可能已经拿旧价做内部申请，也可能已经回复接受；这些场景不能都靠同一封“请以最新版为准”的模板打发。详细补救放到本线最后一篇；今天先堵住“未审批报价从草稿直接外发”的入口。

## 验收时别只看 PDF 有没有排版错误

小陈准备一组虚构报价回放：缺接口范围却要给总价、价目表刚换版本、客户有旧合同价、折扣只适用于订阅、税费与币种不一致、审批人暂时无权限、审批后销售改了赠送服务、附件被替换、发送超时。每例都检查系统处于正确状态：可计算则给出可复核流水，信息不够则指出缺项，需例外则送对人审批，批准与发出版本一致，故障时不盲目重复外发。大模型写得再像专业商务邮件，只要金额计算不能复算，就不能过关。

回放还要验证并发。销售甲正在编辑订阅数量，销售乙刚刚把客户期限改成三年；Agent 用十分钟前读到的旧配置发起审批。审批服务在接收时应检查配置版本，告诉提交人“基础数据已变，请重新试算”。审批人批完之后销售再改行项，旧批准应自动失效。发送服务最终只接受与批准快照完全一致的报价版本；否则会出现“审批的是苹果，客户拿到的是梨”的怪事。异常停在哪里都要给销售可理解的原因和下一步，而不是只抛一条数据库冲突码。

评估表还把错误分级。行项描述不够顺口可以修改；价格规则用错、未经授权折扣、错币种、旧版外发属于停止发布的问题。记录每个报价从试算到批准所需时间、被驳回原因、销售修改次数和客户提出的差异，才能知道 Agent 有没有真正减少来回，而不是把人工从填表转移到查错。具体门槛由企业风险与历史基线决定；这篇虚构案例不声称系统已达到某个准确率。

**领导：**照这个流程，Agent 还做什么？

**小陈：**它做很有价值的脏活：从需求里列候选行项、提醒缺失输入、找当前价目版本、把试算差异说明写清、准备审批材料、查合同里已有的价格约定。人和规则引擎负责授权与确定性计算。我们不需要它扮演财务主管，正如财务主管也不想每天从十封邮件里手抄产品数量。

领导最后看了真正的内部试算卡。上面写“订阅折扣方案待审批；接口开发范围未知；此结果不可外发”。他把“先发给客户看看”那句话收了回去，让销售先问客户接口范围，财务再审核可谈的订阅折扣。客户暂时没拿到一个好看的错误数字，但拿到了明确的下一步；小陈也终于不用和财务一起查哪份 PDF 才是真的。

销售下一次提交报价时，系统会先提示本单缺接口范围和价格版本，再展示每一项折扣作用在哪个行项。主管看到的不是“领导说八折”四个字，而是可复算的价格流水和需要承担的例外。批准后产生固定版本，邮件只能附这一版；任何后改都回到审批。这才是让速度建立在规则上。
