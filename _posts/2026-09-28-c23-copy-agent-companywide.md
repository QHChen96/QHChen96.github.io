**领导：**客服项目能写草稿了。明天把同一套 Agent 给财务、人事、IT 各复制一份。反正换个知识库就行。

**小陈：**要是真只换知识库，客服的“查询当前订单”工具可能被带进人事场景；人事的请假规则可能被当客服条款引用；财务的“生成付款建议”甚至会被误听成“可以付款”。复制按钮按下去，三个部门的权限不会自动长出边界。

小陈把客服项目拆成两层。底下一层是可复用的运行能力：任务记录、工具调用日志、限步、失败暂停、评测回放、版本发布。上面一层是不能照搬的业务合同：谁能看什么数据、哪条规则生效、谁批准动作、出错谁接单。**复制底座可以省工，复制授权就是给事故发邀请函。**

## 先挑第二个场景，不拿部门名称当需求

**领导：**那就按部门挑一个负责人，每人做一个试点。

**小陈：**同时开三个试点，会把核规则、建接口和标评测样本的人全部拉散。先拿三个候选任务比较，而不是比较哪个部门喊得大声。

| 候选任务 | 量与价值 | 证据能否核对 | 动作风险 | 先期判断 |
| --- | --- | --- | --- | --- |
| 财务解释报销进度 | 高频，减少来回问 | 状态能查，但涉及个人财务信息 | 误报付款或改报销单风险高 | 暂缓，先做权限和审批设计 |
| 人事回答请假余额 | 高频，答案依个人身份和地区规则 | 余额可查，规则版本复杂 | 隐私与错误承诺风险高 | 暂缓，先补身份与规则适用性 |
| IT 工单进度查询 | 高频，已有工单状态和负责人 | 可由 IT 工单系统返回 | 只读、可明确转人 | 作为第二场景试点 |

这是**虚构公司的候选表**，不是所有企业都该选 IT。我们选它，是因为输入、权威事实和出口都比较清楚：员工问“我的电脑报修到哪了”；系统确认员工身份，只查本人报修单；Agent 把状态和下一步讲清；查不到或状态冲突就转 IT 服务台，不替工程师承诺修好时间。

## 用一张报修单，试出“复用”有没有越界

**领导：**原客服系统已经会查工单，这活应该半天就好。

**小陈：**工单两字一样，主人未必一样。客服工单绑定客户和订单，IT 工单绑定员工、设备和部门。第二场景要重新写四份契约：身份映射、只读工具返回字段、状态解释规则、人工接手队列。工具服务必须按员工身份校验报修单归属，不能仅靠模型在提示词里“请勿查他人”。

试点范围也锁死：只处理“本人已创建的 IT 报修单进度”，不创建新报修、不改预约、不查同事设备、不碰管理员权限。选一批脱敏历史样本，覆盖正常、已关闭、等待配件、跨员工查询、工单系统超时和同名员工。每条都有 IT 负责人给出的可接受答复与转人条件。客服原有的评测框架可以复用，**评测题库不能直接复用**，因为客户退款与员工报修的危险点不一样。

**领导：**同名员工为什么也要单独测？

**小陈：**因为员工在聊天框里说“我是小陈”，并不等于系统确认他就是报修单上的小陈。我们用登录身份的稳定员工 ID 到 IT 工单系统查“本人有权看的单”，姓名只用于展示，不用作授权键。再拿一个反例：部门管理员说“我替组员问进度”。管理员是否能代查，要由 IT 工单权限规则决定，Agent 不能看见“管理员”三个字就放行。客服里校验的是客户与订单，到了 IT 要校验员工与报修单；复用的是调用审计和拒绝路径，**不是那条鉴权规则本身**。

小陈把试点分成三段：第一周只跑脱敏历史工单，IT 负责人标对错；第二周在内部服务台给坐席看草稿，不对员工自动回复；连续观察到错误与转人情况后，再选择有限的只读自动答复。每一段都有退出条件：跨员工取数一次即停，报修状态无来源却编造预计修复时间即退回草稿模式，服务台接不到转人工单就停止扩量。这样推广节奏不是按部门数冲刺，而是按可承担的风险前进。

**领导：**什么时候能从试点复制成平台？

**小陈：**先证明第二场景独立可靠：跨员工访问被服务端拒绝；回答能点回当前工单状态和查询时间；状态未知不编修好日期；转人后有 IT 队列负责人；版本发布和回滚能单独进行，不影响客服。如果这些过了，再把共同的日志、评测与发布能力抽成平台接口。没过就收窄或停，不用“未来规模效应”替今天的权限漏洞买单。

底座抽取时也保留“业务插槽”：每个场景必须提供身份核验器、权限判定器、权威状态来源、人工队列和结案依据。少一个插槽就不允许创建“自动回复”应用。这比做一个人人都能填提示词的万能平台慢半步，却能防止下一位同事只换标题就把客服退款话术贴进人事系统。

## “可复用”到底复用到哪一层

**领导：**你说底座可复用，听着还是很抽象。给我拿代码和接口说话。

**小陈：**运行底座接收一个带场景 ID 的任务，做统一的超时、限步、轨迹、版本和失败暂停；它不直接认识“退款”或“请假”。每个业务场景提供自己的配置包：谁是请求者、权威数据在哪、允许哪些只读和写入动作、规则版本如何选择、转给哪个队列、什么叫完成。底座可以统一记录 `run_id`，但读取订单与读取报修单走两个互不通用的工具服务，令牌受场景和请求者约束。

| 层次 | 可以共用 | 必须各业务重建或确认 |
| --- | --- | --- |
| 运行控制 | 步数上限、取消、超时、重试框架、追踪 ID | 哪些动作可安全重试，何时停 |
| 证据结构 | 来源 ID、版本、生效时间、引用定位字段 | 哪些资料对当前人、当前问题适用 |
| 评测框架 | 样本格式、回放器、错误分类、报告模板 | 历史样本、人工标准、高风险红线 |
| 权限接口 | 拒绝优先、最小权限、审计格式 | 员工与报修单、客户与订单等具体关系 |
| 发布能力 | 影子运行、灰度、版本绑定、回滚 | 生效日期、审核负责人、业务通知 |

**领导：**为什么连重试规则也不能全共用？

**小陈：**框架可以提供重试器，决策不能由框架替业务下。查 IT 工单状态是只读，短暂超时后按限次策略再查通常可行；创建报修单是写操作，第一次可能已经建成功但回执丢了，盲目再试会建两张；财务付款更不能跟查单共用“超时就再点一次”。同样，错误分类可以统一叫“结果未知”，但补救动作要由各系统的业务流水和负责人决定。把业务差异封装进场景配置与工具实现，底座才是真的可复用，而不是强迫全公司遵守客服的幸运路径。

小陈给每个场景做一份“能力声明”：`read_own_ticket`、`draft_internal_reply` 等能力写明输入、输出、所需身份、数据分类、是否有副作用和失败语义。构建器只能从已批准的能力目录里选工具；不能让场景作者在提示词里随手写“顺便查询员工工资”，然后底层通用令牌刚好有权。服务端每次请求都核权限，[OWASP 的授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)强调拒绝优先与每次请求的授权检查。模型说“我已获领导同意”不等于授权服务有那条记录。

## 第二场景怎么排序：价值分数之外，还有资格门

**领导：**财务进度查询量比 IT 多，为什么不先做财务？

**小陈：**“多”只是一项收益。候选表先过资格门：有没有明确的权威事实来源；请求者身份能否核验；数据能否按最小字段提供；动作能否先限在内部草稿或只读答复；出错后有没有业务负责人接手。财务若暂时只有宽权限数据库接口，哪怕咨询量很高，也得先补数据接口和审批边界，不能让平台直接连全量报销表。IT 报修进度的收益也许较小，却能更快验证底座从客服迁到另一业务时哪些接口真的通用。

过资格门后才排序。小陈给每个候选记五列：月问题量、每单目前人工触碰时间、标准答案可查证的比例、数据敏感与动作风险、集成和知识维护成本。再看**变更频率**：人事规则按地区和合同类型变化，知识负责人若无法及时维护，检索能力再好也会答旧规则。最后看**可回退性**：内部 IT 进度答错还能客服纠正，自动批准付款的外部后果要重得多。排序不是靠一个神秘总分，而是资格门、价值估算和风险承受能力依次决策。

**领导：**那 IT 试点的“完成”怎么定义？

**小陈：**员工问“报修到哪了”，Agent 要给出当前工单状态、查询时间、下一位处理人或下一步、未知项；如果状态是“等待配件”，不能编成“明天修好”。问题可以在提供准确进度后结案，也可以因员工进一步请求改约而转人；两类要分开。不能拿客服场景里的“客户收到一条消息”当 IT 的完成标准。IT 服务台确认结案依据，员工再次追问同一报修单要关联原工单，避免重建问题掩盖未解决。

## 用一次越权尝试，看看底座到底有没有隔离

小陈准备了三个账户：报修人甲、同部门同名员工乙、部门管理员丙。甲问自己的报修单，工具返回必要状态；乙在聊天里粘贴甲的报修单号，工具必须拒绝；丙请求代查，若 IT 制度允许管理员代办，服务端要验证丙的具体角色与这张单的关系，否则同样拒绝。提示词里写“只查本人”可帮助模型选择工具，但真正的拒绝要发生在工具服务端，轨迹里能看到拒绝原因和关联 ID，不能把甲的设备序列号一起记进日志。

**领导：**如果模型在回答里没泄露，服务端其实查到了甲的数据，也算过关吗？

**小陈：**不算。隐私边界看数据是否被不该看的运行读取，不只看最后一句话有没有说出来。模型可能把取到的内容带进轨迹、日志或后续摘要；即使最终拒答，内部已经越权。验收要同时检查工具请求、服务端授权结果、模型上下文和日志。这个反例正好证明“复制客服工具”和“复用安全框架”的区别：框架负责每次调用有授权链，IT 场景负责授权链里员工与报修单的具体关系。

## 发布与恢复：第二场景不能拖着客服一起翻车

两条业务线可共用运行底座，但发布包要隔离。客服规则更新不能改变 IT 的提示、工具白名单和评测阈值；IT 知识库换版也不能让客服工单搜到设备维修 SOP。每个场景有独立 `release_id`、样本集、影子运行结果和回滚开关；底座升级则先在两条线的回归集上通过，再灰度。若底座的日志组件故障，两条线都可能受影响，这类共享故障要有统一值班人和影响范围清单。

**领导：**IT 系统周末挂了，Agent 怎么恢复？

**小陈：**先停自动给具体进度，保留员工请求并转 IT 值班队列；只读查询可在服务恢复后补查，但已由服务台人工答复的工单不能再自动补发旧消息。恢复脚本按工单当前状态与发布时间重算，不盲目重放所有失败任务。回滚时只回滚对应场景发布包；如果是共享底座版本导致两边异常，则暂停相关能力并回到上一版兼容底座。事故复盘看跨场景影响，防止“客服没出错”就漏掉 IT 的积压。

## 领导加了四道面试题

**领导：**第一题，什么是 Agent 平台化时真正可复用的东西？

**小陈：**运行控制、追踪格式、评测机制、发布和故障接管等通用能力；业务身份、权限、知识适用性、动作审批和结案依据必须由场景拥有者定义。抽象的边界是“同一机制、不同业务合同”。

**领导：**第二题，为什么不先挑咨询量最大的场景？

**小陈：**量大只提高潜在收益，也放大错误影响。先过身份、权威数据、最小权限、人工兜底和可回退性等资格门，再用量、人工成本与维护成本排序。高价值但边界未建的场景可以成为后续工程任务，不直接成为自动答复试点。

**领导：**第三题，什么叫最小权限落到实处？

**小陈：**不是提示词写“仅本人可查”，而是工具服务每次根据已验证身份、当前资源与具体动作判定；只返回本任务必要字段，拒绝有审计，跨用户测试实际打到服务端。通用平台令牌不能绕过业务授权。

**领导：**第四题，怎么证明“复制成功”而不是“又搭了一个演示”？

**小陈：**第二场景用自己的历史难题集通过，客服功能未回退；跨员工取数被拒绝，超时不编状态，人工队列能接单，发布与回滚独立；另外记录从选题到上线的真实工程工时。若每新增场景都要从头改底座，平台化的收益也要重新核算。

## 一份能让第三个部门照着填的接入合同

小陈把 IT 试点走过的坑做成接入表，给未来的财务与人事负责人。第一栏是**任务边界**：用户究竟问什么，什么问题不接；第二栏是**数据清单**：哪些字段进模型、哪些只在业务系统展示、日志保留多久；第三栏是**动作清单**：只读、草稿、对外回复、写入业务系统分别由谁批准；第四栏是**失败路径**：工具超时、证据冲突、身份不明、发送未知时怎样停和交人；第五栏是**评测与发布**：样本负责人、红线、灰度和回滚。表格未填齐，平台团队只提供咨询，不给开自动回复开关。

**领导：**各部门会说我们设门槛太高，拖慢效率。

**小陈：**把“缺什么”变成可执行任务，而不是把人挡在门外。财务缺按员工身份查询本人报销单的窄接口，就由财务系统负责人交付；人事缺地区和合同类型的规则版本，就由人事政策负责人整理；IT 缺值班接手回执，就由服务台补队列。平台团队交付统一的接入测试工具和轨迹模板。责任分到具体系统和人，下一次会议就能看进展，不会陷入“AI 团队再调调提示词”的无限循环。

每个接入合同还有**责任矩阵**。业务负责人签准任务和可说内容，系统负责人签权限与回执语义，安全或隐私负责人审数据流，客服或服务台负责人签人工兜底，平台负责人签运行和回滚。出了错先按轨迹定位：是知识版本错、工具授权错、模型判断错、审批漏看，还是渠道重复发送。共同底座的错误由平台修，场景规则错误由业务修，不能因为两者都叫 Agent 就没人负责。

**领导：**那第三个部门接入时，是否还要重新跑所有旧题？

**小陈：**要分层回归。底座改了限步、追踪或授权框架，客服和 IT 的关键样本都要重跑；只改某个部门的业务知识，至少跑该部门全套样本和跨场景隔离样本，确认它没有被别的场景检索到。最有价值的跨场景题不是“正常问答”，而是故意把客服订单号贴进 IT 报修聊天，把 IT 设备序列号塞进财务咨询，检查工具与检索边界都拒绝。各业务数据放在不同命名空间或访问域，光靠提示词写“不要混用”不算隔离。

小陈给领导算了一笔复制效率的账：第二场景从零搭建要花多少工程日，复用底座后节约了哪些日，新增的场景治理又花了哪些日；第三场景再测一次。如果只节省了画流程图的半天，却新增一周排查共享权限问题，就不能在年终总结写“平台化显著提效”。复用收益是**重复劳动确实减少，且风险没有从一条线传到另一条线**，不是“已经有三个部门在用同一个界面”。

最后的上线单写三个具体时点：历史回放通过后只给 IT 坐席看内部草稿；坐席在真实工单中连续确认来源和转人工记录可靠后，才开放有限的自动答复；新版本若出现跨员工取数、无来源的维修承诺或无人接的转人工单，立即回到上一阶段。每阶段保留负责人签名、样本与发布版本，跨部门团队才知道“可用”究竟是哪个范围、哪个日期、哪种权限下的结论。若试点停止，报修工单和待办仍归 IT 系统与服务台，不因 Agent 项目下线而消失，积压任务由值班负责人逐项清点。

**领导：**给我一句能写进会议纪要的话。

**小陈：**“先试点 IT 本人报修进度，只读、不外改；共用运行底座，权限、规则、负责人和验收重新设计。”这样财务和人事以后也能来，但不用明天一起踩雷。

**领导：**客服试点有成效，销售和财务能不能复制同一套权限？

**小陈：**可复用追踪、评测、审核和回退框架，不能复制客户数据访问范围与业务动作。销售助手要核 CRM 客户归属和外联审批，财务要核资金权限与对账，工单场景的“可查本单”并不自动变成“可查全公司”。每条业务线另定对象、动作、负责人和红线样本，先只读试点再扩。
