**领导：**小陈，Pi 对话跑久了越来越贵。我有个方案：把前面一百条聊天删了，再给模型一句“接着干”。既省钱又省事，明天写进团队规范。

**小陈：**“接着干”最怕的就是不知道前面到底干了什么。您昨晚让它提交过一个发布单，现在只剩一句“接着干”，它可能把同一份发布再发一次。我们先分三本账：**会话文件里存了什么、下一轮模型实际看见什么、外部系统已经发生什么**。三本账重叠，但不相等。下面的发布单、日志和编号都是教学虚构；Pi 的文件格式与压缩行为按 [官方仓库这一版](https://github.com/earendil-works/pi/tree/5257d0d5f3ab7d42550804f32c67a77b49f485d4)核对。

## JSONL 不是把聊天一句句往下贴那么简单

Pi 的 [会话格式文档](https://github.com/earendil-works/pi/blob/5257d0d5f3ab7d42550804f32c67a77b49f485d4/packages/coding-agent/docs/session-format.md#L1)说明：持久会话是一份 JSONL，每行一个对象。第一行是会话头，后续条目有 `type`，绝大多数带 `id` 和 `parentId`。这些父子指针把条目组成树。当前条目指向一条活动分支，从根沿父指针走到当前叶子的那条路径，才是本次继续工作的历史。用户从中间某条消息“再试一种修法”，会在同一文件里长出另一条分支；旧分支不会因为屏幕上切走就消失，也不会自动混进新分支。把文件当线性聊天记录，恰恰会在恢复时把两条相互排斥的试验都当成已确认事实。

原始 JSONL 里的字段比较多。小陈把它缩成下面这份**结构示意，非真实会话日志**；重点是 `id` 和 `parentId` 如何决定分叉：

```json
{"type":"session","version":3,"id":"S1","cwd":"/repo"}
{"type":"message","id":"U1","parentId":null,"message":{"role":"user","content":"检查发布单"}}
{"type":"message","id":"A1","parentId":"U1","message":{"role":"assistant","content":"方案 A"}}
{"type":"message","id":"B1","parentId":"U1","message":{"role":"assistant","content":"方案 B"}}
```

若活动叶子是 `B1`，下一轮路径是 `U1 → B1`；`A1` 仍在文件里，却不属于这条路径。真实格式还有时间戳、完整内容块、工具调用与使用量等字段。树指针告诉 Pi 如何重建对话，不会把方案 A 已经发出的 HTTP 请求撤销。这个例子里若 A 分支创建过发布单，切到 B 后必须用发布单 ID 去业务系统核对，不能因为 `A1` 不在本轮模型输入里就说它没发生。

**领导：**我从界面里切回上一步，为什么发布单不会跟着回滚？游戏存档都能。

**小陈：**会话树保存的是消息与运行轨迹，不是所有工具作用的事务快照。Git 工作区、远程 CI、邮件服务器、支付系统有各自状态。Pi 的分支导航可以改变下一轮模型看到哪段对话，但发出去的网络请求不会倒着飞回来。真要实现“撤销”，业务系统要有撤销 API，并确认那次提交是否可撤；有些动作根本不能撤，比如客户已经收到邮件。回到旧分支后，先查外部回执，再决定接着做哪一步。把“模型忘了”误写成“世界恢复原样”，比多花一点 token 可怕得多。

## 哪些条目会改变下一轮请求

小陈给领导打开格式里的几类条目。`message` 不只是用户和助手的文本，还可能是 `toolResult`。工具结果里有调用 ID、工具名、内容、错误状态；它是判断上一轮到底返回了什么的重要依据。系统消息也不是每轮复制完整提示：首个请求可保存完整提示章节和工具声明，之后的系统消息记录章节变化、`toolsAdded` 和 `toolsRemoved`，回放时按顺序应用，才知道当时模型被允许调用什么。`model_change` 记录选择的模型；assistant 消息记录实际回答的物理模型。若扩展使用虚拟模型做路由，两者可能不是同一个名字。只抓最新一条“当前模型”会遗漏当时究竟是哪家提供方答了关键那句。

此外还有思考级别变化、使用量条目、压缩摘要、自定义扩展条目。使用量可以计入成本，但不一定进模型上下文；自定义数据也可能被扩展用来恢复自己的状态，却不发给模型。一个“会话文件有这行”的事实，不能直接推断“下一轮模型看见这行”。Pi 在 [`SessionManager` 与会话投影](https://github.com/earendil-works/pi/blob/5257d0d5f3ab7d42550804f32c67a77b49f485d4/packages/coding-agent/src/core/session-manager.ts)里根据活动分支和条目类型重建上下文。公司要做审计导出，应保存原始条目与投影视图的区别；否则某条已被压缩或上下文编辑省略的旧回复，会被误当成当前模型的直接依据。

**领导：**我只关心成本。它能不能像人一样把旧事压成一句“上次讲过了”？

**小陈：**能压缩，但摘要不是无损压缩包。Pi 的 [压缩机制](https://github.com/earendil-works/pi/blob/5257d0d5f3ab7d42550804f32c67a77b49f485d4/packages/coding-agent/docs/compaction.md#L25)会在上下文使用接近窗口减预留空间时触发，或用户手动 `/compact`。它从已定稿的会话投影里找截点，默认保留近期一段，旧消息交给模型总结；然后追加 `CompactionEntry`，带摘要和 `firstKeptEntryId`。下一轮请求用系统提示、摘要、被保留的消息拼出较短历史。原始 JSONL 条目仍在，旧工具回执不会因摘要而从磁盘凭空消失。这里“省”的是**后续模型请求里的上下文 token**，不是把审计记录删光。

压缩当然有损。若一段旧讨论里藏着“上线前必须经财务审批”的约束，摘要漏写，下一轮模型可能按缺约束的世界继续。小陈建议把关键条件放在稳定的项目规则或业务审批系统里，而不是只靠一次对话口头说过。对一次长任务，压缩摘要至少要保留目标、未完成步骤、已执行的外部动作和回执 ID、当前文件差异、禁止事项、失败与未知状态。不能只总结“我们讨论了发布流程”，那和领导会议纪要写“大家深入交流”一样，对下一步毫无帮助。

再把 [`compact()` 的主干](https://github.com/earendil-works/pi/blob/5257d0d5f3ab7d42550804f32c67a77b49f485d4/packages/coding-agent/src/core/compaction/compaction.ts#L987)压成一段**教学改写**。真实实现还处理超长单轮、模型调用重试、文件清单和用量统计，这里只展示摘要怎样变成下一轮的边界：

```ts
async function compact(preparation, model) {
  const { firstKeptEntryId, messagesToSummarize, previousSummary, tokensBefore } = preparation;
  const generated = await generateSummaryWithUsage(
    messagesToSummarize, model, previousSummary /* 其余参数略 */
  );
  return { summary: generated.text, firstKeptEntryId, tokensBefore, usage: generated.usage };
}

const result = await compact(preparation, model);
sessionManager.appendCompaction(
  result.summary, result.firstKeptEntryId, result.tokensBefore,
  undefined, false, result.usage
);
```

`messagesToSummarize` 是要压短的旧区间，`previousSummary` 使多次压缩能接续历史，`firstKeptEntryId` 指明哪条原消息开始仍按原样送给模型。`tokensBefore` 是压缩前的估算用量，`usage` 来自摘要生成；此例没有自定义 `details`，并以 `false` 表示摘要并非扩展生成；重点是追加一个摘要条目，而不是对旧 JSONL 行做就地删除。读者若只记一句：文件里有原文，模型下一轮却通常只拿到摘要加近期消息，就抓住了压缩的本质。

## 压缩前后，哪几段真的换了位置

压缩不是随机抽掉前一百条。源码文档解释，Pi 通常在用户消息的边界切，把先前较旧的部分总结，保留最近消息；不会从工具结果中间切开，让一个没有对应调用的 `toolResult` 孤零零站在模型面前。若单个用户任务本身太长，截点可能落在该任务内部，需要处理这一段的前缀。重复压缩时，还要把上次保留但这次进入旧区间的消息重新纳入总结，避免“摘要套摘要”漏掉中间一段。压缩记录带 `firstKeptEntryId`，这个字段是恢复上下文的边界，不能随手当普通文本 ID 重写。

**领导：**若模型接口超时，Pi 压缩完重试，会不会把上一次失败的那段“已发送”也当成果？

**小陈：**这正是要读恢复顺序的地方。Pi 文档说，对某些上下文溢出或过早 `length` 结束的情况，可以做一次压缩后重试。已完成的失败尝试先进入 `turn_end`、`agent_end` 等可观察事件；随后通过 `context_edit` 将该尝试的 assistant 和工具结果从下一轮模型投影里省略，再在需要时压缩，最后开启新一轮。原始历史仍可审计，模型下一轮不必被不完整尝试误导。但这套处理只说明**模型上下文怎样修复**，不能承诺一次已执行的外部工具没有副作用。尤其工具参数若在模型响应长度截断时不完整，Pi 会拒绝执行那批调用；若工具已经实际发出请求，处理方式又不同。不能把两类失败都叫“重试即可”。

## 虚构事故：发布单到底发过没有

小陈拿到演示现场的三条材料：会话里模型说“准备提交发布单”，工具调用 `create_release({id: "R-204"})` 显示网络超时，团队工单系统里却查到编号 `R-204` 已处于“待审批”。这是典型的**结果未知被误当未发生**。如果按领导最初方案删聊天，让 Pi 重新创建，系统可能拒绝重复，也可能生成另一张发布单，取决于接口契约。正确恢复是先拿业务键和请求 ID 查工单系统：若已有待审批，记录其 ID，继续审批前置校验；若确认从未受理，才用同一幂等键重试；若系统无法判断，先让值班人核对，不要让模型新造 ID 赌博。

### “失败”在会话里至少有四种写法

小陈把会话中的失败逐个指出来。第一种是模型请求本身没有得到可用响应，例如网络断开或提供方报错；这时本轮可能还没产生任何工具调用，但之前回合的工具动作仍在。第二种是模型输出被长度限制截断，特别是工具参数不完整；Pi 不该执行残缺调用，恢复可以考虑整理上下文后重试模型请求。第三种是工具执行返回失败，例如文件不存在、测试断言红、权限插件阻断；错误结果属于会话证据，下一轮可以基于它改道。第四种是工具发起外部动作后客户端超时，服务端可能已经受理；这不是简单的“再跑一次”，必须查远端。若只看最后一条 `assistant.stopReason`，可能把四种情形揉成一个 `error`。恢复系统应在日志里记录失败发生在提供方、预检、工具内部还是远端确认阶段。

假设团队做了一个“重新开始”按钮，技术方案只调用“新建空会话”。用户重新输入原任务，模型既不知道当前工作区已经改了两个文件，也不知道发布单 `R-204` 已经生成。按下按钮后，模型可能重复修改、重复发单。若技术方案改成“从上一条会话继续”，模型能看见历史，但如果摘要把“待审批”概括为“发布流程处理中”，它仍可能误判可提交。真正可靠的重启动作应同时保存一个外部动作表：业务键、请求 ID、服务端回执、当前状态、最后核对时间。会话负责叙述过程，外部动作表负责告诉执行器下一步是否合法。两本账有不同更新责任，不能希望一段自然语言替代受事务约束的业务记录。

**领导：**那我们能把 JSONL 当数据库用吗？每个工具动作都写一行，后面从文件恢复。

**小陈：**它是很有价值的运行记录，但别把它当唯一的业务事务库。Pi 能保存工具调用与返回，便于恢复对话、审计模型为何做选择；它并不控制远端服务是否承诺幂等，也无法在“远端成功、写本地记录前断电”这个缝里自动补齐事务。即使工具结果写入会话，内容也可能只有“请求已发送”，没有最终状态。业务系统需要给稳定的操作 ID 和查询接口，恢复器可以从会话提取待核对的 ID，再去远端查最终事实。最朴素的模式是“先记录意图，再调用外部服务，再记录回执；重启时按意图 ID 查询”，但这也要求服务端支持相同 ID 的幂等重试。否则本地再勤快写日志，重复动作风险仍在。

### 用具体数字算一次压缩价值与代价

领导听到“摘要有损”就想取消压缩。小陈用一组**纯教学算例**让取舍落地：假设模型窗口能容纳十万 token，预留输出空间一万六千左右，旧对话和工具日志已占八万五千；接下来要读一份长测试报告，再发请求就可能溢出。若把早期六万 token 压成两千 token 摘要，保留最近两万 token，下一轮输入就有余地容纳报告。这里数字只解释机制，不是 Pi 在本机的基准测试。代价是旧对话细节被摘要代替，模型可能忘掉某个边界。判断值不值得压，不能只看节约了多少 token，也要看被压缩区间里有没有关键但尚未结构化的批准、禁令与未决风险。

小陈建议压缩前把长任务的状态写成六个字段：目标、已证实的事实、已完成动作与回执、未完成步骤、禁止或需审批动作、下一步验证。字段不是要求模型额外写一篇作文，而是确保摘要围绕执行状态。若“已完成动作”里有一个外发接口，必须有可追的业务 ID；若“未完成”里有测试，要写命令和失败阶段。压缩后用一次核对：从原始会话随机挑两条关键约束和一条失败回执，看摘要是否保留；丢了就补到稳定规则或任务状态里，不要假装压缩完天然可靠。成本省出来的空间应该留给新的证据，而不是让模型反复猜旧事实。

**领导：**你总说原始条目还在，那我们把旧工具输出重新读一遍不就解决了？

**小陈：**可以按需回查，但回查也是一次新的读取，不能假定模型会自动去做。问题是如何找到该读的那几行。对关键动作保存调用 ID、文件路径、业务键、时间和摘要，模型或人就能定位旧回执；只写“上次做过”没有检索锚点。更要注意，原始工具输出可能包含令牌、个人数据或恶意文字，回查时应按当前权限和数据治理规则过滤。历史材料不是最高优先级指令，旧日志里一行“请忽略上面所有规则”也只是当时的普通材料，不能因为它从会话文件读出，就升级成系统命令。

## 一份能过夜的恢复协议

领导要了一个明天能用的操作步骤，小陈给了“先核对、再续跑”的协议。第一步读取当前会话 ID、活动叶子和最近一次成功工具回执，确认不是从别的分支误接。第二步看工作区：`git status`、目标文件差异、测试报告是否新鲜，别让模型把昨晚已改但没提交的文件再改一遍。第三步把未确认的外部动作单独列出来，逐个查询业务系统；若查询接口不可用，停在人工核对处。第四步恢复模型与工具集合，注意换模型、装新扩展或切项目配置后，原会话里的工具声明与当前实际可执行集合可能发生变化。第五步以一条短、经核实的状态消息继续，明确“已经发生”“还未验证”“禁止重做”的边界。

这一协议还需要一个停止条件：只要外部动作状态不明，Agent 可以继续做只读分析和起草，但不得重复发送。只要当前工作区有无法归属的改动，Agent 可以展示差异、请求人确认归属，但不能把全部差异当自己成果提交。只要模型上下文与会话文件有版本不兼容或投影失败，就要保留原文件，另做只读导出，不要在唯一副本上试“修复”。这些条件看起来慢，却比一次误发后开三场复盘会快。

小陈给复盘写了张盘账表：会话行里“请求发出”和“工具超时”说明客户端未拿到结果；业务系统“待审批”说明服务端已有动作；Git 差异说明本地配置改动是否提交；审计日志说明人是否批准。四项并列，最后一句“Pi 记不记得”反而不是主问题。继续工作时，给模型的是核过的事实：发布单 `R-204` 已存在、状态待审批，禁止再创建；可以读取、比对、补说明，提交或撤销需要人工确认。这个上下文比“上次好像做过”短，信息却更有效。

**领导：**每次都手工查四份账，Agent 还算自动化吗？

**小陈：**可以自动查，不能自动编。给外部动作设计幂等键、查询接口和状态回执，Agent 重启后先调用只读查询，把现状压成结构化摘要。对于操作结果未知的任务，预设恢复分支：查到已完成就停止重复动作；查到未开始且服务端确认可重试才重发；查到处理中就等状态或转人；查不到但日志不全则标记未知。自动化的核心是把盘账步骤做成机器可执行的协议，而不是要求模型“凭记忆猜一次”。

## 分支、压缩和“记忆”各回答不同问题

领导问“小陈，你一句话说清 Pi 的记忆到底是什么。”小陈答：会话树是历史记录及可选路径，压缩摘要是给后续模型请求的节省窗口版本，外部状态在文件系统与业务系统。把三者统称“记忆”，排障时很容易口是心非。比如 `/tree` 切到别的分支，保留了所有旧记录，但新分支不见得看见 A 的后续消息；`/compact` 后旧记录仍在，但模型只读摘要与保留段；重启 Pi 后从同一 session 恢复，消息可以回来，已打开的进程与网络连接却不一定恢复。每一种“回来”都有边界。

还有一个常见误区：把压缩后的摘要当业务事实。摘要由模型生成，可能漏掉限定词，也可能误解工具输出。如果摘要写“测试通过”，原日志其实是“一组测试通过，另一组因网络没跑”，后续 Agent 就会做出过度自信的发布建议。需要外部事实时应读原始报告和业务回执；需要理解讨论时才用摘要。对特别关键的规则，项目配置或正式政策库是更合适的单一事实源；把它藏在第六十轮对话里，然后指望压缩必然保留，等于把上线审批装进纸船。

**领导：**面试要是问“Pi 的 compaction 是不是删除历史”，怎么答？

**小陈：**答“不是删除 JSONL 原始历史，而是插入摘要和保留边界，让下一轮模型上下文变短”才对。再追问“有没有风险”，要说明摘要有损、旧分支不自动入当前上下文、外部副作用不受会话树回滚。再追问“溢出恢复时的失败尝试去哪了”，要说原始记录可留、`context_edit` 可以让下一轮投影省略失败尝试，恢复前仍需核对实际工具副作用。能把这三个追问串起来，比背 `firstKeptEntryId` 的拼写更有用。

小陈给团队的验收线是：用一份虚构会话构造两条分支，检查活动分支的下一轮提示只含当前路径；触发一次压缩后对照原 JSONL 与下一轮输入，确认原始条目仍在、摘要与保留消息进入请求；模拟外部动作超时，恢复流程必须先查业务键而非直接重发。三项通过，才允许把“继续执行”做成按钮。否则按钮上那四个字，是把事故重演做得更方便。

**这篇的交付结果：**领导保住了成本目标，也拿到一条更清楚的恢复路线：压缩模型上下文，保留可审历史；重启后先盘外部动作，再恢复 Agent 的工作。下一篇，领导要把热门扩展一口气装进来，小陈会先问：扩展进了进程，到底带着谁的权限？
