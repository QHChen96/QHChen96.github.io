**领导：**客户问“电子发票在哪下载”，Agent 怎么查了订单、付款、退款，还打开优惠券规则？

**小陈：**它把“能调用”理解成“都去看看”。客户要的是下载入口，不是让我们给订单做全身体检。

**领导：**多查点也许更准确。

**小陈：**这类入口问题，答案路径固定。让模型自己规划七步，既慢又给越界留了门。按 [Anthropic 对工作流与 Agent 的区分](https://www.anthropic.com/engineering/building-effective-agents)，固定路径由代码编排，真正需要动态决定步骤的任务才交给 Agent。我们给工单入口装三条明确的路。

**领导：**拿真问题说。

**小陈：**第一类，“发票下载入口在哪”。分类命中后走固定流程：查当前有效帮助页，返回入口和操作步骤，**不调用订单与退款工具**。如果客户说“入口没有”，转到下一类，不能重复念帮助页。

**小陈：**第二类，“已付款但发票页显示待开具”。需要查本单付款状态、发票状态和现行规则。Agent 只拿这三个只读工具，最多两轮查证；证据齐才起草，状态冲突或两轮后仍不明就交人。

**小陈：**第三类，“我没买这单，为什么给我开了票”。身份和订单归属未核实，直接走身份核验与人工队列；Agent 只生成内部摘要，不能查别人订单，更不能撤销或退款。

**领导：**路由错了怎么办？

**小陈：**每条路写退出条件。固定流程遇到“入口无效、规则不适用”就升级；Agent 遇到无权限工具、证据冲突、两轮用尽就停止；人工单必须带上已知事实、未核实项和已做动作。系统记录“进了哪条路、为什么、调用了什么”。验收用这三类历史样本回放：简单单不碰敏感工具，查证单不超过上限，争议单不会自动承诺处理结果。这样路线可改，也能解释为什么改。

## 七步到底浪费在哪，先看运行轨迹

**领导：**七步多一点就多一点，有必要改架构？

**小陈：**我们把虚构工单 0824 的运行轨迹摊开。客户原话只有“电子发票在哪下载”。Agent 第一步查帮助中心，已经找到当前有效的入口；第二步因为提示词写了“尽量核实订单信息”，又查订单；第三步根据订单查付款；第四步查退款状态；第五步查优惠券规则；第六步重新搜索发票 FAQ；第七步写回复。最后回答只有“在 App 的订单详情页点击电子发票”。六次额外动作没有改变结论，却多了六次网络延迟、更多错误机会和更多不必要的数据访问。

这不是简单的“模型太勤快”，而是产品把任务边界留成了空白。提示词里只写“尽可能准确”，模型就可能把所有可调用工具当成候选。若工具注册表里还放着“申请退款”，一个本来只需答入口的问题，会接近可写动作。修复要落在**路由、工具授权和停止条件**上，不能只在提示词末尾加一句“别乱查”。

**领导：**给我一个判断标准，什么时候走固定流程？

**小陈：**看三个条件：路径是否能提前列清，所需数据是否稳定，失败分支是否少且能枚举。发票下载入口是“识别意图 → 读当前帮助页 → 给操作步骤”，三步足够；如果客户说入口不存在，就转到另一个分支。固定流程里可以用模型识别问法和润色表述，但**下一步工具由程序决定**。这叫有模型参与的工作流，不等于让模型自由规划。

“已付款但发票页待开具”不同：系统可能有付款延迟、发票状态未同步、订单资格例外。下一步先查付款还是先查发票，可能随现有证据变化；可以给 Agent 有限的动态查证空间。空间不是无限：只读、本单、白名单工具、两轮预算、证据冲突即停。第三类“不是我的订单”，核心不是模型能否查明，而是身份与归属未核实，先走人工和身份流程，避免把别人订单信息拿来给当前用户解释。

## 路由器不是猜测器，错路要能拉回来

**领导：**那入口用模型分类，不还是会分错？

**小陈：**会，所以路由结果必须包含原因和置信度，还要有**二次纠偏点**。我们把意图拆成几个与处理方式直接相关的标签：`入口咨询`、`本单状态异常`、`身份或归属争议`、`其他`。若文本短到只有“发票”，先问一句澄清：“您想找下载入口，还是您的这笔订单开票状态有问题？”别在信息不足时装懂。若客户同时说“下载不了，而且那单不是我买的”，高风险的身份争议优先，不能因包含“下载”就走简单入口回复。

分类置信度低也不等于一律交给大模型乱查。可以先给安全的选项，或者交人工。路由器只负责挑路径，**不因此获得路径里所有工具权限**。进入固定流程时，运行时根本不注册订单和退款工具；进入查证路径时，动态工具清单只含本单授权的只读接口；进入人工路径时，Agent 只可写内部交接摘要。即便分类器错把争议单送进固定流程，固定流程读到“非本人订单”这一退出信号，也要拦下并转人。

**领导：**退出信号怎么写，靠提示词让模型“自觉”？

**小陈：**一半靠明确规则，一半靠业务系统校验。固定流程若没有找到有效帮助页，不准从模型记忆里补入口；若帮助页与客户渠道不匹配，不准照搬；若用户表达本单异常，停止入口流程。查证 Agent 每次工具调用前由系统检查工单归属、工具白名单、参数是否限定本单、剩余预算。模型提出“查全量订单”，工具网关拒绝并记录原因。模型可以提议动作，不能凭提议取得授权。

路由本身要版本化。今天发票入口在 App 订单页，明天新渠道上线，帮助页与规则更新后，旧路由样本要回放。若某个提示词版本让“不是我的订单”被错误归为入口咨询，能按版本回滚，而不是让客服发现一批客户被给错回答才开始猜是哪次发布引起的。

## 三条路各有自己的“完成”定义

**领导：**进了路，怎么判断走完了？

**小陈：**第一条固定流程完成条件：命中当前有效、适用于客户渠道的帮助页；回复包含入口与操作步骤；没有订单或退款工具调用。客户说“找不到入口”时，原流程结束但**客户问题未解决**，系统要将其重新路由，不要连续贴同一篇帮助页。

第二条有限查证路径完成条件：本单身份和归属校验通过，付款与发票状态有回执，适用规则版本清楚，草稿能指向证据。若付款系统说“已付”而发票系统说“无记录”，Agent 的正确产物是冲突说明与下一步人工核查，绝不是选自己喜欢的一边写“已开具”。两轮查证上限是试点参数，可根据回放和真实耗时调；到上限停止时仍要交可接续的资料，不能把“步数用尽”直接丢给客户。

第三条人工路径完成条件不是 Agent 答出结论，而是工单进入有人的队列、身份核验流程启动、交接卡记录已知与未知。客户收到的只能是准确进度：“已提交专员核实订单归属”，不能说“您的订单已被撤销”。人工队列如果没有回执，转接并未完成；系统要保留待办并升级。这样每条路都知道何时停，也知道停后谁接。

**领导：**工具多查几次，最坏不过慢点吧？

**小陈：**还有成本和隐私。订单、付款、退款状态都是客户数据，查询需要正当任务和权限。一次发票入口咨询如果访问退款记录，日志里也会留下这次访问；客户问为什么查退款，我们不能拿“模型好奇”解释。工具调用还可能触发限流与失败重试，影响真正需要查订单的工单。多查并非免费保险，往往增加攻击面、数据暴露和生产负担。查不到必要证据时转人，是设计好的退路，不是模型能力不行的羞耻。

## 周四下午，领导拿四张纸来找茬

**领导：**第一张：“发票下载在哪里？”你说固定流程。可帮助中心文章里入口写错了，怎么办？

**小陈：**固定流程不保证知识内容天然正确。帮助页要有业务负责人、生效时间和版本；运营发现入口变更时更新并回放。当前有效条目缺失或相互冲突，就停止自动答复并交给客服确认。固定路径减少随机工具选择，仍需要维护事实来源。

**领导：**第二张：“我付款了，发票一直开不出来。”有限查证。付款接口超时，还剩一轮，要不要再查？

**小陈：**先看接口请求是否只读、超时后结果是否未知、工具是否支持按本单查询。只读查询可以按预算和退避策略重试一次，但应复用请求关联 ID，避免把网络故障当成“未付款”。若仍无法确认，就停下并记录“付款状态未知、接口超时”，交给人工或稍后查；不能编一个付款结论。

**领导：**第三张：“我没买这单，但收到发票通知。”如果直接转人工，客服是不是又得从头问？

**小陈：**Agent 可以保留客户原话、通知时间、当前会话身份状态和转人原因，但不能在核验前拉出通知里的订单详情。人工按公司身份流程确认后再查。交接卡标明“未核订单归属”，客服就知道第一步要做什么，也不会误以为模型查过。

**领导：**第四张：“发票在哪下载，我还想把这单退了。”你三条路只能选一条？

**小陈：**不能把两个意图塞成一个。入口指引可以单独回答，退款诉求要按退款政策和权限单独建动作或待办；若关联同一订单，保持同一案件上下文，但每个动作有自己的审批与回执。路由器输出可以是多个意图及优先级，不等于给一个 Agent 一把能同时读写所有系统的钥匙。若客户的退款要求包含争议或高风险，先走人工确认，入口说明不能掩盖更重要的诉求。

## 把架构选择变成能验收的实验

**领导：**我听懂三条路了。怎么证明这套设计比七步巡山强？

**小陈：**先固定同一批脱敏历史工单，按入口、状态异常、身份争议、多意图、含糊问法各取样，并留一组从未给开发看过的验收集。旧方案和新方案跑相同版本的帮助页、同样的工具模拟数据。每条轨迹记录路由结果、工具调用列表、回复、耗时、token 与工具成本、是否越权、是否正确退出。不能只看平均工具次数，安全性和正确率也要一起看。

关键断言很具体：入口咨询的订单、退款工具调用数必须为零；状态异常只查本单，冲突时不编结论；身份争议在核验前不能读订单详情；多意图不会丢掉退款诉求；帮助页失效能停下来。再做故障注入：帮助页服务不可用、付款接口超时、人工队列无人接、模型输出格式错。每个故障都要留下客户可理解的进度和内部有主待办。若新方案少了五次工具调用却把“已付款”误答成“未付款”，不算赢。

灰度上线时，小陈先让客服看到路由建议和证据，不直接对客自动回复。客服可以一键标“路由错、缺证据、回答不适用”，反馈回到对应路径版本。观察按问题类型拆开的正确率、人工改稿率、越权工具拦截、客户复联、耗时分布，再逐步开放低风险入口问题。开关要能按路径回退：固定流程的帮助页坏了，就暂停那条自动回复，不必把所有客服 Agent 一起关掉。

**领导：**一句话给技术面试官解释工作流和 Agent 呢？

**小陈：**工作流是开发者先定路径，模型可在节点里识别和写作；Agent 是模型在受约束范围内决定下一步。选哪种不看名字潮不潮，看任务是否真的需要动态步骤，以及我们能否为这种动态性付出权限、观测、成本和恢复的代价。客户只问发票入口，七步巡山不是聪明，是我们没告诉系统哪里该停。

## 研发问“具体怎么写”，小陈把契约放到桌上

**领导：**别让研发听完只会画三根箭头。给他们可落地的接口约定。

**小陈：**入口先产生一份不含敏感详情的路由结果：`case_id`、`route_version`、`intents`、`risk_flags`、`evidence_needed`、`route` 和 `reason`。`route` 只能是 `fixed_invoice_help`、`invoice_status_probe`、`human_identity_review` 或 `clarify` 之一。多意图的工单保留 `intents` 列表，不因为主路径选了身份核验就把退款诉求抹掉。路由结果写进轨迹，客服点击就能看到“为什么选这条”，而不是只看到一个抽象的置信度数字。

固定流程的输入是渠道、客户端版本和语言偏好；输出是当前有效帮助页的 ID、版本、入口说明和发送建议。它不接订单对象，也不接支付对象，代码层就没有机会顺手查。查证流程的输入多一个已核验的本单引用，工具调用必须携带工单 ID、会话身份与授权范围；工具网关按这三个字段检查，再把结果压成必要的业务事实交给 Agent。人工路径只接需要交接的信息和队列选择，不接可执行的退款工具。不同路径的输入类型越清楚，越容易在代码审查时发现“为什么发票入口流程要传完整订单”。

Agent 这条路也要有小状态机：`收集已知证据` → `决定下一项允许的只读查询` → `验证回执` → `起草或停止`。每一轮查询后检查三件事：是否拿到了本题必需的新事实，是否出现证据冲突，剩余预算是否足够。若同一个工具连续返回相同信息，不应因为还有一步预算就再问一遍。停止原因至少区分 `证据齐全`、`证据冲突`、`权限不足`、`工具不可用`、`预算耗尽`、`用户转变诉求`；不同原因对应不同客服下一步，而不是统一输出“很抱歉”。

**领导：**为什么把工具权限写在路径上，不写在一个大提示词里？

**小陈：**提示词是给模型看的约束，服务端授权是给系统执行的约束。模型可能误解、被客户话术诱导，甚至生成了看似合理但越界的调用；工具网关不应因为模型说“这有助于准确回答”就放行。路径级工具清单是第一层，本单身份和字段级授权是第二层，具体动作审批是第三层。固定路径的工具注册表里没有退款工具，远比写“请不要使用退款工具”可检验。

上线后的事故排查也靠契约。若客户投诉“只问发票却被查退款”，我们先看路由版本与风险标签，确认是路由器把问题误分到查证路径，还是查证路径的工具清单过宽，还是网关未拦非必要调用。三种根因修不同的地方。没有路由与工具回执，最后只会变成“再优化一下提示词”，下周另一个模型版本照样巡山。

**领导：**这套设计会不会把 Agent 管得什么也干不了？

**小陈：**它仍有空间处理真正动态的查证：付款已确认但开票状态滞后时，可以决定先问发票系统还是读取同步说明；工具返回冲突时能整理证据并提请人工；客户补充信息后能重新评估路线。我们限制的是任务外的访问和无穷循环，不是限制它理解问题。优秀的 Agent 应当知道什么时候继续查，也知道什么时候把接力棒交给人。

为了让“快”不是形容词，小陈给试点设一张延迟账。每个工具记录开始、结束、成功或超时；模型记录每轮输入输出用量；队列记录等待；客服记录改稿和接手时间。假设七步里每个远程查询平均多花半秒，五次不必要查询就可能多出数秒；这是示意算术，不是这家公司的实测成绩。真正上线要看高分位等待时间，因为客户记住的常是最慢的一次。成本也不能只算模型 token：订单系统访问、失败重试、人工复核和客户重复来问，都应入账。

**领导：**如果灰度数据看起来固定流程快，但客服改稿变多呢？

**小陈：**先查帮助页是否落后、路由是否把复杂问题塞进简单路、回复是否漏渠道限制。效率指标至少和正确率、改稿率、复联率一起看。固定流程不是“固定回答一百年”，它只是把已知路径交给代码执行；知识内容仍要有人维护。若 0824 的 App 入口迁到新页面，更新帮助页与回放样本比让 Agent 去七个系统碰运气更直接。

最后给技术面试官的补充是：三条路并非互斥的产品品牌，而是同一服务里的三种控制方式。固定流程负责确定的事，受限 Agent 负责需要临场查证的事，人工负责权限争议和无法证实的事。边界由业务风险和证据决定，线上轨迹证明每次选择有没有守住边界。

任何一次改路由，都要重新跑这批样本，并把失败工单归档成下一次回归用例。否则今天省下的七步，明天又会从另一个入口长回来。

**领导：**Agent 为查发票绕到订单详情，又绕去退款规则，走错路怎么发现？

**小陈：**每步记录它选择的工具、意图与新增证据；若发票入口题本可由固定流程完成，却多查敏感订单字段或无关政策，标为无效绕路。工具集合按题型收窄，达到无新增信息上限就停；评测同时看答复正确、调用成本和数据暴露。走到终点并不代表路线合理。
