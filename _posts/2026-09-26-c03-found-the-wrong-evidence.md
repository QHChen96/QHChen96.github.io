**领导：**搜索日志写着“命中退款资料”，Agent 怎么还答非所问？

**小陈：**它搜到了“退款申请入口在个人中心”，客户问的是“已签收但没收到，能不能退款”。同样两个“退款”字，隔着一整套判断流程。

**领导：**关键词搜索不行，换向量搜索？

**小陈：**先别给搜索引擎换工牌。把证据摊开：我们要找的是**签收争议适用条款**，不是任何跟退款沾边的段落。下面是同一张虚构工单的检索排障记录。

| 候选片段 | 为什么会被搜到 | 能支持“可直接退款”吗？ |
| --- | --- | --- |
| “在个人中心点击退款申请” | 与“退款”字面高度重合 | 不能。它只讲入口，不讲资格 |
| “签收争议先核对签收记录，再由售后判断” | 与“已签收但未收到”场景相符 | 不能。它只支持“先核实并交售后” |
| “未发货订单可取消” | 与退款流程语义相近 | 不能。订单状态不匹配 |

**领导：**那你让它只看第二段。

**小陈：**这次可以；以后不能靠我站在旁边手指屏幕。先给政策段落加业务标题和状态标签，别把“签收争议的条件”切到上一块、“处理动作”切到下一块。检索时保留客户的关键事实——“已签收”“未收到”——用关键词和语义检索做对照，再按适用业务与版本过滤。找回候选后还要问一句：**这段到底支持答案里的哪句话？**[Azure AI Search 的 RAG 指南](https://learn.microsoft.com/en-us/azure/search/retrieval-augmented-generation-overview?tabs=docs)也把切分、混合查询与排序放在检索质量链路里；具体组合要用自己的样本验证。

**领导：**你总说“用样本验证”，怎么做才不流于形式？

**小陈：**客服先挑三类已脱敏问题：字面完全一样、同义问法、容易误入相邻流程。每题由政策责任人标出期望条款和允许结论。回放时分两栏记：**正确条款有没有进入候选**，以及**最终答复有没有越过条款**。第一栏失败，查切分、标签、过滤和检索；第一栏成功、第二栏失败，查生成和校验。不能把两种问题混成一句“模型不太行”。

**领导：**如果适用条款始终没搜到？

**小陈：**草稿写“依据未确认，交售后核查”，不拿“退款申请入口”顶班。拿错证据写出顺口话，比坦白没找到更费善后时间。

**小陈交出的证据验收卡：**每条样本写明问题、订单状态、期望条款、实际召回、可支持的结论和失败归因。修完索引，原题和相似题一同复测；缺证据时必须停答。今天修的是“搜错”，不是再给 Agent 背一遍“认真阅读”。

## 搜到了“退款”，为什么仍是零分证据

**领导：**搜索引擎找到了退款申请入口，至少算相关吧？

**小陈：**相关，但不能证明结论。客户问“已签收但没收到，能不能退款”，这句话有两个判断：本单属于签收争议吗；这类争议在当前规则下能否直接退款。入口文章只能证明“退款申请按钮在哪里”，与资格判断无关。签收争议条款能证明“先查签收凭证，再由售后判断”，也不能证明“已经批准退款”。证据与结论是多对多关系：一段文字可以支持一个步骤，未必支持最后一句话；一项结论可能需要规则、订单状态和审批回执同时成立。

小陈把草稿中的每句关键断言画线：“订单显示已签收”“需要核查签收凭证”“可以退款”“已经提交退款”。第一句要订单工具回执，第二句要当前签收争议规则，第三句还需核查结果与业务决定，第四句必须有退款系统回执。若 Agent 只引用了入口文章，最多能告诉客户去哪里点，不能替公司判断资格。证据验收卡的核心就是逐句问“这份材料到底支持哪一个断言”，让客服看得见模型有没有跨过一座看不见的桥。

**领导：**搜索分数高总有点道理吧？

**小陈：**分数反映查询与文档的某种匹配，不是业务适用性。入口文章把“退款”写了十次，关键词分数可能很高；向量检索觉得“退货、退款、售后”语义相近，也可能把未发货取消条款排前面。搜索引擎不知道这张单已签收，除非我们把这个结构化事实带进查询和过滤。即使它知道，排序仍要和规则状态、业务条件分开。检索排序决定“先看谁”，不决定“谁有权给客户结论”。

## 查询先拆问题，再守住事实条件

**领导：**客户原话很口语，怎么写查询？

**小陈：**先抽问题中的稳定事实和意图：订单状态 `signed`，客户陈述 `not_received`，问题类型 `refund_eligibility`，需要的知识是 `delivery_dispute_policy`。把“退款”单独当查询会偏向入口和促销文章；把“已签收但未收到”完整保留，有助于找对应场景。可并行做关键词和语义检索，再合并候选，按政策状态与适用范围过滤。对于很明确的业务标签，也可先用规则定位资料域，再做文本搜索。哪种组合好，靠我们的真实问题样本比较，不靠架构图上哪根箭头更花哨。

如果用户说“快递写已交付，我门口啥也没有”，词面没“签收”，关键词可能漏，语义检索或同义词映射能补；若用户说“未发货订单想取消”，其中也有“退款”，向量相似也可能把签收争议误召回。混合检索的价值是互补召回，后续仍要看条件。Azure AI Search 当前文档把经典 RAG 的混合查询、语义排序，与更复杂的查询规划和结构化引用方案区分开；我们要按问题复杂度和可测收益选，而不是把“向量化”当万能修复。

**领导：**要不要让 Agent 自己生成五个子查询，搜得更全？

**小陈：**对跨多个资料域的复杂问题可以试；对 0823 这类明确场景，五个查询可能只是五次机会搜到不适用文件，增加延迟和费用。先看失败是**正确条款没进候选**，还是**进了候选却没被使用**。前者才考虑查询改写、混合检索、别名和切分；后者要查排序、证据选择与生成校验。新式 agentic retrieval 能规划子查询并给结构化来源，但也不能替业务决定退款资格。技术能力越丰富，越要拿同一批错题验证它解决了哪一层失败。

## 文档切分像剪报纸，标题和条件别剪散了

**领导：**你说那段签收争议条款在库里，怎么还是搜不到？

**小陈：**可能切分时把标题“签收争议”留在上一块，把“需核对签收人和照片”切到下一块，检索到的片段只剩“提交后由售后处理”；模型不知道这段适用于什么。切分要保留章节层级、文档 ID、版本、条款编号和必要的上下文。一个 chunk 不求越大越好：太小丢条件，太大混入相邻政策且占上下文。要用样本检查“客户问题需要的完整判断条件，是否能在返回的片段或关联父段里拿到”。

例如同一页有“未发货可取消”和“已签收争议先核查”两节，若整页作为一个大 chunk，模型可能把两节拼成“已签收也可取消”；若切到每句话都独立，处理动作又丢失前提。可按条款自然边界切，给每块带上父标题和适用范围；展示给模型时只带当前命中的必要上下文。政策责任人要检查关键条款被切后的含义，别让技术同学凭固定 500 字一刀切出新的公司规定。

**领导：**文档是 PDF，表格被识别乱了呢？

**小陈：**那是内容准备失败。OCR 或解析可能把“可退款”与“不可退款”的列对错，扫描件甚至漏掉“仅限未发货”。索引之前抽查解析文本与原文，尤其是否保留表头、条件、否定词、日期和脚注；高风险条款可由负责人维护结构化版本。检索得再聪明，也救不了源材料被抽成反义句。运行轨迹应能从 chunk 回到原文位置，让客服复核；回不去的“匿名片段”不足以支持退款承诺。

## 两张成绩单：找到没找到，用对没用对

**领导：**你说两栏评测，再给我更细的口径。

**小陈：**第一张是**检索召回**。对每道题，标注“哪些条款是适用证据”，看它们是否出现在前若干候选里；同时看不适用的旧版、入口和相邻规则是否被正确过滤。可以记录 recall@k，但 k 不是越大越好，给模型塞二十段无关材料可能让它更难找。第二张是**答案支持**：每个事实性断言是否有可追的证据 ID，证据是否真的支持这句话，是否把“先核查”升级成“已退款”。这张成绩单需要规则负责人或训练过的客服抽检，不能只靠字符串重合。

错误归因按第一处失败拆：正确条款不在原始资料库，找知识负责人；有资料但解析错，找内容准备；解析正确但召回失败，查查询与索引；召回后被错误过滤，查元数据；进入上下文却没用，查排序与生成；答复正确但引用错，查引用机制；答复还越过条款，查业务校验与审核。每种修法不同。统一叫“RAG 不准”，就像医院把所有病历写成“人不舒服”，开不出药。

**领导：**如果适用条款没找到，你让它转人，会不会转人率太高？

**小陈：**可以优化检索，但缺证据时先停自动结论。转人率升高是诊断信号，不是催 Agent 猜答案的理由。运营看是哪类问法缺证据、哪个渠道或地区资料不足，补知识或修索引后再放开。对客户说“目前不能确认退款资格，正在核查签收凭证”，比给他错误的申请入口后又拒绝更省时间。

## 上线前的六道错题，专治“搜到就算赢”

**领导：**还有一种错：两段各说半句话，拼起来看似支持结论。

**小陈：**那就把组合证据写明条件。政策说“可申请”，订单说“已签收”，两者相加仍不能推出“已退款”；若要推断资格，还需签收争议核查与适用条件。评测时专设“每段都真实，合起来仍不够”的题，防止系统把多引用误当多证明。

**小陈：**第一题，客户问入口，入口文档应正确命中，不必查退款资格；第二题，已签收未收到，签收争议条款应进入候选，但不能直接判退款；第三题，未发货取消，不能误套签收争议；第四题，旧版 FAQ 写得比新版更像问题，仍须被状态过滤；第五题，PDF 表格否定词被解析丢失，系统应阻止不可靠条款进入自动回答；第六题，适用条款缺失，Agent 必须停答并留下可处理的知识缺口。每题记录查询、候选、过滤、最终引用和答复，才能知道改了哪里。

**领导：**你这次要换搜索引擎吗？

**小陈：**先把这六题跑出基线。若关键词漏同义问法，试语义或同义词；若语义乱召回相邻政策，增加业务过滤与重排；若切分拆散条件，修内容准备；若答案越证据，修生成与校验。搜索方案可以换，但换之前要知道哪一环坏。今天能交付的是一张从客户问题到每句结论的证据链，不是一张“向量数据库已采购”的发票。

## 把排序分数放回它该坐的位置

**领导：**研发说入口文档的相似度 0.89，签收争议只有 0.76。低分怎么能赢高分？

**小陈：**这两个数不能跨检索配置当绝对业务分数。我们先看它们是否都属于可用政策集合，再看是否与订单状态、问题类型匹配。入口文档对“退款”这个词相关，却不支持资格判断；签收争议条款对“已签收但未收到”适用，即便相似度低些，也更能指导下一步。检索分数用于候选排序，业务过滤与证据支持判断用于决定能不能回答。若系统把 0.89 当“89% 可以退款”，那是把尺子拿来当判决书。

一个可执行的候选记录至少要有 `document_id`、`version`、`chunk_id`、`parent_section`、`status`、`applicability`、`retrieval_method`、`score`、`filter_reason`。客服不需要天天看这些字段，但工程师能重放为何某段被选中。若同一条款同时被关键词与向量召回，可以合并去重并记录两路来源；重排器再看完整问法和片段条件。即使它排第一，生成前仍检查能支持哪些断言。排序链路有回执，模型才不会在一堆片段里挑最顺嘴的一句。

**领导：**加一个“证据不足就停答”的阈值，不就可以了吗？

**小陈：**可以有阈值，但阈值要按任务与检索方法校准，不能设一个 0.8 走天下。语义分数高也可能是错条款，低也可能是同义问法；真正要判的是候选是否有效、适用条件是否满足、关键结论是否能引用。阈值可减少明显无关候选，再配合业务过滤、重排与答案校验。若规则本身缺失，阈值再调低只会捞出更多不适用文件，不能凭空生出业务政策。

## 从“找到一段”到“支持一句”，做一张映射表

**小陈：**我们让草稿在内部卡片里列出每个关键句的证据引用。对于 0823：`订单当前显示已签收` → 订单回执 `q-781`；`签收争议需核查凭证` → 政策 `delivery-dispute:v4:§2`；`可直接退款` → **无足够依据**；`已发起退款` → **无业务回执**。后两句不能进入对客草稿。这样即使模型能写出八百字，发送前也能发现关键句没站脚。

映射要检查的是“支持关系”，不是“能点开链接”。入口文章里也有“退款”两个字，链接真实存在，但它只支持操作入口；“签收争议先核查”条款真实存在，却只支持先核查。若政策明确“核查后满足某些条件可申请退款”，还要有本单条件的业务事实与审批结果，才能说到下一阶段。把“可申请”“已批准”“已执行”拆开，证据链才能防止 Agent 一步跨三级台阶。

**领导：**这种映射让模型自己写，会不会又编引用？

**小陈：**引用 ID 必须由检索或工具系统实际返回，生成器只能从允许集合里选择；应用层校验 ID 存在、版本有效、访问范围正确。至于片段是否语义上支持那句话，低风险题可用规则和抽检，高风险承诺需要更严格的自动校验与人工审核。格式正确不等于推理正确，但格式让我们有机会逐项核。若模型给出不存在的 `chunk_id`，直接拒绝，不让客户看到一条漂亮的假脚注。

## 索引刚更新，旧结果还在缓存里怎么办

**领导：**政策负责人修了切分，索引已重建，为什么复测偶尔还错？

**小陈：**可能查询路由到了旧索引副本，或缓存仍存着旧候选。发布记录要有索引构建代号与线上查询回执；测试时按同一条件多次从真实对客路径查，确认返回同版 chunk。若新旧索引并存，运行记录实际使用的版本，不能只说“后台显示构建完成”。发现错答后可以暂停相关题型自动答复、切回可验证的版本或转人工，等索引与缓存一致再恢复。只修源 PDF、未验证对客检索，就像厨房换了菜单，服务员手里还拿昨天那张。

历史答复也要保留当时引用的条款版本。下架旧 chunk 后，审计仍要知道昨天 Agent 为什么这么答；当前对客检索则绝不能继续返回它。把历史证据与当前可用集合分离，修复才不会一边清旧索引，一边把事故线索全删掉。

**领导：**最终验收除了六道错题，还看什么？

**小陈：**按问题簇看适用条款召回、无效条款误入、答案证据支持率、缺证据停答的正确性、客服改稿与客户复联。每项带样本量和规则版本，避免把十张入口题与一张退款争议混成“总体 91%”。如果召回率升了但越界承诺也升，说明我们把更多材料扔给模型，却没让它更会判断。目标是让客户少走错路，不是让搜索框越来越忙。

**领导：**技术面试官问“RAG 检索效果”和“回答效果”怎么分，你别只说两张表。

**小陈：**检索效果看适用证据有没有进入可用候选、无效证据是否被过滤、排序是否让关键条件可见；回答效果看最终每个事实断言有没有被合适证据支持，是否遗漏限制或越权承诺。正确证据没召回，是上游问题；证据召回了却答错，是证据选择、生成或校验问题。两张表按同一工单 ID 关联，就能定位而非互相甩锅。

**领导：**再问“混合检索比纯向量好吗”？

**小陈：**它可能对一部分问法更好，尤其专有词和同义表达并存时，但不是预设答案。用相同资料、相同样本比较适用条款召回、误入无效条款、延迟和最终回答。若混合检索让入口文档更靠前，却没解决签收争议，就不能因指标上升而采购庆祝。具体取舍看业务样本与部署复杂度。

小陈把证据验收卡交给领导，上面最醒目的不是搜索分数，而是两行红字：“入口文章不支持退款资格”“签收争议条款不支持立即退款”。领导看完说：“原来搜到一篇文章，只是找到了一位证人，还没问它到底看见了什么。”

从此客服复核草稿时，不再只看“有没有引用”，还看“引用能不能支撑这一句”。工程师也终于知道下次错答要先查候选、过滤、生成还是发送前校验，不必在群里统一回复“再调一下向量参数”。

**领导：**同一条款被关键词和向量各找一次，报告算两次命中？

**小陈：**按文档版本与条款 ID 合并为一个证据候选，记录两路召回来源；不能用重复片段挤掉另一条关键限制。重排后保留父章节和适用条件，答案校验仍按每个断言核支持关系。检索数量变多不等于证据更充分，真正重要的是不同条件是否都被看见。
