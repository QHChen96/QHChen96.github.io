**09:50，领导：**客户等回复呢。Agent 草稿有了，先发，错了再改。

**09:51，小陈：**这条草稿写“已安排退款”，退款系统没有回执。错了再改，客户第一张截图可不会跟着我们更新。

**09:52，领导：**那每条都要人审，Agent 岂不是只负责写周报？

**09:53，小陈：**看动作风险。内部摘要可以自动生成给客服看；对外发消息，本期由客服审核；改订单、退款走各自业务审批。不同动作不该共用一个“自动执行”开关。[OpenAI 的 Agent 实践指南](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)也把工具风险和人工介入作为设计环节。

**09:54，领导：**客服打开审核页，不能又翻三层系统找证据。

**09:55，小陈：**同意。审核卡直接展示：客户原话、订单查询时间与状态、规则文档的版本和条款、草稿里每个关键结论、尚未核实的事，以及**实际发送对象**。客服可以批准、改稿后重新审、拒绝并说明原因。只给一个绿色“同意”按钮，那是让人替机器背锅。

**09:56，领导：**客服批准了，Agent 临发前润色两个字，总没关系吧？

**09:57，小陈：**有关系。审批通过的是**某一版草稿、某个客户、某个渠道**。批准后改了内容，哪怕只改两个字，也要重新审；目标客户换了，更要拦住。发送服务收到请求时再核对批准记录、草稿哈希或版本号、收件人、有效期与是否已发送。不能让模型拿一张旧批准去送十封新信。

**09:58，领导：**发送接口超时呢？

**09:59，小陈：**先查消息平台回执和业务发送记录，确认实际发没发；结果不明就挂起人工核对，别立即重复点发送。审批记录能证明“有人同意发”，不能证明“客户只收到一次”。

**10:00，领导：**给我今天的上线结论。

**小陈：**今天只开**内部草稿 + 客服审核后发送**。验收三条：未批准无法调用发送服务；批准后改稿或换收件人会被拒绝；发送超时不会盲目重发，客服能看见未知状态并接手。拒绝的草稿回到问题队列，按“证据缺失、规则冲突、措辞越界”归因修复。审核量和等待时间要在试点里真实记录，后续再决定哪些低风险话术可减审。

## 10:01，领导问：人审是不是只要有人点过按钮

**10:01，领导：**你说“客服审核后发送”，我最怕最后变成满屏绿勾，大家为了清队列一路点通过。

**10:02，小陈：**那就先定义审核员究竟要判什么。不是给 AI 作文打分，而是确认三件业务事实：回复对象确实是这张工单的客户；关键结论有可追溯证据；文本没有承诺系统还没完成的动作。审核卡按这三件事排版，先显示订单状态和时间，再显示政策条款与适用版本，再标出草稿里的“已批准”“已退款”“已到账”等高风险表述，旁边标出所需回执是否存在。没有证据的句子不能靠点按钮漂白。

**10:03，领导：**客服不都是会看工单吗？还要逐句打标，效率掉没了。

**10:04，小陈：**不是每个形容词都打标。只抓能改变客户决策的声明：订单身份、资格、审批、执行、时效、金额和后续动作。比如“我们理解您的着急”不需要业务回执；“48 小时到账”就需要时效依据和退款执行状态。系统可以自动把这些声明与来源配对，客服看异常和缺口。真正费时间的是打开三个后台找凭证；审核卡把相关事实摆好，人工确认才可能比从零写信快。

**10:05，领导：**如果证据没找齐，客服能不能自己补一句“应该没问题”发了？

**10:06，小陈：**不行。缺证据的处理有明确出口：查工具、转业务负责人、改成不作承诺的进度告知，或者挂起待核实。审核员可以编辑草稿，但编辑后要重新生成版本并通过同样的业务校验。人工负责判断，不是给缺失事实盖章。若公司政策允许客服作例外承诺，那也要以正式权限和审批记录体现，不能藏在“人审”两个字里。

## 10:07，把审批卡做成一张可以追责的收据

**10:07，领导：**你说审批绑定版本，给我看数据长什么样，别只画流程图。

**10:08，小陈：**一张待发卡最少有工单 ID、客户与渠道标识、当前草稿 ID 和版本、内容摘要、证据快照 ID、生成时间、审核截止时间、审核人，以及动作按钮。证据快照包含订单查询的时间和状态、政策文档版本、引用条款、退款或审批回执。客服点通过时，服务端形成批准记录：批准的是哪个草稿哈希、发给谁、走哪个渠道、在何时前有效、由谁批准。客户身份或草稿一变，旧批准即失效。

**10:09，领导：**为什么还要哈希？数据库存一份草稿就行。

**10:10，小陈：**版本号可以，但必须保证内容不可在同一版本下静默变化。哈希是校验内容的一种办法，不是魔法：要约定规范化方式，不能一边审批 HTML，一边发送被另一个模板引擎改写的短信。更重要的是把“批准时看到的最终文本”和“实际发出去的文本”连起来。模板变量若在发送时才填，例如客户姓名、退款金额，也要把渲染后的结果纳入审核或由受控规则保证不会越界。否则人审看到的是“尊敬的客户，金额 {amount}”，发出去的可能是错误金额。

**10:11，领导：**客服点通过后，Agent 又想把“处理中”改成“已安排”，系统怎么知道？

**10:12，小陈：**编辑产生新版本，原批准不适用。即使 Agent 只改了一个标点，也重新审核，规则简单可执行；将来若要允许格式性变动，必须明确哪些字段不影响业务语义，并由发送服务验证，不靠模型自称“只是润色”。这比猜“两个字算不算重大修改”可靠。

## 10:13，批准、发送、送达不是同一个状态

**10:13，领导：**审核通过后点发送，不就结束了吗？

**10:14，小陈：**至少分五种状态：`draft`（草稿）、`approved`（已批准但未提交）、`sending`（已提交发送）、`sent`（消息平台确认接收）、`failed/unknown`（失败或结果待核对）。有的平台还有 delivered 和 read，但那又是送达或已读层。批准不能证明消息已发，平台接收也不证明客户读到。每个状态变化要有时间、操作者和回执，客服工作台看见的状态要与发送服务一致，不能只看 Agent 最后一句“已回复”。

**10:15，领导：**发送时再查订单状态？那草稿可能过期。

**10:16，小陈：**对涉及变化快的事实，要设置证据有效期或发送前再校验。例如草稿 09:50 写“订单待发货”，10:20 已发货，原回复就不合适。发送服务可要求订单查询不早于某阈值，并比较版本；变了就退回重审。固定政策条款和客户诉求也可能变化，但频率不同，不能一律设相同有效期。关键是卡片上要标注“证据取于何时”，审核员知道自己签的是不是过期消息。

**10:17，领导：**我还想让它同时发短信和站内信，省一次审核。

**10:18，小陈：**渠道不同可能截断、替换模板、展示对象不同。一次批准若覆盖多个渠道，就要在卡片上明确列出全部渠道和各自最终文案；否则每个渠道单独批准。收件人标识不能只用客户昵称，同名客户会撞；从已验证的工单绑定关系取消息平台 ID，发送服务再校验一次。错误收件人比一句措辞差更难补救。

## 10:19，接口超时，老板的手指已经伸向“重发”

**10:19，领导：**客户催得急，发送接口超时，我点重发，万一发两遍也没关系。

**10:20，小陈：**如果第一条写的是“已安排退款”，发两遍不仅烦，还会让客户更相信错误承诺。每张已批准草稿生成稳定的发送意图 ID，发送请求携带同一个幂等键。超时后先查询平台回执和本地发送记录；若平台支持按键幂等重试，可以按原键重试；若不支持且结果不明，进入人工核对，不能创建一条新发送意图。队列重复投递也必须被发送服务去重，不能指望 Agent 只调用一次。

**10:21，领导：**如果平台查不到记录，客服要等多久？

**10:22，小陈：**这由渠道的回执能力和业务时效决定，要在运行手册写清最长核对时间、值班人和升级路径。过了约定时间仍未知，可以人工通过平台后台或客户会话核实，再决定是否补发；补发也应明确标为同一业务会话的处理，避免“查无记录”就当绝对未送达。监控里单列 unknown 状态积压，不能把它们算进发送成功率，也不能悄悄当失败自动重试。

**10:23，领导：**客户刚发新消息，之前草稿已经批准却还没发，怎么办？

**10:24，小陈：**新消息可能改变上下文。待发卡绑定会话版本或最新消息水位；客户补充“刚收到包裹”后，旧的“请再等配送”草稿需要失效重审。高并发时两位客服同时审核同一草稿，也要有原子状态转换：第一个批准或拒绝生效，第二个人看到状态已变化，而不是留下两张互相矛盾的批准。流程不是从 UI 上多画一个按钮就能保证的。

## 10:25，分级审核才能避免人被队列淹没

**10:25，领导：**全量人审撑不住，怎么减量而不放飞？

**10:26，小陈：**先把动作分级。内部摘要、知识库检索建议不会直接触达客户，可以自动生成但仍限制数据读取；“您的工单已收到”这类固定确认话术，若不含订单事实，未来可用受控模板自动发；涉及退款资格、地址、金额、完成时效的个性化外发，试点仍人审；真正改变订单或资金的操作另走业务审批。分级依据是对客户和系统的后果，不是“模型自信度 0.9”。自信度再高也不能出具退款回执。

**10:27，领导：**如果审核队列爆了，客户等一天？

**10:28，小陈：**工作台要显示等待时间和工单优先级，并允许发送不作业务承诺的进度模板，告诉客户正在核实、预计下一次联系时间。超过服务承诺就升级值班客服，不让 Agent 在排队时自行放宽规则。看每百单审核量、审核耗时、退回率、错承诺拦截数、客户复联率；若退回集中在“缺回执”，优先修工具或证据链；若集中在语气，可改提示与模板。用数据减少无效审核，不靠让人疲劳地按绿色按钮。

**10:29，领导：**客服改稿多，是不是说明 Agent 没价值？

**10:30，小陈：**要分改稿类型。客服补客户称呼是轻编辑，修正“已退款”是关键事实错误，重写整篇说明可能是检索或业务理解失败。报告分别看“直接可用率”“轻编辑率”“重大事实修正率”和“转人工原因”。如果直接可用率高但重大错误偶发，业务闸口不能撤；如果改稿时间仍比从零回复短，内部草稿依然有价值。我们不拿一条漂亮案例宣传，也不拿一次退回否定整个流程。

## 第二天，若错误消息真的发了

**次日 09:00，领导：**假设昨天那句“已安排退款”已经发出，你先改提示词还是先给客户打电话？

**小陈：**先暂停同类自动外发，查发送回执确认哪些客户收到了什么，再由客服按公司流程纠正和跟进。不能让 Agent 自己群发“上一条作废”，因为它可能再发错收件人，也可能在退款事实尚未核清时许下新承诺。客服需要一张影响清单：工单、客户、渠道、错误语句、真实业务状态、已采取的补救、下一次跟进人。保留发送时的草稿版本、批准记录与证据快照，才知道错误来自模型起草、证据过期、审核漏看、模板渲染还是发送服务串单。

**领导：**归因完怎么恢复上线？

**小陈：**先修具体失效点，用事故样本加相邻变体回放。例如因批准后改稿而出错，就验证版本失效；因证据过期，就验证发送前状态检查；因超时重复发，就验证同一意图只送一次或状态未知可接手。然后按低风险工单灰度，监控拒绝、回退、未知发送和人工接手，确认没有把正常回复一并卡死。恢复是一个有验收条件的发布，不是一句“以后注意”。[OWASP 的授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)强调每次请求的服务端授权；发送服务也应把批准视为一次受约束的授权，而非聊天记录里的一句“领导同意”。

## 领导最后把门槛写在白板上

**领导：**审核页面如果自己加载错客户，发送服务又怎么发现？大家都看见了同一张错卡。

**小陈：**审核卡和发送服务都不以屏幕上的名字为准。卡片由服务端按工单绑定关系生成不可变的待发对象，内含内部客户 ID、渠道收件人 ID、工单 ID、草稿版本与证据快照；审批提交只传待发对象 ID 和预期版本。服务端重新读取绑定关系，若客户身份或渠道发生变化就拒绝。发送服务再用同一份受控记录取得收件人，不接受 Agent 随意填一个手机号。界面展示脱敏姓名和必要联系方式给客服核对，操作日志记录批准者看到的待发对象版本。这样 UI 错误仍可能发生，但不能用一个随意拼的地址把消息发到陌生人手里。

**领导：**万一客服看了十个小时的队列，靠肌肉记忆点通过呢？

**小陈：**不能把疲劳当个人失误就完事。审核卡要突出异常句子和缺失凭证，默认焦点不是“批准”；高风险单要求显式确认关键事实，超时的证据自动失效。排班和队列容量按真实耗时定，超过阈值转交值班人或发进度告知，避免审核员被迫用速度换准确。质检抽样看批准后重大改稿、退款承诺是否有回执、拒绝原因是否合理。人审是有资源约束的系统组件，不能把一队忙到飞起的客服当无限吞吐量的安全缓冲区。

**领导：**怎么防内部客服自己绕过审核，直接调用发送接口？

**小陈：**发送服务只接受有效批准凭据，任何调用方都要按收件人、草稿版本、渠道和时效校验。客服后台的“发送”按钮也走同一服务，不存在一条“人工操作不用检查”的暗道。确有紧急人工外发渠道，也应有独立权限、原因、审计和事后复核。试点前检查旧短信脚本、批量通知服务和测试账号是否还能绕过新门。审批流程只覆盖一条漂亮的新路径，旧接口继续裸奔，线上仍会出现错误承诺。

**领导：**你老说“回执”，消息平台返回 200 就够了吗？

**小陈：**要看 200 的含义：是 HTTP 请求被网关接收、平台创建了消息任务、还是终端已收到。我们把平台消息 ID、接收状态和后续投递状态分开记录；客户投诉“没收到”时能按消息 ID 查。对站内信和短信，两套回执语义可能不同，不能统一写成“已送达”。对外答复若只是“我们已发送处理进度”，至少要有平台接收记录；若承诺客户已经收到，证据要求更高。客服工作台显示真实状态，避免 Agent 用一个绿色圆点解释所有阶段。

**领导：**上线后能不能把最简单的消息自动发出去？

**小陈：**可以通过风险分级逐步放开，但每一类都先定义允许的固定内容、收件人来源、可引用证据、失败后处理和回退开关。例如“工单已收到”若来自确定的工单创建事件、使用受控模板且不含订单结论，可单独验收；“退款将在三天内到账”则仍依赖审批、执行和时效回执。灰度按题型和渠道分层，记录自动发送量、人工接手量、投诉与撤回纠错；一旦某类出现误承诺，关闭该类自动发送，不影响内部草稿和其他低风险服务。放权是逐个证明安全边界，不是某天把“人工审核”总开关关掉。

**领导：**面试官如果问“Human in the loop 怎么设计”，你会怎么答？

**小陈：**先说人要审核哪类高风险动作，再说人能看到什么证据，随后说批准绑定哪个对象、内容、版本、收件人和时限，最后说执行服务如何验证与返回回执。只在流程图里画一个小人，不说明服务端怎么认批准，等于把安全交给图标。

**领导：**审批和执行为什么要分开？

**小陈：**审批是允许在特定条件下做某事，执行是系统实际做了什么。两者之间对象、内容和业务状态都可能变化。执行时必须重新校验批准和当前条件，成功后以业务回执为准。

**领导：**超时算失败还是成功？

**小陈：**都不能先算。先记为结果未知，按发送意图 ID 查回执；安全重试需要下游幂等保证。统计报表也要把未知单列，不用“默认成功”把未解决工单藏起来。

**领导：**今天究竟给客户发什么？

**小陈：**有充分证据、经具体客服审核的那一版文字，发给审核卡上那个客户；没有退款回执的草稿删掉“已安排退款”，改为说明核实进度和下一步。业务问题今天能解决多少就说多少，不能为了显得 Agent 很能干，把客户当成我们测试审批按钮的道具。

**领导：**客服批准一条短信，平台自动截成两条，算同一份文案吗？

**小陈：**渠道渲染后的实际内容与收件人都应落入审核范围。若截断会丢退款限制或更新时间，发送前应拒绝并生成适合渠道的新版草稿；原批准不能默默沿用。平台回执记录每条消息的 ID 与状态，客户投诉时能查到究竟收到哪段，而不是只看工作台里那篇完整长文。
