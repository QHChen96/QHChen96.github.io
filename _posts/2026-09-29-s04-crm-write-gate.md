**领导：**销售每天写 CRM 太慢。让 Agent 读会议纪要，把空格都填上，今晚跑完，明早全公司有数。

**小陈：**明早可能全公司都在追“下季度”是谁说的。客户原话是“我们可能下季度再看”，Agent 把采购日期填成下季度第一天，还覆盖了销售手动记的“预算尚未立项”。表格是满了，事实却被挤出去。

**领导：**不是让它写成草稿吗？

**小陈：**提示词里叫草稿，接口里是正式更新。我们先把会议纪要、字段建议和 CRM 写入分成三步，每一步都有人和证据。今天修的不是模型文笔，是谁有权改变一条客户记录。

以下客户、日期、会议和字段均为虚构。真实 CRM 的字段权限和保留规则须按企业配置核对；产品 API 的具体并发机制也要按所用版本查证。

## 一夜之间，“可能”被写成了确定日期

小陈抽出一条虚构商机 O-271。周一会议，客户说：“新系统我们可能下季度再看，先等仓库改造方案。”销售会后在 CRM 写“项目尚未立项，时间待客户确认”。Agent 夜间读取转写，抽取 <code>purchase_quarter=next_quarter</code>，又把季度映射成日期，更新了“预计采购日期”。晨会预测表立即多一笔“下季度签约”；销售看到后问客户是不是内部已经批准，客户说“我没有这么说”。一次字段写入，已经影响销售动作和管理预期。

**领导：**模型把“可能”当确定，是提取错误；让它更谨慎不就好？

**小陈：**要修两道门。提取层不能丢掉模态词和说话人；写入层即使收到一条看上去完整的建议，也要检查来源与字段权限。若只在提示词里写“请谨慎”，下一次模型又把“希望”“预计”“可能”混进同一字段，CRM 仍会被覆盖。

## 空格可以留，来源不能丢

小陈先把 CRM 字段分级。会议主题、下一次待确认问题可作为低风险建议；联系人职务、项目阶段、预计采购日期会影响跟进和预测，需要来源与负责人审核；预算、报价、合同承诺等更敏感的字段，必须依据专门的业务事实和审批，不靠会议转写自动补。哪些字段可由 Agent 建议、哪些可由销售直接确认、哪些要主管或财务批准，写成字段矩阵，不是给 Agent 一个“编辑 CRM”总权限。

**领导：**那空白字段总能填吧？不会覆盖旧值。

**小陈：**空白也不等于可猜。客户没说预算，预算字段留空就是正确信息。空白可进入待问列表，不能为了整齐填“预计 100 万”。有时空白是权限导致当前用户看不见值，Agent 更不能假设全局为空。写入服务必须按操作者身份、客户账户范围与字段权限检查，而不是把模型输出当成一个拥有全部权限的管理员请求。

建议记录应带 <code>record_id</code>、<code>field_name</code>、<code>proposed_value</code>、<code>source_quote</code>、来源记录 ID、说话人、时间、确定性类别、生成版本和提议人。确定性类别不是模型自称“很有把握”就够；“客户明确承诺”“客户表达倾向”“销售个人判断”“第三方资料”要有不同入库位置。销售确认时看得到原话与当前 CRM 值，能选择接受、编辑或驳回，并写理由。审核界面若只显示新值，人工也容易把漂亮数字当真。

## 销售下午刚改，夜间任务凭什么覆盖

**领导：**销售自己改了字段，Agent 晚上再写，谁说了算？

**小陈：**不能让最后写入的自动任务天然赢。生成建议时记录读取的 CRM 版本和原值；审核时重新读取当前值。如果销售已经把“待确认”更新成“客户明确延后到明年”，旧建议不能直接覆盖。系统显示冲突：建议基于旧版生成、现值已变化、证据分别是什么，由有权限的人重新裁决。没有冲突时也走字段规则，不代表模型可以全量覆盖。

接口级别可以用条件写入或比较版本号。Salesforce 的[REST 条件请求头文档](https://developer.salesforce.com/docs/platform/api-rest/guide/intro-rest-conditional-requests.html)说明 <code>If-Unmodified-Since</code> 可让写入只在记录未变化时生效，变化时返回前置条件失败；具体可用范围、精度和端点要按接入产品核对。无论采用何种平台，业务上要达到“读到的旧版不是现版时拒绝覆盖”，而不是先写进去，等销售发现再道歉。

批量更新还要防重。夜间任务因网络超时重跑，不能生成两条一样的跟进任务或反复把阶段从旧值改成新值。每条字段建议有稳定 ID，审批有唯一回执，写入日志把“建议 ID—审批 ID—CRM 更新 ID”关联起来。即使平台支持按唯一属性 upsert，也只能帮忙识别记录，不能替我们判断字段事实是否可靠。HubSpot 的[批量 upsert 文档](https://developers.hubspot.com/docs/api-reference/legacy/crm/objects/objects/batch/upsert-objects)展示了按唯一属性识别对象的方式；它不是“让模型写什么都能安全入库”的证明。

## 错字段改回去，下游邮件和预测怎么办

一旦错误日期已经写入，不能只把单元格改回空白。晨会预测可能已经导出，销售可能已经据此安排拜访，自动化工作流可能触发了邮件。更正要查写入后的下游影响：这条字段变化触发了哪些任务、报表或对外动作。能撤销的任务取消并留回执；已发邮件或已对客承诺按真实情况另行处理；预测看板按新事实重算并标更正版本。原错误写入和后续更正都在审计里，不能物理删除成“从没发生”。

**领导：**如果只是内部字段，为什么还这么紧张？

**小陈：**内部字段是后续自动化的输入。预计采购日期影响销售资源、库存沟通和管理预测；联系人角色影响谁收到邮件；预算字段甚至会影响报价策略。今天把“可能”写成事实，明天另一个 Agent 就会引用“CRM 已确认”继续放大错误。需要一条数据沿革链，告诉下游这个值最初来自客户明确表达、销售确认还是模型推断。

小陈把历史值分成“当前业务值”和“原始建议”。当前值只由授权人或受控流程维护；原始建议保留为可追溯的草稿，不向全公司知识库当事实检索。驳回建议要回传原因，供改进提取规则，但不把销售的每次编辑自动学成通用政策。客户资料权限也随记录走：有权生成内部建议，不代表有权把客户的预算信息复制到公开培训材料。

## 从影子模式开始，不让第一夜直接写全库

小陈先选不涉及报价承诺的几个字段，拿历史会议纪要和 CRM 版本做离线回放。标注者不仅看建议值，还看说话人、原话、时间与 CRM 原值。错误分为：提取错人、把倾向写成承诺、字段映射错误、覆盖新值、重复创建任务、跨客户串数据、审查界面漏证据。每类都能对应修复位置；不能把所有错都叫“模型偶发”。

试点采用“建议→人审→写入”而非夜间无人值守。记录每个建议的采纳率、审核耗时、回退率和最终字段正确性，同时记录省下的录入时间。若审核比手填还慢，改的是建议呈现与字段范围，不是悄悄取消审核。高风险字段哪怕采纳率高，也要看错写的后果和可追溯性。只有在具体低风险字段经过足够回放和线上抽检后，才考虑更自动化的路径；范围、负责人和回退条件都写清楚。

**领导：**总不能每条字都让销售批一次。

**小陈：**可以按字段和证据组合设置不同路径。明确的会议时间、经过同步验证的参会记录可自动关联；客户原话里的“请下周发资料”可以生成待审任务；预算、采购日期和关键阶段要人工确认。减少的是无价值复制粘贴，不是把客户的不确定性洗成管理层想看的确定数字。

## 领导最后的四连问

销售负责人试用审核界面时，第一眼只看见“预计采购日期：下季度第一天”。小陈把审核卡改成左右对照：左边是 CRM 当前值、最近修改人、修改时间；中间是客户原话和会议时间点；右边是 Agent 建议值、不确定性标签及写入后可能触发的工作流。负责人看到客户说“可能下季度再看”，直接选择“仅加入待确认事项”，不更新采购日期。这个交互比在页面底部加一行“AI 内容仅供参考”更有效，因为决策发生时证据就在眼前。

**领导：**如果销售连续点两次通过，更新会不会执行两次？

**小陈：**审批动作也要有唯一键和状态机。建议初始为待审，第一次通过写入审批人、时间与批准值，第二次点击只返回同一个审批结果。写入任务读取审批回执，按同一个 <code>proposal_id</code> 发送，平台回执再绑定更新 ID。若网络断在写入之后、回执之前，任务先查 CRM 当前值和更新记录，确认是否已应用，不能再对相同字段盲目 PATCH 一次。对于“追加一条跟进任务”尤其要防重，否则双击就生出两条同样的待办。

字段写入还存在“审核时正确、执行时过期”的竞态。销售上午审核建议时 CRM 原值仍是待定；下午客户电话明确延期，另一位销售把日期改成明年；夜间写入工作者才执行上午的审批。如果它只认“人审核过”，就会把下午新事实覆盖。写入任务必须携带审核时看到的记录版本和预期原值，执行时条件不满足就转冲突待办，要求重新审。人工审批是对某个版本的事实作决定，不是授予未来任意时刻覆盖别人工作的永久通行证。

**领导：**整批一百条，平台返回“部分成功”，怎么处理？

**小陈：**逐条保存平台回执，不以整批 HTTP 状态代替每条结果。成功的建议写入审计、更新本地状态；明确失败的看错误类型，权限不足不能重试成成功，限流可按规则等待，字段冲突回人工；结果未知的先查当前 CRM 和操作键。批量任务重跑只选择未完成且前置条件仍成立的建议，不能把一百条全部重发。若平台接口没有足够的逐条回执，缩小批次或加查询对账机制，不能靠“批量成功率 98%”猜剩下两条是谁。

另一个难点是字段间依赖。预计采购日期依赖客户项目阶段与来源，报价金额依赖已批准价格版本，联系人角色依赖身份核验。如果 Agent 分别写三个字段，其中两个成功一个失败，CRM 可能出现自相矛盾的组合。小陈在字段矩阵里标记依赖和原子边界：同一对象内必须一起生效的低风险字段由业务服务在可支持的事务里处理；跨对象或跨系统的变更留流程状态和补救任务。不能让模型因为 JSON 一次输出三个字段，就以为 CRM 一次写入也必然原子成功。

回滚也要按实际影响处理。错误采购日写入后，系统生成了下周跟进任务，又把该商机计入季度预测。更正日期时先确认跟进任务是否已通知销售，若已通知则撤销或重设并告知负责人；预测报表重新计算并标修正时间；若错误日期已进入客户邮件草稿，阻断外发。CRM 的字段历史可以帮助定位原值，却不能自动追回已经发出的邮件。技术回滚与业务补救分别记录，免得改了单元格就宣布事故结束。

小陈给试点做了“影子模式”：Agent 只生成建议，不写 CRM，让销售照常维护一周，再把建议与真实人工记录、客户原话、后续变更比较。影子模式能找到错人、过度确定、字段映射问题，也能估算审核量；它不能证明所有未来自动写入都安全。进入人工审核试点后，按字段统计提议数、采纳数、驳回原因、审查时间、写入冲突、错误更正和下游动作。若某字段提议经常被改，说明提取或业务定义有问题，应先修字段契约，不是催销售提高“AI 采纳率”。

**领导：**什么时候可以让低风险字段自动写？

**小陈：**先让该字段定义清楚、来源稳定、权限明确、写入可撤销；拿足够多的历史和线上样本证明自动提议可靠，设置抽检、告警和回滚条件。比如已确认的会议时间从日历事件同步，事实源相对明确；“客户采购预算”来自会谈语气推断，事实源不明确，风险也更高。自动化边界按字段与来源组合决定，不是按“Agent 已运行三个月”统一升级。

第二天晨会，领导看到 CRM 有不少空格，却多出一列“待核事实”。销售没法再偷懒说“系统自动填的”，也不用挨个猜字段为何变化。小陈拿 O-271 让他们练习：读原话、看原值、决定下一问，最后再决定是否写。十秒钟的判断，比隔天花一小时向客户解释一张不存在的采购日程便宜得多。

这一周的试点还安排了一次“字段误写恢复”演练。测试系统故意把“客户可能下季度评估”写成确定采购日，随后触发一条跟进任务和季度预测更新。值班人员要从字段历史找到建议 ID、原会议片段、审批人、写入回执和被触发的下游对象；再按真实证据改回采购日、撤销错误任务、重算预测，并记录哪些销售已经看过旧值。演练不是为了证明模型不会再错，而是证明错了以后能在有限时间里圈定并修正，不让错误从 CRM 一路流向报价和客户邮件。

**领导：**有些字段是销售手填，有些来自 ERP，AI 建议到底排第几？

**小陈：**不能给所有字段统一排一个来源等级。订单实收金额以财务系统为准，客户意向以经确认的会谈记录为主，会议时间以日历回执为准，产品价格看现行批准版本。Agent 建议只是从资料中提取的候选，不会因为格式整齐就盖过事实源。字段字典要写“事实源是谁、允许谁改、冲突时谁裁决、变化通知哪些下游”。只有这样，销售打开 CRM 时才知道一列数字是业务事实还是未审核的推断。

审批体验也有成本。若审核卡每次都要求销售重读完整一小时转写，没人会认真看；小陈让系统定位原话前后三句，显示说话人、时间点和与 CRM 原值的差异，必要时再打开完整受控记录。关键信息不藏在长文末尾，审核动作也不能只剩一个绿色“接受全部”。销售能逐字段接受、改写或驳回，批量相同的低风险建议可按规则处理，高风险字段始终独立确认。效率来自把证据送到人眼前，而不是让人盲点同意。

还有一个跨客户串写的危险：两场会议里都出现“王总”，模型把 A 客户的预算讨论提到 B 客户商机。写入服务要从会议安排、参会人和 CRM 账户关系核对目标 <code>record_id</code>，不接受模型自己猜一个同名账户；权限校验绑定操作者和目标账户。目标不确定时，建议留未关联待核，不写任一客户。回放样本必须包含同名联系人、集团子公司和销售同时参加两场项目会的情况，否则一张正常纪要的漂亮演示根本测不出这个风险。

领导终于同意把“CRM 填满率”从验收指标里撤下，换成更诚实的几项：建议有来源比例、关键字段误写数、人工审核耗时、冲突拦截数、写入后更正时长和下游错误动作。空格若代表客户尚未确认，本来就应该空着；只有被证实但尚未录入的事实，才值得系统帮忙补。让数据库看起来整齐很容易，让销售真的敢用它做判断才难。

**领导：**结构化 JSON 输出字段都合规，为什么还不能写？

**小陈：**JSON 校验只能证明格式和类型，不能证明客户真说过。新值要有来源、权限和冲突检查。一个完美的日期字符串仍可能是假的采购日。

**领导：**人工审核点了通过，是不是模型就没责任了？

**小陈：**系统仍要提供原话、原值、差异和风险提示，让审核有意义；人工决定写入，但我们继续记录模型提议、审核和实际写入结果，以便发现系统性误导。不能把证据藏起来再说“人已经确认过”。

**领导：**CRM 写入超时，能不能重发整批？

**小陈：**先按建议 ID 和平台回执对账。某些字段可能已经写成功，某些失败；整批重发会覆盖后来的人改动。对每条建议查当前版本，成功的记回执，失败的按原审批和版本条件重试，冲突的回人工。

**领导：**如果客户在会后明确说“下季度绝不买”，旧建议怎么处理？

**小陈：**新证据优先进入审核，旧建议标过期并禁止写入；已经写入的值走可追溯更正，连带检查下游任务和预测。客户的否定句不能因为不符合销售预期就被当噪声过滤掉。

第二天的 CRM 没有一夜变满。销售打开 O-271，看见一条待审建议：“客户可能下季度再评估；采购日期未确认。建议询问项目立项时间。”原来的“预算尚未立项”还在。领导嫌空格多，小陈指着那些空格说：“它们至少没替客户签字。”

会后一周，客户确认今年不启动项目。销售把新原话附到商机，采购日期继续留空，下一次跟进时间由双方另约。Agent 回看自己的旧建议，只能标“已被新证据取代”，不能悄悄把历史建议改成“我早就知道”。销售、主管和后续助手都看得到这次信息怎样变化，CRM 才像一本可靠的业务记录，而不是一张永远填满的表。

如果别的报表仍显示旧日期，数据团队要按字段变更事件查同步链，不能要求销售再手工修改一遍。一个可靠的写入流程包括提议、审批、实际落库与下游同步的回执；其中任何一段失败，都显示未完成和负责人。只有这样，下一位接手的销售才知道该相信哪个系统，不会把两个互相冲突的日期都说给客户听。
