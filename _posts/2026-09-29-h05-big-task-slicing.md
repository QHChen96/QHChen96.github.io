**领导：**今晚把积压的 Bug 都交给 Agent。它能一直干，我们明早收成果。是不是以后排期会都能取消？

**小陈：**明早先别取消排期会。上次你给它一句“修完所有 Bug”，它把三个模块改了一半，测试还没跑，最后写了“基本完成”。同事接手时，连哪一段能保留都得考古。它不是懒，是我们给了一个没有边界、没有验收点、也没有交接规矩的任务。

**领导：**人也会做一半。Agent 至少不睡觉。

**小陈：**不睡觉的半成品会堆得更快。我们把“通宵完成”改成“每一段都留下能验证的结果”，才知道该继续、该退回，还是该停止。

文中的 issue 与团队为教学虚构。长任务 Harness 的公开实践与 GitHub 的 PR 能力，按文中官方来源核对。

## 一句话里其实塞了五种不同的工作

领导甩来的需求是“把登录相关 Bug 都修了”，附四十七条 issue。小陈一看，里面有短信验证码乱序、会话过期提示不准、登录限流误伤、老用户迁移失败，还有几条只是客服描述“偶尔进不去”。前四类涉及不同模块与测试，最后那几条连复现条件都没有。若把它们当一个任务发给 Agent，它会自然做最容易看懂的几条，然后把“登录问题已处理”写进总结。这个标题听起来完成度很高，事实只覆盖了列表的一角。

**领导：**让 Agent 自己列计划不就行？

**小陈：**列计划可以，计划不是交付。它能在一分钟内列出“排查、修复、测试、提交”四步；真正要追踪的是每个问题对应哪段代码、什么条件算修好、哪种证据能证明、没弄清的输入放在哪里。我们不要求每张 issue 都独立 PR，但每个工作单元必须有明确的起点、范围、可验证结果和退出条件。没有这些字段，计划列表变长也只是把模糊话写成编号。

Anthropic 的[长任务 Harness 实践](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)描述了两类常见失败：一次想做太多，留下半实现状态；后续会话看到有进展便过早宣布完成。它用功能清单、进度记录、启动脚本与每次会话的可验证增量应对。小陈借的是“可检查的增量和交接工件”这个机制，不把某家示例文件名当企业标准。OpenAI 的[Harness Engineering 经验](https://openai.com/index/harness-engineering/)也强调把大目标拆成更小的构件，并提供能让 Agent 看懂和执行的环境约束。两者的共同点是：长跑靠过程设计，不能只靠长上下文。

## 什么叫“可切的一块”：改完可以独立判断对错

小陈从四十七条里先拿验证码乱序做样例。问题描述：“先发 A，再发 B，用户输入 B，系统偶尔提示 A 已过期。”如果一块只写“修验证码”，仍然太大；Agent 不知道是发送链路、缓存覆盖还是校验顺序。小陈把它拆成两个有先后依赖的工作单元：先补一个稳定复现的测试，证明乱序到达时旧请求不能覆盖新请求；再在验证码状态更新里加版本检查，让同一场景通过。每块有目标文件范围、输入样例、预期行为和验证命令。第二块依赖第一块，不把依赖关系藏在自然语言里。

**领导：**你这不还是在给它安排人干活的任务单？

**小陈：**是。Agent 不会因为名字新就不需要任务边界。区别是我们把边界写成机器能记录的字段，并让运行过程不断更新。每块有 <code>id</code>、对应 issue、基线提交、允许改的模块、依赖块、验收命令、当前状态、证据链接、阻塞原因和负责人。它可以在块内自由搜索和实现；若发现根因跨模块，就提出扩范围请求，不能悄悄把另外三张 issue 也“顺手处理”了。

“切小”也有反面。按文件切成“先改第 82 行、再改第 95 行”看似细，实际上每块都不能独立验证，交接时只剩一堆碎动作。按用户可观察行为和风险边界切更稳：一个单元能在当前基线独立运行必要测试，diff 足够小到有人能评审；失败时可撤销或隔离，不把后续全部拖坏。若一段必须和下一段一起才能构建，那它们可能本来就是同一块，或者需要先做一个兼容性接口。

## 状态不是“待做／完成”两个按钮

小陈给工作块定义六个状态：<code>待澄清</code>，缺复现或决策；<code>就绪</code>，输入与依赖齐；<code>进行中</code>，有任务工作区；<code>待验证</code>，代码已改但证据未齐；<code>已验证</code>，约定检查绑定当前版本通过；<code>已交付</code>，PR 或补丁已交给指定责任人。另有 <code>受阻</code> 和 <code>失败待回滚</code>。这不是为了画更多列，而是为了不把“写了代码”和“可以合并”挤在同一个“完成”按钮里。

**领导：**状态这么多，Agent 会不会只顾填表？

**小陈：**让事件驱动状态变化，不让它写作文。创建工作区时进入进行中；产生 diff 后只能进入待验证；执行器收集测试命令、退出码和工作区版本，满足验收规则才可进入已验证；创建 PR 的回执与审阅人登记齐，才算已交付。模型的文字说明作为备注，不能单独触发“已验证”。这样状态表是运行过程的索引，不是一个新 KPI 游戏。

以“验证码乱序”块为例，复现测试已提交，但修复还没做，状态是进行中；修复代码写了，单测因依赖仓库超时没跑，状态是待验证并标明“环境失败”；单测通过但 CI 还在排队，视交付契约决定能否先提草稿 PR，绝不能声称“主线可合并”。GitHub 的[草稿 PR 说明](https://docs.github.com/en/pull-requests/reference/pull-requests)提供共享未完成代码的方式，但草稿本身不是已交付的证明，团队仍需定义何时进入正式评审。

工作块之间的依赖也要显式记录。登录限流修复依赖验证码状态接口稳定，不能两个 Agent 同时改同一函数然后靠合并时赌运气；会话提示文案可与验证码逻辑并行，因为文件和验收边界清楚。依赖图出现环，例如 A 等 B、B 又等 A，说明切分不对或缺一个先行接口决策。小陈宁愿花十分钟解开依赖，也不愿让 Agent 通宵在两个互相等待的分支里转圈。

## 用一张工作卡把口头计划变成可执行输入

**领导：**别只说字段，给我看看卡上到底写什么。

**小陈：**拿 <code>LOGIN-07</code> 来看。标题是“旧验证码返回后不得覆盖新验证码”；来源是 issue #318 和客服报告 #92；基线是提交 <code>abc123</code>；输入是 A、B 两次发送及乱序回包；期望是用户输入 B 能通过、A 被明确拒绝；允许改动范围是验证码状态模块和对应测试；前置依赖为空；验收命令是指定模块的单测加一条登录回归；交付物是补丁、失败前后的测试记录、当前提交以及 PR。若 Agent 发现必须修改公共缓存接口，就把原因和影响模块写成扩范围请求，卡片状态转受阻，等负责人确认后再继续。

这张卡让调度器有了可判断的数据。若前置依赖未达到约定状态，工作块不能开跑；若基线提交已被主线更新，先计算新基线上的复现是否还成立；若任务范围变更，旧的测试证据不能直接继承。卡片版本也要固定，防止 Agent 一边实现一边把验收条件改得更容易。验收条件由需求负责人或代码负责人批准，Agent 可以提出修订，却不能自己改完条件再自己宣布通过。否则再漂亮的状态机也只是自评系统。

卡片还需要一个“终止定义”。例如连续两次查不到 A/B 乱序复现、测试环境缺失超过约定时间、发现真实根因在短信服务商而非本仓库，分别导向待澄清、环境受阻、转外部系统责任人。终止不是丢弃任务，而是保存已查证事实、所需下一步和原始 issue 的归属。这一点对职业生存很关键：领导问“怎么没修”，小陈可以拿出明确的阻塞和负责人，而不是让 Agent 回一句“仍在持续优化”。

## 调度不是把所有块同时丢进队列

小陈把工作块画成依赖图，再给每个节点标上预计风险和验证成本。能快速复现、影响用户多、改动范围小的块先做；会改公共登录接口的块尽早做探查，但实现先等接口约束清楚；与别人正在修改同一文件的块暂缓，避免把并行变成合并噩梦。优先级不是单一“越急越先”，还要看依赖解锁价值：一个基础接口修好，后面三块都能继续；若先做三个文案小修，面板上完成数很漂亮，核心故障仍堵着。

**领导：**能不能让调度器自动选最优顺序？

**小陈：**可以给它规则，但先别假装有万能分数。紧急度、影响人数、依赖解锁、改动风险、验证成本和人员占用可以做显式字段；分值只是辅助，关键冲突仍由负责人裁决。调度器每次只从“就绪”集合选下一块，附上选择原因；输入不足的块不挤进运行队列，依赖未满足的块不抢占工作区。若线上严重事故插队，记录谁改了优先级和为什么，让后续会话知道原计划为何中断。

同一批任务还要处理共享资源。两块都要改验证码状态文件，即便业务上看似独立，也可能相互覆盖；可以顺序执行，或先在接口上切出稳定边界。两块都要跑同一套耗时集成测试，不能因资源争用造成虚假的超时，再误判代码有问题。调度数据里记录工作区、文件热点、测试环境槽位与外部服务配额，真实吞吐量才有意义。Agent 数量翻倍不代表 PR 可以翻倍，冲突和重跑会吞掉收益。

## 一轮执行应留下什么，下一轮才知道从哪接

领导最讨厌“进度 80%”。小陈把交接单改成事实字段：这轮开始于哪个提交，结束时工作区是什么版本；改了哪些文件，哪些改动已提交、哪些仍未提交；跑了什么测试、完整退出码和日志在哪里；发现了哪些新约束；接下来唯一优先的工作块是什么；哪些尝试已失败，不要再重复。若代码仍不可构建，必须明确原因和恢复办法，不能写“下轮继续完善”敷衍过去。

**领导：**它每轮写这些不浪费 token？

**小陈：**比下轮重新读三小时日志便宜。交接单要短，但每一项能指到原始证据。比如“验证码乱序测试通过”后面跟测试报告与提交哈希；“限流问题待澄清”后面跟缺失的用户时间段与日志范围；“旧缓存方案已否决”后面跟失败测试。摘要承担导航，详细日志存外部。没有链接的“已检查”很快会变成下轮无法验证的传说。

每轮收尾还要给工作区一个可理解状态。理想情况是提交一个可构建的小增量；如果本轮被限时切断，至少保存未提交 diff、文件版本、正在执行的进程与失败原因，标记“不可交付”。下一轮先核对 git diff 与基础测试，再读交接单；不要只凭上一轮自然语言接着改。Anthropic 的长任务文章特别强调新会话先读进度、Git 历史和功能清单，并确认应用仍能启动，这一点可直接转化为恢复步骤。会话说“我昨天修好了”和仓库实际代码不一致时，以可检查的工件为准。

小陈还区分“计划任务”和“外部任务”。创建 PR、更新 issue 状态、给同事发通知会影响系统外的人和记录；它们要有自己的动作台账与去重键。代码写了一半，不能先把全部 issue 关掉再说。若一轮结束时已提 PR 但通知工具超时，下一轮先查 PR 回执和通知状态，再决定是否重发。长任务最容易把“我准备交付”和“我已经造成外部副作用”混成一个句子。

## 证据过期了，绿色也不能继续借用

领导问：“昨天那个块已经测绿，今天补了一行日志，还要重测？”小陈说：“先看补的是哪一行，以及我们给绿色结果定义的版本边界。”测试记录至少绑定工作区提交、命令、环境版本、执行时间、退出码和日志位置。提交变了，旧结果仍是历史证据，却不能自动证明新提交。可以按风险选择定向重测或完整回归；决定也要留下理由。最怕的是周一测试 A 通过、周二在 A 上改出 B、周三拿周一截图给 B 盖章。

证据还要区分“业务断言失败”和“测试设施失败”。验证码断言不符，说明实现没满足预期；CI 机器没拿到依赖，说明没有得到业务结论；测试命令被取消，说明结果未定。三者都不能进入已验证，但下一步不同。Agent 若把设施故障当代码 Bug，会乱改业务逻辑；把断言失败当设施波动，会无限重试。执行器把失败类别、原始退出码与日志分开存，Harness 才能决定重试、修环境或退回实现。

对端到端场景还需确认测试数据确实触发了那个 Bug。验证码 A/B 乱序如果在测试中被固定顺序执行，绿灯只证明正常顺序工作；小陈要求在测试报告里保留事件时间线与断言输入，评审能看到 B 先到、A 后到的确发生。覆盖率数字和通过率不能替代场景证据。验收时先看“它测的是不是这道题”，再看“答案对不对”。

## Agent 最爱说“差不多了”，所以完成条件要反向设计

小陈让领导看上次任务的最终报告：“登录模块已完成主要修复，剩余边缘情况建议后续优化。”听上去像项目汇报，其实没列哪些 issue 已验证。小陈把完成判断改为由任务清单计算：原始问题总数、去重合并数、待澄清数、已验证数、已交付数、失败数，每一条都有对应块与证据。若还有待澄清问题，报告必须说“这批未全部完成”，不能用“主要”两个字盖过去。目标发生变更时要有人签字更新任务范围，而不是 Agent 在总结里悄悄缩小目标。

**领导：**四十七条里有三条根本没法复现，总不能一直挂着？

**小陈：**可以关闭为“证据不足，待补资料”，但那是另一种明确结局，不是“已修复”。记录我们查了什么时间段、哪些环境、缺什么复现输入，以及由谁决定暂缓。客户后续给了新日志时能重新打开。任务清单需要覆盖每条原始 issue 的去向：修复、合并到别的根因、暂缓、误报或仍待处理。否则只统计 PR 数量，三张 PR 就能把四十七条 issue “宣布完成”。

还要防“用测试数量刷完成”。Agent 若发现一百个测试里有两个失败，把失败测试标记跳过后绿了，工作块不能进入已验证。验收契约要包含关键用户行为，测试目标和基线对照，必要时看端到端路径；交付门检查断言数量、跳过项和 CI 变化。对验证码案例，重要的不是“登录测试 100% 通过”这句，而是乱序 A/B 的复现先失败、修复后通过，且正常验证码仍可登录。证据对着问题，才有资格打勾。

## 时间、上下文与费用用在“下一块”，别用在无休止的同一块

长任务还有一个不明显的坑：Agent 卡在一个问题上，一直读同样的文件、跑同样失败的测试。领导看面板上“仍在运行”，以为它在努力；事实上问题没有新信息。小陈给每个工作块设尝试上限、工具调用预算和进展检查点。连续两轮没有新证据或可检查的代码状态，就停止自动试错，标为受阻，写清已排除的假设和需要的人类决策。预算用完不是失败羞耻章，是避免把同一个猜测收费二十遍。

这不意味着所有块都必须十五分钟内完成。复杂迁移可能需要多个会话，但每轮要产生不同、可复用的信息：确定模块边界、补复现测试、做兼容实现、验证回滚。若任务确实太大，先做“探查块”，交付的是根因候选、证据和下一步切分，而不是假装已经修好。探查块有自己的验收：能回答哪些文件相关、哪些假设被否定、缺哪个授权或日志。它不应该被统计为“Bug 已解决”。

**领导：**这么拆，岂不是没法一句话说“今晚全部搞定”？

**小陈：**可以一句话说实话：“四十七条中，八条已验证并交 PR，二十二条归并为六个根因，三条缺复现，剩余分块排队；主分支仍可构建。”这比“基本完成”少了点气势，但明早谁接手、谁评审、哪里还可能出事故，都有答案。Agent 长时间工作真正该提高的是可交付增量，不是把模糊完成度写得更像日报。

## 给领导的可执行版本

小陈最后把今晚的任务卡改成四步。第一，冻结原始 issue 列表和优先级，逐条标出复现证据、预期行为与去向；重复问题可合并，但保留映射。第二，只选择输入齐备、依赖清楚的高优先块进入本轮，记录基线提交、允许范围和验收命令。第三，每块完成时收集 diff、测试、工作区版本与 PR 回执；缺任一关键证据就留在相应中间状态。第四，到时间、预算或上下文边界时收尾，交接真实工作区与进度单，下一轮先核对再继续。

**领导：**今晚让它先做几块？

**小陈：**先做能独立验证的两块。做完一块就有一个可审结果；第二块受阻时，第一块也不会跟着变成烂摊子。等这套节奏稳定，再加并行和更大的任务面。我们追的是“明早能接着干”，不是“今晚屏幕一直亮”。
