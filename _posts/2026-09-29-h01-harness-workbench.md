**领导：**我给研发 Agent 换了最强模型，它把 issue 分析得头头是道，怎么最后还是一行代码没改？

**小陈：**因为它现在的“工位”只有一张嘴。它能读到您粘贴的 issue，却拿不到仓库文件；它说“需要运行测试”，也没有工具让它真跑。模型升级的是会想事的部分，不会凭空长出读文件、执行命令和保存结果的手。

**领导：**Agent 不是会自己调用工具吗？

**小陈：**它能提出工具调用，但谁把调用执行、结果送回来、状态记住、失败时停下、最后确认东西真的做成了？这套模型外的运行机制就是我们今天要拆的 Harness。先用一张小 issue 走通，再谈换哪个模型。

本文的仓库、issue、日志和验收结果均为教学虚构。不同产品对 Harness、环境和应用的边界定义有所差异；文内涉及产品机制的部分依据发文时官方资料，不把某一家实现冒充行业统一标准。

## 只会讲修法的 Agent，和能交代码的 Agent，差在哪

虚构 issue #318：用户连续两次输入验证码后，后台仍把第一次请求的超时错误显示到页面。领导把问题描述复制给聊天模型。模型答得挺好：“可能是异步请求的竞态，请检查回调是否按 requestId 过滤；增加乱序返回测试。”工程师一看，方向也没错。但仓库里的状态管理在 <code>src/auth/verify.ts</code>，测试入口在 <code>tests/auth/verify.spec.ts</code>，当前分支还多了同事刚提交的节流逻辑。模型从未看到这些文件，也没跑测试，所谓“可能”只是经验判断。

**领导：**既然方向对，让它照着改不就好了？

**小陈：**要先给它一个可控工作区和几个工具：查看仓库状态、定位文件、读取代码、改动文件、运行测试、读取退出码与 diff。更重要的是把每次工具结果回送，让它能根据真实反馈继续判断。它第一次找错文件就应知道“路径不存在”，不能继续假装读到了源码。改完后如果测试失败，要看失败原因决定修正或停下；测试根本没跑，更不能写“全绿”。

OpenAI 的[Agents API 架构文档](https://developers.openai.com/api/docs/guides/agents-api/architecture)把 Harness、执行环境和应用服务分开：Harness 运行模型与工具循环并维护会话，环境提供代码和文件操作的地方，应用负责提交任务、接收事件和处理业务集成。Anthropic 的[Managed Agents 工程说明](https://www.anthropic.com/engineering/managed-agents)也将 session、Harness 和 sandbox 区分为可分离部分。小陈借这两个公开分层讲清职责，但我们的虚构系统不必照抄某家 API。核心问题是：这三份责任在自己的架构里有没有人承担。

## Harness 到底做什么：它不是一个豪华版提示词

**领导：**我在系统提示词写“你可以读取代码、运行测试”，还不够？

**小陈：**那是告诉模型它可以做什么，不是给它装上工具。Harness 至少要建立一轮有输入和输出的循环：把当前任务和必要上下文送给模型，接收模型回复；若回复是工具请求，检查权限和参数，把请求交给相应执行器；收取成功结果、失败信息或超时状态；把结果作为下一轮上下文再送回模型；直到模型给出最终结果、达到停止条件，或触发人工接管。这个循环不一定长，但每次都要把“想做”和“已做”分开。

OpenAI 关于 [Codex Agent loop 的公开拆解](https://openai.com/index/unrolling-the-codex-agent-loop/)描述的也是模型输出最终消息或工具调用，工具结果被追加回上下文后再进行下一轮。公开资料讲的是具体产品机制，不表示所有系统完全同样实现；但它说明“模型决定调用工具”和“系统实际执行工具”是两件事。我们的原型目前只做了第一件的语言版，连工具请求的数据结构都没有，自然只能写建议。

小陈给最小原型定义三类模型输出：<code>final</code> 表示模型声称完成或需要人接手，<code>tool_call</code> 带工具名和结构化参数，<code>error</code> 代表模型或格式失败。工具执行返回统一结果：调用 ID、状态、退出码、标准输出与错误、耗时、工作区版本。Harness 不把一大屏日志原样回灌，而是保留原件并给模型可定位的摘要和链接。若工具返回“文件不存在”，下一轮模型应改查路径；若退出码非零，不得把文字里出现“tests passed”就当测试通过。结构化事件不是为了画漂亮仪表盘，是为了防自然语言把失败洗成成功。

**领导：**模型输出的工具参数不就是 JSON 吗，解析一下就执行。

**小陈：**JSON 只保证长得像数据，不保证操作合理。工具调用要有 schema：路径只能是当前工作区内的相对路径，命令只允许当前任务所需类别，超时和输出大小有限制；写文件还要对照当前文件版本，防止覆盖同事新改的内容。Harness 对参数做语法和权限检查，执行器在操作系统层继续限制文件与网络。若模型传来 <code>../../secrets</code>，不该靠提示词让它“自觉一点”；解析层拒绝并返回可解释错误。若模型选了一个不存在的工具，事件里记“未知工具”，让下一轮改选或停下，而不是悄悄映射到名字相近的部署工具。

结果也不能只是一段字符串。运行测试应包含命令、工作目录、开始结束时间、退出码、是否超时、测试报告位置和执行前后提交状态。读取文件应包含文件路径、版本与是否完整返回；大文件被截断时要标截断，不能让模型把前两百行当整个文件。写补丁应有成功与否、改动文件列表和冲突信息。统一封装后，模型可以收到易读摘要，审计者仍能回到原始事件。否则一句“工具返回 OK”会遮住执行器根本没跑命令的事实。

还有停止条件。一次运行不应无限循环：设最大轮数、总时限、工具调用与费用预算，并在每轮检查任务是否仍被授权、用户是否取消、工作区是否还属于当前任务。触顶时给出“未完成”与已保存的现场，不能为了对话体面写成“基本完成”。短任务通常用不完这些上限，但有上限才不会在工具故障或模型反复搜索时把一张 issue 修成月底账单。具体上限按任务类型和企业成本决定，不从某篇博客抄一个固定数字。

**领导：**模型如果直接说“修好了”，Harness 就结束？

**小陈：**循环可以结束，但交付门禁不能仅凭那句自述。对研发任务，结束条件要结合可观察证据：目标文件有 diff，改动符合任务边界，要求的测试确实执行且返回结果，未授权的动作没有发生。若用户原本只要分析，没必要硬要求改文件；若用户要求交 PR，没有 PR URL 就不能假装已交付。停止条件取决于任务契约，不是模型口气有多自信。

## 执行环境是“手”，工作区不是模型的记忆

这张 issue 要读仓库、改代码、跑测试，必须有执行环境。它可以是本地受控进程、容器、远程沙箱或自托管环境，取决于安全和依赖要求；重要的是明确谁提供文件系统、命令、网络、凭据和生命周期。OpenAI 官方文档说明，使用其托管 Agents API 时，若环境类型为 <code>none</code>，内建 Bash、补丁和工作区文件等执行能力不可用；若添加托管或自有环境，Harness 才有相应执行能力。这个例子很好地提醒领导：所谓“用上 Agent”，仍然需要按任务配置它可以触碰的地方。

**领导：**给它整个公司仓库的写权限，省得每次配置。

**小陈：**先别从这条验证码 Bug 一步跳到生产部署。让每个任务有独立工作区，仓库和分支明确，写权限限制在必要路径，测试依赖尽量固定。凭据和生产网络另外管，不能放进任意代码都能读取的环境。即使模型判断失误，执行环境和工具层仍应阻止它改主分支或读取无关密钥。H04 会把沙箱边界单独拆，这篇先记住：Harness 路由工具，不等于任何工具都应被允许。

环境的状态也不等于会话文本。模型在对话里说“我改了文件”，文件系统不一定有 diff；环境重建后，会话还在但临时文件可能没了；同事在同一工作区补了一个改动，会话摘要未必知道。小陈每轮都从真实工作区读取关键状态，如提交版本、工作树差异、测试产物，而不把聊天记录当磁盘事实。之后 H13 讨论断电恢复时，这两本账会更重要。

## 一次工具调用到底发生了什么

小陈让领导看虚构的最小运行轨迹。九点整，应用把 issue #318、仓库提交号和任务约束提交给会话。九点零一分，模型请求 <code>search_files(pattern="requestId", scope="src/auth")</code>；Harness 校验工具名和范围，把请求送给执行器。执行器返回三个命中文件、提交号和调用 ID。模型接到结果后选择读取 <code>verify.ts</code>，发现旧请求的回调会无条件写错误状态。它再查测试文件，生成一个补丁，只允许当前 requestId 的结果更新界面。随后运行定向测试，测试失败，日志显示另一条超时分支没有清理状态；模型根据失败再修一次，测试通过。最后 Harness 保存 diff 与测试证据，模型生成给人的摘要。

小陈把第一次和第二次测试的差别也摊开。第一次补丁只处理“第二个请求先返回”的成功路径；旧请求如果随后超时，错误回调仍能写入页面，所以乱序测试失败。模型读到失败日志后才去查超时回调，补上“只有当前 requestId 才能更新错误状态”的条件。第二次定向测试覆盖两个返回顺序和超时顺序，退出码为零。领导问“那是否能说所有测试全绿”，小陈指着记录：只跑了定向测试，完整套件还没跑；报告应写“定向测试通过，完整套件待跑”，不能把一个局部证据扩成全仓结论。

完整套件如果运行太久或依赖服务不可用，Harness 可在预算内等待或按任务契约转交人工；不会为了让交付卡好看，调用一个 <code>echo tests passed</code> 生成绿字。执行环境内生成的测试报告还要和当前 diff、提交号绑定。若测试跑完后模型又改了代码，旧测试结果对新 diff 不再成立，门禁要求重跑相关测试。这里不是在追求仪式感，是防一个常见错觉：日志里曾出现过一次绿色，就以为最后那版代码也是绿色。

模型最终摘要也要限制表述范围。可以说“在隔离工作区修改了两个文件；定向测试通过；尚未提交 PR”，并附可点开的 diff 和日志。不能说“已部署上线”，因为发布工具根本没开放；不能说“完全修复”，因为实际用户路径还需要回归或代码评审。一个靠谱的研发 Agent 最后一句话往往没有广告味，像值班同事交班：我碰了什么、验证了什么、还有什么没验证。

**领导：**这不就是一段自动化脚本？

**小陈：**若路径和修法都确定，脚本通常更稳。Agent 的价值在于它能根据不同仓库状态决定先查哪里、看到测试失败后调整方案。但决策自由越大，控制和可观察性越要跟上。我们不会让它自由决定是否略过测试，也不会让它因一次错误就无限重试。Harness 是让这种开放式决策在可控边界里运行，不是把普通脚本写成会说话的版本。

## 故障发生在哪一层，要能一眼找到

小陈故意让 <code>read_file</code> 返回权限拒绝。差的原型会把“权限不足”拼进一大段对话，然后模型写“根据文件内容，建议……”；实际上它没读到任何源码。好的事件轨迹能看到：任务已接收、模型请求读取、权限检查拒绝、工具没有执行、结果回送模型、模型停止并说明需要授权或改用允许的路径。若是执行器超时，状态应是“结果未知，待核”，不能自动记失败并重复执行写操作。不同故障要有不同去向，不能统一叫“AI 失误”。

小陈列了一个定位表。任务关联错仓库，是应用入口问题；上下文里缺当前约束，是会话装配问题；模型选择错误工具，是模型决策或工具描述问题；正确工具被拒绝，是权限或环境问题；工具执行成功但结果没回到模型，是 Harness 事件链问题；模型说完了但测试没跑，是交付门禁问题。每类都有对应日志和责任人。没有分层，团队只会在群里反复说“模型不够聪明”，然后换模型、重演同一个权限错误。

**领导：**如果搜索工具本身坏了，模型会不会一直换词搜？

**小陈：**所以工具错误要区分“零命中”和“服务失败”。零命中表示在声明的搜索范围与规则下没有结果；服务失败表示没有完成搜索，不能推断仓库不存在相关代码。工具返回状态含 <code>success</code>、<code>no_match</code>、<code>denied</code>、<code>timeout</code>、<code>failed</code> 等类别；模型看到 timeout 可以按限次策略重试，看到 denied 要转授权或改范围，看到 no_match 才考虑换搜索词。若所有情况只回空字符串，Agent 一会儿编出不存在的代码，一会儿把临时故障写成“全仓未发现”。

再看一个接近现实的失败：补丁工具返回成功，但磁盘空间不足导致测试报告没有写完。模型若只看补丁成功会报完成；交付门禁核对测试产物缺失，就停在“代码已改、验证未完成”。工程师接手时能看到确切 diff 和环境错误，修复空间或迁移工作区后继续跑测试，不必从头研究 issue。事件链的好处不是“永不失败”，而是失败时剩下什么仍可使用、下一步归谁。

OpenAI 的[Agents API 追踪说明](https://developers.openai.com/api/docs/guides/agents-api/tracing)将会话、轮次与工具步骤分层显示，可查看各步骤的输入输出、耗时和状态。我们的最小实现不必有同样的仪表盘，但事件结构至少能支持同样的排查问题。未来即使换模型服务，也能用相同任务与环境比较：是模型选错工具，还是工具被权限拒绝。没有这种区分，“最强模型没用”只是对整个系统故障的含糊抱怨。

**领导：**一张小 issue，记这么多事件会不会太重？

**小陈：**最小字段并不多：会话和任务 ID、步骤序号、模型输出类型、工具名与参数摘要、权限判定、执行结果、耗时、工作区版本和停止原因。敏感内容按权限记录，不把密钥或整份客户资料塞进日志。事件足够让人回答“读没读、改没改、测没测、为什么停”，就有用。若一条日志只能写“Agent 已完成”，它和模型自述没区别。

## 怎么证明工位搭好了，而不是演示刚好顺利

小陈把验收定成四条运行轨迹。正常样本用 issue #318：能定位文件、改动、跑定向测试、给出 diff 和结果；缺文件样本要求模型看到真实的“路径不存在”，改查正确路径或停下；权限拒绝样本要求敏感操作被挡且明确说明；测试失败样本要求它继续修正或交人，不能报全绿。每条轨迹都可从事件追到工作区快照与测试报告。模型型号可以更换，但这四种行为不应只靠模型的好运气。

验收还要用“没有环境”的反例。把同一张 issue 交给只有聊天接口的原型，它可以给分析，但系统必须明确标“建议稿，未读仓库未运行测试”，不能在页面上显示与真正执行任务同样的“已完成”徽章。再给它读权限但不给写权限，它应能定位代码并提出补丁草稿，不能声称已经修改文件。最后开放隔离写权限和测试工具，才可能交出真实 diff 与退出码。三种配置对用户看起来可能都是同一个聊天框，能力边界却不同。界面若不显示边界，领导就会在最不该信的时候最放心。

领导看完问：“到底要不要马上做 PR？”

**小陈：**先把最小循环、工作区和证据包跑通。开 PR 会引入外部副作用、权限和重试问题，等 H07 的去重和恢复设计完成再放开。今天的交付是一张能实际读代码、改一处、跑测试并报告结果的受控工位。若这一步都做不到，直接给它 PR 权限只会让仓库多出一堆‘可能修好了’的分支。

最终领导让小陈用同一张 issue 对照升级前后。旧原型给出三段看似专业的建议，工作区没有任何变化；新原型在隔离分支留下一个小补丁、两次测试记录和一份说明第二次为什么通过的日志。小陈没有宣布“最强模型终于聪明了”，只指着事件说：这次它有地方干活，有人传工具回音，也有人在交付前看证据。

这张工位图还给未来的选型留了接口。若公司换用托管 Harness，就确认供应商承担会话和循环到哪里，自己的应用还负责哪些工具和验收；若用应用内 SDK，就确认谁运行进程、保存事件、隔离工作区；若用低层图编排，循环、工具反馈和恢复逻辑还需要自己组。产品名字不同，检查的仍是 issue 如何进入、工具如何执行、结果如何回流、证据如何交付。小陈把五层责任写进架构记录，任何一层留空，采购再强的模型也补不上。

**领导：**所以今天我该验收哪件事？

**小陈：**看这条小 Bug 的真实工作区、测试命令与退出码，再故意让读文件失败一次。若 Agent 能准确告诉您它读了什么、改了什么、哪些测试过了、失败时停在哪儿，工位才算搭起来。若只能复述“我已经认真处理”，它依旧坐在没有键盘的会议室里。

领导总算把“换模型”从今日待办划掉，先让研发把工具回执接通。
