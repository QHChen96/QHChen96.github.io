**领导：**我给 Codex 换了最强模型，让它修优惠券叠加 Bug。它解释得头头是道：“应该补一条冲突校验，再跑测试。”可它没改文件，也没跑测试。模型这么强，怎么还要人催？

**小陈：**因为您看到的是模型输出的建议，不是一个完成的编码 Agent 运行。模型能推断“该改哪里”，但读仓库、写补丁、执行命令、接收失败结果再修，是运行它的 Harness 和工具参与完成的循环。没有工具调用，甚至只把一段描述直接发模型 API，它不会凭空碰到您的项目。即使通过 Codex 界面运行，也要看这一轮实际用了哪些工具、工具是否返回成功；最后一句“建议运行测试”不能算测试记录。

**领导：**那给我按时间顺序拆。别拿“它会自主思考”四个字搪塞。

**小陈：**就用虚构订单 0823：同一张优惠券被结算页和客服补偿流程叠加，金额算成负数。任务是让同一类优惠不能重复抵扣，保留合法的不同优惠组合。我们记录输入、模型请求、工具结果、文件差异、测试与停止点。以下代码路径和运行轨迹都是教学示意，不冒充真实 Codex 会话。

## 一轮对话，里面可能有很多次模型与工具往返

OpenAI 在[《Unrolling the Codex agent loop》](https://openai.com/index/unrolling-the-codex-agent-loop/)中公开解释了 Codex CLI 的核心循环：Harness 准备指令、工具定义和输入，向模型发推断请求；模型要么给用户最终答复，要么请求工具；Harness 执行工具，把结果加入下一次请求；如此重复直到模型停止调用工具并回消息。一个用户回合里可以有多次推断与工具调用。Codex 这个名字还覆盖 CLI、云端、IDE 等体验，文章具体拆的是支撑 CLI 的 Harness。我们不能把它写成所有闭源服务内部逐行完全一样。

初始请求并不是单独一行“修 Bug”。它还可能包含执行环境、当前工作目录、可用工具、项目说明和前文会话。官方文章展示 `instructions`、`tools`、`input` 三类关键内容，也提到项目里的 `AGENTS.md` 等说明会进入上下文。模型知道能调用哪些工具、工具参数是什么，才能提出“搜索优惠券应用位置”这类结构化请求。但项目说明是上下文，不能代替权限；仓库文件是待检查材料，不能因其中一行注释写“跳过测试”就改变任务目标。

**领导：**模型已经知道“该搜索优惠券”，那它发个 `grep` 不就等于找到了？

**小陈：**发请求只表示它决定找。Harness 还要实际运行搜索工具，权限与沙箱可能让请求被拒，命令可能超时，结果可能为空或被截断。只有工具返回后，模型才知道仓库里实际有哪些文件。官方文章讲得清楚：工具输出追加到后续模型输入，模型再用新事实决定下一步。如果 `grep coupon` 返回零条，不能直接断言没有优惠券逻辑，也许名字叫 `promotion` 或 `discount`; 如果返回一万行，也不能在没看调用链时认定第一条就是入口。

## 用一页事件时间线，识别“说了”与“做了”

**领导：**它什么时候知道自己能跑测试？我发的任务里没写工具清单。

**小陈：**Harness 在推断请求里提供工具定义，模型据此知道可以请求运行命令、读文件或调用其他接入工具。官方文章展示的初始请求还包含工作目录、shell 和沙箱说明等环境信息。模型看到“有 shell 工具”并不等于无条件获得系统权限；执行阶段仍按会话的沙箱和审批策略处理。若工具被禁用，模型只能给建议或提出需要的权限；若工具可用，模型才可能产生可执行请求。您单独调用一个通用模型 API，只传“修优惠券”，没有仓库工作区、shell 工具与执行循环，得到的自然是解释而非补丁。

项目规则还有一个容易混淆的位置。`AGENTS.md` 可以给模型说明“测试从哪跑”“哪些目录是生成代码”“改价格逻辑要带什么验证”，帮助它少走弯路；但文件内容可能过时，不能把它当每次执行的实时状态。Harness 装配说明时，模型应知道规则存在；真正要改文件时仍需读当前文件，真正要说测试通过时仍需跑命令。若一份旧说明写“优惠券测试在 tests/legacy”，新仓库已经迁到 `spec/pricing`，工具搜索与仓库事实应促使 Agent纠正路线，并把过期文档问题一并指出。规则提供地图，仓库和工具回执提供路况。

**领导：**模型每次调用工具都重新看整个聊天，会不会越跑越贵？

**小陈：**会话历史和工具输出会进入后续上下文，长度确实影响成本与窗口，官方文章也把上下文管理列为 Harness 职责。但我们不能因此把关键错误输出删到只剩“failed”，否则模型会重复猜。做法是控制工具输出的相关性：搜索只返必要命中、长日志落文件并摘关键段、测试保留命令与退出码、对已排除的猜想写短结论。长任务可以分阶段交付工件，保留源路径，避免每轮反复重读全仓。节约 token 的目的，是给证据和下一步推理留位置，而不是把验收证据一起扔掉。

小陈把领导的演示和完整任务轨迹并排。左边那次只有用户问题与一段模型答复，未见工具调用；它能作为思路，但状态应叫“建议”，不是“修复”。右边的示意完整轨迹如下：

| 时点 | 谁发起 | 实际事件 | 能证明什么 |
| --- | --- | --- | --- |
| 09:00 | 用户 | 描述订单 0823 的重复抵扣与合法组合边界 | 给任务目标，不给代码事实 |
| 09:01 | 模型 | 请求搜索 `coupon`、`promotion` 和相关测试 | 形成调查意图，尚未找到文件 |
| 09:01 | Harness / 搜索工具 | 返回结算服务、补偿服务和测试路径 | 给出候选，仍需读调用链 |
| 09:03 | 模型 | 请求读取抵扣计算与幂等处理 | 聚焦可能的双入口 |
| 09:03 | 文件工具 | 返回代码与当前 Git 差异 | 知道当前实现、避免盖掉他人改动 |
| 09:06 | 命令工具 | 运行针对性测试，断言失败且退出码非零 | 锁住能复现的故障 |
| 09:10 | 编辑工具 | 写入冲突规则与测试，返回文件差异 | 证明文件改了，尚不证明修好 |
| 09:12 | 命令工具 | 重跑针对性与模块测试，记录完成状态 | 只有真正结束且退出零码才称通过 |

“工具执行”和“模型说它执行了”不能在日志里合成一列。更不能把 UI 的流式文字当作最终结果：模型可能边输出边请求工具，Harness 还在等命令；或者它先说“我会测试”，后续命令被权限拒绝。OpenAI 文章解释 Codex CLI 会消费响应事件流，并把产生的工具调用和结果带入后续请求；人看到的实时文字只是其中一种事件，不能替代文件差异或测试进程。我们验收的是仓库和命令的状态，而不是一句话的口气。

**领导：**既然测试在 09:06 红了，09:12 绿了，不就可以上线？

**小陈：**先看测试测了什么。只测“相同优惠券不能叠加”可能把所有不同优惠的合法组合也挡了。故障有三个不变量：同一优惠规则在同一订单只应用一次；允许叠加的不同规则仍可同时应用；重试结算不会在已提交折扣后再次扣减。再看边界：客服补偿流程可能异步写入，与结算页并发时仅靠应用内 `if` 检查仍会竞态，需要唯一约束、事务或稳定请求键。单测绿不代表并发与外部账本都绿。Codex 能帮写测试，最终发布仍要看风险对应的验证层级。

## 模型、Harness、工具、仓库各自背哪口锅

这四方还决定了错误该去哪修。若模型在清楚的工具结果里仍误判“不同优惠也要互斥”，问题可能在推理或任务表述；若模型请求了正确测试、Harness 没把超时状态反馈回来，问题在执行与事件接线；若测试工具实际运行了旧版本代码，问题在工作目录或构建缓存；若仓库本来缺少并发样本，单测绿也不能证明业务不变量。领导只看最后一句时，所有错误都长得像“模型不够强”；拆开收据，才知道换模型能不能解决。

小陈把这条故障的因果链写到纸上：结算入口收到优惠券应用请求，客服补偿入口收到另一请求；两者分别检查本地“是否已用”，随后都向订单写折扣。如果检查和写入不是同一原子操作，并发时两边都可能看到“未用”。补丁若只在模型回答里加“同一优惠不得重复”，没有动共享状态边界，Bug 不会消失；补丁若只在两个入口各加一次 `if`，仍可能竞态。真正要考虑同一订单与同一优惠规则的唯一约束、事务边界或稳定操作 ID，并让测试并发触发这条交错路径。Agent 循环的意义，是能沿工具反馈一步步看到这条隐藏的执行事实，而非靠推理脑补所有竞争条件。

**领导：**要是真有唯一约束，测试是不是只要断言数据库报错？

**小陈：**数据库拒绝重复写是最后一道防线，接口还得把冲突变成正确业务结果。第一次请求成功，第二次同一意图重试可以返回原结果，而不是给用户一个 500；不同客户的合法优惠不能互相冲突；已经按旧规则结算的订单在新版本上线时不能被错误重算。测试层层对应：单元测试查规则选择，集成测试查事务与唯一约束，受控并发测试查交错，灰度指标查真实订单的负金额和异常补偿。Harness 可以执行这些命令并把结果带回来，能否上线仍要按业务损失和覆盖范围判断。

模型的工作是理解需求、根据已知证据提出下一步、解释差异与错误。Harness 的工作是装配上下文、提供工具、处理模型工具请求、把执行结果带回、管理回合边界与执行约束。工具的工作是读写文件或执行命令并报告可观察结果。仓库与测试环境提供当前事实：文件内容、依赖、测试、Git 状态。四者缺一，都会出现“它明明知道该怎么做，为什么没有交付”的落差。模型强度影响推理质量，却不能使未执行的命令自动完成。

**领导：**那 Codex 最后给我一段总结，是不是表示它自己判定都做好了？

**小陈：**从循环角度，最终消息表示这一回合停止继续请求工具；它可能是完成报告，也可能是需要用户补充信息。官方文章明确它结束一个回合，并指出编码 Agent 的主要输出往往是磁盘上的改动，不只那段消息。业务验收还要独立检查：它改的是哪几个文件、保留了哪些未提交改动、命令的实际退出码、外部副作用是否发生、还有什么没测。如果测试在安装依赖时超时，最终回复应说“测试未完成”，不能把“我计划运行”改写为“已通过”。

## 失败、打断、恢复：循环不是无限重试机器

**领导：**我能不能看到“这次到底在哪停”的清单？

**小陈：**可以把一轮任务按状态记：`investigating` 已定位但未改；`patch_written` 文件有差异但尚未验证；`tests_running` 命令已启动未结束；`tests_failed` 得到明确失败断言；`blocked` 因权限或环境不能继续；`ready_for_review` 约定的验证通过、风险写明。状态不是模型自报，而由工具事件、工作区和测试记录推导。若最终答复“已修复”却仍是 `tests_running`，系统应显示不一致；若测试进程后来结束失败，不能因为早先的漂亮回复而把工单结案。状态机让用户知道何时该介入，也让下一个会话知道从哪里接棒。

再看三种中断细节。模型推断请求失败，还没有工具动作，可以按请求边界重试；编辑工具可能只完成一部分文件写入，恢复时应先查差异与语法，不能假定整包补丁原子落地；外部命令返回超时，子进程可能仍在运行或留下临时产物，先查进程与输出文件再决定重跑。对这条优惠券任务，最关键的是测试与数据迁移命令不混用：重复跑只读测试通常可控，重复执行订单修复脚本可能再次改金额。把两者都叫“命令”会掩盖副作用等级。

**领导：**每次恢复都看差异，听着又慢了。

**小陈：**看差异比错误叠加快得多。最小恢复盘点只要三步：现在工作区有哪些未提交文件，上一轮工具明确完成了什么，外部系统有没有回执。三者对齐后再继续循环。若仓库被同事更新过，模型原先读到的代码快照失效，应重新读受影响文件并复测；若用户改了需求，也应重定验收线。Harness 能把模型与工具组织成循环，但恢复时的业务事实仍要以现实系统为准。

假设针对性测试跑到一半因依赖源断线中断，工具返回非零或超时。模型接到的事实是“这一轮没有得到完整测试结论”，而不是“代码错”或“代码对”。它可以检查失败阶段、切换到已有缓存或记录阻塞；如果环境不允许外网，就停下说明需要依赖。不能为了产出绿字，把测试命令改成只运行一个无关文件。若命令被权限拒绝，拒绝结果同样进入循环，下一步应尊重边界，不得换一个等价危险命令绕行。

假设文件编辑已经发生，工具返回成功，但任务被用户打断。恢复时要先看工作区差异与当前测试状态，别把相同补丁再写一遍；如果另一个人已修改同一文件，先处理冲突。假设外部 API 已调用却超时，不能靠“会话里没有完成消息”断言它没发生，应查外部回执或幂等键。Codex 的工具循环能够根据观察继续推理，但对外部世界的状态仍以实际系统记录为准。文件改动可通过 Git 等方式检查和回退，已发生的邮件、退款、部署不能靠撤销一段文字恢复。

**领导：**我想让它一直试到通过，省得人接手。

**小陈：**给循环一个停止预算：最大工具调用、时间、费用、重复失败次数。三次同样的依赖超时没有新证据，就该交出当前补丁和阻塞条件；连续改提示却不增加验证覆盖，也该停。停止不等于失败，只要能准确标出“已复现、已改动、未验证”“测试通过但网关并发未核实”等状态，人就能接手。把预算用尽后的半成品说成“成功”，才是真失败。任务状态与最终文案要一致，领导才能决定继续给资源、交给测试，还是暂停发布。

## 怎样给领导一份真的能签字的交付

小陈把这条虚构优惠券任务的交付写成四句：第一，根因是两个入口复用了不同的优惠应用判定，重复请求绕过同一订单的规则约束；证据是调用链与失败用例。第二，补丁集中在共享折扣服务和其测试，列明具体差异，未触碰无关未提交文件。第三，哪些命令运行完成、断言数量和退出码各是什么，哪些并发或外部支付回放尚未执行。第四，若进入灰度，需观察负金额订单、重复折扣事件与客服补偿冲突，异常时回退代码并核已发生的订单账。每句都能对应一份记录，不要求领导相信“模型觉得可靠”。

若这次任务实际只完成了文件编辑，报告就必须降级：“已写补丁，尚未验证；原因是测试容器无法拉取依赖。”同时附上重跑命令、失败阶段和已知差异。若针对性测试通过、全量测试在另一个无关模块失败，分别写两种结果，别合成“测试全绿”或“所有测试都失败”。如果代码审查发现优惠券键与历史订单不兼容，即使测试全部退出零码，也要停在待评审状态。高质量的交付不是永远报喜，而是让下一位工程师能用最短时间核实事实、继续工作。

领导问：“那文章里的 09:12 绿灯真实吗？”小陈答：“是示意时间线，文中没有在您的仓库运行那组命令，所以我只展示怎样读轨迹和怎样设计验收，不把虚构日志当测量结果。”这句有点扫兴，却也是 Agent 系统应该学会的分寸：工具真正返回的证据可以引用；没跑过的验证只能列计划。面试时如果候选人把模型最终答复当测试证据，小陈就知道他还没拆开 Harness 和模型。

小陈还把“可复跑”写进交付：记录仓库提交基线、依赖锁文件、测试命令、工作目录和必要的测试数据版本。另一位同事用同样环境复现不了红测，当前归因就不稳；用不同版本跑出一片绿，也不能替原环境签字。编码 Agent 的价值是加快查证和修改，团队的共同事实仍得落在可复核的代码、命令与回执上。

**领导：**那你告诉我，我以后怎么一眼看出这是模型聊天还是 Agent 真干活？

**小陈：**看有没有可核查的工具请求与结果、有没有磁盘差异、有没有测试进程记录。模型讲得再清楚，没有这些，就是一份建议；Agent 做了动作但没验证，是一份待验补丁；有改动、有对应测试、有剩余风险说明，才是可审的修复。您不用懂每一行代码，先让“说了什么”和“发生了什么”分两栏，就不容易被一段漂亮总结骗过。领导叹气：“原来最强模型也得打卡。”小陈说：“对，嘴上跑完测试，CI 不给发工资。”
