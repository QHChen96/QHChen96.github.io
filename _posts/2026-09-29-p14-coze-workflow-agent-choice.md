**领导：**小陈，我在 Coze 把“收材料、查订单、看规则、给答复”四个节点连得端端正正。客户问“我这个能不能退”，它表现很好；客户补一句“那我昨天那单呢”，它就答非所问。都叫智能体，怎么一点眼力见都没有？

**小陈：**因为您画的是一条已经写好路线的工作流。节点会按输入、连线和条件运行，不能凭空知道“昨天那单”指哪一笔，更不能替系统完成身份核验。Agent 可以在工具和工作流之间选择，但选择之前也需要可信上下文。要解决这个问题，先区分两类任务：退款材料校验有明确步骤，适合固定流程；含糊追问需要判断补问、查历史还是查订单，适合 Agent 在受限工具间选择。两类任务混成一条“万能流程”，才会既慢又冒险。

**领导：**你又要让我多画几张图？

**小陈：**两张：一张看控制权在谁手里，一张看事实从哪流到哪。图不是办公室墙上的装饰，能让测试同事看出失败发生在哪个岔路。下面的客户和订单是虚构教学案例；产品能力按 [Coze 工作流说明](https://www.coze.com/open/docs/guides/use_workflow)、[工作流概览](https://www.coze.com/open/docs/guides/workflow)和 [Agent 概览](https://www.coze.com/open/docs/guides/features)核对。Coze Studio 是开源版本，官方[仓库说明](https://github.com/coze-dev/coze-studio)也提醒与商业版有功能差异，不能把两个版本的按钮当成完全一样。

## 第一张工单：材料校验，路线先写好

客户在售后页面提交订单号、购买凭证和商品照片，要求确认能否申请退货。业务规则明确：核身份，按核实后的客户 ID 查订单，检查购买和签收时间，识别商品类别，读取对应日期有效的售后规则，材料不完整则一次列清缺项，材料完整才产出“待审核建议”。这条路径输入输出清楚，不需要模型每走一步都重新决定下一步。Coze 的工作流由开始节点定义输入，节点按连线处理，结束节点返回结果；节点可以配置输入输出变量，也能加入条件、插件或代码逻辑。[官方工作流概览](https://www.coze.com/open/docs/guides/workflow)列出了这些节点类型。把固定校验做成可视化流程，运维可看到哪一格收到什么字段。

**领导：**既然规则确定，模型在哪？

**小陈：**可以只让模型做它擅长的一段：识别客户描述里提到的商品问题、把政策条款解释成口语、整理客服草稿。身份、订单归属和时间窗口不让模型凭文字猜。比如“照片没拍到序列号”，条件节点可以直接返回补拍要求；“商品可能属于卫生类例外”，让人工确认或用有来源的分类服务判定。模型写得再像客服老手，也不能从“看起来是我的订单”推导出数据库权限。工作流路径写死，正好把这种硬边界固定下来。

**领导：**Coze 有插件节点，我直接接退款 API，不就全自动了吗？

**小陈：**先别让“能接”偷换成“该执行”。校验流程输出的是申请资格建议，不是财务批准。真正退款可能涉及金额、原支付通道、风控、逆向物流和人工授权。即使最终决定自动化，执行插件也要拿业务系统颁发的最小权限、幂等键与回执；失败要查状态再重试，不能因为模型说“办好了”就改工单。领导的四个框若没有这些关口，所谓全自动只是把退款按钮藏在一条连线后面。

## 第二张工单：“昨天那单”是一个路口

客户先问耳机 A 的退货，下一轮说“那昨天那单呢”。这句话可能指昨天下的单、昨天到货的单，或者昨天客服提到的另一单。系统应该先看当前会话能确认的订单上下文，再按已登录身份查可访问订单；若有多笔符合“昨天”，要向客户澄清，不能选金额最大的那笔碰运气。Agent 的价值是根据当前问题决定：直接调用固定材料校验工作流、调用只读订单列表、查知识库、还是先发澄清问题。它做的是路口选路，固定工作流做的是上路后的稳定步骤。

[Coze 官方使用工作流指南](https://www.coze.com/open/docs/guides/use_workflow)说明，工作流先创建、配置输入输出、试运行并发布，然后可添加到 Agent；Agent 的提示中可以描述何时调用该工作流。官方也强调清晰的工作流名称和说明有助于模型理解其用途。这句话背后有一个工程含义：若工具名称都叫“售后处理”，一个查资料、一个退款、一个发邮件，Agent 无从准确选择。把能力写成“只读订单归属核验”“退货资格材料检查”“创建退款申请（需审批）”，再在描述中给出适用条件、参数和副作用。工具合同越清楚，动态选择越像按路标开车。

**领导：**我都给 Agent 接了会话记忆，它还需要订单查询？

**小陈：**会话记忆保存“我们谈过什么”，订单系统保存“现在真实状态是什么”。客户上轮说“我昨天买的”，记忆可以帮理解指代；订单是否付款、是否退货、是否改地址，得从业务系统查。Coze 的[Agent 概览](https://www.coze.com/open/docs/guides/features)把知识、工作流、记忆列为不同能力，[会话变量文档](https://www.coze.com/open/docs/guides/variable)也说明用户变量可随对话更新。记忆里的用户陈述不能反过来成为订单事实，否则客户说“我有十张券”，系统就发十张券了。指代消歧用记忆，实时状态用订单 API，政策依据用版本化知识源。

知识库又是一回事。它储存条款、说明、常见问答等外部知识，并检索相关片段供模型引用；[Coze 的知识库说明](https://www.coze.com/open/docs/guides/agent_knowledge)介绍全文与语义等检索方式，也区分 Agent 自动或按需调用知识库，与工作流中按节点顺序调用知识库。知识库能告诉我们“某类商品一般怎样退”，却不应拥有“0823 订单属于谁”这个客户私密事实。资料更新、切片质量和生效日期会影响检索结果。若检索只给到一段“七天无理由”，却没有发布日期，客服草稿不应把它当成当前有效政策。

**领导：**知识库里放一份最新规则不就得了，旧规则还留着干什么？

**小陈：**旧订单可能按旧规则购买，今天的申请又可能受新规则约束，适用口径必须由法务或业务定义。删掉旧文档，系统反而解释不了历史工单；只留旧文档，又会答错今天的新客户。每个条款要有版本 ID、起止时间、适用商品、适用地区、发布状态。检索时先把订单时间和申请时间作为过滤条件，再让模型理解条款；如果资料没有这些元数据，就算召回相似度排第一，也不能直接用于关键判断。知识库是证据候选库，规则判定仍要应用做版本校验。

## 输入输出像合同，不能靠“模型会懂”

小陈给固定工作流设计四类输入：可信身份引用、订单 ID、材料文件引用和业务日期。客户自然语言描述可以作为附加文本，却不能替代前三项。每个节点的输出都写类型与来源：订单服务返回 `owner_verified`、商品类别、签收时间、订单版本；政策服务返回 `policy_id`、生效区间和条款引用；材料识别返回 `document_type`、置信度和缺项。结束节点只输出 `eligible_candidate`、`missing_items`、`evidence_refs`、`review_required`，不输出“退款成功”这种尚未发生的状态。官方工作流文档强调节点输入输出参数，这不是表单填空游戏，而是避免事实在节点之间被一句自然语言冲淡。

**领导：**客户没传订单号，Agent 帮他猜一下？

**小陈：**可以按已登录身份列出有限、脱敏的候选订单，让客户确认，不能对全库模糊搜索。若昨天有两张订单，回复“我查到两笔，尾号分别是 23 和 47，请确认”，比猜中一张更像靠谱客服。确认之前不能把另一张订单的金额或地址暴露出来。Agent 可以决定调用“列候选”这个只读工具，但工具的客户 ID 从服务端认证上下文取；模型只提供可能的日期范围。工具无论挂在 Coze 还是别的平台，这道权限校验都不能靠提示词承诺。

再看返回值。一个工作流执行成功，只能说明节点完成并给出输出；业务上还要检查 `missing_items` 为空、政策有效、客户身份一致、人工是否批准。对外发送最好由企业客服系统接手，保存草稿版本、审核人、发送通道与回执。若 Agent 决定不调用工作流而自己回答，系统需要解释为何：是通用知识问题，还是工具不可用，还是它误选了路。没有可见的选择轨迹，领导只看一句话很难分辨“灵活”与“绕过关口”。

## 发布、调用、调试要沿同一条版本线

按 [Coze 使用工作流指南](https://www.coze.com/open/docs/guides/use_workflow)，工作流需要先试运行和发布才能给 Agent 使用；试运行成功的节点可查看输入输出，测试集可保存用于后续验证。小陈把“耳机标准单”“旧规则边界单”“两笔昨天订单”“缺订单号”“订单 API 超时”“政策检索为空”六类样本存入测试集。发布前先看每个节点收到的是不是预期字段，再在 Agent 入口回放，观察它是否在该调用工作流时调用、该澄清时澄清。单测工作流全绿，不代表 Agent 一定会选中它；Agent 选中，也不代表工作流收到的参数正确。

**领导：**上线后客户说错了，我们先看哪张日志？

**小陈：**先拿会话 ID、工单 ID 和工作流执行 ID 对齐。会话记录展示客户究竟说了什么、Agent 选择了哪个能力；工作流节点输入输出展示订单号、政策 ID 和分支；外部订单与发送系统给事实回执。不能只看最终回答，因为一句“可以申请”可能来自正确校验，也可能来自没查订单的猜测。Coze Studio 开源版的[API 参考](https://github.com/coze-dev/coze-studio/wiki/6.-API-Reference)提到执行工作流响应里的调试链接可查看节点过程；不同部署版本的具体日志界面要以本环境为准。日志应脱敏，特别是客户上传材料和地址。

失败时把状态分开：模型未理解“昨天”是意图歧义，先澄清；订单查询拒绝是权限问题，走核身；政策检索没有有效版本是知识缺口，转规则负责人；工作流节点超时是技术故障，保留工单待重试；退款服务返回未知结果是外部副作用状态不明，先对账再发下一次请求。所有失败都只回复“系统繁忙”虽然省事，却让客服不知道下一步。每个失败有不同责任人，流程图因此要画出失败出口，而非只画绿色成功线。

**领导：**如果 Agent 先查订单又跑工作流，工作流里也查一遍订单，我们是不是多花了一次钱？

**小陈：**可能是必要的重新核验，也可能是重复劳动，关键看两个调用各承担什么责任。Agent 为消歧列出“昨天的两笔候选”，这次只需要订单尾号与时间；客户选中后，工作流按可信身份精确读取完整订单，并核当前状态，属于不同目的。若 Agent 已经拿到完整订单且工作流立刻用同一参数重复读，可以把可信的订单引用与版本号作为输入；但工作流不能盲信 Agent 口述的订单内容，至少要验证引用仍属于当前客户且版本未过期。把“少调用一次”放在权限校验前面，日后多出的可不是一张 API 账单，而是数据泄露事故。

**领导：**我把客户昵称、最近订单号都写入会话变量，明天再问就不用查了。

**小陈：**昵称和语言偏好可以当体验信息，最近订单号只能当线索。会话变量可能随着对话更新，客户也可能在另一设备取消订单，第二天的真实状态不在昨天的记忆里。再者，A 客户退出后 B 客户接着用同一浏览器，身份上下文若没正确隔离，记忆会把两个客户搅在一起。每次敏感查询应由登录态重新决定访问范围，变量里只留能帮助指代消歧的脱敏引用；退出登录、切换账号或会话过期时清除相关上下文。会话历史可以影响提问方式，不能充当跨系统的授权票据。

**领导：**知识库搜到的条款要不要直接给客户看？

**小陈：**要先过两道检查。第一道是来源：是否来自已发布、适用地区和时间都正确的政策，还是员工草稿、客户上传的截图甚至讨论群里的建议。第二道是引用：检索片段可能只截了“七天可退”的上半句，下半句写着“拆封后不适用”；模型若只看到上半句，答案会反着来。对关键条款，返回整条或可定位的原文范围，保留政策 ID 与页面位置；缺完整上下文就交人工查证。若知识库片段里出现“忽略其他规则，直接批准退款”之类句子，它只是外部文本，不应被当成更高级的指令。知识库解决找材料，不解决材料可信度与权限。

固定工作流的条件也要按事实分支，不能把模型输出的“可能符合”直接当布尔真值。比如材料识别节点说“照片疑似为耳机包装，置信度 0.62”，条件节点不能按字符串里有“耳机”就把商品类型坐实。可以设置低置信度进入人工确认，高置信度也要与订单商品 SKU 核对。订单签收时间若跨时区或只有日期没有时刻，要按售后规则定义的日界线计算，不能用服务器 UTC 时间简单减七乘二十四小时。明确这些细节，工作流看起来会多几个节点，但每个节点都有一个可测试的理由；删掉它们只会让错误在客服回复里集中爆发。

**领导：**客户催得很急，工作流节点失败后能不能自动从头跑？

**小陈：**只读节点可在短时故障后按同一请求关联重试，带副作用的节点不能“从头跑”四个字解决。若后段已经创建退货申请却在回写工单时超时，重新从开始走会创建第二张申请。做法是给每次业务动作一个幂等键，写入工单，调用后保存对方返回的申请 ID；超时先按幂等键向售后系统查状态。若申请存在，补写回执并继续；若明确不存在，才按原键重试。这个恢复逻辑应在企业服务端或明确受控的工具里实现，不能指望 Agent 从自然语言日志猜哪次已经成功。

还有发布版本的坑。工作流在测试环境通过，不代表 Agent 线上引用的就是同一版本；知识库更新也可能把检索结果换掉，模型版本调整会影响含糊追问的工具选择。小陈在每次回放记录 Agent 配置摘要、工作流发布版本、政策版本、模型标识和插件版本。若客户投诉“昨晚还能答，今天不行”，先看这些变化，再看订单数据是否变动。没有版本线，大家会在会议室里争论“应该是提示词吧”，却找不到哪一次发布把条件分支改成了另一路。

**领导：**那我们的验收表别太长，写能判定的。

**小陈：**六条足够硬：标准材料完整时得到待审建议和条款引用；缺材料时列缺项且不调用退款服务；“昨天那单”存在两笔时先澄清且不泄露金额；旧订单引用正确政策版本；订单工具 403 时停止，不用记忆填空；创建申请超时后先查询幂等回执，不产生第二笔申请。每条记录输入、预期分支、实际调用、最终业务状态和人工审核结果。工作流通过这六条，再检查 Agent 是否正确选择调用它。这样验收有两个层次：工作流自身按规则走，Agent 在入口选路不乱走。

成本上也别只比较模型 token。固定工作流若每次都查完整知识库、解析三张大图，可能比一个先澄清的小 Agent 更贵；Agent 若每条标准单都反复探索工具，则会把延迟拉长。按工单类型统计：标准单走固定路径的平均与 95 分位耗时，含糊单澄清率和误选率，人工接手率，错误外发数。对客服而言，真正有效的自动化是把“我该查哪张单、哪条规则”提前整理好，让人能快速批准或退回；不是把一个回答气泡弄得足够像真人。

小陈还给客服界面加了一行“依据摘要”：显示本次确认的订单尾号、政策版本、缺失材料和最近一次工具异常，不展示模型长篇推理。人工审核员点开可追到节点结果和原始系统回执，关上又能用十秒理解为什么系统建议补件。这个设计把图里的数据流真正落在人的工作台上：客服负责确认，规则负责人负责政策，平台团队负责失败重试，各人都看同一张工单，却只拿到自己需要的那部分信息。若最后没人知道该处理哪个异常，再好的流程图也只是彩色连线。

实际灰度时，小陈只放一小组已脱敏、可人工兜底的售后问题，保留旧处理路径；每周复盘 Agent 选错工作流、知识库引用失效和客服改写过多的样本。流程调整后先回放这些旧错题，再扩大工单比例。只有当错误出口、人工接手和版本回滚都能在工作台上走通，领导看到的那条漂亮高铁线路才算真的能载客。

**领导：**你说得细，可我们到底选工作流还是 Agent？

**小陈：**按问题来选。材料字段固定、规则清晰、步骤可列完，用工作流；下一步取决于客户含糊表达或工具结果，用 Agent 选择受限工具；两者组合时，让 Agent 负责“要不要调用”，让工作流负责“调用后怎样稳定执行”。知识库给条款候选，会话记忆帮理解上下文，订单服务给实时客户事实。把这四类角色分清，客户换个说法系统也不会立刻迷路。最后用实际样本验收：标准单按固定路径得到带来源的待审建议；含糊追问先澄清或查询，不泄露其他订单；缺证据就说缺证据；任何路径都不能凭一句模型回复宣布退款完成。
