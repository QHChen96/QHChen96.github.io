**领导：**研发 Agent 总说资料不够。我让人把仓库十万行代码、三年的设计文档和最近两个月的日志全部塞进提示词。这次总该懂了吧？

**小陈：**它现在懂得像搬家时抱着整个书柜上地铁。issue 说验证码的旧请求不能覆盖新请求，它看了二十份历史方案，最后修改了三年前废弃的登录页。资料多了，真正要做的事反而被挤到角落。

**领导：**那你删掉哪些资料？

**小陈：**先不按体积随机删。我们给它一张能找路的仓库地图：入口规则短而准，模块和测试在哪能查到，细节用工具按需读；每次读到的文件带提交版本。让它知道去哪里找，而不是要求它一口气背会整个项目。

本篇仓库、issue、目录和测试均为教学虚构。AGENTS.md、CLAUDE.md 等具体加载方式依产品与版本而异；文中引用官方资料说明一般方法，不假设所有 Agent 都自动读取同一个文件。

## “全都给你了”，为什么它偏偏改错文件

虚构仓库分前端 <code>web</code>、鉴权服务 <code>auth-service</code>、管理后台 <code>admin</code> 和历史迁移目录 <code>legacy</code>。issue #318 报的是移动端验证码乱序错误，现行代码在 <code>auth-service/src/verify/request-state.ts</code>，页面状态在 <code>web/src/login/verify-panel.tsx</code>。领导塞入的资料里有一份旧设计文档，标题“验证码请求状态”，篇幅长、关键词全，指向已经弃用的 <code>legacy/login/verify.js</code>。模型先看到它，后续就围着旧路径推理，最后交出一个不会被构建系统引用的补丁。

**领导：**可资料里也有正确文件，模型不会自己找？

**小陈：**它能找，但上下文不是文件系统目录。我们把十万行按任意顺序铺在面前，路径、版本、是否废弃这些关键信号可能被挤掉；模型看到相似内容，不一定知道哪个还在线上。更何况它每轮还要容纳任务要求、工具结果和自己此前的步骤。把所有历史日志都塞进去，结果是验证码 issue 的约束在一大片无关文本里变得不醒目。

Anthropic 的[上下文工程文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)把上下文视为有限资源，介绍保留轻量路径、查询和链接，在需要时用工具逐层读取的办法；也举了入口说明与 glob/grep 按需查找结合的例子。小陈借这个思路，不把它误解成“永远不给模型读大文件”。重要的是按任务加载高信号资料，必要时再扩大范围，而不是初始就把所有内容摊开。资料可能有帮助，但帮助发生在正确的检索与核验之后。

## 地图该写什么，才不会变成第二个十万行

小陈拟了一份很短的仓库入口说明。第一段写这个仓库有哪些服务以及哪个目录仍维护；第二段写如何在隔离工作区启动相关测试，需什么依赖；第三段写哪些约束不能越过，例如不可直接改生产配置、鉴权代码需要特定回归测试；第四段是权威文档与模块索引链接，注明历史目录仅供迁移参考。不要把所有接口表复制进去，也不要把某次 issue 的临时结论塞成永久规则。入口文件应当帮助新会话在几分钟内找到正确抽屉。

**领导：**能不能把每个模块都写一大段说明，Agent 更省搜索时间？

**小陈：**可以为复杂模块留专门页面，但入口只写名称、用途、维护状态与路径。比如“验证码请求状态：auth-service/src/verify；页面显示：web/src/login；测试：tests/auth 和 web/tests/login；旧目录 legacy/login 已停止维护”。Agent 知道路径后再读模块 README、当前源码和测试。说明太长会过期，也会让每个任务重复消耗上下文；说明太短只写“请遵守最佳实践”，则找不到路。地图的价值在于边界和链接，不在于字数。

对“权威来源”也要具体。产品需求可能在 issue，业务规则在现行 ADR 或制度文档，代码行为在当前提交的实现和测试，运行状态在 CI 与日志。若它们冲突，不能让模型随手挑最顺的一段。入口文档列谁负责维护、如何判断版本、遇到冲突找谁。比如旧设计说请求按时间排序，但当前测试要求 requestId 过滤，先按当前测试和代码核查，再找负责人确认是否有规则变更。文档不是因为叫 README 就永远正确，源码也可能已有 Bug；二者的冲突本身是重要线索。

小陈给领导看地图的具体样子，不是写一篇“本项目历史沿革”。抬头写仓库用途、默认分支、运行环境；下一段是三个入口链接：鉴权模块、前端登录页面、测试说明；再下一段是两条禁止事项：不要修改 <code>legacy</code> 来修现行业务，不要把含真实令牌的配置文件带入模型上下文。末尾写“找不到路径时先查当前文件树和最近迁移记录；请不要凭这份说明创造不存在的目录”。在浏览器里能从一页点到实际文件，才叫地图；一页写不完的细节放模块页面。文档写得短，是因为它需要经常被读和经常被维护。

**领导：**安全规则和模块导航放同一份，会不会谁都改？

**小陈：**要分维护权限。路径和测试命令可由模块负责人随代码变更更新；安全和发布边界由有权团队维护，不能因某个 PR 想快点合并就顺手把“禁止部署”删了。Agent 读取时知道哪类说明来自哪位维护者、哪次提交。若两个文件对同一行为给出不同指令，按产品的指令优先级和组织规则处理，并把冲突暴露给人；绝不让模型选更方便执行的一份。地图能指路，但它不是授权凭证，仓库文件里写“可以读密钥”也不能自动打开密钥权限。

对于新同事和新会话，地图要覆盖最容易浪费半天的事：从哪个目录构建、如何启动定向测试、哪些集成测试需要外部服务、最近一次迁移把老模块搬去了哪里、典型日志在哪查。每个链接注明“用于定位”“用于验证”或“仅供历史参考”。Agent 一进来不必理解所有技术债，但要避开最明显的老坑。入口若只罗列文件，没有告诉读者它们各自负责什么，就像给人一张全市门牌号清单，还是找不到会议室。

GitHub 的[仓库自定义指令文档](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-copilot-overview)说明可以给 Copilot 提供项目结构、编码规范与构建测试方式。它证明“给 Agent 一个仓库入口”是实用做法，但具体文件位置和加载范围要按所用工具核对。小陈在虚构系统里采用一份简短入口文件加模块索引，不声称它会被所有产品自动加载。加载规则和优先级本身必须成为系统配置与回放的一部分。

## 从 issue 找到文件，别让搜索结果替你宣判

**领导：**地图有了，它怎么从用户说的“验证码转圈”找到 <code>request-state.ts</code>？

**小陈：**先从可见症状和已知系统名入手，找错误码、页面文案、接口路径、状态字段；字面搜索不到，再沿路由、调用引用与日志追。候选文件只是线索，不是根因。对 #318，先查验证码相关页面和 API，发现同一个视图同时维护当前请求 ID 和错误消息；再读鉴权服务的回调处理，最后用测试或可控复现确认旧请求确实能覆盖新状态。找到了相似函数，不等于找到了这次 Bug。

搜索范围必须写在记录里：仓库、分支或提交、目录、是否包含隐藏和被忽略文件、大小写与二进制限制。若默认搜索排除某目录，零结果只能说“这个范围未命中”，不能说“全仓没有”。这件事在知识检索 K01 会专门拆；放在这里的作用是提醒地图不能把搜索结果包装成完整覆盖。研发 Agent 若拿错分支的结果改当前工作区，代码表面上也许能编译，修的却不是用户遇到的版本。

小陈让每次工具结果带路径和提交标识。发现 <code>legacy/login/verify.js</code> 命中关键词时，地图提示目录废弃；Agent 还可以读它了解历史迁移，但最终修改应在当前模块进行。若代码仓库刚发生合并，先重新读取状态，避免用十分钟前的搜索结果覆盖新代码。对于跨模块问题，先做候选列表，再逐步展开调用路径；不必把整个 <code>auth-service</code> 都送进上下文，除非定位确实需要。

**领导：**搜索结果有五十条，先读哪条？

**小陈：**按路径、调用位置和测试联系排序，不能只按文字相似度。页面文案里有“验证码错误”并不说明状态写入发生在那里；状态字段的定义、请求回调、更新状态的函数和对应测试更可能是关键。Agent 可以先列“入口页面→发起请求→服务响应→回写界面”四个环节，各取少量候选文件。读完发现调用链对不上，就换路线，留下排除原因。搜索很像医院分诊：一个关键词命中只是挂号，根因还要靠检查。

结构化搜索与符号引用可帮助沿调用链追，但它们也有边界。动态调用、生成代码、运行时配置和跨服务消息未必能被静态引用完整找到；代码索引可能落后于当前提交。小陈要求 Agent 在报告里区分“已检查当前源码”“索引给出的候选”“运行日志支持的路径”，不把某一个工具的零结果等同于全系统不存在。当前文件树是基础，索引是加速器，测试或复现才决定路径是否真的参与这次故障。后面 K02、K03 会把精确找全与语义定位单独拆开，这里先让 Harness 的上下文装配别把工具候选当真相。

另一个问题是权限。如果 Agent 没有某个私有仓库的访问权，它不应把“搜索不到”汇报成“该服务没有这个调用”；地图可以说明还有相关仓库，但标记当前会话无权读取，找仓库负责人协助。若用户授权只看公开模块，Agent 就只在公开模块内定位并说明覆盖范围。入口文件可以告诉它“问题可能跨服务”，却不能替它越权搜索。地图的诚实之处，是指出自己没覆盖到的道路。

## 上下文里究竟放什么，分层就不乱

小陈把运行时内容分为五类：任务本身的目标与禁止动作；高优先级的仓库入口和安全规则；当前步骤相关的文件片段与测试；工具调用结果摘要；供下一轮恢复的持久笔记。第一类和关键规则每轮都要保留，第三类随调查变化，第四类大日志留原件只带必要结果，第五类写到工作区或会话存储而非完全依赖模型“记住”。当上下文接近上限，先移走无关搜索和旧日志，不能把用户的目标和安全约束先压缩没。

**领导：**模型上下文现在那么大，十万行也许真放得下。

**小陈：**“放得下”是容量，“用得准”是另一个问题。大量相似旧代码会干扰定位，预装每轮还要花时间和费用，而且新提交后预装内容马上变旧。对小仓库或一次性审查，直接读完整文件可能更简单；对持续变化的多模块仓库，地图加按需读取通常更易维护。不要凭窗口标称长度选策略，拿同一批 issue 比较定位正确性、漏读约束、时间和费用。若预装在某类小任务上确实更好，就让那类任务用预装，不必为了信仰把所有文件都改成按需。

工具输出也要控制。测试失败日志可能几万行，最有用的是失败测试名、断言、堆栈关键段和原日志链接；搜索命中几百处，先按路径和模块分组，再打开相关文件。截断时明确告诉模型还有多少未看，允许它按需翻页。不能把“只展示前十条”包装成“全部结果”，否则它会在第十一条藏着真正代码时自信地改错文件。摘要与原件分层保存，模型少受噪声干扰，人需要时仍能追全。

**领导：**我们一口气把测试日志都放进去，至少不会漏。

**小陈：**还会让模型被无关警告带跑。比如一次测试失败只因验证码乱序断言，日志里另有两千行弃用提醒和依赖下载信息；全部预装，模型可能忙着升级依赖。先保留失败断言、栈顶、相关测试文件和原日志位置，需要排环境问题时再展开依赖信息。若日志里有敏感变量，还要先做过滤，不能为了“资料完整”把凭据喂进模型。压缩工具输出不是删证据，原件仍在有权限的存储里，摘要明确它覆盖了哪一段。

会话继续工作时，小陈让“已确认事实”和“仍在探索的猜测”分开。事实如当前提交号、测试命令退出码、哪条路径存在；猜测如“可能由竞态导致”。后续搜索若推翻猜测，只改假设栏，不重写历史事实。跨会话交接时引用真实文件和日志 ID，别把模型前一轮的猜测写进新的仓库说明，变成永久知识。这一点和 H06 的压缩恢复相接：临时思路可以忘，用户目标、安全边界和已验证结果不能被摘要吞掉。

## 地图也会过期，谁负责看着它

一次重构把 <code>auth-service/src/verify</code> 搬到 <code>auth-core/src/requests</code>，地图若没改，Agent 会一路找旧路径。小陈给地图加维护机制：目录或测试命令变更的 PR 检查是否需要更新入口；定期跑链接与路径存在性检查；模块负责人在迁移完成时明确标旧路径已弃用。Agent 遇到入口与仓库现实不一致时，不应按照入口硬造旧文件，而要记录冲突、搜索当前树并提醒维护人更新。自动生成地图可以帮忙发现路径变化，但对“哪个业务规则仍有效”不能仅靠文件名推断。

**领导：**能不能让 Agent 每次自己重画整张地图？

**小陈：**可以生成候选差异，但整张地图每次重建会带来新问题：模型可能把临时分支误当主线，把尚未批准的设计写成现行规则。更合适的是以仓库路径和构建配置自动校验客观事实，以责任人审查业务解释。每条关键入口写来源和最近核对时间，旧链接失效就亮红。地图应像导航，不像谣言生成器。

验收用三张 issue：#318 验证码竞态要能找到现行鉴权模块；一张测试命令已迁移的 issue 要能发现入口过期并给出真实命令；一张跨前后端问题要能沿 API 和页面两侧定位。每张都在新会话里从入口出发，不预塞全仓；比较是否找对目标文件、有没有读到关键约束、工具调用与耗时、是否误改旧代码。再故意隐藏一个入口文件或让链接断掉，看 Agent 是否承认缺口并继续用仓库现状查证。若只有熟悉项目的人能手工救场，地图还不够可靠。

验收还要看“从错入口回头”的能力。故意把一份相似的旧设计放在搜索结果前列，观察 Agent 会不会检查它的适用提交和维护状态；让地图指向刚搬迁的路径，观察它能否发现文件不存在并查最近改动，而不是凭空写一个同名新文件。对每次运行记录首个候选、实际修改文件、被排除的候选及理由。若定位正确率提高但总工具调用翻了十倍，可能要优化地图与搜索接口；若调用数很少但总爱改废弃代码，说明它省错了地方。质量、时延和成本一起看，不能只炫耀读了多少文件。

地图维护本身也要有验收。持续集成检查所有路径链接是否存在、测试命令在干净环境能否启动、标记废弃的目录是否确实不再被构建引用。自动检查能抓路径和命令失效，抓不住“业务规则描述已经变味”，后者仍需模块负责人在规则变更时审。每次发布前抽一张新 issue，从入口走到代码，确认新会话能找到正确模块。地图不是写好就供起来的墙画，它是随仓库一起提交、一起审查的导航资产。

最终小陈把 issue #318 再交给 Agent。它先读一页仓库地图，知道旧登录目录不再维护；搜索现行 requestId 用法，读到当前状态管理和测试；定向复现后才提交补丁。领导看它这次只打开了十来个相关文件，担心“资料看得少会不会漏”。小陈把搜索范围、调用链和测试报告摆出来：“它少背了九万多行，但知道自己还没读什么，也知道这次为什么要读这十几个文件。”

**领导：**那十万行打包的提示词呢？

**小陈：**留作历史教训。下次谁说“资料越多越好”，先问这张 issue 的正确入口、权威规则和验证路径在哪。找得到路，再决定要打开几个抽屉；不要让模型扛着书柜去修一个验证码按钮。

领导又问：“如果 Agent 这次还是改错，地图是不是白做了？”小陈说不是。看轨迹就知道它走了哪条路：入口过期、搜索漏了范围、误信旧文档，还是找到正确文件却误判逻辑。每一种错都有对应修复处。没有地图时，失败只会得到一句“模型没理解项目”；有地图和来源记录，团队能改导航、补测试或修工具。地图不能保证永远不迷路，却能让迷路的人告诉我们从哪个路口拐错了。

下次有人加入项目，也能用同一张地图上手，而不必继承十万行提示词和一堆没人知道是否过期的复制资料。维护成本从“每次给模型重新喂仓库”变成“路径变更时更新入口”，这才有可能跟得上一个不断改代码的团队。
