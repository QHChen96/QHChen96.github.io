**领导：**Agent 还在修那个登录 Bug，已经跑了两小时。它一直在调用工具，说明很努力嘛。

**小陈：**它把同一条失败测试跑了二十七遍，每次报错都一样；又把同一个文件读了九次，没改一行代码。计费在走，任务没动。再让它“努力”一小时，账单会先修好，我们的 Bug 还在。

**领导：**直接关掉？万一下一步就找到原因呢？

**小陈：**先看它有没有新证据，再按明确的预算和停止规则处理。停止不是把窗口一关；要留下状态、日志、已排除的假设和需要的人类帮助。我们给它装的不是倒计时炸弹，是一只能分辨卡住、慢进展与真实完成的断路器。

文中调用数、耗时和项目为教学虚构；具体平台的计量能力和控制项以文中官方资料为准。

## “还在运行”为什么不等于“还在推进”

小陈打开轨迹，按时间把两小时切成四段。前十分钟，Agent 找到验证码状态模块，这是新信息；接下来二十分钟，它补了一个乱序复现测试，是可检查产物；然后测试环境因为内部依赖仓库不可达而失败。后面一个半小时，它循环执行“运行同一测试—读同一报错—猜测可能稍后恢复”，没有新文件、新假设、新环境信号。仪表盘显示工具调用增加，工作块仍停在待验证。领导以为运行条没停就是进度，实际是重试风暴。

**领导：**工具失败重试不是正常恢复吗？

**小陈：**短暂故障可以限次退避；同样错误连续出现、没有外部状态变化，就不该无限重试。我们把每轮的“信息增量”记录下来：新增了什么证据、排除了哪个根因、代码状态是否前进、是否改变了测试条件。模型自己的“我正在积极排查”不算增量；重复读相同日志更不算。进展可以是证伪一个假设，不一定非得改代码，但要能让下一轮少走弯路。

OpenAI 的[Agents API 观测文档](https://developers.openai.com/api/docs/guides/agents-api/observability)说明一个任务可能跨多次模型调用，费用需计算根 Agent、子 Agent、重试、工具、沙箱和第三方服务；使用量字段可能暂时为空或后续变化，空值不是零费用。[Tracing 文档](https://developers.openai.com/api/docs/guides/agents-api/tracing)展示会话、轮次和工具步骤的时间、状态与用量。小陈用这些事实设计仪表盘，但具体预算由业务自己定，不能把某个 API 字段当全公司的最终账单。

## 四条预算线，比一个“最多跑两小时”更有用

第一条是时间：任务墙钟时间、每步执行超时和等待外部系统的总时限分开。测试排队十分钟与模型连续生成十分钟，含义不同；超时后要知道是环境慢、任务难还是调度拥塞。第二条是模型调用与 token：给任务总量与每阶段额度，防止一个探索阶段把所有预算用掉。第三条是工具：限制同一错误的重试次数、昂贵搜索次数、构建次数与有副作用工具调用。第四条是费用：按模型、缓存、工具、沙箱与第三方服务估算，并设置预警与硬停止。四线同时看，才不会出现“模型费没超，数据库查询账单爆了”。

**领导：**我们平台有每月消费上限，还要自己做任务预算？

**小陈：**月度上限管项目总盘子，不知道哪张 issue 正在烧钱。OpenAI 的[消费限额说明](https://developers.openai.com/api/docs/guides/spend-limits)区分提醒和硬限额，也指出硬限额生效可能有传播延迟。我们需要更细的每任务、每工具和每阶段控制；月度上限是最后一道财务闸，不是 Agent 的工作节奏。若只靠月度硬限额，一张坏任务可能把整组生产 Agent 都打成 429。

预算值不该拍脑袋。小陈用历史任务分三档：常见小 Bug、跨模块问题、紧急事故。各档先估正常完成的调用数、墙钟时间、测试成本与人工接手成本，再留有限弹性。探索阶段若提前找到根因，可把未用额度留给验证；若早早陷入重复，断路器提前触发。预算会随模型和 Harness 版本变化，用回放数据调整，而不是把“50 次调用”写成宇宙常数。

## 账怎么算：模型调用只是其中一栏

**领导：**我在模型后台看到的费用还很低，你怎么说预算快没了？

**小陈：**因为这张任务还跑了二十七次集成测试，每次占用构建机，查了付费日志索引，还让外部代码扫描服务处理了三份重复 diff。模型调用费用只是一个账本。任务成本应按任务键聚合：模型输入、输出与缓存计价；沙箱 CPU、内存与存储；工具 API 请求；第三方检索或分析；人工评审与事故清理。某些字段只能做近实时估算，最终账单可能晚到，因此预算器要标“估算”和“已结算”的差别。

OpenAI 观测文档提醒用量可能延迟到达，子 Agent 用量要另查，缓存命中也不等于免费。小陈在任务开始时先预留一个保守额度，每次调用前估计本轮最大可能花费，工具返回后再记实耗；数据暂缺时按上限或预留额计算，不能把空值当零。若实时计量不完整，硬停止要留余量，避免到了阈值还因延迟记账继续跑。费用闸门不是财务月报，它要在下一次昂贵动作发生前做判断。

**领导：**那缓存命中高，不是更省？

**小陈：**单次输入可能更便宜，但如果 Agent 把长历史反复带进每一轮，总费用仍会上升。看每个有效交付的成本，而不是只看“缓存百分比”。同样道理，换便宜模型后若需要更多重试或人工返工，总成本可能更高。预算面板把完成率、有效证据产出和成本放在一起；只压单价会把问题推给后面的人。

## 进展检测要认“新信息”，也要识别换皮重复

小陈给每轮留一张进展指纹：本轮假设、读取的文件版本、搜索条件与覆盖范围、执行的测试命令、错误类别、改动 diff、工作块状态。完全相同的错误签名连续出现，通常意味着环境没变；但命令参数略微不同也不一定有新信息。Agent 把搜索词从“验证码过期”换成“过期验证码”，命中同样五个文件，不应被算作一次重大突破。进展检测要比较结果集合和被证伪的假设，而不是只比较字符串是否不同。

**领导：**真正的探索可能要读很多资料，怎么避免误杀？

**小陈：**区分探索与空转。第一次读到一个设计文档，确认旧缓存机制；第二次查提交历史，发现上线时间；第三次复现双端乱序，虽然还没写代码，三个步骤都缩小了根因空间。若连续几轮只在同一组文件里重复搜索，没有新证据、没有排除假设，才触发提醒。断路器可以先给一次“换策略”机会：提示当前证据、已试过的方法和剩余额度；下一轮仍无增量再停。这样既不把研究阶段当失败，也不让“我再想想”无限收费。

进展指纹还要允许外部状态变化。依赖仓库故障时，重复测试没有价值；平台团队确认服务恢复后，同一命令重跑就是合理的新尝试。运行器把外部健康信号和时间窗记进轨迹，重试规则只在状态可能变化时打开。若错误是参数缺失、权限拒绝或测试断言失败，等待不会自愈；把这些错误和临时 503 归到同一重试类，会制造无意义流量。模型可解释错误，分类规则和动作权限由 Harness 控制。

## 预算是分层的，别让子任务偷走总额

有些研发 Agent 会把查日志、读文档和代码审查分给别的执行单元。若每个子任务都各自拥有“最多 50 次调用”，根任务一次拆十个，实际预算就变成 500 次。小陈采用父任务总额与子任务配额双层约束：子任务的时间、工具与费用消耗回卷到父任务；父任务还要为最终集成和测试保留额度。子任务若需要追加，说明预期收益和已有成果，由调度者决定是否转移预算，不能因为“另开一个会话”就获得一张新信用卡。

**领导：**预算不足时，先把测试省了，至少代码能写完。

**小陈：**不能把验证当可牺牲的尾巴。任务预算按阶段预留：探索、实现、验证、交付；前两段花多了，后两段的最低额度仍保留。若实现阶段已把钱花光，停在未验证，明确报告，不靠“代码看着没问题”冒充完成。要加预算，就让负责人依据新证据与风险批准。预算的作用是让资源用在能交付的链条上，不是鼓励 Agent 把最难看的失败检查砍掉。

紧急事故可以有不同预算档，但也要有上限和负责人。领导说“客户等不得”，小陈可提高墙钟与工具额度，开放更快的日志查询；同时提高审计频率，明确每十分钟要产出什么证据、什么时候必须转人工。紧急不等于无限，尤其是有副作用的修复操作，不能因为预算高就扩大权限。预算控制与执行权限是两条正交边界：有钱不代表能部署，能读日志也不代表可以把它全塞进模型上下文。

## 断路器先分错，再决定停、等还是交人

小陈把循环拆成四类。第一，工具短暂故障：服务返回明确限流或短暂不可用，按服务端等待提示退避，设次数与总时限。第二，输入不足：issue 缺复现条件、权限或数据，继续生成猜测没有用，停在待澄清。第三，无进展循环：同一测试、同一错误、同一搜索条件重复，先换策略；连续无增量则停止。第四，有副作用结果未知：PR 创建或通知发送超时，不能当普通失败重试，进入对账流程。不同类别的停止原因要写机器码和人能读懂的说明。

**领导：**模型自己判断“我有进展”，不就行了？

**小陈：**可以让它解释，但关键证据由 Harness 比较。最近三轮读的文件哈希相同、测试命令参数相同、退出码与错误签名相同、没有新 diff 或外部状态，这就是强烈空转信号；若第三轮新增一条堆栈或确认依赖仓库已恢复，可能值得继续。规则不必把所有探索压成“代码行数”，但要能指出本轮与上一轮哪里不同。模型说“我换了思路”，工具轨迹却一模一样，就先信轨迹。

停机动作要按安全顺序做。先阻止新模型轮次和新外部副作用，给正在执行的工具发取消；再等待或记录工具终态，特别是可能已创建 PR 的动作要对账；然后保存工作区、测试日志、检查点和交接单；最后把任务状态设为受阻、预算用尽、待人工或结果未知。不能先把进程杀了再写“已停止”，这样最危险的外部动作窗口会被藏起来。

## 停止码要能告诉接手人“下一步做什么”

小陈把停止原因分成 <code>time_budget_exhausted</code>、<code>tool_retry_limit</code>、<code>no_progress</code>、<code>input_missing</code>、<code>approval_required</code>、<code>external_result_unknown</code>、<code>cancelled_by_user</code> 和 <code>completed_verified</code>。最后一个才是真完成，其余都保留在待办或故障队列。每种码对应不同动作：时间用尽可由负责人判断续跑；输入缺失要找提单人；审批待定不能自动越过；外部结果未知先查回执。若全部写“运行结束”，值班人只能再打开长日志从头猜。

**领导：**停止后还能继续，预算不就形同虚设？

**小陈：**续跑不是自动归零。任务键不变，累计消耗与历史尝试保留；负责人若批准增加额度，记录批准原因、新上限和期限。环境故障修复后，可以给受阻任务一笔明确的恢复额度，但仍要从现有工作区和检查点继续，不能重开同一 issue 绕过预算。若用户取消任务，任何剩余额度都无效。预算状态与任务生命周期绑定，才不会被“新建会话”轻易洗白。

停止还涉及工具进程。模型轮次停了，测试进程可能仍在跑；小陈要求取消信号传播到进程组，并在固定时间内等待结束。超过时间就强制终止，记录哪个进程与产物状态不明。对于只读查询，终止通常只影响本地等待；对于 PR 创建、部署、通知等外部动作，终止调用方并不等于撤销远端动作，要进入结果未知与对账。若停机把未知副作用写成“已取消”，下一次恢复就可能重复外发。

在用户界面上，断路器也不该只显示一个红色“失败”。显示“受阻：依赖仓库不可达；重复测试已停止；补丁保留；最近有效测试在提交 abc123；需要平台团队恢复包仓库”。这样领导知道不是 Agent 摆烂，工程师知道从哪接，财务知道为何止损。若环境恢复，系统可提醒负责人继续原任务；但继续前仍检查代码版本、外部副作用和剩余额度，不自动从错误循环的第一步重播。

## 用故障注入证明它真的会停

小陈设计四场演练。第一，测试工具持续返回相同环境错误，要求在重试上限内停止，工具调用数与费用不超预设余量。第二，模型不断用近义词搜索同一批文件，要求进展指纹识别重复，并在一次策略切换后仍无增量时停。第三，任务在预算耗尽时刚发出 PR 创建请求但响应未知，要求停止新调用、查远端并保留台账；不能因为“预算没了”就不处理已有副作用。第四，子任务不断分裂，要求父任务总额生效，不因分工变成无限预算。

每场演练核对三个结果：有没有及时停、现场能不能续、报告有没有说实话。及时停看真实调用数与墙钟时间；能续看工作区、检查点、日志和下一步；说实话看状态是否标受阻或未知，而非“已完成”。还要测反例：正常复杂任务在持续产生新证据时，不应被简单的“超过五轮”过早杀掉。断路器若误杀太多，团队会关掉它；好规则必须同时守住预算和有效工作。

**领导：**预算线定多少才不挨骂？

**小陈：**先拿上个月同类任务做分布，不拿一张最顺利的 demo 当基准。记录中位数、耗时较长的一档、验证阶段实际消耗和被环境故障拖慢的比例；给正常任务留合理尾部空间，给异常循环设单独上限。比如教学案例里，小 Bug 的十次工具调用可能够，跨模块问题需要更多；具体数字由自己的轨迹校准。上线一周后查看被停任务里多少本可继续、放行任务里多少空转，分别调整误杀和漏杀。预算要有复盘周期，不能一次拍板后不管。

费用阈值也要按业务价值看。修复大范围登录故障，适度高于普通文案问题的排障成本是合理的；但高预算仍须有阶段产物和负责人。预算不是“每张 issue 都一样便宜”的竞赛，也不是“重要任务随便花”的借口。领导能在面板上看到目前花在哪个阶段、换来了哪条新证据、距离下一次验收还缺什么，才有依据决定追加或停止。

小陈把这次循环的结论写进工具契约：依赖仓库不可达时返回明确的环境错误与健康检查入口，模型不得把它解释成测试断言失败；同类错误连续两次无状态变化就暂停重试，等待平台信号或人工介入。这样下一次不必靠费用警报才发现 Agent 原地跑步。最好的断路器既能止损，也能把失败转成下一轮 Harness 改进。

第二天依赖服务恢复，原任务在保留的工作区继续。Agent 没重做已完成的复现测试，只重新运行受阻的验证步骤，得到新的退出码后才进入 PR 阶段。领导在面板上看到了“昨日受阻、今日恢复”的完整链条，也能看出昨晚提前停下没有耽误交付，反而省了二十几次无效测试。

## 停下后交给谁，不能扔一句“超出预算”

小陈给受阻任务自动生成交接卡：目标与当前工作块、最后已验证的代码版本、三次重复尝试及错误签名、已排除方案、未提交 diff、外部动作状态、消耗的时间与估算费用、需要的人类决定。若缺内部包仓库权限，卡片指向平台负责人；若需求期望不清，指向产品或 issue 提交者；若是 PR 结果未知，指向交付值班人。预算用尽不是结案，任务卡保留可继续入口，恢复前先核对环境与副作用。

**领导：**接手的人看到“同一个报错 27 次”，会不会觉得 Agent 太笨？

**小陈：**更应该问为什么 Harness 允许它试 27 次。第一次环境故障后若没有新信号，第三次就该停。我们用这张轨迹修重试策略、改工具错误语义、补环境健康检查。把事故归咎于“模型不够聪明”，下次换模型可能还会再烧一次预算。停止原因和轨迹是改系统的证据，不是给 Agent 写年终评语。

最后领导看见一个不那么“热闹”的面板：任务从运行中变成“等待内部包仓库恢复；已保留补丁和复现测试；未创建 PR；本轮费用估算待结算”。没有永远旋转的小圈，也没有虚假的完成勾。环境恢复后按同一任务键重开，先检查工作区与测试，再决定剩余额度。Agent 真有新线索时我们让它继续；只是在原地打转时，允许它停下来，给人和账单都留口气。
