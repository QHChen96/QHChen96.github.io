**领导：**你给研发 Agent 的新项目有三千个文件。Deep Agents 不是号称能做长任务吗？让它进门先把全仓读完，免得做一半说“没看到”。

**小陈：**上次我们就是这么做的：日志和文件内容把上下文塞满，模型到改代码时反而忘了 issue 里最重要的“不能改支付金额计算”。Deep Agents 的价值不是突然长出无限记忆，而是把长任务拆成“当前需要看什么、哪些结果放到文件里、哪块交子任务处理、主会话只拿回什么”。像做项目的同事，有目录、笔记和分工，不必把整个仓库背在脑子里。

**领导：**它多了个文件工具，就算新原理？

**小陈：**不是单独一把工具。我们今天沿同一张 issue 看主会话、虚拟文件系统和子 Agent 的信息去向：大工具结果何时卸载到文件，摘要保留什么，子任务输出怎样回流，重启后凭什么找回关键依据。再故意让长日志超限和子任务超时，验证它不会把“没读到”说成“已查完”。

本文的项目、issue、文件数量和性能数字都是教学虚构。Deep Agents 的能力与默认项以其 Python 官方文档为准：文件系统与子任务隔离属于该 harness 的核心，规划、技能、沙箱等能力可能需要按版本和配置启用；本文不把所有可选能力说成开箱即有。

## 同一个工具循环，为何长任务会更容易走丢

LangChain 官方[Deep Agents 概览](https://docs.langchain.com/oss/python/deepagents/overview)说它仍基于模型调用工具的循环，建立在 LangChain 组件上，并使用 LangGraph 运行时；它预装文件系统、上下文卸载与子任务隔离等适合长任务的 harness 能力。小陈对领导说：“模型还是那个会读提示、选工具、看结果再决定的模型。不同的是它旁边多了工位：放资料的文件系统、整理长对话的压缩、让专项工作在单独上下文完成的子 Agent。”如果只是把一个更长的模型窗口换上去，不会自动决定哪些材料该保留，也不会让三千份文件都变得同样重要。

这张 issue 要修“退款计算在多币种订单上出现舍入误差”，同时要求不能改变历史订单的对账口径。Agent 开始时只需要读 issue、仓库入口说明、相关测试与搜索到的计算函数；打开全仓三千文件会让错误线索、旧日志和生成文件一起占位置。工具输出可能很长：一次测试跑出两万行，真正的失败堆栈只有二十行。若全部塞进主会话，模型后续回答会受大量低价值文本干扰，甚至被迫压缩时丢掉业务限制。文件系统允许把原始日志存成工件，主会话只留“哪个测试失败、日志在哪、下一步看什么”。

**领导：**它压缩后会不会把关键限制也忘了？

**小陈：**可能，所以关键约束不能只寄希望于一次自动摘要。issue 中“不改变历史订单口径”要落在任务卡或持久笔记里，指向原始需求；压缩前后都跑一条检查，问主 Agent 还能否说清目标、禁止改动、当前证据和未完成步骤。模型摘要是工作记忆，不是原始合同。仓库中的测试、代码和 issue 仍是核对依据，摘要错了要回源，不应因为它写得像结案报告就当完成。

## 虚拟文件系统不等于已经给了真实电脑所有权限

Deep Agents 文档描述了可插拔的虚拟文件系统后端：可以存在运行 state、本地磁盘、LangGraph store、沙箱或组合后端，文件工具包含列目录、读取、写入、编辑、glob、grep 等。小陈把“文件在哪里”画给领导看：状态后端的文件可能跟着 thread 的检查点存在；本地磁盘后端落在指定工作区；store 可跨 thread 保存；沙箱后端提供隔离环境，<code>execute</code> 类命令工具也依赖相应沙箱。选不同后端，重启后是否还在、谁能访问、能否运行命令都不同。不能一听“Deep Agents 有文件系统”，就以为它天然拿到了生产机的根目录。

**领导：**既然有子 Agent，给三千个文件一人一份，让他们并行查。

**小陈：**子任务也需要边界。可以派一个查舍入函数与调用者，一个查现有测试和历史兼容要求；让三千个子任务分别读一个文件，会产生大量不相关结果、成本和整合冲突。Deep Agents 的[子 Agent 文档](https://docs.langchain.com/oss/python/deepagents/subagents)说明它们有隔离上下文，主 Agent 通过委派工具接收结果。隔离是为了让深挖时的长输出不倒灌主会话，不是让子任务自动变得有权改所有文件。任务描述应写目标、范围、允许工具、交付物和停止条件；子任务回来只报关键发现、证据路径和未确认处，不把自己的全部聊天记录复制上来。

小陈给两项子任务交付格式：一是“舍入路径：入口函数 → 汇率换算 → 最小货币单位转换 → 旧订单兼容分支”，附文件位置与测试名；二是“风险清单：哪些订单类型会用旧口径、哪些测试锁住它、改动会影响的账本”。主 Agent 汇总后决定先写失败测试再改代码。若两项调查意见矛盾，回到代码和测试核对；不能因为子 Agent 都说“我查过了”，就像两位实习生互相盖章一样直接合并。子任务结果是线索和证据索引，最终验证仍在主任务的测试与代码审查。

## “小本本”怎么写，才不会变成第二个垃圾桶

小陈没有让 Agent 写一本无限增长的流水账。他把任务工件分成四页：<code>goal.md</code> 写目标、非目标和禁止事项；<code>evidence.md</code> 写关键文件位置与观察；<code>plan.md</code> 写已完成、当前、待办与阻塞；<code>results.md</code> 写测试命令、退出码和最终改动。原始两万行日志另存 <code>logs/test-run-03.txt</code>，在 evidence 里只链接失败段落。这样重启时先读四页就能接棒，需要时再展开原日志；若把每次工具输出原封不动贴进计划页，文件系统只是把上下文垃圾搬了个位置。

**领导：**文件写在虚拟系统里，服务一重启真的还在？

**小陈：**取决于后端和持久化配置。状态后端要看 graph checkpoint 是否耐重启，内存实现重启会丢；本地盘要看工作区是否保留；跨 thread 资料可能要 store；沙箱可能有生命周期。Deep Agents 提供后端选择，不替公司自动决定保留期和权限。试点要做一次真重启：先保存日志和计划，杀进程，再用同一任务 ID 恢复，确认四页与原始日志能按权限读到；若只能在同一进程内找回，就不能写“支持断点续跑”。选择后端是可靠性和数据治理问题，不是一行参数的装饰。

小陈还让文件带来源指纹。<code>evidence.md</code> 若写“函数在 src/money.py 第 86 行”，下次提交后行号可能移动；保留文件路径、提交 SHA 和相关测试，恢复时先比版本。若工作区被别人改过，Agent 不能拿旧调查结果直接打补丁；先重新查看差异和当前代码。虚拟文件系统保存的是当时的观察，不自动让旧观察变成当前事实。它像一本靠谱小本本，最好还记“这条消息是哪天、看哪版代码得出的”。

## 自动压缩和卸载，分别丢掉了什么、留下了什么

长任务里主会话的消息会增长，Deep Agents 文档描述了历史摘要与大工具结果卸载。摘要把此前讨论压成较短的继续工作上下文，卸载则把大结果放到文件，让主会话保留引用路径。两者目的不同：摘要是“这段对话走到哪了”，卸载是“原始材料还在别处可打开”。如果只摘要不保原文，遇到争议无法复核；只存原文不留任务摘要，重启又要从零读两万行。小陈要求摘要必须包含目标、禁止事项、已确认结论、未决冲突和下一步；对于金额、版本、测试退出码这类关键事实，附路径或结构化记录，避免被一句“测试大致通过”抹平。

**领导：**模型会自动决定什么时候压缩，你还要管什么？

**小陈：**自动触发是方便，验收仍要看任务是否保持连续。我们在压缩前注入一个长日志，让主 Agent 的上下文接近限制；压缩后继续让它处理“历史订单不能改口径”的要求，看它是否仍能准确定位禁止修改的分支。若忘了，就在持久任务卡补硬约束，并调整摘要或上下文装配，不是怪模型“记性不好”。对工具结果卸载也做测试：主会话要能找到日志文件、读到关键段落；若后端重启后路径失效，所谓卸载等于把证据扔进了看似有门牌号的黑洞。

## 任务完成要看仓库和测试，不看小本本写得多满

小陈给领导看了压缩前后的一张“信息水位图”。压缩前，主会话里堆着 issue、三千个文件名、两万行测试日志与两轮子任务聊天；压缩后，主会话只保目标、禁改口径、当前决策和证据路径。大日志没有消失，转存到工件；子 Agent 的细节留在自己的上下文，主会话收一个能回查的结论。若压缩后连“为什么不能改旧订单口径”都说不出，这次上下文整理就是失败；若只把日志路径留住，却没有记录是哪个测试失败，也需要补结构化摘要。图上水位下降不是省 token 的表演，是让后续决策仍能抓住关键约束。

**领导：**小本本写在文件里，模型会不会想改就改，把“不能改”那句删了？

**小陈：**不能把安全或业务底线只放在 Agent 自己可写的一页里。仓库入口说明、issue 验收条件和支付账本规则应由人或受信系统维护，Agent 的 plan 只能记录自己理解的执行步骤。文件系统权限可以限制它读写哪些路径，关键规则文件设只读；即便模型生成一份 <code>goal.md</code>，执行与评测仍以原始 issue 和测试为准。Deep Agents 的文件权限能力管内建文件工具的读写范围，但若给了能运行任意命令的沙箱，权限边界还得由沙箱和底层系统控制，官方文档也区分了这些层。把“模型不能编辑规则”写进提示词，不如从工具与工作区权限上真正禁止。

小陈让每个工件有负责人和生命周期。临时测试日志在任务结束后按制度清理，已批准的设计决定进入仓库文档，个人偏好或长期记忆不应吞进客户合同原文。Deep Agents 可以配不同存储后端，但保存到跨 thread store 的资料可能在后续任务再次出现；若里面有旧政策或客户隐私，就要有版本、权限、保留期和撤销路径。长任务“记得多”不等于“记得对”，更不等于“有权跨项目记”。虚拟文件系统只是容器，治理规则仍要由团队制定。

**领导：**子 Agent 各查一块，主 Agent 会不会因此看不到他们犯过的错？

**小陈：**会，如果只收一句“已完成”。子任务交付要有证据路径、工具退出码、未覆盖范围和失败记录。主任务不需要看它每次无关的搜索尝试，却必须知道“测试命令超时”“某目录无权限”“只查了新版本”。隔离的目标是减少噪声，不是隔绝审计。跟踪系统可留子任务的运行轨迹供排障，主会话拿紧凑摘要；若摘要与轨迹不一致，以工具结果和原始文件为准。每个子任务还要有超时与费用上限，防止主任务表面没被日志淹没，账单却被子任务在背后烧穿。

小陈特意注入一条“子任务结果很自信但证据过期”的故障：子 Agent 说旧订单分支不会走新函数，引用的却是昨天的提交；今天早上有人把入口重构了。主 Agent 收到摘要后检查提交 SHA，发现与当前工作区不符，就重新读相关文件、标该结论失效。若只看子任务说“已确认”，这个错误会在最终 PR 中隐身。子 Agent 的上下文隔离提升长任务可管理性，但版本一致性和证据新鲜度仍要显式处理。它像请了一个帮手，不等于所有帮手的笔记天然符合今天的现场。

## “规划”也有版本差异，不能把宣传图当默认配置

官方概览把任务规划、技能等列为可选扩展能力，同时把文件系统、子任务和上下文管理作为核心。小陈在试点配置页逐项写“已启用／未启用”：是否加载技能、是否启用规划工具、后端是什么、是否有沙箱命令执行、子 Agent 有哪些工具、是否配置长时记忆。这样一来，领导看演示时问“它为什么没有自动列任务计划”，团队能回答“本试点没启用该扩展”，而不是临时编一段“模型可能觉得不需要”。产品名不等于具体运行配置；同一个 Deep Agents 项目换后端或权限，行为边界会明显不同。

**领导：**把所有功能都打开，不就最强？

**小陈：**功能越多，工具面、上下文和维护责任也越多。这张 issue 要查代码、跑测试、留工件；若只需只读排障，没必要给编辑文件和执行命令。若要自动改代码，提供隔离工作区、测试命令和明确可写路径；若需要子任务，限定它们的工具和交付。启用前先列本题的失败点，启用后看是否改善：文件系统解决长日志去向，子任务解决专项调查对主会话的干扰，压缩解决长时间连续工作。不要让功能清单倒过来决定任务，把三千文件和八十工具全打开，只因为演示界面看着热闹。

小陈把恢复演练拆成三个断点。第一处在日志写入前杀进程，恢复时应明确“测试结果未知”，重新跑或查测试系统回执；第二处在日志已写、摘要未更新时杀进程，恢复器读工件与退出码补摘要，不再假装测试未发生；第三处在子 Agent 已完成、主会话未收到结果时断开，先查子任务状态与工件，避免又派一份完全相同的调查。每个断点记录工具调用 ID、工件路径和当前仓库版本。它们考的是信息能否接棒，不是模型能否在重启后凭语气继续闲聊。

**领导：**如果这些文件都能恢复，为什么还要 checkpoint？

**小陈：**文件保任务工件，checkpoint 保运行状态；两者互补。恢复时要知道图或 Agent 走到了哪一轮、哪次工具调用结果已入上下文、哪个子任务正在跑；只看目录里的 <code>plan.md</code> 无法证明任务是否已提交 PR 或测试是否已经调用。反过来，只恢复对话状态却找不到日志和工作区，也没法核对主张。Deep Agents 借助 LangGraph 运行时支撑持久化与中断，但具体是否耐重启要看配置的 checkpointer 与后端。小陈的验收不是“文件存在”一条，而是“状态、工件、仓库版本和工具回执能对得上”。

最后他还算一笔信息账：同样修一张 issue，方案甲每轮都把整份日志送回主会话，方案乙把原日志留文件只送摘要；比较的不只 token，还有最终修复是否通过测试、引用的代码是否同一版本、恢复后是否需要重复搜索。若乙省了输入却让主 Agent 看不到关键堆栈，算失败；若甲读得全但两小时后忘了非目标，也算失败。Deep Agents 不是“压缩越狠越好”，而是让重要事实始终可用、次要原文随时可查。用户要的是修好舍入问题，不是看 Agent 把上下文管理术语背得多熟。

小陈给最终 PR 加了一张接棒卡：目标 issue 链接、禁止修改的历史口径、代码提交号、测试命令及退出码、仍需人工确认的币种边界、工件存储位置。换班同事打开卡片，不需要重读子 Agent 的全部对话就能继续审查；若卡片说“全测通过”，却缺测试回执，审查人马上能发现。长任务的终点不是模型说“我记得”，而是任何获授权的人能凭同一组证据接着做。领导拿着卡片问“这回换人还要重新读三千文件吗”，小陈说：“不用，先看这四页；有争议再回原件。”

若小本本里记录的测试命令在新环境已不存在，接棒人也不能照着旧结论说“验证完成”。他应先检查依赖、工作区版本和命令退出码，把环境差异记成新的阻塞项，再决定重跑或转交。可恢复是有线索继续调查，不是把昨天的绿色结果无条件复制到今天。

小陈让 Agent 给多币种舍入错误写一条能复现的失败测试，再改最小代码路径，跑相关单测与旧订单回归，记录命令、退出码、改动文件和对账口径。子 Agent 负责查，主 Agent 负责合并与验证；文件工件用于恢复和审计。若子任务超时，主会话只拿到“调查未完成”，不能把已查到半条调用链写成完整结论。若日志存储失败，先停在测试结果未知，不能凭模型说“测试应该过了”提交 PR。Deep Agents 帮忙管长任务的信息水位，不会自动把未跑的测试变成通过。

**领导：**和普通 Agent 比，Deep Agents 到底多了什么？

**小陈：**同一个模型工具循环旁边，多了可配置的文件工位、上下文压缩与卸载、子任务隔离等常用长任务能力；某些规划、技能、沙箱和长期记忆要按实际配置区分。我们用同一张 issue 比：普通 Agent 若把所有日志留在消息里，很快挤走关键约束；Deep Agents 把原始日志存工件，主会话保目标和证据路径，子任务单独深挖再返回摘要。优势要以任务完成率、上下文占用、可恢复性、工具费用与测试证据回放，不用“名字里有 Deep”来判。领导看到最后的测试记录和可恢复笔记，终于同意先别让它背三千文件：“给它一张仓库地图，至少别让它进门先吞仓库。”
