**领导：**服务器半夜重启，研发 Agent 一恢复，给同一张 issue 开了三张 PR。它是觉得三张比较有诚意？

**小陈：**第一张 PR 其实创建成功了，但响应在网络里丢了；第二次它只看聊天摘要，写着“准备创建 PR”，就又按了一次；第三次人工点“重试”时，任务系统连上一次创建的回执都没查。三张 PR 改的代码差不多，评审人以为在玩找不同。

**领导：**那创建失败就别重试。

**小陈：**也不行。真正失败时任务会卡住。关键是把“我没收到成功响应”和“远端一定没创建”分开，重启先对账，再决定继续还是停。今天我们给 Agent 建三本账：对话交接、运行检查点、外部动作台账。

文中的 issue、PR 编号和故障时序为教学虚构；GitHub API 与持久执行产品能力以文中官方资料为准。

## 三本账分别回答三个问题

小陈让领导把三张 PR 的时间线画出来。23:58，Agent 完成 diff 和测试；23:59，Harness 在本地记下“即将创建 PR”，向 GitHub 发送创建请求；00:00，GitHub 创建了 PR #71，但网络响应超时；00:01，服务器重启。重启后，聊天摘要只保留“下一步：创建 PR”。它没有记远端是否成功，也没有可靠保存请求标识。凌晨的新进程看见“下一步”就执行，于是出现 PR #72。人工早上再点一次重试，PR #73 来了。

**领导：**会话摘要不是已经记录到哪一步了吗？

**小陈：**它记录的是模型对事情的理解，不能当外部世界的收据。运行检查点记录 Harness 在哪个步骤、有哪些输入输出；外部动作台账记录每次创建 PR 的意图、请求、结果和远端对象。聊天摘要适合告诉下一轮“我们为什么走到这里”；检查点适合让运行过程接着走；动作台账适合回答“那张 PR 到底有没有被创建”。如果把三种信息塞成一句“准备交付”，恢复时必然猜。

LangGraph 的[持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)区分线程状态的检查点与跨线程保存的应用数据；它还提醒内存检查点进程重启就会丢。Temporal 的[任务与重试说明](https://docs.temporal.io/tasks)把逻辑上的活动执行与一次次尝试区分开。小陈借这些机制理解“运行可恢复”，但不会因此宣称 GitHub 创建 PR 具有自动的“恰好一次”保证。外部 API 已经发生了什么，仍要由业务侧识别、记录和对账。

## 给动作一个稳定身份，而不是给每次重试换名字

小陈定义任务键 <code>repo-A/issue-318/fix-captcha</code>，再为创建 PR 定义动作键 <code>task-key/create-pr/v1</code>。同一逻辑交付的重试、进程恢复和人工重放，都必须使用同一动作键；代码变更版本、目标仓库、源分支和目标分支作为动作参数另存。若参数变了，比如 PR 原本针对 <code>main</code>，现在要改到维护分支，不能偷偷沿用旧动作键表示同一件事，要先走变更审批和关联处理。

**领导：**GitHub 创建 PR 的接口有个“动作键”参数吗？

**小陈：**不能假设有。GitHub 的[Pull Requests REST API](https://docs.github.com/en/rest/pulls/pulls)提供创建、列出、查看等接口，列出时可以按 head、base 和状态筛选；我们的动作键是自己系统的约束，要写入动作台账，并在 PR 描述中放可检索标记。它不能凭空让远端支持幂等。创建前在本地锁住同一动作键，先查是否已有远端 PR；创建后保存 PR 编号和 URL；若响应未知，再用受限查询对账。标题相同不是足够证据，仓库、源分支、目标分支、issue 映射和任务标记要一并核对。

本地动作记录有 <code>planned</code>、<code>sent</code>、<code>confirmed</code>、<code>unknown</code>、<code>failed</code> 等状态。发出请求前持久化意图，避免重启后完全不知道曾准备做这件事；收到成功响应后记录远端 PR ID；超时则标 <code>unknown</code>，不写 <code>failed</code>。若网络断开时进程根本没发出请求，也要靠实际事件判断，不能把“没看到 PR URL”反推“没创建”。这些状态不是给模型看的花哨仪表，而是重试器每一步的决策依据。

动作键的生成规则要稳定，但不能过于粗糙。只用 issue 编号会误伤同一 issue 的第二个合法修复，例如先修验证码乱序，后来另开 PR 修监控；只用时间戳则每次恢复都会变成新动作，去重失效。小陈让交付单先定义“逻辑交付单元”：仓库、issue、工作块、交付轮次；创建 PR 的动作键从它派生。工作块确需第二轮 PR 时，由负责人明确开启新交付轮次，并关联旧 PR 的状态。这样“新需求”与“旧动作重试”有可审的分界，不由 Agent 临时换名字绕过去。

源分支也要稳定。第一次创建用 <code>agent/issue-318-fix-captcha</code>，恢复时若自动生成 <code>agent/issue-318-fix-captcha-2</code>，GitHub 查询第一条 head 当然找不到，随后第二张 PR 就被创建了。分支名不必承担全部唯一性，但应由任务键确定并保存在台账，恢复必须先找原分支。若原分支已被删除或改写，不能简单“重建同名分支再发一次”；先查旧 PR 是否已合并、关闭或被人修改，确认当前交付版本是否还对应原任务。远端对象的生命周期比本地会话长，不能按会话重启来重置。

**领导：**那 PR 描述里加一串标记，搜索到就是同一个？

**小陈：**标记是辅助线索，不是身份证。描述可能被人编辑，搜索可能延迟，权限可能看不到私有 PR；反过来，同事复制模板也可能复制标记。优先用仓库、head、base、提交 SHA 和动作台账里的远端 ID 建立对应；描述标记用于排查和人工确认。查到两个候选时，不按“最新的那个”自动选。必须比对代码差异、创建人和状态，再决定保留哪个。自动化能处理清晰事实，模棱两可的合并要留下人工裁决入口。

**领导：**查不到 PR 就再建，这总可以吧？

**小陈：**先看查询是否可靠。凭据权限不足时，私有仓库对象可能查不到；搜索索引也可能有延迟。优先用官方列表接口按仓库、head、base 查，再按任务标记与提交核对；若 API 返回限流或服务故障，查询结论是“未知”，不是“不存在”。只有查询成功且覆盖目标范围，才可进入下一步。结果仍不确定就停下交人，别用一次空列表换来第四张 PR。

## 四个崩溃点，恢复动作完全不同

小陈把创建 PR 拆成四个可能被电源打断的位置。第一，意图尚未持久化，系统不能凭聊天记录继续；需重新核对工作区、测试与任务状态，再产生新意图。第二，意图已持久化、请求尚未发送，可以按同一动作键执行一次，但仍要考虑进程是否真的停在发送前。第三，请求已发出、没有回执，这是最危险的未知窗口，必须查远端。第四，回执收到但本地确认记录还没写稳，远端已知存在；恢复时通过查询把 PR ID 补入台账，不需要新建。

**领导：**第二种为什么还说“不确定”？日志写着未发送啊。

**小陈：**因为日志与网络动作之间也有缝。若程序先发请求再写“已发送”，崩溃时日志仍写未发送；若先写“已发送”再发请求，崩溃时可能根本没发。单靠一个布尔字段无法原子地覆盖两个系统。我们用“意图先持久化、动作键稳定、远端可查询、未知先对账”的组合缩小歧义。若远端 API 自身支持幂等键可以利用，但没查官方契约前不能假设。真正难的是跨系统的原子性，不是给错误码起个好听名字。

不同外部动作的对账方式也不同。创建 PR 有源分支和目标分支可查；发送邮件可能有消息 ID 和收件人时间窗；部署有发布单号和版本；更新 issue 标签可读当前标签集合。设计工具时就要同时设计“做了之后怎么查”。若某接口只有写没有读，且也不接受幂等键，超时后自动重试通常很危险。小陈宁愿把它放到人工待核实队列，也不让 Agent 以“努力完成”为由重复产生副作用。

## 三本账怎样对齐：以同一任务键穿针引线

**领导：**别只讲概念，三本账具体怎么连？

**小陈：**会话交接单里只写“当前块已验证，下一步核对创建 PR 的动作键 A-318-1”；运行检查点记录“交付阶段，当前节点 create_or_reconcile_pr，输入工作区提交 abc123”；动作台账记录“动作键 A-318-1，目标 repo-A，head 分支 agent/issue-318-fix-captcha，base main，状态 unknown，远端 PR ID 未确认”。三个地方用同一任务键与动作键关联，但各写自己负责的事实。摘要不复制整份台账，检查点也不冒充远端回执。

恢复程序先验证这个动作仍应发生：issue 未取消、工作块测试仍绑定当前提交、交付权限未撤销。若这些前提变了，哪怕台账写着 planned，也不能继续创建。然后读取动作状态；confirmed 需要核对远端对象与记录一致，unknown 需要远端查证，failed 则看是否是明确拒绝、参数错误还是短暂故障。只有在前提仍有效、远端确认无对象、并发租约拿到手后，才进入创建。决策顺序很关键：先判断该不该做，再判断做过没有，最后才问能不能再试。

台账的记录方式也要能追到每次尝试。逻辑动作只有一个，但尝试事件可以有多条：第一次 23:59 发出后超时，第二次 00:10 查询命中 #71，人工 09:00 核实提交匹配并补账。不要用第二次结果覆盖第一次，让事故从历史里消失。事件里记录时间、执行者、请求摘要、响应类别、远端对象与证据引用；敏感令牌不写入。领导以后问“为什么系统停了八小时”，可以看到是远端查询权限错误还是人工核对等待，而不是一条模糊的“任务处理中”。

**领导：**动作台账和检查点放一个数据库，写起来方便吧？

**小陈：**可以共库，但逻辑边界别混。检查点可能按运行步骤频繁更新，保留期也许较短；动作台账涉及外部副作用，通常要跟业务审计期走。若把台账仅放在进程内存，重启就没了；若两份记录分开写却没有关联键，也无法复盘。共库可以用事务保证“动作意图”和本地状态一起落盘，但无法把远端 GitHub 的创建操作也装进这个本地事务。跨系统那条缝仍须查询、去重和人工处理未知结果。

## 检查点能续跑，但不能代替第三本账

领导提议“给 LangGraph 加 checkpointer 就行”。小陈拿图解释：检查点能恢复图的状态，但在节点里调用 GitHub 创建 PR 时，可能恰好在 GitHub 成功、下一个检查点尚未写入之间崩溃。恢复时该节点重跑，如果节点内部直接重新 POST，就还是重复 PR。LangGraph 文档说明检查点是线程状态快照；把副作用的对账写进节点逻辑，或拆成可恢复任务，才算解决外部不一致。产品给的是持久执行基础，业务上的 PR 唯一性要自己定义。

**领导：**Temporal 不是号称能可靠重试吗？

**小陈：**可靠重试也不是保证外部系统只被调用一次。Temporal 文档把一个 Activity 的逻辑执行与多个尝试分开，说明失败可重新安排尝试。PR 创建这类有外部副作用的 Activity，仍要考虑重试前查询或远端幂等。我们可以让工作流保存动作键和阶段，让 Activity 根据台账对账；不能因为用了工作流产品，就把“超时等于失败”写进业务逻辑。换框架不会改变 GitHub 与本地存储之间的网络事实。

小陈还指出，本地检查点也可能使用内存后端做原型。进程一重启，状态全没；此时“我们有 checkpointer”在生产上没有意义。持久后端要有备份、访问控制和恢复演练；检查点 schema 变化时还要保证旧任务能解释。第三本账可与检查点存于同一可靠存储，但逻辑上仍需分离：前者描述外部动作的唯一性，后者描述运行进度。若同一数据库一起挂了，还要从远端 PR 与工作区反向对账，不能只看会话摘要。

## 两个恢复进程同时醒来，也只能有一个动手

服务器重启后可能有两个 Worker 都领取同一个任务：一个自动恢复，一个是领导点的“立即重试”。如果它们各自查一遍“没有 PR”，再同时发创建请求，查询本身也救不了。小陈在动作键上加并发控制：同一键只有一个执行者拿到有时限的租约；拿不到的只观察状态。执行者每次写动作记录检查版本号，租约失效后不能继续确认旧结果。即便数据库租约防住本地竞争，远端仍要靠查询与唯一性核查，双层保护才稳。

**领导：**万一 Worker 拿到租约后卡住，任务就永远挂着？

**小陈：**租约有到期和续约，超时后新 Worker 可以接手；接手者不能把旧执行者的未知动作当未发生。它先读取动作台账，若有 <code>sent</code> 或 <code>unknown</code> 就查远端，再决定。旧 Worker 若醒来，写入时发现租约版本已变，停止确认与下一步操作。这样解决“谁能行动”和“行动过没有”两件事。只有锁没有对账，锁到期那一刻仍可能重复；只有对账没有锁，同时查询也可能竞态。

异常状态不能被自动清扫脚本当垃圾删掉。<code>unknown</code> 表示我们欠一笔远端核查债，必须有告警、负责人和处理时限。处理人核对 PR #71 确属该任务，就把台账补成 <code>confirmed</code>，关联 issue，并关闭重复 PR #72、#73；若发现 PR 内容不同，不能按标题相似随手关掉。清理事故也需要审计：谁确认、根据哪些远端字段、哪些重复对象被关闭，避免把合法的另一项工作误删。

## 不能只防重复，还要防“旧任务把新 PR 认走”

小陈模拟另一种事故：同一 issue 的 PR #71 被评审退回后，同事在源分支追加了提交；Agent 的旧检查点恢复，看见 head、base 都匹配，就把 #71 当作自己昨晚的交付，宣布“测试已通过”。可昨晚测试绑定的是提交 A，现在 PR head 是提交 B。对账时必须比对当前 PR 提交与工作块验证版本；若不同，动作可以确认“PR 已存在”，但交付状态应退回待验证。防重复解决对象唯一性，不解决对象内容随时间变化的问题。

类似地，PR 已经合并或关闭时不能机械复用。已合并意味着这轮动作可能完成，但要核对合并提交和 issue 去向；已关闭且未合并要看关闭原因，是被拒绝、被替代，还是误操作。若被新 PR 替代，应把替代关系写入台账，而非又开一张。若任务取消后旧 Worker 恢复，哪怕找不到 PR，也必须停在取消状态，不能因为“技术上可以创建”就继续对外产生东西。外部对象与任务意图都在变化，恢复必须同时看两边。

对人工修复也要保持同一原则。值班同事可能在系统故障时手动创建 PR，把地址贴进 issue；Agent 恢复时如果只查自己创建的对象，会误以为没有交付。交接规范要求人工动作登记任务键和 PR 回执；如果没登记，恢复程序的远端查询仍要覆盖可能的人工分支，并把多候选交给人判定。人不是自动化之外的“例外世界”，人在故障时的补救恰恰最容易与自动恢复撞车。

## 演练要在最坏的那一毫秒拔电

小陈准备四轮故障注入：持久化意图前断、发送请求后断、远端创建成功但响应丢失、回执收到但本地确认前断。每轮恢复时检查同一动作键的记录、远端 PR 列表、工作区提交和测试证据。验收不是“流程最终能走完”，而是“任何位置断电后，同一逻辑交付至多有一张有效 PR；若事实不明，任务明确停在待核实，绝不假装完成”。PR 已存在但测试证据过期时，也不能只补账就合并，后续交付门照常执行。

**领导：**故障演练要真的往 GitHub 开 PR 吗？

**小陈：**先用可控测试仓库和模拟 API 注入时序，验证台账与状态机；最后在测试仓库做端到端演练，确认官方列表接口、权限和实际延迟与模拟一致。测试时给 PR 明显的演练标记，结束后按规则关闭。生产环境只收通过的恢复策略和监控。仅用单元测试 mock 出“创建返回 201”，测不到最危险的“创建成功、响应丢失”。

小陈给领导看处理后的账：issue #318 对应动作键固定；PR #71 是真正交付对象，#72 和 #73 被确认重复后关闭，原因与时间留档；工具调用轨迹保留三次尝试及各自状态。下次恢复时系统读到 <code>confirmed:#71</code>，先核对远端仍存在，继续评审流程，而不是重新创建。领导终于不再问“重试按钮在哪里”，改问“这个动作有没有可查的收据”。这次问题才算问对了。

复盘时还要看重复 PR 已经造成的下游影响：评审意见是否分散在 #72、#73，CI 是否白跑了两轮，issue 是否被错误链接到被关闭的那张，通知是否给同事发了三次。关闭重复对象只是止血，真正修复要把有价值的评论迁移或链接到 #71，并让任务看板只指向唯一有效交付。若自动关 PR 的脚本在错误对象上执行，事故会从“重复”变成“丢失评审”。小陈让系统先列出候选和关联，再由负责人确认清理，这一步也进入动作台账。

下周演练时，领导亲自按了两次重试。面板没有多出 PR，只显示“动作 A-318-1 已确认：PR #71；第二次请求复用原结果”。这才是他要的“可以放心点”：按钮可以重复按，外部结果仍有确定归属；若远端状态不可查，面板清楚写“待核实”，不拿沉默冒充成功。

小陈顺手把同样的验收用例复用到“发通知”和“触发部署”工具：每个动作都要能说清唯一业务键、查询渠道、结果未知时的停点和人工对账人。若这些字段答不出来，就先不要把工具接进可自动重试的运行链。
