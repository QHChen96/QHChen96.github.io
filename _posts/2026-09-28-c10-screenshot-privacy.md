**领导：**这张截图已经把客户姓名涂黑了，可以交给 Agent 看了吧？

**小陈：**右下角的收货地址还在，通知栏露出手机号，图片文件名里还有订单号。打码不是给姓名戴墨镜，其他人就认不出来了。

**领导：**那我让客服多涂两笔。原图留日志里，万一出错方便查。

**小陈：**原图留日志，等于从一个入口搬到另一个入口。我把这张图走的路画出来：上传服务存一份，识别文字时传一份，模型请求带一份，应用日志可能记一份，故障监控还可能留一份。先确认每站拿到了什么，再谈“能不能给 AI 看”。[OWASP 的日志指南](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#data-to-exclude)也明确建议对日志里的个人信息做移除、遮盖或其他保护处理。

**领导：**说人话，今天怎么改？

**小陈：**这单只需要判断“破损照片是否足以转人工”，不需要地址。上传后先在受控环境裁剪商品区域，识别结果只保留破损描述和工单 ID；若必须核对订单，由订单工具返回“本单匹配／不匹配”，不把整张订单或完整地址塞给模型。原图只在客服系统按既有权限访问；模型请求、轨迹和异常日志只记工单关联 ID、处理阶段与错误码。

**领导：**保留多久？客服想复盘怎么办？

**小陈：**把规则写进字段清单，不能靠“以后再删”：

| 位置 | 允许保存 | 谁能看 | 到期动作 |
| --- | --- | --- | --- |
| 客服原始附件 | 必要的原图与工单关联 | 处理该单的授权客服 | 按公司已批准的工单留存期删除或归档 |
| 送模型的材料 | 裁剪图或去标识化文字、临时请求 ID | 调用服务 | 请求完成后不进应用持久日志；供应商留存设置单独核验 |
| 运行日志 | 阶段、耗时、错误码、脱敏关联 ID | 运维与审计角色 | 按日志策略自动清理 |

**领导：**那验收别只看你画的图。

**小陈：**拿同一张带“假手机号、假地址”的测试图，逐站抓取输入、模型请求、输出、正常日志和报错日志；不该出现的字段一处也不能有。再用客服账号和普通运维账号分别试读原图，检验权限。删单后抽查附件及其派生副本是否按清理规则处理。任何一站没过，这条通道先不上线。

## 一张截图到底经过几站，先把账盘明白

**领导：**你说的五站，上传、识别、模型、日志、监控，能不能给我看一个真的路径？

**小陈：**拿虚构的破损件工单 0823 走一遍。客户在 App 上传截图，App 先向上传服务取临时凭证，文件进对象存储；客服系统给它挂上工单 ID。图片识别服务把图里的文字提出来，可能识别到通知栏手机号和快递面单；业务服务把识别结果拼进给模型的请求，模型生成“转人工或补拍”的建议；调用网关把耗时、错误和请求 ID 打进监控。若某一步失败，异常处理还可能把完整请求体当错误详情打印出来。一个“客服已打码”的前端视图，不能证明后端这些副本都被打码。

我们要画的是**数据流图**，每条边写清楚：谁把什么字段发给谁，为什么发，落不落盘，保留多久，谁有权限看，怎么删。比如上传服务确实需要文件字节；模型判断“破损照片是否可初步受理”，只需要商品破损区域与工单上下文，不需要完整面单。OCR 若只是为了识别破损说明，就不应默认把整张图的所有文字返给模型。把所有可见内容一股脑送过去，再靠提示词说“请忽略手机号”，不是最小化输入。

**领导：**图里不止文字，角落可能拍到门牌，靠 OCR 能查出来？

**小陈：**不能。敏感信息检测至少有两条线：文字识别找手机号、地址、订单号、姓名；图像检测找面单、证件、门牌、屏幕通知、二维码。机器检测会漏，所以对于暂时无法保证裁剪准确的场景，可以直接让客户在受控页面补拍商品局部，或者由授权客服先审图，Agent 只读客服给出的结构化结论。不能用“打码模型准确率 98%”直接推出“剩下 2% 可以进入外部模型”。真实流程要给失败和不确定结果一个退路。

小陈把工单字段分为四类：判断本题必需的商品破损信息；案件关联所需的工单 ID；需要受控查询但不应暴露给模型的订单归属；与本题无关的手机号、完整地址、聊天通知等。分类不是按字段名字永久贴标签，而是按当前任务。处理“寄回取件”时地址可能必要，处理“照片能否转人工”时就没必要。每次扩大任务范围，都要重新检查最小字段清单，不能沿用上一个功能的“大包请求”。

## 打码、裁剪、去标识，听着相近，效果不同

**领导：**我让客服把姓名、电话、地址都涂黑，总够了吧？

**小陈：**先问涂黑发生在什么时候。若原图先上传到通用存储，再由服务打码，那么原图已经存在了一份；若原图又被送到监控做故障截图，打码发生得更晚。对当前任务，优先让客户端或受控上传处理链**裁剪商品区域**，减少根本不需要进入后续链路的内容。打码是剩余材料的补充措施，不等于裁剪。再对 OCR 文本做字段级过滤，不能只改图片、留下识别出的明文。

黑色矩形也不一定可靠：编辑器可能把遮盖画成可移除图层；缩略图或原始附件可能仍可访问；图片的文件名、元数据和二维码可能暴露订单信息。发布前把处理后文件重新导出为不可恢复遮盖的普通图像，检查是否还有原始图层或可访问的原图链接。对于模型根本不需要的字段，更简单的办法是**不传**，比“传过去再告诉它保密”稳得多。

**领导：**那工单 ID 也能识别客户，为什么还留？

**小陈：**工单 ID 是内部关联键，不等于匿名化。拿着它的人若有客服系统权限，仍能找到客户。所以它可以用于系统之间追踪，但日志和分析平台要控制访问，不在公开报错、客户可见页面或第三方指标标签里随意展示。需要跨系统关联时，可用单次请求 ID 或受控映射的伪标识；映射表留在内部权限域。把可重识别的数据叫“匿名数据”，会让团队误以为可以无限复制。

如果图片里是身份证、银行卡、医疗信息等明显与本题无关的高敏材料，通道应停止自动模型调用，走人工受控处理，并提示客户通过合适入口提交。别因为模型“也看得懂”就把所有材料接进同一条客服流水线。能力越强，越要明确哪些信息没有业务理由进入这次处理。

## 模型请求不进应用日志，排障还怎么做

**领导：**不记请求体，线上出错时工程师怎么查？

**小陈：**记录**足以定位流程、但不包含原文**的结构化事件。一次运行至少有请求 ID、工单的受控关联键、链路阶段、模型和提示模板版本、工具名、耗时、输入材料类别、裁剪／过滤策略版本、错误码、重试次数、权限判定结果。这样能查“是在 OCR 前失败，还是模型超时”，也能复现配置。需要看具体原图时，由有案件权限的人员通过客服原始附件系统访问并留审计，不是让所有能看运维日志的人都看到客户地址。

应用日志之外，APM、错误上报、消息队列死信、任务重试载荷、开发者调试台和备份都要逐站核对。有些 SDK 报错会带请求片段；有些代理层会在调试模式下记录完整 HTTP body；有些失败任务会把原载荷送进死信队列等人捞。安全检查不能只搜 `logger.info`。我们会在测试环境注入虚构手机号 `13800001234` 和虚构地址标记，再故意触发超时、格式错误、OCR 失败、模型拒绝、重试耗尽，搜索每个允许访问的存储与监控出口，看哪些副本出现了标记。真实客户信息不用来做这类探针。

**领导：**可不可以把完整请求加密存起来，只有出事才解？

**小陈：**加密能降低未授权读取风险，不能回答“是否有必要存”。若确实需要短期留样做争议复核，先定目的、范围、审批、期限和访问审计，再单独放在受控证据仓，不跟一般运行日志混在一起。抽样也要尽量脱敏，尽可能用可重放的合成材料替代。工程师不应因为“将来也许要调试”就无限期保留所有客户截图。OWASP 的日志建议也提醒敏感个人数据通常不应直接写入日志，需移除、遮盖、清洗、哈希或加密；选择哪一种，取决于仍要实现什么排障目标。

模型服务商的处理边界要单独核验。请求是否用于训练、是否有滥用监测日志、特定功能是否保存应用状态、可用什么留存控制，都是**供应商、端点、账户配置和合同**共同决定的，不能用“某平台默认不训练”推导出“零留存”。采购或接入时把具体端点、图片输入和工具输出逐项核对，并把配置截图或协议版本留档。模型请求体里只放当前任务必需数据，即使供应商承诺短期不保留，也仍是最稳妥的边界。

## 删除工单，不等于每张副本都跟着消失

**领导：**客服在后台点了删除，为什么你还要做删除演练？

**小陈：**因为工单主表删掉，只能证明主表没了。对象存储可能有原图和缩略图，OCR 缓存有识别文本，队列有待重试消息，监控有错误样本，备份有历史快照，模型供应商又有自己的留存规则。我们给每份材料登记**资产 ID、来源工单、存储位置、派生关系、保留规则和删除方式**。删除或到期事件触发各系统清理；无法实时删的备份要有明确生命周期与恢复后的再次清理流程。具体期限让企业按业务和适用要求确定，技术方案负责做到“规则能执行、执行能验证”。

删除失败不能只写一行“任务异常”。每个副本清理动作返回回执；暂时清不掉就进有负责人和重试计划的待办，超过时限告警。若系统重放旧队列消息，不能让已删除的截图又被重新生成缩略图；消费端应检查工单和资料状态。删除是跨系统流程，和退款一样会遇到“部分成功”，需要可观察、可补偿、可解释。

**领导：**备份不是不能随便改吗？

**小陈：**备份策略可以按企业要求保留，但要知道其范围、保留期和恢复路径。不能对客户或内部审计笼统说“已经彻底删除所有地方”，除非真有证据。对不能即时删除的备份，记录隔离、到期清理与恢复时重新执行删除清单的机制；访问仍受控。这里讲的是工程实现和承诺一致，不替企业决定法律上的期限。先把副本清单做全，法务和业务才有事实可以定政策。

## 权限和事件，比“全员注意保密”更管用

**领导：**只有客服看原图，运维只能看错误码，听着合理。可工程师排障时还是会要截图。

**小陈：**给排障设计受控入口：有工单号、问题单、审批理由和有效期，临时授权给指定人员看原图；访问记录谁在何时看了哪个文件，过期自动撤销。需要共享复现时优先生成脱敏样本或合成截图。运维日志本身保持低敏，日常值班不用碰原图。权限按职责分，不按“都是自己人”一把梭。服务账号也要限制：OCR 服务可读上传材料，但不能列出整个对象存储；Agent 调用服务只拿本次处理的临时引用，不拿永久公开 URL。

若误把原图写进日志，先阻止继续传播：关闭相关调试记录或部署修复，限制含敏日志查询，再查这批记录的时间窗、访问者和副本，按企业事件流程评估通知与处置。删除日志不能抹掉事故轨迹；可在受控审计区保留必要事件元数据，同时把含敏载荷从常规查询面移除。单纯对客服说“下次小心点”无效，因为问题可能出在错误上报 SDK 的默认配置。

**领导：**怎么证明你不是在纸上画安全？

**小陈：**做四类实测。**输入实测**：带多种虚构敏感信息的图片，检查裁剪、OCR 和模型实际请求；**异常实测**：每一站故意失败，检查异常日志、死信队列和监控；**权限实测**：客服、班长、运维、开发、无关坐席分别试读原图及派生文本；**生命周期实测**：到期或删除后查询各副本与回执，再从可恢复环境验证旧消息不会把材料复活。测试结果附实际请求样本的脱敏截图和查询语句，任何一站不通过就阻断这条新能力上线。

## 领导面试题，小陈不靠“我们很重视”答题

**领导：**第一题，打码和最小化输入有什么差别？

**小陈：**打码是在已有材料里遮盖，仍可能遗漏图层、文件名、OCR 文本或原图副本；最小化输入是从任务需求出发，不采集或不传无关字段。先减少材料，再对剩余材料做可靠遮盖。

**领导：**第二题，日志不记原文还能追事故？

**小陈：**能追流程：请求 ID、工单关联键、阶段、配置版本、工具回执、错误码和时间。确需看原始证据时通过客服受控入口按案件权限访问，留下审计，不把原文铺到通用日志平台。

**领导：**第三题，供应商说“不拿客户数据训练”，就能上传完整截图？

**小陈：**不能。训练用途、滥用监测日志、应用状态留存和不同端点的行为是不同问题；还要看账户配置和合同。无论供应商怎样承诺，这次任务不需要的地址和手机号都不该传。

**领导：**第四题，删除成功怎么验？

**小陈：**查主附件、缩略图、OCR 缓存、队列、日志样本和派生副本各自的清理回执；检查失败待办和备份恢复后的处理规则。只看工单页“已删除”是界面验收，不是全链路验收。

**领导：**第五题，识别不确定怎么办？

**小陈：**不把完整图赌给模型。让客户补拍商品局部，或让授权客服审图并给 Agent 一个受控结论。不能因为检测器漏报概率不为零，就把漏报当成客户必须承担的代价。

**领导：**行，今天不讨论“黑条涂得够不够艺术”。先把这张图走过的每扇门都关上。

## 最后用一次“假泄露”检验值班手册

**小陈：**我们拿虚构数据做一场小演练：16:00 测试图上传，16:01 OCR 返回识别结果，16:02 模型调用超时，16:03 错误上报平台出现一段原始 OCR 文本，里面有测试手机号。若值班同学只看到“模型超时”，他可能顺手重试三次，把同一段文字复制到更多日志。正确的第一步是给相关任务暂停重试并标记敏感载荷，第二步限制错误样本的访问，第三步确认同类错误从何时开始、哪些工单受影响，第四步修掉上报载荷并用假数据复测。恢复自动处理前还要检查队列里积压的旧任务，避免修复上线后继续重放含敏请求。

演练报告不需要公布客户内容，只需要讲清发生窗口、受影响系统、记录了哪些字段类别、有谁访问过、删改和隔离回执、仍待处理的副本。若发现实际客户资料进入了不该进入的系统，立刻按企业隐私与安全事件流程升级，由有权限的负责人决定通知和后续处置。工程师不能私自删一段日志、宣称“没事了”；日志删了，也许对象存储的调试快照还在，事故范围仍不清楚。

**领导：**可是这么多检查，客服会不会等半天？

**小陈：**把检查前移到上传与裁剪阶段，并给人一个快的安全分支：能确定商品局部且无敏感内容，就进入 Agent 辅助；无法确定，就进入人工队列并告知客户需要核查。不要让客户看着旋转图标等一个“不确定”。上线后量两条数据：安全分支的处理时长，和被误放行的敏感内容数量。若为了追求毫秒级速度，敏感信息持续漏进模型，速度指标就没有意义；若全部转人工，也要查是不是裁剪和检测设计得太差，而不是直接放弃体验。

最终交付给领导的是三份可以落地的东西：一张带每个副本责任人的数据流表；一套最小字段与异常日志配置；一组可重复执行的假数据探针和删除演练。客服同事拿到的是简明操作：让客户上传商品局部，系统无法判定时转授权人员核查；不要在聊天窗口要求客户把身份证、完整住址重新发一遍。把复杂度留在系统里，别推给客户“自己注意隐私”。
