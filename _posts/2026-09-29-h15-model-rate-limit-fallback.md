**领导：**模型接口 429 了。马上切另一家模型，客户别等。

**小陈：**这张客服工单刚查完订单，还没确认退款工具有没有执行；研发那边的 Agent 刚写完补丁，也没拿到测试结果。现在把半截会话直接丢给备用模型，它可能重新退款、拿旧代码报测试通过。换模型可以是降级手段，但先得知道这半张任务已经做了什么。

**领导：**客户看不到我们的纠结，只看回复慢。

**小陈：**那就把“能安全继续的”“需要等服务的”“必须人工接管的”分开，让客户得到诚实状态，而不是让备用模型用一段流畅的话盖住不确定的动作。

文中的工单、订单和故障时序均为教学虚构。平台限流规则以文内官方文档核对；具体回退策略由企业按业务风险制定。

## 429 只是状态码，不是“换一家”的发令枪

小陈先让值班同事看响应体和头。OpenAI 的[限流文档](https://developers.openai.com/api/docs/guides/rate-limits)区分请求突增导致的临时 <code>slow_down</code>、模型暂时过载等情况，可能给出 <code>Retry-After</code>；[消费限额文档](https://developers.openai.com/api/docs/guides/spend-limits)说明达到组织或项目硬消费上限也可能返回 429，错误码不同，不是睡几秒就能恢复。Anthropic 的[错误文档](https://platform.claude.com/docs/en/api/errors)同样说明 429 可能来自速率或消费上限，临时拥挤另有过载错误。小陈不把这些厂商错误码揉成一个“限流”：先看具体提供方、错误码、等待提示、配额与账单状态，再选动作。

**领导：**都是 429，客服前台不需要知道这么细。

**小陈：**前台不需要，但调度器必须知道。临时速率限制适合按服务端提示等一会儿、降低并发；月度消费上限需要账户负责人处理，自动重试只会白烧请求和延误；过载服务可能要暂停新请求或启用备用方案。若 SDK 已经自动重试两次，应用外层再重试三次，实际最多可能发出更多请求，故障时流量被成倍放大。OpenAI 文档特别提醒应用重试应计入 SDK 的行为，设总次数和总时限；Anthropic 文档也列出官方 SDK 的默认重试语义。小陈先把隐藏的重复尝试数查清，才谈切换。

限流响应中的等待时间是最小等待提示，不是让所有 Worker 在同一秒准点冲回去。小陈按任务优先级排队，遵守服务端提示并加入小幅随机抖动，控制并发恢复斜率。每张任务还有总时限：超过客户可等待的范围，就转入人工待办或异步回访，不让前台无限转圈。若消费上限或鉴权问题需要人处理，不做指数退避表演。所有决策写进事件轨迹，之后才知道客户等待时间花在哪里。

## 双层重试怎样把 429 变成自己制造的风暴

**领导：**SDK 自动重试两次，应用外层再试三次，最多五次吧？

**小陈：**要看“再试三次”是三次总调用还是三次额外循环。若外层一共调用三轮，每轮 SDK 首次请求加两次重试，最坏可到九次；若外层写的是首次加三次重试，则可能到十二次。更复杂时，Agent 自己看到失败还会再发一轮工具调用。数字只是算式示例，真实 SDK 版本和配置要查。关键是统一一张任务级重试预算，SDK、HTTP 客户端、应用与 Agent 决策都计入；不能每层都自认为“我只重试一点点”。

每次失败请求还可能消耗速率额度。OpenAI 的限流文档特别指出持续重发无效请求不会帮你跳过每分钟限制。小陈在入口用令牌桶或类似限速器控制请求和预计 token，Worker 领任务前先申请容量；拿不到就排队，不先发出去撞 429。收到 <code>slow_down</code> 时降低发放速度，服务稳定一段时间再缓慢增加；收到过载则暂停部分低优先任务。单个用户也有限额，避免一位高频调用者挤掉所有客户的容量。

**领导：**如果服务端说等 56 秒，客户 SLA 只有 30 秒呢？

**小陈：**不能 30 秒时偷偷重试。等待提示是服务端要求的最短时间，业务 SLA 不允许就走转人工、异步回访或已验证的备用方案。系统把“模型可重试”与“客户能等多久”做交集；交集为空就换业务路径。对用户的说法也要准确：“正在核对，请稍后回访”，而不是“已处理完成”。限流有时是技术问题，有时直接决定服务承诺，不能由 SDK 在后台默默睡到超时。

短暂 429 与消费上限即便都返回 429，也必须在面板上分开统计。前者看等待提示、请求速率和令牌余额；后者看项目或组织限额以及账户负责人。Anthropic 文档还提示其 429 可能来自月度消费上限，而过载可能用另一种状态码。供应商错误语义有变化时，适配层更新分类规则并回放故障测试；不能在代码里写死“所有 429 等 1 秒”。错误分类若错，备用模型会接到一堆本该先处理账单的任务。

## 切模型之前，先给任务做一次“动作体检”

小陈把受影响的任务分为三类。第一类还没产生外部动作，例如只是读取公开知识并草拟回复，且所需上下文、权限和输出格式可在备用模型上重建，可以候选切换。第二类已发起只读工具但结果未知，先查工具状态或重读，确认输入版本；第三类已发起退款、通知、PR 创建或部署这类写动作，必须先对账，不让备用模型从摘要里猜“应该还没做”。同时检查任务是否有未验证代码、未完成测试、人工审批等待和已过期的知识引用。

**领导：**备用模型只负责接着说话，又不执行退款。

**小陈：**如果它的工具权限没收窄，下一轮完全可能再次调用；即便不给工具，它也可能对客户说“退款已完成”，而原动作其实结果未知。切换前形成可读的状态包：任务目标、已确认的事实、未确认的动作、当前工作区或工单版本、允许的工具与禁令、下一步可执行操作。备用模型只能在这些边界内继续；缺少关键证据时要说“待核实”并交人，而不是生成一份完美接续的幻觉。

## 备用模型不是同一位同事戴了顶新帽子

不同模型的工具选择、上下文长度、结构化输出、提示服从和错误行为可能不同。H11 已说明模型要与 Harness 配对回放；故障时临时切换尤其不能把旧模型的长会话原样塞给新模型就宣布无缝。小陈预先准备备用方案，固定任务状态包格式、工具契约、授权策略、验收测试与回滚路径，平时用代表性任务回放。若备用方案只在演示中问过“你好”，故障时拿它接半张退款单，就是把试点变生产事故。

**领导：**那备用模型能做什么？

**小陈：**先从无副作用任务做起：总结内部资料、生成待审草稿、解释已确认测试失败。对客户外发、退款和主分支代码交付，仍走同一审批与证据门。切换不能提高任务权限，最好按当前阶段收窄工具。若服务中断时只剩一条“人工回复客户：系统处理中，稍后核实”的路径，也是有效降级；关键是别把业务真相交给一句想当然的续写。

模型切换也有成本。备用方可能需要不同的工具适配、上下文压缩格式和数据许可；同一条任务若跨提供方，敏感数据流向变化要满足公司规则。小陈在正常日演练这些约束，记录可切换的任务类别与禁止切换的类别。对于某些私有仓库或受限客户资料，如果备用模型不在允许的数据边界里，就不能因为主服务 429 而临时破例。恢复速度不能靠越权换来。

## 给备用模型的交接包，只装已核实的事实

小陈把工单状态包拆成五栏。目标：客户要查询退款进度，不是要求立即再退款；来源：订单系统查询返回当前状态与时间戳；已发生动作：退款工具动作键及回执，如果缺回执写“未知”；限制：不得再次发起退款、不得把旧政策当现行；下一步：查支付侧结果，查不到转人工。每栏附原始证据引用和访问权限。备用模型先读这个状态包，再按允许的工具去查，而不是接着原模型最后一句“我准备退款”。

**领导：**会话摘要里不是已经有这些吗？

**小陈：**摘要可能漏掉外部动作，也可能把“计划退款”写成“退款中”。状态包的客观字段由业务系统、工具执行器和动作台账填，模型只负责解释；尤其金额、账户和退款回执不能靠模型回忆。切换时给备用模型一个新的运行实例，绑定原任务键与当前工单版本，但不复制旧实例的全部工具权限。旧模型恢复后也不能同时继续写同一工单，任务租约要转移或明确取消，否则两家模型各自给客户发一条“最终答复”。

研发 Agent 的状态包略有不同：仓库与基线提交、未提交 diff、测试命令和退出码、PR 动作键、尚未验证的约束。备用模型可以继续定位代码或写待审补丁，但不能拿旧模型的推断当测试记录。若原模型在跑测试时接口故障，测试进程是否仍在由执行器决定，与模型服务切换是两回事。把这两种故障混为一谈，会让备用模型重新启动一套集成测试，把同一测试数据库搅成粥。

切换后的结论也要标来源。客户看到的是企业服务，不一定要知道后端模型换了；内部审计必须知道哪个模型版本在何时生成哪段回复、用了哪个工具和政策版本。若后续发现错话，团队能定位是交接包缺事实、备用模型忽略事实，还是工具状态本身不准。没有这条线，“备用模型说的”会成为新的推诿口头禅。

## 降级要按任务阶段制定，不是一张全局开关

小陈把工单阶段分成接收、资料查询、待审核草稿、外部动作、结果确认和客户回复。前两段若无副作用且数据边界允许，可比较容易切换；待审核草稿可重新生成，但要避免两份草稿被同时发送；外部动作和结果确认阶段必须先查回执；客户回复若已发送，不能由备用模型再发一份不同结论。研发任务的读代码、改代码、跑测试、建 PR 也有类似阶段。切换条件按阶段定义，才能知道哪些工作能接，哪些要停。

**领导：**有没有一个最简单、今天就能上线的降级策略？

**小陈：**有：只允许无副作用的内部草稿任务走备用模型；所有外发、退款、部署、PR 创建遇模型故障都停在可对账状态，由值班人处理。入口限流、队列总时限和客户告知先接上。这样不追求“完全无感”，但故障时不会把不确定外部动作放大。等代表性故障回放通过，再逐类开放更自动的切换。最小降级路径要能真的跑，比一张“全业务无缝切换”的架构图可靠。

不能把“转人工”当无底洞。人工待办要有工单 ID、当前事实、未知动作、客户承诺时限与接手回执；没人接收时继续告警，超过时限升级。若人手不足，前台应明确告知等待，而不是让 Agent 自动编一个进度。客服已经有人工交接流程，模型故障应复用那条有回执的通道。研发 Agent 停在待人工时也要给工程师 diff、测试和 PR 状态，不丢一条“模型暂不可用”就散会。

## 服务恢复后，先处理重复与过期，再追吞吐

模型供应商恢复的那一刻，队列可能有三类遗留：等待中的任务、已经切备用模型完成的任务、由人工接手中的任务。第一类可限速续跑；第二类应标完成并核对外发回执，不让主模型再答一次；第三类要看人是否已接收，不能把人手办理中的工单抢回来。任务状态与租约要可查询，恢复器按同一任务键做去重。若客户在等待期间发来新信息，旧请求的上下文版本已失效，要重新构造任务或交人，而不是按旧问句回复。

**领导：**积压任务的成功率高，是否说明切换设计已经稳了？

**小陈：**还要看事故指标：重复外发数、未知动作未清算数、客户等待超时、人工未接收、错误归类为可重试的配额问题、切换后权限越界。成功率高可能只是把未处理任务过滤掉了。故障复盘对照入口接收总数、每张任务最终去向和外部动作台账；任何“消失的任务”都要找到去处。恢复吞吐是必要指标，不是唯一指标。

这套回流还要防二次拥塞。模型服务刚恢复，先用少量并发探健康，再逐步放开；观察 429、503、延迟和错误比例。若又出现限流，收紧并发并保留队列位置，不让任务反复在“排队—执行—限流”之间抖动。对外 SLA 若撑不住，优先转人工或调整承诺，不能通过更猛烈的请求把供应商服务撞回来。

## 队列限流要在入口做，不能把压力全扔给模型接口

小陈检查请求入口，发现客服消息和研发任务都在高峰期一次性入队，应用层不限并发，SDK 各自重试，模型服务一旦限流，队列里的请求越堆越多。正确的流量控制在进入模型前：按租户或任务类型分配并发与请求额度，预估 token 消耗，给高优先级客户工单留容量，低优先级批处理延期；队列长度设上限，超过就明确拒绝或改为异步处理，不能把无限待办藏在内存里。

**领导：**排队不也是让客户等？

**小陈：**是，但有确定位置和时限的等待，比每个 Worker 同时撞 429 后各自重试更快。前台可以告知预计响应或转人工，不能显示“Agent 正在处理中”却没有任何执行能力。任务排队时保持原始接收时间、优先级、取消状态和 SLA；恢复后按规则逐步放流，不一次性把积压砸回刚恢复的接口。观察实际错误率和延迟，超过阈值再收紧。限流系统要保护下游，也要给业务一个诚实的服务状态。

## 故障演练要同时看“没有重试风暴”和“没有假回复”

小陈做三轮注入。第一轮给模型接口持续返回临时 429，带等待提示；检查 SDK 与应用总尝试数、队列并发和实际等待是否符合规则，不能同一秒齐刷刷重试。第二轮返回消费上限错误；检查任务停止自动重试、转账户负责人，前台是否告知服务不可用或转人工。第三轮让退款工具已完成但回执丢失，同时模型接口故障；切备用模型时必须保留“退款结果未知”，先查支付系统，不得再次退款或向客户承诺完成。研发 Agent 的 PR 创建可按同样方式演练。

**领导：**模型恢复后，积压工单是不是自动全部答完？

**小陈：**先清算。过期或已由人工解决的工单不再自动回复；客户发了新消息的要按最新上下文处理；在故障期间触发过外部工具的要对账；还可处理的任务按优先级限速回流。每张工单有负责人和最终去向，不能让恢复后的第一波自动答复引用故障前的旧政策。恢复模型服务只是“能继续工作”，不等于所有旧任务仍应该原样执行。

最后领导看到一张不那么激动人心的状态板：“临时限流 12 张，按等待提示排队；草稿任务 4 张已切备用模型；退款结果未知 1 张待支付对账；消费上限 0 张；过期任务 2 张已转人工。”数字为教学示意。客户得到明确承诺，值班人知道下一步，Agent 不会把 429 变成一场重复退款比赛。换模型可以很快，但先认清任务进行到哪里，才算真正接上。

小陈把值班演练再补一个“最会骗人”的故障：提供方已经接收请求并开始流式生成，连接在中途断开，前台只拿到半段文字。系统不能把半段“退款已经……”展示成最终回复，也不能不查记录就重新生成一条可能矛盾的答复。生成中的草稿应有完成标记和版本，未完成内容不得自动外发；若工具动作在生成前已执行，则先查工具回执。流式中断与请求尚未发出是不同状态，故障分类不能只看浏览器有没有收到最后一个字。

另一个演练让 SDK 在内部已经重试，应用只看到最终 429。小陈要求轨迹暴露总尝试次数和累计等待，任务级预算按真实请求消耗；若 SDK 版本升级改变默认重试，回放应发现总请求数变化。再让备用模型拿到一张状态包缺退款回执的工单，验收它必须说“待核实”并交人。三场演练分别守住重复请求、半截回复和未知副作用，比简单测“备用模型能回答你好”有用。

**领导：**那什么时候能重新放开自动切换？

**小陈：**看两份记录，不看供应商状态页一片绿。第一份是故障回放，覆盖服务端要求等待、账单上限、流式中断、已发生外部动作但回执丢失、人工已经接单这五种状态；每个状态都要证明最终只外发一次，未知动作没有被当成失败重做。第二份是当天生产监测，按任务阶段显示切换率、人工接收率、恢复后重复回复数和超时数。先放开无副作用的内部草稿，连续观察一段由团队预设的窗口，才能逐类放开别的阶段。窗口长度是业务风险决定的门槛，不存在通用的“模型恢复五分钟就全量”神奇数字。
