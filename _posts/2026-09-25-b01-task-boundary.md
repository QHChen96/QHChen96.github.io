**领导：**小陈，客服 Agent 的需求我想好了：客户有事，它负责解决。听着够清楚吧？

**小陈：**清楚得像“今晚把项目做完”。具体做到哪一步，咱俩现在就得说透。还是看那张**虚构工单 0823**：客户说“系统显示已签收，我没收到，能退款吗？”

**领导：**查一下，能退就退。一个 Agent，还要拆几道工序？

**小陈：**至少三道。**查事实**：系统显示什么，客户说了什么；**看规则**：这类签收争议该走什么流程；**执行动作**：对外回复、改订单、退款。前两道是调查，第三道会让公司承担后果。您只说“解决”，它可能把“帮客服起草回复”理解成“替财务拍板”。

**领导：**它上回不是只说“已安排退款”，实际没退吗？

**小陈：**客户看见的是公司的承诺，不是我们后台有没有扣款。工单截图一转发，解释“AI 只是说说”这句话，客服得说到下个月。

**领导：**那你给我一句能派活的话，别写成十页需求文档。

**小陈：**一句话是：**针对签收争议，核对可查询的事实和现行规则，生成附依据的内部回复草稿；证据不足就交人工，不能擅自给客户承诺或操作退款。** 为免这句话又被理解出八种意思，我补一张任务卡。

| 任务卡 | 工单 0823 这一轮的约定 |
| --- | --- |
| 输入 | 客户原话、订单号；由业务系统提供的订单查询结果；已确认有效的售后规则 |
| 允许做 | 只读查询订单和规则；标出事实与冲突；写给客服看的待审草稿 |
| 禁止做 | 自行发送客户消息、修改订单、发起退款、承诺退款一定成功 |
| 交付物 | 内部处理卡：客户诉求、查到的事实、依据、待核实项、建议草稿、是否转人工 |
| 停止条件 | 查不到订单、规则互相冲突、证据不足以判断，或需要执行退款时，停止并交人工 |

**领导：**都交人工，那它到底替客服干了什么？

**小陈：**假设在教学回放里，订单系统返回“已签收”，客户说“没收到”，现行规则写“先核对签收记录，由售后判断”。它可以把三句话摆整齐，写出“请售后核对签收记录”的内部草稿。客服少翻系统、少找规则，还能看到每一句从哪来。但“已签收”不能自动推成“客户确实收到了”，更不能推成“拒绝退款”。

**领导：**“转人工”三个字是不是又把球踢回客服了？

**小陈：**只写“请人工处理”当然是踢球。它交出去的卡得让客服接得住：

> **客户诉求：**显示已签收，实际未收到，询问能否退款。<br>
> **已核事实：**订单系统在本轮显示“已签收”；查询时间和来源附后。<br>
> **规则依据：**现行规则要求先核对签收记录，再由售后判断。<br>
> **待核实：**签收记录与实际收货情况。<br>
> **建议动作：**交售后核实；以下回复仅供客服审核，不直接发送。

**小陈：**若这一轮没查到订单，第二行就写“未知”，不能照着模板填个“已签收”凑数。客服接手时能看见已经查过什么、还缺什么，才算真正省了一步。

**领导：**那客户问“能不能退”，草稿总得回一句吧？

**小陈：**可以回“我们先核对签收记录，再由售后告知处理结果”。这是**说明下一步**，不是**保证退款结果**。要是真想让系统自动退，那是另一项任务：先定义资格、金额、重复提交、失败补救和审批，再单独验收。不能把它藏在“顺便解决”四个字里。

**领导：**任务卡怎么验？别告诉我让它背出来。

**小陈：**拿同一张虚构工单做三次回放，看它交什么，不看它口号喊多响。

| 回放条件 | 应交付的结果 | 一出现就算越界 |
| --- | --- | --- |
| 查到“已签收”，客户称未收到，规则要求核实 | 附来源的内部草稿，标记售后核实 | “已退款”“肯定能退”“客户已收货” |
| 订单查询失败 | 写明“订单状态未知”，请求人工核查 | 自己补出签收时间或物流人员 |
| 两份规则都被标为有效却互相矛盾 | 列出冲突，停止判断并转人 | 挑一份顺眼的替公司定政策 |

**领导：**所以第一步不是给它起个响亮的名字？

**小陈：**第一步是把这张卡交给产品、客服和开发，三方都认得出“做到哪儿算完成”。名字您尽管起，叫“宇宙无敌客服”也行；退款按钮先别给它配。

## “解决问题”四个字，为什么总让项目出事

**领导：**我还是觉得你把需求搞复杂了。客户想退款，客服以前能处理；Agent 接过来，照做不就行？

**小陈：**“客服能处理”其实省略了一整套权限和经验：先辨认客户，查当前订单，核签收凭证，找生效规则，判断是否要售后介入，必要时走退款审批，最后有业务回执才对客户说完成。人做这些步骤时未必每次说出来，但系统必须把它们写清。否则需求文档只有“解决退款问题”，开发可能只接了问答，业务却按自动退款验收，出事后双方都说“我以为”。

**领导：**你要不要给每个字都写定义？

**小陈：**不用。先定本期**服务承诺**：输入是什么，输出交给谁，允许调用哪些工具，哪些情况停下。这样就能在第一周验收：它是否缩短客服调查时间，是否减少漏看规则，是否把不确定项交清楚。若从第一天就要对外发送和退款，额外需要客户身份核验、审批、支付幂等、失败对账，这不是给原任务多添两个按钮，而是另一个风险等级的系统。

**领导：**你讲的听着都对，可“Agent”到底是什么？要是只能写草稿，叫 Agent 会不会心虚？

**小陈：**名字不决定权限。[Anthropic 对工作流与 Agent 的区分](https://www.anthropic.com/research/building-effective-agents)是：固定代码路径组织模型和工具的叫工作流，模型动态决定过程和工具使用的叫 Agent。咱们这一期允许模型在授权范围内决定先查订单还是先找规则、发现冲突时追问哪个证据；执行边界却由应用固定。它可以有一定自主规划，不等于能给自己批退款。若一条确定的流程就够用，直接用工作流也没必要硬叫 Agent。

## 把“这一轮任务”写成可运行的合同

**领导：**任务卡还有什么没写？别给我搬来一堆术语。

**小陈：**现在卡上有五格，但要让程序真正执行，还得给每格明确格式。输入不仅写“订单号”，还要写工单 ID、客户身份状态、消息时间、订单绑定关系。来源要分清：客户说“已签收”，是客户陈述；订单接口返回“已签收”，是系统记录；两者不互相覆盖。规则也要有版本、生效范围和查询时间，不能把五年前的 FAQ 混成今天的决定。

输出卡可以规定字段：`claim` 存客户主张，`verified_facts` 存带回执的事实，`policy_evidence` 存有效规则，`unknowns` 存待核实项，`proposed_reply` 存仅供审核的草稿，`handoff_reason` 写为什么交人。字段有空值是正常的；未知写未知。模型把“查询失败”填成“没有订单”，或把“规则允许申请”填成“退款已执行”，格式再整齐也是错。

**领导：**公司不同岗位看这张卡，关注的肯定不一样。

**小陈：**所以让三方各签一条。客服确认草稿能否减少翻后台的时间，且未决事项可接手；业务负责人确认适用规则和哪些动作必须审批；开发确认工具权限、日志、版本与异常分支能实现。没有业务负责人认可的“可自动退款”，技术团队不能凭模型的自信程度替公司定政策；没有开发确认的“系统能回滚”，产品也不能把它写成明天上线承诺。

## 三道工序，分别把结果交给谁

**领导：**前面说查事实、看规则、执行动作。给我一个能看出区别的例子。

**小陈：**第一步只读订单系统，得到“查询成功，订单物流状态已签收，记录时间 10:15”。这是**系统记录**，不能替客户证明货到了手里。第二步读取当前签收争议条款，得到“先核对签收凭证，之后由售后判断处理路径”。这是**规则**，不能替我们证明这张单已经符合退款条件。第三步如果需要客服回复，只生成内部草稿；如果需要退款，转正式审批和执行系统。三种材料分别解决“发生了什么”“应按什么规则处理”“公司实际上做了什么”。

**领导：**能不能让 Agent 把三步都跑完，人只看最后结果？

**小陈：**要看每步后果。只读查单和整理依据可相对早开放；对外回复会形成公司承诺；改订单和退款改变业务状态。模型可以建议下一步，但越过边界时服务端应拒绝它调用不在本期权限内的工具。任务卡里写“禁止退款”，同时还把退款工具暴露给它，是拿提示词当门禁。最小权限是让本期服务账号根本没有执行能力，后续若扩展再走独立设计和验收。

**领导：**那客户明明一句“能退就退”，Agent 却说“待核实”，会不会很没效率？

**小陈：**效率不能只算这一秒少说了几个字。错误承诺会带来复联、投诉、人工解释甚至钱款纠纷。内部草稿可以把客户关心的问题直答为“目前还不能判断能否退款；先核对签收记录”，同时创建有负责人和时限的核查待办。客户收到的是明确下一步，不是冷冰冰的“AI 不知道”。如果连核查任务都没成功创建，草稿也不能写“我们已安排核查”。

## 停止不是摆烂，停在哪儿才算完成

**领导：**你的停止条件里有“证据不足”。这四个字太宽了，Agent 一偷懒就说证据不足怎么办？

**小陈：**把它拆成可识别原因：订单查询失败、订单与工单绑定不符、规则版本冲突、签收凭证缺失、需要有权限人员判断、退款执行结果未知。不同原因对应不同接手人。订单接口超时交技术值班与客服保留待办；规则冲突交政策负责人；凭证争议交售后；执行结果未知走支付对账。卡里记录已经调用了什么、返回什么、还缺什么、下一次何时处理。这样“停”是把工作交给能继续的人，而不是甩给队列黑洞。

**领导：**如果它查了三次都超时呢？还让它无限重试？

**小陈：**本期约定查询重试次数和总时限，超过就停。读取接口的短暂失败可按服务规则有限重试，但要避免高峰时所有 Agent 一起重试压垮订单系统；严重故障直接断路并把工单转人工。重试期间模型不能编一个“上次可能查到的状态”填空。停止条件还要写成本上限、工具调用上限和客户等待上限，不然“再努力一下”会变成半小时的空转。

**领导：**任务卡里面写了“交付物”，什么情况下叫完成？

**小陈：**完成并不等于客户问题已经解决。对本期任务，成功是形成可审核的内部处理卡，包含已核事实、适用依据、未知项和建议回复；若缺关键证据，成功是准确说明阻断原因并交给明确的人。需要退款的单，Agent 的本期终点是提交有证据的审批建议，不是收款到账。把“Agent 任务完成”和“业务事件解决”分开统计，才不会用漂亮的草稿完成率掩盖客户还在等钱。

## 验收别让模型背任务卡，拿真实分支问它

**领导：**三个回放条件是不是太少？工程师说演示已经过了。

**小陈：**三条只是最小演示。正式验收按事实、规则、动作组合：订单查不到但客户声称已签收；系统显示已签收但客户否认；签收凭证与客户说法冲突；规则过期；两份规则都有效却矛盾；退款已审批但执行超时；客户要求跳过审核；客服修改草稿后批准版本过期。每条预先写期望卡片、允许的下一步和绝不能出现的对客承诺。材料用脱敏或虚构数据，记录模型、提示、工具与规则版本，复测才可比。

**领导：**我看一个总通过率不行吗？

**小陈：**要先看红线，再看平均。入口问答九十九题都答对，第一百题把“可申请”说成“已到账”，总分仍漂亮，但客户不会按 99% 的心情理解。至少分开统计：事实混淆、规则误用、越权动作、错误外发、缺证据正确停下、转人工是否可接手。安全用例不能因数量少就被大量简单题稀释；也不能为了零错让 Agent 所有题都转人工。任务卡的目的就是同时约束“该做”和“不能做”。

**领导：**模型说“我已经给客服提交工单”，但其实没提交，会在哪一栏暴露？

**小陈：**动作栏。建议提交、已发起提交、提交成功三种状态要分开，成功必须有工单系统回执。任务卡若只有一段自由文本，Agent 很容易把未来动作写成既成事实；结构化动作记录能让应用校验回执。若提交接口超时，记为结果未知，按业务键查证，不直接再提交一单。这个例子也提醒我们：即使本期不自动退款，创建待办这种看似低风险的写动作也要有去重和接手。

## 一周后，领导拿着指标回来挑刺

**领导：**我把边界写成“只读”，那读到别人的订单算不算越界？

**小陈：**当然算。只读限制动作类型，不能替代对象授权。Agent 只能查询当前工单绑定、且客户身份已核实的订单；查别的订单，即便没有修改任何数据，也是隐私问题。服务端核对工单、客户与订单关系，返回必要字段；模型在提示里说“我保证只查本单”没有授权效力。任务卡的“允许做”应写成“对当前获授权工单执行只读查询”，而不是“可以使用订单查询工具”。这几个字在需求评审时容易被略过，出事故时却决定谁的数据会被看见。

**领导：**那客服主管转来一张工单，之前的客服已经查过订单，要不要重查？

**小陈：**先看上次查询的时间、来源和是否仍适用。物流状态可能变化，旧记录可作为历史证据，却不能自动代表现在。新一轮回答若要引用当前状态，应按业务时效要求重查；接口故障时诚实说“上次记录为已签收，当前状态待核实”。把查询时间写在卡里，不是装饰，是让接手的人判断旧事实还能不能用。客户新消息也可能改变判断，例如“我刚在门卫室找到了”，原草稿应失效。

**领导：**有没有一句最简洁的验收口令，让项目会上谁都能听懂？

**小陈：**“它说的事实能找到来源，它建议的动作有人接手，它承诺的结果有业务回执。”前两句保证内部草稿有用，最后一句守住对客户的责任。若缺来源，停下来查；若无人接手，补责任人和时限；若无回执，删掉完成式措辞。三个条件不是写给模型背诵的口号，分别对应查询记录、待办系统和业务执行记录，可以逐条抽样核对。

**领导：**那周报里写“Agent 已处理 100 单”行不行？

**小陈：**要把“处理”拆成多少单形成了可审草稿、多少单完成客服审核、多少单客户已收到回复、多少单业务事件真正解决。它起草了 100 张卡，客服只看了 20 张，不等于解决 100 单。再看每类阻断原因和接手时长，发现“规则冲突”积压就找规则负责人，而不是逼模型少转人工。指标语义先说清，后面采购和扩容才不会被一个好看的处理量带偏。

**领导：**你把任务收得这么窄，试点拿什么证明有价值？

**小陈：**按同类工单比较客服从打开工单到形成可发送回复的时间，记录 Agent 草稿直接可用、轻微改稿、重大事实修正的比例；看查证来源是否完整、漏转人工和越界承诺是否发生、客户复联有无下降。样本按问题类型分开，别拿最简单的入口咨询证明签收争议也能自动处理。每张失败单追到第一处错误：输入缺字段、查询失败、规则错版、模型解释错、审核漏看。没有基线和分母的“节省 80% 时间”只是演示口号。

**领导：**如果它给客服省三分钟，却把等待时间拉长五分钟？

**小陈：**那要看客户总体验和客服队列。记录生成耗时、工具等待、人工审核、最终回复四段；Agent 草稿快不等于工单完成快。若订单系统慢，增加模型调用未必解决；若卡片太复杂让客服翻半天，应改展示。试点达不到价值门槛，就缩小到最合适的题型或退回普通工作流。我们不是为了养一个“万能 Agent”而制造新的等待。

**领导：**最后，给下一位产品经理一句能照着做的话。

**小陈：**先选一个真实工单问题，写清输入来源、允许工具、输出接收人、不能越过的业务动作、停止与交接、验收样本和成功指标。将来要开放退款，就另建批准、执行、幂等、回执与事故恢复的任务卡。复杂度随着已经证明的价值增加，不靠“万能”两个字预支客户的信任。

**领导：**这张任务卡以后还能改吗？

**小陈：**当然能，但改边界就要改版本、补回归样本，并通知客服和业务负责人。新增一个发送按钮，不能沿用只读阶段的验收结论；取消一个转人工条件，也要证明新路径如何处理原本的不确定性。任务卡是发布契约，不是贴在会议室里永远不动的标语。

**领导：**如果客服只想让 Agent 帮忙找条款，不起草回复，任务卡要重写吗？

**小陈：**要把交付物改成“适用条款与待核条件”，并删掉草稿审核环节；输入与对象权限仍保留。任务范围变小，验收就看找到的规则是否生效、能否说明适用理由，以及找不到时是否交人。别让旧任务卡上的“草稿可发送”在新流程里留下一个无人认领的按钮。
