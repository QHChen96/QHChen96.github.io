**领导：**昨天你让工单 0823 先走固定工作流。我还想知道动态方案能不能更能干，就让开发做了个只读 Agent 对照回放。你看，它很勤快：查询订单失败又查一次；又失败，它还查。

**小陈：**对照回放里，它已经查到第三轮了。订单没回来，调用记录倒是比客服日报还长。

**领导：**再给它一点时间？员工遇到困难也不能立刻下班。

**小陈：**员工至少会说“系统坏了”。它现在把“没查到”当成“再查一次”，永远不交结果。我们继续用虚构工单 0823 做试验：客户问“显示已签收，我没收到，能退款吗？”。正式路线仍是昨天定下的固定工作流，今天查的是动态方案为何会卡住。

## 领导：“Agent 不就是一直想办法吗？”

**小陈：**一次 Agent 运行确实像个循环：看任务和现有证据，决定答复还是调用工具；工具回来后，再看新证据。关键是**每转一圈都要有终点判断**。它不是电风扇，不能通电就一直转。

**领导：**给它写“最多三次”就行？

**小陈：**次数只是一道闸。得先分清结果。订单查到了，下一步可以看规则；订单不存在，要核对输入和权限，不能说客户没下单；接口超时，事实是**查询结果未知**，不是“订单未签收”；规则缺失或互相冲突，就别起草退款结论。每种结果对应的动作不一样。

| 本轮看到什么 | 下一步 | 能对客户说什么 |
| --- | --- | --- |
| 订单查询成功，规则也明确 | 生成带依据的内部草稿，交客服审核 | 审核通过后按已核实事实答复 |
| 查不到匹配订单 | 检查工单绑定和查询范围，再交人核对 | 不说“您没有这个订单” |
| 只读查询暂时超时 | 有限次退避重试；仍失败就停止并标记人工 | 不说“我已经核实” |
| 现行规则缺失或冲突 | 停止给退款判断，交政策责任人 | 不承诺能退或不能退 |
| 达到时间、调用或费用上限 | 保存轨迹与当前未知项，退出循环 | 告知仍在核实，由人工继续 |

**领导：**“有限次”怎么定？我怕你拍脑袋。

**小陈：**先看工具的超时和限流约定，再按客服能接受的等待时间定上限，放进配置并回放验证。这里不编一个全行业通用数字。真正要写在运行规则里的，是**任何上限到了都有退出动作**：保留已经查到的证据，标明没查到的部分，把工单交给谁。

## 领导：“它退出了，客服不会又从头查一遍？”

**小陈：**交接不能只甩一句“失败”。给客服的处理卡会带上订单号、查询时间、已经成功的工具结果、失败工具的错误类型、还缺哪条证据，以及“未向客户承诺退款”。客服看完能接着办，不用猜机器之前干了什么。

**领导：**如果是退款接口超时，也按这张表再试？

**小陈：**不能照搬。今天这个循环只放**只读查询**。退款这种写操作返回超时，钱可能已经动了，要先查业务回执和交易记录，确认实际状态，再决定后续；重复点可能真退两笔。进阶的“结果不明怎么恢复”会单独写，基础篇先把错误种类分开。

**小陈交付的运行规则：**工单 0823 允许查询订单与现行规则；每次调用记录请求、结果和耗时；成功、无证据、冲突、超时、预算到顶各有退出路线。验收用“查到／查不到／超时”三种虚构返回回放：每条轨迹都必须停在一个明确状态，并带可供客服接手的处理卡。不能用“它还在努力”当完成报告。

## 循环里每一圈到底发生什么

**领导：**你说“观察、决定、行动”，我听着像口号。程序里是什么？

**小陈：**运行状态至少有当前工单、已取得的证据、已调用的工具、失败原因、剩余时间与费用预算。模型读状态后可提出三类下一步：用允许的只读工具补证据；基于已有证据给出内部处理卡；因为缺信息、冲突或风险交人。应用先校验提议，再执行工具或结束。工具结果写回状态，下一圈才能看到。若没有新证据、目标已完成或任何硬上限触发，循环必须退出。模型可以建议结束，但**应用负责保证结束**。

**领导：**为什么不用一条无限循环，让它到满意为止？

**小陈：**“满意”没有机器可核的边界。订单系统故障时，它可能把重复请求当成努力；知识库缺现行条款时，它可能越搜越旧。每次循环都占延迟和费用，还可能重复读取敏感数据。至少设最大步数、同工具重复次数、总耗时、成本、无新增信息次数和客户等待时限。数值应按工具性能与客服服务承诺调，不存在一组全行业通用的“最多三轮”。上限达到后的动作要先设计好：保存轨迹、标未知、交客服，不是直接报“任务失败”然后消失。

**领导：**同一个工具连查两次，就算无新增信息？

**小陈：**不一定。第一次超时、第二次成功，是新增事实；第一次查到订单，第二次在相同状态与短时间内又查同单，通常没有新增价值。要比较参数、对象、时间、返回版本和业务时效。可以缓存符合条件的只读结果，但标原查询时间；订单状态可能变化时按规则重查。不能简单按字符串相同就永远阻止，也不能让模型因为“我再确认一下”无限刷接口。

## 读失败、写结果未知，不能共用恢复动作

**领导：**读订单超时，你说有限重试。退款提交超时，我是不是也设三次？

**小陈：**绝不直接照搬。读查询一般可按错误类型退避重试；写操作发出后超时，可能已经产生申请或退款，必须先按业务键查执行回执。若业务系统支持稳定幂等键，按同一个业务意图安全重试；否则挂起对账和人工核实。把“没收到响应”误判成“没执行”，是重复退款最短的路径。运行状态要区分调用未发出、已发出结果未知、明确失败和明确成功，恢复器按状态走。

**领导：**只读接口失败三次，客户等着呢，能不能用上次缓存的签收状态？

**小陈：**可以作为带时间的历史线索，但不能无标记地替代当前事实。客服内部卡可写“上次于 09:40 查询显示已签收，本轮 10:15 查询失败，当前状态待核”，对客如果要说当前订单状态，应慎重或交人工。是否能使用缓存，看业务时效约定；退款资格这类高风险判断更不能仅靠旧状态。缓存降低服务压力，不是把未知重新命名为已核实。

**领导：**重试的退避是什么？是不是睡五秒就行？

**小陈：**对短暂性错误，按服务约定增加等待并加入抖动，避免所有工单同时重试把故障服务压得更重；明确权限拒绝或参数错误不重试。还要看总截止时间：客户等候上限到了，就算单次退避还没结束，也该停止自动循环并交人。[Temporal 的重试策略文档](https://docs.temporal.io/encyclopedia/retry-policies)讲了重试间隔与最大尝试等控制，但我们的具体值要由订单系统容量和客服时效实测决定。

## 四种出口，不能只给客服一个“失败”

**领导：**你那张表里成功、缺证据、故障、预算到顶，客服都接吗？

**小陈：**接手方式不同。成功出口给客服待审草稿，附订单与政策来源；缺证据出口指明缺签收凭证或有效规则，给售后或政策负责人；工具故障出口带错误码、尝试次数和下一次可查时点，给客服及技术值班；预算出口列已查证据和为何没推进，避免人工重做一遍。若需要客户补资料，生成具体请求，不说“信息不足”四个字让客户猜。退出是业务状态，不只是代码里的 break。

**领导：**Agent 一到预算上限就转人，客服队列不会爆？

**小陈：**要监控出口分布与原因。大量单因订单接口超时出队，先修接口与退避；大量因规则缺失出队，补知识与政策治理；大量因模型重复查询耗尽预算，修工具选择和停止判断。给人工队列容量与优先级，超时客户收到进度告知。限制循环不等于把成本偷偷转嫁给客服；指标要把机器调用与人工接手一起算。

**领导：**模型能不能自己说“这单我处理完了”，不出卡？

**小陈：**不能。完成条件由应用核：内部卡字段完整，关键事实有来源，未知项列出，建议草稿经过校验。若客户问退款而卡里只写“谢谢您的耐心”，模型主观觉得完美也不算完成。反过来，有明确缺证据且转人成功，也是本期 Agent 的合格结束，不必强迫它生成一个不负责任的肯定结论。

## 中途崩了，怎样从断点继续

**领导：**进程在第二次查规则时重启，能不能让它从头再跑？

**小陈：**读工具从头可能只是浪费，写工具从头可能重复执行。每个关键步骤保存状态快照：当前工单版本、已完成工具调用及回执、尚未完成的调用、剩余预算、等待人工的原因。恢复时先核工单是否有新消息、旧证据是否还有效、上次工具结果是否已落业务记录；再决定继续、重查或交人。不要把模型的上一段自由文本当唯一记忆。状态持久化和业务回执决定恢复点，模型负责在恢复后的有效上下文继续判断。

**领导：**模型上次说“我正提交退款”，进程重启后怎么知道提交了没有？

**小陈：**看业务请求 ID 与退款系统回执，不看它说了什么。若请求已发、结果未知，进入对账路径；若根本未发出，按审批与时效重新校验后才可决定执行。对于本期只读试点，这一类写入工具不开放，但架构设计不能忘。Agent 运行循环的“状态”要能区分建议、发起、确认，防止重启后把一句将来时当过去式。

**领导：**还没崩，只是客户又补一句“我刚拿到了”，循环怎么办？

**小陈：**新消息使工单版本变化，旧计划可能不再适用。应用可取消或暂停当前循环，重建有效上下文，把新客户陈述和最新订单状态纳入；已完成的只读证据可按时效复用，未发出的退款建议作废。若已进入审批或发送阶段，要检查批准是否绑定旧版本，并按规则失效。不能让模型在旧循环里继续追“未收到”而忽略客户刚刚解决的问题。

## 一张运行轨迹，怎样帮助排障

**领导：**我只想知道它为什么查三轮，别给我一整页思维过程。

**小陈：**给您结构化轨迹：第 1 步请求订单查询、超时；第 2 步按策略退避重试、仍超时；第 3 步达到同工具错误上限，停止并转客服。每步记录参数摘要、授权结果、耗时、错误码、是否获得新证据和剩余预算；不需要模型内部不可见的推理全文。客服看业务摘要，工程师看调用细节。这样能判断问题是接口故障、重试配置错误还是模型忽略了停止条件。

**领导：**如果模型绕过循环控制，在答复里直接说“已退款”呢？

**小陈：**输出校验仍要查退款执行回执；没有就拦草稿。模型没有写入权限，也不能借文字制造业务事实。循环控制负责资源和进度，业务校验负责结论，工具权限负责动作。三层各有用处，不能因为步数上限写得漂亮就以为误承诺也解决了。

## 怎么证明循环没有变电风扇

**领导：**验收用三种返回够吗？

**小陈：**再加具体组合：第一次超时第二次成功，应停止重试并用回执继续；连续超时到上限，应交人并保留未知；明确无权访问，不能换订单号反复试；两条有效规则冲突，不能一遍遍检索旧文直到挑到顺眼的；订单成功、政策缺失，只能写待核；客户途中补充新消息，旧草稿失效；进程重启，恢复后不能重复已确认的写动作。每条检查是否在有限步骤内停下、是否保留有效证据、是否留下接手人。

**领导：**最终统计什么？

**小陈：**按题型看完成率、正确停答率、平均和高分位步数、重复调用、工具失败、人工接手时间与每单总成本。平均两步很好看，但少数单转三十圈会拖垮账单和客户等待。把“因预算退出”单列，分清是规则缺失还是循环失控。成功指标不是 Agent 工作越久越努力，而是它用可控成本给出可靠结果，做不到就及时把活交给人。

**领导：**面试官问“Agent loop 怎么停止”，你就说这些？

**小陈：**先说完成条件、失败和证据缺口，再说时间、步骤、费用的硬上限；接着说重试按错误分类，写操作先对账，最后说状态持久化与人工交接。循环可以让模型动态查证，出口却必须由系统与业务一起定义。否则它查到下班，订单没回来，预算也不会自己发工资。

## 上线第一天，循环卡住了怎么办

**领导：**假设真在线上出现一批工单反复查单，客服群已经骂起来了，你第一步改提示吗？

**小陈：**先关掉该题型的动态重复查询，保留人工接手和已成功的只读结果；限制并发，避免订单服务被重试流量压垮。按运行轨迹定位影响工单、调用次数、客户等待和是否有对外错误承诺。若只读循环失控，通常可按工单暂停并交客服；若发现它曾碰写接口，则要先查业务回执，不能用“关闭 Agent”代替资金对账。提示和策略修复在止血之后，带着失败样本回放再灰度恢复。

**领导：**自动熔断会不会把正常客户也堵住？

**小陈：**按能力和题型分开开关：重复订单查询停掉，不影响现有固定工作流、客服手工查单和低风险答复。界面清楚显示“自动查证暂停，已转人工”，不要让客户看见永远转动的加载圈。恢复时先以有限流量试，观察超时率、每单重复调用、队列积压与客户等待，确认故障没有换个地方出现。开关粒度决定我们能否止血而不把整间客服中心拉闸。

**领导：**如果根因是订单服务限流，Agent 团队说“不是我们的错”，谁管？

**小陈：**服务限流是触发，循环不懂退避和退出是放大器。订单团队要给明确容量和错误语义，Agent 团队要尊重限流并设预算，客服运营要有人工接手容量。复盘按时间线看：第一个限流何时出现，何时开始集中重试，监控何时报警，多少客户被拖延。责任分层是为了找到修复点，不是开三场互相甩锅会。

**领导：**值班人想给模型一句“不要重试”，临时热修能上吗？

**小陈：**若要紧急止血，先用应用配置的硬上限和流量开关；提示热修仍需版本、最小回放与回退。单靠一句自然语言未必挡住所有路径，模型版本或上下文变化还可能让它忽略。把一次事故样本加入固定回归：连续超时、限流、无新增信息、客户中途更新，确认每条都能有限步退出并交人。恢复时看实际工具调用数，不只看模型回答“我会停止”。

**领导：**你把循环设得这么严，它遇到复杂问题会不会来不及查完？

**小陈：**预算应按题型调整，但扩大预算要有收益证据。对复杂签收争议可允许更多只读取证，前提是每一步带来新证据、服务容量和客服等待可接受；对普通入口问答一次检索就够。达到上限不代表把工单扔掉，而是把已查资料和缺口交给人。若复杂单总在预算处停，研究是工具能力不足、检索质量差还是预算设小，不用“无限循环”掩盖根因。

**领导：**客户收到“正在核实”，内部队列却没人领，这算成功退出吗？

**小陈：**不算。交接需要工单待办回执、责任队列和到期提醒；创建失败要留在异常队列并报警。Agent 的循环停止只是计算过程结束，业务处理还没结束。报告分别看“自动处理完成”“人工接手成功”“客户问题解决”，避免把最后一句礼貌回复当作任务完成。出故障后的恢复路线，最终要落到某个人或某个受控系统真的继续做。

**领导：**给我一条值班口令。

**小陈：**先看它有没有新证据，再看工具错误能否安全重试；到时限立即停，带着回执与未知项交给有人负责的队列。写动作结果未知先对账，不能再点一次赌运气。客户看到明确进度，工程师看到完整轨迹，客服拿到可继续处理的卡，这才叫循环有出口。

**领导：**这次电风扇终于有了开关。

**小陈：**还得记得是谁开的、为什么停，以及客户接下来找谁。只停机器，工单仍会在队列里转圈。

**领导：**那客户等候超时与技术调用预算，哪个先到就停？

**小陈：**以更早触发的约束为准。技术预算未用完，客户已等到服务承诺上限，也该退出并交人；客户还能等，订单服务已连续限流，也不能继续打。退出卡记触发的是哪道上限，后续由运营判断是否需要进度告知或优先处理。

**领导：**停得及时，也算会办事。

**小陈：**还得交得明白。
