**领导：**三个 Agent 一起干还不够快。我把并发改成五十，服务器又没说不行。

**小陈：**服务器允许五十个人站起来，不代表合同接口有五十个窗口。现在大家同时去敲门，被限流以后又一起重试，整个系统像早高峰有人一边堵车一边按喇叭。

继续使用**教学虚构**的星河制造续约任务。身份与授权检查完成后，客户事实、合同政策和服务工单是三个必需分支，新闻背景为可选分支。本篇从一项任务讲到多租户调度，所有时间、预算和配额数字用于演算。调度伪代码表达职责，不冒充完整分布式执行器。

## 一、并发、吞吐和延迟，别在同一栏里写“快”

**领导：**并发高一点，不就是处理得多一点？

**小陈：**并发是同一时刻有多少工作在进行；吞吐是单位时间完成多少合格工作；延迟是一项工作从进来到交付等多久。它们相关，但不会同步变好。任务都在等待模型配额时，在途数量很高，完成率却可能很低。

一项续约准备的总延迟包括排队、身份检查、分支等待、研究执行、汇流、写作、验证和业务等待。调高研究并发只影响其中部分。若模型供应商对整个组织的输入 token 有限额，五十路长上下文会竞争同一个池；若合同服务只允许少量同时请求，更多 Agent 会把等待搬到服务内部。调用一旦进入对方队列，应用还可能失去精确的取消和优先级控制。

必须把排队时间和执行时间分开测。合同分支总共四十秒，可能五秒真正读取、三十五秒等配额；换一个更聪明的模型不会解决等待。观察每种资源的队列长度、等待分位数、实际完成速率和限流错误，才能定位瓶颈。只看平均模型响应时间，会把最难任务和高峰拥堵藏起来。

还有一个简单算式帮助检查容量。在系统长期稳定、口径一致的情况下，平均在途任务数量约等于到达率乘平均停留时间。假设每秒接收两项同类任务，平均停留十秒，在途量约二十。这是容量思考的起点，不是性能承诺；任务长尾、突发流量和不同业务类别会改变实际排队。我们要留余量，并按服务目标压测，不把平均值当峰值。

## 二、DAG 的“可以开始”，要由依赖决定

客户续约流程是一个有向依赖图。授权是三个研究分支的前置；证据验收依赖必需分支；写作依赖合格证据；批准依赖被审核的草稿。调度器只将前置满足的任务放入就绪队列。节点很多不意味着全部可以启动，画了箭头也不意味着程序真的检查依赖。

**领导：**写作可以提前跑，等资料回来再补。

**小陈：**可以先做不依赖资料的骨架，但那是另一项明确任务。事实句和商业条件要等证据。我们可以拆成“建立空模板”和“填入核验内容”，不能让提前运行的写作节点用猜测填满，再靠下一轮运气修正。

最小 DAG 调度器维护三组状态：尚未满足依赖的任务、已经就绪的任务、正在执行或已完成的任务。某个节点成功验收后，更新其下游的未满足前置数量；数量归零且没有阻断条件，才加入就绪队列。前置失败时按边的业务语义决定阻断、降级或补资料，不能一律当作完成。图里的循环要单独表达为有限迭代，不能塞进 DAG 后等待拓扑排序自行解决。

下面是**调度伪代码**，先展示逻辑，不处理分布式租约与持久化：

```python
while unfinished_tasks:
    ready = [
        task for task in pending_tasks
        if required_dependencies_passed(task, state)
    ]
    if not ready and not running_tasks:
        return blocked("依赖未满足或流程停滞")

    for task in admit_by_quota_and_budget(ready):
        state.mark_running(task)
        start(task)

    for event in await_next_completion():
        state.accept_valid_event(event)
        update_dependents(event, state)
```

`admit_by_quota_and_budget`不能仅返回前几个任务。它还要检查客户范围、资源配额、全局截止时间和剩余成本。如果任务已经过期，启动后只会产生没有使用价值的结果。`accept_valid_event`沿用上一篇的身份校验，避免旧尝试的晚到完成把下游误解锁。完成事件驱动的是已验收状态，不能只靠进程退出码推进图。

## 三、并发信号量不等于速率限制

**领导：**我加一个 Semaphore，最多三路，不就稳了？

**小陈：**它限制同时执行数量，不限制每分钟发多少次请求。三个十毫秒任务可以在一分钟里发出很多请求；三个长任务则会占着位置很久。供应商可能同时限制请求次数、输入 token、输出 token 和并发，我们要对应地管理。

本地信号量适合一个进程内的执行槽。多个副本各自限制三路，十个副本仍可能同时跑三十路；若对方配额是组织共享，就需要分布式配额协调或统一请求网关。配额不能由模型自己声明“我还有三次调用”，应由运行时记账。按模型、工具服务、租户和业务等级分别设额度，才知道谁在争哪种资源。

速率限制可以用令牌桶等确定性机制表达：按速率补充额度，消耗后才能请求；突发容量单独设定。长上下文模型请求还需要估计 token 消耗并为输出留余量。估计不等于账单，实际完成后按使用回执校正。没有回执的异常调用要保留待对账成本，不能一遇超时就把预算全部退还，好像对方一定没有处理。

**领导：**那被限流就重试。

**小陈：**按允许的重试提示和指数退避，加抖动，避免所有工作单元同时再次冲上去。重试也要经过配额和预算；不能绕开调度器开一条“特殊快速通道”。同一故障长期持续时，暂停受影响资源的派发，让其他不依赖它的工作继续，别让五十个 Agent反复证明接口现在不可用。

任务之间还需要公平。一个客户的一百个可选研究任务不能挤掉另一个客户的必要合同核对。可以按租户分配在途上限，再在租户内优先必需任务、提升等待太久的任务优先级。优先级规则应透明可测，不能只看任务到达顺序，也不能让模型在提示里写“非常紧急”就抢走整个队列。

## 一次高峰演算：扩大并发为什么救不了超额流量

**领导：**高峰时每分钟八个续约任务，给合同接口三个槽位应该够吧？

**小陈：**只作容量演示：若每个合同任务平均占一个槽位三十秒，三个槽位每分钟理论上处理六个。每分钟来八个，理想情况下也积压两个；连续十分钟就多出二十个等待，实际有长尾和重试会更差。扩大主流程并发，只把更多任务推到这三个槽位前面，不能让合同系统多出处理能力。

我们先把任务按相同资源需求归类，再估计实际合格服务率。这个算式假设三个槽位真正独立、没有共享 token 限额、服务时长相近，所以只能当上界思考。若三路都争同一模型配额，资源需求可能更高。压测要保存开始与结束时间、重试、验收失败和资料大小，用持续流量验证队列能否稳定，而不是一次同时发十个请求看看有没有报错。

高峰处理至少有四个选择：拒绝或延后非紧急任务，关闭可选研究，增加真正受限资源的容量，或者优化每项必要工作消耗。每种选择都有产品影响。延后要给可预期的状态和截止时间；关闭新闻不能关闭合同；换更快模型要验证合同证据仍然正确。缓存可以减少重复读取，但必须绑定客户范围和版本，旧价格缓存不能用于换取漂亮吞吐。

任务开始之前还可以判断是否大概率无法赶上业务期限。已知队列等待超过剩余时间时，直接说明当前无法在期限内完成，并按业务规则转入后续处理，比排到最后才超时更诚实。估计不应成为偷偷拒绝困难客户的理由，要按任务类型与优先级透明记录。我们优化的是合格交付，不是把难题删掉以后得到的响应时间。

**领导：**如果八个里有很多重复客户呢？

**小陈：**可以合并相同范围、相同版本的只读研究，多个父任务订阅一份工件；父任务的草稿与批准仍独立。不要只按客户 ID 合并，两个任务可能有不同问题、权限或时间基准。共享任务还要有引用计数或明确订阅状态，一个父任务取消时不能取消其他订阅者仍需要的工作。节约重复计算值得做，但要把共享工作从一个协程提升为有身份与生命周期的任务。

## 四、截止时间要覆盖排队，不能从开始干活才计时

**领导：**每个 Agent 超时三十秒，就不会拖了吧？

**小陈：**如果它先排队一分钟，再干三十秒，用户已经等了一分半。我们要有从接收业务任务开始的整体截止时间，再给每段分配预算。分支进入执行时只能使用剩余时间，不能重新获得一个完整窗口。

统一的绝对截止时间比到处设置相同相对超时更容易协调。全任务还有四十秒，合同研究最多用二十五秒，后面至少留写作和验证的时间；可选新闻只能用剩余宽裕部分。跨进程传递时要注意时钟差异，可以同时携带服务端签发的期限与本地单调时钟计算的剩余时长。示例不必一开始就实现复杂校时，但不能把机器本地时间混成毫秒级一致真相。

下面是**单进程异步示意**，强调等待执行槽也占用时限。`worker`和`task`由应用提供，Python 版本需要支持`asyncio.timeout`：

```python
import asyncio

async def execute_before(task, worker, slots, deadline):
    loop = asyncio.get_running_loop()
    remaining = deadline - loop.time()
    if remaining <= 0:
        return {"task_id": task.id, "status": "timed_out"}
    try:
        async with asyncio.timeout(remaining):
            async with slots:
                return await worker(task)
    except TimeoutError:
        return {"task_id": task.id, "status": "timed_out"}
```

超时包围了`slots`的等待与实际执行，因此不会把排队藏起来。这里只返回结构化超时，生产还需取消底层请求、记录实际计费与任务尝试，并处理晚到结果。协程被取消也不意味着远程工具一定停止；如果涉及发送或写数据库，必须使用后面那篇的动作账本与对账。上层取消传播不应被宽泛的异常捕获吞掉，否则任务表写了取消，底层仍在继续干活。

截止时间还影响交付方式。用户需要快速初步判断时，可以先返回“正在核对合同，尚不能给续约条件”，再继续允许的后台工作；这属于产品协议，要明确什么是进度、什么是正式结果。不能把部分完成的文本标成最终答案，以“很快响应”掩盖事实缺失。

## 五、必需分支与可选分支，谁值得等

续约草稿里的现行合同和未解决服务问题是必要材料。新闻背景只是帮助理解行业。对所有分支使用同一“全到齐才汇总”规则，会让一条失效新闻链接阻塞整项任务。使用“任意两路回来就汇总”又可能把合同缺失藏掉。扇入要依据任务身份与必要性，而非数量。

**领导：**可选任务一过期就丢掉，省心。

**小陈：**停止等待与删除事实不同。它已经交回的合格资料可以保留，但若最终草稿没采用，要记录没有使用。任务到期后不得再改已经生成的草稿；晚到结果可以作为下一版本的候选输入，是否启动新版本由主流程决定。否则审核者刚看完的内容会被后台消息悄悄改掉。

可选分支降级应在产物里说明影响。“未纳入最新行业新闻”通常不阻断合同事实；“合同登记服务不可用”则影响续约条件，必须停止相关建议。服务分支查到工单状态但缺处理日期，可以生成明确待确认事项，而不能默认投诉已经解决。所谓降级是保持已知事实并收窄结论，不是把失败变成成功措辞。

必要性也可能有条件。客户没有历史工单时，服务分支返回经核验的空集合，属于合格结果；接口没查到数据而没有区分权限、异常与空值时，不能算“无工单”。任务契约要让空结果可解释。必需分支的定义可以随场景变化，但由业务规则决定，不让模型在快到超时时把它临时改成可选。

## 六、钱要先预留，再结算，不能谁先跑谁花光

**领导：**我设总预算，花完就停。

**小陈：**如果三个 Agent 都看见还剩三元，同时各自花两元，最后账单六元。预算检查与预留必须在同一个原子操作里完成。否则“总预算”只是一行会被并发绕过的文字。

预算分两本账：预留额度与已结算消耗。派任务前，为模型、工具和可能的重试预留上限；完成后按实际使用结算，再释放剩余。金额涉及模型价格版本、输入输出估计与供应商计费口径，不能用 token 数直接代替钱。任务长时间等待时，是否维持预留和何时释放，要与执行租约和结果状态配套。

还要先给关键路径留钱。三路必要研究、汇总与最终验证的额度优先保留，可选新闻只使用剩余额度。否则所有钱花在丰富行业背景，主流程没钱核对合同，最后只能交一份很有气势但不能用的草稿。预算不足时，返回具体缺口或选择经过评测的廉价路径；换便宜模型需要验证该步骤仍符合质量要求，不能临时降配后继续用原门槛承诺。

**领导：**Agent 的思考轮数能不能直接当预算？

**小陈：**可以设轮数上限，但不能代替成本账。一轮可能只输出一句话，也可能读十万 token、调用昂贵工具。我们可以同时限制模型回合、工具次数、派生任务数、时间和费用；这些限制作用不同。达到限制要形成有原因的停止结果，让主流程知道缺的是哪项证据，而不是只看到一个空字符串。

## 七、工作区与共享服务，也是一种有限资源

给多个编码 Agent 同一个目录，是另一种并发事故。一个改接口，一个改调用方，一个跑测试；写入互相覆盖，测试读到一半更新的文件，失败证据无法对应某个确定版本。多 Agent 不需要每项任务都独立进程，但共享可变资源必须有所有权与同步规则。

编码工作可以按模块分工，使用独立工作区或分支，返回补丁与基线提交，最后由集成步骤串行合入并验证。重叠文件由一个明确责任人处理；测试结果绑定具体提交或工件哈希，不能将旧分支的绿灯贴到新集成结果。独立工作区降低写入冲突，却不能自动解决接口语义冲突，仍需要共同契约和最终集成测试。

本专题的研究分支只读，风险稍低，但也有缓存、工件路径和临时文件冲突。工件路径包含运行与任务身份；写入使用原子提交，不让汇总读到半份 JSON；共享缓存键包含来源版本和数据范围。后台任务若能修改公共知识库，必须再有独立发布流程，不能把研究 Agent 的临时摘要直接写成所有客户都能检索的资料。

**领导：**只读任务也要隔离？

**小陈：**要隔离可见范围和输出归属。只读不代表没有数据泄露，也不代表多个结果不会互相覆盖。客户 A 的合同读缓存命中客户 B 的条目，就是只读事故。权限与缓存策略要以真实业务主键为基础，不能只按自然语言查询做全局共享。

## 八、观测调度，至少能回答这六件事

我们要知道任务何时进入就绪、何时获准执行、何时开始调用工具、何时返回、何时通过验收、何时进入下游。时间点和任务身份共同形成运行轨迹。区分排队、执行、验证和业务等待以后，才能判断“慢”究竟在哪里。成本也按同一任务树归集，防止父任务的账看起来很便宜，子任务费用散在别处。

| 调度问题 | 必需记录 | 改进方向 |
| --- | --- | --- |
| 等谁最久 | 前置任务、排队与执行时间 | 缩短关键路径 |
| 谁抢配额 | 租户、资源类型、限流原因 | 公平限额与独立队列 |
| 钱花在哪 | 预留、实耗、重试与模型版本 | 删除无价值分支 |
| 为什么没启动 | 依赖、截止时间、预算拒绝 | 给出可恢复缺口 |
| 为何重复执行 | 任务 ID、尝试、派发事件 | 修去重与租约 |
| 哪个结果没用 | 接受或拒绝原因、草稿版本 | 收窄派发条件 |

日志无需默认存全部客户正文。任务元数据、资源等待、来源引用和错误类别通常已经能定位很多调度问题；需要查看敏感内容时通过受控路径展开。脱敏也要考虑派生信息与工具参数，不能只遮身份证而保留整份报价。观测是为了定位原因，不是把数据复制到另一个没有权限的地方。

## 九、把五十路收成一套能跑的策略

**领导：**最后到底开多少并发？

**小陈：**先按瓶颈配额和试点服务目标设置，不拍一个对所有步骤都适用的数字。本案例同时执行三个必需研究，模型请求经过组织配额，合同工具有独立资源槽。可选新闻低优先级，整体截止时间包含排队，预算先留给写作和验证。压力测试里逐步增加，并观察合格吞吐和长尾延迟。

**领导：**是不是并发一低就落后了？

**小陈：**能稳定完成合格任务才有意义。队列持续增长时，我们可以限流、缩小可选范围或扩充真实瓶颈；不能把排队改成五十个正在运行的 Agent，然后宣布并发能力强。系统忙与用户得到结果是两件可分别测量的事。

最终交付包括依赖图、必要性规则、资源配额表、预算账本与截止时间策略。它们共同决定任务能否开始、值不值得等、什么时候结束。下一篇在这套状态上继续：合同分支半路断电，发送工具超时却可能已经发出，系统怎样恢复而不重新制造事故。
