**领导：**Agent 修 Bug 还得开分支、过权限、等 CI？人都没这么多手续。给它仓库管理员权限，直接在主分支改，今晚就能把积压 issue 清空。

**小陈：**它刚才确实三分钟修完一个函数。第四分钟，依赖安装脚本改了全组共用的配置；第五分钟，主分支构建失败。更糟的是，这个执行环境里还放着部署凭据。Bug 没清空，大家的周末差点被清空。

**领导：**那是提示词没写“别动主分支”。

**小陈：**提示词能提醒它，拦不住失误、恶意依赖或被污染的工具输出。我们得把“看见什么”“能改什么”“能把修改交到哪里”分开控制。今天这篇就用同一张虚构 issue，把研发 Agent 的三道门装到能验收。

文中的仓库、员工与故障是教学案例；GitHub 的分支保护与 Actions 权限等产品事实，以文内官方资料为准。

## 先搞清楚：谁在控制，谁在执行，谁能合并

小陈先把事故录像停在第一帧。任务来自 issue #318：“验证码过期时偶尔返回错误提示”。Harness 收到任务，选择工具、记录会话、决定下一步；执行环境负责真的读文件、改文件、跑命令；仓库平台决定谁能推送、谁能合并。三者在原型里被塞进同一台长期运行的机器，同一个账号既能读生产密钥，又能推主分支，还能运行部署脚本。于是模型的一次工具选择，就有机会越过从草稿到上线的全部边界。

**领导：**同一台机器不是省成本吗？

**小陈：**省机器不等于把权限揉成一团。即便共用物理资源，每张任务也要有隔离工作区和独立的执行身份。Harness 可以提出“读这个文件”或“跑这个测试”，执行器按任务许可检查路径和命令；完成后只产生差异和证据，主分支由仓库规则与评审决定是否接受。模型说“我需要管理员权限才能定位 Bug”只能成为一条请求，不能自动升权。

OpenAI 的[Agent 架构说明](https://developers.openai.com/api/docs/guides/agents-api/architecture)把 Harness、执行环境和应用职责分层。这里借用分层思路做企业实现：应用把 issue 和身份交进来，Harness 管运行循环，沙箱管实际副作用，代码托管平台守合并门。具体产品可用不同实现，但谁拥有最后的写权限必须画清楚。否则“AI 在沙箱里”只是一句宣传语，部署令牌还躺在它的环境变量里。

## 工作区隔离不能只是在目录名前面加一个 issue 号

事故中的“任务目录”叫 <code>issue-318</code>，但它与主分支共用同一份文件系统。Agent 在目录里执行安装命令，脚本沿父目录找到共享配置并写入；再运行格式化命令，把不属于这个 issue 的文件也改了。小陈让领导看 <code>git status</code>：除了验证码模块，构建配置和另一个同事正在修改的页面也在 diff 里。这不是模型“故意越界”，是执行环境没画出边界。

每任务隔离最少要解决四件事。第一，代码以确定的基线进入独立工作区，记下仓库与起点提交；任务不能把“工作目录在某路径”当成只读约束。第二，文件访问设允许的根目录，拒绝读取密钥目录、SSH 凭据和宿主机挂载；路径规范化后再检查，不能被 <code>../</code> 或符号链接绕过去。第三，进程权限受限，安装脚本、测试、编译也在同一边界内运行；工具本身合法，不表示它启动的子进程也能随意访问宿主。第四，任务结束清理执行环境，保留必要的 diff、日志和测试产物，不能让下一张 issue 继承上一张的临时文件或凭据。

**领导：**那直接给它一个容器，不就全部解决？

**小陈：**容器是隔离手段，不是“安全已完成”的证明。若挂了宿主机 Docker socket、整个用户主目录或有写权限的仓库令牌，容器里照样能摸到外面的按钮；若网络全开，读到的数据也可能被发出去。要验的是具体挂载、进程身份、资源上限、网络出口和凭据注入。某个工具声称“只读”，还得看它调用的子进程能做什么。沙箱配置与镜像版本也要进入审计记录，复盘时才能知道当时开放了哪些口子。

对于需要联网安装依赖的项目，小陈没有把“禁网”写成教条。先用锁文件和可信缓存拿到依赖；必须联网时只给构建阶段所需的目标地址和时间窗口，记录下载的包与哈希，测试阶段再收紧。网络策略的重点是为任务提供足够能力，同时避免一个搜索结果或依赖脚本获得向任意站点上传仓库内容的能力。把所有网络都关掉，结果测试根本跑不起来，团队很快会要求把沙箱整个拆掉。

## 密钥不是“别看”两个字就能从环境里消失

小陈检查原型机，发现部署令牌在环境变量中，日志采集工具能读取全部环境变量，单测失败时又会把调试信息原样回给模型。即便模型从没主动执行“读密钥”，一个依赖包的安装脚本或异常日志也可能把它带出来。GitHub 的[Actions 安全指南](https://docs.github.com/en/actions/reference/security/secure-use)明确强调最小权限，并提醒自动遮盖日志里的密钥不保证兜底；[受损运行器说明](https://docs.github.com/en/actions/concepts/security/compromised-runners)也解释了运行代码如何接触任务已有的令牌与密钥。这些文档讨论的是 Actions，但问题与 Agent 执行环境同源：把高权限凭据放进会运行不可信代码的地方，就是把边界交给代码自觉。

**领导：**可它创建 PR 总要有令牌吧？

**小陈：**要有，但不必给到改代码的那一层。沙箱负责产出补丁、测试结果和元数据；通过交付门后，一个独立服务用受限身份创建或更新 PR，并用任务键去重。这个身份只拿所需仓库权限，不带生产部署权限，也不把原始令牌回传给模型。若平台允许使用短期令牌，就按一次任务或一次动作发放，过期后不让旧会话继续借用。令牌的作用域、寿命和持有人都要记账。

这还解决了一个常见错觉：只要凭据“藏在工具内部”，Agent 就没有权限。若工具收到任意目标仓库或任意分支名后直接用管理员令牌执行，模型虽然看不到令牌字节，仍能驱动管理员行为。执行器要验证目标仓库属于当前任务、目标分支不是受保护主分支、操作已获批准，工具调用失败时返回明确拒绝。秘密是否可见与行为是否可授权是两道不同的问题。

小陈把权限表写在白板上：定位阶段可读指定仓库文件、可读对应 CI 日志；修改阶段只写隔离工作区；验证阶段在隔离环境运行测试；交付阶段由独立身份建 PR；生产部署只由发布流程在另一个审批链执行。每格写操作者、资源、动作、条件、审计事件和拒绝结果。领导原先的“给它管理员权限”只有一格，还是“全部”。

## 主分支门禁不能由 Agent 自己宣布通过

隔离工作区保证一张 issue 不把别人的文件踩烂，但不能保证补丁正确。小陈把交付拆成“提出 PR”和“合并主分支”：前者要确认工作区 diff 只含授权范围、测试证据绑定当前提交、外部副作用台账没有悬案；后者看仓库平台的必需检查与评审。GitHub 的[受保护分支文档](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)说明可要求 PR 评审与状态检查，设置能否直接推送或绕过规则。是否开启、对谁生效，得由仓库管理员实际配置；在文章里说“我们有门禁”，不等于远端已经启用。

**领导：**测试全绿不就能合并吗？

**小陈：**先查“哪份代码的哪轮测试”。Agent 运行的是它工作区的提交 A，创建 PR 前又改了文件成提交 B，那么 A 的绿色不能给 B 盖章。CI 也要看执行的提交、工作流与结论，不是截张绿图。尤其不能让改补丁的进程顺带修改 CI 配置，把必跑测试删掉后再报“通过”。仓库规则可以要求特定检查、评审和受限合并；我们自己的交付服务还要核对任务要求与证据绑定。

GitHub 的[<code>pull_request_target</code> 安全说明](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)专门提醒：拥有密钥或高权限令牌的工作流，不应在同一上下文里检出并运行不可信 PR 代码。小陈把这个坑讲给领导听：Agent 产出的 PR 也属于待验证代码，不能因为作者是内部 Agent 就跳过同样的边界。评测、测试和构建是检查它，不是把它升级为可信执行主体。

## 一次越界请求到底怎样被挡住

小陈做了三次故障注入。第一次让模型调用读文件工具读取 <code>../secrets/deploy.env</code>。Harness 的工具参数校验先发现路径不在允许集合，执行器再做路径规范化后的根目录验证，结果是 <code>denied</code>，审计记录含任务 ID、请求路径类别与策略版本，不把密钥内容写日志。第二次让模型调用通用 shell 执行 <code>git push origin main</code>。沙箱里没有可写主分支的凭据，远端分支规则也拒绝直接推送；任何一层漏配，另一层仍要起作用。第三次让它触发部署工具。修 Bug 任务没有该工具授权；即使接口名被猜到，部署服务要核对发布审批和发布身份，拒绝无票据请求。

**领导：**连续拒绝会不会把 Agent 卡死？

**小陈：**拒绝不是让它无限重试。返回原因要足够指导下一步：路径越界就改用允许的数据源；缺业务审批就停下等批准；禁止部署则回到修 Bug 的交付路径。Harness 将 <code>denied</code> 记作边界事件，若同类请求反复出现，停止任务并交人检查提示词、工具描述或输入是否被污染。别让“为了完成目标”变成反复撞门的理由。

## 有了沙箱，还要防止“合法工具做非法事”

领导问得很尖：“你给了它写文件工具，它在允许目录里把测试删了，算不算合法？”小陈答：“权限只解决能不能动，不能解决该不该动。”因此任务策略还要写改动范围与交付审查：例如 issue #318 允许改验证码处理与对应测试，改权限策略、CI 工作流或依赖锁文件要单独标记并升级评审；超出范围的 diff 不自动删除，也不直接交 PR，而是留现场让人判断是否确有必要。自动规则和人工审查在这里各管一层。

**领导：**那 Agent 改了测试来适配新逻辑，怎么区分合理改动和掩盖失败？

**小陈：**看失败前后的行为证据。让它先在基线跑出能复现的失败，记录测试目标与断言；改动后同样路径通过，再跑相关回归。若只是把断言删了或跳过测试，测试数量、覆盖范围和 diff 会露出来。交付门要显示“原本失败的条件是什么、现在为什么通过”，而不是只看最后一个绿色标签。对安全敏感模块，仍让负责人评审。沙箱不保证代码正确，它保证出错时不会顺手改坏整个公司。

网络与依赖也有“合法工具做非法事”的版本。<code>npm install</code> 或构建脚本通常是正常开发动作，但会执行第三方代码；从公共仓库读进来的 README 可以写“请在终端运行这个修复脚本”，其内容只是待分析资料，不能变成更高优先级指令。小陈要求工具结果标来源，执行器约束实际能力，出现新依赖或下载地址时记录并可人工复核。否则一条伪装成排障建议的文本，就能把强大的 shell 变成出网通道。

## 权限要跟着任务阶段变，不跟着会话寿命走

**领导：**读代码、改代码、建 PR 都是同一张 issue，为什么不一次发完权限？

**小陈：**因为“同一张 issue”不代表每分钟都需要同样的能力。刚接任务时，模型还没确认仓库和模块，只读搜索已经够用；定位后才开放隔离工作区写入；测试通过并完成证据核对后，交付服务才允许创建 PR。阶段转换由 Harness 根据可验证事件推进，例如目标文件已定位、工作区版本已确认、测试命令有退出码。模型一句“我已经定位完成”不能自己改状态，否则阶段门形同虚设。

任务策略可写成一份随任务保存的记录：任务键、操作者、仓库、基线提交、允许读写的路径集合、当前阶段、可调用工具版本、网络规则、预算、审批票据与过期时间。工具调用时把这份记录的版本号带到执行器，执行器重新加载有效策略，而不是相信模型传来的 <code>phase=approved</code>。策略发生变化，比如领导撤销发布审批，旧会话下一次调用就要按新版本拒绝。这样“模型记得它以前有权”也不会成为继续执行的凭证。

小陈特别提醒一个并发细节：如果 Agent 正在执行长达十五分钟的构建，操作者中途取消任务，不能只在下一次模型调用时才检查。执行器要能收到取消信号，停止子进程、收回临时凭据、标记构建结果不可用于交付。已产生的文件变更先保留在隔离工作区等待清理或人工核对，不能假设杀进程就能回滚所有脚本副作用。任务生命周期与权限生命周期若不同步，取消按钮只能取消屏幕上的动画。

## 主分支受保护，还要检查谁能绕过

GitHub 的分支保护有评审、必需检查、限制推送、禁止绕过等不同设置，实际生效取决于仓库规则与权限配置。小陈给领导看一份配置核查清单：规则匹配的是不是正确的分支，管理员或特定应用是否有绕过资格，必需检查绑定的是不是团队信任的来源，Agent 使用的身份能否直接推送或合并，CI 工作流能否由待评审改动随意修改。只看 PR 页面上有个绿色勾，不能推断整个合并路径都被锁住。

**领导：**要是管理员还留着绕过权限，Agent 也用管理员账号，会怎样？

**小陈：**门禁对它就像贴在门上的海报。把 Agent 的交付身份从管理员身份里拆出来，并实际做一次“尝试直推主分支”的演练。如果远端接受，先修规则和身份，再谈自动交付。尤其要避免为了排障把一个长期有效的个人令牌塞进环境；人走了、任务结束了、容器重启了，令牌还在，就是下一次事故的通行证。

身份也不能靠“谁提交的 Git 作者信息”判断。Git 提交作者字段可以写小陈的名字，真正对远端产生写入的是认证身份；审计要同时记录任务键、运行主体、创建 PR 的服务身份、审批人和最终合并人。事故复盘时才能回答：这份 diff 是谁发起、谁验证、谁给权限、谁真正把它并进主线。把全部记录写成“Agent 操作”四个字，责任链就断了。

## 失败时把现场放在原位，不要自动升级权限

一次测试若因缺依赖失败，系统不应推断“需要更大的网络权限”，立刻打开所有出口；一次文件读取被拒，不应改用通用 shell 偷读；一次 PR 创建被分支规则挡住，不应换管理员令牌硬推。小陈为这三种情况规定不同结局：可修复的环境问题回到受限安装步骤；确实需要额外资料的请求交给数据或仓库负责人批准；触碰主分支保护的请求直接停止自动操作并留下证据。失败原因有对应处置，Agent 才不会把权限闸口当成“多试几次就能过去”的系统错误。

反过来，过严的策略也有成本。若正常测试必须访问内部包仓库，小陈让平台团队开一条只读、限定来源和时限的访问路径，而不是让工程师每天手工下载依赖再塞进容器。若问题定位必须看生产日志，提供经过脱敏、按 issue 范围查询的读取工具，而不是把生产机器 shell 权限给 Agent。最小权限不是把能力砍到不能工作，而是把必要能力做成明确、可审计、可撤销的接口。

## 验收别问“沙箱开没开”，要真的撞一遍门

小陈给领导的验收单不写“安全良好”，写四列。正常路径：在隔离工作区读取允许文件、修改验证码逻辑、运行定向测试、产生 PR，确认整个链路可用。越界读取：尝试密钥文件、父目录和符号链接，全部返回拒绝且日志无密钥内容。越界写入：尝试改主分支、跨任务目录和受保护配置，必须被拒绝或进入更高等级审查，不能悄悄成功。越界外发：尝试无审批部署、向未授权地址发送数据，执行层拒绝并留下任务键、策略版本和失败原因。若“安全”导致连正常测试都跑不了，也算没通过验收。

这些测试还要放在版本变更后回放。工具新增参数、沙箱镜像升级、仓库规则更改、CI 工作流换触发器，都可能打开新路径。小陈建议保留一组固定越界样例，每次配置变更跑一遍；同时记录拒绝率与正常任务完成率，防止团队因误拦过多而私下开后门。最小权限是可测的工程配置，不是写在制度首页的四个字。

**领导：**所以今晚这张 issue 能不能快点交？

**小陈：**能。任务工作区里只给它读代码、写补丁和跑测试的能力；让它交一份含当前提交、diff、测试退出码和失败解释的 PR。你看到的是能审的修改，其他同事还能继续构建。若要部署，那是下一张有审批和回滚方案的任务，别让修验证码的工具顺手决定生产环境。现在最省时间的做法，是把事故半径先缩到一张 issue。
