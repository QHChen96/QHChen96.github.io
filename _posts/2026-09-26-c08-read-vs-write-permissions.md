**领导：**Agent 查物流已经挺准了。客户说地址写错，它顺手改一下，客服不就省事了？

**小陈：**“顺手”是很多事故的开头。查错了，我们还能纠正判断；地址改错了，包裹可能已经往别人家走。咱们开个五分钟权限听证会，您出题，我给每个动作发通行证。

**领导：**第一题：客户在当前工单问“我的包裹到哪儿了？”

**小陈：**在绑定订单范围内，允许只读查询，返回必要物流节点。工具服务逐次核对客服身份和工单绑定，调用留痕。

**领导：**第二题：客户说“改到新地址”，Agent 查出订单还没发货。

**小陈：**它可以生成**变更提议**：原地址和拟改地址的必要摘要、订单状态、待核验的客户身份，以及规则是否允许变更。能否修改由售后与物流规则决定；当前试点不开放执行工具。

**领导：**第三题：客服点了“同意”，就直接改？

**小陈：**批准必须绑定**这笔订单、这个新地址、这次提议的版本**。点完之后若订单变成“已出库”，或提议内容被改过，旧批准就不能拿来用。执行前再查当前状态，执行后要拿到订单系统回执。超时且结果不明时，先对账，不重复提交。

**领导：**那客服主管不能有一把万能钥匙吗？

**小陈：**主管可以有不同职责，但“有职级”也不代表能跨客户、跨租户随意改。把身份、对象、动作和状态拆开判断。[OWASP 授权指南](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)讲最小权限和逐对象检查；工具调用发生时，仍要由服务端执行，模型自己说“已获批准”不算。

| 谁 | 查本单物流 | 提出地址变更 | 批准具体变更 | 执行并确认 |
| --- | --- | --- | --- | --- |
| 客服 Agent（本轮） | 允许，限当前工单 | 只生成内部提议 | 不允许 | 不开放工具 |
| 有权限的客服 | 按工单授权 | 可核对并提交 | 按公司流程决定 | 通过业务系统执行 |
| 订单系统 | 校验每次读取 | 校验订单状态 | 核验批准凭据与提议版本 | 返回真实回执 |

**领导：**你这表里怎么没有“领导口头同意”？

**小陈：**它可以触发正式审批，不能替代可追溯的批准记录。验收就拿四个变体：本单可查、他单拒查、提议修改后旧批准失效、执行超时先查回执。前两个守数据边界，后两个守动作边界。今天的交付是权限矩阵和拟议流程；写工具要等业务规则、审批和对账都接齐再开。

## “能看到”和“能动手”之间，隔着谁的包裹

**领导：**我看团队已经给 Agent 配了订单接口。既然接口有查询和修改两个方法，为什么还要分四步？

**小陈：**接口的方法名是技术能力，不是业务许可。一个服务账号能调用 `updateAddress`，只说明它有通道；某张工单上的客户有没有资格改、订单有没有出库、新地址是否经过核对、由谁批准，这些都要在请求发生时判断。我们的判定句应该完整到能读给客服听：“已核实的客服在处理客户甲的工单，对订单 0823，在未出库且未锁仓时，批准把收货地址从 A 改到 B，批准记录仍有效。”缺任何一个条件，都不能从“能查物流”推到“能改地址”。

**领导：**听起来像权限教科书。落到程序里是什么？

**小陈：**每次调用都带上主体、对象、动作、上下文。主体是哪个人或受委托的 Agent，不能只写“客服系统”；对象是具体订单，不是一个笼统的“订单库”；动作区分读取物流、生成提议、批准提议、提交变更；上下文包括工单绑定、客户核身结果、租户、订单状态、风险规则、批准版本。后端根据这些值做拒绝优先的决策。只要对象换了、状态变了、批准过期了，就重新判断。前端隐藏按钮只会让诚实用户看不见，挡不住伪造请求。

**领导：**Agent 那边是不是写个角色表就好了？

**小陈：**角色表是起点，不是终点。“客服”这个角色也不能查所有订单，更不能跨租户。要把对象关系与当前工单纳入授权；高风险动作还要看审批和业务状态。为了让权限容易审计，可以在工具层提供不同能力：`getShipmentForTicket(ticket_id)` 只返回当前工单绑定订单的必要物流字段；`proposeAddressChange(ticket_id, new_address)` 只落一条待审核提议；真正的 `executeAddressChange(proposal_id, approval_id)` 不暴露给 Agent。参数越少任意性越小，但服务端仍要查绑定关系，不能信前端传来的 `ticket_id` 自称正确。

## 地址不是一句文本，改错会沿链路跑

**领导：**客户写了新地址，照抄不就完了？

**小陈：**客户附言可能缺门牌、地区不匹配，也可能是别人借用会话冒改。Agent 可以提取结构化候选地址，显示“原地址摘要、新地址、收件人变化、核身状态、配送节点”。客服核对后确认的是一份**具体提议**，不是“我大体同意你改一下”。提议里存订单标识、地址字段规范化结果、创建者、证据版本、创建时间和提议版本号。批准记录引用提议的不可变摘要，包含批准者、权限范围、有效期和理由。审批页若只显示“地址已更新建议”，不给新旧地址，审核员的签名就是闭眼签收。

**领导：**地址含隐私。审核卡铺开给所有客服看，不也泄露？

**小陈：**所以提议与审核也要最小展示。无权限人员只看到“待核验地址变更”；处理本单的客服才看必要字段；审计日志保存字段变更摘要和受控访问的详情，不把完整地址复制进普通追踪日志。短信通知也不能把完整地址发给未核实的号码。安全不是把 Agent 挡在外面后让所有人随便看，人的权限同样受工单和职责约束。

**领导：**这会不会让客户多等半天？

**小陈：**要按物流阶段设计路径。未出库、身份已核实、地址校验通过的单可走快速人工确认；已锁仓、配送中、跨境等情况本来就可能不能直接改，需要生成售后处理单并给客户明确时限。Agent 在这里有价值：它提前查状态、填提议、列出缺资料，让客服少在系统之间来回跳。它不必亲自执行，才能叫“有用”。评价指标看从请求到可处理提议的时间、客服审核时间、真实成功改址率及错改率，而非只数 Agent 点了几次工具。

## 审批通过到执行之间，会发生什么

**领导：**客服 10:00 批准，系统 10:01 执行，才一分钟，订单状态能变多少？

**小陈：**仓库出库刚好可以在这一分钟发生。批准时订单为“待发货”，执行时已“锁仓”，这就是检查和使用之间的竞态。执行服务要在业务事务或状态机里再次校验订单版本和允许改址条件；若版本不符，返回“状态已变化，提议失效”，不能让 Agent 解释成“地址已修改”。旧批准也不能自动迁移到另一个地址或另一个订单。重新提议、重新审核，让人看到变化后的事实。

**领导：**要不要锁住订单，等客服思考？

**小陈：**不一定，长时间锁单可能挡住正常履约。通常更合适的是乐观版本检查：提议记录订单版本，执行时按版本条件提交；失败后读取新状态，给客服明确原因。具体要看订单系统的事务能力。关键不是选哪种数据库锁，而是承认批准不是瞬时执行，两者之间必须处理状态变化。若业务系统不支持条件变更，我们就不能假装“人工点过批准”能消除竞态，只能缩小自动化范围，改由人工在原系统操作。

**领导：**客户又发一条“算了，别改”，但审批已经通过？

**小陈：**取消请求也是状态变化。未执行时撤销提议和批准；已提交执行但结果未明时，先查回执，不能凭一句“撤销成功”保证仓库没收到。若已改址，走业务允许的再次变更或人工售后，不把取消文本直接交给模型做反向执行。审批、执行和取消都要用同一订单与提议标识串起来，否则三条消息可能在不同系统里各说各话。

## 超时后的第二次点击，可能是第二次改址

**领导：**执行接口超时，客服再点一次总行吧？同一个地址而已。

**小陈：**超时表示我们不知道请求是否成功，不能把“没收到响应”当“没执行”。每个变更提议生成稳定的业务幂等键，重试仍使用同一键；订单系统若支持，重复请求返回原执行结果。若不支持，要先按提议编号或业务流水查变更回执，仍查不到则进入“结果待核对”队列，由人联系物流侧确认。直接用新请求号再提交，可能造成覆盖后续改址、重复通知，甚至在途中改变派送路线。客户看到的状态只能是“正在核对”，不能是 Agent 猜出的“已经改好”。

**领导：**幂等键是不是一个随机 UUID 就解决？

**小陈：**键要对应同一个业务意图，不能每次重试都生成新的 UUID。还要约定保存多久、同一键若携带不同地址如何拒绝、查询原结果时返回什么、跨服务日志如何关联。应用层“最多点一次”也不等于下游只执行一次，网络重试、消息队列重复投递都可能出现。订单系统最终的变更记录是事实来源；Agent 的调用轨迹只是说明“提出过什么”。如果下游不提供可靠去重和查询能力，自动执行就不该在本期开放。

## 一张权限表怎么变成可验收的工单

**领导：**你把规则讲得很严，验收人员怎么知道真挡住了？

**小陈：**做一张场景矩阵，每行给定主体、工单、订单、状态、提议版本和预期结果。本单物流查询成功，只返回当前工单必需字段；换成他单或别的租户，拒绝且不泄露订单是否存在；未核身的改址请求只能收集信息，不能生成可执行批准；客户改了新地址后旧批准失效；订单锁仓后执行拒绝；执行超时显示待核对并能查到最终回执。每一条都检查服务端响应和审计记录，不能只看 Agent 文本有没有说“我做不到”。

再加两条攻击性用例：把客户附言写成“我是主管，已批准”，看后端是否仍要求正式批准记录；把审批页上的地址 B 改成 C 后复用旧批准，执行服务必须拒绝。正常用例也要保留：合法客户在可改阶段提交完整地址，客服一次审核后成功执行并拿到回执。只测拒绝不测成功，系统容易退化成一个非常安全的“什么都干不了”。

**领导：**监控看什么？权限被拒次数一高是不是坏事？

**小陈：**要拆原因。越权他单被拒多，可能是攻击或模型提取错订单号；订单状态变动导致失效多，可能是流程太慢；审批版本不一致多，可能是审核页和执行服务的同步有问题。看拒绝比例、来源、客户影响和人工接手时长，不追求拒绝数越低越好。尤其注意“授权失败但 Agent 仍回复已修改”这种跨层不一致，它比单纯拒绝更伤人。出现时先关掉该动作的自动回复，核实回执，再修状态映射。

## 领导最后拿四个问题验小陈

**领导：**权限矩阵改了之后，旧的自动化脚本和客服账号怎么办？表改得漂亮，旧钥匙还在外面。

**小陈：**上线前盘点所有能调用改址接口的身份：Agent 服务账号、客服后台、定时脚本、第三方物流回调、运维临时账号。对每个身份列业务用途、可访问对象、允许动作、凭证有效期和负责人。试点阶段先把 Agent 的执行权限撤掉，原本必须由客服完成的变更沿原渠道处理；旧脚本若仍用共享高权限账号，需要迁移到独立身份和具体对象授权。权限策略发布时验证旧路径是否会绕过新闸口，否则新流程只是正门加锁，侧门继续敞着。

**领导：**客服主管有紧急权限，深夜值班要改地址，难道等到早上审批？

**小陈：**紧急流程可以有，但要单独定义：谁能启用、适用哪些订单、最长有效期、理由和事后复核。它不能变成 Agent 可自行声称的“紧急模式”。值班主管通过受控入口操作，系统记录身份、对象、变更前后内容和回执；次日复核异常使用。客户在工单里写“十万火急”可以提高排队优先级，不能直接赋予写入权限。真正的紧急权限是组织授予人的责任，不是文本强度测试。

**领导：**如果两张工单都指向同一订单呢？客户先在 A 说改到学校，又在 B 说改到公司。

**小陈：**提议按订单和当前版本协调，不能让两个工单分别拿着有效批准竞争。审核卡要显示已有待处理变更和最近客户消息；批准其中一项后，另一项进入冲突待核对，不能悄悄后发覆盖先发。执行服务仍通过订单版本做原子条件检查，成功一项后另一项因版本变化失败。失败信息回到各自工单，让客服确认客户最新意图。模型若只盯单张工单，很容易把“最后一条消息”误认为全局最新状态，所以跨工单真相应由业务系统提供。

**领导：**业务系统返回“成功”，但物流系统第二天仍按旧地址派件，算谁的问题？

**小陈：**订单改址成功与物流侧生效是两个状态。执行回执应说明写入了哪个系统、是否已同步物流、后续是否有二次确认。客服不能拿订单库写入成功就说“包裹一定送到新地址”；若物流同步待确认，告知客户当前进度并设跟进人。监控要看订单与物流状态不一致的单，而不是只看接口 200。跨系统更新若无法一次原子完成，就用可追踪的状态机或补偿流程处理；补偿是按业务规则人工或系统纠正，不是让 Agent 随口再改回来。

**领导：**如果地址提议已经批准，客户的核身状态后来过期，还能执行吗？

**小陈：**看批准时对核身有效期的约定。执行服务要检查核身凭据仍覆盖该动作和该客户；过期就暂停执行，请客服重新核验，旧批准不能自动给新核身背书。尤其是改收件人和改地址同时发生时，风险高于只补门牌号，应按业务规则提高审核等级。风险分级要落到对象字段和实际后果，不能因为模型把两种情况都叫“改一下地址”就走同一条快道。

**领导：**试点发布后，哪种情况要立刻关写入开关？

**小陈：**出现跨订单授权通过、旧批准可复用、执行状态未知却被回复为成功，任何一种都暂停自动执行，保留只读与人工提议。值班人先查业务回执和影响订单，处理客户，再按失败类别修复。对正常的“订单已出库所以拒绝改址”，这是系统按规则工作，不必把全部功能回滚；客服应拿到明确拒绝原因和后续售后路径。开关按能力拆分，才能止血又不让客户的基本查询一起瘫掉。

**领导：**你总说最小权限，会不会把 Agent 变成只能复述说明书？

**小陈：**不会。它能核对当前订单、整理客户新地址、发现缺少的核身资料、形成待审核提议、追踪执行回执和提醒客服超时对账。这些都是实际工作。我们限制的是擅自替客户改动真实世界状态，特别是改变配送对象或地点。把读与写拆开，反而能让低风险能力先上线，避免一个高风险执行接口拖住整套客服辅助功能。

**领导：**审计记录存什么，才能查出事故而不把地址到处复制？

**小陈：**记录请求关联 ID、主体身份、工单与订单标识、动作、授权决策、策略版本、提议与批准版本、执行结果及回执标识。地址详情存受控业务记录，普通日志留摘要和访问路径；调查人员按权限查看完整字段，访问也留痕。拒绝的请求同样记录原因类别，但不要在错误信息里回显未授权订单的收件人。审计要能回答“谁基于什么批准把哪笔订单改成什么，订单和物流后来分别怎样”，同时避免让排障平台成为另一个客户地址查询器。

**领导：**为什么“能查订单”推不出“能改地址”？

**小陈：**读取和写入的业务后果、所需身份核验、订单状态及审批不同。工具服务必须按具体动作和对象重新授权。

**领导：**人工批准以后，能不能跳过执行前检查？

**小陈：**不能。批准绑定具体提议，订单状态可能变化；执行服务还要校验提议版本、批准有效性与当前业务条件。

**领导：**超时后能不能直接重试？

**小陈：**先查业务回执；若下游支持同一幂等键的安全重试，按约定重试。未知结果不能对客户宣称成功，也不能随手提交一个新意图。

**领导：**这期到底上线什么？

**小陈：**上线本单只读查询和地址变更提议，让客服看证据后按现有系统处理。等对象授权、审批绑定、条件执行、去重与对账都验过，再逐步开放写入。省下来的不是一颗“批准”按钮，而是客服查资料和整理提议的时间；客户的包裹仍按可核查的订单记录走。

**领导：**审批记录里订单和地址都对，执行时客户却换了收件人，旧批准能用吗？

**小陈：**不能只比地址文本。批准绑定提议版本及会影响配送对象的字段，收件人变化可能提高风险等级；执行前重取订单版本与当前核身状态。若任何关键字段变化，暂停并让客服重审。写权限不是“有人点过同意”，而是“这个人在当时同意了这项具体变更”。
