**领导：**小陈，我要三个 Agent：一个查客户资料，一个算报价，一个写邮件。既然都叫 Agent，就让它们自己商量顺序，谁先干完谁先交。智能嘛。

**小陈：**报价没审核就写进邮件，是“先交”的一种；只是客户和法务都不太喜欢。三个任务有硬依赖：先确认客户与商品，再取有效价格和折扣审批，最后才可起草对外文字。独立的资料查证可以并行，报价批准不能并行跳过。Google ADK 把能用模型选择工具的 LLM Agent 与预先定义执行顺序的工作流 Agent 分开。模型做开放式查证，工作流管谁先谁后；这样快的地方并行，不能越的地方排队。

**领导：**名字都带 Agent，工作流 Agent 是不是也会思考？

**小陈：**这里的 Agent 更像“可放进 Agent 树里的执行单元”。[Google ADK 官方工作流说明](https://adk.dev/agents/workflow-agents/)把 `SequentialAgent`、`ParallelAgent`、`LoopAgent`列为模板工作流 Agent：它们按预定义逻辑控制子 Agent 的执行，编排本身不向模型咨询。子 Agent 可以用模型，整体次序却是程序规定的。文档同时说明，ADK 2.0 在 Python、Go 上更推荐图式和动态工作流；本文仍拆这些明确的模板类，因为理解“顺序、并行、循环谁负责”是设计新图的基础，实际项目须按所用语言和版本核文档。

## 先画依赖，别先数 Agent 数量

虚构工单是向客户甲报一套年度软件服务：客户有历史合同、公开需求邮件、销售给出的产品范围、报价系统里的标准价，某项折扣仍待主管批准。可并行查的是客户资格和产品可交付范围，前提是两边都拿同一商机 ID；必须串行的是报价计算之后的审批状态检查与客户邮件草稿。销售经理最终批准邮件前，系统只允许生成内部待审草稿。若让模型自由委派所有任务，写稿 Agent 可能先根据旧合同估个价，再被报价 Agent 的新价打脸；发出后再纠正，就成了“本公司价格以第二封邮件为准”的经典笑话。

小陈用任务图约束：输入先通过身份与商机归属校验；之后客户背景查证与产品范围核对可以并行；汇合时校验两份结果同属该商机、版本有效；报价服务按规则计算并读折扣审批；未批准则停止在内部待处理，批准后才让文案 Agent 写邮件草稿；草稿审核通过再由业务系统外发。图中每条箭头都有事实含义：下游必须拿到上游的特定输出，而不只是等一个 Agent 说“完成”。

**领导：**`SequentialAgent` 不就是依次调用三个子 Agent？写一行不就完了？

**小陈：**一行定义顺序，没定义数据合同。[官方顺序工作流文档](https://adk.dev/agents/workflow-agents/sequential-agents/)说子 Agent 按列表次序运行，共享同一 `InvocationContext` 与会话状态，示例通过 `output_key` 把前一步结果写入 state，供后一步读取。我们的三步也需明确定义键：客户核验写 `customer_check`，报价步骤读取它并写 `approved_quote`，文案步骤只能读取 `approved_quote` 而不能偷看原始邮件里“我觉得老板会批”这种未认证说法。若第一步没有有效客户，第二步不得把空值当默认；若报价状态是 `pending`，第三步根本不应得到可外发文案任务。

状态里的字段要有来源和生命周期。`customer_check` 不只存一句“已核实”，还应有业务服务回执、客户 ID、商机 ID、核验时间；`approved_quote` 要有币种、税费口径、金额、折扣批准人、有效期和版本。模型生成的摘要可以帮助下一步读懂事实，但金额与审批状态必须来自报价系统。若两个 Agent 都能覆盖同一个 `quote` 键，后者写入“预计价”可能冲掉前者的正式价。命名空间与只读引用不是代码洁癖，而是在 Agent 多了以后保持谁说了算。

## 并行能缩时长，也能制造竞态

**领导：**客户背景和产品范围两件事可以同时跑，`ParallelAgent` 不就稳赢？

**小陈：**在任务独立时能缩等待时间。[官方并行工作流文档](https://adk.dev/agents/workflow-agents/parallel-agents/)说子 Agent 并发运行，各自执行分支没有自动共享对方的对话历史或状态；若要共享状态要显式设计，还须处理并发访问。我们给两支只读的输入快照：同一商机 ID、同一请求时间与同一权限上下文；一支返回客户资格证据，另一支返回交付范围证据，分别写不同结果键。汇合节点检查两支都完成、都没有越权、都引用相同商机。千万别在两支里同时更新 `approved_quote`，然后指望运行快的那支“赢得比较正确”。

并行也不是“把所有节点横着摆”。报价需要产品范围才能算，就不能跟产品范围核对并行；审批需要报价请求 ID，就不能与报价计算并行。若做错，程序可能没有显式报错，只是写稿 Agent 用了某个尚未更新的旧 state。并行是否安全，先问“若 A 还没完成，B 能否凭自己手头的信息得出稳定结果”；若不能，就要画箭头。对真正独立的查询，延迟取决于较慢的一支加汇合开销，不等于两支耗时相加；但总资源消耗仍可能增加，两支同时查同一服务也可能触发限流。

**领导：**并行一支成功一支超时，我先用成功的那份写邮件行不行？

**小陈：**看缺的是不是必要事实。客户背景若只是帮助称呼个性化，缺了可用中性称呼，但仍要核基本客户身份；产品交付范围若没核实，报价依据不完整，必须停止。汇合节点要有必需字段清单，而不是“至少有一个 Agent 交卷”。成功支的结果可以暂存，失败支按可重试条件补查；重试时使用同一商机 ID 和版本，若背景数据在等待期间发生变化，汇合前重新核时效。状态从 `parallel_running` 到 `partial`、`ready`、`failed` 必须可见，不能把未完成的并行当成全完成。

## LoopAgent 适合改草稿，不适合反复试审批

文案常需两轮：写稿、检查是否引用了批准价、是否包含未经确认的承诺；不合格就修订。`LoopAgent` 可以把写稿与校验两个子 Agent 反复执行，并设最大次数。[官方 Loop 文档](https://adk.dev/agents/workflow-agents/loop-agents/)明确说循环本身不智能决定何时结束，开发者必须提供退出机制，例如最大迭代或子 Agent 发结束信号。我们设置最多三轮，且通过条件是“草稿金额与已批准报价一致、附件引用有效、禁用承诺不存在”。第三轮仍不通过，就把错误原因交给销售；不要把三次耗尽的草稿标成已审核。

**领导：**我让循环一直试到审批通过，不就全自动了？

**小陈：**审批不是模型采样题，反复试只会变成骚扰。折扣未批准时，不应通过换措辞或重建报价请求让系统放行；它应该进入业务等待状态，待有权限的人在报价系统批准后，以新的回执恢复流程。Loop 适合对同一已批准事实改进文本，不适合重复外部副作用。即便文本循环也要限制 token、时间和总成本，停止条件由独立校验器执行，不能由写稿 Agent 给自己打分说“我觉得挺好”。若把模型生成的 `quality=1.0` 当作唯一退出条件，Agent 三轮中至少一轮会夸自己，工作流便成了自我表扬大会。

## ADK 的 state 和 event，哪个是事实账？

**领导：**顺序、并行、循环会组合成一棵树。失败时我看哪儿知道到底走到哪？

**小陈：**要区分运行事件与业务状态。[ADK 运行事件循环文档](https://adk.dev/runtime/event-loop/)描述 Runner、Agent、SessionService 的关系：Agent 产生事件，Runner 接收并把事件追加到会话；事件可带状态变化。一个 invocation ID 可串起同次调用里的多个子 Agent、模型和工具执行。会话 state 方便后续步骤读取 `customer_check`、`approved_quote` 等键，事件流方便回放“谁何时写了什么、调用了哪个工具、哪一步报错”。但企业的报价批准、邮件发送、CRM 更新仍以各自业务系统回执为准。把 ADK 会话当作唯一业务账，换一次部署或清理会话就丢了客户承诺记录。

**领导：**那失败恢复是重新跑整个根 Agent，还是从子 Agent 继续？

**小陈：**先按副作用边界决定。只读客户查询超时可以限次重试；已请求报价但回执未知，先按请求 ID 查报价系统，别重建第二个报价；邮件已发送但会话事件没写进去，要从邮件服务查消息 ID 后补业务账。为了能接着跑，状态里至少保留工单 ID、商机 ID、输入版本、已完成步骤、外部请求 ID、批准报价 ID、草稿版本、失败原因。恢复时重新校验这些引用的时效和权限；不能因为 state 中还有 `approved_quote=true`，就假定折扣没有被撤回。会话便于继续计算，业务系统决定动作是否已经发生。

并行恢复更细。两支查证，一支成功一支失败，可以只补失败的只读分支，但汇合时需检查成功支是否过期。若产品范围在几分钟内被修改，旧分支结果应作废，重新跑两支或至少重核版本。对循环修稿，保留最新已批准报价 ID、草稿版本和校验错误；从下一轮修稿继续时，先确认原报价仍有效。用户突然要求“改成另一个产品”，那是新任务，不应让旧循环携带上个产品的报价继续。状态设计的目的，就是让恢复能依据事实选择安全位置，不靠模型回忆“刚才差不多做到哪”。

**领导：**你说共享 state，可并行两支同时写，最后谁覆盖谁？

**小陈：**所以不能给两支同一把笔。客户背景支只写 `customer_research_result`，产品范围支只写 `scope_check_result`；两份对象都包含商机 ID、输入版本、数据来源和完成状态。汇合步骤读取两份，只由汇合步骤写 `quote_inputs_ready`。并行文档明确提醒共享上下文时需要处理并发访问，安全的习惯是让分支写互不重叠的键，必要时用外部存储和版本检查。若同时改 `quote_inputs_ready`，完成顺序不确定，快慢差会变成业务判断差；测试机上偶然正确，生产限流时就可能反转。

小陈还把事件顺序摊在白板上：`invocation_started` 关联商机；客户核验工具返回身份回执；并行支 A 报告客户历史证据，支 B 报告产品交付证据；汇合校验写入 `inputs_ready`；报价服务返回价格版本与审批状态；未获批时产生 `pending_approval`，运行停在对外动作前。获批的另一条轨迹才继续写稿、校验、人工审核和发送回执。这里“事件”是教学上的可观测记录名称，具体 ADK Event 结构以运行版本为准；我们关心的是能从一个 invocation ID 追到每个事实依据，区分 Agent 的文字、工具结果和业务回执。

**领导：**那 `SequentialAgent` 共享状态，下一位岂不是可以随便读上一位的全部资料？

**小陈：**共享 `InvocationContext` 提高传递便利，也意味着要主动限定内容。客户身份证件原图不应因为报价步骤要读商品范围就一并塞进 state；可传“核验通过、客户 ID、授权范围、回执引用”，原图留在受控业务系统。文案 Agent 更不需要财务审批人的内部备注，只需要可对客报价、有效期和允许使用的条款。若模型上下文变长，成本与泄露面也跟着扩大。把 state 当数据总线时，字段级最小化、脱敏和生命周期必须同时设计，不能因为一个花括号模板引用起来方便就把整份 CRM 对象传下去。

**领导：**有没有具体的工具合同？别讲到最后只有架构图。

**小陈：**客户核验工具输入可信商机 ID 与当前操作者身份，输出 `customer_id`、`authorized=true/false`、回执 ID；产品范围工具输入产品 SKU 和合同版本，输出可交付项、排除项和版本；报价工具输入上述受控字段，输出金额、币种、税费口径、有效期、审批状态及请求 ID。LLM Agent 可从客户邮件中提取产品意图，但工具端仍核 SKU 是否存在；可建议“需要额外查旧合同”，但不能直接写 `approved=true`。这个合同让模型输出与业务事实有明确分工，也让每个子 Agent 的失败可被机器识别，而不是一句“抱歉我没找到”让下游猜。

对折扣审批尤其要防止时间错位。假设报价 Agent 在上午十点读到 `approved=true`，文案循环到十一点仍没结束，十一点半主管撤销折扣，下午两点销售才点外发。只在报价步骤核一次不够，发送前应按报价 ID 重新核有效期与批准状态；若变化，旧草稿和旧人工批准都失效，回到待处理。ADK 的 state 保留的是曾经读到的快照，不能自动代表外部系统此刻仍认同。时间维度一加，所谓“按顺序执行”才真正接近业务安全。

**领导：**如果客户背景支用了模型，产品范围支也用了模型，它们都能查知识库，费用怎么算？

**小陈：**并行减少关键路径延迟，不意味着总模型调用数减少。两支可能各自调用模型与检索，汇合后又有报价说明和写稿循环。要把子 Agent 的调用、token、工具费用按 invocation ID 归集，并区分“必要查证”和“重复找同一资料”。如果某支只是按 SKU 查固定字段，用普通函数工具就够，不必为了三名 Agent 队形整齐给每一步配模型。成本预算可设置总上限与每支上限，超限时输出缺哪些证据、哪个节点停下，而不是在预算用完那一刻产一份看似完整的报价邮件。

再有一种失败更隐蔽：两个并行结果都成功，却引用不同时间点的产品目录。客户背景支从旧合同读“含高级支持”，产品范围支从新 SKU 表读“不含高级支持”；汇合时不能任选一边，必须按合同版本和产品版本的适用关系判定，必要时转人工。工作流 Agent 负责让两份结果汇合，是否相容由业务校验器决定。把“两个 Agent 都自信”当成结果一致，就是让两个可能错的人互相作证。多 Agent 的可靠性不来自数量，来自它们的证据能否交叉检查。

**领导：**人工审核都在最后了，前面的循环还检查什么？

**小陈：**自动校验筛掉机械错误，让人审关注真正需要判断的承诺。可自动核的是数字一致、币种一致、有效期未过、附件 ID 存在、草稿未出现禁用词或未授权产品；人工核的是客户关系、沟通时机和某些模糊但重要的商业承诺。若把所有问题都丢给人，Agent 只是一个会制造待办的写稿机；若把所有问题都丢给循环，模型可能靠重新措辞躲过检验。两道关口的职责不同，回放时也要分别记录自动校验结果与人审决定。

恢复和上线还需要版本固定。一个运行跨越午休，团队中途改了子 Agent 提示或换了模型；恢复时若直接使用新配置继续，前半段和后半段可能按不同规则工作。工单记录所用工作流定义版本、子 Agent 配置摘要、报价工具版本和政策版本；若配置发生不兼容变化，旧运行进入人工迁移或从安全检查点重跑只读段。这样可以解释“同一客户昨天和今天为什么看到不同措辞”，也能在故障后判断该按原流程继续，还是按新流程重新审。

小陈给领导展示一条拒绝轨迹：报价系统返回 `pending`，顺序编排停在价格关口，写稿 Agent 没启动，客户没收到邮件；销售工作台显示缺的批准人与请求 ID。批准到来后，流程从这个业务事件重新进入，先核报价仍有效，再写稿与审核。另一条通过轨迹则展示两个并行查证结果的版本、汇合检查、文案三轮以内的校验结果和发送回执。两条轨迹都能回答“为什么这张单今天没发”，而不是只留下一个绿色或红色的终点。领导要的快，是少等无关步骤；客户要的稳，是必要步骤一个也别跳。

验收报告还应附上每条轨迹的最大耗时与人工接手点，让业务知道系统在什么条件下会停，也让工程团队知道超时预算和重试次数该按哪个环节调整。顺序、并行、循环不是三个可炫耀的名词，而是三种不同的运行责任。

## 不要把模板类的示例当成所有版本的唯一答案

发文当日，[ADK 模板工作流概览](https://adk.dev/agents/workflow-agents/)注明 Python 和 Go 的 ADK 2.0 已有更灵活的图式与动态工作流，模板工作流的地位发生变化。若团队已经用 Python ADK 2.0，复杂的条件依赖可能直接用图式工作流表达；若现有项目仍用模板类，理解 `SequentialAgent`、`ParallelAgent`、`LoopAgent` 的语义和数据传递仍很有用。不要从网上复制一个老版本导入路径就断言“ADK 不支持”，也别把 Python 的新接口照搬到 Java 服务。选型和样例要标语言、版本、部署方式，实际编译与回放通过才算完成。

**领导：**我只想知道三个 Agent 上线前测什么。

**小陈：**六条足够揭穿假聪明：未批准折扣绝不到邮件草稿；客户资格与产品范围并行完成后，汇合结果同属一个商机；任一必要分支超时则停，不用另一支结果硬凑；草稿校验不通过最多修三次，超限转人工；报价外部请求结果未知时先查回执，不重复申请；邮件外发必须有人审和发送服务消息 ID。每条记录 invocation ID、子 Agent 事件、state 关键字段变化、外部回执和最后工单状态。测试既看答案文字，也看顺序有没有守住。

**领导：**所以“自由发挥”到底留给哪一段？

**小陈：**留给开放式查证和表达。例如客户邮件写得不清楚，LLM Agent 可以决定查产品知识库还是先问销售补充；遇到技术需求，可以挑适用的只读资料工具。报价计算、折扣批准、客户身份、外发动作都有明确制度，就由工作流和业务服务掌舵。Agent 在自己的车道里灵活，关键路口按信号灯走。这样的系统看起来没有“全都交给 AI”那么酷，但周五晚上真的要交付时，大家能知道是哪一步停了、该找谁处理，不用让三个 Agent 在日志里互相甩锅。

本文产品机制依据 [Google ADK 模板工作流](https://adk.dev/agents/workflow-agents/)、[顺序](https://adk.dev/agents/workflow-agents/sequential-agents/)、[并行](https://adk.dev/agents/workflow-agents/parallel-agents/)、[循环](https://adk.dev/agents/workflow-agents/loop-agents/)与[运行事件循环](https://adk.dev/runtime/event-loop/)官方文档；商机和报价为教学虚构。
