**领导：**客服还压着 186 条工单。隔壁都用 Agent 了，咱们明早也上一个：查订单、回消息、该退钱就退钱。最好别再招人。

**小陈：**我拿一条脱敏工单试了下。您先看它写的第一句。

> 客户：订单 0823 显示“已签收”，可我没收到。今天能退款吗？<br>
> **没设好规矩的 AI：**“可以，已为您安排退款。”

**领导：**它真退了？

**小陈：**没退，它压根没有退款权限。但顾客要是收到这句，截图比退款到账还快。它只看到了旧版 FAQ 里“签收异常可退款”，没看到现行规则要求**先核对签收记录，再由售后判断**。钱没动，话先说满了。

## 领导：“那 Agent 到底比聊天框多干了什么？”

**小陈：**先给它一件明确的活：**查清这张工单，起草回复；关键事实还对不上，就标记转人工。**再接两个只读工具：查订单与物流、查当前有效的售后规则。要是订单“未发货”，下一步该查取消规则；这张偏偏是“已签收”，客户又说“没收到”，它就去查签收争议规则；规则要求人工核实，它才写草稿、标记转人工。

**领导：**它本来就知道我们订单？

**小陈：**不知道。我不给查询接口，它只能看我贴进去的字；我给了接口，它才能查。**模型负责判断下一步，工具负责真的去查，知识库放规则，状态记着这单已经查过什么。**它根据查询结果再决定继续查还是停，这个“边做边决定”的过程，才是这里的 Agent。[Anthropic 对 Agent 与工作流的区分](https://www.anthropic.com/engineering/building-effective-agents)也是看下一步由谁决定。

**领导：**查到订单“已签收”，直接驳回不就行了？

**小陈：**客户说没收到，系统说已签收，正是不能装懂的时候。给您的内部处理卡是这样的：

| 查到的事实 | 依据 | 处理 |
| --- | --- | --- |
| 订单 0823 的物流状态为“已签收” | 订单查询结果 | 保留查询时间与原始记录 |
| 客户反馈“未收到” | 当前工单 | 标记为签收争议 |
| 现行规则要求核对签收记录 | 当前有效的售后规则 | 转人工售后；不承诺退款 |

**小陈：**给客服看的待审核草稿是：“您好，我们查到这笔订单的物流状态为已签收，也看到了您反馈未收到。我们会交由售后核对签收记录，再尽快告知处理结果。”客服确认信息没错，再点发送。它不会替客服写“已经退款”。

**领导：**上回旧 FAQ 都搜出来了，这次靠它自觉不看？

**小陈：**靠文档管理。旧版标成归档，不进入现行规则检索；每条结果都带版本和生效日期。两份都写着“现行”、或者找不到生效日期，就停止起草并转人确认。它不负责猜哪份文件更像领导签过字。

## 领导：“听着像流程。为什么还叫 Agent？”

**小陈：**您说得对，不能什么都往 Agent 身上塞。工单进来后脱敏、登记、限定只查现行规则、留操作记录、交客服审核，这些步骤固定，用**工作流**。客户问“发票在哪里下载”，按固定步骤查并回复就够了；这张单把“已签收”“没收到”“能退款吗”揉在一起，问法还会变，我没法给每句话预写一条路线。让 **Agent** 看查到的结果，在授权工具里决定下一步查什么。

**领导：**让它查完直接发，省一步行吗？

**小陈：**不行。我们只给它**只读查询**和**写内部草稿**的能力；发给客户、改订单、退款，都走现有系统的人工确认。提示词里写“千万别退款”像在工牌背面写“别碰收银台”，钥匙还是别交给它。工作流把权限锁住，Agent 负责在锁住的范围里找答案。[OpenAI Agents SDK 的工具与校验文档](https://openai.github.io/openai-agents-python/)也把工具调用和检查作为需要明确设计的部分。

## 领导：“我这里七个产品名。今晚到底装哪个？”

**小陈：**先看它们各自干什么。把写代码的工具和搭客服系统的平台排一场“谁最会回工单”的比赛，评委都得加班。

| 产品 | 它在这件事里的岗位 | 小陈的判断 |
| --- | --- | --- |
| [Codex](https://openai.com/codex/) | 帮开发改代码、做验证 | 用来**开发**客服系统，不直接当客服系统 |
| [Claude Code](https://code.claude.com/docs/en/overview) | 帮开发读项目、改文件、运行命令 | 同上；代码改动仍要审阅 |
| [Coze](https://www.coze.com/open/docs/guides/features) | 可视化搭问答助手、接知识和工具 | 适合快速试对话体验 |
| [Dify](https://docs.dify.ai/en/learn/key-concepts) | 可视化搭应用、工作流和知识问答 | 这次先用它做**内部答复草稿**试点 |
| [n8n](https://docs.n8n.io/integrations/builtin/cluster-nodes/root-nodes/n8n-nodes-langchain.agent/) | 连接工单、订单和审批等系统 | 试点过关后，再接正式业务流程 |
| [OpenAI Agents SDK](https://openai.github.io/openai-agents-python/) | 让开发用代码管工具、交接和校验 | 要做进自家产品时评估 |
| [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) | 编排有状态、可暂停的多步流程 | 遇到复杂长流程再评估 |

**领导：**Coze 也能搭，为什么先用 Dify？

**小陈：**两者都能做演示。眼前要先验证“查订单、查现行政策、出有依据的草稿”，我选 Dify 搭一个内部原型：给它只读的订单快照查询和现行规则库，让它按工单内容选择要查什么。这是**按这次任务选**，不是宣布它全面胜出。业务数据能否进入平台，要先按公司的数据要求确认。明早回放只用脱敏的历史工单和订单快照，不把客户资料直接扔进未经批准的服务。

**领导：**n8n 呢？还有最后那俩开发工具？

**小陈：**先别让七个产品一起开晨会。原型能稳定出草稿后，用 n8n 接工单流转和人工审批；[n8n 官方也提供工具调用前人工审批的做法](https://docs.n8n.io/build/integrate-ai/ai-examples/human-in-the-loop-for-tools/)。如果之后要做成自己的客服产品，开发再比较 Agents SDK 和 LangGraph。现在先把这张单答对。

## 领导：“明早我看什么，别给我看一段漂亮演示。”

**小陈：**看 **50 条历史工单回放**，专挑“旧规则混进来”“客户描述含糊”“订单状态与客户说法冲突”的。每条都留：查了什么、引用哪个版本、草稿是什么、为什么转人工。验收线也写死：**错误承诺退款 0 条、引用过期规则 0 条、该转人工却没转 0 条**；再拿客服原本的处理时间作对照。没过线就修资料和流程，不扩大范围。

**领导：**那剩下 186 条怎么办？

**小陈：**客服照常处理。回放过关后，只把“内部草稿助手”给客服试用，客服审核后发送；自动退款不在这次范围。它先帮人少翻几页规定，别第一天就替公司签支票。

**领导：**行。明早先看那 50 条。至于“AI 员工替我省下一个客服”——

**小陈：**先让它别给您招来一个投诉专员，再谈升职。

## 第二天早会，领导把“Agent”两个字问到底

**领导：**你昨天那张图我看了。模型、工具、知识库、状态四样东西摆一块，就叫 Agent？

**小陈：**还差“谁决定下一步”与“谁拦住危险动作”。模型能读客户话、提出要查订单还是规则；应用决定哪些工具可用、这张工单能查哪个订单；工具返回可核事实；知识库提供当前规则；状态记录已查与待办；最后按证据起草、停止或交人。若步骤全部由程序预设，只是模型在其中写一段话，叫工作流更准确。若模型在边界内根据新证据动态选下一步，才有这里说的 Agent 性质。名称不会给它退款权限。

**领导：**那它是不是只要会多想一会儿，就比普通聊天更厉害？

**小陈：**多想不等于多知道。没有订单接口，它无法知道 0823 当前物流；没有有效规则，它可能拿旧 FAQ 充数；没有业务回执，它不能证明退款执行。真正的能力来自“能在授权范围取到正确外部信息，并在适当时刻停下”。模型负责理解与组织，程序负责权限、状态和动作，客服负责本期对外确认。把所有责任写成“让模型更聪明”，会让整个团队找不到出错位置。

**领导：**客户问一句“今天能退吗”，你给我讲这么多，客户会不会跑了？

**小陈：**客户回复反而要短：“目前还不能确认是否符合退款条件。系统显示已签收，但您反馈未收到，我们会先核查签收凭证，再告知处理结果。”前提是核查待办确实创建、有负责人和更新时间。内部为了说准，查证可以复杂；对客不用背系统架构。Agent 的价值是把复杂过程变成可承担责任的简短答复，而非让客户读我们的技术汇报。

## 工单 0823 做一遍，Agent 哪一步该停

**领导：**那你把昨天的工单从头到尾演一遍，别跳步骤。

**小陈：**接入时先核当前登录客户与工单绑定，取客户原话；客户说“显示已签收”只是客户陈述。应用允许只读查本单，订单系统若返回“物流已签收，查询时间 10:15”，卡片写“系统记录显示已签收”，不写“客户确实收货”。再检索适用于该商品与地区的现行签收争议规则，带文档版本与条款位置。若规则说“先核对签收凭证，由售后判断”，Agent 应生成内部处理卡和待审草稿，标缺签收凭证、交售后。客服审核后才能外发。整条路里没有退款批准或支付执行回执，因此任何“已退款”都应被系统拦住。

**领导：**如果订单接口超时呢？

**小陈：**状态未知。有限次重试符合服务约定时可重试，超过时限就交客服通过原系统查。模型不能把客户的“页面显示已签收”冒充系统查询，也不能把超时解释成“无此订单”。处理卡记录已尝试什么、错误类型、下一步责任人。若规则库同时返回旧版和新版，先过滤生效状态；两份都标有效却冲突，停下给政策负责人。Agent 能正确停住，也是一种完成，而不是必须给出一个肯定退款答复才叫有用。

**领导：**如果钱真的退了，谁告诉它？

**小陈：**退款系统的执行回执。批准记录只能支持“申请已批准”，执行回执支持“退款已处理”，到账还可能需要支付渠道进一步确认。模型不能用“客服说已安排”跳过阶段。写入工具以后若超时，先查业务流水和幂等记录，不能再点一次造成重复退款。这些是未来扩展所需的状态机与对账，不在明早内部草稿试点里偷偷实现。

## 七个产品放同一桌，先问岗位

**领导：**我还是要选产品。大家都叫 Agent，我怎么买？

**小陈：**先分岗位，再比工具。[Codex](https://openai.com/codex/)和 [Claude Code](https://code.claude.com/docs/en/overview)是给开发者做代码工作：读项目、改代码、跑命令，适合帮我们实现客服系统、写测试、查回归，不是直接替公司管理退款审批。[Dify](https://docs.dify.ai/en/learn/key-concepts)和 [Coze](https://www.coze.com/open/docs/guides/features)偏向搭建应用与对话原型，能快速试知识、流程和工具体验；是否满足本公司的数据、权限与部署要求，要做实测。[n8n](https://docs.n8n.io/integrations/builtin/cluster-nodes/root-nodes/n8n-nodes-langchain.agent/)擅长把现有系统和工作流接起来，也有 Agent 节点；它能串流程，不等于订单接口自带逐对象授权。[OpenAI Agents SDK](https://openai.github.io/openai-agents-python/)与 [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview)更偏开发框架，适合团队在代码里控制运行、工具、状态和交接。

**领导：**听着 Dify 和 Coze 能做，n8n 也能做，SDK 也能做，结论不还是“都行”？

**小陈：**用五项具体条件比：一，是否方便把 0823 的原话、订单回执、现行规则分层提供；二，工具调用前是否能由我们自己的服务端核工单与订单关系；三，草稿能否留在内部、按版本交客服审；四，失败后能否拿到可追踪的调用与转人记录；五，数据在哪里处理、谁能看到、是否满足公司要求。再量开发时间、维护人力、费用和迁移难度。厂商功能页面能说明它有什么按钮，不能替我们证明一张真实工单的权限边界。

**领导：**那为什么文章里先挑 Dify，不挑 Coze？

**小陈：**这是本例的试点路线，不是永久排名：团队要很快把“订单快照 + 有效规则 + 内部草稿”做成一个可回放流程，Dify 的可视化应用与工作流形态便于先验证业务问题。若团队已有 Coze 经验或其部署、治理更符合要求，按同一验收单做对照即可。工具的胜负取决于本公司数据去向、权限接法、可观测性和维护能力。客户不会问我们选了哪个平台，只会问为什么没有退款却说退了。

**领导：**n8n 什么时候出场？

**小陈：**当内部草稿试点证明有价值，要与工单派发、人工审核、通知和回执系统可靠连接时，再评估它的编排作用。它可连接系统和人工步骤，但每条写动作仍需业务授权、幂等和对账。也可能公司原有工作流系统更合适，不必为凑七个产品把同一工单拆到四个平台。选型以减少真实集成负担为准，不是让 PPT 一页塞满 Logo。

**领导：**Agents SDK 和 LangGraph 是不是“更专业”，直接上就对了？

**小陈：**团队能维护代码、需要复杂状态、暂停恢复或深度接业务系统时，代码框架给更多控制，也带来开发与运维责任。Agents SDK 提供 Agent 运行、工具、交接、轨迹等构件；LangGraph 强调有状态的图运行与持久化。它们不会自动替我们写政策、核客户身份或保证退款幂等。先用原型找准任务，再决定是否迁到自建产品；如果固定工作流就能解决大部分问题，也无需为框架丰富度买复杂度。

## 明早到底展示什么，才能不把原型当生产

**领导：**你让我看 50 条历史工单，为什么是 50？能保证什么？

**小陈：**它是内部试用的**起始回放量**，不是统计保证或自动退款许可证。样本要覆盖常见入口题、签收争议、订单查询失败、过期规则、规则冲突、客户要求越权、退款执行未知；每条预先标期望结论与红线。固定模型、提示、规则版本和工具返回，再看最终草稿与完整轨迹。同一题重复跑可测稳定性，但不当作新场景。若样本全是简单问答，50 条也无法证明高风险问题安全。

**领导：**三项红线都是零，是不是就能全量对客？

**小陈：**只说明这批回放没观察到关键错误。还要看客服改稿、缺证据转人、等待时间、权限拒绝、数据去向和故障恢复。内部试用先只给客服草稿，客服可看来源、改稿并反馈；逐步灰度时按题型与渠道控制，对外仍要审核。自动发送与自动退款分别做新的权限、批准、回执、事故止损验收。离线零错误不能给系统签一张“以后永远不会错”的免检证。

**领导：**如果试点出了一句“已为您退款”，你会不会马上换最贵模型？

**小陈：**先看第一处错误。检索取旧政策，修文档准入和索引；证据正确但模型说满，修生成与回执校验；客服卡正确却发送错客户，修收件人绑定与发送服务；权限越界，立刻关工具并修后端授权。换更强模型可在同题对照里评估，但不能替这些确定性边界。客户需要我们给出真实处理，不会因为后台模型贵就接受假退款。

**领导：**那 186 条积压怎么减？

**小陈：**先让 Agent 给客服做可审核的查证卡，量每单节省的查资料时间、重大改稿比例、转人是否有用；简单题可用固定流程和受控模板，疑难题给人。看客户从发问到有结论的总时间，不只看模型生成速度。若客服审核队列被草稿淹没，原型没有省人力，需要改分流和卡片；若权限与证据没接好，“自动处理 186 条”可能只是“自动制造 186 张待解释的截图”。

**领导：**我问最后一个：面试官问 Agent 和自动化区别，你怎么回答？

**小陈：**工作流的主要步骤与分支由程序预先确定，Agent 可根据任务与新证据在允许范围动态决定下一步，例如补查签收凭证或转人。模型、工具、知识库和状态给它工作材料，服务端权限、预算、审批与回执给它边界。动态选择有成本和不确定性，所以从能解决问题的最简单路径开始；证明动态取证确有收益，再逐步扩。至于明早，领导可以先看 0823 的完整证据链，别让一声“已退款”替财务连夜加班。

**领导：**你写这么长，真要给刚入门的人看？

**小陈：**看懂一张工单就够入门：客户说的话是诉求，订单和政策是要查的证据，模型在授权范围选择下一步，程序守住权限与停止条件，人负责高风险审批，业务回执才证明真实动作。工具名记不住没关系，先记住“谁说的、查过没有、有没有权限、做成没有”。后续遇到新的框架和产品，再拿这四问去拆，就不容易被“全自动”三个字晃晕。

**领导：**那今晚的工作安排？

**小陈：**客服照常处理积压单；技术只用脱敏工单做内部草稿回放，把错条款、误承诺、越权请求和故障交接逐条记下来。明早展示证据链和失败清单，能省下多少客服时间按试点数据说。我们今天先让 Agent 学会查证与停手，别让客户为它的第一天上班交学费。

**领导：**如果回放里它连续十单都转人工，是不是至少安全？

**小陈：**关键风险可能低了，业务价值却还没证明。逐单看为什么转：缺现行规则，就补资料与文档审核；查单接口超时，就修接口和重试策略；客户问题本来是固定入口题，就把它交给普通工作流，不必让 Agent 每次绕一圈。转人卡还要有证据、责任人和时限，不能写“请人工处理”五个字。试点报告把正确停答、过度停答、人工接手耗时分别列出。领导明早看到的应是哪些问题已能省时间、哪些边界还需业务系统补齐，而不是一个全绿或全红的演示页面。

**领导：**若两位客服对这单是否能退款意见不同，Agent 听谁的？

**小陈：**先回到有效政策、订单与签收凭证；规则解释仍有分歧，就交政策负责人裁决并记录版本。模型可以把争议点列清，不能按谁职位高、谁说话更像命令来决定。裁决后更新规则与回放样本，让下一张同类工单有依据。这比在提示词里写“优先听领导”更像一个能长期运行的客服系统。
