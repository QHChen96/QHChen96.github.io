**领导：**不是说有检查点，Agent 掉线也能断点续跑吗？现在存检查点的数据库也挂了，你总不能告诉我“断点”跟着一起下班了吧？

**小陈：**它确实可能下班了。我们得先知道丢的是读写连接、主库节点，还是已经确认写入的一段数据。更要紧的是，Agent 在库出事前可能改了工作区、开了 PR、给客户发了消息。会话检查点只是运行进度的一本账；磁盘和外部系统各有一本。恢复时先让三本账对上，再让它继续说话。

**领导：**你这话听着像财务盘点。我只想知道多久能恢复。

**小陈：**先给一个真实范围：如果只是连接故障而已，存储恢复后可从最后持久检查点核对续跑；若恢复到旧备份，就会出现一段“系统已经做过事，检查点却说没做”的空窗。我们先暂停新写动作，圈出这段空窗，才能估算恢复时间。直接把 Agent 重启，是把未知写成已知。

本文中的故障时间、任务和数字均为教学虚构。框架所提供的持久化能力与应用自己的备份、外部动作对账责任分别说明，不把示例设计写成任何产品默认保证。

## 事故第一分钟：让它停手，不是让它重来

09:12，检查点数据库连续超时。两台 Worker 还活着，客服 Agent 有一张退款工单停在支付接口之后，研发 Agent 有一张 issue 已写完代码、正准备建 PR。领导的第一反应是重启 Worker，等数据库起来后让任务从头跑。小陈先冻结这两类任务的外部写权限：退款、外发、开 PR、部署全部暂停；只读查询和状态盘点在权限允许时可以继续。入口新任务暂存到有持久保障的待处理队列，若队列也依赖故障库，就直接限流并告知不可接单，不往内存里无限塞。

**领导：**停写会影响客户，难道恢复系统不该先追进度？

**小陈：**假设退款接口实际返回成功，但成功回执没写进检查点。重启后 Agent 看到的是“准备退款”，再扣一次就是事故扩大。影响客户的不是短暂停写，而是我们假装知道它没做过。此时允许客服显示“正在核对进度”，把待确认单交给值班人；等外部回执查清，再恢复动作。发布进度也一样：PR 已开却没记下，第二次开一份同名 PR，还可能基于错误分支。

第一分钟的记录要固定故障起止、受影响的任务键、Worker 租约、正在执行的工具调用、最后一次成功持久写入时间。日志能帮助定位，但日志不是唯一事实源：有的请求已经到支付侧，应用日志却因为网络中断没记完成；有的日志写了“准备调用”，接口压根没收到。小陈给状态板加一个明确的“外部结果未知”计数，不允许统计系统把它算成失败或者成功。

## 检查点到底保存了什么，没保存什么

**领导：**断点续跑不是把聊天记录存起来吗？恢复聊天记录就好了。

**小陈：**聊天是输入输出的一部分，运行状态还包括当前节点、工具结果、等待人工批准的标记、任务 ID、版本与下一步。以 [LangGraph 的官方说明](https://docs.langchain.com/oss/python/langgraph/persistence)为例，checkpointer 保存线程的图状态，用于继续对话、人工介入和故障恢复；store 是跨线程的应用数据，两者用途不同。内存 checkpointer 在进程重启后会丢，生产要用持久后端。可这也没有保证你的支付平台、Git 工作区和数据库在同一个事务里更新。

小陈在白板上写出一个最小状态：<code>task_id</code>、<code>thread_id</code>、<code>checkpoint_version</code>、<code>phase</code>、<code>action_key</code>、<code>approved_scope</code>、<code>evidence_refs</code>。其中任务键确定逻辑工作单元；检查点版本说明保存到了哪一步；动作键用来查询或去重外部写操作；证据引用让结论可复核。字段可以放在不同存储，名字也不必照抄，但关系必须可追。若检查点只留“我现在要去退款”，外部却没有稳定动作键，恢复时就无法精确询问支付系统“这一次退款到底发生没有”。

**领导：**用可靠工作流引擎是不是就没这事了？

**小陈：**工作流引擎能改善执行历史的持久性，不能替业务决定外部动作该不该重发。[Temporal 官方文档](https://docs.temporal.io/workflow-execution)说明工作流通过事件历史重放恢复，失败后从已记录事件继续；[事件历史文档](https://docs.temporal.io/workflow-execution/event)也区分活动调度、完成与失败事件。要是活动已经调用外部系统，完成事件却没记录，仍要靠活动的幂等设计和外部回执处理未知结果。换引擎不会把外部支付系统自动变成同一个原子事务。

还有一件容易混：检查点“写入成功”不等于备份已包含它。主库中最后一个已确认检查点可能在 09:11:58，备用库或备份只到 09:08。若我们把 09:08 的备份恢复起来，却告诉领导“从 09:11:58 继续”，就是报表上的魔术。恢复计划必须写明可用恢复点与可能丢失的窗口，不能靠界面上最后一条聊天时间猜。

## 三本账摆在同一张桌上

小陈把一张研发 issue 的三条记录摊开：检查点库记录“已读取代码，准备修改”；工作区里 <code>git diff</code> 显示补丁已经写好，还有同事未提交的另一处修改；GitHub 上已经有一条对应任务键的 PR，但本地日志只写到“提交请求”。若只信检查点，就会再改一次代码、再开一次 PR；若只信工作区，就可能把同事的改动算成 Agent 成果；若只信 PR，就不知道测试是否通过。对账的目标不是挑一本“最权威”的账，而是确定每个事实由谁拥有。

客服工单也是三本账：检查点说“准备申请退款”，本地执行台账有相同 <code>action_key</code> 的已发送记录，支付系统回执显示成功且退款号固定。此时支付系统对支付事实更权威，检查点需要补记“已退款”；但是否已经通知客户，要另查外发渠道。若支付侧查询不到，不能立刻认定没发生：先看查询是否最终一致、查询条件是否正确、回执是否延迟，再按支付接口契约决定等待或人工核实。未知不是失败的同义词。

**领导：**这样查一张任务要很久，能不能自动对？

**小陈：**能自动查有稳定键和查询接口的事实，比如订单号、退款动作键、PR 对应分支；自动查不到的才留人工。对账单至少列任务键、外部动作键、检查点版本、源系统、证据时间、证据链接、当前结论、负责人和下一次检查时间。它比一段“任务可能已完成”的摘要更适合故障期间交接。若有十万张任务，先按故障窗口和写动作筛出高风险集合，纯只读且已过期的任务另行处理，不要求人逐张读会话。

## RPO 和 RTO：领导要的“多久恢复”其实有两个数字

**领导：**数据库团队说半小时内恢复。这不就是答案？

**小陈：**那可能只是数据库能连上。RTO 是业务恢复到可服务状态允许花多长时间，RPO 是允许丢失多少时间范围内的数据。两者要按任务类型定。客服内部草稿丢十分钟，可能重新生成并核对就好；已批准的退款动作若丢十分钟检查点，不能从备份点盲目重跑。即便技术层 RPO 为五分钟，外部动作的对账范围仍可能更大，因为确认写入与外部回执不在同一时刻。

小陈给出一组演练用数字：09:12 库故障，09:08 为最后可验证备份，09:11:58 为主库最后已确认写入。若只有 09:08 的备份能恢复，备份缺口从 09:08 到 09:12，至多四分钟的检查点状态需要另行重建；但故障前还可能有未持久化的在途任务，也要纳入。09:11:58 不能写成恢复点，除非真的有可用日志或副本能恢复到那里。数字只是示例，实际应由数据库团队用备份、日志与校验结果给出。

如果检查点存储用 PostgreSQL，[官方持续归档与时间点恢复文档](https://www.postgresql.org/docs/current/continuous-archiving.html)说明可由基础备份和 WAL 归档恢复到时间点；前提是备份和所需 WAL 确实可用。小陈要求每次演练记录“成功恢复到哪一秒”，并抽检线程状态，而不是只看备份任务页面写着“成功”。基础备份在，WAL 缺一段，声称能恢复到故障前一秒没有意义。备份是否加密、谁能解密、恢复时磁盘空间够不够，也都写进演练单，免得把事故现场变成密码找人游戏。

**领导：**我们给客户承诺一小时，数据库半小时起来，剩下半小时不够吗？

**小陈：**要加上对账和业务验收。数据库能接受连接只是基础设施恢复；检查点可读、任务租约可重新分配、外部未知动作已圈出、客户通知能准确发出，才叫业务恢复。一小时 RTO 要拆成发现、冻结、存储恢复、状态核对、灰度放行几段，并用事故演练测真实耗时。若核对耗时超出承诺，早一点转人工或发延期告知，比最后一分钟宣布“技术已恢复”负责。

## 恢复点选错，比完全不恢复更会制造鬼故事

假设原检查点 A 写着“将要创建 PR”，检查点 B 写着“PR 已创建，等待测试审查”。库故障后只恢复到 A，但 GitHub 上 PR 已存在。Agent 若从 A 继续，第一件事又创建 PR。这不是模型幻觉，是恢复点与外部世界分叉。小陈把已恢复的库当成“可信到某个版本的旧记录”，扫描故障窗口内的动作台账与外部回执，再为每张任务生成补偿状态。PR 已存在则补上 PR 链接与创建回执；代码 diff 存在但测试未完成则标未验证，不能把旧日志里的“测试开始”写成“测试通过”。

**领导：**那把外部回执直接写回检查点不就好了？

**小陈：**要写，但如果写回时库又不可用，仍会有缝。可以在执行外部动作前记录意图和幂等键，在动作完成后记录回执；外部系统支持按键查询或去重时，恢复器可以核对。对不支持幂等键、也查不到结果的系统，应用不能承诺自动无重复。此时停在待人工核实比调用第二次安全。动作的“准备、发送中、已确认、未知、人工核实、已终结”需要明确状态，不能只用一个布尔值 <code>done</code>；布尔值表达不了“可能做了”。

不同恢复点还可能涉及 schema 变化。昨天部署了新状态字段，今天恢复的备份却是旧版本；新 Worker 读旧检查点可能误解字段默认值。小陈在任务检查点写状态 schema 版本，恢复环境固定对应应用版本，先做兼容性校验和迁移演练。若代码版本已经不可回退，也不能把旧状态直接交给新模型解释，必须把可迁移字段映射清楚，失败的任务留在隔离区。数据库恢复和 Agent 逻辑恢复是两个步骤。

## 四类任务，四种处理；没有“全体从头再来”

**领导：**给我一个能发给值班同事的判断顺序，别让他们在凌晨背论文。

**小陈：**先按外部写动作分。任务还未开始，且入口记录和任务键完好，可以按原任务重新排队；任务只读过资料，检查点缺失也能从确认的输入和权限重新读取，但不能把旧资料快照当今天的真相；任务已改工作区或生成草稿，要核对文件版本、作者和测试状态再续；任务调用过外部写工具，先按动作键查回执，无法确认就交人工。只要任务已取消、审批已过期或输入版本变了，即便恢复点完整，也不能自动续跑。

小陈把判断顺序转成值班表：每张任务先看是否在故障窗口，随后看检查点版本是否真的存在，再看是否有进行中的 Worker 租约；租约过期不等于外部动作没发生。接着查工作区，区分 Agent 产物、人工修改和构建产物；最后查外部回执。每一步都留下证据链接和判断人。如果某个源系统暂时不可查，就写“待核实”，并设置复查时间和升级联系人。值班表中的未知状态允许存在，没人因报表不好看把它涂成失败。

**领导：**如果检查点和 PR 都有，就是完成了吧？

**小陈：**还要看交付条件。PR 存在可能只是草稿，CI 失败；检查点写了“测试完成”也要有测试命令、退出码、目标提交和执行时间。客服则要看客户消息是否真的送达、是否被撤回或被人工覆盖。任务最终状态由业务验收条件决定，不由检查点最后一句“我完成了”决定。恢复过程中我们可以补记录，不能补编证据。

## 备份演练不能只测“还原成功”，要测“还原后没有重做”

小陈把演练分成三次。第一次断数据库连接但不丢数据：观察 Worker 是否停止写动作，库恢复后检查点版本是否连续、租约是否只有一个持有人，任务是否按原键继续。第二次把数据库恢复到较旧时间点：预埋三张任务，一张只读，一张工作区已改但未测试，一张退款已成功而检查点还没记；验收三张分别重读、重验、补回执，不能全从头跑。第三次让外部支付接口查询也故障：退款结果保留未知，人工待办有负责人和时限，支付服务恢复后补核对，不因双故障而擅自重发。

**领导：**为什么第三次还要故意让支付接口也坏？这不是为难自己吗？

**小陈：**真实事故不按我们安排，一场故障常让另一个系统变慢。单测数据库能恢复，证明不了未知外部动作能收口。第三次的及格线并不是“自动完成退款”，而是“任务不会消失、不会重复扣款、客户得到真实状态、值班人有明确接手”。我们要演练的是失去证据时怎么保守前进，而不是每次都让自动化表演大获全胜。

监测面板也要同时显示四组数：最后可验证恢复点与当前时间差、受影响任务数、未清算外部动作数、已由人工接收的任务数。恢复点差距降为零，却还有一张退款结果未知，事故就不能宣布清零。小陈要求抽样回放原始任务键，核对外部系统没有重复 PR、重复退款和重复外发；样本可以分层抽，但所有未知写动作必须逐条有去向。留存策略也要足够覆盖发现延迟：如果回执日志三天就删，而故障一周后才发现，盘账时会凭空少一本账。

**领导：**我还有个担心：主库恢复了，原来那几台 Worker 也还活着，谁保证它们不会和新 Worker 同时接同一张任务？

**小陈：**恢复器先撤销旧租约，再用带版本的租约把任务交给新执行者；工具调用处还要再次检查任务状态与权限。旧 Worker 可能在网络恢复后才收到响应，它不能凭手里一张过期租约继续写。对于外部服务不支持版本检查的动作，应用仍用稳定动作键查询或去重；若对方既不支持查询也不支持幂等，就只让一个经过人工确认的执行者接手。数据库恢复后的“双主”执行，比库继续坏着更隐蔽，因为两边都觉得自己在完成任务。

恢复时还要把时间顺序排准。检查点库用自己的提交时间，工具网关用发送时间，外部系统用回执时间，三台机器的时钟可能有偏差；只按时间戳排序，容易把“回执晚到”看成“动作晚发生”。小陈优先用任务键、动作键、检查点版本和外部流水号关联，再把时间作为辅助线索。若两个回执共享相同动作键却状态冲突，先保存原始响应并查供应商契约，不用模型挑一个看起来顺眼的。这类异常若直接覆盖旧记录，复盘时就再也看不到冲突是从哪里来的。

**领导：**那备份频率拉到每分钟，问题是不是就解决了？

**小陈：**备份更密能缩短部分状态缺口，但外部调用与检查点写入之间仍有一条窄缝。更何况每分钟备份是否完整、能否恢复、日志是否连续，都要演练证明。真正要缩小事故影响，还要限制一次任务能触发的写动作、给动作稳定键、保留回执、控制自动重试和设置人工接管边界。备份是恢复材料，不是替代业务对账的万能橡皮擦。

## 复机最后一步：把“继续运行”还给有证据的任务

11:03，数据库恢复到 09:08 的备份点，支付侧回执可查询，GitHub 正常。小陈没有按下“全部恢复”。他先跑只读的状态盘点，给故障窗口内每张任务生成差异；把纯草稿任务放小流量续跑；把工作区有人工修改的研发任务交给工程师确认；把已完成退款的回执补进任务台账，客服只做后续通知；把查不到回执的两张单保持待核实。全部数字为虚构演示，真正的分流标准来自前面的字段、权限与验收条件。

**领导：**今天这事故，能不能写成“数据库恢复，Agent 自动续跑成功”？

**小陈：**写准确一点：“存储已恢复到 09:08；故障窗口任务已分流；已确认外部动作补记，未知动作有负责人继续核实；只读任务恢复，写权限逐步放开。”如果后来确实完成对账，再把最终结果补上。我们不是要把“断点续跑”四个字砸了，是要让它承受得起追问：断的是哪一层，续的是哪一步，凭的是什么证据。

最后领导盯着那张三本账的对照图看了半天，问：“所以检查点库算 Agent 的记忆，外部回执算现实？”小陈说：“差不多。记忆可以帮它接着干活；现实决定它能不能安全地接着干。两者意见不一致时，先停下来查，不要让一个特别自信的模型替现实投票。”
