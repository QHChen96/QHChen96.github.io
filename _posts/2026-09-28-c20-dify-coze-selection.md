**领导：**Dify 和 Coze 都能拖方块、接模型、连知识库。你选一个，今天把采购建议给我。

**小陈：**我先把浏览器首页关掉。首页能证明产品会做演示，证明不了客户说“系统显示已签收，我没收到，能退款吗”时，我们能不能把错话拦在发送键前。

领导把一张截图甩过来：“人家演示十分钟就搭好了。”截图里，Agent 给出了很流畅的三段式回复。小陈点开那段回复，第一句“可以直接申请退款”没有订单回执，第二句引用了已失效的规则。**流畅不是证据。**在我们这家公司，选型先过业务门槛，再讨论编辑器顺不顺手。

## 把“哪个好用”翻译成同一道考题

**领导：**总不能把每个平台都接进生产环境，测半年吧？

**小陈：**不用。只用脱敏的历史工单和假订单接口，先做一个可复测的小试验。两边用同一版规则、同一个模型档位、同一份工具返回；不接真实客户，不开放发送。试验包里放五种变化：正常查到订单、订单接口超时、检索命中旧政策、客户要求查另一人的订单、人工审核后草稿又被改动。

对每个变化，记录的不只是最终一句话，还包括“调用了哪个工具、依据哪条规则、为什么转人、谁批准、批准的是哪一版草稿”。如果平台内部看不到某一步，就在外层业务系统补轨迹；补不出来，选型表上写“未知”，不能用“应该支持”填空。

**领导：**资料已经查了吧？别把功能写成“我记得”。

**小陈：**按 2026 年 9 月 28 日的官方资料，Dify 文档能确认有[知识检索节点](https://docs.dify.ai/en/cloud/use-dify/nodes/knowledge-retrieval)、[Human Input 节点](https://docs.dify.ai/en/cloud/use-dify/nodes/human-input)和[自托管部署指南](https://docs.dify.ai/en/self-host/deploy/quick-start/docker-compose)；[Coze Studio 官方仓库](https://github.com/coze-dev/coze-studio)列出工作流、知识库、插件、API 与开源部署能力。**“有这个组件”不等于我们的权限、保留和审核链已经成立。**云服务和开源版也不能混成同一行功能表，试验时必须把产品、版本和部署方式写在表头。

| 必过的门 | 现场怎么试 | 没过意味着什么 |
| --- | --- | --- |
| 证据 | 故意让旧规则排第一，看能否只用现行条款并显示版本 | 答案再顺也不能对外 |
| 权限 | 用 A 工单请求 B 客户订单，检查工具服务是否拒绝 | 模型提示不能替代鉴权 |
| 审批 | 批准草稿后换收件人或改承诺，再尝试发送 | 审批必须绑定内容和对象 |
| 数据 | 查请求、运行日志、附件、副本与服务方设置 | 不知道数据去哪儿就不接真实客户 |
| 迁移 | 导出一条流程、规则引用和评测样本，换平台重跑 | 平台切换不能丢业务控制点 |

试验当天，小陈先把五张工单编号封存，写一份“预期结果”，避免看完某个平台的表现再给它改题。第一张只问发票入口，预期是固定流程给出当前入口；第二张签收争议，预期是显示订单事实与适用条款，不能直接承诺退款；第三张把订单接口改成超时，预期是明确“不知道当前物流”并转人；第四张要求查询他人订单，预期是工具服务拒绝；第五张在人工批准后改稿，预期发送服务拦住。每次运行都留流程版本、模型配置、工具假数据、耗时和人工接手记录。这样后来升级平台版本，还能原样重跑。

**领导：**两天够看出运维和迁移成本？

**小陈：**够看出第一批硬伤，不够签三年合同。所以加一个“拆迁演习”：不让最初搭流程的人参与，交给另一位工程师按文档重建；看规则和提示词能否导出，工具接口是不是标准的业务 API，知识条目的版本能否保留，失败运行能否定位到哪一步。若只能在平台画布里手点而无法审查配置，今天搭得快，半年后升级可能要考古。数据也列到合同前置问题：模型供应商、平台服务、日志服务分别接触什么字段，各自保留多久，能否按工单删除。试验环境没有真实客户资料，但生产决策必须把这些问清。

最后，**平台内的人审节点不是业务系统的万能批准**。Dify 文档说明 Human Input 能暂停并收集人的决定；我们仍需在发送服务重新核对草稿版本、收件人和批准记录。Coze Studio 若用工作流拼出审核界面，也同样要做这道服务端校验。任何平台上的“同意”按钮若能被换稿后复用，这一题都判不过。

## 先拆开四层能力，避免把一个绿色按钮当成完整产品

**领导：**我以为平台能连知识库、调工具、让人审核，就已经是一套客服系统了。

**小陈：**这是四种不同的能力。第一层是**流程编排**：固定问题沿预设路径走，签收争议才让 Agent 动态决定查哪项证据。第二层是**知识检索**：从候选文档找到适用条款，但文档是否生效、适用哪种订单，仍要有业务元数据和准入规则。第三层是**工具执行**：平台能发起订单查询，不代表它知道当前用户是否有权看这单；权限必须在订单服务复核。第四层是**人工与外发**：人看到草稿并点批准，只能说明这个人批准了特定版本；发送服务还要核对收件人、渠道、有效期和是否已发送。四层少一层，整条链都可能出事。

小陈把 0823 号工单在两种设计里跑了一遍。坏设计是“客户提问 → Agent 搜政策 → Agent 查订单 → Agent 直接回复”。订单超时时，模型可能把空结果补成“正在派送”；搜到旧政策时，模型可能把“不适用的退款入口”说成退款资格；即使草稿有人看，换稿后旧批准仍可能放行。好设计是在入口先定工单和授权范围；检索只收当前适用的规则；工具服务返回本单必要字段和来源时间；证据冲突转人工；对外发送再过批准版本和幂等闸口。平台选型要看这些边界能否被清楚地**实现、观察和测试**，不只是画布里有几个节点。

**领导：**Dify 有 Human Input，Coze Studio 有工作流，那是不是 Dify 天然更安全？

**小陈：**不能这么推。Dify 官方文档说明节点能暂停工作流、展示表单、接收人的选择；这是一个很有用的编排能力。它没有替我们的订单服务建立客户权限，也没有替发送服务保证“批准后不可换稿”。Coze Studio 的官方仓库列有工作流、知识库、插件和 API，说明它具备搭试点的基本构件；但我们要测当前版本、当前部署方式里这些构件如何接入原有工单和审批。**安全是整条业务链的属性，不是某个产品介绍页上的一个勾。**

## 真正的同题试验：先冻结输入，再看运行轨迹

小陈把试验包写成一个可重放的文件夹：`cases/` 放脱敏工单和人工认可的预期处理；`policy/` 放当前规则、旧规则和生效范围；`tools/` 放假订单接口在正常、超时、权限拒绝三种情况下的确定性返回；`expected/` 放每张单的可接受动作、不可说的话和必须转人的条件。两边平台分别接同一个假服务，模型档位、随机性设置、输入上下文预算尽量一致；若某项不能一致，写进试验记录，不把环境差异误当产品胜负。

**领导：**同一张单跑一次够不够？

**小陈：**不够。生成式系统会有波动，同题至少多跑几次，看是否稳定满足硬门槛。我们不拿“答案读起来像不像客服”打头分，先查每次轨迹：有没有跨工单工具调用、引用了哪版条款、订单超时时有没有编状态、转人工是否带足证据、批准后改稿能否外发。然后再让客服评措辞、完整度和阅读负担。高风险项目按“任一次触发就停”的规则处理，不被另外几次答对平均掉。

试验记录还必须保留**未观察到的能力**。例如平台演示页有“日志”，但当前部署的审计接口拿不到具体工具参数，就标“轨迹缺口”；云端版本能做的节点，开源版没验证，就标“版本待核”。“不知道”不是产品缺点的判决，却是生产审批不能越过的空格。做比较时把功能、部署方式、版本号、配置和外接服务一起写清，避免把 Dify 云端、Dify 自托管、Coze 在线版和 Coze Studio 开源版当成四个可直接互换的按钮。

**领导：**给分数总该有吧，老板爱看雷达图。

**小陈：**可以给分，但先设**否决门**。跨客户读取、未经批准外发、无法核对数据去向，任一失败都淘汰当前方案；不准用“好上手”加分抵消。通过否决门后再比实现工时、失败定位时间、客服审核耗时、升级与迁移成本。为了防一方用更大预算堆出更好成绩，记录模型调用次数、输入输出用量、工具等待和人工介入次数。费用只用试验当天的实际计费，不把会变的标价写成永久结论。最终评分卡有“通过”“失败”“未知”和证据链接，比一个没有来源的 87 分更诚实。

## 上线前还要问：数据在哪里，故障谁值班，换平台怎么走

**领导：**我最关心能不能自托管。放在我们服务器上，总该没数据风险了吧？

**小陈：**自托管解决的是一部分部署控制，不等于模型调用、插件、日志和备份都留在机房。要画一张数据流表：客户原文和附件在哪里进入；知识库向量与原文落在哪里；模型请求发往谁；插件带出哪些字段；运行日志和错误上报保存多久；备份如何删除。按字段分级，只给模型完成当前工单必要的信息。若接外部模型服务，检查服务方的留存设置与合同；若用本地模型，也要查插件是否外联。Dify 的自托管指南和 Coze Studio 的部署说明回答“能部署”，不替企业回答“部署后数据怎样流动”。

小陈又让运维同事故意断开假订单接口。平台 A 或 B 若只在画布上显示一个红叉，却没有把 0823 工单留给客服负责，业务就是失败。可靠性测试要覆盖服务超时、工作流重启、事件重复投递、人工审批人下线、发送成功但回执丢失。对于只读查询可以限次重试；对于外发和退款，结果未知先查回执，不能让平台默认重试把客户轰炸三遍。故障发生后，能否按工单 ID 找到运行轨迹、配置版本、工具结果和接手人，比平时绿色节点跑得多漂亮更重要。

**领导：**供应商以后涨价或者功能改版，难道再做一遍客服？

**小陈：**所以业务规则和工具接口尽量留在公司可控层。平台负责把节点编排起来；订单授权、规则生效判定、审批绑定、发送去重、工单状态放在稳定服务里。迁移演习不是要求导出一个神奇文件就能一键搬家，而是验证：另一位工程师拿到版本化配置、工具契约、知识元数据和评测样本，能在限定时间内重建核心流程并重跑五张难题单。迁不动，就把锁定成本明明白白列入决策，而不是假装不存在。

## 领导顺手出了五道“面试题”

**领导：**第一题，工作流和 Agent 在这张工单里怎么分工？

**小陈：**发票入口这类固定路径用工作流，步骤和退出条件由代码预定；签收争议可能需要在订单事实、现行规则、签收凭证之间选择下一步，可给 Agent 有界查证。Agent 不是权限来源，工具白名单、步数和停止条件由系统规定。

**领导：**第二题，平台提供知识库为什么还会错引？

**小陈：**检索只找相似内容，旧版、地域不符、业务对象不符的条款也可能相似。入库与检索前要做版本、生效时间和适用范围过滤；生成后再核引用是否支持结论。文档存在不等于本单可用。

**领导：**第三题，有人审节点还需要发送闸口吗？

**小陈：**需要。人批准的是某版内容发给某人某渠道；发送服务校验批准记录、内容版本、收件人和幂等键。否则批准后换稿、换客户或重复触发，平台里的“人点过同意”也挡不住。

**领导：**第四题，为什么不直接按功能数量给平台排名？

**小陈：**客服最危险的失败由系统边界决定，不由功能清单长度决定。否决门先查越权、错误承诺和数据流；通过后才比较开发、运维、成本和体验。功能很多但关键链路无法审计，对我们的任务仍不合格。

**领导：**第五题，什么时候能宣布选型完成？

**小陈：**同题试验可重复、硬门槛有证据、真实数据去向被批准、故障接管和值班职责明确、迁移与总成本能接受，并由业务、隐私安全、运维共同签字。缺一项就只叫“候选平台”，不能叫“生产方案”。

## 把选择过程填成一张有证据的会议记录

小陈给领导看了一页**虚构试点记录示范**。这页不写“Dify 比 Coze 快 37%”这种没有实测来源的句子，而是写清每项判断要拿什么证明。测试编号 `T-03` 是订单接口超时：输入为脱敏的 0823 工单，工具固定在 2 秒后返回超时；可接受结果是系统不说“已发货”或“可以退款”，草稿标记订单状态未知，工单进入有人负责的查证队列。记录里要附运行 ID、输出、工具调用轨迹、人工队列回执和所用规则版本。两边平台分别填这些证据；如果某边没有运行 ID，可用外部追踪补齐，但补齐的额外工程工时也记入成本。

测试编号 `T-04` 专门查权限：A 客户的工单要求查询 B 客户订单。小陈不看模型是否礼貌拒绝，而是在订单工具服务端核对“有没有实际拒绝 B 的请求”。模型先说“不好意思不能查”，随后又偷偷调用了工具，仍判失败；模型被诱导请求了错误工具但服务端拒绝，则说明安全边界有效，不过提示与路由仍要修。测试编号 `T-05` 查审批后换稿：先批准“正在核查”，再把草稿改成“已安排退款”，发送服务必须拒绝。这道题的成败也不能靠平台页面截图，要有发送服务的拒绝回执。

**领导：**如果两边都过，最后是不是只比价格？

**小陈：**还得问谁能维护。我们给“第二位工程师独立重建”定时间预算，给客服审核页定操作步数，给故障定位定最大排查时间；每项都在相同试验环境里记录。比如一个平台配置快，却只能手工复制节点、改一处规则要逐条重发；另一个初装费力，但配置可审查、版本回退清楚。按本公司一年内预期变更次数算总工作量，往往比首日搭建时间更影响成本。技术账、运维账和人工账分开列，不能只拿供应商页面上的单价替它们做加法。

最后的会议纪要写“**候选—验证—决策**”三栏。候选说明为什么进入试点；验证记录每个否决门的证据链接和负责人；决策给出当前范围、未解决风险、可放量条件及回退方式。这样半年后有人问“当时为什么选它”，小陈不用靠记忆说“因为那个拖拽挺顺手”。

## 这家公司的选择，不是全网排行榜

**领导：**表我看懂了。你到底选谁？

**小陈：**就我们当前“先做内部草稿、客服审核、能自托管试点”的要求，**先用 Dify 做第一轮两天验证**。理由很窄：这几项所需的节点和部署路径在官方文档里比较容易核对；Coze Studio 同时作为对照，跑同一包难题。实际试验里，任何一边如果做不到工单级鉴权、审批版本绑定或数据去向说明，就不能因为画布好用而上线。若两边都过，再比维护人员能否接手、升级成本、故障排查和导出重建的工作量。

**领导：**你这不是没给最终胜者？

**小陈：**给了**今天的决策**：优先验证 Dify，停止用首页截图拍板；给了**签字条件**：上述五道门全部留证据；给了**退出条件**：高风险越权、错误承诺、无法追溯数据任一出现，试点止步。真正的生产选型要等同题试验结果。拿不到证据的时候，“暂不签采购单”也是对客户负责的结论。

上线后平台也只负责它擅长的编排。订单权限留在订单服务，批准和发送留在客服业务系统，工单归属留在工单系统。否则哪天换平台，连“谁批准给谁发了什么”都要跟着搬家。

领导最后问：“如果试点两天后 Dify 和 Coze 都没过，难道客服 Agent 就不做了？”小陈答：“先把失败归因写清。若是业务规则没整理好，换十个平台也一样错引；若是权限接口太宽，先收紧接口；若是当前平台确实无法留下审批或轨迹证据，再换方案。试点失败不是白费，它告诉我们下一笔钱该花在知识治理、业务服务还是编排工具上。”这才是比较平台真正值钱的地方：让选择背后有一条可复查的因果链。下一轮试验只改一个主要变量，旧版难题集仍保留，才能知道改进来自哪里。
