**领导：**凌晨建索引跑到一半断了，明天再跑一遍就好。今天先让客服 Agent 答，客户总不能等搜索系统修完。

**小陈：**已经有一条答复把“十四天退货”与“数字权益仍按旧例外”拼在一起，引用一半来自新批次，一半来自旧批次。新政策确实改了普通商品期限，但数字权益那份例外也同时更新；索引任务只写进了前六千份文件，剩下四千份还停在旧版。现在让它答，就像把一本规章的上半部换新、下半部留旧，还在封面上盖“最新版”。

**领导：**那先让它只看旧索引，总比半新半旧强？

**小陈：**旧政策已经被法务撤销，高风险退货问题不能继续按旧规对客户承诺。我们先把受影响问答停在人工核查，保留可用的无关知识域；新索引在后台建完整、查漏文档与权限、回放通过，再把查询入口切过去。重跑只是构建动作，能否回答是另一道门。

政策、文件数、时间和故障记录均为教学虚构。文中使用 Azure AI Search 官方索引错误与别名能力作技术参照，具体发布原子性、批次清单与停答门槛是虚构公司的系统设计，不代表某产品自动提供全部机制。

## “任务失败”不是唯一坏状态，成功也可能少了几页

小陈先看构建日志：一万份来源清单里，六千份写入新索引，三千份尚未处理，一千份尝试过但有解析或权限元数据错误。任务返回“失败”很明显；更阴的是允许跳过坏文件后返回“成功”，却让一份关键政策没进索引。Azure 的[索引器错误与警告文档](https://learn.microsoft.com/en-us/azure/search/cognitive-search-common-errors-warnings)说明可配置容忍失败文档，警告不一定停止任务，执行历史会记录失败项。小陈因此不把作业状态 <code>success</code> 当发布许可：它只说明程序按配置结束，不说明业务需要的文档、段落与 ACL 都齐。

**领导：**一万份文件总会有一两份坏的，难道全库都停？

**小陈：**按知识域和风险分。若坏的是一份过期的内部会议便签，可以标缺失并继续发布不依赖它的域；若坏的是现行退货政策或它的例外条款，相关自动回答必须停。构建清单要知道每份来源的业务重要性、现行状态和依赖关系。我们不要求零警告才让任何人搜索，也不容许高风险来源缺页后还自称“已更新”。停答范围和失败范围要对应，不能一份政策坏了就让代码搜索也下线。

小陈为每次构建写一份不可变清单：<code>generation_id</code>、源快照时间、来源 ID 与版本、内容指纹、应有文档数、应有切块数、权限元数据版本、解析器与嵌入模型版本、构建任务状态、失败文件列表和回放结果。索引里的每个块都带 <code>generation_id</code> 与 <code>source_version</code>。从一条客户答复能反查它所用的代次和原始政策，事故时就不用猜“搜索结果到底哪天建的”。清单不必都展示给客服，但查询网关和排障看板必须能读。

## 旧版和新版并存，查询只能站在其中一边

**领导：**不能边建边用吗？新文档到了就先吃新的。

**小陈：**对独立、低风险资料可以做增量更新，但同一政策族的原文、例外、FAQ 与权限必须在一个可见版本里一致。今天的错答恰好是普通商品新规进入索引，数字权益例外还在旧分片。模型不会自动知道两个片段属于不同代次，只会把它们拼成语气完整的一句话。要么查询锁定旧代次且旧业务规则仍有效，要么暂停该域，等新代次完整发布；不能让一个回答从两个政策时间线各拿一半。

小陈把构建流程分成准备、核验、发布三段。后台按源快照构建 <code>index-v8-candidate</code>，与现行 <code>index-v7</code> 分开；做清单对账、解析错误审查、权限元数据核验和关键问答回放；通过后把查询入口指向 v8，并让缓存键跟代次走。Azure AI Search 的[索引别名文档](https://learn.microsoft.com/en-us/azure/search/search-how-to-alias)给了应用指向别名再更换底层索引的机制；具体请求中如何保持页面、关键词和向量结果同一代次仍要由应用架构设计。不要以为“用了别名”就自动修好业务数据快照。

**领导：**索引切换那一秒，正在回答的请求怎么办？

**小陈：**每次请求在入口处固定一个代次，整个检索、重排和引用都用它；新请求走新代次，已开始的旧请求要看旧业务规则是否仍允许完成。若法务已明确撤销旧政策，高风险旧请求不能因为“几秒前开始”就继续发送，外发前再核政策版本，必要时取消或交人。查询锁代次防技术混版，业务生效门防过期承诺。两把锁各管一件事，不能用“原子切别名”掩盖法务早已撤销旧规的事实。

## 构建失败后，怎么恢复而不把六千块又写重

小陈给构建批次做幂等。同一来源快照、解析版本和目标代次组成任务键；重试时检查已处理文件的指纹，内容相同就跳过或安全覆盖，不凭“写入次数”生成重复块。失败的一千份按错误类别处理：源文件权限拒绝要修授权，扫描 PDF 解析失败要补解析，嵌入服务限流可退避重试，字段映射不匹配要修模式。不能把四类错误都写成“网络抖了一下，重试三次”。重试完成后重新对账全量清单，不能只看失败队列清零。

**领导：**为什么不能就在现行索引里补那四千份？

**小陈：**若现行索引允许原位更新，要能证明同一查询不会同时看到新旧块，旧块删除与新块写入、权限更新和缓存失效要协调好。这个政策族跨多份资料，我们选择候选索引加一次切换，比较容易验证“整批同版”。低风险、小范围更新可用不同策略，但也得带版本并可回放。技术手段可变，原则是任何一条当前回答的证据都落在可解释、完整且业务有效的代次里。不能因为原位补写省硬盘，就把混版风险交给客户测试。

候选索引完成后，小陈做三类检查。数量检查：来源清单的关键文件和应有块都在，失败与跳过有明确原因；内容检查：抽取标题、表格、例外条款和有效期，确认解析没有把十四天写到错误产品；权限检查：普通客服、主管和撤权账号分别查询，看受限片段是否在不该见的人面前消失。最后问答回放包括“第八天普通商品”“第八天已激活数字权益”“旧订单跨生效日”“无权限报价”，每条核原文和代次。数量齐但内容错、内容齐但 ACL 丢，都是候选失败。

## “回滚索引”不等于“旧政策重新生效”

小陈又给构建清单补一项“删除账”。很多更新程序很会添加新块，却忘了原文删掉或撤回时要删除旧块。法务撤销 V7 文件，新批次里不再出现它，不代表旧索引里的 V7 块自动消失；如果只做增量写入，搜索仍可能召回一份已撤销政策。构建前先根据来源快照算“应有文件集合”，与旧集合求差，明确新增、修改、删除和权限变化四类操作。删除也要有回执：目标块在新代次里确实不可见，相关缓存与 Wiki 派生页已失效。没有删除账的“更新成功”，只是知识库越来越像装满旧报纸的抽屉。

**领导：**源系统在构建这一个小时里又改了一次，V8 快照不就过期了？

**小陈：**快照版本要固定，不能一边建一边拿到不同时间的资料。源系统若支持一致快照或变更序号，按同一水位读取；不支持时至少记录每份文件版本与读取时间，构建结束再对关键来源比对，发现跨水位的变化就把它列进下一批，必要时阻断本批发布。尤其已生效的政策撤销事件要走快路径：先停用依赖旧规的自动答，再等新批次。不能为了等完美快照无限拖，也不能装作一小时内业务世界静止不动。发布记录应说明“本代次覆盖到哪个来源水位”。

小陈把两个时钟并排：<code>source_watermark</code> 代表源资料已读到哪次变更，<code>published_generation</code> 代表查询当前使用哪批索引。若源水位领先发布代次，系统知道自己有更新债；对低风险知识可以显示“同步中”，对已生效的关键政策先阻断旧结论。构建任务的开始时间、完成时间和业务生效时间不能混成一项。业务上最危险的窗口不是“索引任务红了多久”，而是“旧规则失效到旧答案真正停下隔了多久”。这项延迟要监控，不能只监控作业是否运行。

**领导：**每个请求都查这么多版本，速度会不会被拖垮？

**小陈：**查询入口不用每次遍历全量清单，只要读取当前已发布代次与关键域的停答标志，再把代次传给检索、重排和缓存。清单对账在发布前后台做，来源变化事件更新停答状态。请求路径上要保留必要的轻量检查：用户权限有效、政策域可用、使用的代次仍有资格对当前问题回答。若状态服务不可用，高风险问题按配置转人，普通低风险问答可降级处理。把全部验证挪到每次请求会慢，把全部验证挪到凌晨批处理又会出现生效空窗；两者要按风险分工。

索引代次也包括解析与嵌入版本，不只是文件日期。若旧块用一种切分规则，新块改了结构化字段或向量维度，混写可能让关键词与向量候选代表不同段落，引用位置对不上。小陈在候选构建里固定解析器、切块参数、嵌入模型、字段模式和权限映射版本，必要时全量重建。若只改重排模型，不一定要重建原索引，但回放仍要检验关键条款有没有被丢。版本清单让团队知道什么变动需要重建、什么只需查询层切配置，而不是每次更新都“先跑了再说”。

## 发布前的完整性，不是只有一个 100% 进度条

小陈把完整性拆成五关。第一关是来源覆盖：应读的一万份里实际读到多少，关键文件是否全在。第二关是可解析性：文档读进来不等于标题、表格、脚注和例外条件都被正确抽取。第三关是索引一致性：每份来源的块数、版本和删除标记是否对齐，没有新旧重复。第四关是 ACL：块权限是否与原文和当前用户一致。第五关是问答行为：代表性问题能不能引用正确代次且不混版。五关都过才发布；某关允许豁免，也要由负责人写明影响范围和替代处理。不能把一个 100% 进度条盖在五种不同风险上。

**领导：**关键文件清单谁维护？今天的关键文件，明天可能就不重要了。

**小陈：**来源负责人维护重要级别、有效期和依赖域，构建器读取它而非自己猜。新政策获批时，它自动进入关键集合；旧政策被撤销时转入历史，只供按历史日期查询。客服、法务和技术一起定最小集合，例如退货总则、数字权益例外、当前审批表。若清单维护缺失，发布前的静态检查会提示“新增生效政策无重要级别”，默认不给它自动答权限。关键文件清单本身也有版本和审核记录，不能只存在小陈个人电脑上的一张 Excel。

小陈再看“成功但有警告”的作业。某份 PDF 的一页脚注提取失败，索引器没有停，页面主文仍入库；若脚注恰好写“数字权益不适用”，客服答案就会错。单看文档计数，一万份全在；单看任务状态，也是成功。为此，政策类资料要有结构校验：条款编号和附件数是否与原件一致，重要表格行列能否定位，随机抽几个条件回原文。模型可以协助识别“例外条款可能缺失”，但最终校验以原文和负责人的确认作准。错误警告要按内容重要性处理，不是简单划一条“允许 1% 文档失败”的线。

**领导：**如果缺的是一份大到处理不了的扫描件，总不能让整批永远卡着。

**小陈：**先把它从自动回答覆盖里明确排除，相关问题转人工或用原系统受控查看；同时分解扫描件、补 OCR 或人工录入关键条款，再进入下一批索引。不能一边承认它没被解析，一边让 Agent 对它所属政策说“我已经查过全部资料”。发布公告写清覆盖范围和缺口，客服看到题目命中缺口能直接转人。索引系统的工作是让已覆盖资料可查，不是靠未记录的缺页假装自己全知。

## 事故发生时，先保客户答复再修后台任务

小陈给值班人一张动作卡：确认源政策何时生效、旧版是否仍可用于历史或当前问题；按知识域打开停答标志，客服入口给出人工核查路径；冻结当前失败批次与日志，记录已发出的混版答复；核对来源清单和失败文档，修解析或权限；后台重建并回放；切入口后抽查真实请求；最后由业务负责人判定是否要联系已收到错话的客户。每一步有负责人和回执。工程师可以修索引，不能代法务宣布旧规有效；客服能跟客户解释等待核实，不能自己把数字权益条款猜出来。

**领导：**如果停答期间客服也查不到材料，人工接手不就只是换个人说“不知道”？

**小陈：**人工路径不能再依赖坏索引。值班客服拿到原始政策系统的受控链接和当前版本号，查不到就升给政策负责人；系统只给出已知的订单事实、问题分类和待核字段，不生成政策承诺。接手记录谁核了哪份原文、哪天回复客户，方便索引恢复后对账。若原始系统也故障，那就是更高一级的业务连续性问题，停止自动承诺并通知客户核实中的期限，不能让模型凭记忆补空白。恢复方案必须能在索引不可用时仍有一条真实可走的路。

小陈把“结果未知”也写进恢复单：构建日志说某块写入超时，不代表它一定没写；别立刻重复插入一份。先按来源 ID、块 ID、代次和指纹查目标索引，已写对的确认，缺的补写，写错的覆盖或删掉。同一构建批次的操作要能重复执行而不产生双份块。若索引服务暂时查不了目标状态，保持候选隔离，等可查再对账。恢复不是“再运行一遍看看”，而是以当前实际状态为准推进。这个原则与 Agent 外部工具结果未知时的幂等对账一样，只是对象换成了知识索引。

**领导：**V8 上线后发现一页错了，切回 V7 不就几秒？

**小陈：**技术上可能几秒，业务上未必允许。V7 政策若已被撤销，回到它会让客户重新听到旧承诺。正确动作可能是关闭受影响知识的自动回答、让客服回原始法务资料并交人核实，修正 V8.1 后再发。若 V8 只是索引排序错误，而 V7 的业务事实仍有效，才考虑切回 V7，同时保留事故记录。回滚能否用，取决于旧代次的业务有效性、权限状态和安全性，不能只看索引能不能指回去。

小陈还检查缓存。若查询入口已切 V8，但上一小时的答案缓存只按问题文本命中，客户仍会听到 V7。缓存键至少绑定知识域、索引代次、来源权限版本和请求人的可见范围；关键政策改动时按代次失效。静态页面、Wiki 摘要和下游报表也可能保存旧结果，若它们参与当前回答，同样要进入发布清单。索引只是证据链的一站，最终答复记录应能列出使用的页面、块与生成版本。

## 演练验收：故意把电拔在最尴尬的位置

小陈让测试环境模拟三次中断：处理 60% 时停构建服务，确认候选从未被查询；索引全部写完但校验未过时停发布器，确认入口仍指向安全状态；入口刚切完就让缓存服务失败，确认当前问答不会命中旧政策。另模拟一份关键 PDF 解析失败、一个普通销售撤权和法务撤销旧规。每次记录止血时间、告警、恢复步骤、代次清单与客户可见结果。演练不是看脚本最后能不能跑到 100%，是看失败中途有没有让客户听到混版或失效规则。

**领导：**那今天到底什么时候恢复自动答？

**小陈：**V8 候选对齐一万份来源清单，关键文件解析和 ACL 检查通过，回放四类问题正确，查询入口与缓存同代次，已撤销的 V7 不再用于现行回答，人工接管期间的工单有记录。任何一项缺失，受影响主题继续由客服查原文并交责任人，其他知识域正常服务。值班看板显示“V8 构建完成但未发布”或“已发布并回放通过”，不再只给一颗绿色的“任务成功”灯。

领导看着那条混版答复，终于没再说“明天重跑就好”。小陈给它标上当时的两个来源代次、停止自动答的时间和受影响工单清单，交客服负责人复核是否需要更正；然后把发布门与中断演练写进值班手册。知识库能自动更新很方便，前提是知道自己什么时候只更新了一半。让半成品躺在后台，比让它精神饱满地给客户讲错话强得多。
