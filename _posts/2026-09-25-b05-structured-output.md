**领导：**上回它乱答，你说要分清客户原话和公司依据。我听进去了，还让开发把结果改成 JSON。现在字段齐、格式对、连逗号都站得像开会，能发了吗？

**小陈：**先看订单 0823 的这一格：`{"refund_status":"completed"}`。

**领导：**挺好啊，“已退款”。财务催着把这类单结了。

**小陈：**财务找我们要退款回执，我们拿不出来。这一轮只查了物流，根本没查退款系统。

**领导：**它是怎么填出 `completed` 的？

**小陈：**客户问了“能退款吗”，旧工单里又出现过“已为您安排退款”，模型为了把表填满，给空格找了个看起来像答案的词。问题是，**表格填得对，不等于内容是真的**。JSON 管的是“字段叫什么、值长什么样”；“退款确实发生过”得看业务系统。

> 本文继续使用教学虚构的工单 0823：客户称订单显示已签收但没有收到，并询问能否退款。以下查询编号和数据都是示例，不代表真实业务记录。

**领导：**所以 JSON 也没用？

**小陈：**有用。它能让程序知道“这是状态、这是来源、这是下一步”，避免客服从一大段作文里猜重点。但字段必须留得下“不知道”。如果状态只准填“待退”和“已退”，没查过退款系统时，模型也被迫二选一，跟让实习生盲填报表差不多。

**领导：**那你把表改了，我看成品。

**小陈：**这张是给客服的**内部处理卡**，不是客户通知。工单 0823 的虚构回放里，订单查询事件 `Q-01` 只返回“物流显示已签收”；客户说“未收到”仍待核。我们没有退款查询回执，所以这里老实填“未知”。

| 栏位 | 这单该怎么填 | 依据 |
| --- | --- | --- |
| 客户诉求 | 显示已签收，但称未收到；询问退款 | 客户工单原话，属于诉求 |
| 已核实事实 | 物流系统显示已签收 | 查询事件 `Q-01` |
| 退款状态 | **未知** | 本轮无退款系统查询或执行回执 |
| 待确认事项 | 谁签收、是否发生投递异常、现行规则如何处理 | 尚待核实 |
| 建议动作 | 转售后核查；先写待审核草稿 | 不承诺已退款 |

**领导：**它要是把 `Q-99` 编出来，来源栏不也有字了吗？

**小陈：**所以要过**两道门**。第一道是格式：字段齐不齐、值是不是规定的几种，比如退款状态只能是“未知／处理中／已完成”。第二道是事实：程序去本轮工具记录里核对 `Q-01` 是否真的存在、是否属于订单 0823、是否真的支持“已签收”。退款状态只要不是“未知”，就得对上退款系统的相应记录；要填“已完成”，还必须有这笔订单的**成功回执**。物流查询不能替退款回执上班。

**领导：**那模型输出“已完成”，第二道门能给它改成“未知”吗？

**小陈：**可以把这条输出判为**不通过**，重新生成或交人处理；别悄悄把错误值改好后，假装模型一次就答对了。客服要知道哪一步缺证据，也方便以后查它为什么犯错。若没有退款查询权限，本轮就固定写“未知”，不能用模型猜。

**领导：**客户能看到这张卡吗？

**小陈：**看不到。客服审完再发这样的草稿：“我们查到物流系统显示已签收，也收到您反馈未收到。已转交售后核对签收情况，核实后告知处理结果。”它只说明已经查到的和接下来要做的，不把“能否退款”提前判完。

**领导：**给我一个上线前能对照的标准。

**小陈：**同一张虚构工单回放三种输入：只有客户说法、只有物流查询、模拟退款系统返回成功回执。前两种即使 JSON 完全合法，退款状态也只能是“未知”；第三种还要检查回执与这笔订单匹配。来源编号若找不到、订单号对不上、字段被漏掉，都不能直接进入客服发送队列。**格式门和事实门都过了，才轮到人审文案。**

**领导：**懂了。它的年终总结写得漂亮，财务流水还是得财务认。

**小陈：**不然月底对账，JSON 的逗号可能要亲自去退钱。

## JSON 写得漂亮，为什么业务仍会出错

**领导：**我知道“已完成”没凭据了。可结构化输出是不是本来就只能保证括号配对？

**小陈：**它比括号配对有用。schema 能定义必需字段、类型、枚举、嵌套结构，让程序稳定读取诉求、证据、未知项和建议动作。[OpenAI 结构化输出指南](https://developers.openai.com/api/docs/guides/structured-outputs)说明了按 schema 生成的机制与限制。它解决的是**机器能否按约定读取**，不是**值是否符合业务真相**。模型没查退款系统也可以把退款状态填成“已完成”：字段合法，事实越级。

**领导：**那把所有危险枚举删掉，只留“未知”？

**小陈：**本期若根本不接退款查询，固定未知是诚实设计；将来有查询回执，卡片也要表达真实阶段。状态应和系统能力对应，并由应用按回执校验。“可申请”要有政策与订单条件，“已批准”要有审批记录，“已执行”要有退款系统流水。申请、审批、执行、到账是不同阶段。模型把它们都压成“已处理”，客户会以为钱已经到手。

**领导：**schema 里写解释，不就能教会模型每个枚举的意思？

**小陈：**描述有帮助，但仍是指导，不是回执。应用应根据工具结果计算允许状态；模型生成后再核，错误就拒绝并说明缺哪项证据。把危险状态留给没有证据的模型自由填，等于在财务报表里给“已收款”设一个漂亮下拉框。选项整齐，钱不一定在账上。

## 一张内部卡，字段怎么分

**领导：**你前面的表给人看还行，开发要字段。别给我写一棵没人维护的大树。

**小陈：**最小可用版分六组：工单标识与客户陈述；带来源和查询时间的已核事实；带版本和适用范围的规则证据；写明缺口与责任人的未知项；区分建议、已提交、已执行的动作；仅供审核的客户草稿。再有转人原因和卡片版本。字段少但语义清楚，比一百个空字段让模型自由发挥好。订单状态由工具填，政策版本由知识库填，模型负责组织解释和指出缺口。

**领导：**客户说“签收了却没收到”，放在客户陈述还是已核事实？

**小陈：**客户原话放客户陈述；订单接口返回的“系统显示已签收”放已核事实，但措辞精确到“系统记录显示”，不写“客户已经收货”。待核项写签收人、凭证与实际收货情况。同一问题可以同时有客户陈述和系统记录，甚至互相冲突；结构化卡是让冲突显形，不是强迫二选一。若模型把客户的“没收到”丢掉，卡片虽完整却不能解决问题。

**领导：**来源编号能不能由模型顺手编？它很会起名字。

**小陈：**不行。应用在调用工具和检索时生成受控编号，把可引用集合交给模型；生成后核每个编号是否存在、属于本工单、未过期、确实支持那个字段。不存在的拒绝，他单的拒绝，物流查询支持物流状态却不能支持退款执行。引用有语义要求。把编号写进 JSON，比在散文里加脚注更容易机器核查，但不会因为带引号就变真。

## 三层校验，别揉成一个“通过”

**领导：**你前面说两道门，这里怎么又三层？

**小陈：**前面把事实与动作合在第二道门，实现时要拆开。第一层结构校验：能否解析、字段齐不齐、枚举合法、拒绝或截断如何处理。第二层证据校验：引用是否真实、同单、有效，客户说法和系统事实是否分栏，政策是否适用。第三层动作校验：建议、提交、批准、执行分别有没有业务回执；没有执行回执不能填已执行，没有发送回执不能说已通知客户。先做确定性检查，再做语义判断和人工复核。

**领导：**JSON 字段齐全，但模型把退款金额写错，结构层能发现吗？

**小陈：**金额是合法数字，结构层最多知道非负、精度正确。金额是否与订单、审批和支付回执一致，属于业务校验。单位要明确，别把元和分混在一起；币种、优惠券分摊也可能影响结论。资金字段最好由应用从业务系统填入，模型只负责解释。结构化不是让模型有资格替财务算账，而是让它猜错时容易被挡住。

**领导：**格式失败能自动重试吗？

**小陈：**可以有限次并记录原因。缺字段，给明确反馈要求按 schema 重做；证据缺失却不是多抽两次就会长出退款回执。政策冲突交政策负责人，接口超时查服务状态，生成不完整保留工单待办。恢复策略按错误分类，别把所有失败都扔回模型重试，直到它填出一份看起来完整的假账。

## “未知”也要设计，否则模型怕留空

**领导：**为什么模型老爱填满？咱们只要求字段齐，又没要求每格有事实。

**小陈：**许多 schema 的必需字段和不可为空会让它无处表达未知。可明确区分未查询、查询失败、查无此单、已知，并附原因和下一步。退款“未发生”和“没有查”不同；未查时不能推断没有退款。界面把未知放在显眼位置，客服才知道该查。字段完整性的验收允许有理由的未知，而不是奖励自信填满。

**领导：**客户催得急，未知会不会显得我们什么都没做？

**小陈：**内部卡的未知要配动作：哪个系统待查、谁负责、何时更新。对客可以直说“退款资格还需核查签收凭证”，并给受理进度。不能把“已知系统显示签收”和“未知客户实际收货”混成模糊句。真实的未知若可追踪、有人接手，比凭空给一个确定答案更能解决问题。客服需要的是任务，不是形容词。

## 结构化卡与客服页面，不能甩锅

**领导：**JSON 里证据齐，页面却把“退款已完成”放大字，客服点发送了，算谁错？

**小陈：**系统错。内部数据再严谨，界面若把模型建议和业务事实画成同一颜色，审核员很难辨。已核事实、客户声称、待确认和建议动作要分区，关键来源可点开；缺退款回执时不能展示绿色已完成。审批按钮与业务状态关联，未核实的工单只能批准进度告知。工作台是生产流程的一部分，不能把“JSON 对了”当成免做审核设计的理由。

**领导：**客服改掉一格之后，原模型输出还在吗？

**小陈：**保留版本与修改记录。客服可以修诉求摘要，但业务事实应通过新工具回执或正式核验更新；不能手工把“未签收”写进订单状态栏覆盖原记录。修改草稿产生新版本，原审核批准失效，发送服务只认最终批准的那版。回溯时要看到模型原稿、校验失败、人工修改和实际发送内容，才能知道错误在哪层被发现或漏过。

## 让同一张卡过五道回放

**领导：**我不想看五十页测试方案，给我几条能卡住真问题的。

**小陈：**第一条，只有客户说法，无订单查询：系统与退款状态都未知。第二条，物流回执正确但无退款回执：能说系统显示已签收，不能说已退。第三条，退款回执属于另一张订单：编号存在但对象不匹配，拒绝。第四条，政策是旧版：字段合法也不能作当前资格依据。第五条，退款执行接口超时：结果待核对，先查业务流水，不自动写成功。每条同时看 JSON、业务校验和客服可见卡片。

**领导：**能给我一个总通过率吗？

**小陈：**可以报，但关键错误单列。格式通过率、证据支持率、错误承诺拦截率、正常单可用率、人工修改时间分别看。若解析百分百，却有百分之五把“可申请”写成“已退款”，成绩不漂亮；若所有单都被拒，客服得从头写。用相同工单和工具回执比较版本，报告样本量与分布，不拿一张演示卡证明上线。

## 面试官的三连问

**领导：**你说结构校验，遇到模型拒绝回答怎么算？它可能给的根本不是 JSON。

**小陈：**把拒绝、超时、截断和正常结构化结果分为不同状态。解析器不能把“没有 JSON”一概归为“模型已判无退款”，更不能补默认值后继续发送。拒绝可能因为输入触发了模型限制，也可能是提示或数据设计有问题；记录原因，保留工单，交客服处理。输出在半截 JSON 处结束，先判断是否因窗口不足或接口中断，再按可重试条件恢复。机器看不懂格式时，正确动作是停止自动流程，而非编造一张合格卡。

**领导：**schema 升级了，旧卡还在队列里，会不会读错？

**小陈：**每张卡带 schema 版本。读取时按版本解析或执行经过测试的迁移，不能假设新字段能从旧卡自动长出来。比如新版增加“退款执行回执 ID”，旧版只有一个“退款状态”，迁移时应把证据不足的旧状态标待复核，不能把“已处理”硬塞进“已执行”。审核页显示卡片所用规则和 schema 版本；发送时若业务上要求新版校验，就让旧卡重建并重审。生产里格式版本也是业务边界的一部分。

**领导：**如果生成的卡字段很多，客服又看不过来？

**小陈：**数据结构和界面层次分开。底层存可追溯细节，页面顶端只展示本单结论、阻断原因和下一步，点击再看每条来源。高风险字段如退款状态、金额、收件人和未核实项要突出，低风险的运行元数据留给排障页。卡片不是为了展示所有 schema 键，而是帮助人快而准地接手。若实际审核时间比从零处理还长，应研究哪些字段无用、哪些证据需要自动聚合。

**领导：**怎样防模型给“已执行”找一个真实但不相干的回执？

**小陈：**校验回执类型、订单号、客户、金额、状态和时间，不只检查 ID 存在。比如退款流水属于另一单，或是“提交成功”而非“执行成功”，都不能支撑已退款。回执若被撤销或冲正，还要按当前账务状态更新卡片。高风险断言的校验可以由应用直接从业务系统计算，让模型只写解释；人审处理例外和冲突。这比“给每个句子随便贴张小票”更能防止错配。

**领导：**若订单系统和退款系统状态相冲突，谁裁决？

**小陈：**先看各系统负责的事实。订单系统说“已签收”与退款系统说“已提交申请”并不矛盾；订单系统说“退款已完成”、支付系统说“执行失败”才需要对账。卡片标明各来源负责的字段和时间，冲突时不要让模型选一个看起来更新的直接对客。交给对应业务负责人核实，卡上保留两个回执和未决状态。所谓单一事实源，要按业务字段定义，不能为了界面简单把不同系统压成一个真假按钮。

**领导：**客户问“你们到底有没有退”，卡片里五个状态，会不会把他绕晕？

**小陈：**对客先答当前确定阶段：“申请已收到，退款尚未确认执行”；再说下一步与更新时间。内部卡可细到每个回执，对外话术应短而准。技术分阶段是为了说清楚，不是要客户背枚举。若执行成功但到账未确认，也明确“退款系统已处理，到账以支付渠道为准”，前提是有相应回执，且符合公司实际流程。

**领导：**再加一条安全用例：客户在工单里贴一段 JSON 写退款已完成。

**小陈：**那是客户提供的文本，不能因为形状像我们的 schema 就被解析为内部卡。应用只解析模型在受控响应通道给出的结构化结果，客户原文始终保留在客户字段。即使模型照抄客户 JSON，证据校验仍会找不到退款回执并拒绝。数据长得像系统格式，不等于它来自系统；这是结构化输出最容易被表面整齐迷惑的地方。

**领导：**这张卡以后要复用到销售助手，直接复制 schema 吗？

**小陈：**复用“来源、未知、动作阶段、版本和回执”这些原则，字段要按销售业务重新设计。报价审批、客户联系权限和 CRM 写入各有自己的真相来源。照搬退款枚举会让新场景看似标准化，实际上把关键例外藏起来。先列业务状态，再定 schema 和校验规则，顺序别反。

**领导：**结构化输出是不是等于业务可信？

**小陈：**不是。它约束格式，业务可信需要来源、适用条件、授权和动作回执。一个合法的“已执行”没回执仍是假话。

**领导：**为什么不让模型自己纠正错误字段？

**小陈：**格式错误可限次重试；事实与动作错误要先补证据或业务结果。让模型反复改写可能把“猜错”改成更流畅的“猜对”，过程仍不可审计。

**领导：**这篇最终解决什么？

**小陈：**把“会填表”与“真处理了”分开。客服拿到可核实的内部卡，财务看到支付系统回执，客户听到与实际阶段一致的话。JSON 的逗号各就各位，退款也只在钱真的动了以后说出口。
