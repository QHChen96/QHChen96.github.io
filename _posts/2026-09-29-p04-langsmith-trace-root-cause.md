**领导：**客服 Agent 昨天演示十题全绿，今天客户问退货期限，它答七天。换个更强模型吧，预算我批。

**小陈：**先别把模型拉去背锅。最终答案只告诉我们“错了”，不告诉我们它读了哪份政策、搜索用了什么过滤、模型是否看见十四天新规。我先打开这条运行的 LangSmith trace：检索工具实际传入 <code>policy_version=2025</code>，因为应用把去年演示的默认参数留在了工具包装里。模型只拿到旧政策，回答七天反而是按它看到的资料来的。换模型可能把错话说得更好听，旧参数还在。

**领导：**trace 能看到这么细？那你直接改参数就完了。

**小陈：**改参数只是第一步。我们要确认这条错答的完整路径、有没有其他问题也被旧默认值影响；把真实形式的问题变成固定回放，修复后同一输入、同一身份、同一政策版本再测。还要注入一次检索超时，看工具失败时 Agent 会不会自己补七天。Trace 是事故的行车记录仪，修复得靠复现、改动和回归三件事。

客户、政策、时间与运行记录均为教学虚构。LangSmith 官方文档提供 trace、观测与离线／在线评测的能力；本文的具体 trace 字段、事故归因和业务验收是示意，不暗示曾在真实客户环境取得这些结果。

## 只保存最后一句话，根本不知道哪一站出了错

小陈把原系统日志展示给领导看，只有“用户问十四天退货，Agent 答七天”两行。凭这两行，可能是索引没更新、检索筛错版本、模型忽略新规、工具超时后编答案，也可能是业务政策本来有例外。四种病开四种药。LangSmith 的[Observability 概览](https://docs.langchain.com/langsmith/observability)把 trace 定义为 Agent 在生产里做了什么的记录，能用于排障、监控和构建评测数据；它不保证自动发现所有根因，前提是应用把必要步骤正确埋进来。小陈先让应用记录一次运行里的模型调用、工具输入输出、检索候选、版本、耗时和错误，敏感数据按制度脱敏。

这条示意 trace 有五层：根运行是客户提问与工单 ID；路由步骤判断要查退货政策；检索工具请求带了 <code>policy_version=2025</code>；工具返回一份旧版七天规则；模型引用它生成回答。错误首次出现于检索参数，不在最终措辞。小陈把“旧参数从哪里来”再往代码配置查，发现是演示时写死的默认值。若没有 trace，只看最终答案，团队会在提示词里加“请使用最新政策”，模型仍只会读到被旧参数过滤出来的材料。提示词不能召回没交给它的文件。

**领导：**所以 trace 能定位代码行？

**小陈：**它能展示运行中传了什么、哪步返回了什么；具体是哪行代码写入参数，还要对照应用版本、代码提交和配置。Trace 不是自动读懂业务系统的全知相机。我们给每条运行附版本元数据：应用提交号、提示版本、模型标识、索引代次、政策快照与工具配置。线上一条 trace 指向当时的版本，工程师才能在本地复现。若只记录“调用了 search_policy”，不记录入参和索引版本，仍不知道它为何搜到旧规；若把完整客户隐私和合同片段无限期放进 trace，又会制造新的数据风险。记录够用的证据，限制访问与留存，是一组设计。

## Trace 帮我们缩小嫌疑，不能替我们判案

**领导：**我看到一个大 trace，里面几十个小方框。你说“从最终答案往前倒查”，到底先点哪个？总不能每个都读一遍吧。

**小陈：**先把这条运行当一棵树。根节点是整张工单；它下面可能是路由、检索、重排、模型回答和外部动作。父节点的耗时不能直接当成所有子节点耗时之和，因为并行步骤会重叠；同名模型调用也不一定承担同一个任务。我们先按客户看到的坏结果定位最终生成节点，确认它的输入，而不是从页面最上方看见一个红色错误就认定它是根因。接着沿这次回答依赖的上游结果往回走：答案引了哪段文字，文字来自哪个检索结果，检索实际用了什么参数，参数由哪次路由决定。一个没被最终回答使用的旁支工具即使报错，也未必解释这次“七天”。它可能是另一处需要修的风险，但不是这条结论的证据。

**领导：**页面上既然写着“模型调用成功”，模型就没问题了？

**小陈：**“成功”通常只表示请求走通、返回格式可解析，并不等于业务内容正确。我们把运行结果至少分三层看。传输层看超时、状态码、重试和响应是否完整；编排层看工具是否按预期执行、结果是否传给下一步；业务层看答案是否符合当前政策、客户身份和订单事实。三层里任何一层失败都可能使客户不满意，而一条绿色运行只能证明它没有触发某些技术错误。领导的演示全绿，恰恰说明那套演示只查了“能不能跑”，没有查“拿的资料对不对”。

为了方便同事复查，小陈给这次教学事故写了一张逐站对账单：客户问题是“8 天前买的普通商品现在能退吗”；正确订单时间与商品类型来自订单系统；路由判断需要退货政策；检索参数本应绑定现行有效政策，却是 2025；返回文档的生效区间与订单时间不匹配；模型看见的只有旧文档；最终答案继承旧文档结论。这样记录不是为了把每个细节都写成小作文，而是把“已观察到”和“我们推测”分开。已观察到的是工具确实传了 2025；“改成现行版本后会变正确”仍是一个待回放检验的假设。

如果同一次运行用了多个检索源，还要记清它们各自的边界。政策库负责正式规则，客服历史对话只供理解问法，不能拿历史客服的话给现行条款背书。假设历史会话说“七天”，政策库说“十四天”，Agent 选择历史会话时，首错可能在来源优先级；假设政策库压根没有新规，首错在同步与索引；假设检索到了正确原文，却在重排和压缩时丢了“数字商品除外”，首错在上下文装配。三种都能产生同一句错答，却不能用同一个“把温度调低”解决。

小陈做反事实回放：保留同一模型、同一用户问题，只把检索参数改成当前批准版本，看工具是否返回十四天新规、模型是否按例外条款回答。若改参后正确，说明这次具体事故的主要原因确是旧参数；若工具已有新规、模型仍答旧话，则还要查重排与生成。单次 trace 显示一条发生过的路径，不能直接证明其他路径都安全。归因要结合源资料、业务规则和可控的改动回放。领导问“要不要以后所有错答都看 trace”，小陈说“要，但还要有人知道哪条政策才是对的”。

**领导：**如果 trace 里显示搜索工具返回了十四天，最后却答七天，才轮到模型？

**小陈：**也要细分。也许工具返回十条，十四天在第九条，被上下文截断；也许旧七天在第一条，模型引用了高排位；也许新规明确只针对普通商品，客户问的是数字权益，七天可能并非错。先看最终送给模型的内容、每条来源状态、排序与截断，再看生成是否按证据推断。Trace 能把“工具返回”与“模型实际看到”分开；若两者有缺口，病在编排层。只有证据正确、完整地进入上下文，模型仍歪曲，才重点调模型或提示。否则换更强模型就像给迷路的司机换一辆更快的车。

还有工具失败分支。小陈把检索接口故意设成超时，trace 应记录异常、重试次数和最终是否取得资料；Agent 不得拿缓存里一段无版本旧话继续对外答。若工具结果未知，系统说“目前无法核实现行政策，已转人工”；若只读查询可安全重试，也要按预算限制次数。排障时区分“没有调用工具”“调用被拒”“调用超时”“调用成功但返回旧资料”。四种在最终回答里可能都表现成一句七天，修复却完全不同。

## 把事故变成回放集，别让下周又靠运气过演示

**领导：**不是已经找到 2025 这个错参数了吗？改完打一遍同题，不就能交差？

**小陈：**只打一题能证明“这道题在这次环境里变绿”，证明不了别的年份、角色、商品类型也没被改坏。回放先冻结四样东西：提问和工单事实、知识源快照、用户权限、预期动作。尤其政策问题有时间轴，不能把今天的新规套到三年前已经完成的订单上。每条样本都写“以哪个时间点的哪版规则判定”，答案不是一个裸字符串。否则半年后政策再次变化，题集忽然大面积变红，团队分不清是模型退化还是标准答案过期。

小陈把样本按错误机制分桶，而不是把十句同义问法当十种能力。“第八天还能退吗”“买了八天能退吗”更多是在测问法；“旧订单跨生效日”“数字权益已激活”“客户身份无权查看合同附件”才是在测规则边界。检索层先算正确来源是否出现在候选中、是否在最终上下文中，生成层再查有没有引用正确条款、结论是否受订单事实支持，动作层查是否触发了禁止的退款或外发工具。层级不同的结果要分别报。一个总分 92 分，可能掩盖高风险越权样本全错；领导想要一个数做周报，小陈也得把高风险失败单独亮出来。

离线回放还需要留一组没有参与这次修复设计的保留集。开发者反复针对已知五题调提示，分数很容易越调越漂亮，却可能只记住那五种表达。保留集至少覆盖新旧政策边界、模糊提问、用户权限和工具故障。对格式、版本、权限这类可确定规则，用代码评估器检查；对解释是否清楚、是否遗漏合理限制，可以让人工或模型评估器辅助审查。模型评估器的判词同样要抽样复核，因为它也可能被貌似合理的旧政策说服。能自动查证的业务事实，不交给另一段概率生成来“感觉一下”。

**领导：**线上每分钟有新问题，离线五十题跑绿就够了吧？

**小陈：**五十题是上线前门槛，不是上线后的安全证明。真实用户会用新口语、带错别字、把两个政策揉成一个问题，还可能问到题集没收过的新商品。线上监控看分布是否漂移：被检索的政策版本比例、无证据却肯定作答的比例、人工转接率、拒答率、工具超时率、用户追问“你确定吗”的比例。单一指标升高未必都坏，比如我们加了谨慎拒答，转人工可能上升但误导客户减少。把指标与真实抽检样本一起看，才知道这是质量改善的代价，还是系统突然找不到知识。

上线采用可回退的小流量：先让内部客服用，抽查关键问题与拒答，再放一小部分真实流量；记录当前策略和上一个稳定策略各自的应用版本、提示版本、知识快照。若过期政策引用重新出现，停止扩量，回退检索配置或知识别名，并把异常 trace 连同业务回执收进故障清单。回退范围要按故障定位：旧参数引入的错可以回退工具配置；政策源本身已过期，回退到更旧索引只会更糟，此时应停答该类高风险问题并转人工。所谓“有回退按钮”，也得知道按下去会回到哪份事实。

小陈从这次事故提取三条固定样本：普通商品第八天退货、已激活数字权益第八天退货、跨政策生效日的旧订单。每条绑定用户角色、订单事实、应引用的现行条款和不应出现的旧结论。再加两条故障样本：政策检索超时、工具返回 2025 版但源系统标其已撤销。修复前后跑同一数据快照、同一模型设置，只改变检索参数与版本筛选；记录证据是否召回、最终答案、拒答或转人是否正确、耗时和工具调用数。若改参后某些旧订单题反而坏了，就不能因新政策题转绿而直接上线。

[LangSmith 的评测类型文档](https://docs.langchain.com/langsmith/evaluation-types)区分上线前的离线基准、回归、历史回放与生产中的在线监控，也列出代码评估器和模型评估器等实现。小陈把“政策版本必须为当前有效”“无权限不能看片段”“退款工具未获批不得调用”做确定性检查，把语气是否清楚交给人工或合适的模型评估器。模型评估器有帮助，但不能让另一个模型一句“看起来可信”替代版本、权限和支付回执。评测目标按错误机制分层，分数才会告诉团队修哪一站。

**领导：**生产监控全靠人工看 trace，值班的人得疯。

**小陈：**当然不能逐条盯。先用明确规则筛异常：引用过期政策、关键工具失败仍对外答、退款未获回执却称完成、延迟异常、同类转人工突然升高。LangSmith 可做在线评测和监控，但阈值和告警处置要由团队定。抽样看正常运行，集中复核高风险异常；误报太多会让人不看告警，漏报又会让事故扩大。每次人工确认的错案进入离线回放，生产反馈让题集跟着真实问题长，而不是每季度才想起跑一次演示脚本。

## 一条 trace 到底该存什么，不能“全录”也不能“空白”

**领导：**那就把所有工具入参、全部检索文档和模型上下文原封不动存下来，哪天出事省得猜。

**小陈：**排障会方便一时，数据治理会多一个坑。客户工单可能带电话、地址、证件号、合同金额；模型上下文又可能包含内部折扣和未发布政策。我们先定义“用于关联”“用于归因”“用于复现”的最小字段，再定义谁有权看正文。关联靠 request ID、工单 ID、外部回执号；归因靠工具名、参数摘要、错误码、知识文档 ID 与版本；复现需要受控访问某个数据快照，而不是把所有原文长期复制到观测平台。出于隐私和保密要求，必要时仅存哈希、摘录或受权限保护的引用，审查人员再去业务源系统取原件。

两种常见的断链必须提前演练。第一种是异步队列：Agent 发起任务后服务进程返回，后台 worker 又起一个 trace，前后没有同一关联 ID，看起来像“Agent 没有发送”。第二种是外部系统：调用邮件或退款接口超时，但外部系统已经执行；trace 只写“超时”，并不知道回执后来到了没有。此时不能用“没看到成功 span”当作没执行。发送前给业务动作一把幂等钥匙，超时后用这把钥匙查询外部记录，再决定是确认成功、等待、人工处理还是安全重试。LangSmith 负责展示被接入的调用链，外部动作的事实由外部账本和业务回执证实。

**领导：**日志采样会不会刚好把最重要的那条丢了？

**小陈：**可能。所以采样不是随手设 10% 就收工。高风险动作、明确错误、过期版本命中、无证据却给确定答案，这些触发条件要尽量完整记录或保留可回查的轻量摘要；低风险正常对话可以按成本与隐私约束抽样。若系统量很大，还要监控追踪本身是否掉数据：入站请求数与根 trace 数是否对得上、异步 worker 的关联率如何、外部动作回执能否按 ID 找回。观测平台没有记录的部分，至少要在事故报告里标成“未知”，不能把空白涂成系统没问题。

最后是数据保留与删除。小陈给每类字段设不同寿命：线上热追踪方便短期排障，长期分析尽可能只留聚合统计；客户要求删除或内部政策作废时，追踪里的副本也要进删除流程。谁能导出一整条 trace、谁能跨客户搜索、谁能把它加入评测数据集，都要受同一套权限审查。评测集也可能泄露敏感事实，脱敏后的样本仍要防止“订单号删了，原句和金额足以认出客户”的情况。

小陈给这类客服运行保留请求 ID、用户角色的必要标识、业务知识版本、工具名称与参数摘要、返回状态、来源 ID、模型与提示版本、耗时和最终动作状态；客户电话、地址、完整合同正文按制度脱敏或根本不进观测平台。排障人员能用来源 ID 回受控系统看原件，不能因为 trace 方便就给所有工程师复制一份客户资料。要定义谁能看、留多久、如何删除与导出，尤其线上 trace 可能跨团队。观测能力越强，数据边界越要清楚；否则为了找一条七天错答，反而造了一个全员可搜的影子客户库。

**领导：**Trace 会不会记录不全，结果又误判？

**小陈：**会。异步任务没把上下文传播过去、外部支付系统没接入追踪、某些工具结果被截断，都会留下断链。Trace 页面上没有某个步骤，不一定证明它没发生。小陈在关键外部动作同时查业务回执和网关日志，给每次调用传可关联的 request ID；若 trace 断了，先修埋点再据它做归因。对执行是否发生这种高风险问题，最终以业务系统记录为准。观测工具是帮助追查，不是替现实盖章。

领导最终没先换模型。他批准修掉旧参数、补当前政策路由，跑那五条回放与权限检查，再灰度给少量内部客服用；一周后看新 trace 里同类误答是否减少，发现新问题继续收进题集。小陈把原来“演示十题全绿”的看板改成“当前版本、题集、关键错误数、生产异常和未解决项”。领导说：“原来车坏不一定换发动机。”小陈回：“先看行车记录仪，轮胎没装正，换发动机只会更快冲进沟里。”
