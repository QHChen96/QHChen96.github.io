**领导：**三个研究 Agent 已经有了。让它们自己商量，合同专家找服务专家，服务专家找写作专家，写作专家再找合同专家。交流充分，答案自然完整。

**小陈：**交流充分可能是真的，完整得等到下个月。我们先规定谁有权决定下一步、谁必须回来交结果、谁负责把这轮工作结束。否则你画出来的是一个群聊邀请链接。

沿用**教学虚构**的星河制造续约准备任务：授权检查后，客户事实、合同政策、服务工单分别研究，最终生成有来源的内部草稿。我们把同一业务要求画成几种协作方式，比较控制权而不是给框架贴高级标签。文中伪代码用于解释设计，只有明确标为 SDK 示例的片段对应当前官方接口。

## 一、先读懂一条箭头究竟代表什么

**领导：**架构图里箭头不就是“发过去”吗？

**小陈：**至少可能是四件事：发一条消息、调用一个函数、移交本轮对话控制权，或者触发下一阶段任务。它们的返回路径、失败传播和权限规则都不同。同一张图如果不标清语义，开发甲会写函数返回，开发乙会写队列消息，开发丙会等用户继续说话。

函数调用通常有明确的调用者与返回值：主单元调用合同专家，拿到证据后继续自己的工作。消息投递可能只得到受理回执，业务结果晚些时候从另一条通道回来。对话交接则让另一个单元成为当前发言与决策的主体；它完成本轮答复时，不一定再自动回原来的协调者。工作流边表示满足条件后进入下一节点，控制者可以是图运行时，而不必是一个模型。

这些区别决定主状态怎么写。调用专家时可以记录`pending_tasks`和结果；交接时需要记录`active_agent`、交接原因、已收集信息和剩余目标；队列投递需要业务关联键、去重规则与回复期限。用一个`next_agent`字符串装下所有关系，最初很省事，出了超时后就不知道它是在等回复、等结果，还是已经换人接管。

**领导：**那我们最先选哪种？

**小陈：**续约准备是一个明确的后台产物，销售只需要一份草稿。先用主流程协调三个研究单元，结果都回来，再统一生成答案。用户不需要同时与三位专家对话，因此没有必要把三条研究分支都设计成交接。

## 二、主 Agent 调专家：借脑子，控制权还在主流程

在 Supervisor 或经理式结构中，主单元拥有整体目标，决定调用哪些能力、分派什么子目标、如何整合结果。专家负责有边界的任务，完成后把结果交回。这里的主单元可以是模型 Agent，也可以是确定性代码；“Supervisor”描述的是责任关系，不能只看它有没有调用大模型。

**领导：**专家也是 Agent，为什么还叫工具？

**小陈：**从主单元视角，它暴露的是一个可调用能力，有输入和输出。所以可以把 Agent 包装成工具。专家内部可能循环检索好几次，外层仍像调用一次函数。主单元不需要看到全部内部推理，只需要拿到可验收的证据包和状态。

[OpenAI Agents SDK 的编排指南](https://openai.github.io/openai-agents-python/multi_agent/)明确区分`Agent.as_tool()`与 handoff。下面是**SDK 配置示例**，展示前一种关系，省去业务工具和模型配置；运行时仍需配置相应模型服务，不能直接用于生产续约：

```python
from agents import Agent

contract = Agent(
    name="合同研究",
    instructions="只核对授权合同与现行政策，返回来源和未知项。"
)
service = Agent(
    name="工单研究",
    instructions="只整理当前客户的未解决工单及确认承诺。"
)
manager = Agent(
    name="续约协调",
    instructions="调用专家收集证据，只生成内部待审草稿。",
    tools=[
        contract.as_tool(
            tool_name="research_contract",
            tool_description="核对续约条款"
        ),
        service.as_tool(
            tool_name="research_service",
            tool_description="整理服务问题"
        )
    ]
)
```

这段只说明谁调用谁。它没有自动完成客户鉴权、证据 schema、合同版本校验、预算和人工审核。应用仍要把真实客户范围放进受控上下文，并在工具实现处检查授权。模型收到“只核对授权合同”是行为指令，实际访问控制必须由服务执行。专家工具返回一段文字也不自动成为合格证据，需要额外校验和结构化处理。

主单元不应把所有专家输出原样再读三遍。我们让每位专家返回关键事实、来源定位、冲突、未知和工件引用，主流程只展开当前决策所需部分。主单元还要检查是否重复派了同一任务：已有合格合同证据时，不该因为换了问法再开一轮相同检索。它可以要求专家补一个明确缺口，保留原任务与新尝试之间的关联。

**领导：**主 Agent 是不是就成单点了？

**小陈：**在逻辑责任上，它是收口点；在部署上可以通过持久状态与恢复机制避免一个进程倒下就全丢。更容易发生的瓶颈是它反复做无用决策。必需的三路研究由代码一次派出，通常比让经理模型逐条决定“现在该叫谁”更稳定。开放探索的部分再留给模型决定。

## 三、handoff：把接力棒交出去，就得承认接管发生了

**领导：**那用户问合同问题，让合同专家直接回答，这不更快？

**小陈：**这就是适合交接的场景：前台先判断问题属于合同，再让合同单元成为当前处理者。它可以追问缺失合同号，继续与用户确认。只要业务允许，就没有必要每次把答复送回经理翻译。

`handoff`的关键是接管，不是“调用后返回”四个字的换皮。SDK 通常把可交接目标表示成模型可选的工具；模型选中后，运行时更新活跃 Agent，后续使用目标 Agent 的指令与工具。交接前后的对话历史是否全部传递、哪些内容过滤掉，取决于实现与配置。我们应明确目标需要哪些已确认事实，不能默认整段历史既必要又安全。

[OpenAI handoffs 文档](https://openai.github.io/openai-agents-python/handoffs/)提供目标 Agent、交接参数 schema 和输入过滤等配置。尤其要注意：交接工具的`input_type`用于交接参数，不是自动替换下一位 Agent 的全部输入。把“交接原因”放进参数，并不等于目标已经拿到核验过的合同事实。真实业务数据应从受控上下文或授权工具读取。

一个完整的交接包应保留用户原目标、已确认客户身份、已完成步骤、未解决问题、可见证据和权限阶段。比如“客户已确认账号，但尚未确认合同版本”，下一位不能把前半句当成全部检查已完成。交接原因要描述事实：“问题涉及续约条款，转合同服务”，而不是“你是最厉害的专家”。后者能鼓舞电子士气，却不能帮助恢复流程。

**领导：**合同专家答完以后再转回来，不就一样了？

**小陈：**可以显式设计转回，但要说清什么时候转、交什么、原角色还剩哪些责任。不能假定框架替我们建立了业务调用栈。尤其在客服场景，用户已经转人工或转另一个专业服务时，旧 Agent 的晚到答复必须失效，否则会出现两个处理者同时对客户发言。

交接也不意味着所有子工作都必须串行。一个已经接管对话的专家仍然可以在内部并行调工具、或调用其他有边界的研究单元。真正顺序的，是当前对话由谁负责这一条控制链。用交接去拼装本来可以独立并行的三路研究，通常会增加不必要的传递；用交接保持连续专业对话，则有价值。

## 四、router 与扇出：选谁干活，和大家怎么回来是两回事

路由器回答“这项输入应交给哪个能力”。它可以由确定性规则、分类模型或两者组合实现。一个合同续约问题只进合同分支，一个横跨使用情况与服务风险的问题可以进入多条研究分支。路由结束不代表业务结束，结果如何汇合需要单独设计。

**领导：**那路由器只要选对专家就行？

**小陈：**还要有选不出来的结果。未知类别、缺少关键输入、多个领域冲突，都应有可处理的路径。分类模型硬选一个标签，表面路由成功，实际把复杂投诉送进 FAQ 专家，最后还得人工救场。路由输出最好包含候选能力、已知缺口和理由依据，但不要拿模型自己报的置信分数直接当经过校准的概率。

续约准备的路由可以先用业务规则：合同、使用事实和工单都是必需任务；外部新闻研究只在用户要求行业背景、且访问政策允许时启用。这样减少模型决策空间。若模型提出新任务，代码验证能力白名单、权限、任务数量与依赖，再批准派发。让模型建议分工，不等于让它自由创建任意工具或扩大预算。

扇出是生成多个可执行任务，扇入是按约定等待与合并。最容易漏的是扇入条件。必需合同分支失败时必须阻断相关续约建议；可选新闻超时可以生成注明缺口的草稿。系统要保存本轮预期任务集合，而不是数“收到了三条消息”就宣布完成。重复回执、旧尝试结果和取消后晚到消息都不能充当新的完成项。

## 五、把外层流程和内层循环分开画

**领导：**研究 Agent 自己还有循环，主流程也有循环，这是不是套娃？

**小陈：**是两种不同的循环。内层研究循环解决“还需要哪条证据”，外层流程解决“整体产物是否满足要求”。每层都有自己的预算和停止条件。如果只设一个全局最大轮数，子任务可能把额度耗完，主流程连结果都没来得及检查。

合同 Agent 的内循环可能是：检索合同，发现版本不明，再查政策登记，确认适用期，产出证据包。主流程则是：接收三路结果，校验结构与事实冲突，发现工单责任人缺失，只补问服务分支，重新验证草稿。补问必须指向具体缺口，不能让经理一句“再深入一点”把全队重新启动。否则所谓迭代就变成无期限返工。

下面是**编排伪代码**，接口由本文定义，重点是业务状态而非真实 SDK 语法：

```python
async def prepare_renewal(request):
    context = authorize_and_resolve_customer(request)
    plan = build_required_tasks(context)
    envelopes = await run_bounded(plan)
    evidence = validate_and_merge(plan, envelopes)

    if evidence.required_gaps:
        return blocked(evidence.required_gaps)

    draft = await write_internal_draft(evidence)
    issues = verify_claims(draft, evidence)
    if issues:
        return needs_revision(draft, issues)
    return awaiting_review(draft, evidence.references)
```

`authorize_and_resolve_customer`先做身份与授权；`build_required_tasks`生成稳定任务 ID 和必要性；`run_bounded`实现有限并发、超时和预算；`validate_and_merge`核验任务身份及证据，再合并。缺少必要材料时返回阻断结果，不调用写作去补编。`verify_claims`检查主张与来源的对应，最后的`awaiting_review`是一种业务状态，不能偷偷继续发送。

这段没有要求“经理一定是 Agent”。计划若稳定，可以全用代码；任务内部存在开放检索，才用模型循环。这样分层能把不可协商的约束留在确定性逻辑中。哪份证据必须有、谁能批准外发、总预算多大，不应该由经理 Agent 每次心情不同地重新决定。

## 受理回执、结果回传与用户答复，不是同一种消息

**领导：**合同服务已经回复“收到”，协调者为什么还在等？

**小陈：**收到表示任务受理，不表示证据通过。异步服务通常先发受理回执，再发结果或状态更新。我们要用消息类型和关联任务区分它们，只有合格结果才能解锁写作。把所有回复都放进同一聊天历史，很容易让模型看见“已受理”就误以为完成。

续约任务可以有三种明确事件：受理事件说明任务进入队列；完成事件带结果引用并等待验收；业务答复说明最终草稿处于待审。它们各自记录时间，不互相替代。连接断开后，协调者根据持久任务 ID 查询状态，而不是重新发一条全新的任务；服务重复发送回执时，主流程按事件 ID 去重。流式文本也只是产物片段，最后一块文字到达前不能宣布结构完整。对专业对话交接，则记录谁已接管本轮，而不是等待一份从未约定的研究报告。消息语义明确以后，用户进度、任务推进与对话控制才不会互相踩脚。

## 六、无负责人群聊，为什么最容易变成电子车轱辘

开放讨论并非毫无用途。需要提出多个方案、比较理由、反思不确定问题时，多个角色可能提供不同探索路径。麻烦在于，讨论过程不能替代完成判定。续约准备至少要有必要证据集合、未解决冲突清单和产物标准。没有这些，模型很容易把“我同意上一位专家”当成进展。

**领导：**那设置一个“总结专家”，专门喊散会。

**小陈：**总结专家也得拿到结束规则。它看见五段流畅文本，不一定知道合同分支从未读到生效版本。我们要统计的是必需任务被验收的数量、缺口是否关闭、产物是否满足约束，而不是发言轮数。总结者有权收尾，但不能有权把缺失证据宣布为事实。

防止无效循环可以建立进展指纹：当前任务集合、合格证据版本、未解决问题、草稿版本。连续几轮指纹没有变化，又没有合法的等待理由，就返回停滞状态，带出具体缺口。这个指纹只是辅助判停，不能对自然语言整段做哈希就声称有进展；换措辞但没有新增证据，仍属于同一个问题。

还要限制派生深度和派生数量。专家再次派专家时，需要继承客户范围、剩余预算与父任务身份；不允许子任务扩大权限或重新获得完整预算。三层已经能覆盖的研究，不必因为角色提示里的“必要时寻求帮助”扩张成一棵无法收口的树。父单元终止时，子任务如何取消、晚到结果怎样处理，也应写在协议里。

## 七、谁能宣布“整个任务成功”

**领导：**三个研究 Agent 都说成功，系统还敢失败？

**小陈：**当然。分支成功只说明各自交了东西。主任务要检查结果属于同一个客户、符合这轮版本、覆盖必需字段、不存在未处理的关键冲突。每位专家的状态都可以是成功，最终草稿仍可能不合格。

我们把完成拆成四级：任务执行结束、分支产物通过验收、整体草稿通过事实验证、业务审核通过。每一级都有不同责任人。执行器能宣布“函数返回了”，不能宣布“合同可用”；证据验证器能宣布“引用存在并属于目标合同”，不能替业务批准价格；业务审核通过也不自动意味着外部发送成功，发送回执属于另一段动作流程。

如果图框架把多个节点完成后推进下一超步，它提供的是调度语义；实际条件仍由状态和边定义。LangGraph 这类框架可以将固定流、条件分支和动态任务组合起来，但我们仍要明确状态 reducer、必要分支集合与汇流门。后面会专门解释为何最后写入覆盖、结果乱序和任务重试会破坏“看似都完成”的流程。

**领导：**经理 Agent 能替人工审核吗？

**小陈：**若业务已经明确批准某类低风险动作自动执行，可以把相应规则做成确定性门；这不是经理自己争取来的权限。对于本案例的折扣和客户承诺，仍按业务审核。系统必须知道审批绑定了哪个草稿版本、哪些内容、哪位有权限的人，不能把“上一轮我同意了”应用到被改过的新草稿。

## 八、把交付责任写成一张表

| 组件 | 拥有的决定 | 不应独自决定的事 |
| --- | --- | --- |
| 授权与身份服务 | 可访问的客户对象和数据范围 | 商业承诺是否合理 |
| 编排器 | 派发、等待、补任务、结束流程 | 在缺证据时宣布事实成立 |
| 研究 Agent | 在允许来源中如何找证据 | 扩大客户范围或批准价格 |
| 结果校验器 | 结构、版本、任务归属与必需覆盖 | 代替专业解释争议条款 |
| 写作 Agent | 组织有依据的内部草稿 | 把建议升级成已获批准 |
| 业务审核者 | 对具体版本作批准或驳回 | 推定外部动作已成功 |

表里没有“全能大脑”，也没有“大家共同负责”。明确的责任不会降低灵活性，反而让开放研究有一个可恢复的外壳。团队维护各自的 Agent 时，应把输入输出契约和错误口径当作接口测试的对象；提示词改版不能悄悄改变返回结构，让整个流程靠猜。

上线前的演示应包含三个故障：合同专家返回阻断，经理不能生成确定续约条款；用户专业问答交接后，旧角色不能再外发；可选分支超时，主流程说明缺口并按既定规则继续。演示全员成功只证明快乐路径，看到控制权在异常时仍一致，才说明编排基本站得住。

## 九、领导三连问，答案写进验收单

**领导：**什么时候用经理式，什么时候交接？

**小陈：**需要统一产物、汇合多份研究时用经理式或代码协调；需要一个专业角色持续直接处理用户对话时用交接。两者可以组合，但每一条边必须说清是返回结果还是转移控制权。

**领导：**模型编排和代码编排只能二选一？

**小陈：**不用。身份、必需分支、预算与审批用代码；证据探索与任务内的工具选择交给模型。可变的决策留给模型，明确的业务约束由运行时落实。组合以后仍保留可观察状态，不让“智能”吞掉责任。

**领导：**群聊式协作到底什么时候能用？

**小陈：**在有明确产物、有限轮数和独立验收的讨论环节里用。把它当一段产生候选意见的过程，最后按证据和业务规则收口。没有进展就停，有必要材料缺失就阻断，不能为了“协作感”让角色互相道谢到凌晨。

这一篇交出的不是更多箭头，而是控制权表、任务回传路径和终止规则。下一篇接着处理最现实的麻烦：合同专家说可以九折，服务专家说必须先解决投诉，主流程怎样把两份材料合成一份能信的结论。
