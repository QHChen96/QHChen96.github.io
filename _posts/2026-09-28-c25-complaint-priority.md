**领导：**客户写“我要投诉到总部”，为什么机器人回“送您一张券”？

**小陈：**系统只看到了“对配送不满意”，命中了安抚模板。它把**客户在升级投诉**误当成**客户想要补偿**。这不是文案问题，是路由错了：本该有人接的单被普通问答吞掉。

领导问能否把“投诉”两个字一出现就设最高优先级。小陈打开另一单：“我想问，投诉入口在哪？”这人要的是操作说明，不一定已经发生紧急事故。再看一单没有写“投诉”，却说“快递员把包裹放门口，我现在找不到，里面是急用药品”。只盯关键词，既会堵满高优队列，也会漏掉真要紧的单。

## 把三件事分开判，再合成处理路径

**小陈：**第一列是**意图**：查进度、请求处理、正式投诉、取消服务等；第二列是**风险**：是否涉及隐私、安全、错误承诺、可能扩大损失；第三列是**紧急度**：是否有明确时点和等待代价。身份与证据不足另打标，不能凭模型“看起来很像”填满空白。分类模型可以提供候选，业务规则决定哪些词句直接触发人工复核。

| 例句 | 意图与风险判断 | 路由 |
| --- | --- | --- |
| “发票在哪下载？” | 固定入口、低风险 | 帮助流程，失败再升级 |
| “投诉入口在哪里？” | 查询入口，未证实紧急损失 | 给入口，同时保留人工入口 |
| “我投诉过三次还没人回，今天要给我结果” | 已升级投诉、重复联系 | 高优投诉队列，带历史工单 |
| “配送员把含药品的包裹丢失了，今晚就要用” | 可能有紧急影响，事实待核 | 立即转人工；不自动承诺赔付 |

**领导：**模型拿不准怎么办？总不能所有模糊话都转人。

**小陈：**让不确定性显形：低置信度但低风险的入口题，可以澄清一句；高风险信号一旦出现，即使意图分类不确定，也先进人工预审队列。规则命中原因、模型建议、原句片段和当前工单历史都显示给接单人。Agent 在等人期间可以确认“已收到，会由专人核对”，不能继续推优惠券，也不能许诺处理结果。

实际分流写成一段可解释的顺序：先查硬规则（已立案投诉、重复升级、明确人身或重大财产影响、身份与订单冲突），命中就进人工；再让模型判断普通意图和需澄清项；最后由路由服务结合工单历史与班次队列决定去向。模型输出只是一份建议，路由服务保存它依据的文本片段和最终规则 ID。这样误分流发生后能查到是模型漏认了“急用”，还是硬规则没有覆盖“第二次投诉”。

**领导：**高优队列要是塞满了呢？

**小陈：**设容量和升级链，不让高优标签变成另一个无人看的筐。达到阈值时通知值班负责人增援或手动改派；超过承诺时限而无人接手，自动升级到备用队列。与此同时，持续看高优队列里的误报比例：如果十张里八张只是问投诉入口，优先修分类和规则，而不是让客服夜夜加班。低优队列也不能无限等待，普通咨询同样有最晚处理时间。

规则冲突时还有先后顺序：明确的安全或隐私风险先于普通意图，已存在的人工投诉待办先于新的营销建议，身份未核验先于任何订单详情查询。路由服务把最终结果和被覆盖的建议都留在轨迹里。比如模型说“客户似乎想要补偿”，硬规则说“客户明确要求投诉且前两次未解决”，最终必须进投诉队列。客服可以纠正误分流，纠正原因会进入下一轮规则和样本集，而不是只在聊天群里骂机器人。

**领导：**排队之后谁保证有人接？

**小陈：**队列要写责任人与时限。高优投诉有班次负责人和超时升级；若某队列无人在线，路由不能显示“已转人工”就算结束，要走备用值班队列。每一次改派都回写工单。实际客服平台也把队列与分配作为独立配置，[Microsoft Dynamics 365 的统一路由文档](https://learn.microsoft.com/en-us/dynamics365/customer-service/administer/overview-unified-routing)可作为理解队列机制的参考；我们自己的时限与风险规则仍由业务定。

验收不只测“投诉”关键词。拿已知升级投诉、普通抱怨、紧急影响、反问句和讽刺话语做回放，重点看**漏进高风险队列**与**误把低风险全塞进去**。一周后抽查高优单是否按时有人接、普通单等待是否恶化、转人后客户是否仍重复讲述。领导要的不是一张红黄绿热力图，而是真正要紧的单没有在队尾吃灰。

小陈把最初那张错单重新跑一遍。新路由看到“我要投诉到总部”与过去两次未解决记录，直接生成投诉队列待办，卡上显示前两次的处理结论与未决项；对客户只说“已记录投诉，将由负责团队核查”，不发券。客服接手后核对实际诉求，再决定是否给补偿。**优惠券不是禁词，只是不能拿它堵住客户正在说的事。**

## 第一层原理：意图、严重度、紧急度、置信度为什么要分开

**领导：**我不想让客服盯四个标签。不能算一个总分，超过 80 就转人工？

**小陈：**总分容易把危险平均掉。客户只是问“投诉入口在哪”，意图和关键词像投诉，但未出现实际损失；客户没说“投诉”，却描述急需的包裹丢失，风险和紧急度可能很高。再有一位客户明确要求查另一人的订单，问题不一定紧急，却有权限风险。把这些加成一个分数，可能用“表述不激烈”抵消“跨客户查询”。正确做法是先识别**不可用平均值抵消的硬边界**，再给普通队列排序。

意图回答“客户想做什么”，例如查入口、询进度、要求处理、正式投诉；严重度回答“如果处理错会造成什么影响”，例如普通等待、错误承诺、隐私泄露或可能扩大损失；紧急度回答“多久之后影响会明显增加”，例如今天必须核查的时点；置信度回答“系统对前面三个判断有多少证据”。这四列分别有来源。模型可从原话提取候选意图，历史工单和业务规则提供风险线索，订单系统提供状态，班次表提供可用队列。缺证据就留空或标待核，不能用一个高置信度的语言模型回答覆盖业务系统的空白。

**领导：**那硬规则优先到什么程度？

**小陈：**先明确权限制止与安全风险，再看已经存在的投诉升级、重复未解决、紧急影响；这些条件命中时，模型推荐的营销或 FAQ 路径只能作为被覆盖的建议留在轨迹。硬规则也要有负责人和版本，不能在代码里写一堆无人维护的关键词。比如“投诉入口在哪里”单凭“投诉”不触发正式投诉队列；“我已经投诉三次还没人联系”结合历史记录才升级。判断既看原话，也看**同一案例过去发生了什么**。

## 第二层实现：路由是一条决策链，不是一句模型分类

小陈写了一份最小路由结果，供工单系统而非模型直接消费：

```json
{
  "ticket_id": "0823",
  "intent": "complaint_escalation",
  "risk_flags": ["repeat_contact", "unresolved_claim"],
  "urgency": "high",
  "evidence_refs": ["msg-18", "ticket-0711", "ticket-0786"],
  "matched_rule": "route-complaint-v4",
  "target_queue": "complaint_duty",
  "fallback_queue": "service_manager_oncall",
  "needs_human_ack": true
}
```

这里的字段是虚构业务接口，不是某平台默认格式。路由服务先验证引用的历史工单属于当前客户和当前诉求，再查规则版本，最后写入目标队列与备用队列。若身份尚未核验，`evidence_refs` 不能把别人投诉记录带给模型。若客服后来判断“这是问投诉入口”，可以更正意图与路由，但更正要记原因；下一轮评测集加入这张单，不能只给模型改一个提示词就算修好。

**领导：**模型信心分数低，是否一律转人？

**小陈：**还得结合风险。低风险入口题置信度低，可先澄清“您是想查询投诉入口，还是提交已有投诉的进度？”；有隐私、安全或重大损失信号时，哪怕模型只给 0.4，也应先交人工预审，避免漏判。置信度本身也未必校准，0.8 不天然意味着十件里八件正确。用历史标注样本分桶检查“给 0.8 的样本真实准确率如何”，按场景调阈值。更重要的是，把“高风险漏转”单独统计，不用总准确率掩盖它。

路由完成后，工单系统还要拿到队列**接受回执**。进队列与具体客服接手是两步，不能只要 API 返回 200 就告诉客户“专人正在处理”。若队列下班，备用值班队列接收；若两边都不可用，创建有主的故障待办并告警，客户得到准确的处理预期。像 [Microsoft 的工作分类规则](https://learn.microsoft.com/en-us/dynamics365/customer-service/administer/configure-work-classification)与[队列分配文档](https://learn.microsoft.com/en-us/dynamics365/customer-service/administer/assignment-methods)展示的，分类、分配和容量是不同环节；我们的业务约束也必须分别落地。

## 第三层现场：高优队列塞满后，不能让普通客户也永远等

**领导：**大促当晚投诉突然翻倍，高优队列排了四十张。是不是把所有客服都拉去处理投诉？

**小陈：**先看容量和技能。严重隐私事件、可能扩大损失的单由具备权限的值班人立即接；普通升级投诉按等待时间与影响排序。普通入口咨询不该无限推后，至少给准确的等待预期和自助入口，超过本队列的服务承诺也要升级。把所有人拉到高优队列，可能导致原本三分钟能解决的发票问题积成第二波投诉。队列策略要在“高风险不漏”和“整体服务可用”之间用容量数据做决定，而不是看板一片红就手动全改最高优。

小陈给班长看三项实时信号：每队列待接数量、最老未接工单的等待时间、当前可接手且具备权限的人数。再加一项“高优误报率”，通过抽样复核判断规则是否把大量问入口的客户塞进投诉队列。容量不够时先增援，再查是否规则过宽；不能通过偷偷下调优先级让红色数字消失。不同队列的处理时限是公司服务承诺，应由业务负责人定，本文不替任何行业写法定分钟数。

**领导：**客服接过单以后还发现它其实是更高风险呢？

**小陈：**允许人工升级并保留原路由轨迹。客服看到新证据，例如客户已多次联系、订单涉及重要物品或错误回复已外发，可把单升级到有权限的专员队列；系统更新责任人和时限，并通知原队列。反向降级也要有理由，不能为了冲 KPI 把麻烦单踢回普通队列。无论升级还是降级，客户先前已收到的承诺仍在工单里，不能随着队列变化消失。

## 第四层评测：要同时查漏判与误报

小陈从历史工单里抽四组样本：明确高风险、表达隐晦但实际高风险、普通不满、仅咨询投诉入口。每条由客服负责人标注可接受路由与理由，标注争议先裁决再纳入固定集。离线回放记录混淆矩阵：高风险被错放普通队列是**漏判**，普通单被送高优是**误报**。两者成本不同，不用一个“分类准确率 95%”遮住高风险那 5%。样本集还按渠道、班次和规则版本分层，避免模型只会读 App 标准文本，看不懂微信语音转写和客户的反话。

线上灰度时保留人工复核，观察的不只是哪条队列被命中，还看“多久有人接”“客服是否重分”“客户是否再次联系”。一条工单进了正确队列但过了两天无人接，路由模型再准也没解决业务问题。若新规则让高优漏判减少，却令误报暴涨、普通队列等待翻倍，要调整策略和增援，而不是把模型准确率当最终胜利。高风险红线一旦破，能按路由规则版本圈定受影响工单并回退到上一版。

## 领导临时出了五道面试题

**领导：**第一题，为什么关键词“投诉”不够？

**小陈：**它分不清查询投诉入口与正式升级，也漏掉不用“投诉”一词表达的紧急损失。要看诉求、历史联系和业务证据，关键词最多是一条候选信号。

**领导：**第二题，意图和优先级是什么关系？

**小陈：**意图描述想做的事，优先级决定资源先处理哪件事。同样是查订单，涉及隐私冲突和普通进度查询的风险不同；同样是投诉，已多次未解决和首次询问入口的紧急度不同。不能用一个意图标签直接决定排队顺序。

**领导：**第三题，模型置信度能当业务风险吗？

**小陈：**不能。置信度是模型对自己分类的估计，且需校准；风险是处理错的后果。高风险信号出现时即使分类不确定也应人工预审，低风险不确定可以澄清。风险由业务规则与事实共同决定。

**领导：**第四题，队列分配成功等于转人工成功吗？

**小陈：**不等于。入队、具体客服接手、处理完成是三种回执。无人接手时必须有超时提醒与备用队列，客户告知也要符合真实状态。

**领导：**第五题，怎么防团队为了降低转人工率而压低优先级？

**小陈：**同时看高风险漏转、同案复联、投诉升级和人工接手时长，并抽查被判普通的工单。路由更正与规则版本留痕，任何优先级变更都能追到理由和操作者。

## 把那张送券错单复盘到具体哪一步

小陈把最初那张工单按时间拉开。10:00 客户说“已经联系两次，今天再没人处理，我要投诉到总部”；10:00:01 文本分类只抽出“配送不满意”；10:00:02 营销安抚流程找到一张可用优惠券；10:00:03 机器人发出“送券”草稿；10:05 客户再次追问，普通队列尚未有人接手。错误不是“优惠券文案太轻浮”这么简单：分类没有读取同案历史，路由没有重复未解决的硬规则，发送前也没有拦住正式投诉进入营销流程。三处缺口必须分别修。

修完后同单重放：入口先关联该客户前两次已核实但未解决的工单；规则 `route-complaint-v4` 命中“重复联系且明确升级”，路由到投诉值班队列；Agent 只生成内部摘要，列客户原话、前两次处理结果和未决事实，不给补偿承诺；队列返回入队回执后，对客户告知“已记录投诉，将由负责团队核查”；具体客服接手后，再按政策决定是否补偿。每一步都有 `ticket_id` 和规则版本，回放报告能指出若漏了哪条历史，结果会怎样变化。

**领导：**那优惠券要不要从系统里彻底删掉？

**小陈：**不用。客户诉求查清、补偿条件满足且经授权时，优惠券可能是合适的处理手段；但它是**处理决定之后的动作**，不是看到负面情绪就自动触发的入口。我们把营销工具从投诉路由阶段移走，只允许有权限客服在核实后提出。这样不靠禁止所有补偿来防事故，而是把动作放回正确的业务顺序。

再看一个相反的误报：客户只问“投诉入口在哪里，我想了解流程”，系统若立刻拉响最高级告警，会占掉真正急单的席位。修复后的规则给出入口并保留人工选项，若客户随后补充“我已经投诉三次无人回复”，才更新风险和队列。分类要允许随着新证据改变，不能把第一次猜测写成永远不可逆的标签。

领导把验收单最后一行写成：“坏单必须被拦，普通单仍能走。”小陈又补了可操作的检查：高风险样本每条都要找到目标队列和接手回执；普通样本不能大面积挤进高优；任何队列无人在线都能落到备用值班人；被客服纠正的路由在下一轮回放里重现。只有这些同时成立，系统才不是把错误从机器人回复挪到了人工队列里。

小陈还拒绝把所有错误折成一个“平均损失”。高风险投诉漏转可能让客户迟迟得不到处理，误把普通问题转高优则占用稀缺坐席，两者都要量，但权重应由业务负责人根据后果确定。离线测试可以分别报高风险召回、普通问题误报和人工接手延迟；上线门槛先规定最严重的漏判不能出现，再看整体效率。若测试集只有十条高风险样本，即使十条全对，也不足以证明罕见表达一定能被识别；灰度期间仍需抽查和可随时暂停的规则开关。

**领导：**客户在电话里情绪很激动，转写文本漏了半句怎么办？

**小陈：**把语音识别低可信或文本缺失单独标记，不能把缺字后的“普通抱怨”当完整证据。若出现风险关键词、重复联系或无法确认事实，先给人工听原始片段；原始通话按权限访问和保留，不复制到每个模型日志。渠道质量本身是路由输入的一部分，模型不能因为看不清就假装看懂。客服复核时也应能一键标注“转写有误”，让这类问题与模型分类错误分开统计。转写缺失的样本要进入回放集，修复后再重新验证路由。

**领导：**客户连发三条催单，优先级是不是自动涨三级？

**小陈：**重复消息不等于风险变高，要结合业务后果、服务承诺到期、客户权益和是否存在错误承诺。可把三条归同一事件，保留最早等待时间，避免刷消息挤掉真正紧急的退款或隐私事故。队列规则给客服可解释的原因，并允许人工纠偏；看高优先级命中与误升比例，不只看谁喊得最响。
