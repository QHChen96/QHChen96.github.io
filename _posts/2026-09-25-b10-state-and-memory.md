**领导：**刚才那个 Agent 还叫客户“0823 订单的朋友”，我换个窗口，它又问订单号。它失忆比我周一早会还快。

**小陈：**新窗口发起的是新一轮请求。如果应用没把必要历史和状态带过去，模型只能看见这次收到的内容。网页上还能翻到旧聊天，不代表模型这一轮也看到了。

**领导：**那全量聊天记录每次都塞进去。

**小陈：**先别给它灌一整年的客服群聊。虚构工单 0823 里，我们需要保存的不是“它昨天说过什么”这么简单。客户说没收到、订单系统显示已签收、查过哪条现行规则、有没有真的发消息或退款，这几样东西来源不同，不能全装一个“记忆”抽屉。

## 领导：“你给我画个抽屉柜。”

**小陈：**我们按用途分五格。这是项目的设计分法，不是某个产品强制要求的名称。

| 抽屉 | 放什么 | 工单 0823 的例子 | 重新打开时怎么用 |
| --- | --- | --- | --- |
| 本轮上下文 | 此次模型真正需要读的材料 | 当前问题、有效规则片段、已核实订单状态 | 每轮按任务装入，避免旧消息淹没关键事实 |
| 会话历史 | 用户与助手说过的话 | 客户此前补充“门卫也没收到” | 选取相关部分续接，不能把助手的旧说法当业务事实 |
| 任务状态 | 这张工单办到哪一步 | 已查订单，待核对签收凭证，责任人为售后 | 应用保存，重新进入后接着办 |
| 长期资料 | 可反复检索的公司知识 | 当前售后规则及版本 | 按权限和生效时间检索，不能靠一次聊天永久记住 |
| 运行凭据 | 检查点记进度；外部系统的业务回执证实动作结果，两者不能互代 | 上轮停在查单后；退款系统是否有成功回执 | 分别核对运行进度与实际执行状态，再决定续跑 |

**领导：**“会话历史”和“任务状态”听着差不多。

**小陈：**历史是“我们聊过什么”；状态是“这件事目前办到哪”。假设 Agent 上轮说“我已经退款”，聊天记录确实有这句话，但退款系统没有回执。下轮如果只读历史，它会把自己的吹牛当成绩。任务状态应写“退款未确认”，有实际回执才改成“已退款”。

**领导：**那“记住我叫领导”属于哪格？

**小陈：**这种长期偏好可以另行考虑，但要有用途、保留期限和访问范围。客户的订单号、地址、支付信息不能因为模型“记性好”就到处存。我们先把当前工单办对，不急着给 Agent 写一本《领导语录》。

## 领导：“窗口关了再开，这单怎么接上？”

**小陈：**应用根据工单号取回任务状态，核对订单绑定和权限；把必要的历史摘要、现行规则和已核实事实装入本轮上下文。若上次工具调用中断，先看运行记录和业务回执，判断是未执行、已执行还是结果未知。未知就交人或对账，不能靠聊天记录猜。

**领导：**你给我一个能验收的结果。

**小陈：**重开工单 0823 后，界面能显示“已查订单，签收争议待售后核实”；模型不再反复问已绑定的订单号，也不编造退款。我们故意拿掉上次查询结果，再看它是否标“需重新核实”；故意留一条“我已退款”的旧回复但不给回执，再看它是否拒绝把退款状态写成成功。

**小陈交付的状态安放图：**每一格写清保存在哪里、保留多久、谁能改、重新进入时如何核对。能续聊只是体验；能辨清事实、状态和外部动作，才不会把“记性好”做成一台自动复读机。

## “记住了”到底指哪一种记住

**领导：**我还是觉得你那五个抽屉太多。客户只想下次别再报一遍订单号。

**小陈：**体验上是一句话，背后至少两件事：应用能根据登录身份和工单找回绑定订单，且当前会话仍有权限处理它；模型在本轮输入里看见必要的订单事实。第一件事不能靠模型记忆，第二件事也不能靠网页还显示旧聊天。若客户换账号或客服转组，旧绑定未必继续有效。让客户少重复报号，前提是身份和对象关系确实已核实，不能为省一句话把别人订单带进来。

**领导：**会话历史和任务状态都有“已查订单”，为什么不能只保留一个？

**小陈：**历史记录“助手说过我查了”，可能是一句没有调用回执的虚话；任务状态记录“查询事件 Q-01 成功，订单系统于 10:15 返回已签收”，才能继续使用。历史帮助理解对话脉络，状态帮助判断办到哪一步。两者可关联，但真相由业务回执和权限关系支撑。若历史写“已退款”、状态写“未确认”，下轮应以业务系统回执核实，而不是让模型选一个听起来最像结尾的。

**领导：**长期记忆不就是给它一个数据库，什么都往里存？

**小陈：**那会变成个人信息杂物间。先定义用途：客户允许保存的联系偏好、公司生效知识、工单处理状态，分别在不同系统有不同保留期限和访问权。订单号、地址、支付信息只在需要处理的工单范围内可见；规则库可供授权客服检索，不能混进私人偏好。搜索某位客户的历史时，服务端按身份和目的过滤，不让模型凭“我想记住”把资料写进无限期的全局库。

## 关窗再开，怎样恢复 0823

**领导：**给我按时间说，不要继续讲抽屉。

**小陈：**10:15，订单查询成功，回执 Q-01 显示系统已签收；10:16，检索到现行签收争议条款；10:17，Agent 形成内部草稿，标“签收凭证待售后核实”；10:18，页面关闭。11:00 客服重新打开，应用先核登录和工单归属，取任务状态与证据引用，再判断旧订单状态是否仍够新，必要时重查。现行规则也按当前版本取，不能因为上轮看过就永远沿用。模型收到的是整理后的本轮材料，而不是整段旧对话原封不动倒进去。

**领导：**客服看到上次草稿，能直接按发送吗？

**小陈：**要看草稿是否被审核、客户是否补新消息、证据是否过期、收件人是否仍同一人。批准绑定具体草稿版本、证据和收件人；变化后旧批准失效。页面重新打开不等于恢复到“可发送”状态。若没有批准，仍是待审草稿；若发送接口上次超时，则先查消息平台回执，不重复发。会话恢复的目标是接着正确处理，不是把所有按钮复原成关闭前的颜色。

**领导：**客户刚在 10:59 说“包裹找到了”，应用能发现吗？

**小陈：**工单状态要带最新消息水位。11:00 恢复时发现有新消息，旧的“请核查未收到”草稿失效，重新整合客户意图。订单查询回执仍是历史记录，但处理目标变了。模型若只读 10:17 保存的摘要，会继续追一个已解决的争议；应用应该先比较工单版本，再装上下文。真正的记忆要会更新，而不是把过去冻结成正确答案。

## 检查点与业务回执，两种“保存”不能混

**领导：**开发说用了检查点，进程挂了也能恢复。那退款回执还要查？

**小陈：**要。检查点说明程序上次运行到哪一步，可能写“已发出退款调用，等待响应”；业务回执说明退款系统实际上做了什么。进程在调用后、收到响应前崩掉，检查点可能只知道“结果未知”。恢复时按业务键查退款流水，不能从检查点里的“下一步是发送”推断钱已退。反过来，有支付回执但检查点未更新，也不能再发起一次退款。[LangGraph 的持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)讨论图状态与检查点；外部系统动作仍要以该系统回执为准。

**领导：**这不就是数据库事务吗？

**小陈：**有相通处，但模型调用、消息平台、退款系统往往不在一个数据库事务里。我们要给业务意图稳定标识，记录请求、审批和执行状态；未知时对账，重复投递时去重。检查点让计算过程可续，幂等和回执让外部动作可核。若写操作不支持可靠查询或去重，就不要自动执行，把接手人和核查步骤写进运行手册。恢复能力不能只在流程图上画一枚“重试”按钮。

**领导：**如果只读查单中断，恢复可以重查吧？

**小陈：**通常可在权限和服务预算内重查，但要先看工单版本、上次查询是否成功以及缓存时效。重查得到新状态，卡片应标时间变化；不能把新旧结果混成同一次回执。只读也有费用和隐私边界，无限重查不是恢复。不同工具的恢复策略按后果分，不能一条“失败就重试”管全场。

## 摘要会忘什么，怎么让它不乱补

**领导：**两百轮会话太长，摘要总要用吧？

**小陈：**可以用，但摘要保留的是脉络，不是业务账本。它应记录覆盖的消息范围、客户核心诉求、已承诺但未完成事项、未决冲突，并附原消息 ID。模型生成摘要后检查关键状态：客户称未收货不能被写成订单系统证明未收货；“可申请”不能被写成已批准；“客服会核查”不能被写成已完成核查。高风险字段直接从结构化任务状态与业务回执取。摘要帮助下一轮少读寒暄，不能把旧错误压缩成更坚固的错误。

**领导：**客户姓名和喜好放摘要里，下次显得亲切，不好吗？

**小陈：**看客户是否允许、当前服务是否需要、保存多久、谁能读取。无需处理退款的个人偏好不该长期保存在工单摘要里；地址与支付信息更应受严格限制。昵称说错只是尴尬，订单数据串到另一位客户身上是事故。真正能提升体验的首先是“不再重复问已核实资料”和“接手的人知道进度”，不一定是 Agent 记住客户喜欢哪个称呼。

## 同一客户，两张工单，记忆不能串线

**领导：**客户 A 上周有退款工单，这周新开物流工单，你让模型读上周记录不是更懂他吗？

**小陈：**先判断是否同一身份、是否与本次任务相关、权限是否允许。上周的已退款回执只能证明上周那单，不代表本周这张也能退；上周的旧地址也不能自动覆盖本周订单。跨工单可在必要时提供受控摘要和引用，但模型必须区分对象。测试要故意给两个相似订单，看它会不会把 A 单的审批结果贴到 B 单；缓存键和状态存储也要带客户、工单与订单标识，不能只按会话昵称关联。

**领导：**换一位客服接手，能看到完整记录吗？

**小陈：**按职责授权。接手客服需要看已核证据、未决事项、客户沟通与下一步，才能继续；不需要看其他客户或过量支付资料。权限转移和交接记录要明确，谁接手、何时接手、上一次给客户承诺何时更新。若上轮 Agent 退出时没建立待办，只留“我会继续处理”的聊天句，换人时会发现根本没人负责。这是任务状态设计的问题，不是模型失忆。

## 面试官问“Memory”，小陈不再只说向量库

**领导：**状态到底存哪些字段，给我一张能让开发开工的便签。

**小陈：**工单状态至少含客户与订单绑定、当前处理阶段、最后一次有效订单查询 ID 和时间、规则文档版本、待核事项、责任队列、下次联系时间、当前草稿版本、审批与发送状态。每个字段注明来源、更新时间和修改权限。比如订单物流状态由订单系统回执更新，不能让模型随手写；待核事项可由模型建议、客服确认；“退款已执行”只能由退款系统回执更新。任务状态里保留引用而不是把所有原始敏感内容复制一份，查看详情再按权限回源系统。

**领导：**字段越来越多，状态迁移错了怎么办？

**小陈：**给状态 schema 版本，升级时测试从旧版迁移，不能把旧卡的“已处理”直接迁成新版“已退款”。若原字段语义模糊，就标待核实，查业务回执后再确定。迁移前后抽样比较工单阶段、责任人和对客承诺，保留可回滚快照。业务状态不是一段可以随意改写的摘要；一次迁移错误可能让成百上千张旧单看起来都结案。

**领导：**客户要求删除聊天记录，状态还能留吗？

**小陈：**按适用的公司制度和法律要求处理，区分服务必需记录、审计义务与可删除偏好，不能模型一句“已忘记”就算完成。删除请求要传到会话历史、缓存、检索索引和衍生摘要，必要保留的业务记录则按法定或合同规则管理。这里没有一套适用于所有企业的留存数字，项目要让数据负责人和法务定范围与期限。技术上必须知道信息被存在哪里，才谈得上按请求处理。

**领导：**状态落库成功了，页面为什么还是旧的？

**小陈：**可能缓存未失效、事件异步投递晚了，或工作台订阅的不是当前工单版本。页面要展示状态版本和更新时间，执行高风险动作前服务端再读最新状态；不能因 UI 显示旧草稿就使用旧批准。运行追踪里关联状态写入、消息通知和页面读取，排障时定位延迟。对客户的处理进度如果仍未知，别为了界面绿色而假装已完成。

**领导：**如果同时两个 Agent 处理同一张单，会不会各自记一份？

**小陈：**不能各自闭门写状态。每次更新带版本条件，冲突时重新读取并协调；客服人工修改和客户新消息也可能并发。一个 Agent 说待核签收，另一个拿旧规则写可退款，最后写入者覆盖前者，会让待办消失。按业务事件追加记录或用状态机约束转移，重要动作由单一执行服务确认。并发不是模型记性问题，是共享任务状态的一致性问题。

**领导：**检查点保存得越勤越好？

**小陈：**保存点太少会丢进度，太多会增加开销和敏感数据复制。按有意义的边界保存：工具调用前后、人工审批前后、进入结果未知时、对外动作确认后。检查点里尽量存状态引用与必要摘要，业务回执仍留在权威系统。恢复测试故意在调用发出后、响应返回前中断，看看它是查回执还是重新执行。能通过这个场景，比“程序重启后页面还在”更能证明恢复可靠。

**领导：**一条历史消息说“退款完成”，任务状态说“未知”，客户今天又说没收到钱。客服怎么处理？

**小陈：**先查支付或退款系统，以交易流水和当前状态为准；历史消息作为可能的错误承诺留下，供客服解释与补救。若系统确认已执行但渠道未到账，说明阶段差异；若根本未执行，就按公司流程纠正客户认知并推进申请。状态卡把“客户听过什么”与“公司做过什么”并列呈现，客服才不会只核账却忘了处理客户已经收到的错误承诺。

**领导：**模型不是有长期记忆产品吗？为什么还要自己做状态？

**小陈：**产品能力可以帮助保存和检索信息，但业务系统仍要定义真相、权限、时效与删除。会话历史、任务状态、公司知识、个人偏好、运行检查点和业务回执目标不同，不能统一塞进一个“记忆”字段。知识库可用检索技术，任务状态需要可更新的结构化记录，外部动作需要回执。面试时我会先问“要记住什么、给谁用、何时失效”，再选存储方式。

**领导：**那上下文窗口和记忆是什么关系？

**小陈：**窗口是本轮模型实际看到的材料；记忆是应用长期或跨轮保存的信息。保存了不代表自动进入窗口，进入窗口也不代表永久保存。每轮由应用按任务、权限、时效选取，给输出留预算。大窗口可以装更多材料，不能保证跨会话自动记住订单，更不能替业务系统维护退款状态。[OpenAI 会话状态指南](https://developers.openai.com/api/docs/guides/conversation-state)也把请求上下文与状态管理作为需要显式处理的事。

**领导：**恢复时最危险的一句话是什么？

**小陈：**“它上次说已经做了，所以接着做下一步。”先看运行检查点，再看业务回执和当前授权；结果未知要对账，状态过期要重查，新消息要让旧草稿失效。今天我们让客户少报一次订单号，靠的是应用真的保存并核对了状态，不是让 Agent 在新窗口里装作见过他。

**领导：**那验收别只让我重新打开页面看一眼。

**小陈：**还要模拟换客服、换会话、订单状态更新、旧草稿待发、工具执行后进程中断、客户补新消息。每种都看任务状态是否正确恢复、该失效的批准是否失效、结果未知是否对账。最终客服能说清上次做了什么、现在该做什么，客户才算没白报那次订单号。

**领导：**如果恢复后状态记录显示“已完成”，客户却又来投诉？

**小陈：**先问完成的是哪个任务：草稿生成、消息发送、签收核查，还是退款执行。每个完成状态带回执和时间，客户问题未解决就重新打开待办，不让“Agent 已完成”挡住售后。状态名称若混淆业务结案与机器运行结束，宁可改数据模型，也别让客服靠猜。

**领导：**记性好，也得记对账。
