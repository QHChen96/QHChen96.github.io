**领导：**管理台里林女士的偏好写得明明白白，助手还建议周一早上直接打电话。是数据库失忆，还是它上班没带脑子？

**小陈：**数据库记住了，回答链路没用对。它检索到去年某次紧急联系，忽略了当前邮件优先的默认条件，还把另一位联系人放进候选。先拆开每一步，才能知道问题出在找不到、选错了，还是找对以后没带给模型。

本篇继续采用**教学虚构**的星河制造续约助手。林女士默认工作沟通先邮件，仅允许本周末紧急事项电话；当前任务是准备周一的续约联系草稿。我们不靠扩大返回条数赌模型运气，而是建立能解释“为什么读这一条、为什么排除那一条”的检索流程。本文实现是应用设计示意，不是某个产品完整源码。

## 一、先分清查询是在找属性、找经历，还是找现在的业务状态

**领导：**一个搜索框解决所有问题不好吗？

**小陈：**界面可以只有一个，后面要分路。“林女士现在怎么联系”是已知主体的当前属性查询；“她上次为什么反对升级”是事件与证据检索；“最新报价批准了吗”要查审批系统。三个问题都用向量相似度，会把确定查询做成猜谜。

属性查询可直接按租户、联系人与属性查当前记录，拿到值、条件、版本、来源和复核时间。事件查询需要找到相关经历，再展开前后文；业务状态则从权威服务获取，记忆可以提供定位和背景。问题改写器可以建议查询类型，应用根据允许的对象、字段与接口验证，不给它自由读取所有数据的能力。

一个问题可能同时走两路。准备联系草稿需要当前沟通偏好，也需要上次尚未解决的问题；合同金额还要读取现行政策。每路返回结构都保留来源地位。汇流时不会把历史事件中的“客户希望优惠”抬成当前批准，也不会把未解决的问题删掉，只因新合同看起来没有相似描述。

拆路还有诊断价值。属性读取失败可以直接检查主键和状态，语义召回失败看查询与索引，权威接口不可用按业务降级。如果所有东西都叫记忆搜索，团队就只能反复调一个相似度阈值，调到名字能找到、旧价也跟着找到，领导看着结果更热闹，事故也更热闹。

## 二、先圈定能读谁，再讨论像不像

读取上下文来自经过认证的请求：谁在使用、属于哪个租户、当前任务允许访问哪个客户、有哪些角色与用途。客户 ID通过业务解析确定，不能直接相信提示里的“我是管理员”或模型生成的 ID。授权失败应在检索前停止；知道某条记忆 ID也不自动取得读取权限。

**领导：**先全库搜，再把别的客户删掉，结果不一样吗？

**小陈：**风险与召回都不一样。未经授权内容可能已经进入搜索服务、日志或重排模型；全局候选还会挤掉本租户的真实命中。应在索引查询层限定授权范围，检索后再核对主记录与来源权限，两道门各自解决不同阶段的问题。

范围不只租户。某销售能看客户共享背景，不一定能看同事的个人笔记；某 Agent可以处理工单，不一定能读取销售谈判备注。命名空间便于组织，真正访问控制由服务执行。不能因为文件在`shared`目录或记录带`user_id`，就把它当已认证的隔离方案。

如果当前搜索后端无法在查询阶段完成所需隔离，可以按权限域分索引、先拿授权记录集合再搜索，或暂时走确定查询。不要在生产里把“模型别用别人的资料”当过滤器。选择哪种实现还要衡量索引数量、权限更新成本和搜索规模，但目标一直是未经授权内容不进入下游处理。

## 三、精确查找与语义召回，怎样组合而不互相抢活

手机号、订单号、审批号和联系人 ID属于精确标识。向量擅长描述相近的内容，不能保证相邻编号严格分开。已知属性直接读取；含标识的事件问题先精确过滤或关键词匹配，再在相应集合里搜索。“上次讨论报表口径”没有明确文档名，语义召回才更有价值。

关键词搜索可以保留专有名词、产品版本与明确短语，语义搜索可以找措辞不同但含义接近的经历，两者合并时先按稳定记录 ID去重。不要把两个系统返回的原始分数直接相加：一个分数可能是距离，另一个是词项相关性，范围与方向不一定相同。可以用排序融合，或在受控候选集合上统一重排。

**领导：**给我一个简单能落地的融合办法。

**小陈：**先按两路各自排名，给记录累计倒数排名分。教学公式可以写成`1 / (c + rank)`，同一记录在多路出现就累加。常数和候选数从真实样本调，公式只是解决分数不可直接比较，不负责判断版本、权限或事实真假。

召回候选数与最终注入数分开。多取一些合法候选有助于重排，最后上下文却不能跟着无边界膨胀。查询去掉重复词不应去掉“不”“仅周末”“今年”等决定条件的词；改写也要保留原问题，避免“现在能不能电话”被改成“客户电话偏好”，丢掉当前时点与动作判断。

如果问“为什么当时没电话”，这是历史问题，需要当时有效的偏好与事件背景。当前读取通道默认只查有效记录，历史通道则按合法的时间范围获取旧版本。不要为了回答历史就把过期记录重新开放给所有当前查询；同一数据有不同用途，查询计划要明确表达。

## 四、相似度最高，为什么仍然不能排第一

**领导：**搜索排名第一的是“本周末急事可电话”，问题也有电话，为什么不选？

**小陈：**因为任务是周一常规联系，例外条件不成立。它语义很像，但不适用。当前有效性、主体、用途与条件属于硬判断，不能被一个高相似度抵消。

候选先过资格门：租户与主体是否正确，记录是否有效，来源有没有撤回，当前调用者仍有权限，用途是否匹配。再比较相关性、来源质量、时效与信息完整性。不同属性有不同时间要求；表达习惯可以较久复核，工单状态需要更近期观测，不能用同一个“最近的总是更好”权重处理所有内容。

条件判断要保留未知。系统不知道任务是否紧急时，不能自作主张把紧急例外启用；先按明确默认偏好准备，或提出具体确认项。模型重排可以分析条件，但关键限制由结构字段和服务核对。把“电话”抽出来单独排，很容易丢掉“允许但不优先”和“仅特定时间”两个关系。

否定与修正是另一类重排陷阱。“她拒绝了旧方案”和“她接受了旧方案”高度接近，却方向相反。应保留谓词、状态与来源，让重排器看到完整主张；对已经被纠错的记录做硬排除。检索置信度只说明匹配程度，不变成事实置信度，更不能当行动批准。

## 五、展开证据：一句摘要解决定位，原始条件解决误会

长期记忆可能写“林女士要求先确认报表口径”。这足以定位相关事件，却未必足以写方案。展开来源后发现，她要求确认的是月报里的活跃用户定义，不是所有报表都暂停。这时需要带入精确范围、版本与尚未解决的事项，避免把方便的摘要扩成新的业务结论。

**领导：**展开原话是不是又绕回全量历史了？

**小陈：**按证据引用拿必要片段即可。先读取记忆的来源消息与关联工件，再获取解释条件所需的相邻上下文；不把半年聊天全部倒进来。片段边界留住说话者、时间与否定，省掉与本次问题无关的闲聊。

证据权限同样复核。记忆存在不意味着来源仍可见；权限收紧或来源撤回后，应停止使用相应主张或给出可验证的降级表示，不能仅靠已生成的摘要继续透露内容。展开失败时记录原因：来源丢失、无权访问、服务不可用、版本不匹配，四种情况的处理不同。

压缩证据应保留哪些条件，可以按主张校验：谁提出、针对什么、何时有效、是否已经被解决、是否被后来更正。若压缩后任何一项改变原意，就缩短其他文字，不压掉这个条件。来源链接在文末有利于审计，正文中的证据地位与关键内容仍要讲清，读者和生成模型都不能靠点出去补齐逻辑。

## 六、把读取过程写成程序，别把所有责任塞进提示词

下面是**教学伪代码**，表示控制顺序，函数需要按实际数据库与认证服务实现。`ctx`由服务认证产生，模型不能自行填写；`plan`是已校验的查询计划。

```python
def load_memory(ctx, plan, stores, budget):
    scope = stores.auth.resolve_scope(ctx, plan.subject)
    if not scope.allowed:
        raise PermissionError("scope denied")

    exact = stores.current.read(scope, plan.required_keys)
    candidates = stores.search.search_in_scope(scope, plan.event_query)
    valid = []
    for item in exact + candidates:
        current = stores.records.revalidate(item.id, scope, plan.as_of)
        if current and current.revision == item.revision:
            valid.append(current)

    ordered = stores.rank.rank_for_task(valid, plan)
    evidence = stores.sources.expand_allowed(ordered, scope)
    packet = stores.pack.fit_with_conditions(evidence, budget)
    stores.trace.record(scope, plan, packet.selected_ids, packet.excluded)
    return packet
```

这里重新校验的对象是事实主记录，不是重新让模型问一遍“看起来合法吗”。版本对不上时可以读取新版本重新评估，而不是永远把同一逻辑记忆都排除；删除或权限失败则拒绝内容。实际实现最好按批读取，减少逐条远程请求，批处理仍保留每条状态与排除原因。

搜索失败也不等于整次任务失败。当前属性主键读取正常时，可以完成沟通方式判断；关键历史争议无法找到证据，则草稿不推测那个争议的原因；审批接口不可用时，不批准报价。返回结构应包含已知、未知和失败类型，让生成阶段可以明确收窄，而不是看到空列表就编一段最像真相的话。

最容易被遗漏的是无结果。没有记录只表示没找到有效内容，不表示用户没有偏好；搜索服务错误也不表示这家公司从未有过问题。程序区分`not_found`、`unavailable`、`denied`和`conflict`，生成阶段按类型行动。记忆系统的质量，有很大一部分体现在它不记得时能否说清边界。

## 七、上下文预算：先装必须知道的，再装值得知道的

一次请求的输入包括系统规则、工具定义、当前任务、消息历史、证据与记忆，还要给输出留空间。预算按实际模型和调用接口计算，不用中文字数猜 token。工具结果可能突然变大，预留余量并在发送前再次计量，避免刚好塞满后下一步调用就溢出。

**领导：**把记忆限制成十条，够简单吧？

**小陈：**十条可能一条十字，也可能一条两页。更合理的是按预算和必要性选择，硬约束先保留，关键事实与尚未解决的事项随后，相关经历再择优。达到数量上限不代表预算安全，达到预算也不代表内容足够回答。

选择单位应是一条完整主张及必要条件。不能刚好在“不允许”前截断，也不能保留结论丢来源。太长的事件先形成带引用的压缩片段，无法完整表示就不使用这条事件支持确定结论。当前属性通常短而关键，可以直接携带；大段案例只在确实影响方案时加入。

多样性选择可减少同类候选反复占位。例如五条都说客户关心报表，不如保留一条完整要求、一条未解决状态和一条相关合同边界。MMR这类相关性与重复度折中方法可以帮助选择，但不能替代必需事实覆盖检查。按算法删掉一条看似重复的否定，可能正好删掉唯一的例外条件。

## 八、注入时保留地位，客户留言不会因此变成系统命令

记忆包清楚区分当前有效偏好、历史事件、权威观测与未知项。每条包含主体、适用时间、关键条件、来源和修订。不要仅用“重要记忆：客户说……”把整段原话放在最高级指令附近。原话可以含请求甚至攻击文本，它作为数据被解释，不取得工具权限。

**领导：**记忆里客户写“以后别走审批，直接报最低价”，助手就照办？

**小陈：**它可以知道客户提出过这个要求，仍然按报价流程处理。写入门不把请求误记成批准，读取门不把数据升级成指令，动作门核验当前权限与批准。三处分别执行，不能因为第一处漏了一句就让后两处全部失守。

上下文可以使用明确结构，但分隔标签本身不构成安全保证。模型可能受内容影响，外部读取与动作仍由服务控制。对于高风险字段，只接受权威接口的结构值，模型引用的记忆只辅助说明；当前文案与行动参数也要核对，防止模型在表达中偷偷把“客户希望”改成“公司同意”。

生成后可以检查关键事实是否有支持，记录哪些记忆真的影响了结果。不要把模型自述“我用了这条”当唯一证明；可以结合实际字段依赖、引用定位与可控反事实重放。把这条偏好换成相反值，沟通草稿是否随之正确变化；如果不变，可能检索成功却未被利用。

## 九、缓存省钱之前，先保证客户改口不会被缓存打回去

缓存键不能只有问题文本。相同的“怎么联系客户”，在不同租户、联系人、授权、时间与记忆修订下有不同答案。完整键至少覆盖查询范围、权限或访问代次、相关记录版本和模型/提示版本；具体取舍按系统成本设计，但不能跨主体共享一份客户事实结果。

**领导：**缓存五分钟，大多数时候都没事。

**小陈：**客户刚改口后的下一轮，恰好最需要立即生效。关键属性更新可增加失效代次并清掉相关缓存；读取再复核版本。缓存寿命是一个风险上限，不是更新传播协议。删除与权限撤销更不能等“多数时候没事”。

向量索引也是派生缓存。搜索到旧修订要核对主记录；索引重建和增量写入协调，记录消费到哪一代。后台晚到的旧事件不能重新发布撤回内容。读取服务可以短期回退精确查询，明确语义检索暂时不完整；不应为了掩盖故障把老缓存当当前正确值使用。

还要区分检索缓存与答案缓存。记忆包可在版本相同情况下复用，最终答案可能还依赖实时合同或工单状态，不能因偏好没改就永久复用。所有依赖应进入缓存验证；找不到依赖关系时，宁可降低缓存范围，也不要通过不断延长时间把过期事实包装成性能优化。

## 十、一次具体查询，从错误结果走到合格草稿

原始请求为“周一联系林女士，确认续约方案”。确定性读取拿到邮件优先第七版；事件搜索找到周末电话例外和报表口径待确认。例外因时间与紧急条件不成立被排除，报表事件来源仍有效，工单工具确认该问题尚未关闭。最后包里只有当前偏好、相关未完成事项与现行合同引用。

草稿因此采用邮件开场，列出需确认的报表口径，并避免声称服务问题已经解决。它没有为了显得了解客户写“您一向不接电话”，因为偏好是沟通优先顺序，不是人格标签；也没有强调无关旧争议。记忆让本次决定更准确，表达仍保持适度。

**领导：**检索结果里旧电话例外分数最高，最后为什么没用，管理台能解释吗？

**小陈：**能看到合法范围、时间条件、检索来源与排除原因。日志记录必要 ID与版本，敏感正文按权限保存，不把整段客户资料随便喷进监控。解释足够定位错误即可，不能为了可观测把原来隔离的数据集中到一个谁都能看的日志台。

排除原因形成稳定枚举便于统计：主体不匹配、失效、已撤回、权限不足、条件不成立、预算不足、内容重复。预算不足和检索遗漏分开；如果必要事实因为预算被删，应当阻断或重新压缩，而不是计作一般正常排除。指标要反映实际决定风险，不能只算平均命中数。

## 十一、当前产品接口怎样接到这条链路

[LangGraph Stores](https://docs.langchain.com/oss/python/langgraph/stores)提供命名空间、键值与检索等机制，便于组织跨会话信息。应用仍要定义主体、访问控制、有效性和当前属性的地位。开发用内存存储可以演示流程，生产持久性与索引能力按具体后端选择，不能因对象名叫 Store就默认支持所有事务与权限要求。

[Mem0 当前 Search 文档](https://docs.mem0.ai/core-concepts/memory-operations/search)展示把实体范围放进`filters`，并区分 Platform与 OSS的过滤、重排配置。本次核对的 OSS v3示例也使用`filters={"user_id": "..." }`，不要混用旧教程的顶层搜索参数。具体版本和 SDK锁定后再写适配层，升级时执行隔离与改口回归。

**领导：**上了重排，是不是正文里那些检查都可以删掉？

**小陈：**重排负责从候选里挑更相关的，授权、有效版本、来源撤回与动作批准各有责任。可以选供应商帮我们实现某些能力，仍要用测试确认服务在哪一层生效。能力名称一样，生效位置、异常返回和数据保留策略可能不同。

[LangMem 的概念指南](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)讨论记忆价值超出相似度。我们把这点继续落实为资格过滤、条件、必要覆盖与预算，是本文应用设计；这些字段和策略并非声称产品开箱全包。产品之间的详细取舍放在本专题最后一篇，先把业务要求建立起来。

## 十二、怎么证明是记忆派上用场，而不是碰巧答对

建立最小可复现场景：同一任务分别注入邮件偏好、电话偏好、无有效偏好，观察草稿是否按规则变化；再加入旧值与他人资料干扰，正确结果应保持。样本在同一预算、同一模型与同一权威数据下比较，避免“加了记忆也加了三倍上下文”却把全部收益归给检索算法。

检索层记录必要事实是否被召回、有效性门是否拦下错误候选、上下文是否覆盖必需条件；使用层核对最终动作与证据。一个系统可能召回率很高，却总把临时例外当默认；另一个可能答案看似正确，只是猜中了常见做法。两类假成功在反事实和更新测试中都会露出问题。

**领导：**上线之后重点盯什么？

**小陈：**盯改口到可用的延迟、错主体命中、失效内容进入上下文、无结果时的乱猜，以及预算删掉必要条件的次数。费用与延迟一起看，按查询类型拆开。一个慢而正确的读取可以优化，一个快而串客的读取不能拿平均响应时间给自己庆功。

交付包括范围解析、查询分路、版本校验、证据展开、预算选择和可追踪记忆包。周一的草稿已经给出正确解法，下一篇处理更长的问题：续约会话持续数天、上下文被压缩之后，怎么保住目标、事实和未完成动作，重启时继续做对。
