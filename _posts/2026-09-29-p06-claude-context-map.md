**领导：**这次让 Claude Code 改客户数据导出，我把整个仓库三千个文件都给它看。看完还漏了“合同约定导出前必须由客户管理员批准”。上下文不是挺大吗，怎么这么健忘？

**小陈：**它没法把“读过”变成永远记得。仓库文件、聊天历史、命令日志、项目说明和工具定义都占同一个工作上下文；长任务会压缩旧内容。审批红线如果只躺在一份两年前的会议记录里，模型读过一眼也可能在后续几十轮里失去它。我们先把资料分成入口规则、可搜索的事实、当前任务工件三层，再看实际运行中哪一层没有进来。

**领导：**我直接把那句话贴在开头，叫它“千万别忘”，不就行了？

**小陈：**贴开头能帮一会儿，却不能证明压缩后仍被保留，也不能替系统拦住越权导出。我们会写清能复核的项目约束，给它找到合同原文的路径；执行前再用权限检查或 hook 拦高风险动作。今天先解决“去哪找、怎么装、丢了怎么找回”这件事。合同、文件名和运行轨迹都是教学虚构，不是某家公司真实配置。

## 上下文窗口像办公桌，仓库像档案室

[Claude Code 官方工作机制](https://code.claude.com/docs/en/how-claude-code-works)说得很直白：模型的上下文窗口容纳对话、读入的文件、命令输出、项目规则、记忆等；空间用满时会压缩旧工具结果和对话。仓库不是被永久装在模型脑子里。Claude Code 可以接触项目目录，靠搜索和读取把相关材料搬上“办公桌”；不相关的文件仍待在档案室。这个比喻有个重要限制：办公桌上的纸会随任务推进被新纸挤走，压缩时可能只留下摘要，不能把“曾经读过”当成“下一步仍持有原文”。

领导想一口气预读三千文件，听着保险，实际有三种损失。第一是容量：生成代码、构建产物、大日志会占掉本该留给任务推理与验证的空间。第二是干扰：三个版本的客户政策并排出现，模型不一定知道哪版有效。第三是时效：仓库后来更新了合同或配置，开头塞进去的副本可能已经过期。文件是事实来源，当前任务的上下文只是某一刻装配出的工作包。知道什么时候重新查源，比把源全部背下来更可靠。

**领导：**那它每次都搜，岂不是很慢？

**小陈：**先给它地图，再按需开门。地图不是三千份文件的摘要，而是几条稳定入口：服务边界、关键目录、常用测试命令、受监管动作的审批依据位置。任务具体问“客户数据导出”时，先用文件路径模式找 `export`、`contract`、`approval` 相关文件，再在候选目录里用内容搜索找“管理员批准”“授权记录”“导出范围”等字样。`Glob` 偏向找文件名与路径，`Grep` 偏向找内容；命中以后才读小范围原文及其调用者。若名称和词语没命中，就换同义词、接口路由、事件名、测试断言继续查，而不是宣布“没有这条约束”。

## CLAUDE.md 该装路标，不该装整个知识库

小陈还给领导算了一笔“看起来便宜”的阅读账：假设一个自动生成的类型文件有两万行，工具把它全文送进上下文，真正与导出审批相关的只有一个接口签名。无论窗口上限多大，这份输出都会和项目指令、用户问题、已读合同、错误日志一起参与后续请求，既占预算，也提高模型从噪声中找错重点的机会。先用路径范围定位到 `services/export`，搜索函数名只回传命中位置，再读函数前后必要代码，通常更能让每一段文字有用。数字只是解释成本方向的示意，实际 token 数与工具截断方式以会话的 `/context` 统计为准。

更难的是“同名不同源”。仓库有当前代码、废弃示例、测试夹具、第三方包；合同有有效版、已撤销版、谈判草案；聊天里还有领导口头说“先跳过审批”。小陈把每条发现记成“来源、版本、适用范围、与任务关系”，先看当下执行路径，再看正式业务来源，最后把历史讨论当线索。若正式合同说必须批准，代码和口头指示说不必，不能从哪份文字更近、更醒目就决定合规边界。Agent 应指出冲突并停在可授权的人面前；应用层还须有真正的审批校验。

搜索也有阴性证据问题。`Grep` 找不到“审批”两个字，可能代码使用英文 `approval`，可能审批封装在共享中间件，可能文件被生成或忽略，可能这个功能确实缺校验。把“未找到”升级成“系统不存在审批”是推理越界。小陈会沿接口调用、数据库字段、单测名称、配置开关继续交叉验证；仍无结果就如实写“在检查过的路径中未发现”，而不是承诺全仓没有。对三千文件的大仓，这种范围声明非常关键，领导看的是风险判断，不是搜索工具给的一句零结果。

**领导：**既然 `CLAUDE.md` 每次都读，把全部合同贴进去不就永远记得了？

**小陈：**它确实适合放持续有效的项目说明，但不是无限容量的保险箱。[官方的项目记忆文档](https://code.claude.com/docs/en/memory)把 `CLAUDE.md` 描述为由人维护的项目指令，常用于代码规范、构建命令和架构入口；自动记忆是另一套由工具积累的偏好与学习。它们都是进入上下文的文字，不是强制权限配置。文件太长会持续占用窗口，还可能因旧规则与新规则互相打架，让模型随手挑一条。官方建议把项目规则写得具体、简短，并把只在某些目录才需要的内容拆到相应位置。我们只把“导出前必须取得客户管理员的当前有效审批，审批记录位置在受控合同系统”这类稳定边界写进入口；合同全文仍在有权限的系统中查。

小陈给虚构仓库写了三段简短的入口约束。第一段说：客户数据导出由 `services/export` 承担，相关测试在 `tests/export`，变更前先看接口契约。第二段说：任何真实导出前必须验证客户管理员审批记录、租户与范围一致；没有记录时只允许生成草稿和失败报告，不得执行导出。第三段给出受控合同资料的查询入口与负责人，要求以当前生效版本为准。这里不放客户姓名、合同价格或长期有效的访问令牌；那既占窗口，又可能把秘密扩散到每次任务。

**领导：**既然写了“不得导出”，模型会乖乖遵守吧？

**小陈：**大多数时候能引导，但不能拿它当权限闸门。官方文档明确把 `CLAUDE.md` 和自动记忆视为上下文，不是强制配置；要在工具执行前阻断动作，应靠权限设置、合适的 PreToolUse hook 或业务服务端校验。还要留意层级：用户个人、项目根目录、子目录可能有多份说明；子目录的说明在访问相关文件时才会加载。假设根目录写“导出必须审批”，子目录旧文件却写“测试环境直接放行”，两份互相矛盾，模型有机会选错。团队要定期清理冲突，并让业务服务端以同一份审批事实裁决，不能把 markdown 文案当最终授权。

有些团队更想共用 `AGENTS.md`。Claude Code 官方目前说明，在相应版本和配置下，它能读取仓库的 `AGENTS.md`；是否与 `CLAUDE.md` 同时读取，取决于项目指令设置，默认行为还受目录中是否存在 `CLAUDE.md` 影响。小陈不会假定“仓库有 AGENTS.md，Claude 一定看了两份”，而是让同事在实际会话用 `/context` 查看已加载的文件。版本不同的环境还需核对官方文档和客户端配置。项目规则的关键不是文件名神圣，而是它确实进了当前会话、没有冲突、且可从业务系统执行校验。

## 从一个问题查到一条调用链，而不是搜到关键词就收工

客户数据导出这件事，搜索路径可以像侦探走楼梯。先找路由或命令入口，看看谁接受 `export_customer_data` 请求；再找服务实现，确认它调用审批查询的顺序；再找存储与任务队列，确认异步执行时审批状态会不会过期；最后找测试，看看“无审批”“审批过期”“租户不一致”“导出任务重试”是否覆盖。每一步都围绕一个问题，读到答案就继续。若仅在 `README` 搜到“需要审批”，代码实际上没查，最多证明文档有愿望，不证明系统有门。

小陈用一个虚构的事故作对照：旧代码在 Web 层检查了审批，后台队列重试时直接调用底层导出函数，绕过了 Web 层。Claude Code 如果只读路由文件，可能认为有保护；顺着调用链读到 worker，就会发现第二个入口。再看服务端校验是否放在所有执行路径的共同边界，才能知道该把修复落在哪。仓库地图帮助找到楼门，调用链帮助找到后门。对索引、全文检索或代码智能插件，能力和效果随环境而变；本文的 `Glob`/`Grep` 是最基础的按需发现方式，不宣称每个项目都只靠这两种搜索就足够。

**领导：**既然看了调用链，它后来怎么还是忘了审批？

**小陈：**因为小陈检查了会话时间线。前半段读了合同与 worker，后半段跑了一个巨大测试套件，日志不断回流；再经过自动压缩，新的摘要保留了“要修导出重试”，却没保留“必须有客户管理员审批”以及合同版本。压缩是为了腾出空间继续工作，不等于从此保存每条原句。[官方的上下文可视化说明](https://code.claude.com/docs/en/context-window)区分哪些项目根规则会重新注入、哪些聊天与工具结果会被摘要、哪些嵌套规则要等相关文件再次读到才加载。若关键限制仅在旧聊天里提过一次，就有被摘要遗漏的风险。把稳定边界放项目入口，把任务特有证据写到持久工件并保留来源，压缩后再核对一次，是可操作的补救。

## 压缩前后，交接单要留下“凭什么”

**领导：**官方不是说压缩时项目规则会重新加载吗？红线写进 `CLAUDE.md` 后，还要写交接单？

**小陈：**因为规则和事实是两种东西。规则“导出前必须审批”可以稳定存在；这次客户的审批记录是否有效、刚才哪条命令失败、worker 修到哪一行，不能写成普遍规则。按[官方上下文说明](https://code.claude.com/docs/en/context-window)，项目根的 `CLAUDE.md` 会从磁盘重新注入，路径范围规则和子目录说明在再读相关文件时加载；旧对话与工具结果则进入摘要，最近读改的少量文件还可能被重新读取。实现会随版本变化，不能把某个数量当永恒契约。设计上应把任务的动态证据落到可查工件，压缩后核对，而非推测工具“应该保住”了哪几段。

这份工件还要避免另一种坑：写出一个漂亮摘要，却没有可复查来源。像“审批已确认”只有四个字，下一轮根本不知道谁批、批哪个租户、有效期多久、批准了哪类数据。更有用的是“审批查询返回记录 ID、租户标识、范围摘要和截至时间；原件在受控系统，以任务执行时重新查询为准”。若审批在压缩到恢复之间被撤销，旧摘要不会自动更新。把关键约束写成判断条件，把动态事实写成要重查的指针，才能让后续步骤在正确时间做正确验证。

**领导：**那 Claude 自动记忆是不是会把这次教训记住，以后再也不犯？

**小陈：**自动记忆可保存偏好与反复出现的工作方式，官方也把它与人写的 `CLAUDE.md` 分开。但它不应保存某客户的审批状态、导出范围或合同密文。记忆可能帮助它下次主动找审批入口，不能代表当前审批已经存在。对“一定不能越权”这种底线，让权限设置和服务端校验负责；对“每次先去哪查”，让项目指令与文档入口负责；对“这次查到什么”，让带版本的任务工件负责。三个职责拆开，出了错才能找到是规则没加载、资料没检到，还是执行闸门没挡住。

**领导：**你又要写一份总结？这和模型自动压缩的总结有啥区别？

**小陈：**自动压缩的目标是让对话继续；我们的任务工件要让人能查账。它至少留六项：任务目标和不得越过的边界、已核实的事实及来源路径、已改文件与差异、已跑验证及结果、外部动作是否发生、下一步与待确认项。比如“合同审批条款见合同系统记录 C-27 当前版；导出服务仍需服务端检查；worker 重试未实测；本次没有触发真实导出”。这不是把合同全文再复制一遍，而是留一个有权限、有版本的证据指针。新会话或压缩后的会话先照指针复查原件，再继续修改。

特别要把“已发生”和“建议做”分开。如果前半段 Agent 只生成了导出任务草稿，不能在压缩后把它写成“导出已完成”；若调用外部导出接口超时，不能凭聊天记录里没有成功回执就断言没有导出。通过业务任务 ID 查询真实状态，再决定重试或人工接管。上下文管理与状态恢复在这里相遇：会话可以压缩，客户数据动作的事实不能被压缩成模糊一句“差不多好了”。

## 拿两次会话做验收，避免“这次碰巧记住”

第二次回放还要刻意加入两种刁钻情况。其一，合同系统短暂不可用，模型只能看到昨天缓存的一份批准截图；正确行为是把审批状态标为未知，停止真实导出并给出恢复后的重查路径，而不是把截图当现行授权。其二，员工把一句“老板口头同意先导出”写在 issue 评论里；它能作为调查线索，不能代替客户管理员审批。只测顺利路径，模型很可能在例外处用最像答案的那段话填空。故障样本让我们看出它是否懂“找不到证据”和“证据证明没有”之间的区别。

观察维度也包括成本与速度，但不能让它们压过正确性。可以记录每次任务读了多少个文件、实际进入上下文的文本量、检索是否重复、压缩后是否重读了关键来源、从提问到得出可审结论的时间。若优化让工具调用减少一半，却让审批红线在压缩后消失，这不是效率提升。反过来，每轮都把全部合同重新读一遍，也会拖慢合法任务并扩大敏感数据暴露。目标是用最少足够的材料作出可追溯判断，必要时为高风险决策额外核查。

小陈把验收表交给另一名同事，不提前告诉他红线在哪，只给项目入口和同一张工单。若同事能沿地图找到现行依据、在压缩后恢复到同一判断，说明结构可供接手；若只有小陈熟悉隐藏路径才跑得通，方案仍靠个人记忆。仓库地图真正的价值，是让换人、换会话、换模型时都能把关键证据找回来。

小陈不让领导靠观感验收，设计两次同题回放。第一次从全新会话开始，只给“修客户数据导出重试”，观察 Claude Code 是否读到项目入口、是否找到审批依据、是否追到 worker 绕过 Web 层的路径、是否在没有审批记录时停止真实导出。第二次把会话拖长，加入一段大量但无关的构建日志，再压缩并继续问“现在能直接跑导出吗”。两次都要能指出现行审批依据在哪里、哪些测试已跑、真实导出是否发生。若压缩后答成“可以直接跑”，则看是根规则没加载、工件没写、来源失效，还是业务校验根本没做；不同原因需要不同修复。

评估时不只看最终一句“不能导出”。还看它是否找到正确租户与审批记录、是否区分草稿与真实导出、是否没有读取不相关客户的合同、是否能在权限不足时停下并交出已完成工作。一个模型可以碰巧说对一句话，同时沿错路径访问一堆不该看的资料；也可以因谨慎拒绝所有导出，导致合法任务无法完成。我们要的不是“它很听话”的演示，而是有正常路径、有失败路径的可复测轨迹。

**领导：**那我能不能把那个任务工件也塞进 `CLAUDE.md`，以后都不用重查？

**小陈：**别把一次工单的临时进度写成所有会话的永久规则。`CLAUDE.md` 放稳定入口和重复犯错的项目规范；每次任务的工件留在该任务的文件或受控记录里，带时间、版本和负责人。过期合同、一次性的测试失败、某个客户的审批号，长期出现在所有会话里既占上下文，也可能误导别的客户任务。项目规则是地图，任务工件是这趟旅程的路书，合同系统才是法定原件。三者位置弄反，地图会越画越像垃圾场。

**领导：**最后一句，大上下文到底值不值？

**小陈：**值，但要用在真正需要同时比较的材料上。跨几十个模块的重构，确实可能需要更多代码和测试一起进入窗口；一条导出审批红线，却不靠“三千文件常驻”保证。即使模型上下文很大，旧规则和新规则混杂、长日志冲淡约束、压缩漏掉细节的问题仍在。把入口做短、搜索做准、证据留指针、压缩后复核，才是这类任务能交接的办法。领导点头：“原来不是给它喂饱就行，还得教它看档案号。”小陈说：“对，合同红线不是零食，不能吃完就忘。”
