**领导：**退货流程不是三步吗？建退货单、约快递、通知客户。Agent 串起来跑，完成时说“明天上门”。

**小陈：**昨天它也是这样说的。退货单建成了，快递接口返回无运力，通知系统却照模板发了“明天上门”。客户第二天请假在家等，人没来，投诉倒是准时到了。

**领导：**那第二步失败时重试，重试成功不就补上了？

**小陈：**先看失败的是“快递明确拒绝”，还是“预约请求结果未知”；再看客户通知有没有发。跨三个系统没有一颗能同时撤销一切的按钮。要把每一步的事实、可撤销动作和对客承诺条件拆开，不然“重试”只会把承诺叠得更厚。

本文的退货单、时间、物流能力和补偿措施均为虚构教学案例。实际取消、改约、赔付和对外承诺要遵循企业政策及合作方接口契约。小陈今天交付的是跨系统状态表，不是让模型自作主张给客户安排快递。

## 一条流水线为什么会只成功一半

虚构公司把退货拆到三个系统：售后系统创建退货申请，物流系统预约取件，消息系统通知客户。每个系统只对自己的数据库负责，售后系统写成功不意味着物流系统也写成功。网络和队列把它们隔开，任何一步都可能超时、重复或晚到。若用一个外层 <code>try/catch</code> 包住三次接口，捕到异常时无法自动把已经发生的第一步“变成没发生”；更不能撤销客户收到的消息。

**领导：**那把三步放一个数据库事务里呢？

**小陈：**售后数据库管不了物流合作方和客户的短信。我们可以在自己系统内做局部事务，保证“创建退货申请”和“记录下一步待办”一起落库；跨系统则要接受短暂的部分完成，用一份持久化的业务流程记录把状态收敛到可解释的结果。分布式补偿并不是魔法撤销，是再执行一组符合业务规则的修正动作。

## “已建单”不能替“已预约”打勾

小陈把退货业务实例记为 <code>return_flow_id</code>，关联已批准的退货申请、客户订单、售后单 ID、物流预约操作 ID 和对客通知 ID。每一步至少有 <code>NOT_STARTED</code>、<code>IN_PROGRESS</code>、<code>SUCCEEDED</code>、<code>FAILED_FINAL</code>、<code>UNKNOWN</code>；是否有 <code>COMPENSATING</code> 与 <code>COMPENSATED</code> 取决于该步可否补偿。流程总状态不是简单“全部成功/有一步失败”：可能售后单成功、预约未知、尚未通知；也可能预约成功、通知失败，客户不知道具体时间；还可能消息已发，但预约后来被物流取消，需要再次告知客户。

**领导：**这些状态是不是写得太细？客服只想知道要怎么回客户。

**小陈：**就是为了让客服少猜。客服界面可以把复杂状态翻译成“退货申请已建，取件待确认”“取件已约，通知未送达”“预约失败，人工处理中”。但底层必须留足凭证，才能决定下一句话可否说。让客服只看一个“处理中”，系统却不知道卡在哪，客户会每次重讲一遍。

业务规则按事实推进：只有售后单有创建回执，才可向物流预约；只有物流预约有确认的预约 ID 和时间窗，才能生成“某时上门”的对客消息；只有通知渠道有回执，才可标“已通知”；最终仍要处理客户实际改约、取消或未取件的后续事件。这一连串判断在应用层完成，模型可写自然的话，但不能用语言把一个 UNKNOWN 变成 SUCCEEDED。

所有跨系统命令带业务操作键，消费端重复投递仍指向同一业务动作。创建售后单的键、物流预约键和发送通知键不同，因为它们是三种副作用；同一步重试沿用该步的键。若第一次预约成功但回执丢失，按原键查询或安全重试，不要产生第二次上门。若新预约需要改时间窗，则要生成经确认的新操作并处理旧预约状态，不能仅改一个参数继续用旧键。

## 快递拒绝、接口超时、客户改约，走三条路

**领导：**物流明说“无运力”，还能怎样？取消退货单。

**小陈：**有时可以改约下一时间窗；有时客户不愿意等，需要取消或换退货方式；有时售后单一旦建好还关联库存和财务，不一定允许直接删除。补救路线由业务规则和客户选择决定，不能由模型看到错误码就即兴决定。

我们先分类：技术性暂时故障可限次重试，前提是同一步幂等且不会叠加预约；业务性拒绝如该地址不覆盖，重试同样请求没意义，应提供其他方案；结果未知则先查物流侧，以免本来约上了又去取消；已发错误承诺要单独追客户影响。分类后，流程可选择向前修复、做补偿、或停在人负责的待办。对客户的说明与实际状态同步，不能把“系统正在找方案”说成“明天上门”。

假设物流 14:00 返回明确无运力。客服负责人确认客户愿意改约周五，则保留售后单，产生新的物流预约动作；周五预约成功后再通知。客户不愿改约且政策允许取消申请，先确认没有生效物流预约，再调用售后取消接口，得到取消回执后告知。取消接口也超时，就进入“取消结果未知”，继续对账；不能因为补偿动作失败，系统还把流程写成“已撤销”。每个方案的决定人、证据和客户沟通都留在同一 <code>return_flow_id</code> 上。

微软的 [补偿事务模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)强调，跨系统步骤失败时的补偿是按业务规则修正已完成的动作，未必严格按原顺序倒放，而且补偿自己也会失败。文章借用这个原理，不假设合作物流一定支持取消，也不假设发出的消息能收回。

## 取消是新动作，不是把旧记录擦掉

**领导：**退货单取消了，就把原来的记录删掉，页面干净。

**小陈：**删掉就没法解释客户为什么收过“明天上门”。补偿应新增可核实的反向业务事件，例如“取消申请”或“取消预约”，保留原建单与原预约的回执、取消原因和操作者。若物流已经派车，取消不一定即时生效；若客户已寄出商品，流程也不能退回“从未申请”。补偿的目标是到达一个业务上可接受、可解释的状态，不是擦掉历史。

这里有一个次序问题。客户通知属于很难撤回的外部副作用，所以应尽量放在关键事实确认之后。售后单创建相对可补偿，物流预约可能有取消窗口，客户承诺一旦说出口，就要承担处理它的后续成本。不要把“先发一条消息安抚客户，后面慢慢补”当优化；这正是事故起点。若通知必须尽早发生，也只能准确说“我们已收到申请，取件时间待确认”，不提前填写明天日期。

系统实现可以让一个持久化的流程协调器每完成一步就记录结果和下一步任务。售后系统局部事务里保存“申请已建＋预约待办”，由后台工作者取出待办调用物流，成功后更新状态并创建通知待办；工作者重启后从持久化状态续跑。所谓断点续跑不意味着把整个 Agent 思考过程重演，更不能重放副作用。对账进程定期扫描 <code>UNKNOWN</code> 和长时间 <code>IN_PROGRESS</code> 的步骤，查合作方真实状态，无法判定就分配人工。事件投递至少一次时，幂等与状态转移约束决定最终不会多约、多发。

**领导：**如果建退货单和“预约待办”只写成一半？

**小陈：**在我们自己数据库里应尽量用同一个局部事务一起落地，或使用可靠的 outbox 记录待投递事件。否则售后单建成了，协调器却不知道要约物流，业务永久悬空。跨系统无法靠一个本地事务包住，但本地记录至少不能自己先断链。恢复扫描要能找出“有售后单、无预约状态”的孤儿流程，交人核实后补发待办或取消。

## 地址一改、回执一迟，补偿会撞上并发

小陈给领导看另一张虚构单。客户上午申请退货，下午主动改了取件地址；与此同时 Agent 用旧地址重试预约。旧预约回执晚到，新预约又成功，物流出现两单。只靠 <code>return_flow_id</code> 去重不够，还需要流程版本和字段条件：每次预约绑定地址版本、时间窗与客户确认记录；回执回来时若版本已过期，不能把旧预约标为当前成功，应进入异常处理并尝试按合作方规则取消旧预约。取消结果也要有回执。

再如，客户自己在 App 撤销申请时，物流可能已经受理。应用不能单方面把三系统状态都改成“已撤销”。先冻结新的通知与动作，查询现有预约，调用允许的取消接口，若已无法取消，给客服一张明确待办与客户沟通方案。跨系统一致性不是一瞬间相等，而是每个不一致都有可追踪的收敛路径和截止时间。

下游消息发送失败也不能反向取消一个已成功的退货和预约。先查消息是否真的送达，再按同一通知键安全重试或换允许的渠道；人工客服要看见真实预约时间，必要时直接联系客户。把“通知失败”一律当“全流程失败”，可能引发多余取消，客户原本约好的快递反而没了。

## 领导把小陈拉进面试现场

正式评审时，小陈把三步流程再摊成“动作账”。退货申请建立时记售后单 ID、创建回执、能否取消和最晚取消条件；物流预约时记预约 ID、地址版本、时间窗、可改约范围与取消条件；通知客户时记消息模板版本、实际填入的时间、发送请求和渠道回执。每条动作都绑定 <code>return_flow_id</code> 和一个独立的 <code>operation_id</code>。业务流程记录负责串起动作，外部系统回执负责证明动作真的发生。只有模型说“我已安排”而没有物流预约 ID，账上就是没安排。

**领导：**动作账会不会变成一堆只有工程师能看懂的日志？

**小陈：**工程记录和客服页面分层呈现。工程师需要请求键、响应码和时间序列来排障；客服需要“申请已建、取件未确认、下一步由物流联络人负责、承诺回复时间”四件事。客服点击详情时能追到对应回执与受控客户资料。关键是不能让客服为查一个预约状态横跨三个后台猜谜，也不能让 Agent 把“售后单已建”的绿勾翻译成“上门已约”。

补偿决策还要看客户是否已经行动。物流预约失败、消息未发时，可以在公司规则允许下改约或取消售后单；消息已经发出“明天上门”时，即使随后取消预约，客户也需要收到更正并得到一个可执行安排；快递已经取走商品后，所谓“取消退货单”更可能造成货在路上、系统却显示无申请。小陈要求每条补偿动作先检查当前业务事实和可撤销窗口，再由业务负责人选择。如果无法安全自动执行，流程停在“人工裁决”，附上已发生动作、客户已知信息和可选方案。

**领导：**那自动化岂不是每次异常都停？

**小陈：**只停无法凭规则确定的异常。物流明确返回“当前时段无运力”且客户已同意备用时段，系统可以按预先批准的规则向前改约；请求超时但有可靠查询接口，先自动对账；通知接口短暂故障且渠道支持幂等，按同一通知键重试。客户不同意改约、取消费用不明或两个预约同时成功，才交人。把可自动处理和必须人工裁决的边界写清楚，自动化就不会在最难的地方假装全能。

跨系统任务还有“重复跑整条流程”的诱惑。工作者进程崩溃后从头执行第一步，若售后系统没有幂等保护，可能多建一张退货申请；第二步又多约一次快递。正确恢复从持久化步骤状态读取：每个成功步骤先核对回执，不重新执行；UNKNOWN 步骤先对账；确认未执行且前置条件仍有效的步骤才按原操作键重试。若客户中途改地址，旧步骤的前置版本失效，工作者不能机械续跑旧计划，先把流程交给规则或人工重新决策。

小陈给团队写了四个故障注入位置。售后单提交前断网，期待没有售后回执、无物流请求；售后单回执返回前断网，期待查同一操作键而不是新建；物流预约成功但回执丢失，期待对账找到旧预约、不再生成第二个；通知已发送但渠道回执迟到，期待发送任务进入未知并查证，不再盲目补发。每个位置都测进程重启后的状态。只跑“物流返回明确失败”一种演示，覆盖不到最危险的未知结果。

**领导：**我们怎么衡量这套流程比原来好？

**小陈：**看客户收到的承诺与真实预约的一致率、重复售后单和重复预约数、异常流程从发现到有主接管的时间、补偿失败积压以及客服查清状态的耗时。分子分母要按经核实的退货流程计，不能只看 API 调用成功率。若自动化把平均处理时间缩短，却多出客户空等一天的案例，那不是成功。

最后，小陈让一位没参与开发的客服按图处理“售后单成功、物流未知、通知未发”的样本。客服没有看后台日志，就能说出客户现在该收到什么、自己下一步查哪个回执、查不到交给谁。工程师也能从同一个 <code>return_flow_id</code> 追到请求和补偿。流程图若只有作者看得懂，生产故障时就会变成没人敢动的艺术品。

领导要求再测一条“补偿本身失败”的分支。售后单已经创建，物流明确拒绝，客户选择取消；取消售后申请的接口却超时。系统不能把流程标成“已取消”，也不能恢复到“待取件”，而是进入“取消结果待核”，继续查询售后系统并交给负责人。若查询确认取消成功，补上回执后告知客户；若确认未取消，按同一操作键安全重试；若仍未知，保留待办并说明真实进度。补偿动作和原动作一样，需要幂等、对账、超时和审计，不能被当作清理脚本一跑了之。

**领导：**客户等不了这么久，能不能先给一个大致日期？

**小陈：**可以说明计划中的下一次反馈时间，不能把未确认的取件日期当成已预约。若物流有多个可选时段，展示“可尝试的时间”并请客户选择，选中后仍以预约回执为准。承诺越具体，证据也要越具体。这样客服说话不如演示视频里流畅，却能让客户知道哪部分已经办妥、哪部分还在等合作方。

流程日志还要给业务一个“长时间悬空”视图。售后单创建超过约定时间仍无物流结果、物流已预约却迟迟未通知、补偿开始却没有结束回执，都按不同风险进入值班队列。单看每个服务的成功率，它们都可能是绿色：售后创建成功、物流偶发超时、消息服务正常；只有按 <code>return_flow_id</code> 看端到端结果，才能发现客户那句“明天上门”缺了哪张凭证。

**领导：**为什么不用数据库事务，非要说 Saga？

**小陈：**单一数据库事务能管本库的原子修改，管不了合作物流和客户收到的消息。跨服务长流程要让每一步独立提交并保留回执，失败时按业务规则向前修复或执行补偿。Saga 是理解这类顺序局部事务与补偿的一种模式，不是买一个框架就自动有取消能力。

**领导：**补偿是不是等于回滚？

**小陈：**数据库回滚让未提交的本地修改仿佛没发生；补偿是在已经发生之后再做一个反向或修正动作，历史和客户影响仍在。取消退货单可能需要审批，取消取件可能有时间窗，通知更无法从客户记忆里删除。

**领导：**说“明天上门”的最低证据是什么？

**小陈：**有经核实的客户地址和授权、有物流侧可验证的预约 ID、明确上门时间窗、尚未被客户改约或取消的有效状态。只建了退货单，最多说“申请已提交，时间待确认”。机器人生成得再肯定，也不能替代物流回执。

**领导：**流程卡住三天，谁管？

**小陈：**每个中间状态都带超时、负责人和升级队列。协调器发现超时，先对账，再分配售后或物流联络人；客服对客户给真实进度。不可恢复的流程写入异常台账，直到客户得到可执行的替代方案。没有责任人的“等待自动重试”不是恢复策略。

上线前，小陈用六种虚构故障回放：售后单创建失败、物流明确拒绝、物流结果未知、通知超时、取消预约失败、客户中途改地址。每种都检查三个系统的回执是否一致、客户是否只听到有依据的承诺、是否出现重复预约、失败状态是否有负责人。领导终于把演示里那句“明天上门”改成“预约确认后再通知”。客户没有听见一场技术名词讲座，只听到一段不需要第二天请假白等的实话。

小陈提醒客服，流程中的“人工接管”不是把异常从系统里删掉。人工选择改约、取消或补救后，也要回写对应操作和回执，让协调器知道下一步该停还是继续。否则后台扫描看到物流仍是失败，可能又自动发起一次预约。人和自动流程共同维护同一份状态账，才不会轮流把对方的处理推翻。

交接时客服还要能看见自动流程最近一次查询合作方的时间。十分钟前的“无运力”可能已经过期，不能据此永久拒绝客户；刚刚返回的“预约成功”也要核对地址与时间窗是否仍是客户当前选择。状态记录包含事实与时效，恢复程序按当前版本再判断，才不会拿旧回执处理新要求。
