**领导：**小陈，演示翻车了。Pi 一条回复里说“修改服务、修改测试、运行测试”，我以为它会按说话顺序来。结果测试先读到旧代码，报红以后 Agent 又把红测当新 Bug 改了一轮。你们是不是把循环写反了？

**小陈：**循环没写反，是我们把“模型列出三个动作”和“运行时保证三个动作依次完成”画了等号。先说明，下面的退款模块、文件名和日志都是教学虚构；并行语义依据 [Pi 官方源码固定提交](https://github.com/earendil-works/pi/blob/5257d0d5f3ab7d42550804f32c67a77b49f485d4/packages/agent/src/agent-loop.ts#L508)。领导想要的不是让模型少说几句“首先、然后”，而是给有依赖的动作真正的执行顺序。

## 先看循环：什么时候模型会再答一次

小陈从 [`agent-loop.ts` 的 `runLoop()`](https://github.com/earendil-works/pi/blob/5257d0d5f3ab7d42550804f32c67a77b49f485d4/packages/agent/src/agent-loop.ts#L160)画起：外层循环处理一次运行结束后可能到来的 follow-up，内层循环在工具调用、steering 消息或明确继续时再请求模型。每一轮先准备当前上下文与工具声明，再调用提供方获取流式 assistant 消息；若消息含工具调用，执行工具、追加结果，再进入下一轮。模型如果只给文本且没有待处理消息，Agent 就有理由停下。用户在模型运行中补一句“别改支付模块”，通常进入 steering 队列，在当前 assistant 回合之后处理；follow-up 则等 Agent 原本的工作收尾。两者都不是把一句话注入正在执行的文件写入系统调用里。

**领导：**模型明明把“改文件”和“跑测试”写成了第一、第二步，它怎么能不按顺序？

**小陈：**因为模型输出的是结构化 `toolCall` 数组，不是人类会议纪要。Pi 的 [`executeToolCalls()`](https://github.com/earendil-works/pi/blob/5257d0d5f3ab7d42550804f32c67a77b49f485d4/packages/agent/src/agent-loop.ts#L508)会检查执行模式：Agent 默认 `parallel`；只要批次里有工具声明 `executionMode: "sequential"`，或全局模式设为顺序，整批走顺序路径。否则它走并行路径。并行路径里的预检按调用数组顺序做，真正的执行函数被收集后通过 `Promise.all` 并发启动。完成事件可以按照实际完成时间出现，工具结果消息最终按源调用顺序追加。**回执在会话里的排列顺序，不证明工具执行时也是这个顺序。**

这正是演示翻车的根。假设模型在一条 assistant 消息中发了 `edit(service.ts)`、`edit(service.test.ts)`、`bash(test)`，三项都被允许。两个编辑与测试可能同时跑；测试读取文件时，第一个编辑还没落盘，于是红测看见旧状态。即使返回消息排成“编辑成功、编辑成功、测试失败”，时间线上也可能是“测试开始、两个编辑完成、测试结束”。如果仅看最后三行日志，很容易把并发导致的观察差写成“新改动没通过测试”。这种误判会使模型进入错误修复循环，改得越勤快，仓库越像领导改需求那样难以预测。

把 [`agent-loop.ts` 的分流代码](https://github.com/earendil-works/pi/blob/5257d0d5f3ab7d42550804f32c67a77b49f485d4/packages/agent/src/agent-loop.ts#L508)缩成下面几行，就能看见“暗门”在哪。此处为**教学改写**，保留了分流与并发时序，省略事件、取消和错误处理：

```ts
async function executeToolCalls(context, assistantMessage, config) {
  const calls = assistantMessage.content.filter(x => x.type === "toolCall");
  const mustWait = calls.some(call =>
    context.tools.find(tool => tool.name === call.name)?.executionMode === "sequential"
  );
  if (config.toolExecution === "sequential" || mustWait) {
    return executeToolCallsSequential(calls);
  }

  const prepared = [];
  for (const call of calls) prepared.push(await prepareToolCall(call));
  const completed = await Promise.all(prepared.map(runPreparedToolCall));
  return completed.map(createToolResultMessage);
}
```

前三行只在**选择执行策略**；`prepareToolCall` 的 `for` 保证预检是顺序的；`Promise.all` 才是同时启动执行的地方；最后 `map` 按数组位置整理结果，不会把现实时间倒回去。要让测试依赖编辑完成，必须改变批次结构或执行模式。仅在提示词里写“按顺序思考”，不会修改 `Promise.all` 的语义。

## 预检是顺序的，为什么仍然挡不住竞争

小陈把并行实现拆成两个阶段。第一阶段逐个发 `tool_execution_start`，调用 `prepareToolCall()` 查工具是否存在、参数是否合法，运行 `beforeToolCall` 钩子；可能在这一步被扩展阻断。第二阶段把准备好的执行函数放进数组，再并发执行，最后 `Promise.all` 汇总。这个设计让插件审核、参数错误等预检结果按一个可理解的顺序产生，但预检不能替代写入完成。审批放行了第一个 `edit`，只是“准你执行”，不是“文件已写到磁盘”。若一个插件在 `tool_call` 阶段靠读文件判断另一个同批工具是否已经改好，也会读到错误时点。

| 位置 | 发生的事 | 能推断什么 | 不能推断什么 |
| --- | --- | --- | --- |
| 预检结束 | 工具名、参数、扩展阻断已检查 | 这次调用有资格进入执行 | 前一个工具动作已完成 |
| 执行结束事件 | 某个具体工具返回或失败 | 该工具已产生回执 | 同批所有工具已完成 |
| 结果消息追加 | 批次结果按调用顺序进入会话 | 下一轮模型能依顺序阅读回执 | 真实动作也按这个顺序发生 |
| 下一轮模型请求 | 已持有批次的回执 | 可以据实际结果决定后续 | 能反推未知外部系统没有副作用 |

**领导：**那我把系统提示改成“请一定等改完再测”，够不够？

**小陈：**能降低模型同时发出三个调用的概率，不能建立运行时保证。更稳妥的办法是把有依赖的动作放在不同模型回合：先完成编辑，收到编辑工具回执，下一轮再发测试。若这是你自己写的“提交计划”工具，还可以给它声明 `executionMode: "sequential"`。热门插件 Plannotator 的 [提交计划工具](https://github.com/backnotprop/plannotator/blob/0ba146d5bbb5ed371798f6b3195af5ecffe72480/apps/pi-extension/index.ts#L1215)正是因为“编辑计划文件＋提交审阅”同批时可能读到旧计划，明确设了顺序模式；它的代码注释解释了整个批次会按序跑。这个真实例子证明并行问题不只在支付业务，连审阅一个 Markdown 文件也会遇到。我们能借鉴机制，不能把某个插件“解决了自己的竞争”当作全局顺序已经有保障。

还有文件级互斥。Pi 扩展文档建议会改文件的工具把完整的“读—改—写”操作包进 `withFileMutationQueue()`。原因是即使两个不同工具都只改同一文件的一小段，若同时读到旧版本，再各自覆盖整文件，后写者会冲掉先写者。队列解决同一文件的竞争，不解决“编辑 service.ts 后测试 service.test.ts”这种跨文件依赖；后者仍需工具批次顺序或拆回合。团队不能靠一个锁宣称所有流程都串行，也不该把互不相干的只读搜索全部锁成单车道。并发策略要跟资源冲突一致。

## 失败返回与“结束”不是一个布尔值

演示里还有第二个错：测试命令返回了红字，Agent 却继续写“已经修好”。小陈把工具回执划成几种。参数 JSON 不合法或工具名找不到，执行前就失败；`execute()` 抛异常，会转成失败的工具结果；工具函数若只返回一段写着“Error: timeout”的文本而没有 `isError: true`，运行时不一定替它判断。反过来，某个工具成功返回 `terminate: true` 也不能单独强迫整批停止：源码的 [`shouldTerminateToolBatch()`](https://github.com/earendil-works/pi/blob/5257d0d5f3ab7d42550804f32c67a77b49f485d4/packages/agent/src/agent-loop.ts#L689)要求这一批已完成调用全部声明终止。假设一个工具给了“本轮结束”，另一个工具没给，下一轮仍可能继续。终止语义不能靠末尾文字猜。

模型自身的 `stopReason` 也要分开看。`error` 或 `aborted` 会走结束当前 run 的路径；`length` 表示响应被截断。如果截断的消息里带了工具调用，Pi [源码明确拒绝执行整批不完整参数](https://github.com/earendil-works/pi/blob/5257d0d5f3ab7d42550804f32c67a77b49f485d4/packages/agent/src/agent-loop.ts#L258)，为它们生成失败结果。这是比“JSON 看着差不多就试试”稳得多的处理：一段没收完的 `bash` 参数可能少了引号、路径或过滤条件，贸然执行比报错重试危险。停、失败、截断、取消、继续，是不同的控制状态；只用 `success` 一个字段无法交代清楚。

**领导：**那模型工具调用失败后，是不是一定会重新调用？

**小陈：**不一定，取决于回执、队列与下一轮选择。读文件路径拼错，模型看见错误后可能改路径；没有相应工具能力，可能解释限制；用户在此时发 steering，下一轮可能先处理新约束；预算或外部取消也能结束。更要命的是“失败”常常指**没有拿到确认**，不指**动作没有发生**。测试运行超时通常可以按条件重跑；发邮件或支付请求超时，要先查服务端是否收到，不能给模型一条“失败请重试”就当去重。Agent loop 帮你再次思考，但不帮业务系统撤销已经发生的动作。

## 插件挡下的调用，也要留下一个能读懂的结果

领导接着拿出另一段演示录像：模型要执行 `bash` 清理测试目录，权限插件弹出“拒绝”。模型下一轮却说“清理已完成，准备测试”。小陈沿 [`AgentSession` 的前后工具钩子](https://github.com/earendil-works/pi/blob/5257d0d5f3ab7d42550804f32c67a77b49f485d4/packages/coding-agent/src/core/agent-session.ts#L603)查：`beforeToolCall` 将工具名、调用 ID、输入交给扩展的 `tool_call` 事件，扩展可以改参数或阻断；`afterToolCall` 在执行结果出来后发 `tool_result`，扩展可以改内容和结构化结果。若阻断，Agent 应收到明确的失败回执，而不是一条含糊的“工具返回了东西”。录像中的问题更可能是模型没有正确解释拒绝，或展示层把 `isError` 丢了；真正诊断要看会话里记录的那条调用与结果，不能只看一帧弹窗。

这也解释为什么 `tool_call` 钩子出错时 Pi 要保守处理。官方扩展文档说明该类处理失败会阻断工具，避免审核程序自己崩了却把危险动作放行。假设公司在事件处理器里用正则识别 `rm`，输入一复杂就抛异常；运行时不应因为“审核器没返回否决”就执行命令。另一方面，事件处理器失败会让正常命令也受阻，所以审批代码要有自己的错误日志和修复流程，不能只把用户晾在“正在执行”。工程上应该把拒绝、需要人工批准、策略故障分别显示。三个状态对业务动作都意味着“目前没有确认执行”，但治理动作不同：拒绝需要改方案，待批需要找人，策略故障需要修插件。

工具结果还有两个出口。模型看的 `content` 可以是人读得懂的短文本；程序调用者可消费 `structuredContent`，其结构由 `outputSchema` 约束。一个插件若在 `tool_result` 里把 `content` 脱敏，却忘了更新 `structuredContent`，另一个脚本可能仍拿到原始数据。反过来，若只改了 `content`，Pi 的文档说明替换内容时应同步处理结构化内容；否则结构化内容可能被丢掉。审计时要分别确认“模型看到了什么”“程序拿到了什么”“终端展示了什么”。三份视图可能不同，不能拿其中一份截图证明另外两份安全。

**领导：**我们还有一个工具，里面再调用两个工具。它们也受权限插件管吗？

**小陈：**按 Pi 当前扩展 API，如果自定义工具通过 `ctx.executeTool()` 调另一工具，这种嵌套调用仍经过参数验证、`tool_call` 和 `tool_result` 钩子，并带 `parentToolCallId`。不过嵌套调用不是模型直接发出的独立消息，不会逐条写进主对话的 tool call／tool result；父工具要负责把它们的结果归纳成自己的回执。Pi 会在父结果上保留有上限的嵌套调用记录，包括名称、参数、状态、耗时与错误，但不存子结果全文。审核器如果只监听模型最外层发的工具，不监听嵌套事件，就可能漏掉真正访问网络或写文件的子动作。反过来，计费和追踪若把父结果与子工具又算一遍，也可能重复计数。这个问题比“有没有一个权限弹窗”更接近生产系统。

取消也要有对象。用户按下中断时，`AbortSignal` 会传给正在执行的工具；愿意配合取消的工具可以停止。已经提交给外部服务的请求可能无法撤回，或者本地工具不检查 signal 而继续跑完。小陈要求工具回执记录“收到取消信号的时间、进程或请求是否确认停止、是否产生业务回执”。若模型因取消停止发言，不能由此断言磁盘没有被写过。恢复步骤还是先看差异和外部系统的事实，再决定是否继续。这个原则同样适用于网络错误、终端被关和电脑断电。

## 三种方案摆到领导桌上，各管一类顺序

小陈把解决并发的方案写成三个选项，让领导按实际动作选，不再用“全都串行最安全”拍脑袋。第一种是**分回合**：编辑与测试存在因果依赖时，让第一批编辑回执完整入会话，再让模型发第二批测试。这最直观，模型也能在第二轮检查 diff；代价是多一次模型请求和可能的延迟。第二种是**顺序工具声明**：当一个工具本身代表审批、提交计划或发布这类必须等待前动作结束的关口，在其定义上标 `executionMode: "sequential"`，使含它的批次整批按序执行。它约束的是单条 assistant 消息内的运行顺序，解决不了另一个并发进程同时改同一工作区。第三种是**资源互斥**：对可能同时改同一文件的工具使用文件变更队列，或在服务端对同一业务键加唯一约束和事务锁。它管资源冲突，不能替代前两种的流程依赖。

| 症状 | 首先考虑 | 验证方式 |
| --- | --- | --- |
| 测试先读到旧文件 | 分回合，或把关键工具设顺序 | 测试开始前核文件内容与差异摘要 |
| 同一文件两次修改互相覆盖 | 完整读改写排队 | 构造两个并发修改，确认两者都保留 |
| 两笔退款同时通过“尚未退款”检查 | 数据库唯一约束和业务幂等 | 并发请求与支付网关回执对账 |
| 被拒绝的工具仍被模型当成功 | 保留 `isError` 与阻断原因 | 对照调用 ID、事件与会话消息 |
| 工具返回太长，被截掉关键错误 | 保存完整日志位置，模型只读摘要 | 检查尾部错误、退出码、跳过数量 |

**领导：**你这张表怎么连数据库都扯进来了？我们不是在讲 Pi 吗？

**小陈：**因为 Pi 负责调度工具，不替公司业务定义原子性。它可以保证某个回合的工具先后，不能保证两个不同员工、两个不同 Agent 或外部重试不会同时提交退款。用顺序工具把测试改得漂亮，服务端缺少幂等仍会重复扣款；反过来，数据库有唯一约束，也不能让模型拿一次旧版本红测当作新版验证。工程边界刚好在这里：Agent loop 管“这一轮怎样走”，工具与业务系统管“动作到底发生了什么”。

为了让回放能辨别这两层，小陈给工具结果加上具体的业务关联：代码工具回报文件路径与变更摘要，测试工具回报命令、工作目录、退出码和测试报告路径；外发工具必须有请求 ID、幂等键、服务端状态或“未知”的明确标识。若只返回“OK”，模型下一轮没法判断有没有用同一个版本验证、是否可以重试、是否要等人工。多给回执字段会占一些上下文，但比反复让模型在模糊结果上猜，通常省下更大的返工；大日志可以落文件，只传定位线索。

**领导：**那我们是不是要把 Pi 全局改成顺序，省得以后出事？

**小陈：**那会把三个互不相关的只读搜索也排队，延迟变长，成本未必下降。正确做法是给动作建依赖：能并行的读动作并行；需要前置产物的测试、发布、审阅必须等它；对共享文件加读改写保护；外部副作用再加业务幂等和权限。执行模式只是控制一批工具怎么跑，不是业务一致性协议。比如写数据库与发邮件按顺序执行，邮件超时仍然可能已送达；顺序不等于可重试。一个可以上线的工具契约，至少写清输入 schema、读写范围、外部副作用、超时、取消、错误返回、幂等键和“未知结果”怎么处理。

小陈还提醒领导不要把 `tool_execution_start` 当“实际进程已启动”。Pi 发这个事件的时点在预检前；插件可以在后续 `tool_call` 阻断。审计若只统计 start，会把被拒绝的危险命令也算成已执行；若只统计成功回执，又会漏掉结果未知的外发。一个完整追踪至少要配对 start/end、`isError`、阻断原因与业务回执 ID。第五、六篇会看热门插件怎样在这些事件上挂自己的网关和追踪。

## 小陈给演示仓库的改法

这次虚构事故，小陈没有给提示词再叠一层“绝对不要并行”的彩带。他把流程改成三段。第一段只读：让 Agent 搜索入口和测试位置，记录工作区未提交差异。第二段写入：模型可以在一个回合修改相互独立的文件，但若两个工具会碰同一文件，要用文件变更队列或拆回合；编辑结束后检查 diff 和文件内容。第三段验证：新的模型回合在已写入的版本上跑针对性测试，命令回执包含退出码、运行范围、跳过数量和日志位置。失败时先判是竞争造成的旧版本测试，还是逻辑断言真的失败。交付文本只对实际跑过的范围负责。

**领导：**我最关心一句话：面试问“Pi 里多个工具怎么跑”，候选人怎样答才算懂？

**小陈：**答到“默认并行”只是及格线。还要说：预检按调用顺序，真正可执行项通过 `Promise.all` 同时跑；完成事件可能先后不同，回写给模型的结果按原调用顺序；存在 `executionMode: "sequential"` 或全局顺序设置时整批串行；参数截断不执行；文件并发和跨文件依赖分别处理；外部副作用还需要服务端幂等与对账。能用同一条虚构轨迹解释“为什么测试先读到旧代码”，才是真的读过源码，不是背过 README。

**这篇的交付结果：**领导得到的是一张可复现的并行时序账、一份工具契约、一条把编辑与测试拆开的运行路线。下次测试再报红，小陈先看它读的是哪个版本，而不是先让 Agent 再改三份文件。领导说：“那你顺便查下它是不是能忘记这次翻车。”这就进入下一篇的会话树和压缩。

真要在复盘会上讲清楚，带上原始调用 ID 和时间戳；它们比“应该是按顺序的”更有说服力。
