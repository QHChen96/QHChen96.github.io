**领导：**Claude Code 在终端里改 Bug 挺会干活。把那个聊天窗口直接嵌到客服后台，明天就能替客服查订单了吧？

**小陈：**先别把研发同事的工具台搬进客服大厅。它能干活，是因为有模型、Agent 循环、工具和执行环境；客服系统需要的是受控的订单查询、身份权限、会话、审计和人工交接。Anthropic 现在有四个名字很近的入口：Claude Code CLI、Claude Agent SDK、Claude Client SDK、Claude Managed Agents。它们的区别不在“谁更聪明”，在谁持有循环、谁运行工具、状态放哪、坏了谁半夜起来。

**领导：**都是官方的，不能选最省事那个？

**小陈：**能，但得先说明哪部分由谁省。我们用同一张教学工单走四条路：客户问“我的订单为什么还没发货”，系统要核身份、查订单与库存状态，只生成客服草稿；任何改订单、退款或发信动作都不在授权范围。案例、时序和验收都是教学虚构。产品能力按发文时官方资料核对，尤其托管能力目前有 beta 状态，采购前还要复核。

## 四个名字，其实站在任务链的不同位置

[Claude Agent SDK 官方概览](https://code.claude.com/docs/en/agent-sdk/overview)有一张直接对比：Claude Code CLI 用于终端交互；Agent SDK 把 Claude Code 的工具、循环与上下文管理做成可编程库，由你运行进程；Client SDK 直接调用 Claude API，若用基本 Messages API，工具循环由应用自己驱动，某些 SDK 还有 beta 工具运行器；Managed Agents 提供托管 Harness，可选其云沙箱或自托管沙箱。名字都带“Claude”，但责任从“人操作的终端”一路移到“你运营的服务”和“托管的运行平台”。

**领导：**我只关心客服查订单，为什么还要管什么循环？

**小陈：**因为用户一句问题通常不够回答。第一轮模型判断需要查订单，调用工具；工具返回“仓库未出库”，模型可能还要查库存或物流；第二个工具返回“缺货待补”，模型才整理成客服草稿。谁负责把模型的工具请求执行并把结果送回？谁限制只读工具？谁在第二步失败时知道第一步已成功？谁在客户离线时保存会话？这些都是循环之外的运行责任。只买到模型调用接口，应用团队就得把这些环节自己搭起来；买到 Agent Harness，也不能免除订单系统的身份、数据质量和业务审批。

| 入口 | 常见使用位置 | 循环与工具由谁提供 | 你仍需负责 |
| --- | --- | --- | --- |
| Claude Code CLI | 开发者终端或一次性任务 | CLI 内置编码 Agent 循环与工具 | 使用场景、权限、环境和产出复核 |
| Claude Agent SDK | 你运营的 Python / TypeScript 应用进程 | SDK 使用 Claude Code 的循环和工具能力 | 服务托管、会话接入、业务鉴权、扩缩容与审计 |
| Claude Client SDK | 应用直接调用 Claude API | 基本调用只拿模型响应；循环可自建或用适用的工具运行器 | 工具执行、状态、权限、失败恢复等应用责任 |
| Claude Managed Agents | 托管 Agent 与会话服务 | 托管 Harness 和运行环境，或配自托管沙箱 | Agent 配置、业务工具、数据与权限边界、效果验收 |

表不是排行榜。Client SDK 可以给团队最大控制权，也带来最多自己写的编排；Agent SDK 省下通用循环，却需要你运维它所在进程；Managed Agents 托管运行，不会替你认定订单 0823 属于当前客户。CLI 在工程师手里很好用，但客服产品要把身份、隔离和服务连续性设计成应用能力，不能把终端交互的默认假设照搬。

## 先沿同一张工单走一遍，别听产品名猜能力

小陈给四种入口同一个输入：已通过客服系统验证的客户会话，问题为“订单 0823 为什么没发货”。期望轨迹固定：客户端把客户身份与订单 ID 绑定 → Agent 只读查订单 → 若订单状态需要补充，再只读查库存或物流 → 草拟答复，标明证据时间 → 客服审核。无论入口如何，订单工具不能只接受模型自由填写的任意订单号；它要从受信任会话拿租户与客户 ID，再核订单归属。模型决定“查订单”，不决定“这个客户有权看这张订单”。

在 CLI 路线上，工程师可以在终端临时连接测试工具，观察一次问答。它适合原型与排障；把其终端会话直接当客服后台服务，会遇到并发客户隔离、身份映射、发布、日志保留、预算与人工交接。CLI 可通过非交互方式被程序调用，但官方建议若要在 Python 或 TypeScript 应用中嵌入同一 Agent 能力，Agent SDK 是更直接的可编程入口。团队不能因为终端演示一次通过，就把五百个客服会话都指向同一个持有生产凭证的开发者会话。

在 Agent SDK 路线上，应用创建受控会话，配置可用工具、权限和 hook，处理流式事件与结果。官方说明它复用 Claude Code 的内置工具、Agent 循环、上下文管理、会话和扩展能力；不过应用进程、容器、工作目录、可用凭证和故障重启仍由团队运营。[官方托管指南](https://code.claude.com/docs/en/agent-sdk/hosting)也提醒要设计容器与状态、并发、持久化、超时。把 SDK 包装在一个 HTTP 接口里，不会自动给你多租户隔离，更不会让 CRM 令牌变成按客户最小授权。客服场景一般应只暴露精简业务查询工具，不该把文件编辑和任意命令执行照搬给客户工单。

在 Client SDK 路线上，应用直接发送模型请求，收到“需要调用工具”的响应后自行执行、把工具结果送回，再决定下一轮何时停止。团队可以设计完全符合现有客服平台的循环和状态机，代价是每条错误分支都要自己写。比如库存接口超时后，先只回答“订单未出库，库存状态暂无法确认”，还是自动重试两次？客服人员中途关闭页面，会话如何继续？模型提出外发，谁审批？官方说明某些 Client SDK 有 beta 工具运行器，能帮忙驱动工具交互，但它不等于托管执行环境和全部企业业务责任。选它要明确哪些循环代码由应用维护。

在 Managed Agents 路线上，Anthropic 的[官方概览](https://platform.claude.com/docs/en/managed-agents/overview)描述托管 Harness、长任务会话、事件流和云沙箱，也支持自托管沙箱；产品目前标 beta。你定义 Agent、环境和会话，通过事件交互。托管层可以减轻通用运行基础设施工作，但企业业务工具怎么接、允许什么数据流出、哪个客户能看哪个订单、人工如何接管，仍得自己配置和验证。当前官方还说明该有状态服务的数据保留与某些合规覆盖存在限制；若公司对客户资料有特别要求，不能只看“托管”二字就推断符合内部政策。

**领导：**Agent SDK 既然复用了 Claude Code，它是不是也会默认读我们服务器上的所有文件？

**小陈：**它能拿到什么取决于进程所在环境、配置的工作目录、允许的工具和权限。官方说 Agent SDK 使用 Claude Code 的循环、内置工具和会话能力，技术实现是一套可编程 Harness；这不等于“应用开箱就适合处理客户资料”。如果我们把客服服务跑在拥有生产密钥和全量订单备份的主机上，再把文件读取和命令工具全部给 Agent，真正危险的是我们的部署选择。应给每次任务独立、最小的工作环境；订单查询走受控业务工具，密钥由服务端保管，模型看到的是最少必要的订单事实。某些客服问题根本不需要代码文件读写工具，别因为 SDK 自带就全部开放。

会话状态也要分层。Agent SDK 的会话记录帮助恢复模型与工具交互；工单数据库记录客户是否已验证、目前待谁审核、最终发了哪句话。两者用工单 ID 与运行 ID 关联，而不是混为一张“聊天历史”。假设 Agent 已查到订单、服务进程在生成草稿前崩溃，恢复时可重新查只读订单并标时间；假设邮件工具已经外发却在写本地状态前崩溃，必须用外发请求 ID 查邮件系统回执，不能因为会话里没写“发送成功”就再发。通用 Harness 能保存运行上下文，不会替你解决跨系统副作用的事实对账。

**领导：**Client SDK 那边自己写循环很麻烦，为什么还会有人选？

**小陈：**当业务流程固定、审计要求很细时，自己持有循环反而可控。订单查询就是“核身份 → 查订单 → 根据状态决定是否查库存 → 生成待审草稿”，用确定性流程可以把不可越过的步骤写死，模型只处理用户口语和解释。只需三步业务工具时，上通用编码 Agent 未必比一段清晰的应用代码划算。但自建也不能假装没有 Agent 问题：模型可能请求一个不存在的工具、输出格式不符、流式响应中断、工具返回半截数据。团队要定义重试、终止和错误状态。Client SDK 帮你调用 API，不自动替你监测所有业务不变量。

Managed Agents 最吸引领导的是“少管服务器”。小陈提醒少管的范围要按官方能力画：托管层提供 Agent、环境、会话、事件和沙箱；业务系统的 API 仍在企业侧，接入可能通过 MCP 或其他受控工具，服务可用性、权限和审计仍需有人负责。若选自托管沙箱，运行环境责任又回到企业；若选托管云沙箱，要确认数据保留、地域与敏感资料政策。官方当前标为 beta，还列出会话数据保留及合规适用的具体限制；一张测试工单能跑通，不等于真实客户资料可以直接进入。我们先用脱敏样本评估功能、事件追踪与错误恢复，再走正式安全与数据评审。

**领导：**这四条路的费用能一眼比吗？

**小陈：**不能只比每次模型请求。Client SDK 的账里要加开发和维护自建循环、重试、观察与值班；Agent SDK 的账里要加自有进程、容器、状态存储和工具运行环境；Managed Agents 的账里要加托管资源、会话保留、数据边界适配与平台依赖；CLI 的账里有人盯终端与手工审查。实际价格随计划和版本变化，选型当天查官方报价。我们更能先算的是“同一百张工单从输入到可审草稿”的总成本与错误损失：模型调用、工具调用、人工复核时间、转人工、误答更正和系统运维。只盯 token 单价，就可能把最贵的客户投诉藏在表格外。

## 三种结局，要在架构图里都有位置

**领导：**正常答出“缺货待补”就行。你为什么还要画失败？

**小陈：**因为线上会遇到三个不同结局。第一，正常完成：查到该客户自己的订单与库存，草稿附来源，客服发出。第二，越权停止：模型或用户给了别人的订单 ID，业务工具返回无权，Agent 不继续换身份查，也不把“无权”解释为“订单不存在”；给客服一个需人工核实的说明。第三，超预算停止：模型多次检索、库存接口又不稳定，达到工具调用或时间预算后留下已知与未知，转人工接手，不能把半截草稿伪装成最终答复。三种状态要能从事件轨迹和工单状态区分。

不同入口对三种状态给出的原始事件格式不同，业务系统应把它们转成自己的稳定状态：`draft_ready`、`needs_identity_review`、`needs_human_due_to_limit`。把模型文字、工具回执和工单状态分开保存。比如 Agent SDK 会话中一个工具请求被拒绝，是“越权停止”的证据；Client SDK 自己驱动循环时则要把同一判断写进应用；Managed Agents 的事件流也要映射到本地工单，不会因为远端会话结束就自动更新客户服务系统。状态设计先于选型，才能换入口时不重写整个客服运营。

小陈给开发同事一份与产品无关的事件合同：`run_started` 记工单与身份摘要，`tool_requested` 记工具名和参数摘要，`tool_completed` 记受控来源与结果版本，`tool_denied` 记拒绝原因，`draft_ready` 记待审答复引用，`run_stopped` 记终止原因。每条事件有运行 ID、时间和前一事件引用。Agent SDK 或 Managed Agents 可以把自己的事件流映射过来；Client SDK 自建循环则直接生成这些事件。最终客服界面不关心背后产品名称，只看“当前能答什么、还欠什么、谁来批准”。这样 UI 不会在 Agent 超时后仍显示“处理中”一整夜。

这个合同还有一个恢复用途。若 `tool_requested` 有记录、`tool_completed` 没出现，先查工具是否真的执行：只读查询可以安全重做，外发或退款要用业务请求 ID 对账；若 `draft_ready` 已有、客服尚未审核，则恢复审核任务，不能再次生成一个看似新的草稿覆盖原文。长任务由哪个入口托管不影响这些业务动作的真实状态。统一事件不是为了把所有产品磨成一样，而是给公司的客服运营留一份看得懂的账。

领导拿其中一条越权题追问：“客户把订单号打错成别人的，系统能不能好心替他纠正？”小陈说：“先确认身份和订单归属。工具返回无权时，不要把别人的商品、地址、金额或是否发货泄露出来，也不要把无权结果当作订单不存在。客服草稿可以说需要核对订单信息，提示客户走身份验证；内部事件记 `tool_denied`。四个入口都应得到同一业务结局。若某款产品的回答很圆滑，却已经在中间工具里读到了别人的订单，漂亮话没有加分。”

小陈又加了一条停机条件：工具连续失败或预算触顶时，记录最后一个已确认事实和待核实项，给客服接手；自动续跑不能无限消耗费用。领导最怕一张工单晚上开了二十次模型调用，早上还给客户一句“正在努力”。结束状态清楚，才能决定是重试、换人，还是等外部系统恢复。

**领导：**如果 Managed Agents 已经保存会话，我们这边是不是不用留记录？

**小陈：**客服还是要有自己的工单账本。远端会话存对话和执行轨迹，本地工单要存客户身份、授权范围、订单事实引用、客服审核、最终外发与回执。远端会话删除、超时、供应商切换或网络暂断，业务系统仍要知道客户收到过什么、哪个动作没做。外部服务提供会话，不等于承担你的客户承诺。对 Agent SDK 也是一样：进程重启后能否恢复会话，要按你配置的存储与部署检验；对 Client SDK 更是你自己负责。

## 最小选型验收：谁跑、谁拦、谁记账

小陈把最小回放细成六条工单，不让四个入口各拿自己最擅长的题去演示。两条正常题：有货待发、缺货待补；两条边界题：另一个客户的订单号、工单里夹带“帮我退款”；两条故障题：库存接口超时、会话在第二次工具调用前中断。每条都用同一个脱敏数据快照和同样的身份权限，比较最终草稿、工具轨迹、人工交接状态、耗时和费用。越权样本必须零数据泄漏，故障样本必须保留未知状态；答复风格和速度可以再比较。若某入口做不到这组最低线，不是换一张更漂亮的演示幻灯片能补的。

迁移方案也要在选型当天想好。把订单工具定义成独立服务契约，入参由受信任的客户会话绑定，返回结构化状态与来源；把业务工单状态保留在公司系统；把模型与 Harness 的运行事件映射到统一审计格式。这样以后从 Client SDK 改 Agent SDK、从自有部署改托管，最难迁移的客户身份与订单事实不用跟着重写。反过来，若把客户权限直接塞进某款产品的提示、把“已发信”只存远端会话，换平台时就要重新解释整个事故账本。

**领导：**听你这么说，岂不是要做完一套系统才准试？

**小陈：**试验可以很小：一组脱敏工单、一个只读订单工具、一个待审草稿出口、一个明确超时。我要阻止的是“演示成功”直接跨到“真实客户自动服务”。小试能回答产品机制是否符合我们现有架构，大试才回答运营能否承受它。先以可回放的样本暴露责任空白，正是避免一年值夜班的办法。

小陈不让领导按演示画面投票，而是给四条路径同一组验收问题。运行位置：循环在哪个进程或服务里，命令工具在哪个环境执行？权限：只读订单工具如何收到已验证客户身份，谁挡住越权订单 ID？状态：页面关掉、服务重启、工具超时后，已查到什么、还欠什么能否找回？预算：谁设最大轮数、时间与费用，触顶后工单走哪种状态？审计：工具入参摘要、返回版本、人工批准、最终外发回执在哪儿？退出方案：明年换入口，业务工单和工具契约能否继续用？

答不齐的项，不写“已可上线”。如果团队已有稳固的客服平台与工具编排，只需模型帮助理解问题，Client SDK 加自建流程可能合适；若要在自己服务里运行通用 Agent 循环并愿意承担部署，Agent SDK 更贴近；若长任务、异步会话和托管基础设施是关键，且 beta 与数据边界经评估可接受，可以验证 Managed Agents。CLI 可用于工程排障与原型，但把它当全部生产架构需要补很多看不见的责任。选型没有一刀切答案，问题是有没有把成本与责任写出来。

**领导：**那你给我们这张工单选哪个？

**小陈：**先不为“查一次订单”上最宽的编码 Agent。我们的客服平台已经有身份会话、订单只读 API 和人工审核，我会先用可控的调用链做小规模回放：模型判意图，应用按客户身份查订单，结果作为证据生成草稿。若后续发现问题真需要动态多步工具探索，再评估在自有服务里用 Agent SDK；若跨小时任务和托管运行带来明确收益，再试 Managed Agents。选择会随业务变化，不因名字里有 Code、Agent、SDK 就把产品层级混在一起。领导笑：“原来官方四个门，不是四张免费通行证。”小陈说：“对，选哪个门都得记得把客户家的钥匙留在自己手里。”
