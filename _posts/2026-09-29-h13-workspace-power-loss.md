**领导：**测试跑一半机器断电了。Agent 有检查点，让它从上次对话继续不就完了？

**小陈：**先别让它碰键盘。检查点说“补丁已写，准备跑测试”，磁盘上有一半补丁，测试报告没生成；同事抢修时还改了同一个文件。它若按摘要继续，最轻是覆盖同事改动，最重是拿半份代码报“测试通过”。

**领导：**那重跑整张 issue，干净点。

**小陈：**也不干净。可能已经创建 PR、可能已有可用的测试成果，重跑会重复外部动作和浪费时间。先把会话检查点、真实工作区和外部系统对齐，给每一段改动判定“已验证、未验证、他人修改或未知”，然后再续跑。

文中的断电事故、提交与 PR 为教学虚构。Git、LangGraph 与长任务 Harness 的能力以文内官方文档为准。

## “接着改”之前，先回答现在站在哪个版本上

小陈拿到任务 #318 的检查点：基线提交 <code>abc123</code>，上轮写了验证码版本检查，下一步运行乱序测试。这个记录只说明 Harness 认为流程走到那里。真实工作区里，<code>LoginService</code> 有未提交修改、测试文件有新用例、依赖安装留下临时产物；而 <code>LoginController</code> 还有同事夜间追加的一行防护。Git 的[status 文档](https://git-scm.com/docs/git-status)说明它能展示 HEAD、暂存区与工作区之间的差异，以及未跟踪文件；[diff 文档](https://git-scm.com/docs/git-diff)可比较提交与工作树。小陈先看这些客观状态，再对照任务日志与文件写入记录，不能让检查点一句“已完成补丁”覆盖磁盘事实。

**领导：**既然有未提交修改，全部保留不就好了？

**小陈：**保留现场是第一步，不等于全部算 Agent 成果。谁写了哪段、从哪个基线写、是否经过测试，都要分。若同事的防护改动和 Agent 的版本检查兼容，可以合并后重新验证；若两者改同一条件，先人工裁决。若某文件是依赖安装生成的垃圾，也不能因为它“存在”就交 PR。工作区事实与改动归属是两道题；Git 告诉我们差异，不替我们判断业务归属。

Anthropic 的[Managed Agents 架构文章](https://www.anthropic.com/engineering/managed-agents)把会话、Harness 和沙箱分为可独立失败的部分，解释沙箱丢失不等于会话必然丢失，也不保证沙箱里的文件天然幸存。LangGraph 的[持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)说明检查点保存图线程状态，内存后端在进程重启后会丢。无论采用哪套产品，团队都要知道“检查点在哪、文件在哪、外部 PR 在哪”。会话能恢复不是工作区快照自动完整，更不是外部动作回滚。

## 三本账对不齐时，谁说了算

小陈把恢复桌面分三块。会话账：任务目标、上一次工具请求、检查点位置、未决问题；工作区账：仓库提交、暂存与未提交 diff、测试产物和进程状态；外部账：PR、issue 更新、CI run、通知或部署回执。三块用任务键、工作区版本和动作键关联。检查点若写“测试通过”，但工作区已变化，测试只能证明旧版本；PR 若已创建，摘要说“准备创建”也不能让系统再发一次。

**领导：**冲突时就信磁盘，磁盘是真的。

**小陈：**磁盘是真实内容，但不告诉我们它来自谁、是否被验证。测试报告也是真实文件，却可能属于前一个提交；PR 是真实远端对象，却可能是同事手动创建的另一项修复。每本账负责自己的字段：任务意图看任务卡，文件内容看工作区，测试结论看执行记录，外部动作看远端回执。字段互相矛盾时标“待核实”，不简单选最顺眼的一本。

## 在四个位置断电，后果各不一样

第一处是读文件时断电。模型可能只拿到文件前半段，工具结果已写入对话，但完整性标记还没到。恢复后重新读取该文件或校验哈希，不能拿半份源码生成补丁。第二处是写文件时断电。一个补丁可能只应用到部分文件，工作区处于语法错误状态；先保存 diff 与文件版本，再决定补齐或回滚。若用原子写入工具会减少半写风险，但多文件改动仍可能只完成一部分，不能假设“一次调用”就是事务。

第三处是跑测试时断电。进程可能被杀，日志只写到第 18 个用例；“前 18 个没失败”不是整个测试集通过。恢复时检查进程是否仍在、报告是否有完整结束标记和退出码；若没有，记录“测试结果未定”，在当前工作区版本上重跑。第四处是开 PR 时断电。GitHub 可能已创建而本地没拿到回执，要按 H07 的动作键查远端；若查到 PR，补账并核对 head 提交，不能再开一张。

**领导：**四种都重跑不就省判断？

**小陈：**读文件重读通常可行，改文件盲重可能重复打补丁，测试重跑要确认环境清理，PR 盲重会重复创建。恢复动作由副作用性质决定。最重要的是不要把“工具调用没有成功返回”统一翻译成“什么都没发生”。跨文件与跨系统的动作在断电瞬间可能停在任何中间态，恢复器必须先识别现状。

若 Agent 用的是独立工作区，断电后也要确认那份工作区是否还在、挂载是否是同一卷、是否被自动清理。若环境重建成空目录，不能把旧检查点的文件引用当成仍然存在；要从上次可验证提交恢复，再决定如何处理未提交改动。若未提交 diff 有快照，就在新隔离环境里应用并重验；若没有，诚实标记这一段可能丢失，别从聊天摘要凭空“复原”。

## 工作区恢复要分 HEAD、暂存和未暂存三层

**领导：**Git status 给我一串字母，怎么判断哪段能保留？

**小陈：**先看 HEAD 指向哪个提交，再看暂存区与 HEAD 的差异，最后看工作区与暂存区的差异；未跟踪文件也单列。三层可能代表不同的执行阶段。Agent 也许已经把验证码修复暂存，却在测试文件里留下未暂存的新断言；同事又新增一个未跟踪脚本用来抢修。若恢复器只打包 <code>git diff</code>，可能漏掉暂存或未跟踪内容；若直接 <code>git add .</code>，又可能把密钥、测试产物和同事脚本全塞进 PR。恢复先列清单与来源，不做一键提交。

对已提交部分，小陈看提交哈希与父提交关系：是否基于任务开始的基线，是否混入其他分支，是否已有 PR 指向这个提交。对暂存与未暂存部分，按路径和内容指纹与任务工具日志对照；匹配上轮 Agent 写入事件的，标“任务待验证改动”；匹配同事说明但无提交的，标“他人改动”；无法匹配的保留为未知。标记只是恢复判断，不等于自动批准合并。若基线已经前进，恢复时还需重放最新主线的相关测试，防止旧修复与新代码语义冲突。

**领导：**既然原工作区很乱，新建一份干净的然后挑文件复制，不是更快？

**小陈：**可以在完成快照和归属后新建隔离工作区，但不能在原现场尚未保存时先清理。复制文件也会丢 Git 的上下文：一个测试是否被删、文件权限是否改、子模块版本是否变，都要比较 diff 才能知道。正确做法是保留原现场只读，从已验证提交建立新工作区，按已确认的补丁顺序应用，再跑基础测试。失败的补丁留在证据库，不把未知文件硬塞进新环境。新工作区地址与原工作区地址都登记，防止后续 Agent 接错目录。

原工作区能保留多久也要定。线上任务可能含客户资料或临时令牌，不能为了排查永久存整份磁盘镜像；但在未解决冲突前立即清理又会丢证据。小陈让恢复记录标保留期限、访问角色和脱敏范围：代码 diff 与测试报告可按研发审计期留，敏感日志在受控存储按更严格期限，临时凭据立即撤销。恢复能力与数据治理是同一项运维工作，不是两个互不相关的团队口号。

## 测试报告也有“半成品”，不能只看文件是否存在

断电前测试框架可能已经创建 XML 或 JSON 报告，但尚未写结尾。若解析器把“读到 18 个通过用例、没有失败节点”当成全部通过，恢复器就会把一份半成品报告当绿色。小陈要求测试记录同时有进程终止事件、退出码、预期测试数或完整性标记，以及报告对应的代码版本。缺任何一项，状态是“结果未定”。报告文件存在只证明写入开始过，不证明测试结束。

**领导：**测试进程如果还活着呢？

**小陈：**确认它属于原任务、运行的代码快照、命令和环境仍然有效，再选择等待或取消。机器断电通常进程已没了，但容器连接丢失时，远端测试可能继续运行。恢复器不能看不到终端输出就另起一轮同样的集成测试，否则两个进程同时写同一份报告或测试数据库，结果更乱。可查任务 ID 与进程 ID 的执行器先查询状态；查询失败标未知，超过时限后由受控清理流程处理，不能把“无响应”当“已结束”。

重跑前也要清理或隔离上轮残留。验证码端到端测试若向测试短信队列写了两条消息，再跑一次可能读取旧消息而假绿；数据库迁移测试可能已经执行到一半。每个测试套件定义是否可重复、测试数据命名空间和清理方法。只读单测重跑通常简单，集成测试要先确认环境状态。小陈不想为了证明代码修好，先把测试环境搞成一片幻觉。

## 外部 PR 与本地提交之间还有一条版本线

小陈查到 PR #71 已存在，但它的 head 提交是 <code>abc124</code>；断电前未提交的修复在工作区里，PR 并不包含它。若只看“PR 已创建”，会以为工作已交付；若只看“工作区有修复”，又可能重复创建 PR。恢复单同时写 PR ID、远端 head、当前本地 HEAD 和未提交 diff。只有当 PR 指向的代码包含已验证修复，并且 CI 对应那个提交，才可进入正式评审。

**领导：**可以把未提交补丁推到 #71 的分支吗？

**小陈：**先确认那条分支的现状和所有者。评审人可能在断电期间追加建议，同事可能推了修复；盲推会覆盖远端变化。读取远端 head、比较共同祖先和本地 diff，冲突交人或在新工作区合并。推送后测试证据必须按新提交重跑，PR 动作台账补版本变化。PR 是活对象，不是一次创建后永远静止的收据。

另一个场景更危险：外部 PR 已合并，而本地检查点仍写“待创建”。如果 Agent 按旧摘要重新开 PR，可能把已上线的修复又提一次，甚至覆盖后续热修。恢复时查询 issue 与 PR 的状态、合并提交和目标分支；已合并就转结案核查，而非再执行创建。若 PR 关闭未合并，要看关闭原因和替代 PR，不按“找不到开放 PR”推断从未创建。对账范围要包含打开、关闭和已合并对象。

## 恢复器自身要有“只读阶段”，别一启动就写

小陈把自动恢复分为观察、分类、执行三段。观察阶段只读取检查点、任务卡、Git 状态、测试报告与远端回执，生成一份差异表；分类阶段按每个字段标一致、缺失、版本过期、归属未知或相互冲突；执行阶段才做重读、重跑、补账、合并或停机。若观察阶段发现任务已被用户取消，直接停止，后面不再运行模型。若发现工作区由人修改且归属未知，先保全再交人；不能让恢复器为了“自动化覆盖率”默认选最新文件。

**领导：**为什么不能让 Agent 自己看看然后决定？

**小陈：**它可以辅助解释差异，但机械事实和高风险动作要由执行器与策略判定。Agent 看见两份 diff，能说明可能的语义冲突；它不能凭对话摘要决定删掉同事改动。恢复计划应列每一步的前置条件与预期结果，例如“当前 head 必须仍为 abc124，才可在测试仓库补 PR 描述”；条件不满足就停止重算。这样恢复过程中若有人继续修改远端对象，也不会用旧观察结果执行新动作。

恢复也要防两个进程同时接管同一任务。一个自动恢复 Worker 与一个人工点击的“继续”可能同时读取相同检查点，分别重跑测试、更新 PR。任务键上的租约或版本比较保证同一时刻只有一个执行者推进；租约过期后的新执行者仍先对账，不能假设旧执行者什么都没做。H07 的 PR 去重只是一个外部动作实例，工作区恢复本身也需要避免双写。并发控制失败时，系统应宁可停在待核实，也不能让两个恢复器互相覆盖检查结果。

恢复完成后，更新交接单时写“核实到哪里”：工作区版本、测试证据、PR 状态、他人改动的处理、仍未知的部分。若工作区重建成功但旧客户端测试尚未跑，状态只能是待验证；若 PR 存在但 head 不一致，状态是交付冲突。恢复结论比“服务已重启”更重要，因为值班人真正关心的是下一步是否可以安全继续。

## 同事的修改不能成为 Agent 恢复时的擦车布

事故当晚同事为线上故障紧急改了 <code>LoginController</code>，没有提交。Agent 的旧补丁也想改附近代码。小陈先冻结工作区并复制只读快照，记文件哈希和操作者时间线；再用 Git diff 把已提交基线、Agent 改动、同事改动分层。若同事改动可以独立提交，就让负责人先收成单独提交；若混在同一个文件里，请双方确认各段意图，必要时人工拆分。恢复程序绝不能执行“重置到检查点”覆盖掉人手修改，检查点不是删除别人劳动的授权。

**领导：**怎么知道哪段是同事改的？Git 又不记录未提交行的作者。

**小陈：**有时确实不知道。可结合工具调用记录、编辑器保存日志、文件时间、运行器写入事件与同事说明，但证据不够就标“来源未知”，交人裁决。不要假装有行级来源魔法。系统设计上可减少这种情况：每任务独立工作区，不让同事和 Agent 共用一份目录；人需要抢修时在另一个分支做，再通过集成门合并。若历史事故已发生，恢复器的责任是保全未知，而不是快速给未知编一个作者。

恢复后的第一轮测试必须绑定合并后的新版本。A 提交的测试绿、同事补丁单独也绿，不代表两者组合正确。小陈先跑基础构建、乱序用例和旧客户端回归；若任一失败，任务停在待验证，定位是哪条变更引入，不把两份绿色相加。PR 若已存在但 head 是旧版本，更新 PR 后也要等新 CI 结果。恢复不是让进度条跳回断点，而是让每个已验证结论重新对准当前代码。

## 演练要模拟“断在半句”，不是优雅退出

小陈在测试环境做四次故障注入：读文件只返回半块、补丁写两文件后断电、测试跑到中间杀进程、GitHub 创建 PR 成功但响应丢失。每次恢复，先看是否保存现场，再看是否错误标完成，最后看能否安全继续。验收标准写得很硬：人手未提交改动不丢；无完整退出码的测试不报通过；同一任务至多一张有效 PR；无法确认的状态保持待核实，不自动强行推进。

**领导：**这样恢复会慢一点。

**小陈：**比“快速覆盖同事改动、重复开 PR、上线半份补丁”便宜。正常情况下，对账只读几处状态，很快就能继续；只有事实冲突才停。停在哪里、缺哪个证据、谁能决定都写清。长任务系统真正的恢复能力，不是断电后一秒钟屏幕又开始滚字，而是滚出来的每一步仍建立在真实工作区上。

演练结束，小陈还量两组数。第一组是恢复正确性：人手改动丢失次数、未完成测试误报次数、重复 PR 次数和来源未知却自动覆盖次数，目标都是零。第二组是恢复效率：从 Worker 重启到完成只读对账的时间、需要人工裁决的比例、恢复后重跑测试的成本。若正确性没过，速度快没有意义；若正确性过了但每张任务都要人工考古，就继续改工作区隔离和动作台账。恢复系统要靠重复演练变好，不能只在事故当晚临时开会。

**领导：**这次机器断电，最后到底从哪接上？

**小陈：**从已验证的提交和同事的防护补丁分别建证据，确认两者能合并后生成新工作区版本；原来跑到一半的测试作废，在新版本上重跑；PR #71 已存在，更新同一张并等新 CI。若同事那行代码的意图还没问清，就先停在待核实，别让 Agent 用“继续”两个字把它当无关改动抹掉。领导收到的是这张恢复单，不是一个重新转起来的进度圈。

小陈把恢复单也写入任务历史：原工作区快照的保留期限、新工作区基线、每项改动归属、重新验证的命令与结果、PR head 从哪个提交变到哪个提交。下次有人问“断电后到底改了什么”，不用把两段聊天记录接起来猜。若后来发现恢复判断错了，也能沿着这份记录回到当时的文件和测试版本，判断需要撤回哪一笔变更。

这份记录还要有负责人签收；系统能完成只读对账，涉及人手未知改动时仍要由知道业务背景的人确认。自动恢复停在正确的位置，本身就是一种成功。
