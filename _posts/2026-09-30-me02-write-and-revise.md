**领导：**林女士昨天说先邮件，今天说周末有急事可以电话。助手记完以后回答“客户不接受电话，但可以优先电话”。这记忆比我们开会纪要还会打架。

**小陈：**因为它把两句话都当永久事实。第二句有时间和条件，不能直接覆盖第一句，也不能毫无解释地追加。写入记忆要先弄清楚谁在说什么、什么时候适用、和旧值是什么关系。

本篇继续使用**教学虚构**的星河制造续约助手。林女士为当前联系人，偏好最初是工作沟通先邮件；随后出现临时例外、长期改口、同事转述和纠错。我们把这些不同事件放进同一套写入流程。字段、时间与数据库片段属于教学设计，实际权限与来源由应用验证。

## 一、说过一句话，不等于形成一条事实

**领导：**大模型把聊天总结一下，存起来不就行了？

**小陈：**先看这四句话：“我以后先电话”“她以前先电话”“如果着急就先电话”“你刚才说我先电话，其实我没有”。相似度可能很高，主体、时间、条件和真假完全不同。总结器只提取“先电话”，就会同时制造四种错误。

抽取需要保留说话者、被描述主体、内容类型、适用条件和来源。客户自述、销售转述、助手推测和工具结果不能同权。当前用户说“客户想八五折”，描述的是客户诉求，不是已批准价格；助手说“她大概比较急”，是分析，不是永久性格。写入层先判断这些地位，再决定能进入哪个区域。

一个候选可以很明确地表达未知：已找到原话，但联系人身份待确认；主体已确认，但是否长期适用待确认；内容属于商业批准，缺权威记录。把未知保留成状态，比让模型输出一个很高的自报置信度靠谱。应用不能仅因结构完整就把候选变成有效记忆，也不能把已存在的错误记忆当确认新候选的唯一依据。

原始来源最好先形成稳定记录。对话消息有消息 ID、说话者与时间，工具结果有来源对象、版本和观测时间。抽取之后保留定位，不让长期记忆成为找不到原话的孤儿。源消息撤回或修正时，依赖它的候选和有效记忆才能被找到并处理。

## 二、写入流水线：候选与正式发布分开

一条可维护流程包括接收事件、抽取候选、检查归属和类型、验证来源与范围、查找已有相关记忆、判断关系、提交修订、发布索引。每一步都有可解释的结果。拒绝不等于故障，例如没有长期用途的即时情绪可以记录为不提取；来源不足的业务判断进入待验证，而不是为追求写入成功率强行保存。

**领导：**查已有记忆，会不会把模型带偏？

**小陈：**旧记忆用于比较和发现冲突，不用于给新信息盖章。比较时要同时带旧值的来源、范围和时间，告诉抽取器它可能已失效。模型可以建议新增、修订、补条件、待确认或不写，确定性代码验证这些操作是否在允许类型与权限内。

候选区与有效区使用不同状态。研究 Agent提出的客户背景先进入候选，业务服务确认后再发布；明确的个人表达偏好可以按既定规则快速验证；系统权限和公司政策不得通过普通聊天改写。不同类型有不同门槛，避免一个通用“记忆管理 Agent”同时取得修改所有东西的权限。

我们可以让抽取输出严格结构，并要求每条候选带原文片段的定位与解释。格式校验检查字段，归属校验核对联系人，业务验证核对所需权威来源；三者分别记录。模型“建议删除旧记忆”也只是建议，删除服务要确认范围、原因与授权，不能让恶意网页通过一段文字清空团队知识。

## 三、归属错了，后面的更新做得再漂亮也没用

销售说“王经理让我先发邮件”，王经理可能是林女士的同事，也可能是销售自己的主管。这句话不能直接更新林女士的偏好。名字只是一条线索，系统应在当前任务的合法联系人集合里解析，必要时明确追问。多个同名对象或来源不足时，保持待确认。

**领导：**我们把所有客户偏好记在公司下面，省得解析联系人。

**小陈：**会把一个人的习惯变成整个公司的规则。公司级联系流程可以共享，个人偏好通常归联系人；当前谈判要求归商机或合同；本次紧急沟通例外归任务。记忆键由主体与属性组成，条件和用途补足适用范围，而不是把全部句子塞到一个`customer_profile`字段。

写入者身份也需要保存。客户自述可以成为偏好来源，销售录入是业务代理来源，工具返回可验证状态。保存身份有助于纠错和冲突处理，不意味着该身份永远有权改动。提交时验证当前授权，特别是跨团队后台任务，不能凭旧消息里的用户 ID直接写当前客户的共享记录。

处理代词时同样保留证据。“她现在换了邮箱”要联系上文确认她是谁；“我们不再用短信”还要判断“我们”代表部门、公司还是这次会议参与者。抽取器可以提出主体候选，应用根据业务关系验证。错归属的长期记忆往往比漏记更危险，因为检索时它会显得结构规范、来源完整。

## 四、先分类：新增、替代、例外、纠错与撤回

新增表示以前没有同范围同属性的有效记录。替代表示新的有效值取代旧值，例如林女士明确说“之后工作联系改成先电话”。例外表示在某个条件下适用不同动作，例如“本周末紧急事可以电话”。纠错表示旧记录本来就不成立，例如助手误记了同事的话。撤回表示不应继续保存或使用某项信息。不能把后四种都做成新增。

**领导：**最后一句更新的，直接覆盖不就好了？

**小陈：**新到达不一定新发生。昨天会议纪要今天导入，但今天早上的客户表达才是当前偏好。要看有效时间、来源权威性与适用条件。一个晚导入的旧事件不能覆盖当前值；一个新推测也不能覆盖已确认事实。

同样，两种值可能并不矛盾。“工作沟通先邮件”和“周末紧急事可电话”可以同时成立，只要条件明确。读取时根据当前日期、紧急性和用途选适用规则；条件未知时保留默认偏好并请求确认，不把例外推广成所有场景的优先路径。记忆系统的价值在这里体现：不是只维护一条字符串，而是维护有边界的事实。

纠错与替代也不同。替代保留“以前确实有效”的历史；纠错标记旧结论不成立，后续历史问答不应仍当作事实引用。删掉旧值虽然暂时减少冲突，却会失去来源与修正原因。根据保留策略保存必要审计信息，使系统能回答为什么改变，而非默默换一段客户画像。

## 五、两套时间，才分得清“以前是什么”和“何时知道的”

有效时间描述事实在业务世界里适用的区间，记录时间描述系统何时接收到或写入它。九月二十九日客户改偏好，九月三十日销售补录；有效开始可以是二十九日，记录时间是三十日。只有创建时间，系统无法可靠回答二十九日晚上应采用哪种沟通方式。

**领导：**我们只是客服，不用搞历史数据库吧？

**小陈：**至少把两种时间分开。起步可以用`valid_from`、`valid_to`、`recorded_at`与来源时间。复杂历史查询需要更完整的双时间建模，但不能连原始时间都没留。数据越迟到、修正越多，只有“最后更新”越容易误导。

有效区间常用左闭右开表达：新值从某时刻开始，旧值结束在同一时刻，避免边界同时有效。来源只有日期没有时间时，不应假装精确到秒；记录时间精度与时区，再按业务规则处理边界不确定。只知道“下个月起”就保留这种范围，必要时确认，不能让模型随手挑一个时间当真实生效点。

删除与失效时间也分开。过期表示不参与当前决策，历史仍可按权限使用；撤回可能要求停止更多用途并清理派生副本；纠错使旧主张不再成立。状态与时间共同决定读取，索引只负责召回候选，不能靠创建时间排序替代这些判断。

## 六、并发更新：两位销售不能各自盖一个“最新版”

两位销售同时读到偏好第六版。甲根据客户确认改成先电话，乙补录旧会议纪要仍写先邮件。如果两次都直接覆盖，结果由谁提交得晚决定。我们用修订号进行条件更新：写入方声明自己基于哪版，只有当前版仍一致才提交，否则重新读取并判断冲突。

下面是**条件更新 SQL 示意**，实际应与来源、历史版本、事件去重在同一事务中完成：

```sql
UPDATE memory_current
SET value = :new_value,
    revision = revision + 1,
    source_ref = :source_ref,
    valid_from = :valid_from
WHERE tenant_id = :tenant_id
  AND subject_id = :subject_id
  AND predicate = :predicate
  AND revision = :expected_revision;
```

受影响行数为一表示该条件更新成立；零表示记录不存在或版本已经变化，不能悄悄当成功。重新读当前来源与区间，决定补历史、合并条件还是请求确认。重试不应简单改`expected_revision`后盲写旧值，那只是把有锁的覆盖变成绕一圈再覆盖。

事务边界包括正式记忆、历史修订、已处理事件和待索引事件。先提交正式值，再以可靠事件发布索引；如果索引失败，当前记录仍可按主键读取，并显示索引进度。数据库与向量服务通常不能共享一个简单本地事务，应用要用版本与重试协调，不能声称调用两个写接口就已原子完成。

## 七、去重分两层，别把“重复内容”与“重复事件”混成一件事

事件去重避免队列或请求重复执行同一写入。用消息或业务事件 ID标识逻辑来源，重复请求保持同一 ID，并核对输入内容哈希；同一 ID带不同正文应拒绝或隔离，而不是当作正常重试。事件、结果与记忆修订的关系持久保存，故障恢复后仍能判断是否已提交。

语义去重避免相同事实被重复提取。“先发邮件”和“工作联系邮件优先”可能表达同一偏好，可以归为同一属性与值，但两条来源仍有价值。它们不能因为相似就把不同联系人或不同条件合并。反过来，“不要电话”和“可以电话”在向量空间可能接近，绝不能当重复。精确归属与条件先于语义相似。

**领导：**多出现几次，就提高置信度。

**小陈：**先看是不是独立来源。四个 Agent复述同一条消息，仍然只有一条消息；同一销售复制三次纪要，不是三次客户确认。来源链去重后才讨论支持程度。模型生成的频次不应提高事实地位，否则系统会把自己的错误反复抄写成共识。

大量个人资料也不宜揉成不断增长的单一段落。每次修改整段画像容易误删别的属性，出处和有效期难以分别维护。关键属性按结构记录，事件按集合保留，长背景用带引用的摘要；摘要重建时从当前有效记录生成，而不是在上一版摘要上无限增补。

## 八、同步记住与后台整理，各有适合的责任

明确偏好通常很短，验证与写入可以在交互路径上完成，让用户下一轮立即看到。长会话的经验整理可以后台做，减少响应等待；后台工作要记录基于哪个事件范围与当前记忆版本，提交前再验证。两个路径遵守同一写入协议，不能让后台绕过已发生的更正。

**领导：**后台在处理，我先回复“已经记住”可以吗？

**小陈：**如果还没持久提交，应说已收到或正在保存。数据库已写但索引未更新时，可以通过主键读或已验证的新修订覆盖近期召回，保证同一用户马上改口后不被旧索引拉回去。不能把未验证候选当临时补丁直接注入模型，省掉最后一道事实门。

异步索引事件携带记忆 ID与修订。索引消费者读取最新有效记录，旧事件不回写旧内容；删除标记与撤销状态优先阻止召回。查询向量结果后重新核对主记录的状态与版本，拒绝失效候选。缓存键包含有效修订或失效代次，使“更新数据库、却还读旧缓存”成为能检查的状态。

后台整理不能自动修改系统最高级指令。它可以提出经过证据支持的流程建议，进入受控发布；个人写作偏好可以进入相应用户范围。权限、价格审批和工具允许名单有自己的配置来源，不能因为一份总结写得很像规则，就被发布到全体 Agent的系统提示里。

## 九、当前 Mem0 的自动抽取，别按旧印象理解

[Mem0 当前工作原理文档](https://docs.mem0.ai/core-concepts/how-it-works)描述抽取与检索两阶段，并明确自动抽取路径为 additive：新增事实不必默默重写旧事实，需要应用用明确 update 或 delete 修正。这个边界特别适合本篇的改口案例。不能只不断调用`add`，再期待检索器永远自己判断哪一句最新。

[Add 文档](https://docs.mem0.ai/core-concepts/memory-operations/add)还区分推断抽取与原样存储，以及范围与过期参数。具体选项要按 Platform、OSS和 SDK版本核对；产品标识筛选不替代应用身份认证，过期不可见也不必等同于所有副本物理删除。调用时把业务语义明确写进服务层，不让不同环境的默认行为替我们决定。

**领导：**那还需要记忆库做什么？

**小陈：**它可以承担抽取、搜索、元数据与部分存储管理，省掉重复工程。我们仍然负责来源地位、对象授权、改口解释与版本策略。工具能帮忙，不意味着业务含义会自动正确。用产品时把边界写进测试，而不是凭宣传中的“智能更新”四个字通过验收。

## 十、一次故障从头走完：写成功了，回复却丢了

林女士明确把默认偏好改成电话，服务在事务里提交第七版并登记事件。随后网络断开，客户端没有收到成功回复，于是重发同一消息。若应用只靠进程内的去重集合，重启后会再次创建第八版；若登记事件在另一次提交里，记忆提交之后崩溃也会留下空档。事件结果与修订一起持久化，重试才能返回原来的第七版。

**领导：**这次没多写，就算恢复好了？

**小陈：**还要看读。向量索引可能仍是第六版邮件，近期缓存也可能没清。读取先核对主记录修订，拒绝旧版本；已知属性直接查当前表，向量故障不影响这次确定读取。相应索引任务可以稍后重跑，用户下一轮不能因为后台慢半拍继续收到旧建议。这叫把已提交的改口实际带到后续使用里。

如果索引消费者先处理第七版，再收到第六版的迟到事件，它应以逻辑记忆 ID重新读取当前值，或用版本条件阻止倒退。把队列事件正文无条件写进索引，会让消息乱序变成状态回滚。批量重建也要标记读取的快照范围，并在切换前追上增量变化，不能把昨晚的全量副本重新宣布为当前事实。

还有一种故障更隐蔽：客户撤回了源消息，但总结任务已经排队。撤回服务先使对应来源不能继续发布，再查派生记录；后台提交必须核对来源当前状态，拒绝依赖已撤回消息的新修订。不能只删有效表里已有的记录，任由延迟任务几分钟后再提取一次。写入正确性包括当下修改，也包括堵住后来的错误复活。

## 十一、边界冲突怎么给业务人员解释

同一个属性出现相互矛盾的可靠来源时，系统应保留双方来源并标记待确认。销售转述“先电话”，客户本人后来写“先邮件”，通常按明确的当前客户表达处理；若两条都来自客户，却缺少生效时点，不能假装已经解出时序。界面给出具体待确认项，而不是用“记忆冲突”四个字让业务人员猜数据库发生了什么。

**领导：**每次都问客户会不会烦？

**小陈：**先使用已有条件能解掉的冲突。不同用途、不同联系人、不同时间段，可以自动分开；真正影响当前联系而无法判断的才确认。问法也明确：“工作沟通目前默认先邮件，本周末紧急事项可电话，这样对吗？”确认对应一个结构修订，不能确认完又只存成第三段自然语言。

人工调整走相同写入协议。管理员能看到候选原话、归属与旧修订，选择修订或纠错并写明依据；提交时依然检查版本，防止审核期间客户已经再次改口。运维权限不等于业务事实权威，管理员不能凭方便把未知价格改成已批准。这个入口让记忆能修好，同时让每次修理留下可以解释的路径。

## 十二、这条流水线的完整验收

| 输入变化 | 预期处理 | 需要留下的记录 |
| --- | --- | --- |
| 同一消息重复投递 | 不新增修订 | 事件 ID与原结果 |
| 客户明确长期改口 | 新值生效，旧值停止当前使用 | 来源、有效区间、修订 |
| 本周末的紧急例外 | 单独条件化 | 条件与截止时间 |
| 销售转述同事偏好 | 归正确主体或待确认 | 归属依据 |
| 旧纪要迟到 | 补历史，不覆盖当前 | 两套时间 |
| 后台旧版本提交 | 拒绝或重新比较 | 预期版本与冲突原因 |

验收时直接追踪当前表、历史表、索引与本轮上下文。只看管理台多了一行，是写入可见性测试，不是事实更新成功。尤其在改口后的下一轮，确认模型收到的是新的有效值，并知道临时例外与默认偏好的区别；否则数据库正确、回答仍错，问题可能在检索与组装。

**领导：**现在林女士说周末急事可电话，最终记成什么？

**小陈：**工作沟通默认邮件保留，新增仅限本周末紧急事项的电话例外，带来源和期限；如果她随后明确“以后都先电话”，再形成替代修订。助手不会同时坚持两个没有条件的永久偏好，也不会把一次例外宣布成公司政策。

下一篇把正式记忆拿出来用：同一句“该怎么联系客户”，怎样先限定主体与时间，再做精确和语义检索，最后只把真正有用的记忆装进上下文。
