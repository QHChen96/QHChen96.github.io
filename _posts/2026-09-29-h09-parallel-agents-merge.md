**领导：**一个 Agent 修 Bug 要两小时，三个一起不就四十分钟？我已经开了三个：一个改验证码、一个改缓存、一个“顺手优化登录”。

**小陈：**它们现在都在改 <code>LoginService</code>。第一个加版本检查，第二个把状态换回单值缓存，第三个重命名接口。三个人同时握方向盘，车确实动得很快，方向不一定是公司。

**领导：**Git 会提示冲突，解决一下就好。

**小陈：**Git 只会告诉我们哪些文本改动撞了；更可怕的是它没提示冲突，却把彼此的业务假设撞碎了。并行不是按 Agent 数量算速度，要按任务依赖、文件热点、接口契约和最后谁集成来设计。

文中的仓库、任务与合并事故为教学虚构。Git 工作区和 GitHub 合并规则等产品事实，参考文内官方资料。

## 事故现场：文本能合并，行为却不能上线

上午九点，领导给三条任务发同一份基线提交。Agent A 负责验证码乱序，改 <code>LoginService</code> 的状态更新；Agent B 负责登录性能，发现多次读缓存很慢，改同一服务的读取路径；Agent C 负责错误提示，重命名服务返回值并调整调用方。十一点三条分支都说“本地测试通过”。小陈把 A、B、C 依次合并，Git 只在一个 import 行提示冲突，修完之后构建居然也过了。上线前的端到端测试却发现：B 的缓存优化让 A 的版本检查绕过去了；C 的新返回值又让旧客户端把“验证码过期”显示成“账号异常”。

**领导：**不是说 Git 冲突少吗？

**小陈：**文本冲突少，不代表语义冲突少。A 和 B 改不同函数，Git 当然能自动拼起来；它不知道“缓存读取必须保留请求版本”是二者共同约束。A 的单测只测它的函数，B 的单测只测缓存速度，C 的快照只测新页面。各自绿灯不能推出合并后行为正确。并行的真正验收必须在集成版本上跑共同场景。

GitHub 的[合并冲突说明](https://docs.github.com/en/pull-requests/reference/merge-conflicts)解释文本冲突何时阻塞 PR，Git 的[worktree 文档](https://git-scm.com/docs/git-worktree)说明一个仓库可以关联多个独立工作树。工作树解决的是文件操作互不覆盖，不能自动保证三条分支的业务假设兼容。Anthropic 的[并行 Agent 编译器案例](https://www.anthropic.com/engineering/building-c-compiler)也提到任务锁与频繁合并冲突；那是特定工程的经验，不是“多 Agent 默认更快”的普遍定律。

## 并行之前先画依赖，而不是先数座位

小陈把三张任务卡摊开。验证码乱序与缓存性能都依赖同一状态模型，必须先确定“状态携带请求版本”这个接口契约；在契约没定前同时实现，几乎必撞。错误提示任务如果只改展示层，并消费稳定的错误码，可以与验证码实现并行；若它要改服务返回结构，也得等待接口定义。小陈把“探索根因”“写测试”“实现修复”“集成验证”按依赖排成图，找真正可以同时进行的部分。

**领导：**那三个 Agent 现在应该怎么分？

**小陈：**A 负责定义验证码状态契约与修复代码；B 先只做性能测量和方案对照，不修改共享服务，等 A 的接口定下来再实现缓存优化；C 可在独立工作区准备展示层测试，但涉及返回码变更时先提交接口提案。三个都能产出有价值的东西，不一定都要同时写同一份生产代码。并行探索往往比并行改热点文件更稳。

每张并行卡要写清输入基线、目标、允许读写范围、禁止改动的共享接口、交付形式、验收命令、依赖和集成人。若任务开始后发现必须跨界，Agent 提出变更请求；调度者可把两块串行化、切出共同接口块，或交同一个负责人整合。不能让它们分别在自己分支里默默扩大范围，最后扔给一个没有上下文的合并人“解决冲突”。

## 文件归属不是“谁先改谁占坑”

小陈给并行任务做一张热点表：<code>LoginService</code> 属于共享核心，A 在本轮拥有写入权；B 可读并提交性能测量，不能直接改；展示层文件由 C 写；测试工具函数由集成人维护。归属不是永久产权，任务阶段结束就释放。若 B 找到必须修改核心服务的性能瓶颈，它把建议、基准测试与预期接口变化交给集成人，A 或下一轮 B 在新基线上实现。这样并行仍能贡献发现，写入冲突不靠抢。

**领导：**给每个文件上锁，不就完了？

**小陈：**锁能防同时写，不能判断接口设计是否合理。A 锁住核心文件，B 在旁边新建一个绕过 A 的缓存适配器，仍可能破坏行为。归属表要同时写共享不变量：旧回包不得覆盖新请求、错误码对旧客户端保持兼容、性能测量不能改变验收语义。集成人和代码负责人对这些不变量负责，变更需明确决策。文件锁是实现手段，业务约束才决定什么能合并。

独立工作区仍然重要。Git worktree 或独立克隆能让每个执行单元有自己的 HEAD、未提交文件和测试环境，不把另一条任务的草稿误当自己改动。任务启动记基线提交，结束保存 diff、提交、测试证据与冲突状态。若多个 Agent 共用一个目录，连是谁写了哪行都说不清，后续对账几乎无从下手。隔离还要覆盖生成文件、依赖缓存和临时配置，否则代码目录分开了，测试却互相改同一份数据库，红绿结果照样混乱。

## 调度器怎样判断“可以并行”，别靠标题看起来不同

**领导：**验证码、性能、文案这三个标题完全不一样，调度器怎么知道它们会撞？

**小陈：**先用任务卡里的预期读写范围和依赖判断，再用实际探索结果修正。起步时 Agent 只读搜索，标出可能触碰的模块、关键接口和测试资源；调度器发现 A、B 都写 <code>LoginService</code>，直接排队或要求拆出共同契约。若 C 只写展示层，但依赖错误码接口，它可先写针对稳定错误码的测试，真正改接口的步骤等待决策。标题是自然语言标签，真实冲突在文件、数据模型、接口和环境资源里。

可以把依赖表示成有向图：A 的版本检查完成并验收后，B 的缓存优化才能进入实现；C 的展示层测试不依赖 A，可以先行，但 C 的服务返回值修改依赖接口评审。调度器每次只启动依赖已满足、资源不冲突的节点。若节点运行中发现新依赖，比如 A 需要改数据库 schema，立刻更新图并暂停受影响节点，不继续按照旧计划猛跑。图不是领导开会画完就永久正确，Agent 的探索会不断暴露实际边界。

并行还有环境冲突。两个任务都要在同一套预发数据库写测试数据，即使代码文件毫不重叠，也可能互相污染测试；两个任务同时跑大构建，机器资源争用会把正常测试变成超时；一个任务刷新共享缓存，另一个任务的性能基准瞬间失真。资源清单里除了路径，还应有数据库、队列、端口、模拟服务、限流配额。能隔离就各自隔离，不能隔离就预约或串行。否则团队会把基础设施互撞误认为模型能力不足。

**领导：**这些锁和依赖都做完，还会冲突吗？

**小陈：**会。任务最初的影响范围可能估错，公共接口可能被间接调用。目标是让冲突早发现、可裁决，而不是保证零冲突。运行中每次写文件、改 schema、调用外部测试环境都记录资源；越出任务卡的范围触发重新协调。集成人看见两条分支触碰同一不变量，就能在合并前安排接口会议，而不是等 CI 红了才考古。

## 三种冲突分别处理，别一把“自动合并”梭哈

第一种是文本冲突：两条分支改同一行，Git 明确停下。小陈让集成人读取两边 diff、任务目标和最新主线，再在一个受控集成分支解决；解决后运行双方相关测试。直接选择“保留当前”或“保留对方”只有在明确业务理由下才可以。冲突标记消失不等于语义恢复，尤其是条件判断与错误码分支，两边各加一行，随手删除一行就可能丢掉一个验收条件。

第二种是语义冲突：Git 自动合并，但共同不变量被破坏。A 增加版本字段，B 的缓存读取仍从旧字段取值；代码能编译，只有双端乱序才失败。解决靠跨任务验收场景和接口契约，不能靠 Git 冲突计数。集成人在每次叠加分支后运行一组共享不变量测试，并把失败归到引入的那一步；如果一次性合并三条再跑，定位成本更高。

第三种是流程冲突：两条分支都各自准备创建 PR、更新 issue 或发通知。代码上没冲突，外部世界却出现两个交付对象。H07 的动作键与外部副作用台账在这里也适用：同一逻辑交付指定一个集成人，分支 Agent 只交代码或报告，不各自对外宣布完成。若确需两张 PR，明确它们的先后依赖和 issue 映射，避免领导看到两个“已修复”就以为问题解决两遍。

**领导：**合并冲突发生后，让两个 Agent 自己谈好不行吗？

**小陈：**它们可以提出方案，但要有一个最终决策者。若 A 说“优先正确性”，B 说“优先性能”，这不是文字分歧，是产品和技术权衡；要拿用户影响、性能基准、兼容约束给负责人定。Agent 自己商量可能得出一份语气和谐的折中方案，实际把版本检查关掉一半。裁决的输入可自动整理，决定和风险承诺由被授权的人或明确的规则承担。

## 交接产物要能合并，不能只交一句“我做好了”

每个 Agent 收尾时交一张短卡。A 写：基线 <code>abc123</code>，提交 <code>a1</code>，改动两个文件，乱序测试先红后绿，注意 B 不得移除请求版本。B 写：在基线 <code>abc123</code> 上测得缓存读取慢，性能数据与环境参数在报告 R-2；没有生产代码改动，待 A 的接口合并后再复测。C 写：展示层新提示通过快照测试，旧客户端错误码未改；若服务返回结构变化，需要重新验。三张卡都指向原始 diff 或报告，不让集成人从自然语言猜代码状态。

**领导：**A 的测试绿了，C 的测试也绿了，为什么还要重测？

**小陈：**因为它们跑在不同提交与环境上。集成后代码组合变了，至少跑共同构建和跨模块场景。A 的“旧回包不能覆盖新请求”与 C 的“旧客户端提示正确”要在同一个集成版本上成立；B 的性能改动进来后，再跑乱序测试和性能基准，防止优化偷偷改语义。各分支的绿灯是各自局部证据，集成门需要新的共同证据。只看分支测试通过数，很容易把三张 100 分试卷拼成一份不及格的系统。

冲突裁决要有一个明确负责人，而不是三个 Agent 互相说服。文本冲突时，集成人看两边意图和测试，决定保留、合并或退回；语义冲突时，先核对用户行为和共享不变量，必要时请模块负责人定规则。不能让“最后合并的分支赢”，也不能让模型根据代码风格猜谁对。裁决记录写明影响范围、被否决的方案、需重跑的测试；下一轮 Agent 能看到，不会又把同一冲突带回来。

## 合并顺序也是一项设计决定

小陈没把 A、B、C 一股脑丢进主线。先让 A 的正确性修复在集成分支上过基线构建与乱序用例；再把 C 的展示层改动接进来，跑旧客户端与新客户端提示；最后才在新基线上实现 B 的性能优化，同时重跑乱序和性能基准。这样每一步新增的风险面清楚。若 B 加入后乱序测试变红，问题大概率在 B 与版本契约的结合处，不需要把三条任务全盘推翻。

**领导：**为什么性能优化最后做？

**小陈：**因为它是建立在正确状态模型上的优化。若先把错误的单值缓存做得更快，再改成版本化状态，前面的性能结果大半作废。依赖图决定顺序，不是小陈偏爱哪个 Agent。若客户投诉性能已经严重到必须抢先止血，可另开临时限流或降级任务，明确与正确性修复的关系和回滚条件，而不是让 B 的分支悄悄覆盖 A。优先级变动要公开，避免两个执行者各按旧目标冲刺。

合并后的测试也分层。每一步跑快的构建、定向单测与共享不变量测试，尽早发现语义碰撞；最终 PR 再跑完整回归、端到端、兼容与性能基准。性能数据必须注明基线版本、机器规格、数据量与重复次数，避免 B 用旧版本小数据的快结果证明新集成版本有收益。若性能结果不稳定，记录波动与原因，不因某一次最佳值就宣布成功。单分支证据保留作分析，但最终验收绑定集成提交。

代码评审也按集成版本看。评审人需要看三个来源的 diff、冲突解决提交和共享接口变化；如果只审 A、B、C 各自的 PR，集成时新增的手工修改没人看。集成人把解决冲突的理由写到 PR 描述，必要时请 CODEOWNERS 对关键模块复核。GitHub 的[CODEOWNERS 文档](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)说明可为文件指定代码所有者并请求评审，但具体要求仍得在仓库规则里配置。图上有“负责人”，远端也要真的能找到这个人。

## 故障演练：三条分支怎样不把彼此的成果擦掉

小陈安排一次合并演练：A 与 B 从同一基线改共享服务，C 改展示层；运行到一半人为让 A 提前合并，同时让 B 继续按旧基线写入。调度器应提示 B 的基线已旧，重新读取 A 的版本契约；B 的旧补丁若与新文件冲突，不能自动覆盖。若 B 已产生未提交修改，先保存 diff 与报告，换新基线后重新实现。C 因接口不变可以继续，若接口变了则停在待评审。演练验收是每份产物都有去向，合并版通过共享场景，没有谁的未提交改动被静默丢弃。

第二轮让三个 Agent 都提议修改同一测试文件。系统不能简单“测试文件谁改都行”，因为它恰好定义了验收边界。集成人核对是否有人删除断言、放宽条件或只保留自己的测试；必要时把测试变更单独作为接口契约的一部分评审。第三轮让一个 Agent 中途失败退出，其他两个不应因此失去各自工作区；但若后续依赖该 Agent 的接口结果，状态要受阻，不能凭摘要猜接口内容继续。并行系统不仅要快，也要在少一条线时仍能说明真实进度。

## 并行收益要算集成成本，别只看三个进度条

小陈给领导算一笔教学账：单 Agent 完成三块若需六小时，三个 Agent 同时跑各两小时，看起来省四小时；但如果接口冲突排查两小时、重新测试一小时、返工一小时，总耗时仍是四小时以上，还多占三份模型调用和审查时间。数字只是示意，真正应量的是交付周期、集成等待、冲突返工、合并后失败率与人工审查负担。并行最适合边界清楚、产物可组合的工作；在高度共享的热点模块里，先解决接口与责任归属比再加两个 Agent 值钱。

**领导：**那是不是永远不要多 Agent？

**小陈：**不是。让它们并行查不同资料、跑互不干扰的评测、写不同模块的测试，通常能获益；只是“同时改同一核心函数”不该成为默认模式。Anthropic 的[多 Agent 研究系统经验](https://www.anthropic.com/engineering/multi-agent-research-system)也指出研究任务往往比编码有更多真正可并行的部分。场景不同，收益不同。我们先用单任务边界和一个集成人把三条线管住，再用历史数据决定并行上限，不拿 Agent 数量当绩效。

最后小陈把验收写成两段。第一段检每个分支：独立工作区、明确文件归属、交接卡和分支测试；第二段检集成版本：共享不变量、构建、乱序、旧客户端、性能回归、PR 评审。若文本合并成功但端到端失败，状态仍是“集成未通过”；若一个分支超时，其他独立成果可保留，但不能把整体项目标完成。领导看到的不是三条同时冲刺的动画，而是一条能安全进入主线的路线。

为了证明并行值不值，小陈留一组对照任务：一组按单 Agent 顺序做，一组按三条清晰边界并行做。两组比较从接任务到可合并 PR 的实际时间、集成人工分钟数、冲突数、合并后回归失败数和模型调用成本。若并行组的代码产出快了，却在集成阶段花更多时间，下一次就缩小并行粒度；若探索和测试明显提前，而共享代码仍由一个人接入，就保留这种分工。决策依据是完整交付周期，不是三条任务进度条同时变绿的视觉效果。

**领导：**那我以后说“三个 Agent 一起上”，你会先问什么？

**小陈：**问它们各自交什么、碰不碰同一份状态、谁把结果接进主线、接完测哪几条共同规则。四个问题答得出来，就可以开工；答不出来，先拆任务。否则我们买到的只是三倍的“我这边没问题”。

这次事故后，团队把共享模块写入任务卡的风险字段。新任务涉及同一状态模型时，调度器会先提示接口归属和集成人；只有负责人确认可并行，才分配独立工作区。这个小小的停顿，省掉了之后两小时的冲突会。
