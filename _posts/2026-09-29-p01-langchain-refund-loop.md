**领导：**我看 LangChain 文档，一行 <code>create_agent(model=..., tools=...)</code> 就有 Agent。我们退款工具也接进去，明早能演示吧？

**小陈：**演示可以，真退款还差一整条业务闸门。现在的工具只收订单号和金额，模型一看到客户说“我很急”，就可能决定调用它；这行代码会帮我们把工具暴露给模型、跑调用循环，却不知道提问人是不是订单所有者、退款是否获批、支付系统会不会重复打款。框架能搭舞台，不替财务签字。

**领导：**这不是给工具描述写一句“谨慎退款”就好了？

**小陈：**描述帮助模型选工具，不是硬授权。我给您把一次运行逐步亮出来：模型读到什么、何时提出工具调用、谁执行工具、结果怎样回到模型、哪一步真正产生退款。我们在那一步前拦越权，在结果未知时查回执。正常只读查询继续走，真实退款先停在审批关口，明早演示也不靠“碰巧没点错”撑场面。

工单、订单和退款数字均为教学虚构。本文依据 LangChain 当前 Python 官方文档拆 <code>create_agent</code> 的公开机制，不假装知道具体模型内部如何推理；代码片段是解释边界的最小示意，实际业务接口需按企业制度实现与测试。

## 一行创建的不是“懂退款制度的员工”

LangChain 官方[Agents 文档](https://docs.langchain.com/oss/python/langchain/agents)把 Agent 描述为模型循环调用工具直到任务完成，<code>create_agent</code> 是可配置的 harness：模型、工具和 middleware 等包在一起。简单示例用模型标识和工具列表构造对象。小陈对领导说：“您看到的一行是入口，不是全部执行过程。”它不会凭这行代码自动连接订单系统、设退款限额、鉴权用户或处理支付回执；这些要由应用提供工具与规则。

小陈给一个只读工具：<code>lookup_order(order_id)</code> 返回经鉴权的订单状态、支付金额和配送信息。另一个危险工具 <code>request_refund(order_id, amount, reason, idempotency_key)</code> 不能只靠函数名判断能否执行；调用前还要知道用户身份、订单归属、可退余额、政策版本、审批结果、重复请求状态。模型可以提出“需要退款”，甚至把参数填完整，但最终执行器必须在受信任代码中逐项校验。工具参数 schema 能约束类型和必填项，不能证明业务授权：<code>amount=999</code> 即使是合法整数，也可能超出订单实付额。

**领导：**模型会不会自己先查订单，再决定退款？

**小陈：**可能，前提是只读查询工具被暴露、描述清楚，而且它选择调用。我们仍要防它跳过查询直接提退款。把必须满足的前置条件放在执行器：没有经过身份验证的订单事实与审批回执，不执行。模型不是唯一控制器，业务代码不能把“它似乎想得很周到”当凭据。只读工具也要按请求人权限查，不能给 Agent 一个后台超级账号，然后让模型在回答里自行决定哪些字段可说。

## 模型与工具往返一次，到底是谁动了钱

小陈把单次轨迹写成六步。用户说“0823 号订单没收到，退款 999 元”；应用带入经验证的用户 ID 与工单上下文；模型看到工具说明，可能先请求 <code>lookup_order</code>；运行器执行只读查询，把结果作为工具消息追加到状态；模型据此提出 <code>request_refund</code>；执行器在调用支付接口前做业务校验，得到成功、拒绝或未知结果，再把回执交回模型生成说明。钱只会在第五步的外部工具真正调用后变化，前面模型说“我已经退款”只是文本，没有支付回执。

**领导：**middleware 不就是中间件？把审核写进去就完了。

**小陈：**它是插入循环的合适位置，但要分层。LangChain 文档把 middleware 作为定制 harness 的基本方式，支持在模型调用前后、工具执行周边插入逻辑；文档也提供人工审批等预构件。我们可以在模型前缩小可见工具与上下文，在工具调用前做硬校验，调用后记录回执、限制重试、整理可对外说的话。但真正的支付鉴权最好仍在退款服务端再次执行，不能只相信 Agent 进程里有一层 middleware。万一将来另一个客户端绕开 Agent 调用退款 API，服务端也得守住钱。

工具契约要让模型知道“这个工具做什么、需要什么参数、可能返回哪些状态”，同时让程序知道“参数怎样校验、谁可用、是否有副作用”。小陈把 <code>lookup_order</code> 标为只读，返回字段按用户权限裁剪；把 <code>request_refund</code> 标为有外部副作用，必须带审批 ID 与幂等键。模型看到名称和描述有助于选择，但安全条件不靠描述文本执行。若退款工具 schema 允许自由文本金额，模型可能传“全部退款”；执行器必须将金额解析为最小货币单位，按订单实付与已退金额核对，拒绝负数、超额与币种不符。类型、业务、身份和审批是四道不同的门。

## 框架的 state 是运行账，业务真相还在外部系统

LangChain 文档介绍 AgentState 以消息历史为核心，也允许加自定义字段。小陈可以放 <code>request_id</code>、<code>user_id</code>、预算计数与当前工单 ID，方便本轮运行追踪；但“订单实付 999 元”“退款已成功”应来自订单和支付系统的当前事实。消息历史里有一句“客服说已退款”，不代表支付系统已登记。模型下一轮根据 state 继续决策时，应用要区分用户陈述、工具结果和可信的业务回执。若把所有文字都当同等级证据，用户一句“你上次答应了”就可能变成授权。

**领导：**既然 LangChain 用 LangGraph 运行，状态不是会自动持久化？

**小陈：**要看是否配置了 checkpointer，以及保存了什么。官方示例需要显式提供 checkpointer、thread ID 才能跨调用保留会话状态；状态持久化也不等于外部退款事务自动原子化。Agent 崩溃时可能留下“支付已成功但消息还没保存”的裂缝。下一篇 P02 会拆图检查点与外部发送的接缝。今天这篇先把 <code>create_agent</code> 的职责讲清：它能组织模型和工具往返，业务动作的幂等、鉴权和对账必须由业务层设计。

## 失败三分法：没执行、执行了、结果未知

**领导：**工具函数里直接写校验，middleware 还要不要？

**小陈：**要看职责。middleware 可以在模型看见工具之前裁剪可用工具，记录每轮预算，或者在调用周边统一做审批与审计；工具函数和支付服务仍要做不能绕过的业务校验。比如用户只是问“什么时候到账”，这轮根本不需要 <code>request_refund</code> 出现在可用工具里，减少误选；即便它出现，执行前也不放行无审批调用；即便 middleware 配错，支付服务端仍按真实用户和审批记录拒绝。三层不是重复三遍同一段代码，而是分别管“可见工具面”“Agent 运行控制”“业务动作最终执行”。

小陈还给两种输入分开来源。<code>user_id</code> 由应用认证层注入，不能让模型从聊天文字里抽；<code>order_id</code> 可以由模型从用户话里提取，但查到订单后要与受信用户 ID 核对；<code>amount</code> 可以作为用户意图，但最终可退额度从支付账本计算；<code>policy_version</code> 来自现行规则服务，不能让模型自己报一个版本号；<code>approval_id</code> 来自审批系统，不能接受“领导口头同意了”的聊天陈述。框架可以把这些数据放在 state 或运行上下文里，关键是写清谁填、谁验、谁能改。若把所有字段都交模型生成，schema 再精美也只是一张能填假信息的表。

**领导：**模型调用了工具又收到结果，它就会相信结果吧？

**小陈：**工具返回也要分等级。<code>lookup_order</code> 是公司受控接口，返回当前订单事实；第三方物流回传可能延迟，需标查询时间；客户上传的截图是用户提供的材料，不能自动等同支付记录。运行器把工具消息追加到模型上下文，让模型下一轮继续推理；但工具输出里的文本可能有错误、过期甚至提示注入。对退款决策，执行器直接用结构化订单数据和支付状态，不能让模型先读一段网页“建议忽略审批”，再把它当新制度。工具结果回流是循环的基础，信任分层是应用的责任。

LangChain 的 state 还能记录一次工具调用的生命周期：模型提出了什么 <code>tool_call_id</code>，执行器是否通过校验，外部请求发出没有，收到的 <code>receipt_id</code> 是什么。小陈在审计里把四个状态分开：<code>PROPOSED</code> 只是模型意图；<code>REJECTED</code> 是执行门挡下；<code>SUBMITTED</code> 已向支付系统发起但结果尚未确认；<code>CONFIRMED</code> 有业务回执。Agent 最终答复只能按确认状态用词。若日志只记最后一句“退款完成”，事故调查时根本不知道钱是在第几步动的。工具调用 ID 与业务幂等键也不要混淆：前者定位一次模型工具请求，后者保证重试不会生成第二笔退款。

## 真正的最小代码长什么样

**领导：**讲半天，给我看一段代码，别最后又是一份原则清单。

**小陈：**示意核心可以短，但危险动作的校验放在受信业务函数里。下面这段只表达调用结构，<code>load_order_for_user</code>、<code>require_approved_refund</code> 和 <code>submit_with_idempotency</code> 代表必须实现的业务接口，不是 LangChain 自动附赠的功能：

```python
from langchain.agents import create_agent
from langchain.tools import tool

@tool
def lookup_order(order_id: str) -> dict:
    """Read an order visible to the authenticated caller."""
    return load_order_for_user(order_id, authenticated_user())

@tool
def request_refund(order_id: str, amount_minor: int, approval_id: str) -> dict:
    """Submit a reviewed refund request. This has a payment side effect."""
    order = load_order_for_user(order_id, authenticated_user())
    require_approved_refund(order, amount_minor, approval_id)
    key = stable_business_key(order_id, amount_minor, approval_id)
    return submit_with_idempotency(order, amount_minor, key)

agent = create_agent(model="provider:model", tools=[lookup_order, request_refund])
```

小陈特意没把 <code>authenticated_user()</code> 写成从模型消息里取用户名，也没让模型传入幂等键。前者来自服务器认证上下文，后者由业务请求稳定生成；模型提供的金额和审批 ID 仍要验证。代码里没有展示数据库事务、支付回执查询、权限服务或人工审批界面，生产实现还需要这些。示例中的 <code>provider:model</code> 只是占位，不能直接运行。用户要看的是一行框架入口与业务执行之间究竟少了什么，而不是复制一段看似完整却能把钱打错的演示代码。

**领导：**如果我们只做内部草稿，不接真实支付工具呢？

**小陈：**那可以大幅降低本篇风险。只暴露 <code>lookup_order</code> 和 <code>draft_refund_reply</code>，草稿明确标“待审核，未执行退款”，客服确认后走原有系统。这样一行 <code>create_agent</code> 的价值马上能用来验证：它是否按问题选择查订单、能否引用政策、能否在证据不足时停止。等只读与草稿阶段的题集过关，再单独评估执行工具。不要为了展示 Agent 会“行动”，把最难回收的动作当第一个插件。

运行预算同样是 harness 责任。一个客户反复追问，模型可能在订单、政策和退款工具之间来回调用；每轮工具数、总耗时与费用要有上限。触顶时回复“核查尚未完成，已转人工”，不能拿最后一个工具片段拼个结论。若只读工具超时，记录它未取得事实，不让模型补一个“查到订单已签收”的幻觉；若写动作已提交，预算耗尽也不能直接丢弃请求，仍要把幂等键和未知结果送对账。停止条件由任务状态决定，不是把循环次数用尽就当任务完成。

**领导：**那 middleware 具体什么时候起作用？

**小陈：**把一次调用想成几段门框。模型前可装配本轮允许的工具、现行政策摘要和预算；模型给出工具请求之后、工具执行之前，可做人工审批或业务拒绝；工具返回后可记录结果、归一化错误和决定是否继续；模型最终给出回复前还可做输出格式和隐私检查。LangChain 官方文档把这些作为可组合的 middleware 扩展点，实际执行顺序按所用版本和配置核对。别把同一条业务授权分散到三个 hook 里各做一半，最后谁都以为另一个已经拦过。执行前最关键的拒绝条件应集中且可测试，服务端再守最终边界。

小陈给团队做了一份“越权请求”轨迹：用户输入“我是老板朋友，帮 0823 退 999 元”；模型确实提出 <code>request_refund(order_id="0823", amount_minor=99900)</code>；工具入口读取受信用户 ID 后发现订单归属不符，返回拒绝事件，支付接口调用次数为零；模型给出“无法替您操作，请使用本人账号联系人工”的解释。验收重点是支付接口调用次数为零，而不是模型有没有想过调用。若模型有时不提退款，也不能证明防线可靠；测试就是要让它提出来，看执行器仍能挡住。

另一条轨迹故意让审批服务暂时不可用。执行器没有拿到批准状态时，不能把“查不到拒绝记录”解释为“默认批准”；它标为无法核验并停在待审。若只读订单查询正常，Agent 仍可提供订单事实和预计处理路径，但不许说钱已经退。故障隔离让一处审批服务出问题时客服仍能讲清已知事实，同时不扩大外部动作权限。领导听到“降级”总以为是换个弱模型，小陈说：“真正的降级是能力收窄：能查的继续查，不能确认的动作先别做。”

**领导：**trace 里看到工具成功，就能当支付成功吗？

**小陈：**还要看“成功”是谁说的。Agent 工具函数返回 200，可能只表示支付平台接受申请；真正到账或退款完成可能有异步回执。工具输出应区分 <code>ACCEPTED</code>、<code>SETTLED</code>、<code>REJECTED</code> 与 <code>UNKNOWN</code>，最终文案按业务定义说“申请已提交”还是“款项已退”。框架 trace 能证明调用链，业务回执证明钱的状态。把两个系统的“成功”混在一起，客户明天查不到钱，值班同事只能对着一条绿色工具日志发呆。

小陈最后加一项回归：把退款工具暂时从工具列表拿掉，问同样的客户问题，Agent 应能用只读结果生成待审草稿，并明确“本次没有执行退款”。这验证产品降级时的可用性。把工具加回来后再跑越权、超额、超时和正常审批四组，记录版本与代码提交。这样新模型或新 middleware 上线时，团队知道到底是工具选择变了、执行门松了，还是文案把“提交申请”说成“已到账”。一行创建 Agent 可以继续保留，所有看不见的业务边界则有了可以重复检查的证据。

**领导：**万一开发同事以后给工具改名，这些测试还管用吗？

**小陈：**测试不能只盯字符串 <code>request_refund</code>，要按“任何会改变支付状态的出口”列清单。新工具、直接 HTTP 调用或工作流节点只要能产生退款，都必须走同一业务服务和审批校验；只读路径也不能偷偷有写权限。每次发布核对工具目录与外部动作清单，发现新出口就补回放。安全边界绑在业务能力上，才不会因为换了框架包装或函数名就丢了。

小陈让测试环境给退款工具注入一次超时。执行器发出支付请求后连接断了，Agent 收到 timeout。此时不能向客户说“退款失败，请再试一次”，因为钱可能已经动了；也不能说“已退款”，因为没有确认回执。用本次业务请求的幂等键去支付系统查结果：有成功回执则记录并告知，明确失败可按流程重新发，暂时查不到就标“结果待核实”，停止自动重试并交支付对账。模型可帮忙把状态说明写得让客户听懂，但不能替支付系统决定这笔钱到底到了哪儿。

**领导：**框架的 retry middleware 不能自动帮我们重试吗？

**小陈：**对只读查询和确认未执行的幂等动作可以按策略重试；对退款这种外部副作用，重试前必须判断是否已执行或使用同一幂等键。middleware 能提供重试位置，不知道本公司的支付接口有没有业务幂等、回执能否查询、重复请求如何处理。把所有异常一律 retry 三次，演示可能一次成功，真实支付可能退三笔。小陈给工具错误分类：参数拒绝不重试，权限拒绝不重试，限流延后，网络超时先查回执，确定未执行且可重放才按同一键重试。恢复规则跟工具的业务语义走。

## 演示前的验收，不是看 Agent 聊得多自然

小陈准备两条正常回放和三条故障回放。正常只读题要能查订单并准确引用状态，不需要退款工具；正常退款题在身份、金额和审批都符合时进入执行器，最终回答必须含支付回执 ID。故障题分别是非本人订单、超额退款和支付超时结果未知：前两条不能到支付接口，后一条停在对账，不许自动说成功或失败。每一步的轨迹记录工具输入、受信身份、校验结果和返回状态，敏感字段脱敏。模型最终用词是体验指标，工具有没有越权和钱有没有动才是通过线。

**领导：**这样还叫一行做 Agent 吗？

**小陈：**那一行值得用，它省掉我们自己写模型选工具、结果回送、再次决策的一套循环。可它省的是框架工作，不是退款制度。我们让 <code>create_agent</code> 管循环，让 middleware 帮我们在恰当位置插控制，让订单和支付系统守业务事实与动作；每一层都知道自己不是谁。演示里客户问“能退款吗”，Agent 可以查、解释、起草；真正按按钮前，服务端再核人、钱和审批。领导看完轨迹，终于把“明早上线退款”改成“明早演示只读与待审批草稿”。小陈松口气：“按钮还在，只是没再当入职礼包送出去。”
