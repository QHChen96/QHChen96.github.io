**领导：**小陈，销售助手升级一下。查客户的一个，查合同的一个，查工单的一个，写方案的一个，再安排六个负责动脑子。十个 Agent，总比一个聪明吧？

**小陈：**十个人同时往一张表里填不同价格，聪明不聪明先放一边，财务大概会先聪明地关掉我们的权限。多 Agent 的第一步，是把事情分对。数量只是结果，不能当设计目标。

本专题用一个**教学虚构**的续约任务贯穿：客户星河制造的合同即将到期，销售需要一份内部续约准备稿。稿件必须写清客户当前产品使用情况、现行合同约束、未解决的服务问题，并给出附来源的下一步建议。系统可以查授权资料、整理证据、生成草稿；折扣审批和对客发送由业务流程决定。人物、时间和数字用于讲机制，不代表真实项目成绩。

## 一、先别招十个，搞清楚一个到底干了什么

**领导：**你又要从基本概念讲起？

**小陈：**这次只拆三个容易混的东西。模型调用是一次输入换一次输出；Agent 是围绕目标反复选择工具、读取结果、决定继续或停止的运行单元；多 Agent 是把多个这样的单元组织起来。它们可以调用同一个模型，也可以用不同模型，不需要十家供应商才算一支队伍。

假设一段程序依次调用“查合同接口”“查工单接口”“生成摘要”。前两步是确定性函数，最后一步调用模型，这是一条工作流。你可以把三个节点都命名为“专家”，但名字不会自动产生独立规划能力。反过来，一个主 Agent 用工具派出两个能独立搜索、筛选来源并返回结果的研究 Agent，即使都在同一个进程里运行，也具有多 Agent 协作结构。判断时看控制关系、任务边界和状态归属，别数类名。

角色提示也不是隔离机制。给两次调用分别写“你是法务”“你是销售”，只是改变了模型收到的指令。如果它们读取同一份没有版本的资料，拥有同一把管理员钥匙，写同一个共享变量，系统层面的风险几乎没变。真正的边界包括每个单元可见的上下文、可调用的工具、可访问的对象、可产生的结果，以及谁有权把结果并入主任务。

**领导：**那一个 Agent 就够用了？

**小陈：**够不够先测。我们先让一个有合适工具的 Agent 做同一批续约任务，记录事实正确率、必要证据覆盖、耗时、费用、人工返工和禁止动作。没有这条基线，多 Agent 只能证明我们花钱组织了一次线上团建。

基线也要公平。不能拿旧模型、短提示、缺少合同检索的单 Agent，对比新模型、完整知识库、三倍预算的多 Agent，然后把改进全归给“协作”。先保证任务、资料版本、工具能力和评判口径一致，再比较同等成本或同等时间下的表现。若增加上下文筛选就能修掉主要问题，可以先改善单 Agent；若少数复杂任务才需要分工，可以按条件启用协作，不让每个客户都享受十人接待。

[LangChain 当前的多 Agent 指南](https://docs.langchain.com/oss/python/langchain/multi-agent)也把上下文管理、团队独立开发和并行执行列为主要动机，并明确提示：复杂任务并不总需要多个 Agent。这里的工程选择要由我们自己的任务证据决定。

## 二、把“一份续约方案”拆成可以验收的东西

**领导：**我只要方案，你怎么老在拆？

**小陈：**因为“方案”是最终产物，不是可以直接并行执行的原子任务。先列它必须回答的问题，才能知道谁可以独立工作。否则十个 Agent 都会去搜索“星河制造续约建议”，最后交十份内容差不多的作文。

这份草稿需要三组事实。客户研究分支负责核对 CRM 中的客户身份、合同关联账号与授权范围内的产品使用指标；合同分支负责确认生效合同、续约条款和适用政策版本；服务分支负责列出未关闭工单、影响与已确认的处理承诺。它们各自产出结构化证据包。汇总步骤对齐时间和对象，再让写作单元生成草稿；验证步骤检查每条关键主张能否找到支持证据。对客动作单独经过业务审核。

这里有两个顺序不能省。第一，先确认客户身份和访问范围，再让三个分支去检索。否则同名企业、集团子公司或历史合同会混到一起。第二，先确认合同与服务事实，再写续约条件。写作 Agent 可以先起一个空白骨架，却不能在关键证据回来之前把折扣、服务承诺填成确定事实。所谓并行，是把没有未满足依赖的工作同时推进，不是全员同时开始胡猜。

**领导：**任务拆得越细，管理起来越清楚？

**小陈：**太细会把协作成本放大。查一个字段就开一个 Agent，光解释客户是谁、输出写哪儿、结果怎么验收，就比查询本身还贵。一个分支最好包住一段有独立目标、独立资料与独立验收的工作；内部的小步骤继续用工具或普通函数完成。

判断边界可以看三件事。上下文是否自然分开，例如合同全文和工单日志没有必要都进入客户使用分析；输出是否可以稳定表达，例如工单列表能以编号、状态、影响和来源组织；错误是否能局部处理，例如新闻检索失败不应重跑已经核验的合同。三个条件都成立，拆分才有实用价值。若两个单元每走一步都要交换完整上下文、修改同一段核心逻辑，它们通常拆得太碎，应合并或用确定性顺序协调。

## 三、任务卡里没有这些字段，交接迟早翻车

**领导：**我给研究 Agent 发一句“你去查合同”，不就交代清楚了？

**小陈：**它不知道查哪家、哪份、截至什么时候、查不到怎么办。人还能回来问你，程序可能直接挑一份搜得到的旧合同，再很礼貌地说“已完成”。

一份可以落地的任务契约至少包含任务标识、目标对象、已核实输入、允许资料源、权限范围、交付结构、必要证据、截止时间和失败口径。还要注明哪些问题不由这个分支决定。合同研究可以判断“这一条文档写了什么”，不能替法务解释尚有争议的适用性，也不能以模型口吻批准折扣。把“只读并核对现行条款”写进工具权限，比把“请谨慎”重复三遍有效。

下面是**教学任务卡**，字段名是本文设计，并非某个框架的固定接口：

```json
{
  "run_id": "renewal-042",
  "task_id": "contract",
  "customer_id": "customer-17",
  "snapshot": "2026-09-30T09:00:00+08:00",
  "goal": "核对生效合同的续约条款和适用政策",
  "allowed_sources": ["contract_store", "policy_registry"],
  "required": true,
  "output_schema": "evidence_bundle_v1",
  "on_missing": "return_blocked",
  "side_effects": "none"
}
```

`run_id`标记一次业务运行，`task_id`标记其中一项逻辑工作；后续重试应保留逻辑任务身份，再增加尝试编号。`customer_id`先由授权流程确认，不能允许模型通过输入随便换成另一个客户。`snapshot`表达这轮资料核对的时间基准，不意味着所有系统天然支持同一时刻快照；不支持的来源要另记读取时间与版本。`required`决定缺失时是否阻断最终草稿，`on_missing`则让“查不到”成为能处理的结果。

任务卡也需要验收示例。“有一段续约建议”太宽；“返回合同标识、版本、生效状态、条款定位，列出冲突和未确认项”就能具体检查。输出是否符合结构、是否来自当前客户、引用是否存在，可以由代码先验；条款是否真的支持推断，再由适当的验证流程判断。模型说“我完成了”是叙述，系统验收才是状态迁移。

## 一个该合并的反例：三个角色同时决定价格

**领导：**那我们再分一个报价 Agent、一个折扣 Agent、一个谈判 Agent，它们共同决定最后价格。

**小陈：**这三个决定高度耦合。报价依赖生效价格表，折扣依赖客户资格和审批，谈判依赖已批准的可让步范围。若三位都能写“最终价格”，我们必须花更多步骤解决冲突。先用一个受控定价流程计算可用候选，专业 Agent 提供客户背景和风险，不让它们独立修改同一个承诺。

这里可以保留能力分工，却集中决定所有权。价格服务返回基准价格、适用规则、待批准范围和不可突破的条件；写作只消费这份版本化结果。客户诉求改变时，由主流程重新进入对应定价步骤，旧候选失效。这样既能让不同团队维护资料，又避免几个角色相互批准。判断是否拆分时，除了看能否同时开始，还要问合并后是否需要重新做完整判断；如果汇流阶段几乎重做了全部工作，拆分收益通常值得重新评估。

## 四、为什么并行不等于十倍提速

**领导：**三个分支一起查，至少快三倍吧？

**小陈：**先算关键路径。假设身份核对五秒，三个研究分支分别二十、二十五、三十五秒，汇总与检查共十秒。顺序执行是九十五秒，并行理论上是五加三十五加十，也就是五十秒。若额外分派、序列化和合并花六秒，就是五十六秒。这个例子快了约一点七倍，离三倍还有一段年终奖的距离。

这是一组教学数字，不是产品跑分。真实系统还会排队、遇到限流、访问慢接口和重试。重要的不是给出漂亮倍数，而是发现谁位于关键路径。若合同检索最慢且必需，给可选新闻研究多开五个 Agent 并不能让交付更早；若汇总必须读三份超长输出，节约的研究时间可能被重新吃掉。要测从接收任务到得到合格草稿的时间，而非最后一个模型调用的耗时。

还可以用并行比例做一个上界估算。若任务中四成工作无法并行，六成可以分给三个同速工作单元，在忽略协调开销时，速度提升上界约为`1 / (0.4 + 0.6 / 3) = 1.67`。这是经典并行计算思路在教学任务上的应用，前提包括工作量可均分、资源不竞争。模型服务共享同一限流池时，这些前提往往不满足。算式告诉我们该优化串行部分，而不是继续增加人数。

**领导：**那多 Agent 还会更贵？

**小陈：**会。每个分支都要读自己的指令和上下文，可能多轮搜索；主 Agent 还要派单、读结果、整合。成本账至少计模型输入输出、工具调用、运行时间、存储、人工复核和失败返工。缓存可以降低一部分重复成本，但不能假定所有请求命中缓存，更不能把跨客户敏感信息放进不合适的公共缓存。

一个常见浪费是把五万字全量客户资料复制给三个分支。总输入膨胀，分支却只用其中十分之一。正确做法是先根据任务选字段与证据入口，再让分支按需查细节；原始大文件存为有权限的工件引用，别让每次交接都重新背一遍。多 Agent 的上下文收益来自合理分配，并不来自把同一个长提示复制十份。

## 五、角色越多，为什么答案反而越像开会

**领导：**研究、写作、审查都有了，准确率总该更高。

**小陈：**要看错误怎么传。研究者把“历史合同曾允许九折”写成“当前可九折”，写作者照着润色，审查者又只读润色后的稿件。三个角色都很认真，仍然把同一个错误传了三遍。多一道模型调用，不自动多一道可靠校验。

中间输出是一个信息压缩过程。原文里有适用客户、有效期、例外条件和来源位置；摘要若只保留结论，下一步就没法还原那些限制。我们要让证据包保留主张、支持材料、版本和未知项。写作者可以改变表达，不能升级证据地位；“待核实”不能在第二轮变成“已确认”。这也是为什么后面专门讲协议、来源和冲突处理。

可靠性还取决于依赖结构。仅作数学演示：如果五个必要步骤各有九成成功概率，且错误独立、任何一步失败都导致整项任务失败，端到端成功概率是`0.9^5≈59%`。真实 Agent 错误常常相关，不能照抄这个比例预测项目；但它提醒我们，必要链越长，局部成功率越不能代表最终结果。可选分支、验证门和恢复机制要按真实风险设计。

**领导：**给每个角色换不同模型，总能减少相互影响吧？

**小陈：**可能改变错误相关性，但不是保证。如果它们都读同一份失效文档，换模型只会用不同口音说同一句错话。独立性还包括资料路径、验证依据和检查方法。确定性规则核对合同版本，授权接口核对客户身份，独立读取来源核对关键承诺，往往比让三个模型投票更有价值。哪一种组合有效，要在目标任务上测出来。

**小陈：**我给你一张已经填好的判断表，不让你回去做题。续约准备的三路只读研究有各自的证据来源，能独立交付；三份结果在主流程按规则汇合；价格决定和发送动作集中控制。因此我们先试三分支，主流程保留固定顺序。暂时没有理由开六个自由讨论 Agent。

| 观察到的瓶颈 | 优先动作 | 为什么 |
| --- | --- | --- |
| 单 Agent 常选错工具 | 改善工具目录、按状态收口工具，再评估拆分 | 工具太多可能是配置问题 |
| 合同与工单上下文互相挤占 | 按资料域分研究任务 | 每个分支只读相关证据 |
| 多个独立来源等待太久 | 有限并行检索并设置汇流条件 | 可缩短独立等待的关键路径 |
| 客户身份经常混淆 | 先修主键、授权和资料关联 | 多 Agent 会扩大错误传播 |
| 草稿事实错，审查总放行 | 引入来源核验和确定性检查 | 角色数量不能提供事实依据 |
| 必须逐步获得客户确认 | 设计有状态交接与权限阶段 | 并行启动后续动作会越界 |

有些任务天然适合分工，例如几个互不依赖的研究方向、不同资料域的核对、可独立验收的测试维度。也有些任务高度耦合，例如多个编码 Agent 同改一个核心接口、多个销售 Agent 共同决定同一笔交易承诺。后者并非永远不能拆，但需要先规定所有权、版本与集成路径，不能从“都去改”开始。普通批量计算若不需要自主判断，用并行函数即可，不必额外套角色。

**领导：**不同团队各管一个 Agent，是不是也算理由？

**小陈：**算。合同能力由合规团队维护，工单能力由客服维护，主流程由销售产品维护，可以让版本和职责更清楚。但团队边界不能直接复制成运行边界。一个低延迟接口可能更适合共享服务，一个跨域判断可能需要合并上下文。我们要把组织维护优势、运行性能和数据授权一起看，而不是照着公司通讯录画架构。

## 七、试点怎样证明协作真的有用

评测样本要覆盖普通续约、合同缺失、多个合同版本、服务承诺冲突、权限不足、工单接口超时和同名客户。每个样本给出事实快照、需要的证据、不能做的动作以及合格产物。这样才能判断多 Agent 是在正常题上更漂亮，还是在困难题上更可靠。分支失败时能否给出明确缺口，也是成果的一部分，不能全部从统计中删掉。

对照至少包含三个方案：经过合理配置的单 Agent、确定性工作流加单个写作模型、三路研究协作。固定资料与模型版本，保存实际花费与运行轨迹；同等预算下比质量，同等质量门槛下比时间与成本。若只给多 Agent 更大预算，结论应写“额外资源换来何种收益”，不能写成架构本身的普遍优越。任务有随机性时还要重复运行，观察波动。

**领导：**最后给我什么，别只交架构图。

**小陈：**交一张任务依赖图、三份任务契约、同口径的对照记录，还有试点开关。普通客户先走工作流；当资料量或研究难度满足条件时启用三个研究分支；必需证据缺失就返回待补资料；全部事实核对后只生成内部草稿。我们用这些规则决定什么时候分工、分到哪里、什么时候结束。

验收也分两层。分支层检查来源、对象、结构与状态；业务层检查草稿是否完整、关键主张是否成立、是否触碰禁止动作。一个分支写得很长但没有当前合同引用，必须判不合格。三个分支都成功但客户 ID 不一致，主任务必须阻断。把这种失败记录保留下来，后面才能知道是拆分、数据、模型还是汇总出了问题。

## 八、领导最后三问，小陈当场交底

**领导：**多 Agent 和工作流可以同时存在吗？

**小陈：**可以。工作流规定先检查身份、再并行研究、再验证草稿；某个研究节点内部可以运行一个会自主选择工具的 Agent。固定业务门与动态探索各管适合的部分，主流程仍知道现在处于哪一阶段。判断架构时把内层循环和外层顺序都画出来，别把它们压成一个黑盒。

**领导：**多个 Agent 一定要并行吗？

**小陈：**不一定。审核依赖草稿，交接依赖前一个角色收集的信息，都会顺序执行。多 Agent 解决的是分工和边界，并行只是其中一种组织方式。真正值得争取的，是每份必要证据有归属、每段工作可验收、每次外部动作有责任人。

**领导：**所以你给我招几个？

**小陈：**先三个研究单元，一个主流程。写作和验证先作为清楚的步骤，验证里能用规则解决的就用规则；需要语义判断时再调用模型。做完对照，若收益不足就收回多余分支。少开一个没价值的 Agent，也算我们给公司完成了一次降本任务。

下一篇把“主流程”拆开：主 Agent 调专家、把对话交给专家、路由后并行汇总，三种控制方式看起来都叫协作，实际责任完全不同。
