**领导：**公司决定统一走模型网关。把所有绕过网关、直接调用模型服务的代码找出来。我问 Agent，它报了三处，挺快。审计组怎么报了三十处？

**小陈：**它答的是“我看到的典型例子”，你转发时写成了“全公司清单”。三和三十不一定谁全对，但“给出三处”本身绝不等于“找全”。它只读了一个仓库的几个文件，没固定提交，也没查 SDK 别名、内部封装、环境变量和其他仓库。我们要交审计的是带范围、规则、复核结论的明细表，而不是一句口才很好的总结。

**领导：**又是范围？上篇都讲过了。现在我只想把三十处找齐。

**小陈：**这次多一个难题：同一件事有十几种代码写法。先定义“直连”是什么，再用几路搜索把候选找出来，最后逐条验证调用到底去哪。只凭字符串会漏；只凭模型理解会飘。两种工具各干擅长的部分。

本文的企业仓库、数量和代码片段均为教学虚构。GitHub Code Search、Semgrep 与 ast-grep 的能力以各自官方资料为准；具体发现率必须在本公司固定题集上实测，不能把示例数字当产品效果。

## 审计会议第一问：什么算“绕过网关”

领导原话是“直连模型服务”。小陈把判定条件写到白板：生产可达的应用代码或定时任务，向外部模型提供方发送推理请求，且未经过公司规定的网关身份、预算、审计和数据策略。研究脚本、废弃示例、测试替身、文档引用和打包进生产但从未启用的代码，不能随便混成一类；它们也可能有治理风险，但处置优先级不同。若公司网关本身调用提供方，那是网关的正常职责，不应算违规直连。没有这一层定义，审计清单从第一行起就会吵起来。

**领导：**看见 <code>openai</code> 或 <code>anthropic</code> 就算，不就简单？

**小陈：**太宽会误报，太窄会漏报。文档里引用 API 名称、测试里 mock SDK、网关实现里真的调用提供方，都能包含那些字符串；相反有人用 <code>httpClient.post(modelEndpoint)</code>，参数来自配置中心，源码没有提供方名字。审计要分“命中候选”和“确认直连”。前者宁可适度多找，后者必须看到调用链、运行配置和网关边界的证据。

他先设一张分类表：A 类明确的提供方 SDK 调用，B 类通用 HTTP 客户端指向模型端点，C 类公司旧封装或第三方库间接调用，D 类配置中出现直连端点或凭据，E 类运行环境流量或日志显示模型服务出站。A 到 D 主要靠代码和配置找，E 用来检验静态清单是否漏了真实流量。分类既告诉搜索器该找什么，也告诉复核者看到命中后该问什么；不能把五类命中简单加总，因为一处真实调用可能同时出现在代码、配置与网关日志里。

## “三个典型例子”是怎么把审计带沟里的

小陈回看 Agent 的回答：第一处是 <code>new OpenAI(...)</code>，第二处是旧服务的 <code>chat.completions.create</code>，第三处是一个测试脚本。它引用了真实文件，语气也很肯定，但没有说搜索了哪些仓库、有没有结果上限、是否翻页、排除了什么目录。模型在有限上下文里往往倾向给一个能读懂的概括，而审计要求完整性。就像领导要全公司紧急联系人，它递来三位最熟的人，并补一句“应该差不多”。

**领导：**那我提示词里写“务必列出全部，不得遗漏”呢？

**小陈：**这句话改变不了工具实际扫描范围，也不能让模型凭空读到没索引的仓库。可以要求它汇报覆盖范围和未覆盖项，但完整性仍由可复跑的搜索计划、仓库清单和样本回放证明。模型适合解释候选、建议别名和帮助人看调用链；最后一栏“已逐条复核”要有具体证据与责任人。若提示词能让遗漏自动消失，审计组早就失业去开咖啡店了。

小陈先固定输入：本次审计针对生产部署清单中列出的四十二个仓库、截至某个完整提交号；数字只是虚构示例。每个仓库记录语言、构建产物、生产版本和负责人。另列出无访问权限的两个仓库，以及一套由外部团队维护的配置服务。这样最后说“覆盖四十二个仓库”时，别人能看见它是哪四十二个；不能只挑命中多的仓库做分母。若线上仍运行旧提交，对旧提交也搜索；主分支通过并不代表生产已切过去。

## 候选发现分四路，别把鸡蛋都塞进关键词框

第一路是字面检索。小陈把 SDK 包名、构造方法、常见接口路径、请求字段、端点配置键列成词表，用 <code>rg</code> 或 Git 搜索逐项扫固定仓库。它快，易复跑，适合先找明显点；但一词多义和别名会带来误报与漏报。[GitHub Code Search 官方语法](https://docs.github.com/en/search-github/github-code-search/understanding-github-code-search-syntax)支持仓库、路径、语言、内容与符号等限定，还能组合布尔条件和正则；使用时要记录查询式与目标仓库，不能把网页第一页当全集。GitHub 文档也提醒裸词可能匹配路径或内容，审计内容时最好显式限定，避免一个文件名看起来像代码命中。

第二路是符号与结构搜索。若代码用 <code>import { Client as ModelClient }</code>，只搜 <code>OpenAI</code> 的构造调用可能找不到后续 <code>ModelClient</code> 实例。沿 import、类型、符号引用和调用点追，能把别名与封装展开。对常见 AST 形态写规则，譬如创建 SDK 客户端、调用通用 HTTP post 且端点来自模型配置。官方 [Semgrep 规则文档](https://docs.semgrep.dev/writing-rules/overview)说明规则可做代码模式与数据流分析；[ast-grep 指南](https://ast-grep.github.io/guide/introduction.html)展示基于代码结构的匹配与规则系统。结构搜索不神奇：规则只覆盖写出来的形态，宏、反射、动态调用或不支持的语言仍可能漏。

第三路是配置与依赖。源码不出现提供方端点，配置中心或环境变量却可能给 <code>MODEL_BASE_URL</code> 注入真实地址；包管理文件能提示引入了哪些 SDK，但“装了包”不等于“生产调用过”。小陈把配置键与构建产物映射回服务，再去查谁读取这个键、谁给它赋值，最后看生产是否加载。遇到镜像或脚本里的直连路径，还要看构建流程有没有把本地文件排除或替换。代码清单与配置清单一对，就能发现“文件里看着走网关，运行时被环境变量改成直连”的坑。

第四路是运行证据。服务出口日志、网关请求记录或可批准的网络观测，可以发现真实向提供方域名出站的工作负载；但需要区分公司网关本身、测试集群、SDK 的遥测请求与真正推理调用。运行证据不能替代静态审计，因为低频定时任务在观测窗口内可能没跑；静态审计也不能替代运行证据，因为动态配置和旧镜像可能让源码判断失效。小陈把两路结果用服务身份、版本和时间对上，差异单独排查，不用某一路替另一路盖章。

**领导：**这么多工具，换个厉害的代码搜索产品不就统一了吗？

**小陈：**工具能帮找线索，不能替我们定义“绕过网关”的业务边界。GitHub Code Search 适合跨仓定位文本和符号定义，但官方文档明确符号搜索主要找定义，不能把它当所有引用关系；结构规则能发现特定语法，却依赖规则与语言支持；运行出口能看到已发生流量，却看不到未来才会触发的分支。统一界面可以提升效率，统一结论仍要靠多源证据。今天要的是审计闭环，不是给搜索框选妃。

## 一处候选怎么从“像”变成“就是”

小陈拿审计组报出的第十七处示范。文件 <code>services/invoice/model_client.py</code> 调用 <code>completion_client.generate()</code>。字面搜索没 <code>OpenAI</code>，结构搜索发现 <code>completion_client</code> 来自公司旧 <code>llm_bridge</code> 封装；继续看封装，它根据 <code>MODEL_ENDPOINT</code> 选地址。生产配置把该值设到公司网关域名，且带着网关签发的身份。此处虽然直接调用“模型客户端”函数，但请求实际走网关，判为“经网关，非违规”；把它算成直连会误伤团队。

第十八处在批处理仓库，代码也是同一个封装，却有一个任务的生产环境变量覆盖成提供方 API 地址。代码审查只看库会漏掉；配置和运行出口对上后，确认它绕过网关。审计表附仓库与提交、部署任务、配置来源、请求目的地、是否经过网关、证据链接、负责人和修复单号。若出口日志因权限不足查不到，只能先标“高度疑似、待核实”，不能因为叫它“第十八处”就暗示证据全齐。

**领导：**那个批处理一个月只跑一次，运行日志可能没留到今天，怎么定？

**小陈：**静态证据可以证明确有生产可达路径和直连端点配置，但是否实际发出过请求，还需要任务调度记录或下一次受控运行的出口证据。两个结论分开写：“存在可达直连路径”与“已观测到直连请求”。治理上可以先改路径，不必等它下月真的发出去；审计陈述上不能把推断写成观测。小陈把这条标成“确认配置风险，历史实际调用未证实”，下月的运行窗口再核对。细分事实不妨碍采取行动，反倒让行动更准。

## 审计表要能追踪去重，不能一处算三十遍

四路搜索会把同一调用点重复发现。小陈给每条候选一个复合定位：仓库、提交、文件、符号或调用点、运行服务、配置环境。不同查询命中同一调用点合并为一条候选，保留发现来源；同一代码部署在两个环境、一个走网关一个直连，则拆成两个“运行实例结论”，因为处置不同。依赖包发现和真实调用也分开，不因 <code>requirements.txt</code> 出现 SDK 就计算一次违规。

**领导：**报表里到底是三十“行代码”、三十“服务”，还是三十“问题”？

**小陈：**先说计数单位。候选调用点、确认的生产直连路径、已观测直连请求和需要修复的服务，是四个不同指标。一处封装可能被十个服务引用，一个服务也可能有多处调用。领导如果要安排修复人力，看服务和调用路径；审计如果要证明覆盖，看仓库、文件与规则；安全如果要评估数据暴露，看已观测请求和数据类型。把四个数揉成一句“三十处”，下一次会议肯定会吵到午饭凉掉。

小陈给审计表设计了必填列：<code>repo</code>、<code>commit</code>、<code>path</code>、<code>symbol</code>、<code>deployment</code>、<code>endpoint_source</code>、<code>gateway_passed</code>、<code>evidence</code>、<code>verdict</code>、<code>reviewer</code>、<code>next_action</code>。状态只允许“待复核、已确认直连、经网关、非生产、误报、未覆盖”，每个状态转换要留原因。命中原文若包含凭据，只记录脱敏定位，不复制完整值；审计可以复核事实，不能为了复核又造一个泄露副本。

## 找全能力怎么测：埋点、反查与两条独立线

**领导：**你怎么证明这回不会又只找出三处？

**小陈：**不能数学证明所有未知写法都被看见，但可以用多种办法压低漏检。先从已知生产路径抽一批做种子，要求查询规则全部找出；再在测试仓库埋别名 import、旧封装、HTTP 直连、配置中心覆盖和跨仓调用五类样本，检查每一路分别捞到什么。结构规则上线前跑正负样例，避免把测试 mock 也当违规。然后让静态清单与独立的出口观测互相反查：日志里出现而清单没有的服务必须解释，清单上显示直连而运行记录没有的也要区分低频与死代码。

“已知样本全部发现”只证明已知样本，不证明全宇宙。小陈给每个仓库登记是否可访问、是否已索引、语言是否支持结构规则、构建产物是否可追到源码、是否有运行出口记录。覆盖率的分母是计划范围内的仓库和部署，不是搜索结果页数。若云上遗留服务没有代码仓库权限，就列“未覆盖”与负责人，不能从统计里悄悄删除。审计组问“为什么你们只有二十九处”，可以逐项对照范围和证据，而不是让 Agent 再写一句“我已经尽力”。

## 结构搜索也会漏：别把“懂语法”听成“懂整个系统”

**领导：**AST 都能看懂代码结构，为什么还要人反查？

**小陈：**因为调用路径不总在一个语法节点上。比如服务代码调用 <code>invoice_ai.summarize()</code>，这个函数从依赖包导入；依赖包在另一个仓库，运行时又根据环境变量选择提供方。当前仓库的 AST 可以告诉我们函数怎么被调用，未必知道包发布时是哪版、那一版是否经网关。再比如反射按字符串装载类、插件注册表根据配置选择实现、代码生成在构建时才产出调用点，单文件模式很难覆盖。结构规则要写明语言、文件、模式和版本，跨文件能力也要按工具与许可核验，不拿“语义扫描”四个字代替测试。

小陈把一条封装路径拆成四段：业务入口能否触发；符号引用能否走到封装；封装如何选择实现；运行配置把请求指向何处。每段都有不同证据：路由或任务调度、调用引用、包源码或发布产物、环境配置与出口记录。只找到最后一段的端点字符串，不代表业务入口会走到；只找到入口的 <code>generate()</code>，也不能推断终点是外部模型服务。审计用的是有方向的证据链，不是看关键词离得近不近。

**领导：**如果一个函数同时支持网关和直连，结论怎么填？

**小陈：**按配置环境拆。预发走直连、生产走网关，就写两条环境结论；若生产开关可在运行时切，记录当前值、谁能改、变更审批和回滚策略。静态代码含直连分支，即便当前没启用，也应评估是否删除或加不可绕过的服务端限制。否则某个脚本把 <code>USE_GATEWAY=false</code> 设错，审计报表仍会停在“上周查过，没问题”。代码风险与当前流量是两个维度，处置可以同时包括修代码和封出口。

## 漏检率的分母别乱算，误报也要有人收

小陈做一张回放题集，含二十条预先确认的调用路径、十条特意设计的非违规相似路径；数量是教学示意。规则发现十八条真路径、错报四条，这只能在这三十条样本上算召回和误报，不能冒充“全公司 90% 找全”。更重要的是错漏的原因：漏的是别名封装、运行配置，还是未索引仓库；误报是 mock、文档，还是网关自身。每一类原因对应不同修法。规则版本更新后用同一题集回归，还要补入上次漏掉的真实案例，避免团队只记住容易题。

**领导：**误报四条就人工看一下嘛，没必要写这么细。

**小陈：**如果每天新提交都扫，四条会反复打扰同一组人，久了大家连真告警也不看。排除规则可以减少已知误报，但每条排除要有理由和到期复审，不能用一个大范围 <code>tests/**</code> 把生产共用的测试工具或调试脚本一起藏起来。清单也记录“为什么排除”，新部署若把原本非生产文件打进镜像，审计会重新评估。降低噪音是为了让真路径及时被处理，不是为了让面板好看。

运行出口证据同样有采样偏差。若只保留一天日志，月度任务当然查不到；若网络代理统一出口，看到提供方域名不一定能直接反推出哪个业务服务；若内部网关也向同一域名请求，必须用工作负载身份或网关调用链区分。小陈给每条运行结论附观测窗口、日志保留、身份解析和缺失比例。静态规则与出口日志出现差异时，不让 Agent 任选一个“看上去更合理”的说法，而是生成待查项：是死代码、低频任务、代理身份丢失，还是规则确实漏了。

## 修复验收：删掉一行代码远远不够

第一条确认直连路径修完后，研发提交把客户端地址改为公司网关域名。领导准备把这一项划掉，小陈又查了五件事：生产镜像是否包含修复提交；配置中心是否还覆盖旧地址；调用是否带网关要求的身份与审计标签；数据和工具结果是否按网关策略处理；出口观测是否只剩网关的提供方流量。若只是代码改了而镜像没发，审计问题还在生产；若地址走网关但凭据被写进日志，又造了新问题。

**领导：**那清单什么时候能关闭？

**小陈：**同一条发现需要有“确认、派工、代码修复、部署验证、运行复查、关闭”六个状态，不因为 PR 合并就跳到终点。无法拿到运行证据的低频任务，可由负责人按计划做受控触发，或在下一次自然运行后补证；在此之前保留“待运行验证”。若服务已退役，要有退役记录和入口关闭证据，不能凭“应该没人用”撤销。每个状态都带时间和证据链接，下一位审计同事才能知道不是我们把表格颜色涂绿了。

**领导：**照你这套，今天能给我什么？别说等两周调研。

**小陈：**今天先给可行动的第一版：固定四十二个仓库与生产提交，跑字面和配置查询，复核高风险候选；把静态与运行证据能对上的直连路径先派修复单。剩余结构规则、低频任务和无权限仓库列为待补查，指定负责人和截止时间。第一版可以写“目前确认的路径”，不能写“最终全量”。每天增量扫描新提交，修复后用相同规则和网关日志验收，直到覆盖表上的缺口逐项关闭。

领导盯着小陈的表格，终于发现审计组的“三十处”里有二十个候选、六个重复发现、三处确认直连、一处待核实。数字都是本故事虚构的，不代表实际企业比例。原来的 Agent 报三处也许碰巧报中了其中一处，却没有能力说明“只剩这些”。小陈把对领导的汇报改成：“已经确认三条生产直连路径并分派修复；另有一条待核实；其余候选已分类；两个无权限仓库待补查。”这话不如“全找到了”响亮，但明天有人接手时能照着做。
