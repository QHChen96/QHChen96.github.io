**领导：**查单接口不是已经有了吗？把地址给 Agent，它就能帮客服判断“签收了却没收到”。

**小陈：**我在评审里试了两个订单号。接口给我返回了完整收货地址、支付信息和另一张工单的记录。客户问快递在哪儿，我们却顺手把客户家的楼层也打包给模型看，热情得过头了。

**领导：**你不是在工单 0823 里吗？怎么能查隔壁订单？

**小陈：**原接口只看传来的订单号，不看这张工单和当前客服有没有权利查。把它原样变成 Agent 工具，模型一旦填错号，后端还会很配合地送数据。这次我按代码评审的方式给您看改动。

```text
旧工具：get_order(order_id) → 整张订单、地址、支付信息、所有操作记录
新工具：get_ticket_order(ticket_id, order_ref)
        → {订单状态、物流节点摘要、签收时间、查询时间、来源回执 ID}
```

**领导：**把 `order_id` 改成 `ticket_id`，就安全了？

**小陈：**改个参数名等于给门换了块牌子。服务端要用当前客服身份查工单，再核对 `order_ref` 是否属于这张工单可见的订单集合；每次请求都做这个判断，不能信模型说“我有权限”。拒绝时不给模型泄露另一订单是否存在。授权要按对象逐次检查，这也是 [OWASP 授权建议](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)强调的事。

**领导：**接口失败时让 Agent 再试一次，不就好了？

**小陈：**得看失败种类。超时可按配置有限次重试，仍失败就写“查询结果未知”；未授权立即停，不靠重试把权限磨出来；订单引用无效先让客服核对工单。工具返回要有稳定的状态码和请求 ID，方便查日志，但日志里别把地址和支付信息再抄一遍。

| 工具返回 | Agent 与客服下一步 |
| --- | --- |
| `ok` | 引用订单状态、物流摘要和查询时间，继续查适用规则 |
| `not_authorized` | 停止查询，记录拒绝原因，交人工核对权限 |
| `not_found_in_ticket` | 核对工单绑定，不推断客户没有订单 |
| `temporary_error` | 限次重试；仍失败则标未知并交人 |

**领导：**怎么证明你这版真的比原接口稳？

**小陈：**拿绑定订单、隔壁客户订单、空订单引用、订单系统超时四条回放。只让第一条返回必要字段；其他三条分别拒绝、待核或报临时故障，答复里都不能说“我已查到”。另外抽查工具调用和日志：能追到谁查了哪张工单，却看不到不必要的客户信息。

**小陈交的接口契约：**输入的工单作用域、服务端鉴权、最小返回字段、错误状态和审计字段写进接口文档，产品、客服、后端按同一份验收。工具越窄，Agent 越不容易把“帮客户查件”办成“带领导参观数据库”。

## 先追那串门牌号，是哪一步越了界

**领导：**模型没把地址说给客户听，也算数据泄露？

**小陈：**客户地址已经进了不需要它的模型上下文，还可能随请求轨迹、故障日志、调试平台产生副本。风险不以“最后有没有念出来”为唯一标准。原订单接口给人类客服工作台用时，也许有更宽的字段，因为工作台有权限和显示控制；把它原样暴露为 Agent 工具，等于把后台整张订单记录交给一个只需判断签收状态的流程。数据流第一步就收错，后面再让模型“不要透露”只能补最后一道门。

更严重的是跨对象查询。客服已登录不等于有权看任意订单；Agent 通过共享服务账号调用后端，也不等于有权查当前用户没授权的资料。客户输入一个隔壁订单号，模型把它传给 `get_order`，原接口只验证号码存在便返回资料。即使模型后来没输出，服务端也完成了一次无权读取。修法不是让模型“更小心地选择订单号”，而是工具服务每次按当前身份和工单关系核对对象。

**领导：**那一张工单如果合法关联两张订单呢？

**小陈：**允许集合可以有两张，但由业务系统建立关联并给出可查范围，不由模型在提示里写“这是我的两张订单”就扩权。工具输入是受控订单引用，服务端查 `ticket_id` 所属租户、当前坐席或客户身份、工单与订单关系、该动作是否在允许范围；通过后只返回处理此题必要字段。若第二张订单需要重新核身份，工具返回“需核验”，不泄露它是否属于别人。权限决定要能追溯到具体对象和请求，不只靠“客服角色”四个字。

## 认证、授权、字段裁剪，三道门各管一件事

**领导：**我们已经让客服登录了，还要检查什么？

**小陈：**登录解决“你是谁”，对象级授权解决“你能否对这张工单的这笔订单做这件事”，字段裁剪解决“即使能查，要返回多少”。这三件分开做。一个客服可看工单 0823 的物流状态，不代表可看该客户的完整支付卡信息；一个主管可处理多个售后队列，也不代表可跨租户浏览所有订单。OWASP 授权指南强调最小权限、默认拒绝和逐请求校验，正好对应这里的服务端闸门。

工具网关不能把前端传来的 `customer_id`、`tenant_id` 当真。当前认证身份与租户从可信会话或服务令牌得出，工单归属从服务器读，订单绑定从业务数据库查。模型可以选择“我想查当前工单的关联订单”，但不应提供一个任意订单 ID 决定访问范围。若工具必须接受 `order_ref`，后端也要把它与允许集合相交。先对外部对象作授权，再读取敏感字段；不能先查完整订单再在应用层发现无权、顺手把对象留进日志。

**领导：**只返回状态会不会让 Agent 无法判断“没收到”？

**小陈：**要按任务返回必要的**业务事实**，不等于只返回一个布尔值。签收争议需要订单状态、物流节点摘要、签收时间、凭证是否存在、查询时间与来源回执；可能还需签收人信息，但能否给 Agent 看、看什么粒度，要按业务风险决定。完整地址和支付详情与“是否需要核查凭证”无关，可以不返回。若后续人工核查确需地址，由有权限客服通过受控界面查看，不把工具返回扩大到所有 Agent 路径。

## 把接口契约写成能测试的输入与输出

**领导：**给后端一份具体规格，别让他们猜“必要字段”是什么意思。

**小陈：**这条试点工具的输入可以是 `ticket_id` 和 `order_ref`，调用上下文由服务端附 `actor_id`、`tenant_id`、`purpose=delivery_dispute`、`trace_id`。输出 `status=ok` 时只含订单状态枚举、最近必要物流节点、签收时间、凭证可用状态、`observed_at` 和 `source_receipt`；不含客户姓名、完整地址、手机号、支付方式。错误输出含明确代码和请求关联 ID，不返回原始数据库异常或被拒订单的细节。

工具调用前依次检查：身份有效、工单属于同一租户、当前角色或客户对工单有权、订单引用在工单可见集合、该工具对当前问题类型可用。检查可以在服务端统一策略层实现，避免每个模型工具单独复制一段不同的 `if`。新工具默认拒绝，经过评审才加入路径白名单。返回后对字段做 schema 校验，缺 `observed_at` 或来源回执就不能让 Agent宣称“刚刚查到”。

**领导：**未授权时返回“订单不属于您”不是更清楚？

**小陈：**有时会泄露另一订单确实存在。对当前用户，安全答复是“无法在这张工单下查询该订单，请核对信息或完成身份验证”；内部审计可以记录具体拒绝原因，但对模型和客户不透露其他客户的订单详情或存在性。错误码可把 `not_found_in_ticket` 与系统故障分开给受控客服工作台看，外部文案仍按最小披露设计。权限拒绝不要靠重试磨开门，也不要自动改查相似订单号。

## 错号、串号、换班，四个现场都得挡

**领导：**你原来只测四条，再给我说清失败时怎么恢复。

**小陈：**第一，绑定订单 731 正常返回最小字段，引用回执能查；第二，换成隔壁客户订单 732，工具拒绝，响应不含地址、不含该订单是否存在的敏感信息，审计记录一次拒绝；第三，空引用或格式不对，返回输入错误，客服核对工单，不由模型穷举订单号；第四，订单系统超时，返回未知，试点只对只读查询有限重试，仍失败就留下有主待办。再加第五，客服换班后旧人失去工单权限，旧线程和旧工具调用不能继续查；第六，客户撤销授权或工单归属变化，下一次请求重新校验，不沿用昨天的许可。

如果订单工具返回了别人的数据，事故处理不止修代码。先关闭该工具或相关路径，查访问轨迹里谁在什么时间读过哪些工单、哪些结果进入模型或日志、有没有对外输出，再按企业隐私事件流程处理。清理不必要副本、修服务端授权、用跨客户回归测试证明拦截有效。不能只给模型加一句“请不要再次访问他单”，那把门仍是开的。

**领导：**模型如果能自己拼新的 URL 绕过这工具呢？

**小陈：**运行环境不应给它任意网络访问或通用数据库账号。工具清单只开放经过授权包装的能力；网络出口、服务凭据和后端权限按最小范围配置。模型提出调用什么是一回事，系统允许它实际连到哪里是另一回事。若使用通用 HTTP 工具，也要在网关限制目的地、方法和业务授权，不能让“只读查单”通过一个万能请求工具变成浏览内部网络。

## 审计记录能证明谁查了什么，却不复制客户家门牌

**领导：**没有完整请求和响应，出事了怎么查？

**小陈：**记录 `actor_id`、服务身份、租户、工单 ID、受控订单引用、工具名、目的、授权决定、拒绝理由类别、时间、耗时、回执 ID、返回字段类别与版本。需要核实具体订单时，授权调查者回到订单系统按权限访问原始记录。通用日志不写完整地址和支付资料，异常堆栈也不把整个响应对象打印出来。测试用虚构地址作为探针，正常、拒绝、超时和解析失败四条路径都查一遍日志，确认没有漏在报错分支。

授权策略本身也要测。研发写“只有客服角色能调用”还不够，要测同角色跨工单、同租户不同客户、不同租户相同订单号、离职或换班权限撤销、被拒订单 ID 是否能被枚举。OWASP 也建议为授权逻辑建立单元和集成测试。这里的测试有意义，因为同一个角色对不同对象的访问结果必须不同，不能只用一条 happy path 证明“有登录”。

**领导：**面试官问“为什么改参数名不算安全”，你怎么答？

**小陈：**因为安全边界在服务端逐对象授权和最小字段返回，不在函数签名。把 `get_order(order_id)` 改成 `get_ticket_order(ticket_id, order_ref)` 只是创造了施加约束的入口；若内部仍按 `order_ref` 直接查全表，漏洞原封不动。真正的验收是拿他单号调用，后端拒绝且日志不泄露；拿本单号调用，也只返回本题必要事实。把客户家门牌号从模型上下文里拿出去，才算关了这扇门。

## “有权看”还要带着任务范围和有效时间

**领导：**客服主管本来能看很多订单，Agent 借他的身份工作，为什么还要限制到本单？

**小陈：**主管的工作权限不等于每次 Agent 任务的授权范围。人类主管也许因处理申诉而能打开多张单，Agent 这次被交付的是“处理 0823 的签收争议”，其工具权限应当是该任务可用的子集。服务端判定要同时看**主体、对象、动作、目的和当前状态**：谁在调用、要看哪笔订单、是读取物流还是改地址、是否为了这张已接手的工单、授权是否仍有效。只看角色会把“能处理售后”误扩成“可看所有客户”；只看工单 ID 又可能忽略调用人已失去案件权限。

实际实现可用短期作用域凭据或服务端上下文绑定本次运行和工单，但凭据不是让模型自由携带的万能票。过期、换班、权限撤销后要重新判断；后端不能因为一次调用已通过就把后续查询永久放行。工具结果进模型前还要裁剪，日志访问另行授权。模型自身没有法律上的“客服身份”，它是在企业应用授权范围内提出请求，真正的权限由系统执行。

**领导：**如果核验完身份后，客户突然切换账号呢？

**小陈：**在每次工具请求时按当前会话和案件关系重新检查，必要时终止旧运行。旧对话上下文里可能还留着上一位客户的订单摘要，因此账号切换要清理或隔离线程；不能只改前端头像。测试要保留旧 `run_id`，切换账户后故意重放工具调用，确认后端拒绝。授权检查和模型上下文隔离必须配套，少一道都会在客服坐席共用电脑时出事。

## 返回字段收窄以后，还可能从旁门漏出去

**领导：**新工具响应里没地址，是不是完事？

**小陈：**看四个旁门。错误信息可能把原始订单对象序列化；追踪 SDK 可能默认捕获完整工具参数和结果；缓存键可能把手机号、订单号明文写进共享系统；后台调试页可能仍允许按任意订单号调用旧接口。工具包装层要审正常响应、异常响应、日志、缓存和调试入口，不是只审 API 文档里的成功样例。原接口若继续在内部可用，也要看是否被别的 Agent 路径绕过去；不再授权给 Agent 的旧工具要从工具注册表和凭据权限中撤掉。

还有数据聚合风险。单次只返回“签收时间”和“物流节点”，模型连续查十张单仍可能拼出不必要的客户画像。因此按工单限定可查对象，也按任务限制查询次数和频率；异常跨单尝试触发审计和告警。限次不能替授权，授权也不能替最小化返回，几道措施各守一段。客户问一张包裹，Agent 没理由打开十张邻居的订单去做统计。

**领导：**如果工具结果看起来合法，但订单系统返回旧缓存？

**小陈：**返回里必须有 `observed_at`、来源回执和数据新鲜度。Agent 可以说“订单系统在 16:02 显示已签收”，不能说“现在一定已签收”；若过了业务允许的陈旧度，重新查或标未知。字段裁剪不能裁掉判断信息可靠性的元数据。最小返回不是“把字节减到最少”，而是“只给完成任务所必需、足以核对的事实”。

## 一次接口评审，最后交三份东西

**小陈：**第一份是权限矩阵：不同主体对本单、他单、跨租户订单的读取和写入结果，以及换班和身份撤销后的变化。第二份是工具契约：输入范围、输出字段、错误码、审计字段和超时处理。第三份是回放包：本单成功、他单拒绝、无效引用、系统超时、旧线程重放、异常日志脱敏。产品能看懂客户会得到什么，后端知道哪里校验，测试能证明门真的关上。

**领导：**如果以后要支持退款，也沿用这个工具扩个字段？

**小陈：**不要把只读查单工具膨胀成又查又改的万能口。退款是有副作用的写动作，要有独立的资格判断、审批、幂等键、结果回执和未知状态恢复。即使同一工单使用两个工具，也让每个工具只承受清楚的权限。今天的查单接口先把数据边界守住，明天讨论退款时才不会把“查询成功”误当成“执行获批”。

领导最后把原接口的完整响应截图关掉：“我本来只想知道包裹在哪，差点把客户住哪也一起交代了。”小陈把新工具返回的六个必要字段摆在旁边：这次终于够用，也没有多送一套客户档案。

**领导：**还有个边界：客服在 16:00 获得本单权限，16:01 被移出班组，16:02 的查询已经发出，怎么算？

**小陈：**工具服务在真正执行读取时校验当前权限，不靠运行开始时的快照；如果权限已撤销，就拒绝并记录。若查询已完成而结果尚未送入模型，也应检查运行身份和工单归属是否仍有效，避免旧结果在新会话继续使用。严格程度按业务与系统能力设计，但“先授权一次，之后整晚随便查”肯定不行。工单转给新坐席时，新人通过正式交接取得权限，旧人不能凭旧链接继续看附件。

这种竞态要在测试里故意制造：授权检查后暂停请求、撤销工单权限，再继续执行；系统要么在同一可信事务或受控时间窗完成读取，要么重新校验，不能出现“检查的是旧状态，读取的是新对象”。权限测试只测静态角色，会漏掉换班、撤销和工单合并这些真实客服最常见的边界。

小陈把这项测试也写进接口验收单：任何一次权限撤销后的工具请求，都要有明确拒绝回执，并且不能在模型输入、缓存或报错日志里留下被拒订单的业务字段。
