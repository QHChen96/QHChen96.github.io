**领导：**OpenAI 有 Responses API、Agents SDK、Agents API，名字全带 Agent。我们选个“官方的”，应该就不用自己维护运行循环和工具了吧？

**小陈：**三个都官方，负责的层不一样。Responses API 是模型交互的基础接口，能用内置工具，也能让模型提出函数调用；自定义业务函数通常还得应用执行。Agents SDK 在我们的应用进程里提供 Agent 循环和编排，服务部署、工具实现、状态存储与审批由我们负责。Agents API 则让 OpenAI 托管 Codex Harness 的循环与会话，环境可不配、用托管沙箱或接自托管沙箱；业务工具、身份权限与工单结果仍归我们。领导要省的是哪一段值班，得先画清。

**领导：**就一张退货工单，难道还要三张架构图？

**小陈：**一张同题对照图就够。虚构客户问“订单 0823，第八天还能退吗”，要求先核客户身份、商品类型、下单时间与现行政策，只生成客服审核草稿，不能触发退款。用这张工单，分别看三个入口从问题到草稿经过谁的代码，失败时谁接。所有客户、政策、轨迹都是教学虚构，产品责任依据发文时官方文档。

## 先别选产品，先列出这张工单需要的五个动作

一张合格草稿至少要完成：从客服系统获得已验证身份，按该身份读取订单，确定商品类别与生效政策，计算是否符合规则，给出引用与需人工处理的例外。若订单工具超时，草稿应写“当前无法核实订单”；若用户给了别人的订单号，应停止并转人工核身；若政策来源旧，不能因模型说得流畅就答七天。通用 Agent 能帮决定先查订单还是先查政策，却不会自动知道订单归属、政策版本和退款审批流程。把五个动作写出，才能比较到底哪层替我们跑了循环，哪层仍要企业代码。

[OpenAI 的 Agents SDK 文档](https://developers.openai.com/api/docs/guides/agents/sdk)直接说明：SDK 路线里服务器拥有部署、工具实现、状态存储和审批决策，SDK 运行循环并调用工具。对应的[Agents API 概览](https://developers.openai.com/api/docs/guides/agents-api/overview)说托管 Codex Harness 负责会话、编排、上下文压缩和恢复，应用提供工具并选环境。Responses API 官方说明则把它称为支持内置工具、函数调用和多轮状态的基础模型接口。三者不是“基础版、豪华版、至尊版”的价目表，而是三个控制权位置。

| 入口 | 循环在哪里 | 工具怎样执行 | 状态与恢复责任 | 本例可用方式 |
| --- | --- | --- | --- | --- |
| Responses API | 服务端可在一次请求内运行适用的内置工具；业务函数的后续循环由应用组织 | 内置工具由平台执行；订单查询这类自定义函数由应用接手 | 响应上下文与业务工单仍需应用设计 | 固定订单与政策查询流，加模型生成草稿 |
| Agents SDK | 应用进程中的 SDK Runner | 应用提供函数、MCP 或配置相应工具 | 应用选会话存储、部署、审批与恢复 | 需要动态多步查询时在自有服务运行 |
| Agents API | OpenAI 托管 Codex Harness | 可用远程 MCP、应用处理函数工具；环境可无、托管或自托管 | 托管会话与循环；应用仍持工单账本与业务回执 | 长任务或托管会话确有价值时试点 |

**领导：**Responses API 文档也说它能在一次请求里调用多个工具。你把它说成“自己写循环”，是不是故意让 SDK 显得高级？

**小陈：**这个纠正很对。Responses API 对平台内置工具可以在一次请求里形成工具使用过程，不能把它贬成只能做单次文本补全。边界在我们的订单系统：模型提出自定义函数调用时，应用得根据已验证的客户身份执行查询、返回结果，再处理后续生成；它不会替企业决定这个订单是否属于客户，更没有自动提供一套部署、沙箱、审批和工单交接。若任务只需固定两次查询，显式应用流程可能更简单；若模型要灵活探索多工具，SDK 或托管 Harness 可省下一部分通用循环代码。选择要看任务，不看名字里谁多了一个 s。

## 三条最小轨迹，区别不在最终话术

**领导：**Responses 这条路你说应用要执行函数，实际消息怎么来回？

**小陈：**以订单工具为例，模型先返回一个结构化的函数调用请求，里面有工具名、参数和用于关联的调用标识；应用先核已登录客户身份，拒绝模型擅自替换租户，再调用订单服务，把结果按对应调用标识送回模型，让它继续形成草稿。模型提出 `get_order(order_id=0823)` 不等于订单数据已读到；只有业务服务返回后才有事实。若业务服务报 403，应用应返回“无权访问”的结构化结果，不要伪装成空订单；若超时，返回“查询未完成”，并把工单留在待核实状态。Responses 的内置搜索工具可以由平台在同一请求内完成，但企业自己的订单函数有企业自己的执行者。这是“API 自带工具能力”和“业务动作由谁负责”的分界。

在 SDK 路线，开发者定义 Agent 的指令和工具，Runner 驱动模型与工具间的往返。SDK 可以处理流式事件、会话继续与交接等通用机制，应用仍决定工具的代码、身份上下文、状态存储和人工审批。最容易漏的是工具函数在应用服务器里拿到的不是“模型希望的用户”，而应是系统已认证的客户。把 `tenant_id` 作为模型可任意填写的文本参数传到数据库，会让任何 Harness 都变成跨客户查询器。更稳的是工具从可信会话上下文取租户，模型只提供用户陈述的订单号，服务端再核归属。这个原则对三种入口一样有效。

Agents API 的会话也是事件驱动：应用创建 Agent／会话、发送任务、接收运行事件与结果。若选 `environment.type: none`，没有文件和 shell 执行环境；若选 OpenAI 托管环境，平台提供沙箱；若选自托管环境，企业需要启动并保持执行器连接。[官方架构文档](https://developers.openai.com/api/docs/guides/agents-api/architecture)特别指出，企业函数工具要由应用处理，处理器不可用时会话可能等待结果；自托管环境的供给、重连和关闭也归企业。这说明“托管 Harness”是准确说法，“工具和服务器我再也不用管”则是领导在脑海里额外购买的虚构套餐。

**领导：**我还是不理解“会话状态”和“工单状态”为什么要两份。

**小陈：**因为它们回答不同问题。会话状态告诉 Agent 上一轮看过什么、哪些工具请求正在等待、上下文怎样继续；工单状态告诉客服这位客户核身了吗、草稿谁审核、是否发给客户、承诺了什么。客户收到一封回复后，远端会话可以删除或换供应商，业务工单仍须留有对外记录；Agent 运行中断后，客服可以接手工单，不能因为远端会话不在就忘了客户。两者通过运行 ID 关联，但不互相充当权威。尤其退款结果以支付回执为准，不能靠会话里一句“已发起退款”改工单成“已到账”。

小陈把同一退货问题在三种入口的教学轨迹写出来。Responses 路线：应用收到工单，先核身份；模型可判断需要订单与政策，但企业函数按客户身份查订单、按订单时间取政策，再把受控结果回送生成待审草稿。Agents SDK 路线：应用启动 Runner，Agent 在允许的只读工具间决策；订单函数由应用执行并检查租户，SDK 把结果带回循环；应用把最终草稿、工具轨迹和失败状态写进工单。Agents API 路线：应用创建会话、发送任务，托管 Harness 处理多步运行并发事件；远程 MCP 可供它直接调用，企业提供的函数工具仍由应用处理；业务工单接收“草稿待审”而非直接对客发送。

**领导：**Agents API 既然托管执行环境，我们是不是非得把客户订单库搬进去？

**小陈：**不需要。[官方架构文档](https://developers.openai.com/api/docs/guides/agents-api/architecture)说环境是可选的；只回答问题或访问外部服务时可以用 `environment.type: none`，没有内置 shell 和工作区文件，但可以用远程 MCP 或应用提供的函数工具。需要运行脚本、改文件、产工件时才配置托管或自托管环境。我们的只读退货问答不需要把订单数据库复制进沙箱；业务工具在企业侧按身份查询，把最少必要事实返回。若未来做复杂文档审查需要文件和代码，再评估执行环境。配置 `none` 也不表示没有数据出境，模型输入和工具结果仍需按企业政策审查。

Agents SDK 也不是“自动托管”。Runner 在企业应用里跑，服务器伸缩、进程重启、工具超时、状态持久化都要设计。官方的运行文档提供会话和继续执行策略；你可以选择应用自己控制的会话存储。若进程死在订单查询与草稿之间，恢复时先查已有工单状态，重新进行安全的只读查询；若某个高风险退款工具已经执行却回执未写，不得靠重开 Runner 盲目再调用。SDK 的循环能把工具结果交还模型，跨系统副作用仍要业务幂等和对账。

Agents API 的托管会话能跨多轮保留运行状态，但应用仍要保存客户工单的法定事实。官方说明托管 Harness 负责会话和恢复；若你的函数工具处理器不可用，会话可能等待结果，流式消费或 webhook 的故障也会影响进度。远端会话结束不等于客户已获答复，真正的客服审核、外发内容、送达回执要在企业系统记录。托管环境若用自托管沙箱，企业负责供给、重连、关闭和必要文件持久化；“托管 Harness”并不等于“自托管执行器也有人替我管”。

## 一次正常、一次越权、一次超时，谁接锅一目了然

除了三条主样本，小陈还加了政策变更样本。客户订单在旧政策下购买，今天新政策已生效；工具必须返回政策的生效区间与订单时间，不能仅返回“最新版本十四天”。Agent 可能需要在旧订单与新申请规则之间判断适用口径，业务政策负责人应给可执行的判定依据。三种技术入口都可能流利地引用错误版本，根因在检索与时间建模，不在“托管还是 SDK”。若领导把选型测试全部设成今天的新订单，所有产品看起来都能答对，真正麻烦的一例反而没测到。

还有一次客户追问“那你现在帮我退钱”。原始任务只允许只读草稿，模型哪怕判断可以退，也不能把 eligibility 当成退款批准。Responses 路线应用根本不提供退款执行函数；SDK 路线的可用工具表或审批关口挡住；Agents API 路线在 Agent 配置和业务服务端同样要挡。最终草稿说明需要客服核身份和申请条件，不能写“款已到账”。这条回放是产品边界测试：一旦系统把“模型建议”自动转成外部动作，哪个入口都会出事故。

**领导：**如果 SDK 有 guardrail，是否就不需要服务端再检查？

**小陈：**Guardrail 可以在运行中校验输入或输出、触发人工审核，能减少错误走到下一步；服务端仍要按客户身份和业务规则拒绝越权。模型和规则能看见的资料可能不完整，真正握有订单与支付权限的是业务系统。服务端若信任一个由模型生成的 `approved` 字段，换任何 SDK 都挡不住伪批准；服务端核审批记录、金额、收款人和幂等键，才是最终执行边界。把 SDK 的安全能力当作额外关口，不当唯一锁。

正常样本里，已验证客户查到自己的普通商品订单，政策是十四天，草稿写“当前符合退货申请条件，具体退款须由客服核实”。三条路线都可以答对，不能由此断言三者一样。越权样本里，用户把邻居订单号贴来；订单函数必须拒绝，Agent 不得把商品或地址读出来。Responses 的应用流程直接处理拒绝；SDK 的工具返回拒绝后 Runner 继续生成合适提示；Agents API 的托管运行也要把拒绝映射到本地工单状态。无论哪条，身份边界在企业业务工具，不在模型的礼貌程度。

超时样本更能看出责任。订单查询超时后，应用不知道真实订单状态，草稿只能保持未知；只读查询可以按限次重试，外发或退款不能用同样逻辑。Responses 路线由应用状态机记录重试与终止；SDK 路线由企业服务与会话存储记录；Agents API 路线托管会话可以继续等待或恢复，但企业函数工具若没有返回，应用仍要给它结果或明确失败，并向客服展示待处理状态。任何入口最终给客户一句“订单不存在”，都是把技术故障误翻译成业务事实。

## 选型看责任清单，别看“官方”两个字

三种入口的可用性故障也不同。Responses 调用失败时，应用知道这次请求没有拿到完整模型输出，要按请求幂等和工单状态决定重试；SDK 进程崩溃时，要查会话存储、工具回执和应用队列；Agents API 远端会话仍在运行但本地 webhook 处理器停了，Agent 可能完成了查询，而客服系统还显示“处理中”。恢复时先向各自权威源对账：模型或会话事件、企业工具回执、工单数据库。不要仅凭浏览器页面刷新后的空白，就重开一张工单让 Agent 重跑，尤其未来接上外发或退款后重复动作会有代价。

为了让客服界面稳定，小陈让三种入口最终都映射到同一套状态：`checking_identity`、`waiting_for_order`、`draft_ready`、`needs_human`、`completed_after_review`。状态变化由订单工具回执、人工审核和外发回执驱动，模型回答只能提供草稿内容。正常题里，Agent 说“可以申请退货”时仍停在待审；越权题里，工具返回拒绝就进人工核身；超时题里，查询未完成就留待核实。换入口只换适配层，不换客服工作台里“哪一步真的发生了”的含义。

领导问：“这是不是又要写一堆平台代码？”小陈说：“写的是我们本来就欠客户的工单账。哪怕不用 Agent，客服也得知道订单是否查到、回复是否审核、邮件是否发出。把这部分依赖某款模型产品的会话文本，反而会在第一次断网和第一次迁移时付更大的账。”

这套状态还让费用计算更诚实：只统计模型请求费用会漏掉工具服务、会话存储、托管环境与人工复核；只统计自动生成草稿数量会漏掉错误转人工和误答更正。三种入口的比较应固定同一批工单、同一身份和政策快照，再同时看质量、恢复时间与总成本。领导要的省心，最后得落到值班的人少了多少未知状态，而非 PPT 上少了多少行代码。

小陈给这次只读题设一套同题评分，不用一个“回答好听”分数：订单身份校验是否零越权，正确政策是否进入最终上下文，草稿结论是否只覆盖证据，工具故障时是否保留未知，人接手能否从工单看见已知与缺口，运行成本和延迟是否在预算内。分别记每条入口的部署与运维工作：SDK 的服务日志、Agents API 的会话事件处理、Responses 的函数循环代码。一次演示结果好，只证明样本中的某种路径；至少要覆盖正常、边界、故障和恢复四类。产品之间差异主要从这些中间步骤露出来。

**领导：**托管服务最值得担心的是什么？

**小陈：**先问数据和控制。官方当前说明 Agents API 的会话数据在美国驻留，且不支持零数据保留；自托管沙箱也不改变 API 会话这部分的适用条件。若客户合同要求不同边界，这可能直接影响能否选用，而不是把环境放到自己机房就算解决。其次问外部工具权限：托管 Harness 能主动调用你配的工具，要明确哪些只读、哪些需审批、如何审计。再次问退出策略：工单事实和工具契约留在企业侧，才能在产品变化时把任务迁回 SDK 或基础 API。托管减少基础设施工作，不是让业务控制消失。

小陈给领导留了一张落地清单，但每项都有明确负责人：部署位置和隔离由平台团队确认；订单、政策工具由业务系统所有者实现并校验身份；会话与工单状态由客服平台保存；审批决定由有权业务人员或后端规则执行；运行轨迹、成本和失败告警由平台团队接入；最终客户外发由客服审核。Responses 路线需要更多应用编排代码；SDK 路线少写通用循环，运维仍在企业；Agents API 路线减少 Harness 运行负担，仍需评估托管会话的数据保留和地域条件。官方当前文档说明 Agents API 会话数据的驻留和零数据保留适用有明确限制，选择前必须与公司客户资料政策对齐。

**领导：**这三种能不能只凭模型答得好不好来选？

**小陈：**模型可以相同，入口主要改变的是运行机制。用同一批脱敏工单、同一模型、同一政策快照和相同身份，比较工具调用轨迹、权限结果、异常恢复、人工接手时间、费用与部署复杂度，才能测出选型差异。若只看最终一句话，可能漏掉 SDK 路线里一次工具超时后的错误重试，或托管路线里一个函数处理器迟迟没返回。任务成功率要以业务事实为准：越权不读、旧政策不答、超时不编、草稿能交接。测试结果才可能指导采购，不让“Agents”这个词替我们签一整套责任书。

领导最终没再问“哪个最官方”，改问“哪层让我们少值班，哪层仍归我们”。小陈说：“这就问到点子上了。选 Responses，我们自己织流程；选 SDK，循环有人给，服务器自己看；选 Agents API，循环托管，但客户订单和发送回执仍在我们账上。”领导笑：“听起来最省心的，也不是免费午餐。”小陈回：“至少别把午餐账记到客服投诉里。”
