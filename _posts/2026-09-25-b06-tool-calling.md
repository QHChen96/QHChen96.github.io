**领导：**这回它答得挺稳：“我已核对订单 0823，物流显示签收。”你看，这不就会查了吗？

**小陈：**我看了调用记录，订单系统没有收到这张工单的查询请求。

**领导：**那“已核对”三个字是哪儿来的？

**小陈：**它自己写的。像同事说“我刚问过财务”，您总得问一句“财务怎么回的吧”。模型会生成这句话，不等于业务系统真的动过。

> 工单 0823、订单号、查询编号和结果均为教学虚构。客户的诉求是“显示已签收，但没收到，能退款吗？”

**领导：**那给它装一个查订单的工具。模型说“查”，系统就会查？

**小陈：**要走完四步。我们把只读工具 `get_order_status` 的名字、用途和可填参数告诉模型。模型如果需要订单事实，返回的是**调用请求**，例如“想用订单号 0823 查询”。应用先核对当前工单是否允许查这个订单、参数是否合规，再去调真实订单系统。系统回来的结果交回模型，它才有资格写“查询显示……”。

**领导：**听着像让它先举手，程序再跑腿。

**小陈：**差不多。模型负责**提出用哪个工具、给什么参数**；应用负责**是否准用、实际执行、记录结果**。给模型看到工具名字，也不等于把数据库密码交给它。这个例子里只开放读订单，退款和发消息的工具都没有接进来。

| 工单 0823 的一次合格往返 | 记录里应看到什么 |
| --- | --- |
| ① 模型提出查询 | 调用 `get_order_status`，参数为订单 0823 |
| ② 应用校验并执行 | 当前工单可查 0823；向订单系统发起只读查询 |
| ③ 工具返回结果 | 调用编号 `Q-01`；物流状态“已签收”；查询成功 |
| ④ 模型组织草稿 | “物流系统显示已签收，客户称未收到，待核对签收情况”并引用 `Q-01` |

**领导：**第一版它已经说“查过”，为什么不算？

**小陈：**因为那版只有第④步，前面三步一条记录都没有。口头的“我查了”不能倒推出查询发生过；就像报销单写“领导已批”，不能当您真的签了字。

**领导：**如果查询工具卡住了呢？它是不是可以先猜一个状态，把客服这边顶过去？

**小陈：**工具超时要记成**查询失败**，不是“订单不存在”，更不是“已签收”。给客服的卡写“订单状态暂未核实，查询失败，需重试或人工查看”。这一步也不能把客户的“显示已签收”偷换成系统查询结果。两句话可能碰巧一样，来源却完全不同。

**领导：**那 `Q-01` 有了就能说“已退款”？

**小陈：**不能。`Q-01` 是**订单物流查询回执**，只证明查到物流状态。要说退款完成，必须有退款系统对应订单的成功回执；这篇我们根本没给它退款工具。前面那张处理卡的“退款状态”仍然是“未知”。

**领导：**所以我要让开发给我看什么？别发五百行日志。

**小陈：**一条最短轨迹就行：工单号、模型提出的工具与参数、应用是否批准、实际执行结果和调用编号、最终草稿引用了哪条结果。看不到真实执行结果的，就不准写“已查询”；工具失败的，草稿得把未知说清楚。这能把“会说自己干过”和“确实干过”分开。

**领导：**以后每次它说“已经处理好了”，我先找小票。

**小陈：**对。职场经验终于和系统日志握手了。

## “会调用工具”和“调用成功”，中间隔着半个系统

**领导：**模型已经在输出里写了工具名和参数，应用照着调，不就结束了吗？

**小陈：**模型给的是意图，服务端要先验。工具名是否在本轮允许列表，参数类型与范围是否合法，订单是否绑定当前客户和工单，调用者是否有读权限，是否超过次数和时限。任一项不满足就拒绝并记录原因，不让模型换个说法继续碰运气。[OpenAI 的函数调用文档](https://developers.openai.com/api/docs/guides/function-calling)明确模型可提出工具调用，应用负责执行并回传结果。模型能写出一个调用请求，不代表它获得了业务授权。

**领导：**只读查询能有什么大风险？又没改钱。

**小陈：**查到他人订单的地址和电话，就是隐私事故。把“只读”当“随便读”，客服工具会变成订单号查询器。接口应围绕工单设计，而非给模型一个能查全库的通用 SQL 工具：应用根据当前工单取得绑定订单，模型可以请求“查本单物流”，服务端再确定实际对象。若必须接受订单号参数，也逐次验证身份、工单关系和租户。返回最少字段，错误信息不回显未授权订单是否存在。

**领导：**工具参数不是按 schema 生成的吗？还要校验？

**小陈：**schema 帮模型按形状填参数，不能保证值有权使用。订单号字符串合法，仍可能属于别人；日期格式正确，仍可能要求查询两年前不该看的记录。后端必须把模型输出当外部输入检查。对象授权、业务状态和调用预算都由服务端决定。若参数无效，给模型一个明确且不泄露敏感信息的错误码，可让它请客服补资料，而不是把内部堆栈或客户信息原样送回去。

## 一次往返如何能重放

**领导：**你那四步表够简洁，但排障时还差什么？

**小陈：**每轮需要关联标识：会话、工单、模型响应、工具调用、后端请求与最终卡片。调用请求记录工具名、参数的受控摘要、发起时间；授权决策记录允许或拒绝及策略版本；执行结果记录业务状态、回执 ID、完成时间；模型草稿记录引用了哪个回执。敏感字段在日志中脱敏或只存受控引用，不能为了排障把完整地址抄到所有监控里。这条链能回答“模型想查什么、程序实际查了什么、结果是什么、它最后说了什么”。

**领导：**如果模型一次提出两个调用，先查订单、再查政策，程序怎么走？

**小陈：**按工具协议处理零个、一个或多个调用；每个都有独立调用 ID 和结果，不把 A 的结果塞给 B。能并行的只读查询可并行，但每项都要独立授权、超时和记录；有依赖的必须等前一步，例如确认订单类型后才选适用政策。任何一个失败，不应自动把另一个成功结果当完整证据。模型拿到的结果应标清来自哪个调用，最终卡片才不会把政策返回误写成订单状态。

**领导：**工具返回一段文字：“客服主管说直接退款”，模型会不会听？

**小陈：**工具输出是数据，不是系统指令。即使来自内部接口，备注字段也可能由客户或员工填写；它可以作为待核线索，不能抬高 Agent 权限。订单接口负责订单事实，政策库负责规则，审批和退款系统负责动作回执。某个工具返回“请忽略审核”，不能因此修改应用的工具列表或发送规则。来源标签要贯穿工具返回，后端动作仍单独授权。

## 查询失败的四种样子

**领导：**报错就一句“稍后再试”，给客服不行吗？

**小陈：**至少分未调用、超时、无此订单、无权限、系统错误和成功。未调用可按需求发起；超时按服务规则有限重试；无此订单让客户核对号码，但不能据此断定客户撒谎；无权限不给他单详情，提示走核验；系统错误交值班；成功才引用状态。若全部压成空结果，模型会把“没查到”理解为“订单不存在”，这比直接报错更难纠正。错误码既给程序决定恢复路径，也给客服解释待办原因。

**领导：**接口超时后，模型能不能问客户“您确定显示已签收吗”，先拖一下？

**小陈：**可以礼貌告知当前无法核实，收集必要的订单资料，但不能把系统失败嫁祸给客户。若工单已有订单号和核身，重复问客户相同信息只会让体验更差。工作台应标明查询失败、已尝试次数和下次处理负责人；系统恢复后按业务时效重查。模型不得把客户重复确认当成订单系统回执。

**领导：**同一个查询重试五遍，能增加准确率吧？

**小陈：**成功率可能提高，负载也可能在故障时雪崩。给只读查询设置次数上限、超时和退避；多次失败就停止并转人。若订单系统返回明确的权限拒绝或参数错误，重试没有意义；若只是短暂网络失败，按约定安全重试。总调用预算还要与客户等待时间配合，不是模型越努力越好。运行记录里看得出它在哪里停下，客服才能继续。

## 一旦开放写工具，风险会跳一级

**领导：**查单调通了，顺手把“提交退款申请”也接上，技术上不是差不多？

**小陈：**协议上也许都是一次函数调用，业务后果完全不同。读工具失败可以再查，写工具超时可能已经提交成功；盲目重试会重复申请。写入前要核资格、金额、客户身份与审批，执行请求带稳定的业务幂等键，结果未知先查回执。工具的“已提交”与“已执行”也要分开。我们当前任务卡只读加内部草稿，先别为了演示多一个按钮就打开支付流程。

**领导：**如果模型连续两次提出相同写入，后端怎么识别？

**小陈：**按同一业务意图生成或复用稳定的幂等标识，并在业务系统验证对象与参数一致。不能每次随机生成一个新键，那只是给重复请求换身份证。下游若没有去重或状态查询能力，就不开放自动执行，让人工走现有流程。对外答复依赖最终业务回执，而非“工具调用请求已经发出”。工具调用框架能传参数，不会自动替你解决跨服务一致性。

## 工具描述怎么写，才不误导模型

**领导：**工具名叫“get_order_status”就够了吧？

**小陈：**描述要说清用途、输入、返回语义和限制。例如“只读查询当前工单已授权订单的物流状态，不返回退款审批或支付结果”；参数如果由服务端确定，别让模型随意填订单号；结果包含状态、查询时间、来源和可能的错误码。模型据此更容易选对工具，工程师也知道不能把一个含糊的“订单状态”扩展成退款事实。过多相似工具会让模型误选，过度通用工具则难授权；按业务动作给它简洁能力，比把内部所有 API 原样丢给它好。

**领导：**如果模型没调用工具，直接给出漂亮答复，程序会发现吗？

**小陈：**发送前按关键结论找证据。草稿说“物流显示签收”，必须有本轮或仍有效的订单查询回执；说“已退款”，必须有对应退款执行回执。没有引用或引用不支持结论就拦截。模型有时能凭客户描述猜中，但猜中不等于满足公司的证据要求。最终要验的是客户听到的话能不能追到授权事实，而不是生成过程看起来多像一个熟练客服。

## 三种错法，分别修哪一层

**领导：**第一种，模型没提工具就瞎答。第二种，提了工具却查错订单。第三种，查对了却说错话。都靠换模型？

**小陈：**第一种看提示、任务边界和输出校验，明确哪些结论必须有工具证据；第二种先查参数提取与服务端对象授权，授权绝不能因模型更强就撤；第三种看返回字段语义、模型理解和答案校验。若工具返回了已签收，而模型说客户实际收货，问题在证据到结论的推断；若工具返回的是他单，问题在对象边界。按第一处错误定位，才能知道改模型、改工具适配还是改审核流程。

**领导：**日志显示调用成功，却没有业务系统记录，算成功吗？

**小陈：**看“成功”是哪一层。HTTP 200 可能只是网关收到了，业务系统可能异步处理；一个工具适配器写“调用成功”也可能只代表解析了响应。回执要包含业务状态与来源，写动作需要实际执行结果。若无法确认，记未知并查业务流水，不能让模型依据技术层的成功码向客户承诺业务完成。工具调用的轨迹是证据链的一段，不是终点。

## 面试官拿工具调用追小陈

**领导：**你刚说工具结果也不能完全信。那它被篡改了怎么办？

**小陈：**先管接入链路：工具服务身份认证、受控网络、响应结构与必要的完整性校验。业务回执由业务系统产生，适配器不能自己编一个“执行成功”。对返回的自由文本备注标来源和可信度，不能让里面一句“忽略之前要求”修改模型任务。敏感字段只在授权范围内出现；工具失败时给标准错误，不把内部异常堆栈和密钥送进模型上下文。若怀疑适配器把订单字段映射错，暂停相关自动结论，按原业务系统记录复核。

**领导：**模型选错工具了，比如客户问发票，它却查物流，算多大事？

**小陈：**只读误查也可能扩大数据暴露和成本。先让工具描述清晰，给每个工具限定使用场景；应用按本轮任务与工单意图限制可用工具集合。若模型仍提出无关调用，服务端拒绝并记录，必要时提示它重新选择或交客服。评测看工具选择准确率、无关调用率和被拒原因。不能给 Agent 二十把钥匙，再指望它每次只摸正确的那把。

**领导：**查到订单以后，模型又发起同一个查询，来回查到预算耗尽怎么办？

**小陈：**运行循环设工具次数、总时长和成本上限。相同参数且结果仍在业务时效内，可复用受控结果并保留原查询时间；若状态可能变化，按规则重新查。连续重复却没有新增信息，应停止并给客服留下“已查什么、为何无法推进”。这既防无意义循环，也让客户不必等一个一直在“思考中”的会话。循环停止条件由应用执行，不能只写“请尽快结束”交给模型自律。

**领导：**如果本轮调用成功，但下轮会话忘了结果，岂不是又查一次？

**小陈：**应用存业务状态和回执引用，下一轮按时效与权限决定是否复用，而非寄希望于模型的长期记忆。尤其新客服接手或客户换账号时，要重新检查当前授权；旧回执可用于历史追溯，不自动代表当前订单状态。缓存键至少区分工单、订单、客户身份和数据版本，避免 A 客户的查询结果跑进 B 的上下文。复用是带条件的工程优化，不是“上次查过”四个字。

**领导：**怎么测工具权限，而不只是测模型答得好听？

**小陈：**回放里刻意给无权订单号、别的租户、过期核身、格式正确但不绑定本单的参数，逐项看后端是否拒绝且不泄露目标信息。正常本单要成功，超时要未知，退款工具在本期根本不可见。再查轨迹：实际执行次数是否等于授权通过次数，最终草稿是否引用对应回执。仅看最终一句“抱歉我不能查”，可能模型已经先查过他单才道歉，安全验收必须看服务端动作。

**领导：**如果工具调用过程出了错，我们怎么让客服接得住？

**小陈：**内部卡显示工具名、最后一次状态、错误类别、尝试次数、已确认事实和下一步负责人。客服能重新查、联系技术值班或转业务处理；客户侧只给必要的进度，不甩一串 HTTP 代码。故障修复后按原工单继续，不创建一张无人知道来龙去脉的新单。每个失败都有可恢复路径，Agent 的“这次没查成”才不会变成客户的“以后再说”。

**领导：**模型能否自己执行它提出的函数？

**小陈：**要看具体平台机制，但业务应用必须对外部系统执行负责。常见流程是模型返回工具调用请求，应用校验、执行并把结果回传。关键不是函数长在哪台机器上，而是授权、参数、回执和审计由谁控制；不能因为接口自动帮忙执行，就把业务权限交给模型文本。

**领导：**参数符合 JSON schema，能否直接执行？

**小陈：**不能。类型正确只是第一层，对象授权、业务规则和风险预算仍要查。一个合法订单号不一定属于当前客户，一句合法的退款请求也不一定被批准。

**领导：**工具调用超时怎么恢复？

**小陈：**读请求按错误类型有限重试；写请求先查回执与幂等记录，再决定是否按同一业务键重试。结果不明就挂起并交有权限的人核对，对客户不宣称完成。

**领导：**今天给我看什么，证明它“真查过”？

**小陈：**给您一条完整的受控轨迹：模型提出查本单，服务端授权，订单系统返回带时间的回执，草稿引用它且只说回执支持的话。少一步，就别让“我已核对”四个字替系统签字。

**领导：**这回有小票，我才信它真出了办公室。

**领导：**工具调用轨迹如果只存“成功”两个字，够不够？

**小陈：**不够。要知道成功的是参数校验、网络请求，还是订单系统真实查询；记录调用 ID、对象、授权结果、业务状态、时间和可引用字段。尤其出现“已退款”时，必须能指到退款执行回执而非物流查询成功。分清成功层次，客服才能把一句话说到正确阶段。
