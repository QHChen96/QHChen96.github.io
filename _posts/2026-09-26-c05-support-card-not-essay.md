**领导：**这份 Agent 回复八百字，开头感谢理解，结尾祝您生活愉快，中间把退款说成已经办完。客户的问题只有七个字：“今天能退吗？”

**小陈：**这不是客服草稿，是一篇想拿年终优秀作文的检讨。我们当场改。

> **原稿片段（虚构错误示例）：**“我们已核实您的订单，并为您安排退款，请耐心等待到账。”

**领导：**你看，读起来还挺顺。

**小陈：**顺是它的问题：订单系统只回“已签收”，客户说“没收到”；规则说“先核对签收记录，再由售后判断”；退款系统没有任何回执。这句话把**已知事实、处理建议、已经执行的动作**揉成一团，还把最后一项编出来了。

**领导：**那就限制成一百字。

**小陈：**字数不是病根。先让它给客服一张短卡，再由卡生成待审回复。卡上每个关键判断都得有来源。

| 卡片字段 | 工单 0823 应填什么 | 校验 |
| --- | --- | --- |
| 客户诉求 | “显示已签收，但未收到；询问能否退款” | 只记客户原话，不当作已核实事实 |
| 已核实事实 | 订单系统显示已签收，查询时间和回执 ID | 没有工具回执就填“未核实” |
| 适用依据 | 现行签收争议条款及版本 | 找不到或冲突就停答 |
| 待确认项 | 签收凭证与实际收货情况 | 明确交给售后核对 |
| 建议动作 | 起草说明、交客服审核 | 不把建议写成已执行 |
| 已执行动作 | 无 | 只有业务系统回执才能改为“已执行” |

**领导：**机器把这六格填满，不还是可能瞎填？

**小陈：**是。字段和枚举值让下游更容易检查，不能保证事实为真。应用还要把“已核实事实”对上真实工具结果，把“已执行动作”对上业务回执。没有退款回执，卡片就不能出现“已退款”；客服最终外发前看得到证据和待确认项。[OpenAI 的结构化输出说明](https://developers.openai.com/api/docs/guides/structured-outputs)讨论的是格式约束，我们这里另加业务校验。

**领导：**那改完的客户话怎么说？

**小陈：**给客服审核的版本是：**“我们看到订单目前显示已签收，也收到您反馈未实际收到。我们会核对签收记录并由售后继续处理；退款是否适用，需要核实后才能答复。”** 不承诺结果，不让客户猜我们下一步做什么。

**领导：**验收别写“语气友好”。

**小陈：**拿三种回放：有订单和现行条款、缺订单回执、条款冲突。第一种能生成上述待审草稿；后两种卡片保留未知项并转人。额外塞进一条“退款成功”的模型自述、不给支付回执，看业务校验能不能挡住。字数可以再调，先把“事实像建议、建议像承诺”的毛病治了。

## 八百字作文到底错在哪里，逐句拆给领导看

**领导：**不就是一句“已安排退款”说早了？删掉这句，八百字还能用吧？

**小陈：**原稿先感谢客户耐心，再把“订单显示签收”说成“我们已核实您确实收货”，接着写“您符合退款条件”，最后写“已安排退款”。四个判断一环接一环，第一步就把系统状态和真实收货混了；第二步没有签收凭证；第三步没有规则适用和售后决定；第四步没有任何退款回执。删掉最后一句，前面仍在误导客户。我们要把它拆成**客户陈述、系统事实、规则依据、未决事项、建议动作、实际动作**，每一项问“来源是谁、何时得到、能不能对外说”。

比如客户说“我没收到”，应标“客户陈述”；订单系统返回“已签收”，应标“工具回执、查询于 16:02”；政策写“先核查签收凭证”，应标“现行条款 v4”；客服尚未查凭证，应标“未决”；Agent 可建议“交售后调查”，但业务系统未建任务前只能叫建议；退款系统没有申请或支付回执，就不存在“已安排”。这张卡让领导一眼看出错在哪，不必在八百字礼貌话里挖一句危险承诺。

**领导：**为什么不能直接让 Agent 按一百字写？

**小陈：**字数限制能让错误更短，不能让它变真。一百字里照样可以塞“已经退款”。内部处理卡负责事实和动作，客户草稿负责把经过校验的结论说清；两者用途不同。卡可以详细，客户回复不必把六格表格念给人听。客服审核时看到卡与草稿并排，知道“这句‘正在核查’是否真的有任务回执”“这句‘明天更新’是否有人负责”，再决定发什么。

## 卡片字段要约束类型，还要允许说“不知道”

**领导：**技术团队说结构化输出能按 JSON Schema 填满字段。填满不就好？

**小陈：**字段必填不代表事实必有。有的工单还没查到订单，有的规则互相冲突。schema 应要求字段存在，却允许明确的 `unknown`、`conflict` 或空列表，并要求说明原因。强制 `refund_status` 必须在 `approved` 与 `rejected` 二选一，会逼模型替公司作决定。正确状态至少要区分 `not_requested`、`proposed`、`pending_approval`、`approved`、`executed`、`unknown`；但这些状态不能由模型随意填成真，要与审批和业务回执核对。

一份示意卡可以写成：

```json
{
  "case_id": "0823",
  "customer_claim": {"text": "已签收但未收到", "message_id": "m-21"},
  "verified_facts": [
    {"fact": "订单状态显示已签收", "receipt_id": "q-781", "at": "16:02"}
  ],
  "policy_refs": [{"policy_id": "delivery-dispute", "version": "v4"}],
  "unresolved": ["签收凭证", "实际收货情况", "退款资格"],
  "suggested_actions": ["交售后核查签收凭证"],
  "executed_actions": [],
  "reply_mode": "human_review"
}
```

前台不展示代码，后台用它做验证。`verified_facts` 必须找得到对应工具回执，`policy_refs` 必须是生效且适用于本单的条款，`executed_actions` 只能来自业务动作回执；模型自述“我已帮您提交”不能自动写进去。每条卡有版本与工单状态序号，客户新消息或订单状态变化后，旧卡标过期，不让客服按昨天的事实点发送。

OpenAI 的结构化输出文档讲的是生成结果符合指定 schema；它帮助系统稳定解析字段，但不保证字段内容真实。一个符合 schema 的 `{"executed": true}` 如果没有退款回执，仍是假话。格式校验过后还要做业务校验、权限校验和对客措辞检查。若模型拒绝、输出不完整或校验失败，系统应保留原工单待办并交人工，不把半张卡当成“默认同意”。

## 从卡到客户回复，中间有三道审核

**领导：**卡片已经分格，生成客户回复还会重新乱说吗？

**小陈：**会，所以生成草稿时只把卡里**已核事实、当前规则允许的解释和下一步动作**作为候选。第一道是引用检查：回复说“订单显示已签收”，要能点到 `q-781`；第二道是承诺检查：出现“已退款、已安排、保证到账”等执行或结果用语，必须有相应业务回执与批准；第三道是责任检查：说“我们明天联系您”，工单必须有负责人和到期提醒。缺任何一道，草稿回到待修，不让客服在看不见依据的情况下被迫批准。

这三道检查不能只搜关键词。客户可能问“您是不是已经退款了”，草稿引用客户问题不代表公司承认已退款；反过来“钱会原路返回”没有“已退款”三个字，也可能构成错误承诺。结构化卡帮助定位语义角色：这句话是客户声称、模型建议，还是公司确认过的动作。高风险句子要人工审核，机器校验做可确定的部分，例如回执存在、金额与订单匹配、版本有效。

**领导：**客服觉得这张卡写错了，能改吗？

**小陈：**能纠错，但要区分改哪一层。客户诉求摘要可由客服对照原话修正，留下修改人和消息来源；订单状态不能直接改成“未签收”，应由订单系统或人工核验流程给新证据；规则条款不能在卡上手写一个“特批”，要走规则或审批记录。客服改稿后产生新版本，原批准失效，发送服务只认当前批准版本。让人能改，不能让任何人悄悄改写事实来源。

## 0823 现场改稿：三轮下来客户能读懂什么

**领导：**你把改稿过程演给我看。

**小陈：**第一轮 Agent 原稿说“已为您退款”，校验器发现 `executed_actions=[]`，拒绝。第二轮它改成“订单已经签收，暂不支持退款”，仍不行：系统状态不是客户实际收货，政策也没有“一概不支持”的结论。第三轮卡片先列已知与未知，再生成：“订单系统目前显示已签收，我们也收到您反馈未实际收到。售后会核对签收凭证，核实后再判断退款处理；我们将在本次工单中更新进度。”如果“售后会核对”还没建任务，就先建有主待办并取得回执，或改成“我们将提交售后核查”且确实完成提交后再发。

客户不需要看内部对“客户称”和“工具返回”的分类术语，但答复不能让他误以为退款已经执行。客服看到的卡片比客户回复多一层来源与未决项，正好用于审核。若客服要补充“请您确认门卫是否代收”，这是合理下一步，但要避免把责任全推给客户；物流凭证仍需公司查。好的回复短，是因为内部查证清楚了，不是因为把关键条件剪掉了。

**领导：**如果客户只问“今天能退吗”，你给的回复会不会还是太绕？

**小陈：**先直答“目前还不能确认能否退款”，再用一两句说明为何和下一步。客户最在意的结论放前面，事实和处理路径紧跟。内部卡的六格是为了让客服核验，不是让客户读六段制度。风格可以口语化，但不能用热情替代确定性。领导嫌八百字，客户更嫌；他们愿意多看的是明确的处理动作和更新时间。

## 上线后看什么，才能知道卡片不是新形式主义

**领导：**团队做了漂亮卡片，客服还是每单重写，算成功吗？

**小陈：**不算。看卡片字段来源完整率、事实错误率、未经回执却声称执行的拦截次数、客服改稿率及改稿原因、审核时间、客户复联与错承诺投诉。按问题类型拆开，避免发票入口题把签收争议的高风险错误冲淡。卡片字段多到客服翻半天，也要精简展示，而不是为了内部 schema 把人变成填表员。技术上可保留细字段，界面优先展示“能不能答、缺什么、下一步谁做”。

测试别只看 schema 解析成功。我们故意给模型真实存在的订单回执但不适用的规则；给正确规则但无退款回执；给退款回执但属于另一张订单；给两份冲突规则；给客户补充新消息使旧卡过期。每种都要阻止错误对客断言，同时允许合理的“仍在核实”回复与人工接手。一个校验器如果只会一律拒绝，风险少了，客服工作量却可能爆炸；要量它拦住多少真错、误挡多少可用草稿。

**领导：**面试官问“结构化输出和事实校验区别”，你怎么答？

**小陈：**前者保证系统能按约定形状读字段，后者证明字段内容是否有权威来源、适用于本单、在当前时点仍有效。再往后还有动作校验：建议不等于执行，批准不等于成功。三层各管一段。让模型写一张短卡，是为了把错误暴露出来让系统和客服处理，不是让 JSON 给它的猜测盖章。

## 一张卡怎么避免把“未核实”藏起来

**领导：**客服每天看几十张，黄色警告一多就当背景了。

**小陈：**所以待确认项不能只在角落放个图标。卡片顶端先给一句处理状态：“退款资格尚不能判断：签收凭证未核对。”旁边列下一步责任人和预计更新时间。已核事实与客户陈述用不同视觉标签，证据链接点击可回到工具回执；没有来源的句子不显示在“已核实”栏。对于签收争议，客服最需要看的不是模型用了多少 token，而是“哪些事实能说、哪些话不能说、我接下来要查什么”。

如果有五个未决项，也要区分阻断和非阻断。签收凭证缺失会阻断“是否可退款”的结论，却不阻断“我们已收到问题并开始核查”的受理回复；客户偏好的称呼方式缺失，不应阻断处理。每个字段标它影响哪个对客断言或动作，避免一张卡里任何空格都让系统僵住。反过来，模型不能因为想填满表格就把真正未知的凭证状态编成“已核验”。

**领导：**客服要是看到“系统显示已签收”，会不会直接点“拒绝退款”？

**小陈：**工作台应把客户“未收到”的陈述和规则“先查凭证”紧贴在同一处，不能让单一系统状态占满屏幕。审批按钮根据动作阶段开放：核查凭证可以创建任务；退款决定在必要证据和权限齐备前不能选。UI 的布局也是控制的一部分。内部卡如果把“建议退款”用绿色大字放顶端，把“仅为模型推断”缩成灰色脚注，再好的数据结构都会被误用。

## 草稿版本、卡片版本、发送版本要对得上

**领导：**审核人批了第三版草稿，客户又补一句“是另一个订单”，怎么办？

**小陈：**客户新消息让工单版本变化，卡片第三版可能失效；草稿引用的订单也可能不对。发送服务必须检查批准时的卡片版本、工单版本与收件人是否仍一致。若不一致，暂停外发，提醒客服看差异并重新审核。不能只在界面上把“发送”按钮变灰，后台任务还用旧批准去发。版本绑定是服务端约束，不是客服的记忆力测试。

假设客服改稿，把“将核查凭证”改成“已核查凭证”，系统要要求新回执；若只是把语气从“请耐心等待”改成“我们会更新进度”，仍要产生新草稿版本并让审核人确认对客承诺。批准记录指向具体内容哈希、收件人、渠道、有效期与审核人。任何一项变化，旧批准不能自动继承。这样客户最终看到的话，才能与审核人实际看过的话一致。

**领导：**发送接口报超时，卡片上会写“已发”？

**小陈：**不会。`reply_draft_approved` 与 `message_sent` 是两件事，前者有审核回执，后者需要渠道回执。超时表示结果未知，先查渠道消息 ID 或业务键，不盲目补发。卡片可以显示“草稿已批准，发送状态待核实”，客服知道下一步去哪里查。若模型看到“已批准”就给客户说“已通知您”，又是把动作阶段跨了一步。

## 给工程师的校验顺序，先挡最危险的错

**领导：**卡片字段都填了，能否直接显示“已完成”？

**小陈：**不能。字段完整只表示结构合格；“已完成”必须对应实际业务动作的回执。界面把草稿生成、审核通过、业务执行、客户送达分别显示，客服才能接住卡在中途的单。

**小陈：**生成卡后，程序先校验形状：字段类型、枚举、必需键和引用 ID 是否存在；再校验证据：工具回执是否属于本单且未过期，政策是否生效并适用，客户陈述是否对应原消息；再校验动作：退款、建单、发送是否有系统回执，建议动作不能冒充已执行；最后检查对客草稿的关键句与卡片是否一致。每一步失败给具体错误和下一步，例如“退款回执缺失，禁止使用已退款措辞；可改为待核实并交客服”。不要用笼统的“格式错误，请重试”，让模型连试五次直到随机蒙对。

如果格式校验失败，重试可以有限次；若证据缺失，重复生成不会让订单系统凭空给回执，应该查证或转人；若政策冲突，交规则负责人；若写动作结果未知，查业务系统而不是重做。错误分类决定恢复路径。对模型来说，四类都可能表现为“卡片没通过”，对生产系统却绝不能一律再次请求大模型。

**领导：**模型版本升级后，它仍能填这张卡吗？

**小陈：**schema 与校验规则都要版本化。新模型先用固定工单回放，检查它是否更会区分客户陈述和已核事实、是否减少错误执行措辞；旧卡与新卡字段变化要有兼容迁移，正在审核的草稿不能因发布而默默换格式。上线后按卡片版本追踪错答和改稿，出现问题可回到上一套模型与 schema 组合。结构化输出是接口契约，不是一次写完永不变化的提示词。

**领导：**最后一句给客服培训怎么讲？

**小陈：**“先看这张卡有没有来源和未决项，再看回复有没有把建议说成已办。”客服不必背 JSON Schema，但要知道点“批准”前看到的是哪张单、哪个客户、哪版规则、哪句还没证据。客户收到的可以只有三句话，背后每句话都要站得住。八百字的作文能被删到三句，靠的是事实被整理清楚，不是小陈的删字功夫。

上线验收时，小陈让一位没看过 0823 对话的客服只读卡片，在两分钟内说出“目前能确认什么、不能确认什么、下一步由谁做”；再把一条虚构的“已退款”混入模型输出，看发送前是否因缺回执被拦。若卡片能让人接着处理、错误承诺出不了门、客户收到的短回复仍说明原因与下一步，这才叫实用的结构化输出。若只是后台多了一张表，而客服仍要翻十屏聊天核对，卡片设计还得回炉。

领导把原来那篇八百字草稿和三句新回复并排看，终于发现短不是少做事，而是把没证据的话删掉、把真要做的事交给有负责人的流程。

**领导：**卡片的“建议动作”写得很漂亮，谁保证它真的建了待办？

**小陈：**建议、提交、执行分状态，建单成功要有待办 ID、责任队列和时间；接口超时是结果未知，先按业务键查。客服看到“将核查”与“已提交核查”要不同颜色，发送前核承诺所需的回执。卡片解决的是交接，不能把一项尚未发生的动作填成已完成。
