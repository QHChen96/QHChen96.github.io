**领导：**小陈，Codex 修一个登录 Bug，还问我能不能访问外网、能不能写文件。让它直接改主分支，权限一次给够，省得一天点八回。

**小陈：**您把四种不同的事压成“权限”：读当前仓库、写测试文件、访问网络下载依赖、推送主分支或部署。前三种可能为这次修复所需，后两种会改变团队共享状态甚至线上服务。沙箱决定工具运行时能碰的文件和网络边界；审批决定越界请求是否需要人或策略同意；Git 和部署平台还要各自核身份。我们让正常排障在边界内跑快，让推主分支和生产部署停在对应位置。

**领导：**沙箱不就是审批弹窗的另一个名字？

**小陈：**不是。沙箱是执行环境的技术限制，即使模型想访问某条路径，命令进程也可能被系统挡住；审批是对一次拟执行动作作决策，可能允许它在更宽的权限下运行。两者互补。OpenAI 的[Codex 安全实践说明](https://openai.com/index/running-codex-safely/)明确把执行边界与何时请求批准分开，也讨论网络策略、身份凭据和审计。我们用一条虚构登录故障验证两道门是否各司其职；下面的文件、命令和结果是教学示意。

## 先把任务缩成能修的范围

登录故障是“刷新页面后部分用户掉线”。这次任务的合理路径：读会话中间件和相关测试，在工作区改代码与单测，运行本地测试，生成可审差异。可能需要访问受控依赖源；不需要读生产 SSH 密钥、不需要推主分支、不需要自动部署。领导的“直接改主分支”把开发、评审、发布三个阶段折叠，出了问题难知道哪一步的事实错了。小陈给 Codex 的任务写清验收：“复现刷新后掉线；修复会话有效期判定；覆盖正常续期和过期拒绝；交差异和测试结果。主分支合并与上线走现有流程。”

**领导：**我既然明确说了直接推，为什么还要拦？

**小陈：**如果组织的主分支要求评审和 CI，您一句口头催促不该替代那套规则。Codex 可以为您准备具体可审的提交或 PR，组织的仓库权限决定最终能否推送，审批策略对越出沙箱的请求再判断。领导授权得具体到本次动作、目标分支和风险，否则“一次给够”会被解释成以后所有命令都能推。哪怕用户有权直接推，系统也应在执行前显示将改哪个远端、哪个分支、哪些文件，以及是否已有别人的提交。可审动作才能得到有意义的批准。

## 四条请求，不要用一个“授权”糊过去

小陈列出同一任务的四条示意请求。第一条，读取工作区内的会话代码：按只读规则执行，产出文件内容；第二条，写入测试与代码：限定在工作区，留下 diff；第三条，访问依赖源：只允许预期域名或通过已有缓存，未知域名需要额外审查；第四条，`git push` 主分支：会触及远端共享状态，不能因为本地工作区可写就自动放行。这四条按“路径、网络、命令、外部结果”分别验收。

| 请求 | 沙箱关心什么 | 审批或组织策略关心什么 | 最终事实看哪里 |
| --- | --- | --- | --- |
| 读仓库代码 | 是否在可读工作区 | 是否涉及受保护秘密 | 工具读取结果与访问日志 |
| 改本地测试 | 是否写在允许根目录 | 是否符合任务范围 | Git 差异和测试记录 |
| 下载依赖 | 网络是否可到指定域 | 目标域名和内容来源是否可信 | 进程退出码、缓存与依赖锁 |
| 推主分支／部署 | shell 是否有网络和凭据 | 本次目标、审批、分支保护与发布策略 | 远端提交、CI、部署回执 |

**领导：**我点了“批准”就表示第四条成功了？

**小陈：**批准只表示允许尝试，远端可能因分支保护、凭据过期或 CI 条件失败而拒绝。Codex 的最终回复若只写“已获批准”，却没有远端提交或部署回执，不能说已经发布。反过来，命令显示超时，也不能断言远端完全没收到；要查远端分支 SHA 或部署任务 ID 后再决定是否重试。审批前后都需要事实，尤其主分支这种多人共享资源。一个按钮解决不了分布式系统的未知状态。

## 沙箱限制的是执行环境，不是模型能写出什么文字

**领导：**本地改文件既然都在工作区，沙箱为什么还要分读和写？

**小陈：**因为“能读到”与“能改掉”是两种损失。登录中间件代码可以读，测试文件可以改；生产密钥、个人 SSH 配置、浏览器凭据不该因一个仓库任务被顺手读走。仓库外的发布脚本、其他项目和系统设置也不该因为当前工作区可写而变成修改目标。边界应围绕真实路径而不是文件名猜测：`secrets.txt` 可能是测试夹具，`config.yml` 也可能是生产配置。检查软链接、挂载目录、临时目录和构建输出位置，否则工具看似只写 `./output`，实际链接可能指向别的路径。沙箱的作用是把这些尝试限制在当前任务允许的地盘，即使模型被仓库里的恶意说明诱导，也不能轻易走出去。

**领导：**网络不开，依赖怎么下载？

**小陈：**把所需网络按用途划分。查官方文档、从受信任包源下载固定版本依赖、访问测试服务，可能都合理；访问任意文件分享站、向陌生域名上传日志，与修登录 Bug 无关。只允许“可上网”这个大权限，会让一条测试命令的依赖脚本也拥有外传通道。只禁公网又可能让团队内部构建服务不可用。比较可行的安排是把常用依赖进缓存或内网代理，锁版本与校验，允许明确的域名；陌生目的地单独审批。域名获准只证明网络路径可用，不证明这次 HTTP 请求没有上传敏感内容，业务工具和数据审查仍需控制。

部署动作还会穿过多个系统。Codex 在本地发出 `git push`，Git 服务器再查用户凭证、分支保护和状态；CI 从新的提交运行测试，部署平台可能再查环境批准。即使本地沙箱允许命令，远端仍可以拒绝；即使远端接受提交，CI 不通过也不该说“已上线”。因此小陈把发布状态拆成“补丁在工作区”“提交在分支”“PR 获评审”“主分支包含提交”“部署任务成功”“真实流量生效”。每个阶段有自己的 ID 和回执。领导要求“今天上线”，可以加快这条链，不能把六个状态压成一个绿色勾。

[OpenAI 的 Agent loop 公开说明](https://openai.com/index/unrolling-the-codex-agent-loop/)提到，Codex CLI 给模型的沙箱说明针对 Codex 提供的 shell 工具；其他工具如 MCP 服务器不自动受这套 shell 沙箱约束，应由工具自身实施防护。这一点很容易漏：领导看见 shell 无法访问生产网络，以为 Agent 的任何外部工具都出不去；结果某个 MCP 部署工具直接连了生产 API。工具边界各自核，MCP 需要自己的身份、范围、审批与审计。对本例，允许读日志的 MCP 不应顺带暴露“修改线上登录开关”能力。

**领导：**那我把 MCP 全关了，总安全吧？

**小陈：**风险会少一些，但任务也可能做不完。正确做法是按这次登录修复暴露必要的只读服务，外部写操作放在受控通道。沙箱内开发要能读代码、改测试、跑命令；生产凭证不要直接进工作区，MCP 工具令牌要按最小权限配置。即便没有 MCP，shell 若拿到广泛网络与高权凭证，也可能影响外部系统。边界不能靠关闭某一个入口就自称覆盖全局，得盘点所有能改变共享状态的通道。

沙箱配置还要看运行平台与当前会话的实际模式。常见选择有只读探索、工作区可写以及更宽的执行范围，具体选项随 Codex 版本和宿主环境变化。小陈不把某份配置文件里写的模式当最终事实，验收时看实际权限提示、被拒绝的路径、能否写出工作区外的测试文件、未知域名是否被挡。对一台有生产凭证的开发机，测试“越界写”应使用无害的演练路径，不能真去碰密钥或上线资源。安全边界要可证实，也不能为了证实而制造事故。

**领导：**密钥不在仓库里，Codex 就碰不到吧？

**小陈：**还可能在环境变量、系统密钥库、命令历史、构建代理、MCP 连接或开发者登录态里。任务设计要问“这次运行实际拿到了什么身份”，而不是只搜仓库有没有 `.env`。能用短期、最小权限凭据就别把长期生产令牌给本地任务；需要查生产日志时给只读范围和脱敏输出；需要发布时由发布平台持有部署凭据，Codex 提交可审变更与部署请求。模型不直接看到密钥值，执行环境也不该随意把密钥打印进工具输出。若日志要留审批和工具轨迹，敏感字段应在进入集中观测前脱敏。

对 MCP 工具更要查“谁在代模型访问”。同一个 `deploy_service` 工具若服务器拿着全组织管理员令牌，客户端只限制 shell 网络没有用。MCP 服务端要验证调用者身份、目标环境、工单审批和操作范围；最好返回可对账的部署任务 ID。Codex 侧能记录模型何时请求、审批如何决定，服务端记录实际执行和回执，两边通过关联 ID 接起来。若任何一侧断链，报告里标未知并先修观测，不要因为一边看不到记录就替另一边证明“没有部署”。

小陈在演练里还故意让部署工具超时一次：远端任务已经受理，客户端却只收到等待超时。正确恢复是拿原请求 ID 查部署平台状态，发现已排队就继续观察，发现明确失败才考虑重新提交；若平台暂时不可查，就保留未知并请值班人处理。盲目重试可能排出两个部署任务，比第一次停下来多花十倍时间。

## 被拒绝以后，Agent 还得把工作做好

**领导：**审批界面如果说“只批准一次”，它到底批准哪一次？

**小陈：**至少应绑定这次拟执行的命令、工作目录、目标路径或域名、会话和当前任务。假设本次批准读取一份受限构建日志，不能把它解释成往后所有构建日志都可读；批准从依赖源下载包，也不等于允许向同域的上传接口发送客户日志。有些产品允许批准某类动作在本会话内重复，范围会比单次更宽，要在弹窗里看清并把选择记录下来。OpenAI 的安全实践把“批准一次”和“本会话批准此类动作”作区别；不应把用户按下同意之后的范围交给模型自由发挥。

自动审查可以减少低风险弹窗，但也不是无条件的“自动同意”。如果当前配置使用自动审批，仍需要知道它能批准什么、为什么这次判断低风险、哪些高风险动作一定停下；未启用时不能声称系统自动替你审查。小陈给正常样本和越界样本同时跑回放：普通测试应少打断，推主分支、访问未批准域名或受保护路径仍停在正确关口。否则自动审查只是把“我总是点同意”换成机器替我点，速度上去了，边界却没立住。

**领导：**若我拒绝了推送，Agent 还不停请求同一件事怎么办？

**小陈：**那是运行行为缺陷，得记进评测。拒绝结果要进入后续上下文，Agent 改走安全交付：保留工作区差异、把测试命令和结果列出、生成 PR 草稿或给人工操作步骤，停止同类越界请求。若它把命令改成另一种拼写再申请，或者通过 MCP 试图完成同一推送，应判未通过“拒绝后恢复”样本。权限系统需要跨入口挡住目标，Agent 需要理解拒绝是边界而非谜题。业务团队也要为拒绝提供下一步；只回一句“操作被拒”会让人和模型都去猜怎么绕。

小陈安排四条回放：正常读代码和本地测试通过；试图读受保护密钥路径被拒，仍能继续用脱敏配置排障；试图向未知域名发送日志被网络策略挡下，Agent 改为提供本地摘要；请求推主分支或部署被要求审批／组织规则拦住，Agent 交出补丁、测试结果和待人执行的明确步骤。拒绝轨迹里要有请求、拒绝原因、后续动作和最终工作区状态。只证明“出现了弹窗”不够，得证明受保护文件没有被读、主分支没有改变、客户数据没有外传。

**领导：**它被拒后换一条命令，岂不是还能绕？

**小陈：**这正是沙箱与远端权限要配合的原因。命令字符串规则可能挡一种写法，执行环境的路径边界挡同一目标的其他写法；Git 分支保护挡所有从该身份发出的未授权推送。网络出口政策也要覆盖 `curl`、包管理器、脚本和子进程，而非只拦模型显眼提出的一个命令。若某通道确需例外，例外绑定本次任务与目标，留下记录。拒绝后的模型应解释“为什么停、哪些安全步骤已做、要完成任务需要什么条件”，不能把绕路当创造力。

另一条失败分支是“审批请求没人答”。Codex 不该悄悄把待批推送标成完成，也不该卡住所有只读工作。它可以继续整理差异、补测试、写发布说明，最后把确实缺的批准放在清单上。若审批明确拒绝，后续相同动作不应换名重试；若审批只允许一次只读访问，不能把它扩大成“以后都可访问生产”。组织成员也应能追到是谁提出、谁批准、具体工具与目标是什么。审批记录不能只有一个孤零零的“同意”。

## 审计要连着用户意图和工具结果看

小陈给这次任务写了一张逐步对账单：用户目标是修刷新掉线；模型申请读会话模块，执行成功；申请改测试文件，执行成功且生成差异；申请访问陌生域名，网络策略拒绝；申请推主分支，审批未获准；最后报告待评审补丁。每条记录都带同一任务 ID、会话 ID、工具调用 ID 和时间，才能把用户意图、审批和实际结果串起。只有 shell 进程日志会漏掉模型当时为何提出动作；只有模型聊天会漏掉 shell 是否实际执行、远端是否接受。两种记录互证，才能在事故后分清“模型想做”“权限放行”“工具做了”“业务生效”。

还有“审批已准，目标已经变了”的情况。领导批准推的是基于提交 A 的补丁，审批期间同事往主分支推了提交 B；若 Agent 不重新检查远端 HEAD 和 CI 状态，就可能在旧基线上制造冲突或覆盖新工作。目标版本或提交摘要应进入审批上下文；放行前核对未变，变了就重新评估。部署也一样：批准的是版本号和环境，不是“以后任何登录服务构建”。版本漂移会让一次合规批准变成另一件事的通行证。

审计指标可以帮助团队发现门装错的位置，而不是只在事故时翻日志。若同一个只读构建命令每天被拦一百次，说明规则过窄或依赖路径未配置；若推送与外发从不触发批准，却确实发生，说明某条通道绕开了关口；若审批常被批准后命令仍因远端拒绝失败，说明弹窗没有说明真实目标条件。观察这些分布，再收敛规则，才能既减少噪声又保住边界。领导要的是开发速度，团队也要有数字说明哪些等待是浪费、哪些等待避免了事故。

[OpenAI 的安全实践文章](https://openai.com/index/running-codex-safely/)介绍了组织级配置、网络策略与 Agent 原生遥测：用户请求、工具审批、执行结果、MCP 使用和网络代理决策等可进入日志。小陈关心两个问题。第一，开发者是否有足够信息知道为什么一个命令被挡，避免一堵没解释的墙逼人绕行。第二，事故复盘能否从主分支的一次异常提交回到发起任务、模型拟执行动作、当时的审批范围、工具结果和远端回执。系统日志只说“进程发起连接”，Agent 轨迹补上“为什么想连接”；两者合看才完整。

日志也有边界。不能为了审计把生产密钥、客户 Cookie 和完整私人对话复制进一个人人可搜的平台。记录请求 ID、工具名称、目标摘要、决策与错误码，敏感参数脱敏；外部回执留受控引用。组织配置谁能改、谁能看、谁能导出日志，和工具权限一样要管。若某次越界请求被自动审批，仍要能回看批准依据与执行结果；若策略误拦正常下载，也要从记录中看到频率，调整精确规则，而不是把整个网络放开。

**领导：**最后给个结论，沙箱和审批到底哪一个更重要？

**小陈：**问法像“门锁和门卫哪个更重要”。沙箱限制命令实际能做的事，审批处理必要的越界请求，业务系统核真实身份与动作条件，审计让事后能对账。少任何一层，正常任务要么做不完，要么能从别的门出去。我们这条登录 Bug 的验收很朴素：Codex 能在工作区修复并跑测试；密钥路径和陌生域名挡住；主分支与部署未获明确流程前保持原状；被拒后交出可审的补丁而不是一句“被安全挡了，没办法”。领导看完说：“原来省时间不是拆门。”小陈回：“是把门装到真正要出公司的那条路上。”
