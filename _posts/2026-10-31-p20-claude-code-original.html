01 / VERSION

先把“最新版”说准确

本教程固定以 Claude Code 2.1.314 为运行器基准，资料核验于 2026-10-31（北京时间）。

GitHub latest release 与 npm latest 都指向 2.1.314。GitHub 发布记录为 2026-10-30 01:06:26 UTC，即北京时间 10 月 30 日 09:06:26，且不是 draft 或 prerelease。官方文档会持续更新；文中的实验性功能、宿主限制和最低版本另行注明。

需要分开的版本决定什么怎样核对
Claude Code 版本运行器、工具、交互和扩展能力claude --version
Claude 模型版本推理能力、上下文、价格、供应商可用性/model 与模型配置
Agent SDK / 插件版本程序接口与扩展组件各自包版本；不能套用 CLI 版本号

latest 与 stable 是两条发布通道。官方说明 stable 通常滞后一周左右，并跳过出现明显回归的版本；本教程的“最新”指 latest。原生安装的默认通道为 latest，Homebrew 的 claude-code cask 跟随 stable，claude-code@latest 跟随 latest。

02 / FIRST PRINCIPLES

Claude Code 是一个组装好的编程 Agent

模型判断下一步，工具操作真实环境，Claude Code 把上下文、执行、反馈和开发者交互连接起来。

如果你只调用一次模型 API，得到的是一次回答或工具调用请求。要让它解决一个仓库里的 bug，还要有程序负责：读取文件、运行测试、修改代码、收集错误、再次调用模型，并在过程中处理权限、历史和用户补充。围绕模型组织这些设施的部分，称为 Agent Harness。

Claude Code 已经把一套面向开发工作的 Harness 组装成产品。你提供任务和项目环境，通过终端、IDE、桌面或云端入口使用它。AgentScope 则让你通过代码组合 Agent、模型、工具、状态和协作流程。两者都依靠“模型—工具—反馈”循环，但交付层级与配置方式不同。

对象主要职责订单修复示例
Claude 模型理解目标、判断下一步、生成工具参数认为需要先查看金额函数和失败测试
Claude Code Harness管理上下文、工具执行、会话和交互把实际测试结果送回模型
工具执行一个具体动作读 pricing.py、编辑文件、运行 unittest
实际工作环境保存文件并运行进程或服务你的 checkout、Python 解释器、业务接口
验收规则说明什么结果才算完成折扣不影响运费，现有测试通过

官方把循环描述为收集上下文、执行动作、验证结果。这些阶段可以交错和重复。图中的“整理上下文”“处理工具调用”等是公开行为的教学分层，不声称它们对应未公开的内部类、微服务或线程。

来源：How Claude Code works · 产品入口 · AgentScope 2.0.11 对照

03 / EXECUTION

跟着一个失败测试走完整条循环

学习包中的练习采用整数分计价。规则是：先给商品打折，再原额加入运费。起始实现故意把运费也算进了折扣。两件单价 100 元的商品，打九折、运费 5 元，应付 185 元；错误实现得到 184.50 元。

阶段模型可能选择什么真正的证据在哪里
了解任务读取 CLAUDE.md、实现和测试文件工具返回的实际内容
复现错误调用 Shell 运行测试退出码、失败用例、期望值与实际值
形成修改决定将运费移出折扣计算实际写入的代码与 diff
检验结果重新运行同一组测试新的测试输出
结束回复报告改动和验证范围结论应与上述文件和运行结果对应

这里每个“选择”通常需要模型推理，每个“执行”需要实际工具完成。一次用户请求可能包含多轮模型调用。只读分析任务可能只需要搜集证据；复杂修复则可能多次编辑和测试。

验证是否发生、验证范围是否正确，仍取决于任务、策略和工具结果。运行器结束一次回复，不自动等于业务目标达成。你可以通过具体的输入、预期结果和检查命令，把“完成”变成可观察的条件。

文件查询不必固定记成某套旧工具名。当前 Read、Edit、Write、Bash 等仍是重要入口；macOS / Linux / WSL 默认不再暴露 Glob、Grep 两个独立工具，文件搜索可通过 Shell 完成。子代理委派工具现名 Agent；早期教程里的委派 Task 已更名。

来源：执行循环 · 工具参考。金额案例为本教程设计，运行验证见第 11 节。

04 / CONTEXT & MEMORY

知道项目，不等于把整个仓库塞进模型

模型在某一次请求中，只能依据当次提供的上下文推理。Claude Code 通过搜索、读取、工具反馈和按需加载，逐步取得相关材料。一个仓库可以很大，但当前模型窗口仍然有限。

机制保存 / 提供什么应放什么
当前上下文系统指令、对话、相关文件、工具结果这次任务正在用的工作材料
CLAUDE.md / rules按目录与范围加载的工程约定构建命令、模块边界、业务术语、稳定约束
Auto memory跨会话选择性保存的记忆文件用户纠正、偏好、持续项目事实的引用
Session transcript保存到磁盘的对话与工具记录继续、查阅或分叉某段会话
File checkpoint特定时间点的已跟踪文件快照交互中恢复部分代码状态
Git提交、分支和长期版本历史正式版本管理与协作合并

CLAUDE.md 与 settings.json 的区别

CLAUDE.md 被送进模型上下文，表达“应该怎样工作”。settings.json 由运行器读取，配置模型、权限、Hook 和扩展等行为。发现的多层 CLAUDE.md 是按规则组合进上下文；不要把它理解为配置键那种逐层覆盖。

当前版本已经原生支持 AGENTS.md。默认情况下，只有工作目录及祖先没有 CLAUDE.md、.claude/CLAUDE.md 或 CLAUDE.local.md 时，才使用 AGENTS.md；也可以调整 Project instructions。个人 ~/.claude/CLAUDE.md、受管项目指令和 .claude/rules/ 不参与这项排除判定。支持起始于 2.1.277，禁用相关内置组件或旧版本会影响结果。

Auto memory 是文件式记忆

本地会话的默认记忆路径在 ~/.claude/projects/<project>/memory/。启动加载 MEMORY.md 前 200 行或前 25KB，先到者为限；主题详情按需读取。同一 Git 仓库的 worktree 可以共享这份项目记忆，但不同会话不会因此共享完整聊天历史。

压缩、恢复、回退，分别改变什么？

操作改变什么应保留的判断
/context查看当前输入占用用实际占用判断是否有无关日志或材料
/compact用摘要缩小当前工作上下文摘要可能损失细节，关键事实可回源核验
--continue / --resume恢复保存的会话恢复窗口与存储历史不是逐字等价；已结束的工具进程不会因此复活
/branch分叉对话到新会话仍要单独决定文件目录是否隔离
/rewind按选择恢复对话或已跟踪文件不负责撤销远程 API、数据库或部署

Checkpoint 主要跟踪内建文件编辑工具触及的文件。仅由 Bash 改动且从未被跟踪的文件，不能假定会随 rewind 恢复；已被跟踪文件的后续 Bash 改动可能一并回退。多代理改动的覆盖也有条件，长期版本管理仍交给 Git。

来源：项目指令与记忆 · 上下文与压缩 · 会话 · 检查点范围

05 / EXECUTION CONTROL

权限与沙箱各控制一层

执行一个动作前，运行器需要决定“是否允许”。动作开始后，操作系统环境还可以限制进程能够访问的文件与网络。这是权限控制与沙箱的职责差别。

层面决定什么例子
项目指令希望模型采取什么行为只修金额计算，不扩大功能范围
权限规则 / 模式工具调用能否执行，是否需要确认允许既有测试命令，限制某些操作
适用 Hook在生命周期事件处运行程序或检查编辑后校验格式；执行前验证条件
内建 Shell sandboxShell 及其子进程运行时能访问什么文件与网络边界
业务服务授权外部接口允许当前身份操作哪些业务数据tenant_id、角色、订单归属

最新版的默认模式，要看入口

2.1.283 起，交互终端和 VS Code 的内建起始模式为 Auto，但设置、组织政策、模型与提供商条件会影响结果。2.1.302 起，claude -p 与 Agent SDK 没有显式模式时，内建起始模式仍为 Manual / default。无人交互时需要批准的动作，必须通过适用的授权规则或回调等机制处理。

模式直观理解
default / manual按常规规则对需要批准的动作询问；只读行为也要看路径与已有配置
acceptEdits接受文件编辑和适用的常见文件操作，其他动作继续走权限规则
plan以调查和方案为主，代码编辑受限制；Shell 行为有额外条件
auto由独立分类器审查适用动作，减少普通批准提示
dontAsk需要询问却未获准的动作直接拒绝
bypassPermissions跳过大量许可提示；不会自动建立 OS 隔离

内建沙箱默认关闭，支持 macOS、Linux 和 WSL 2；原生 Windows 当前不支持这层隔离。它主要覆盖 Shell 命令及子进程，不能把 Read / Edit、Hook、MCP server 全部画进同一个内建沙箱。工具仍由各自权限与部署机制约束。

选择开发流程时，可以按任务风险和已有授权配置模式。小范围、有明确验收的修复可以直接调查并执行；大范围且方案未确定的改动再使用 Plan。无需把每一次文件读取都变成一轮人为审批。

来源：模式与入口默认值 · 权限规则 · 沙箱范围。流程选择为本教程建议。

06 / EXTENSIONS

Skills、MCP、Hooks、Plugins 插在不同位置

机制增加的东西OMS 场景
CLAUDE.md常驻项目约定说明分仓模块位置、构建命令和库存术语
Skill可复用的方法与资源入口规定排查订单未分仓时先看哪些证据
MCP外部工具与数据连接调用已授权的订单或库存查询服务
Hook按事件触发的处理逻辑文件编辑后执行现有格式检查
Subagent独立的任务执行与上下文委派库存预占逻辑审阅
Plugin可一起安装、更新和分发的组件包打包团队的排查技能、工具连接和检查逻辑

Skills：方法按需加载

通常先让模型看到技能名称与描述，真正使用时才把 SKILL.md 正文送入上下文；参考文件和脚本继续按需读取或执行。自定义 commands 已并入 Skills，旧 .claude/commands/ 仍兼容。你指定的 arch-diagram 就属于这种“方法、配置规范、脚本和渲染资源”的组合。

Skill 的 allowed-tools 表示本次调用这一轮的免提示授权，不是完整工具白名单；下条用户消息到来时会清除。该授权仍受适用权限与组织受管策略约束，例如启用 allowManagedPermissionRulesOnly 时，项目与个人技能的这类授权不生效。disallowed-tools 用于在生效期间移除工具。技能正文留在上下文多久，与权限持续多久，是两个问题。

context: fork 技能会在子代理里以技能正文执行任务，但不继承主会话历史；它与“复制当前对话的 forked subagent”不是同一入口。当前常见交互中默认后台执行，background: false 可要求等待，非交互场景另有规则。

MCP：连接可调用能力

Claude Code 作为 MCP client，连接本地 stdio 或远端服务，发现工具、资源等能力，将调用请求送到相应服务，再把结果交给模型。方法可以由 Skill 描述，具体查询由 MCP 工具完成，租户与数据授权仍由服务端落实。

当前 MCP tool search 默认开启，工具定义按需加载；“超过上下文 10% 才打开”是可选 auto 阈值模式，不能再当统一默认值。模型、提供商与组织配置可能影响可用性。

Hooks：事件触发与处理器分开理解

PreToolUse、PostToolUse、SessionStart 等事件由宿主触发。处理器可以是 command、HTTP、MCP 工具、prompt 或 agent。程序检查可以是确定性逻辑；使用 LLM 的 prompt / agent 处理器仍然是模型判断，agent 型 Hook 当前标为实验性。

PostToolUse 发生在动作之后，检查发现问题时需要后续修正，不能把检查失败理解为自动撤销动作。针对编辑文件的快速检查通常比每次改动都跑完整构建更合适。

Plugins：复用与分发

插件把 skills、agents、hooks、MCP、LSP 等组件打包。清单通常放在 .claude-plugin/plugin.json，组件在插件根目录的相应目录。插件根目录的 CLAUDE.md 不会自动成为项目指令。

当前还有 Mods：它们通过插件内的进程内 JS/TS 扩展接事件、工具流程或界面，支持范围取决于终端、IDE、桌面和 headless 宿主。理解扩展层时，先掌握 Skills / MCP / Hooks；需要修改产品运行或界面行为时再研究 Mods。

来源：Skills · MCP · Hooks · Plugins · Mods

07 / PARALLEL WORK

多代理要同时画清“对话”和“文件”两条边界

多个推理过程可以同时工作，但独立的上下文不自动产生独立的代码目录。设计并行开发时，要分别决定：谁知道什么、谁修改哪些文件、谁负责整合和验收。

方式上下文关系协调方式与用途
普通非 fork 子代理独立上下文，接收委派任务和适用配置把搜索、审阅等过程留在子代理，向调用方报告
Forked subagent复制启动时的父对话背景，之后独立执行适合子任务确实需要已积累背景；内部轨迹不全部回灌
Agent Teams多个完整会话，每个成员独立Lead、消息通信、可用时共享任务表；实验性
独立 / 后台 sessions各自有会话与生命周期外部调度或 agent view 监控，可按条件互发消息
Git worktree不管理模型上下文把文件改动分到独立目录与分支

当前子代理比早期教程更灵活

现在可以按配置嵌套子代理，具名代理也可以互发消息；后台子代理可以把适用权限请求交给主会话处理。普通非 fork 子代理与复制父对话的 fork 必须分别说明，不能一概说“子代理全都继承历史”或“子代理绝不继承历史”。

上下文隔离的收益，是让大量搜索结果、日志和文件内容留在子任务中；主代理获得必要结论和证据。代价是额外模型调用与交接。交接任务应写清目标、必要背景、范围和输出格式。

Agent Teams 的条件

当前 Teams 仍为 experimental，默认关闭，需要 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1。它只在交互入口启动 teammates；-p 与 Agent SDK 即使设置变量，也不会因此获得 Teams。共享任务表要求相应 Task 工具可用；没有这些工具时成员通过消息协调。

后台会话与 worktree

claude agents 对应的 agent view 当前是 research preview；--bg 启动完整独立的本地后台会话，不能与 -p 组合。它和“某个主会话下的后台子代理”有不同生命周期。

claude -w pricing-fix 可以在 Git worktree 中开始任务。Worktree 分开工作目录和分支，但仍共享 Git 历史及部分设置；数据库、端口、外部服务和自动合并需要另行设计。

对你的并行开发目标，一个实用起点是：一名整合负责人，多个职责明确的执行会话，每个修改任务拥有清楚的文件范围，必要时使用独立 worktree。需求未拆好时，直接增加会话数量会把问题转移成文件冲突与协调开销。

来源：Subagents · Agent Teams · Agent view · 跨会话通信 · Worktrees

08 / PRODUCT & SDK

做自己的企业 Agent，在哪一层接入？

入口你得到什么适合的需求
Claude Code 交互产品已经组装的开发 Agent 与界面读仓库、写功能、修 bug、开发协作
CLI 的 -p用子进程调用同一 Agent，输出文本或 JSON 事件一次性脚本、CI、跨语言宿主
Claude Agent SDKPython / TypeScript 代码驱动 Claude Code binary 与其循环、工具、会话将长程工具任务嵌入自己的应用
Claude Client SDK / API直接模型 API；循环由应用或可选 tool runner 管理精确控制一次请求或自建业务执行器
AgentScope 等框架通过代码组合模型、业务工具、状态和流程业务 Agent 服务与跨模型架构
Managed Agents通过服务接口使用托管 Harness需要托管运行环境与服务化会话的场景

Agent SDK 默认会读取哪些环境配置，也会随版本变化。当前文档说明，省略 settingSources 时会像 CLI 一样读取相关用户、项目和本地配置；显式空列表可以关闭这部分发现，但不等于消除所有受管设置、全局状态或自动记忆影响。构建多租户服务，应显式设计工作区、凭据、记忆与授权范围。

与你的两个项目对照

BossOS：可以把 Claude Code CLI / Agent SDK 作为一种执行适配器。BossOS 自己管理任务领取、依赖、执行器选择、工作目录、结果归档和整合。Codex、Claude Code、OpenCode 的接口不完全相同，应在适配层统一生命周期与事件。

SCRM：在线话术推荐优先保留明确的客户事实、租户隔离、知识检索和时延目标。AgentScope Java 或直接模型 API 可以承担实时链路；需要文件环境、复杂资料整理或长程工具执行的离线任务，再评估 Agent SDK worker。选型依据应来自实际延迟、成功率与成本测量。

下面是一条非交互调用示例。它只展示接口形态；可执行工具仍受实际权限配置控制：

claude -p "分析 pricing.py 的金额计算并说明依据" \
  --output-format json \
  --max-turns 8

持续集成可消费 stream-json 事件；结构化输出可用 JSON Schema。宿主还要处理退出码、被拒绝的工具、预算/迭代限制和任务状态。JSON 结构符合 Schema，表示结构合规，事实与业务规则仍要核验。

来源：Agent SDK 总览与产品对照 · SDK 配置加载 · CLI 参考。BossOS / SCRM 内容是接入建议。

09 / WORKFLOW

从一个清楚的任务开始，逐步增加配置

首先让项目有可执行的验证命令，再补充简洁的项目约定。遇到反复出现的任务才抽成 Skill；需要访问外部数据才接 MCP；需要固定事件检查才加 Hook；有独立任务边界再增加子代理。

一份短 CLAUDE.md 应写什么

# 项目约定
- 金额统一使用整数分。
- 折扣作用于商品，运费最后原额加入。
- 保留公开函数签名和类型标注。
- 验证命令：python -m unittest -v。
- 先读相关实现与失败证据，再做范围内修改。
- 验证足够后结束，不扩展到无关模块。

它把稳定约定放在合适的位置，避免每轮重新描述。庞大的教程、无关历史和所有业务资料不适合无差别装入常驻上下文；可以留在参考文件中，任务相关时再读取。

给 Claude Code 的任务描述

目标：修复订单折扣错误。
现象：商品九折时，运费也被打折。
范围：pricing.py，保留现有函数签名，不增加依赖。
验收：现有四个测试通过，测试本身不修改。
执行：先运行测试，用两三句话说明判断，然后完成修复与验证。
输出：改动原因、实际验证结果、仍未验证的范围。

这个模板给出目标、证据、范围与验收，不要求 Agent 在每一步都重复规划。复杂任务可以先澄清方案；具体而小的修复直接依据证据推进。你仍可在执行中补充信息或调整方向。

成本和效率看什么

记录任务是否完成、模型调用与工具等待、重复读取、上下文占用、重试次数、并行协调开销以及最终修改量。子代理减少主窗口负担，也会产生自己的调用成本；超长上下文和高 effort 应当服务于实际任务难度。把正确证据放进输入，往往比增加一长串笼统要求更有用。

机制依据：执行与反馈 · 项目约定 · 子代理成本与上下文。任务模板与选用顺序为教学建议。

11 / HANDS-ON

一个可以跟着做的失败测试练习

学习包的 lab/ 包含 CLAUDE.md、pricing.py、test_pricing.py 和 README。只依赖 Python 标准库。下方是故意保留错误的起始实现：

"""Claude Code 反馈循环练习：这份起始实现故意包含一个业务错误。"""


def payable_cents(
    unit_price_cents: int,
    quantity: int,
    discount_percent: int = 0,
    shipping_cents: int = 0,
) -> int:
    """返回应付金额，单位为分。输入均满足 README 中的有效范围。"""
    subtotal = unit_price_cents * quantity
    return (subtotal + shipping_cents) * (100 - discount_percent) // 100

在 lab 目录先运行：

python -m unittest -v
claude

把第 9 节的任务描述发给 Claude。观察“模型请求”“实际执行”“工具结果”和“下一步修改”的区别，然后尝试：

  1. 查看上下文。使用 /context，确认工具结果如何占用输入。
  2. 压缩后继续。使用 /compact，指定保留业务规则、失败原因和验证结果。
  3. 检查项目指令。另开会话，使用 /memory，区分持久规则与上次聊天。
  4. 比较工作区。在自建 Git 演示仓库中比较会话分叉与 worktree 的文件边界。

已经完成的验证：起始实现运行 4 个测试，3 个按预期失败、1 个通过；独立临时目录中的参考实现通过同一组 4 个测试。没有实际启动 Claude Code，也没有调用真实模型。你运行时的工具轨迹、延迟和交互由模型、账号、版本及配置决定。参考解答与验证记录在 reference/，可完成练习后查看。

验收目标：你能指出模型凭哪条证据认定问题、修改发生在哪里、何时运行了测试，以及为什么“输出说修好了”需要与实际结果对应。

12 / CHECK YOUR UNDERSTANDING

用八个问题检查是否理解了边界

Claude Code 与 Claude 模型分别负责什么？

模型根据上下文判断下一步；Claude Code 管理工具、上下文、执行与交互。真正的文件或业务变化由工具作用于实际环境。

为什么换一个会话后，有些约定还在，有些聊天细节没了？

CLAUDE.md、适用规则与 auto memory 可以重新加载；旧聊天属于另一个 session。新会话不会自动拥有旧会话完整历史。

“不要修改生产配置”写进 CLAUDE.md 后，会形成什么约束？

它成为模型应遵循的上下文指令。技术上的执行许可与访问边界由相应权限、Hook、沙箱和业务系统负责。

Skill、MCP、Hook、Plugin 各自增加什么？

Skill 增加方法和资料；MCP 增加工具与数据连接；Hook 增加固定事件触发的处理逻辑；Plugin 负责把组件打包和分发。

普通子代理、forked subagent、context: fork skill 是否都继承主历史？

不是统一行为。普通非 fork 子代理从委派任务开始；forked subagent 复制父对话背景；context: fork skill 在新的子代理里以技能正文为任务，不继承当前聊天。

为什么四个 Agent 可能仍然互相覆盖代码？

上下文隔离不自动隔离目录。需要明确文件归属或 worktree，并有整合负责人；worktree 也不会自动解决合并和外部服务冲突。

能否在 Agent SDK 中打开实验变量就获得 Teams？

当前不能。Teams 的 teammates 只在交互入口启动；程序化协作可用子代理、多个受控会话或应用自己的调度层。

恢复会话、回退文件，能撤销已经发出的订单或消息吗？

不能据此保证外部操作撤销。应查询真实系统状态，用业务接口的幂等、事务或补偿处理外部影响。

延伸阅读：工作原理 → 上下文 → 扩展层 → 协作 → Agent SDK。文档会继续更新，复现时同时记录运行器、模型和扩展版本。
