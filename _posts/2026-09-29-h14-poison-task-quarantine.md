**领导：**队列里那张 issue 从昨晚跑到现在，Agent 真有韧性。可后面二十张任务怎么全没动？

**小陈：**第一张任务缺仓库 ID，模型每次都调用“读取仓库”，工具每次都回 <code>missing_repo_id</code>。它重试了六十七次，还排在队首。它不是韧性，是拿身体堵着收费站。后面二十张输入完整的任务只能陪它看报错。

**领导：**把重试次数从六十七改成一百，总能等到仓库 ID 吧？

**小陈：**仓库 ID 不会靠等待长出来。我们先给错误分类，再把不可自动修复的任务移到待处理队列，带着原任务键、失败证据和负责人。补齐输入后才能重放，重放前还要查它是否已经造成外部动作。

文中的任务和次数为教学虚构。队列产品与工作流重试能力以文内官方文档为准。

## 三种“失败”长得像，处理方法却相反

小陈把昨天六十七条日志按错误类别摆好。<code>missing_repo_id</code> 是输入错误，不会因为网络恢复而自愈；<code>503</code> 或暂时限流可能在退避后恢复；创建 PR 的请求超时是结果未知，可能已经在远端成功。若把三者都塞进“失败就重试三次”，坏输入白跑，临时故障可能被打成流量洪峰，外部动作可能重复。分类要发生在工具返回和调度层，不让模型靠一句“我觉得可以再试”决定。

**领导：**Agent 不能从 issue 描述里猜仓库 ID 吗？

**小陈：**可以尝试从可靠映射里查，例如项目绑定的仓库，但不能凭 issue 文字瞎编。若项目确实有唯一仓库映射，补全后把来源和版本记下来；若一个项目对应三个仓库，缺字段就是要人澄清。错误码 <code>missing_repo_id</code> 还要包含缺失字段、可查询来源和修复人，不能只回“参数无效”。Agent 可协助找候选，但自动执行必须等输入达到唯一、可验证的状态。

AWS 的[SQS 死信队列说明](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/capturing-problematic-messages.html)描述了消息多次处理失败后移出主队列，以免坏消息反复占用消费资源；Google Cloud 的[Pub/Sub 死信主题文档](https://docs.cloud.google.com/pubsub/docs/dead-letter-topics)也提供类似能力，同时提醒投递次数是近似的。小陈借用“隔离坏任务”的队列模式，但不会把消息中间件自带的重投次数当业务真相。Agent 的任务可能已经读、写、测试甚至创建 PR；进死信队列前后，仍要核对应用层动作台账。

## 错误分类表应该让人一眼知道下一步

小陈把失败分成四类。可重试：网络短暂中断、服务临时不可用，按错误语义和服务端等待提示限次退避。需修输入：缺仓库 ID、issue 不属于指定项目、必要字段格式错，停止自动执行并给负责人待办。结果未知：创建 PR、发通知、部署请求超时，先查远端回执，不直接重放。需审批：读受限文件、跨仓库修改或外发，需要合法批准才继续。再加一类明确永久失败，如目标仓库不存在且已核实，不应反复试。

**领导：**工具只返回字符串 <code>error</code> 怎么办？

**小陈：**那先修工具契约。至少有稳定的错误类型、是否有副作用、外部请求 ID、可重试建议、原始日志引用和安全的显示消息。调度器不能仅凭错误文案里出现“temporarily”就决定重试。未知错误先限次、降速并进入人工排查，不要默认为临时故障。错误语义是恢复策略的输入；输入只有一个模糊词，恢复器再聪明也只能猜。

对部分成功尤其要小心。任务先生成补丁，再在创建 PR 时失败；它不是“整张任务失败可以从头再来”。工作块、测试和外部动作分别记录状态，失败分类落在具体动作上。补全仓库 ID 后重新进入队列，要从已保存的工作区与检查点恢复，并对账 PR 是否已存在。若断电后什么持久工件都没有，才可能重做前段，但仍需查外部副作用。队列重放只是“给它重新安排一次处理”，不是时光倒流。

## 重试规则要按错误码和动作副作用交叉判断

**领导：**既然临时 503 可以重试，我给所有工具统一三次，方便维护。

**小陈：**同一个 503 出现在只读搜索与创建 PR 上，风险不一样。只读搜索失败可在限次退避后再查；创建 PR 请求若发出后连接断开，哪怕错误包装成 503，也可能已经成功，先查远端。调度器按“错误类别 × 动作副作用”做判断：无副作用且明确临时故障，有限重试；可幂等的写动作，按约定的业务键重试并核对；不可确认的写动作，先对账；永久输入错误，直接隔离。只看 HTTP 状态码不够，还要看请求在哪一步断、工具有没有远端请求 ID。

退避也不能只是固定睡一秒。服务端提供等待提示时优先遵守；没有提示则用有上限的指数退避并加抖动，避免所有 Worker 同一秒醒来再次打满下游。设单动作尝试上限与任务总时限，任何一个先到都停止；平台长期故障可以把任务批量转成“等待服务恢复”，由健康事件唤醒，别让每张任务各自开闹钟。这里的具体秒数依服务容量和业务时限定，不能从别家公司文档里抄一个常数。

**领导：**临时故障恢复了，为什么隔离队列里的任务不自动全部倒回去？

**小陈：**要控制回流速率。假设一小时积了两万张任务，服务刚恢复就全量重放，会把它再打挂。按优先级和创建时间分批，设置并发与速率上限，观察错误率；有客户时效要求的先处理。重放前仍要核对每张任务是否取消、输入是否过期、外部动作是否已发生。恢复下游与恢复业务队列是两个阶段。系统若只有“全部重试”按钮，故障可能在两小时后再演一次。

还要注意队列的投递语义。多数消息系统可能重复投递，消费端不能假设“每张任务只进来一次”；可见性超时、Worker 崩溃和重放都可能让同一任务再次被领取。任务键、租约、状态版本和外部动作台账要在应用层维持唯一逻辑结果。消息 ID 是运输标签，不一定等于业务任务键；重新投递可能有新消息 ID，却仍是同一张 issue。若去重只看消息 ID，隔离和重放流程会成为重复 PR 的入口。

## 死信队列里的任务怎么修，不是点开改一行字段就完

小陈把待处理页设计成一张真正的修复单。顶部是失败分类与发生步骤，中间展示安全脱敏后的原始输入、字段校验结果和最近几次尝试，底部是工作区与外部动作状态、负责团队、修复建议与重放前核对项。操作员可以补仓库 ID，但不能直接改任务键；改动形成新输入版本，保存操作者和理由。若原始 issue 已取消，操作页显示“不可重放”；若 PR 已存在，先进入对账，不显示“从头执行”。

**领导：**人手改坏字段怎么办？

**小陈：**修复操作也要校验。仓库 ID 必须属于该项目，操作者要有权选择目标仓库；如果 issue 涉及客户生产数据，还要核对数据边界。修复后的输入先跑只读预检，确认目标仓库可达、权限足够、任务仍有意义，再允许重新入主队列。错误若来自工具契约或平台缺陷，靠改字段没用，应该先修程序并选择用原流程版本还是新流程版本重放。n8n 的[执行重试文档](https://docs.n8n.io/workflows/executions/all-executions/)就区分使用原工作流或当前保存的工作流重试；我们也要记录这次重放使用哪个 Harness 和工具版本，否则结果差异无法解释。

人工重放还要有批量与单条两种方式。单条用来处理敏感或结果未知任务，操作者逐项核对；批量适合同一种已修复的环境故障，但先抽样验证、设限速并保留可停止开关。批量重放的每张任务仍有独立状态和动作键，不能只记“本批成功 98%”。剩下 2% 的失败要重新分类，不能自动循环把它们又倒回主队列。旧问题修好后出现新错误，是新证据，可能需要另一位负责人。

隔离队列的访问权限也要收紧。里面的原始输入可能含仓库路径、内部错误日志或客户资料；为排障方便把完整消息公开给所有人，会把故障恢复变成数据泄露。待处理页按角色展示必要字段，原始日志另走受控链接，导出和批量重放都留审计。队列任务保留期限与业务记录相匹配；过期前提醒负责人处理，过期后按政策归档或清理，不能让十年前的坏任务某天又被误重放。

## “毒消息”也可能是代码缺陷，不一定是用户填错

第二周又出现一批任务被隔离，错误都是 <code>schema_version_unsupported</code>。领导说：“用户怎么老传错格式？”小陈查到是新版本 Agent 工具先上线，队列里仍有旧版本任务，消费者只认新 schema。把旧任务全当坏输入会冤枉用户。错误分类里应包含生产者版本、消费者版本和迁移路径；若可安全迁移，生成新输入版本并批量回放；若数据缺失无法迁移，交负责人补救。坏任务是“当前消费者处理不了的任务”，原因可能在输入、代码、配置或权限，责任不能一股脑推给提交人。

**领导：**那隔离率高的时候要不要暂停全队列？

**小陈：**看故障范围。单张任务缺字段，隔离它即可；同一版本的任务大面积失败，可能是发布缺陷，应暂停受影响消费者或回滚，不让成千上万条消息冲进死信队列。监控按错误类别、任务来源、版本、仓库和时间聚合；如果突然集中出现，触发事故调查。队列深度本身不能说明原因，隔离增长的形状才能提示是个别坏任务还是系统性故障。

顺序要求也要写在设计里。若某仓库的任务必须按先后执行，把第一张任务隔离后让后续同仓库任务继续，可能违反业务依赖；这时需要把同一任务组设为受阻，而让其他仓库继续。AWS 的[SQS 死信队列文档](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)提醒严格顺序场景要谨慎使用死信队列。小陈把“不卡全公司”和“不打乱同一仓库的必要顺序”分开处理：隔离范围是有依赖的任务组，不是整条全局队列，也不是只看单条消息。

## 看板不能只报成功数，还要报欠了多少笔修复

小陈给值班面板加四组数：主队列等待与最老任务时间，按错误类别的隔离数，待人工处理时长，重放后再次失败比例。若主队列吞吐恢复但隔离队列一直增长，说明系统只是把问题扫到角落；若重放失败率高，说明修复条件没定义清楚。每条隔离任务必须有负责人和到期提醒，长期无人处理升级给对应服务负责人。面板还显示“结果未知”的外部动作数，这是不能靠简单重放消掉的欠账。

**领导：**能不能只按隔离总数做 KPI？

**小陈：**总数容易误导。发布一个更严格的输入校验，短期隔离数会上升，但无效任务更早被发现，可能是改善；故障恢复后批量回放，隔离数下降，也可能只是错误又流回主队列。要联看正常任务完成时延、重复副作用、人工处理时长和客户未结问题。坏任务被隔离是必要动作，任务最终有明确去向才算恢复闭环。

## 隔离队列不是垃圾桶，要有人能把任务救回来

小陈为被移出的任务保留原任务键、原始输入、输入版本、失败步骤、错误类型、尝试次数、最后有效检查点、工作区引用、外部动作状态和负责团队。缺仓库 ID 的任务进入“待补输入”，平台服务故障持续超时的任务进入“待环境恢复”，PR 结果未知进入“待对账”。可以物理上用一个死信队列，也可用任务表不同状态，但用户界面必须能按原因找人、设置时限和查看证据，不能把所有问题塞成“失败 20 条”。

**领导：**有了待处理队列，后面的任务就能继续？

**小陈：**前提是消费策略别被单个任务霸占。调度器确认坏任务已从主队列移出，租约释放，正常任务按优先级继续；隔离队列另有处理者和告警。不能只在界面隐藏坏任务，后台 Worker 仍反复领取它。也不能因为一个输入错误，就把同一客户或同一仓库的所有任务都隔离，除非它们共享确实故障的资源。隔离粒度要与错误传播范围一致。

死信任务还要有生命周期：首次隔离时间、最后处理时间、处理人、修复动作、重放记录和最终去向。若超过处理时限，告警升级；若被人工认定不再需要，标取消并说明原因，不直接删除；若修复了输入，生成新的输入版本，保留原任务键和历史错误。AWS 的队列死信功能负责搬消息，企业业务状态仍要自己设计。否则从主队列消失的任务会在一周后变成客户投诉：“我提交的 issue 怎么无声无息没了？”

## 重放前的“有没有做过”比“能不能再试”更重要

领导试着补上仓库 ID 后按“重新运行”。小陈拦住：这张任务虽然读仓库失败了六十七次，理论上没写代码，但不能凭印象判断。先查工具轨迹是否仅有读取请求，是否有同一个任务键的其他 Worker、是否有人手动建了 PR。若全是只读失败，按新输入版本重放风险低；若已存在工作区或 PR，恢复到已知进度，不从头再做；若外部结果未知，保持隔离直到对账结束。重放是一项有前置条件的动作，不是一个把失败记录清空的按钮。

**领导：**人工补字段以后，为什么还用原任务键？

**小陈：**因为它仍是同一张 issue 的同一逻辑目标。换任务键会让 PR 去重、预算和审计链断开，系统误以为是全新任务。输入版本可以递增，说明这次修了什么；任务身份保持不变。若业务目标真的改变，比如原来修验证码现在要改登录方式，才应由负责人创建新工作单元并链接旧任务。靠换名字绕过失败状态，是最危险的“恢复”。

演练时，小陈故意放三张任务进队列：一张缺仓库 ID、一张外部服务返回临时 503、一张输入完整且可运行。验收要求第三张不被第一张卡住；第二张在退避后有限次恢复或隔离；第一张被移到待处理，补字段后用原任务键回放，不产生重复 PR。再加一张“创建 PR 响应未知”的任务，检查它不被自动重投，而是先查远端。四类任务各有结局，队列吞吐和正确性都能看见。

**领导：**明早面板上那张“失败任务”会显示什么？

**小陈：**显示“待补仓库 ID；已尝试 2 次后隔离；未产生代码或 PR；负责人：研发平台；后续任务正常运行”。昨天的六十七次重试不再出现。领导要催，可以催具体负责人；平台要修，可以看具体字段；Agent 可以去处理下一张有条件成功的 issue。真正可靠的队列，不是每张任务都永远重试，而是每张任务都有清楚、可恢复的去向。

小陈把演练结果又写成值班手册：如果见到单条 <code>missing_repo_id</code>，修输入并按原任务键回放；如果同版本大批任务报 schema 错，先暂停该消费者并查发布；如果是 503 集中出现，按下游健康与限流提示退避，避免群体重试；如果创建 PR 结果未知，直接进对账队列。值班人不必背所有框架术语，只要顺着错误类别找到对应动作和联系人。

**领导：**那“重试”按钮还留着吗？

**小陈：**留，但按钮上要写明条件和后果。可重试的只读任务显示“限次重试”；待补输入的显示“修复后重放”；结果未知的显示“先核查远端”，未核查前不允许直接重发。有副作用动作若支持明确幂等键，也要展示使用哪个键。界面上的三个不同动作，比一个醒目的“再试一次”更能救周末。

上线后第一周，小陈抽检所有从隔离队列回流的任务，核对输入修复版本、重放开始位置、外部动作台账与最终交付证据。若同一任务被隔离两次却错误原因没变，说明修复过程本身失败，应升级给负责人，不继续循环。若任务在等待人工期间被客户取消，重放必须拒绝。待处理队列是业务责任的暂存处，不是自动化把难题偷偷藏起来的抽屉。

领导后来问“为什么正常任务今天都完成了，那张坏任务还在待处理？”小陈把处理单打开：缺失的仓库 ID 有三个候选，项目负责人尚未确认目标；系统已经列出候选来源和各自权限，没擅自选择。下一步是负责人在今天下班前确认一个仓库，确认后只读预检，再从保存的检查点继续。这样等待有名字、有期限、有证据，不会被含糊写成“Agent 还在努力”。

若负责人到期仍未确认，系统升级提醒而不自动猜一个仓库；若确认的仓库与原任务权限不符，退回澄清。隔离任务因此有明确出口，正常任务也不用陪它排队。值班人还要检查隔离队列自身的处理时限，免得主队列通畅后，坏任务又在另一个角落里无声过期。
