**领导：**新退货政策周五生效，知识库里把旧文件替换掉不就行了？

**小陈：**周五有人只换了文件，提示词仍写“签收后七天”，检索索引一半是新版，一半是旧版。正在处理的工单查第一步时看到旧规则，写草稿时又看到新规则。周一客服以为 Agent 学会了穿越。

**领导：**那我们把所有东西一起更新。

**小陈：**先打包成一次可识别的发布：`release_id` 绑定政策文件版本、生效范围与时间、索引快照、提示词和路由配置、工具权限、模型配置、评测集版本。每张工单开始时固定该发布版本；运行中不悄悄切换。新规则若有法定或业务生效时点，发布时间也必须跟它对齐，不能因为技术部署早了就提前对客户生效。

**领导：**影子运行和灰度怎么做？

**小陈：**影子运行读真实的脱敏工单，但**不向客户发送、不执行写操作**；与当前版本并排产出内部草稿，客服和规则负责人看差异。通过后先让少量有审核员覆盖的工单走新版，按风险分层，持续观察错引规则、错误承诺、漏转人工、技术错误和响应时间。扩大比例只在预先写下的门槛内进行。安全发布和分阶段部署也见 [Microsoft Azure 的部署实践](https://learn.microsoft.com/en-us/azure/well-architected/operational-excellence/safe-deployments)。

**领导：**周一发现错了，回滚能把已经发给客户的话收回来吗？

**小陈：**收不回来。回滚只能阻止**之后**的工单继续用错版本；已发错的单要按 `release_id` 找出影响范围，由客服核实、纠正并记录。未发送草稿和正在跑的工单按风险暂停，重新评估后再决定沿旧版完成还是重启，不能把半程工单混着跑。

**领导：**给我发布当天的清单。

**小陈：**发布单必须有：规则负责人的生效确认、版本清单、固定难题集通过记录、影子差异、灰度比例和审核覆盖、监控阈值、回滚负责人和演练结果。发现错误规则被引用、未经批准承诺或跨客户访问，立即停止扩大并回滚到上一套**完整发布包**；告警和回滚时间留痕。验收再抽任一线上答复，查得出它属于哪个发布版本和哪份规则。这样周一至少不用靠猜上周五到底改了什么。

## 一份政策变更，怎么变成四处不同步

**领导：**我明明只改了退货政策，为什么提示词、索引、工具权限也得管？

**小陈：**因为 Agent 给客户答复时不是只读一份文件。它可能先由路由器判断问题类型，再从知识索引找规则，再按提示词把规则与订单事实结合，还可能调用退货资格工具，最后经过审核或发送服务。只更新文件，索引未重建，旧片段仍能被检索；索引更新了，提示词里硬编码的“签收后七天”仍可覆盖新条款；工具字段未适配新规则，模型看到的资格标记仍按旧口径。四处不一致会让同一张单前后两步引用不同版本。

发布包因此不是把所有代码物理打进一个压缩文件，而是一份**可复现的配置清单**：政策文件 ID 与版本、生效时间和适用人群、索引构建代号、提示词版本、路由版本、工具契约版本、模型配置、评测集版本，以及回退目标。运行开始时记录 `release_id`，关键读操作带上相应版本或“按业务生效时间查询”的规则。若系统不能固定索引版本，至少要记录每次检索实际命中的文档版本并在发送前验证，不能假装“同一次运行天然一致”。

**领导：**周五 18:00 生效，下午 16:00 发布索引会怎样？

**小陈：**可以提前构建待生效索引，但对客检索必须按生效时间和业务条件过滤。16:00 的客户仍适用旧政策，18:00 之后的新咨询才看新政策；跨时间点正在处理的工单更复杂，要由业务负责人决定按客户提交时间、处理决定时间还是其他规则判定适用版本，并把这个判定写进发布单。技术部署时间与业务生效时间是两只钟，不能用“代码已上线”替代政策何时对客户生效。

正在跑的工单也不能无声换版本。0823 若 17:59 查到旧规则，18:01 才准备外发，系统应在发送前按业务适用规则检查是否需要重新评估；若新规影响结论，暂停草稿并交人或重跑。简单地“运行开始固定旧版”有时保护一致性，有时会让已失效规则继续对客户说话，必须结合生效边界和已作出的承诺。版本钉住解决技术一致性，业务负责人解决跨时点适用性。

## 影子运行，不是把真实客户交给第二套系统练手

**领导：**影子运行读真实工单，还安全吗？

**小陈：**影子只在已有权限内读必要脱敏材料，不能调用写工具，不能发客户消息，不能改变工单状态。它生成的草稿标“仅内部比较”，只给授权评审看。若新政策需要调用新接口，也先用沙箱或只读查询验证，不能在影子模式里悄悄提交退款。影子运行要记录它用的发布包、与现行版本的结论差异、引用的规则版本和差异原因；不只是把两段文案并排说“新版更顺”。

差异分类很重要：**新政策本该改变结论**，例如退货期限从七天变十天；**不该改变却改变了**，例如发票入口题突然也说能退货；**两版都不确定**，需要业务裁决。评审看的是条件和证据，不是哪个回答更热情。影子期间若发现旧版也有误答，要单独修旧版风险，不能把新版本上线当成事故清零按钮。

**领导：**灰度选谁？随机抽 1% 不就好？

**小陈：**先限定题型与风险，再定比例。可以让有审核员覆盖的低风险单先走新版，对新政策真正相关的场景确保有足够样本；随机 1% 若全是发票入口，根本测不到退货规则。按渠道、地区、客户类型和政策边界分层，观察正常工作时段与高峰时段。微软的安全部署指南强调逐步扩大暴露面、每阶段看健康信号，阶段之间留足观察时间；不该上线五分钟没告警就从 1% 推到 100%。

灰度阶段每张工单记录发布包 ID，客服能看到是否走新版。若同一客户跨渠道追问，系统应关联原单与当时答复版本，避免新旧策略在两处各说各话。灰度分配键要稳定，不能客户刷新页面就随机切换版本；若业务生效时点要求所有客户用同一政策，灰度可只灰度**Agent 的处理方式**，不能让不同客户被适用不同法定或已公告的业务规则。业务政策一致性高于实验方便。

## 监控不能只看报错率，还要看它说错了什么

**领导：**新版本技术错误率零，是不是可以扩大？

**小陈：**还要看业务健康。检索是否引用失效规则，退货资格判断是否与批准政策一致，客服改稿和否决率是否升高，是否出现未经审批的承诺，客户是否复联，人工队列是否积压。技术上 HTTP 200、模型正常生成，仍可能高效地说错话。灰度看板按题型和版本对照，不把旧版发票入口题的好成绩冲淡新版退货边界题的错误。

发布前写好**停止扩大**与**立即回退**条件：跨客户取数、越权写动作、错误承诺等红线出现就暂停相关自动路径；一般质量指标连续偏离基线也暂停观察，查清后再放量。阈值由业务风险和历史数据定，不能事故发生后临时改成“再等等看”。客服和技术值班人都要知道开关在哪、谁能操作、操作后的工单去哪里。回退开关必须演练，不能只在控制台截图里存在。

**领导：**如果旧版也有错，回滚到旧版岂不是倒退？

**小陈：**回滚目标必须是**已知可用的完整发布包**，并按故障范围选择：若新索引错了，可暂停受影响题型自动答复，交人工审核，同时修索引；若新版提示词整体漏掉限制，可回到上一套组合；若旧政策已经失效，不能为图技术方便把客户答复回滚到旧政策，可能需要临时人工流程或快速修复新规则的技术实现。回滚不是“把所有文件按日期往前复制”，而是在业务正确性与技术稳定性之间选一个仍合法可用的安全状态。

## 回滚只能止住新错，发出去的话要逐单处理

**领导：**周一上午发现 50 张单引用错规则，回滚后它们会自动恢复？

**小陈：**不会。回滚只影响下一次运行。先按 `release_id`、政策版本和错误引用定位候选，再分层：哪些只是影子草稿，哪些在客服待审，哪些已经批准但未发送，哪些已对外发出，哪些引发了退款或退货动作。待审草稿可撤销重生成；已发送的要由客服核对正确结论并按影响程度更正；已执行的业务动作可能需要业务补救，不能把数据库版本回滚当客户问题解决。影响表每张单有负责人和状态。

对正在跑的任务，先暂停危险写动作与外发，记录当前运行版本和已发生的工具回执。恢复后判断是沿原版本继续安全完成、用新版本重新查证，还是交人。不能把半程运行的检查点悄悄指向另一版索引，制造“前半段按旧规则查，后半段按新规则答”的混血工单。若已经有退款申请结果未知，先按原业务键查回执，别让重跑造成第二笔。

**领导：**你说回滚要演练，具体演什么？

**小陈：**演练从发现错误引用开始：值班人多久能暂停相关题型，能否把新工单导向人工草稿，能否查询当前所有运行中的发布包，能否让上一套安全配置恢复并用固定样本验证，能否列出已发错的候选工单。演练用虚构数据，不向客户发消息。回滚记录操作者、时间、原因、前后发布包、验证结果；失败了有第二条降级路径。工作日能演，周五晚才有把握按按钮。

## 发布单在手，领导继续问五个问题

**领导：**第一，政策文件改了，索引还没建完，能发布吗？

**小陈：**不能把它当已完成发布。待生效文件与旧索引可并存，但对客路径必须指向经过验证的适用版本；索引构建和线上查询均有回执。构建失败就暂停该题型自动答复或留在仍适用的安全流程。

**领导：**第二，影子运行与灰度差别？

**小陈：**影子不影响客户和业务状态，只供内部比较；灰度让限定真实流量使用新版处理，因此必须有健康门槛、审核覆盖、回退和影响追踪。两者都需要版本清单，但客户风险不同。

**领导：**第三，回滚为什么不一定能回旧政策？

**小陈：**旧政策可能已到期，回去就会继续答错。技术上能回退版本，不代表业务上可继续适用。必要时把相关自动处理退回人工，等正确的新版本修复后再放开。

**领导：**第四，为什么运行要记录 release ID？

**小陈：**事故时能从一条客户答复还原模型、提示、索引、政策、工具和评测的组合，圈出影响范围，复现错误并验证修复。不然“周五到底改了什么”会变成全公司猜谜。

**领导：**第五，谁决定扩大灰度？

**小陈：**技术负责人看服务健康，业务规则负责人看政策适用与错答，客服负责人看人工承接和客户反馈；按发布单事先写好的门槛共同决定。一个绿灯不能替三方承担后果。小陈拿起发布单最后一栏：“停止扩大与回退负责人”。领导终于没有问“能不能今晚全量”，只问“回滚按钮谁试过”。

## 把周五这次发布排成一条能执行的时间线

**领导：**文章讲得好听，下午五点开发布会，你给我从头到尾怎么排。

**小陈：**先在变更单里写政策的业务生效时间、适用人群、例外和对存量工单的处理方式；规则负责人确认，知识负责人将旧新条目状态与索引计划对齐。工程打出不可变的发布清单，列明每个组件版本和哈希。离线回放至少覆盖旧政策适用场景、新政策适用场景、生效前后边界、签收争议、工具超时与人工交接。失败样本不是等领导会上点出来才补，发布门槛事前写好。若临近生效仍有红线题失败，启用人工过渡流程，不用“先上线再观察”赌客户。

接着跑影子比较，选择已脱敏且有权限的实际工单，核对新版是否只在该改变的地方改变；未改变的发票、物流等题型也要抽样防串台。客服和业务负责人确认差异后，在新规则生效的窗口内做带人工审核的小流量灰度。阶段之间留足观察时间，覆盖不同班次和正常流量，不要只有发布后五分钟、三张工单就宣布稳定。放量看版本级指标和抽样内容，任何红线出现立即停。发布当天留技术、规则和客服三位值班联系人，谁接告警、谁改话术、谁联系客户都明确。

**领导：**如果周五晚样本不够，周一才有业务高峰呢？

**小陈：**那就保持小流量或人工审核覆盖到周一高峰，别用周五夜里的安静证明周一白天的安全。发布窗口选择本身就是风险控制：能否在问题暴露时找到有权决策的人，能否观察到代表性流量，能否及时回退。政策生效时间可能不能改，自动化开放时间可以更保守；业务需要准时执行新政策时，先让人工按新规则处理，Agent 等验证够了再扩大。这样既不拖业务政策，也不让客户替系统冒险。

## 发布包里的版本关系，需要机器能校验

**领导：**版本都列了，系统怎么防止人把 v4 规则配到 v3 索引？

**小陈：**发布流水线检查依赖：索引构建输入包含预期知识版本；提示词引用的规则 ID 在发布包里存在且状态正确；路由输出的工具契约版本能被当前服务接受；评测运行的配置哈希与拟发布配置一致。构建后用线上同一查询路径做冒烟测试，不只看后台“索引完成”。如果发布清单与实际服务返回版本不符，发布失败。这样 `release_id` 不是文档上的编号，而是一次可复查的组合。

数据库和缓存也要考虑版本兼容。若新工具字段 `return_eligibility` 替代旧字段，灰度期间新旧运行可能并存，工具适配器需同时理解两版，或把旧运行安全停下再迁移；不能先删旧字段让还在跑的工单崩掉。知识缓存以版本为键并在撤回时失效，搜索索引如果异步更新，要等查询回执确认再放流量。越是跨多个系统的发布，越需要明确“已提交”“已构建”“已对客可用”三种状态。

**领导：**热修复能不能跳过影子和评测？客户正在收到错答。

**小陈：**可以加速流程，不能不要证据。先暂停错误路径和外发止血，再做最小修复；针对事故样本及相邻反例跑快速回归，确认线上版本与回退方案，带人工审核小范围恢复。完整回归可以随后补跑，但谁批准加速、跳过了哪些常规检查、补检何时完成要写清。微软的安全部署指南也强调紧急变更可以调整审批和观察时间，但应有明确协议和补检。事故时更要防“修旧错造新错”。

## 回滚演练里，最容易漏掉的是客户与数据

**领导：**程序回旧版、索引切回旧快照，回滚不就结束？

**小陈：**只对还未发生的运行可能有效。已发给客户的话、已提交的退货申请、已写入工单的承诺都不会跟着版本指针倒退。演练要把工单分组：未开始、运行中未外发、待人工审核、已外发、已执行写动作。未开始的进安全发布包；运行中的冻结检查点与回执，决定重跑或转人；待审草稿撤回旧批准；已外发的核影响并更正；写动作按业务系统结果处理，不能重新提交。每组有不同负责人和完成凭证。

若发布包里包含数据库结构或知识条目状态迁移，技术回滚也未必是逆向一键。迁移可能不可逆，旧代码未必能读新字段；要在发布前设计兼容窗口、备份与恢复验证。若无法回到旧组合，就启用安全降级：暂停相关自动答复，保留工单与人工通道，修复新版本后再灰度。把“回滚不可行时怎么办”写进发布单，比事故发生时才发现按钮灰了强。

**领导：**怎么确认周一的事故处理完？

**小陈：**技术侧确认错误发布包不再处理新单，线上查询不会返回错误知识，运行中任务已分流；客服侧确认已发错客户清单有负责人、更正或补救已完成，未结案件仍按承诺推进；业务侧确认新政策实际适用没有被错误回滚。指标恢复绿色只是一个信号，最老一张受影响工单如果仍无人负责，事故就没有结束。领导在复盘会上该问的不是“按钮按了没有”，而是“错版本还会不会再答、已经答错的人有没有被接住”。
