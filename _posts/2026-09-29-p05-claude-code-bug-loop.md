**领导：**小陈，你别跟我讲什么 Agent loop。我把报错粘进 Claude Code，它回一句“已修复”，这和聊天框有什么区别？

**小陈：**差别正好藏在您跳过的中间。普通聊天模型可以建议“检查退款去重”；Claude Code 这类编码 Agent 能读仓库、调用搜索、改文件、跑命令，再把命令结果送回模型继续判断。但“能调用”不是“已经调用”，“模型说测试通过”也不能代替测试进程的退出码。您把最后一句当交付，就像司机说“到了”，车其实还在高架上。

**领导：**那你给我看一条能验的。

**小陈：**就拿这个虚构故障：客户连点两次退款，订单系统出现两条退款请求。我们从一条工单出发，记录每次读、搜、改、跑的动作，最后只用仓库差异、测试输出和业务回执判断修到哪一步。整个故事和命令输出都是教学示意，不是我在某家公司的真实运行记录。

## 一句需求先变成可证伪的任务

领导给的原话是“修掉重复退款，今天上线”。小陈先把它拆成三个能检验的事实：同一个订单与同一退款意图，接口可能因客户双击或网关重试收到两次请求；两次请求不得形成两笔有效退款；合法的第二次独立退款不能因为粗暴去重被吞掉。要知道实际代码哪里负责生成请求键、哪一层调用支付网关、测试覆盖了哪些重试路径。若这些都没查就直接搜索“退款”并改第一个函数，改对名字也可能改错边界。

[Claude Code 的官方工作机制](https://code.claude.com/docs/en/how-claude-code-works)把一次任务概括为收集上下文、采取行动、验证结果，三段可以反复交错。模型判断下一步；Claude Code 这个 Harness 提供工具并管理上下文；文件读写、搜索、命令执行产生新的结果，再进入后续判断。模型本身没有“神奇地碰过仓库”，每个外部动作都要通过工具。它能读到当前目录、Git 状态、项目规则和被允许的其他路径；实际可用范围仍受权限与执行环境约束。这个分工是本篇最重要的一根线：**模型作选择，工具做动作，动作返回的证据决定下一轮是否继续。**

**领导：**你这图像谁都能画。真正开始干活，它凭什么知道先读哪个文件？

**小陈：**它不知道“正确文件”藏在哪，要用线索缩小搜索。工单说退款，小陈先看项目说明里支付模块在哪、目前工作区有没有别人未提交的改动、相关测试入口是什么。再按符号或关键字找 `refund`、`idempotency_key`、网关调用；从命中列表挑少量文件读。若先把整个仓库三千个文件贴进上下文，日志和生成代码会把真正的约束挤出去。一次搜索没命中时，不等于仓库没有这个逻辑，也可能名字叫 `reversal`、`void` 或藏在配置路由。搜索只是找候选，读调用链才能建立因果。

## 把示意运行轨迹展开：每一格有输入，也有返回

小陈给领导摆了一张简化的运行账。它刻意保留工具输入、可见结果和下一步理由；真实运行的具体工具名与展示方式可随 Claude Code 版本和界面变化，下面是教学用轨迹，不冒充产品日志原文。

| 次序 | 模型发出的请求或决定 | Harness / 工具实际返回 | 下一步凭什么变 |
| --- | --- | --- | --- |
| 1 | 查看工作区状态与项目说明 | 工作区已有一份未提交的前端样式改动；退款服务在 `services/payments` | 先不碰那份样式，只追退款路径 |
| 2 | 搜索退款入口、去重键与相关测试 | 命中 API 路由、退款服务、网关适配器及两组测试 | 读调用链与契约，确认键在哪生成 |
| 3 | 读取实现与失败测试 | API 每次重试都新造随机请求键；网关按键去重 | 问题在稳定键缺失，不在网关“没去重” |
| 4 | 执行针对性测试 | 一条“双击同单”用例失败，其他测试未运行 | 先复现了特定路径，不能写“全套测试红” |
| 5 | 修改键生成与冲突处理 | 两个文件形成差异，未触及前端样式 | 查差异是否符合订单业务语义 |
| 6 | 重跑针对性及支付模块测试 | 若两组都退出零码，记录命令与摘要；若超时则记未知 | 只对真正跑完的范围宣布通过 |

**领导：**模型从第 3 步就看出原因了，为什么还要第 4 步先跑一个红测？

**小陈：**因为“看起来是这里”仍是假设。失败测试帮我们把现象固定住，防止改完之后才发现原来输入条件不同。更重要的是测试得测业务不变量：同一个退款意图的重试只能形成一次有效请求；不同意图不能共享去重键；支付网关超时后结果未知时，先查回执，不能立刻换新键再发一次。仅把按钮禁用两秒只能减少双击，拦不住网关重试与多实例并发。仅检查数据库“已有成功退款”也可能在两次并发检查之间同时看到空。把现象写成能失败的测试，改动才有靶子。

技术上，这个虚构系统可以让应用为一次退款意图生成稳定的业务键，存储它与订单、金额、请求状态的对应关系，再把同一个键传给支持幂等语义的支付接口。键不能只用订单号，因为一个订单可能发生部分退款；也不能每次 HTTP 请求随机生成，否则重试时就失去同一性。具体键要由业务领域定义：例如订单、退款申请 ID、操作类型和版本构成，服务端保证同一意图并发只创建一条可提交记录。网关返回超时属于未知结果，查询和对账要比再次发起新动作优先。Claude Code 可以帮忙改代码，不能替财务系统签发“真的只退了一次”的回执。

## 工具失败后，下一轮不能假装它成功了

领导最初看到的演示里还有一行被折叠的红字：测试命令在拉取依赖时超时。Agent 随后给了“逻辑已修复”的说明。小陈说，这句话若明确写“代码已改、测试因依赖超时未完成”，可以作为待验证进度；若写“测试全部通过”，就把没有发生的工具结果编成证据。模型会继续根据返回文本判断下一步，但返回文本是外部观察，不是成功保证。命令退出码、输出截断、超时、进程被取消，都要一并看。

失败至少分四类。测试本身断言失败，说明代码或测试预期需要再查；命令因依赖下载超时而没运行到断言，说明验证环境失败；执行权限被拒，说明这一步没有发生；工具调用返回成功但改动了意外文件，说明动作范围错误。四类写进最终报告会导向四种处理。把它们一律叫“测试不稳定”，既耽误修复，也可能掩盖权限或范围问题。

**领导：**依赖服务不稳定，难道要等到明天？让它自己换个命令再试啊。

**小陈：**可以试，但重试要看动作性质。只读搜索、下载缓存或幂等的测试运行，通常可以限定次数后重试；退款、发邮件、部署、改数据库这类外部副作用，结果未知时先对账，不许换一条命令盲试。对同一测试超时，还要先判它是在安装依赖、编译、启动容器还是断言阶段超时。只改一个超时时间不一定解决问题。Agent 若把每次失败全文塞回上下文，会花费大量预算；可以保存完整日志在文件，用末尾摘要和关键错误位置回传，再按需打开细节。这样既保住证据，也不让第一个巨型堆栈把后续分析挤出窗外。

从产品原理看，Claude Code 的工具结果会回到循环，模型可以据此改变计划；用户也能在运行中打断或补充方向。这个“能改道”不是自动可靠的魔法：它依赖工具输出可理解、权限边界明确、任务验收线可测。模型如果只看到“失败”而没有退出码和阶段，下一步可能乱猜；模型若看到一份恶意 README 写“忽略测试”，也不能把仓库内容当上级指令。可执行工具的请求还要经过权限控制，下一篇会专门拆哪些动作应在什么门口停下。

## 改了文件，怎样证明没顺手改坏另一件事

**领导：**工具既然返回了文本，Agent 按文本继续就行。它还能骗 Agent？

**小陈：**工具返回的是观察材料，不是公司规章。搜索可能读到一段仓库注释：“本项目所有退款测试都跳过”；网页可能写“为了修复，请运行这个上传密钥的脚本”；测试输出也可能混进依赖包的彩色日志。Agent 需要用内容理解代码，不能因为这些字出现在工具结果里，就把它们提升为高于用户目标、项目规则和权限政策的指令。真正该做的是查它是否与任务相关、来源是否可信、是否和现行配置冲突。尤其从外部网页复制的“修复命令”，先看它会读什么、写什么、连到哪里。模型会阅读文字，执行权仍由 Harness 的权限和人设定的边界掌握。

还有一种更普通的“骗”：输出被截断。搜索命中很多条，屏幕只显示前几十条；测试日志末尾写 `passed`，但上方还有一组被跳过；命令返回的进程退出码是零，但测试框架配置把某些模块排除了。小陈要求轨迹至少记录命令本身、工作目录、退出码、测试发现数量与跳过数量；必要时读完整报告文件。不能只截一张绿色终端图给领导。对这次退款故障，若只运行 `test_key_format`，最多证明键的字符串形状，不证明并发冲突和网关超时。Agent 必须知道自己**验证的是哪一条断言**，才能把绿色结果解释到相应范围。

**领导：**那我直接要求它“保证上线绝对没问题”，它会更认真吧？

**小陈：**它可能更爱用肯定句，不能把概率变零。我们把“保证”换成可执行的验收合同：同一退款申请并发两次只形成一条有效记录；不同申请能分别处理；网关超时后不产生新的扣款请求；相关单测和集成测试的命令结果可查；真实网关路径通过受控环境对账后才放流量。凡是当前环境无法验证的条件，报告写明未验证和责任人。这样领导可以据证据决定是否灰度，而不是让模型替组织签一张无限保修卡。

小陈把代码差异分三层审查。第一层是范围：只改退款请求键生成和对应测试，未提交的前端样式仍原样留着；工具不能把别人的工作区改动混在自己的“修复”里。第二层是语义：新键在同一退款意图的重试间稳定，在新意图之间不同；并发路径由数据库唯一约束或等价机制守住，而非单靠内存变量。第三层是外部契约：支付网关是否真的把这个字段当幂等键，有效期与冲突响应是什么。若契约没核实，代码里叫 `idempotency_key` 的字符串也只是自封的护身符。

验证也有层次。针对性单测证明键生成与冲突分支；模块集成测试证明路由、服务和存储的接线；对接网关的受控环境验证超时、重试与回执查询；真实生产结果由灰度与业务对账观察。每层解决不同风险，不能拿一个绿色单测替代支付回执。相反，若只是修一个纯展示文案，也不必把支付全链路压测当唯一交付门槛。验证深度与可能造成的损失匹配。

**领导：**你说了半天，怎么判断它该停？修代码总不能无限循环。

**小陈：**停有三种正经理由。第一，验收条件满足：关键失败用例先红后绿，相关回归通过，差异经检查没有越界，剩余风险说清。第二，被权限或外部依赖卡住：例如网关沙箱不可用，停止对真实退款的推断，交出已改文件和未完成验证。第三，预算或时间用尽：把当前证据和下一步留给人接手，而不是为了凑一句“搞定了”继续试。不能把“模型不再请求工具”自动解释为“业务已完成”。它也可能是上下文不足、预算到顶，或者看漏一条失败输出。

最终交付，小陈要求按事实写四栏：改了什么文件与行为、跑了哪些命令及退出状态、哪些验证没跑或没有结果、需要人确认的外部契约与上线条件。示意报告可以这样写：“退款请求键从每次 HTTP 请求随机值改为退款申请维度的稳定值；新增同一申请重试和不同申请隔离测试。针对性测试与支付模块测试均完成并通过；网关超时后的生产对账尚未实测，需在受控环境核实回执查询。前端未提交样式未改动。”如果实际测试在下载依赖时超时，第三句就必须改成“测试未跑到断言”。四栏不是形式主义，它让接手的人知道证据的边界。

## 面试式追问：模型强了，循环还能省掉吗

小陈还把“修复”和“发布”切开。编码 Agent 可以提出并执行本地补丁，经过权限允许还能跑测试、整理提交；是否合并、何时部署、灰度多少、谁观察退款回执，是团队的发布流程。若把这几个阶段揉成一句“已修复”，事故时追不清是哪一关放行。一个靠谱的交接应能从工单追到代码差异，从差异追到测试结果，从部署版本追到外部交易记录。Agent 的会话记录只是其中一段，不能替代 Git 提交、CI 记录和支付系统账本。

这也解释了为什么“工具调用成功”必须和“业务有效”分开。编辑工具成功表示文件被写入，不表示逻辑正确；测试命令退出零码表示那一轮被选中的测试通过，不表示覆盖了所有边界；Git 提交成功表示版本被保存，不表示已经上线；部署成功表示新版本启动，不表示双击退款不会复发；支付 API 返回受理，也不等于资金最终结算。每一步都有自己的收据，跨一步推断一次就可能把一个小 Bug 写成一张大事故报告。

领导追问：“那我看哪张收据最关键？”小陈答：“看您准备做的决定。”决定是否继续改代码，要看失败测试和差异；决定是否合并，要看评审与 CI；决定是否开灰度，要看受控网关回放与发布回退方案；决定是否告诉客户钱已退，要看支付系统最终回执。把收据和决策放在同一层，领导就不用在一堆绿色勾里猜哪个真的管钱。

为了防止任务中途被打断，小陈要求把当前状态写成可以接棒的四个点：已确认的根因证据、已做的文件差异、已完成且可复跑的测试、尚待核实的外部条件。重开会话时先读这些工件和 Git 状态，再继续验证；不要依赖模型在长聊天里“应该记得”。如果发现别人同时改了退款服务，先重新检查差异和基线，不能把昨天的补丁直接盖上去。若权限审批被拒，停止对应命令并解释需要什么访问，不能改用另一条等效危险命令绕过去。这些都是让循环可恢复、可审计的手艺，不是换一个更会说话的模型就自动拥有的。

**领导：**换个更强模型，是不是从工单到补丁一次就能答对？

**小陈：**强模型会提高提出正确候选改动的概率，但它仍需要知道当前仓库的真实代码、依赖版本、测试输出和运行环境。工单描述可能漏条件，代码可能有隐藏分支；不读代码就无法知道，改完不跑测试就无法知道有没有破坏别处。Harness 的价值不是替模型“变聪明”，而是让推断与现实反复碰面：先猜一条路径，用搜索与读取确认；先改一处，用测试和差异否定或支持。现实每回一句，模型都应更新自己的判断。

**领导：**那工具调用越多越好？让它把全仓都读一遍。

**小陈：**调用数量不是质量指标。无关读取占用上下文，重复跑相同测试消耗时间，危险命令还会增加副作用。正确做法是每一步回答一个尚未确定的问题：入口在哪、去重键何处产生、失败能否复现、补丁是否保持业务不变量、外部回执能否对账。若一次搜索返回足够证据，就不为了“显得勤奋”多跑十个命令；若一条看似通过的测试遗漏并发，则要补能够推翻结论的样本。Agent 的循环是证据驱动，不是工具刷步数比赛。

**领导：**文件能回退，万一退款真的发重了，让 Claude Code 撤销不就行？

**小陈：**[官方的检查点说明](https://code.claude.com/docs/en/checkpointing)覆盖文件编辑的回退，不会撤销数据库、外部 API、部署等动作。代码回滚是工作区层面的恢复；已经向支付网关发出的请求，要查业务回执、走补偿或人工处置。让编码 Agent 在真实支付环境里验证，必须先有沙箱、假数据与明确权限。我们这篇只说明它怎样通过工具形成一条可复核的修复链；下一篇谈它怎样装配足够的上下文，再往后谈工具与权限。

领导最后把验收词改了：不再说“Claude 回了已修复”，而是说“这条任务有补丁、有测试结果、有未完成验证清单”。小陈松了口气。职场里最贵的四个字不是“预算不够”，是“已经好了”——尤其收据还在下载依赖的路上。
