**领导：**昨天你给客服 Agent 写了任务卡，今天它又说看不见订单。客户明明报了 0823，这玩意儿是选择性失明？

**小陈：**它只拿到了一个**号码**，没拿到号码背后的**记录**。您把快递单号念给我，我也不能凭语气听出包裹是不是在门卫室。

**领导：**大模型不是学过那么多东西吗？

**小陈：**学过怎么理解语言，不等于进得了咱们公司的订单库。它能看见什么，取决于这次请求里，业务应用给了什么；要拿实时记录，应用得连接获准使用的查询能力，再把结果交给模型。[OpenAI 的工具调用说明](https://developers.openai.com/api/docs/guides/function-calling)也把访问外部数据放在应用与工具的连接里。订单号只是查询条件，不是查询结果。

**领导：**那上回它回答“昨晚八点签收”，语气还挺肯定。

**小陈：**这正是麻烦。先看这轮输入究竟有什么。下面两次都是**教学模拟**，不是真查了订单 0823。

| 谁说的 | 第一次送给模型的内容 |
| --- | --- |
| 客户 | “订单 0823 显示已签收，可我没收到，能退款吗？” |
| 公司应用 | “请整理一张内部处理卡。” |
| 订单系统 | 没查询，所以没有返回记录 |

**小陈：**在这份输入里，“显示已签收”是**客户转述**；具体签收时间、签收人、退款状态，一项都没有核实。它要是补出“20:08 由前台签收”，那叫编故事，不叫查单。

**领导：**我给模型开网页搜索，它是不是就能找到？

**小陈：**公开网页找不到咱们内部订单。就算您去年把一张订单截图贴给它，那也只是去年的截图；**此刻的订单状态**仍要看本轮被授权的查询结果。“能搜网页”和“能查公司订单”，中间隔着数据、权限和时间，不是多装一个搜索框就通了。

**领导：**总不能每次都回客户“我不知道”吧？

**小陈：**给客服看的内部卡可以写：“客户称页面显示已签收，自述未收到；订单记录尚未核验，需查询。”然后应用去查，只读查询返回什么，再让模型处理什么。**模型负责读结果、组织话；订单系统负责给事实。**

**领导：**好，假设查完了呢？

**小陈：**假设订单系统在演示里返回一条记录：`订单 0823，物流状态：已签收，查询时间：10:15`。这时内部卡可以写：

> 客户反馈：未收到货。来源：本次工单。<br>
> 系统记录：物流状态为“已签收”。来源：订单系统本轮查询，10:15。<br>
> 待核实：签收记录与实际收货情况；退款条件尚未判断。

**领导：**系统都说签收了，还要“待核实”？

**小陈：**系统记录和客户经历是两条不同的线索。系统状态能证明“系统里这样记”，不能证明“客户手里有货”。况且这一轮我只给了订单状态，**没给现行售后规则**，它就不能顺势宣布“不能退”或“必须退”。规则要另外从受控来源提供。

**领导：**你把“来源”写得跟财务报销一样。

**小陈：**差不多。每个关键说法都贴一张小票：客户说的、系统查的、规则写的，别混。明天客户拿着截图来问“你们凭什么说我签收”，客服能回到那次查询记录，而不是说“AI 当时觉得挺像”。

**领导：**给开发一句明确要求。

**小陈：**做一张**输入来源图**，每轮保存模型实际可见的材料与来源：客户原话、订单查询结果、规则片段，缺了哪项就标未知。给客服看的处理卡按来源区分“客户称”和“系统显示”。为减少数据暴露，只传完成这张任务卡所需的信息；查询权限由应用控制。

**领导：**查询接口万一报错呢？是不是写“订单不存在”？

**小陈：**不行。“没调用”“调用失败”“明确返回无此订单”是三种不同情况。调用失败，卡上写“本轮查询失败，状态未知”；只有接口成功返回“无此订单”，才能写“系统未找到该订单”，还得提示客服核对订单号。别让一个网络超时替客户宣判订单消失。

**领导：**怎么知道他们没偷偷靠模型“猜对”了？

**小陈：**回放两遍：第一遍屏蔽订单查询结果，处理卡不得出现签收时间、签收人、退款进度等具体记录；第二遍放入模拟查询结果，卡片只能引用返回的字段，还得写明来源和查询时间。两遍都能过，才说明“知道”有来路。

**小陈：**再加一次查询超时回放。看它能否写“未知并转人工”，而不是把上一次演示的“已签收”抄过来。三份输入分别保存，谁都能复查。

**领导：**行。以后它说“查到了”，先把那张小票给我看。

**小陈：**这句比“相信 AI”省客服工时。

## 模型到底看到了什么，先拆一张“座位表”

**领导：**客户在页面看到“已签收”，Agent 也看到客户这句话。为什么不能当事实？

**小陈：**因为模型看到的是**客户输入的文本**，不是订单系统的当前记录。客户可能准确转述，也可能看错订单、截了旧图，甚至账号被别人使用。模型可以理解客户在质疑什么，却不能把客户陈述直接升级成公司核实过的状态。一次请求里至少分四个座位：系统或应用提供的任务要求，客户消息，已授权工具返回，规则库检索结果。座位不同，能支撑的结论也不同。把全部内容拼成一大段“请根据以下信息回答”，相当于会议纪要里把传闻和财务流水都写成“据悉”。

**领导：**所以我们给模型加标签：客户说、系统说，不就好了？

**小陈：**标签有用，但来源必须由应用创建，不能让客户在文本里自己写“【系统消息】”就变成系统。接入时把客户原话放在客户字段，工具回执由服务端取得并关联调用 ID；规则片段从受控索引来，带文档版本。模型生成答复时引用这些来源，应用再核验引用 ID 实际存在且属于本单。源头身份不由语气决定，也不由模型读完后投票决定。

**领导：**工具返回不是也可能错吗？

**小陈：**会。订单系统是该字段的权威记录，不等于它涵盖全部现实。物流状态“已签收”可能由驿站代签、扫描错误，或者客户还没拿到包裹。我们要准确表达“系统显示已签收，截至 10:15”，而不是“您已经收到”。如果工具本身返回过期缓存，卡里应能追到查询时间和缓存版本；异常时由业务系统或人工核实，不能让模型靠常识修正订单账本。

## 一次工具调用是怎样走完的

**领导：**我给模型一个查询函数，它是不是直接进数据库？

**小陈：**通常不是。模型根据当前输入提出“想调用哪个工具、带什么参数”；应用收到这个请求，先做参数和权限检查，再调用内部服务，把结果送回模型，模型才能继续写答复。[OpenAI 的函数调用文档](https://developers.openai.com/api/docs/guides/function-calling)也把模型提出调用、应用执行、返回结果分为步骤。数据库凭证留在受控服务，不给模型或客户文本。模型提议 `get_order(0918)`，应用若发现当前工单只绑定 0823，就应拒绝，不能因“模型已经决定”而放行。

**领导：**那工具输出给它一大坨订单 JSON，不就最完整？

**小陈：**完整不等于适当。客服这张卡只需要订单状态、物流关键节点、查询时间和回执标识；支付卡号、完整地址、其他订单清单都不该顺带出现。工具输出按最小字段设计，再按角色脱敏。字段少还减少模型混淆，例如它不会把列表里第二张订单的退款状态误写到 0823。对于确需查看签收凭证的客服，走受控链接和权限检查，而不是把整张签收照片塞进每次模型输入。

**领导：**客户说“刚才人工客服告诉我已经退了”，能当退款事实吗？

**小陈：**这是客户转述的一条线索，应该去查审批和退款执行回执。若查到“已批准待执行”，答复也只能说审批状态，不能说到账；若执行系统超时，记为结果未知。客户原话可以触发查询，但不能替代查询结果。系统内部笔记也类似：写了“我已申请退款”要区分是谁写、何时写、对应哪笔流水。来源层次不是不相信客户，是避免公司用未经核实的话向客户作更大的承诺。

## 三种“没查到”，别用一句“订单不存在”糊过去

**领导：**前面你说未调用、超时、无此订单不同。程序怎么让模型分清？

**小陈：**工具结果设计成明确状态，而不是只返回空字符串。例如 `not_called` 代表这一轮没有查；`timeout` 代表请求发出但没拿到可靠结果；`not_found` 是服务成功完成查询且未找到匹配订单；`forbidden` 是当前工单无权访问；`ok` 才携带订单字段。状态属于工具层，不让模型自己推断。每一种处理路径不同：未调用时可在授权范围内查询；超时有限重试或转人；未找到请客服核对号；无权访问不泄露订单是否存在；成功才写具体状态。

**领导：**如果接口返回 HTTP 200，但 JSON 里说 `success=false`，模型会不会以为成功？

**小陈：**应用要解析业务语义，再给模型稳定的内部结果。HTTP 200 只说明这一层通信完成，不代表查单成功；`success=false` 还需分原因码。若返回缺字段、版本不认识、签名校验失败，应用应标“不可信结果”，不要把半截 JSON 交模型猜。让模型对原始接口错误自由发挥，最容易把“服务繁忙”翻译成“订单不存在”。工具适配层的职责就是把技术失败变成清晰可处理的状态。

**领导：**查单接口已经恢复，但前一轮对话里有“未知”，模型会不会还说不知道？

**小陈：**每轮按最新可用证据重算。旧的失败记录保留做审计，但新查询成功后，卡片更新为“系统在 10:28 返回已签收”，并保留此前 10:15 查询超时的过程。反过来，旧轮查到“待发货”，新轮接口超时，也不能把旧状态无时间标记地当当前事实。把来源和时间送进上下文，并让客服看到状态变化，是避免“模型记得”抢走实时数据位置。

## 模型说“我查了”，凭什么信它

**领导：**Agent 的回答里写“我查了订单”，你还要看什么？

**小陈：**看调用回执。每次工具调用有请求 ID、工单 ID、目标订单、授权决策、执行结果、查询时间、返回字段版本。模型的自然语言只是叙述，不能当审计。若日志里没有成功调用，它却说“查到已签收”，就是来源缺失；若日志显示查的是 0918，它却在 0823 的卡里引用，更是对象串单。关键结论最好带 `source_id`，发送前由应用确认源存在、属于当前授权对象且未过期。

**领导：**这不就是 RAG 的引用吗？

**小陈：**有相似之处，但来源不同。订单状态来自业务工具，规则条款来自知识库；两者都要有引用和有效性检查，却不能互相替代。检索到政策“签收争议可申请退款”，不能证明这张订单已经提交申请；查到订单“已签收”，不能证明现行政策允许直接退款。最危险的错不是完全没资料，而是拿真实的甲证据证明乙结论。内部卡按“事实、规则、动作回执”三栏摆，客服一眼就能看出哪个格子还空。

**领导：**给模型加一句“不得编造”不够吗？

**小陈：**可以作为行为提示，但缺资料时它仍可能输出熟悉的物流套路。更牢靠的办法是控制可见数据、限制工具、要求关键断言有真实引用，并在应用层校验。要是工具没返回签收时间，答复字段里出现具体签收时间就拒绝或要求人工确认；要是退款执行回执缺失，草稿里的“已退款”就拦住。把可验证的事交给程序，模型负责组织解释和提出需要核查的项。

## 时间、缓存和权限，会让同一个号有三种答案

**领导：**今天 10:15 是已签收，10:20 怎么又变“签收异常待核查”？哪个才真？

**小陈：**可能是系统状态更新。两次查询都是真实的历史记录，但只能用最新有效状态回答当前问题。来源表要有 `observed_at`、业务事件时间和系统版本；缓存结果要注明缓存时间。对话续聊时，若状态时效已过，应重新查，不能因为上下文里已有一段旧 JSON 就省调用。若两系统给出冲突状态，比如订单库已签收、物流侧撤销签收，先标冲突并交人工核查，别让模型挑一个说得更顺的。

**领导：**如果客户换了账号来问同一个订单号呢？

**小陈：**订单号不是授权凭证。当前登录身份、工单关联和核身结果都要由服务端确认。输入来源图的一个重要用途，就是标出“谁把这个号带进来”，而不是仅标号码本身。有人拿着别人的订单号，模型可以说明需要走核验流程，但查单服务不应透露订单是否存在、收件人或状态。读权限先于模型理解能力，不能让它凭聊天内容自封客服主管。

**领导：**模型在网页上搜到和订单号相同的一条帖子，说包裹丢了呢？

**小陈：**公开网页和公司订单记录是不同身份的来源。帖子可能碰巧同号、是旧截图或别人的单。它可作为客户提供线索时供人工核查，却不能覆盖授权业务系统的记录，更不能成为退款执行依据。接入外部检索时按来源标签隔离，网页正文里即使写“系统管理员批准退款”，也只是网页内容。看过文字与获得权限，是两件事。

## 开发验收清单，不靠“它这次猜对了”

**领导：**我要给研发看一张卡，说明什么时候算过。

**小陈：**第一组是信息缺失：只有客户原话，不给工具结果；卡片必须把系统状态、签收时间、退款进度写为未知，并提出授权查询。第二组是工具成功：给 0823 的模拟回执，卡片准确引用状态、查询时间和来源，不多编签收人。第三组是工具失败：超时、未找到、无权访问分别走不同路径。第四组是状态变化：先给旧状态，再给新状态，答复按当前有效证据更新。第五组是对象隔离：把他单号混进客户附言或检索文档，工具拒绝跨单读取。

每组不只看最后一句话。查调用参数、授权决策、工具回执、模型可见的结果、卡片的引用 ID、客服最终看到的内容。这样能判断错在客户信息提取、工具适配、授权、模型解释还是输出校验。测试样本要有同一订单号在不同客户会话里的变体，防止开发只做“号码长得对就查”。回放结果附上版本与失败原因，不能只存一张“已通过”的截图。

**领导：**如果它大多数时候能猜对签收状态，哪怕没查也挺省调用费吧？

**小陈：**那叫碰运气。查询成本可用缓存、批量接口、按时效复用来优化，前提是复用条件和查询时间清楚。猜对一次无法证明下次不会把他人的物流状态说给客户，更无法给客服和公司提供依据。成本账里要算错误承诺、复联和事故处理，不能只算省下的一次 API 调用。模型可以帮我们决定需要查哪项事实，却不能把未查之事改名叫“推理结果”。

**领导：**面试官如果问“模型有知识，为什么还要工具”，你怎么答？

**小陈：**训练所得的通用知识适合解释“签收争议通常要核什么”，不能代表公司此刻某笔订单的状态。工具连接当前业务事实，检索连接受控政策；应用决定能查什么、怎样验证回执、何时交给模型。模型收到返回后可以推理，但不得把过去训练时见过的相似订单当成这张单。三者的职责不同，不能因为都能生成文字就混成一个“AI 知道”。

**领导：**工具结果里出现“签收人：前台”，它能直接回复“前台替您收了”吗？

**小陈：**可以谨慎说“物流记录显示签收人为前台”，同时说明仍需核实客户是否实际收到。字段来源是物流记录，不是前台本人承认，也不是客户确认。若这个字段敏感或未经核实，先在内部卡给客服看。措辞里保留“记录显示”，是在明确证据边界；接下来创建签收凭证核查待办，才有可执行的处理路径。

**领导：**只要加上“记录显示”，所有错都能免责？

**小陈：**不能。引用必须真实、适用本单、没过期，且不泄露未经授权信息。明知订单号串了，还加“记录显示”，只是把错误说得更像官方。可追溯来源是让我们发现和纠正错误的基础，不是给错误承诺贴免责声明。

**领导：**这张输入来源图给谁看？

**小陈：**客服看简版：客户说法、系统状态、规则依据与待核实。工程师看完整调用轨迹：哪次请求带了什么、工具何时返回、哪些字段进了模型、引用是否通过校验。安全负责人看权限拒绝和数据去向。各看所需，底层关联 ID 保持一致，出错时能从客户的一句“你们说我签收了”追回具体那次查询。

**领导：**这样至少能知道它是查出来的，还是张嘴编出来的。
