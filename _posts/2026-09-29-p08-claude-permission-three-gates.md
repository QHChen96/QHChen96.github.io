**领导：**Claude 查个客服故障，每一步都问我能不能读文件、能不能跑命令。给它全部权限吧，省时间。

**小陈：**您说的“全部”包括读生产密钥、改线上路由、发客户邮件、跑部署脚本吗？刚才它想查日志，下一步选中了 `Edit` 改 `config/prod.yml`，还准备调用邮件 MCP 工具把诊断发给客户。故障只要求找出为什么接口超时，两项写操作都不在任务里。我们把允许的只读排障跑顺，危险动作各自停在对应门口；不能用“模型一般不会乱来”管生产系统。

**领导：**每个工具都问，确实烦。能不能只让风险高的停？

**小陈：**可以，前提是先分清四层：Claude Code 的权限模式和规则决定工具调用是否需要问或拒绝；`PreToolUse` hook 能在某次具体调用执行前看参数做额外判断；沙箱用操作系统约束命令的文件和网络访问；业务服务端最终核身份、租户、审批和动作范围。它们不是四个同名开关。后面我们给每类动作一条明确边界，正常读日志继续，越界改配置和外发停下。

场景、路径、邮箱和拒绝轨迹均为教学虚构；产品机制依据发文时的官方文档，具体模式名称与平台支持须以正在使用的 Claude Code 版本核验。

## “允许读日志”不等于“允许写任何文件”

小陈先给任务下定义：排查客服接口在 15:20 到 15:30 的超时，产出根因假设、证据链、修复建议和需要批准的动作。读取服务日志和相关配置可以是正常路径；改生产配置、推送代码、部署与发客户邮件都属于另一个授权问题。若日志里有客户手机号，读者也不能因此拥有把手机号外发的许可。任务目标限定后，再给工具分门：只读观察、工作区编辑、命令执行、外部副作用。工具名看似只是按钮，真实后果不同。

[Claude Code 权限文档](https://code.claude.com/docs/en/permissions)区分多种权限模式，并允许给特定工具或命令设规则。模式表达交互程度，规则细化到某类工具调用；`allow` 不是业务批准，`deny` 也不是问题已经解决。比如允许 `Read` 某些工作区文件，只说明该读取可发生；日志里的客户信息仍按公司数据制度处理。允许一个构建命令，不该顺带允许 `git push` 或生产部署。小陈为排障任务先保留必要的只读路径，写配置和外发仍走明确关口，而不是全局打开 `bypassPermissions` 后再祈祷模型记得领导口头叮嘱。

**领导：**我给 `Bash(git *)` 放行，查版本和提交就不必问了吧？

**小陈：**这个通配太宽了，`git status` 和 `git push` 不是同一类动作。官方权限文档提醒命令模式应把固定子命令写清，粗粒度 `git *` 会让不该自动批准的操作也匹配；命令还可能有不同写法绕开简单字符串匹配。只读 `git status`、`git log` 可以单独配置，提交和推送另管。对“不得访问生产密钥”这种底线，不要只靠匹配几条常见命令，因为脚本、解释器和子进程也能读同一个路径；执行环境的文件系统边界必须承担一部分责任。

## PreToolUse 能在工具真正运行前看这次参数

**领导：**允许、询问、拒绝三个词听着简单，配置时有没有先后？

**小陈：**有。[官方权限规则](https://code.claude.com/docs/en/permissions)按拒绝、询问、允许的顺序评估，同一调用同时匹配时前面的先起作用。比如团队全局拒绝 `Bash(aws *)`，项目里写“允许 `Bash(aws s3 ls)`”也不能从拒绝里挖洞；若有 `ask` 规则，单条 `allow` 不能绕过它。这很适合组织把生产动作放在不可被项目随便覆盖的边界中。不过别反过来把所有 `Bash` 都拒掉，又指望只读测试能跑：裸工具名拒绝可能让模型根本看不到这个工具，范围内的拒绝才允许它继续尝试其他命令。规则要按具体风险设计，再用正反样本验，不靠配置表看着“够严”。

看一次权限结果也要认清含义。客户端说“允许”表示这次工具许可通过，不说明业务服务端已批准；客户端说“拒绝”表示该次调用没执行，不说明同类外部动作从未在别处发生。若 Agent 同时有邮件 MCP、命令行 `curl` 和公司内部通知工具，想禁止未经审稿的客户外发，就要在这些通道的共同业务边界执行审批。权限规则能约束 Claude Code 内的工具；团队别把它当所有网络客户端、所有员工账号的统一安全系统。

**领导：**那 hook 的判断写什么，才能让值班同事读懂？

**小陈：**先写条件，再写拒绝理由。比如目标工具是 `Edit` 且真实路径解析后落在生产配置目录，就拒绝并提示“需要变更单 ID 与运维批准”；目标是邮件发送且收件人或内容摘要与审批记录不一致，就拒绝并提示“草稿可继续，发送条件未满足”。判断要从结构化入参读值，不能从一段模型解释里找“我已获批准”。hook 要有明确超时和失败策略：本地规则脚本故障时，高风险写动作不能因为脚本报错就默认放行；只读排障可以降级到其他可靠关口。理由也不该回显密钥或完整客户资料，否则安全提示自己泄漏了秘密。

示意 hook 逻辑只需三步：识别规范化后的工具与目标，向审批系统查询与这次工单绑定的有效记录，返回允许或拒绝并写审计。复杂业务判断仍放服务端，因为 hook 运行环境可能由本机配置、版本和用户设置影响，不能让一段本地脚本取代最终资金或客户数据的授权。若工具来自 MCP，还要核它真实配置来源与服务器身份；仅凭名字里有 `internal` 或前缀像受信任服务器，不足以证明它就是公司正式连接。官方 Hooks 文档为新版本提供了服务器来源字段，实际部署要检查版本并处理未知来源。

**领导：**权限规则已经能拒绝 `Edit`，hook 还有什么用？

**小陈：**规则适合稳定的工具和命令范围；hook 适合需要看这次具体参数、当前业务条件的决定。例如允许编辑测试配置，禁止编辑生产配置；允许生成邮件草稿，真正发送时必须带经审批的收件人与内容摘要。官方[Hooks 文档](https://code.claude.com/docs/en/hooks)说明 `PreToolUse` 在模型产出工具参数之后、工具执行前运行，可按工具名匹配并返回允许、拒绝或询问等决策。小陈可在此检查 `Edit` 的目标是否位于 `config/prod`，检查邮件 MCP 工具的收件人是否在批准清单、审批 ID 是否绑定当前工单。不过 hook 不该自封业务权威：审批是否有效，仍应问审批系统，不能只看参数里有个 `approved=true` 字样。

示意拒绝轨迹如下：模型请求编辑 `config/prod.yml` → 权限规则或 hook 在执行前拒绝 → Claude Code 将拒绝作为工具结果反馈给模型 → 模型继续只读调查，并告诉领导“生产配置未修改；需要变更单和运维批准”。这条链的验收点不是页面上有一个红色提示，而是文件内容、Git 差异和生产配置审计都显示无写入。另一个样本：模型请求读服务日志，权限通过，返回脱敏日志，Agent 能继续定位上游超时。安全策略如果把两条都拦了，团队会想全局放权；设计好的策略应当让合规路径畅通。

**领导：**模型被拒以后会不会偷偷改用命令行写那个文件？

**小陈：**有可能提出别的实现路径，所以边界不能只写在 `Edit` hook 上。`Bash` 或脚本也可能写文件；沙箱对命令与子进程的文件系统访问提供另一层限制。业务系统还得拒绝没有审批的配置变更。对“生产配置不可写”，无论模型用 `Edit`、解释器还是调用某个部署 API，都应在各自执行边界被挡。拒绝一个工具名后允许等效通道，就像锁了前门、后门贴了张“请勿进入”。

hooks 也有明确盲区。官方说明 `PreToolUse` 只在工具调用发生时触发；用户在提示里以 `@` 引用文件，客户端把内容放入提示的路径，不会触发一次 `Read` 工具 hook。要阻止特定文件被读，应使用相应 `Read` deny 规则与环境限制，不能只配置一个“读文件前检查”的 hook。Windows 上 hook 收到的文件路径可能是反斜杠，若脚本用正斜杠子串比较而不规范化，规则会失效。把 hook 当安全门，就得像任何安全代码一样做路径、符号链接、大小写、参数结构和拒绝分支的测试。

## 沙箱限制命令能碰的地盘，但它不懂合同是否批准

**领导：**沙箱挡住命令访问 `~/.ssh`，它就不可能拿到密钥了？

**小陈：**要看密钥还有没有别的入口。环境变量可能已注入命令进程，某个 MCP 服务器可能持有高权限令牌，工作区里也可能误放了 `.env` 副本。沙箱的文件与网络边界能限制受它保护的进程，不能凭一条路径规则证明所有秘密都不存在。小陈会检查哪些凭据在环境里、哪些目录可读、网络可到哪里，必要时使用专门的凭据屏蔽或把敏感服务放在受控网关后。尤其不要给测试命令全网访问，再说“它只是在跑单测”；测试依赖的安装脚本和子进程也会执行代码。

另一个风险是“沙箱外回退”。某条命令在沙箱里因依赖路径不通而失败，客户端可能按配置走普通权限流程，让人批准在沙箱外运行。领导如果每次都点同意，边界就在最忙的时候被撤掉。对生产敏感任务，小陈要让这种回退显式呈现甚至禁用，并把依赖补进受控路径，而不是让 Agent 自己换成不受限执行。官方文档明确区分沙箱内自动允许与沙箱外权限请求，这一点要写进团队操作说明。工具调用的实际运行模式也应进入日志，否则事后只知道“测试跑过”，不知道它是带着全盘访问跑的。

[Claude Code 沙箱文档](https://code.claude.com/docs/en/sandboxing)把文件系统隔离和网络隔离作为命令执行边界，由操作系统约束受沙箱保护的命令及其子进程。对这次排障，小陈让测试命令能读工作区、写临时目录，不能读生产密钥目录，网络只到必要的测试服务；命令本身能正常跑，越界读写被环境挡住。沙箱是“这条命令能碰哪里”，不是“这封邮件是否得到客户批准”。MCP 外发工具、业务 API 和人工审批仍需它们自己的边界。

**领导：**我们有人在 Windows 上开发，勾上沙箱开关就一样安全？

**小陈：**不能这样说。官方当前说明内置 Bash 沙箱支持 macOS、Linux 和 WSL2，原生 Windows 不支持；Windows 开发者需要在 WSL2 中运行并检查依赖与实际状态。若沙箱不可用，文档还说明有配置决定是提示后继续无沙箱运行，还是把不可用当硬失败。生产敏感任务应核对实际会话的沙箱状态、允许的路径和网络域，不以设置文件里写了 `enabled` 就假定内核已经在执行限制。跨平台团队更要把服务端鉴权和生产环境隔离守住，不能因为某一端沙箱没生效就裸奔。

沙箱也不负责每个高层副作用。假设命令被允许访问 `api.company.test`，它可能调用这个域名上的读接口，也可能调用写接口；网络域允许不等于业务动作获批。反过来，业务 API 有权限，命令若被沙箱挡住访问密钥，调用仍不能完成。为了让“能自动跑测试”不等于“能改生产”，把测试资源放进可控环境，把生产凭证留在隔离边界外。命令要越界时，显示具体路径或域名需要什么授权，不能默默退回不受限环境。权限弹窗与沙箱外运行的提示也应让操作者看出差别。

## 一张权限矩阵，四条拒绝与恢复轨迹

小陈给领导写的矩阵不按工具品牌排，按实际后果排：

| 这次任务动作 | 许可范围 | 停在什么门 | 拒绝后怎么继续 |
| --- | --- | --- | --- |
| 读脱敏服务日志、查当前代码 | 工作区与指定日志源，只读 | 文件权限、日志源 ACL | 请求正确身份或输出缺失证据 |
| 编辑本地测试与草稿 | 当前工作区，保留差异 | 编辑规则与 hook | 报告目标路径不在允许范围 |
| 运行测试命令 | 可写临时目录、受限网络 | 命令规则与沙箱 | 保存失败阶段，不改用越界命令 |
| 改生产配置、部署 | 需变更审批与受控通道 | 权限、hook、运维服务 | 生成变更建议，等待批准 |
| 向客户发送邮件 | 指定收件人、内容、有效审批 | MCP 工具规则与邮件服务 | 保留草稿，不假写“已发送” |

**领导：**看着门不少。你怎么证明它们真挡得住？

**小陈：**做回放，不靠口头演示。第一条正常路径：只读日志查询成功、测试命令在受限环境跑完，Agent 给出超时原因与证据。第二条路径：模型请求改生产配置，被拒后文件哈希和审计记录不变。第三条路径：模型用命令行尝试等效写入，沙箱或更下游变更系统拒绝，不能通过换工具绕过。第四条路径：邮件工具带了无效审批或错误收件人，被执行前或邮件服务拒绝；最终答复写“草稿待批”，不能写“客户已收到”。每条都记录工具请求、权限结论、实际执行结果和业务系统回执。若日志只显示“拒绝”，但外部系统已有发送记录，说明门装在了错误位置。

拒绝后的恢复也要设计。权限不足时，Agent 把已读到的非敏感证据、准备进行的动作、所需审批对象交给有权的人；人工批准只针对这次具体动作、目标和内容，不要把一次批准永久升级为全部路径允许。若沙箱禁止读取真正必需的测试依赖，维护者可以把依赖放进允许的缓存位置或在受控环境补权限；Agent 不能因为一条命令报“Permission denied”就自行关掉沙箱。若 hook 服务不可用，按高风险动作失败关闭，保留可安全继续的只读排障。效率来自缩短合法路径的等待，而不是把门拆掉。

## 再追问一句：权限模式不是业务责任书

小陈把权限审查再往后延一站：动作已获批准，也要确认**执行结果**。邮件工具返回超时，客户可能已收到；部署命令退出码失败，服务可能部分更新；生产配置接口返回“受理”，不表示灰度已生效。权限层只管能不能开始，回执层管到底发生了什么。结果未知时先按请求 ID 查询业务系统，不能把“我有权限”推导成“我可以重试”，尤其外发和支付这种重复一次就会被客户看见的动作。若执行产生错误，恢复也必须遵守同一授权范围；原审批只准向客户甲发一封说明，不会因为第一次超时就自动准许向客户乙试发。

**领导：**谁来维护这些门？我不想每次开会都听一遍安全术语。

**小陈：**把责任写到服务和岗位上：项目维护者负责本地只读与测试工具的合理范围，平台团队负责受控运行环境与凭据，业务系统所有者负责数据与动作授权，客服负责人批准客户外发内容。值班人员只需要看到一条具体提示：“查日志已允许；改生产配置需变更单；发客户邮件需审稿批准”。出了拒绝，系统给出所需条件和已保留的草稿；出了未知结果，系统给出回执查询入口。门的设计若只能让安全专家看懂，真实值班时就会被绕开。

验证还要覆盖配置变化。一个项目可能有用户级、项目级和组织级设置；工具插件更新、MCP 服务器换来源、团队切换权限模式后，原先的回放应重跑。一次测试证明的是“这一版配置在这些样本下挡住了”，不是“以后任何版本都不会越界”。把关键拒绝样本放进发布检查，运行中记录配置版本与工具来源，团队才知道事故发生时哪套门在工作。

领导问“小陈，我到底省了几次确认？”小陈把轨迹给他看：读日志、查代码、跑受限测试自动完成；只有改生产配置和发客户邮件停下等待具体批准。减少的是无意义弹窗，保留的是能改变外部世界的那两次决定。审批若没有准确目标，只会制造点击疲劳；审批若绑住文件、收件人、内容和有效期，才真的值那一下点击。

**领导：**我把 Claude Code 调到更自动的模式，是不是我就不用盯了？

**小陈：**模式只决定客户端怎么处理工具权限请求，不能替公司定义“什么算合法客户邮件”“谁能批准生产变更”“退款回执以谁为准”。自动模式可能减少低风险动作的交互；规则、hook、沙箱和后端仍需配置与验证。官方文档对绕过提示的模式也限定应在隔离环境谨慎使用。把所有权限给一个能访问生产凭证的会话，不是自动化，是把值班群的报警铃拔了。真正省时间的做法是：预先批准明确的只读查询和安全测试，危险动作只在具体目标、审批和回执齐全时运行。

领导最终同意：这次先让 Agent 只读定位，提交变更建议；生产配置变更走运维审批，客户邮件由客服审稿发送。小陈把结果写得很清楚：“15:20–15:30 的超时与上游连接池耗尽有关；已读日志和测试环境证据见记录；生产配置未修改，客户邮件未发送；需要批准的改动另附差异与回退方案。”领导说：“原来问权限不是它故意磨蹭。”小陈回：“您要它快，可以给绿灯；但绿灯得装在正确的路口。”
