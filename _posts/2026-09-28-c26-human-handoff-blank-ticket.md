**领导：**Agent 遇到签收争议已经会转人工了，怎么客服满意度还往下掉？

**小陈：**我坐在客服旁边接了一单。客户说“显示签收但没收到”；Agent 问过订单号、查过签收状态、找过现行规则，然后屏幕显示“已转人工”。客服打开的是一张只有客户名字和工单号的白纸，又问：“您方便提供一下订单号吗？”客户回了一句：“我刚刚不是说了吗？”

转接按钮正常，交接失败。客服要的不是模型写一篇《客户情绪观察报告》，而是**下一步处理所需、可核实、带来源的事实**。小陈当场把那张白纸改成交接卡。

## 一张能让人接着做的卡

**小陈：**卡片不超过一屏，字段却不能偷懒。虚构工单 0823 的交接如下：

> **客户诉求：**系统显示已签收，客户说未收到，希望核查并问能否退款。  
> **身份与工单：**已按客服流程核验当前客户与本单归属；工单 ID 0823。  
> **已核事实：**订单工具 16:02 返回“已签收”，查询回执 `q-781`；现行签收争议规则版本 `v4` 要求先核对签收凭证。  
> **尚未确认：**签收人、投递照片和客户实际收货情况；是否符合退款条件。  
> **已做动作：**给客户发过“正在核查”的批准回复；尚未创建退款。  
> **下一步：**物流调查签收凭证，客服小陈在本班结束前查看回执并更新客户。  
> **转人原因：**订单状态与客户陈述冲突，需要人工核查，Agent 不得直接承诺退款。

**领导：**Agent 摘要要是写错了，客服不是更容易被骗？

**小陈：**所以“客户说”“系统查到”“Agent 推断”分开标。订单状态来自工具回执，政策来自可点开的版本条款；客户陈述原文只摘必要片段；模型推断不得填进“已核事实”。客服点回证据就能复核。卡片里不复制完整地址、手机号，跨班交接仍按工单权限读附件。

**领导：**那“已转人工”这句话什么时候能说？

**小陈：**分三态：`已入人工队列`、`客服已接手`、`处理完成`。系统只把工单放进队列时，对客户说“已提交给客服团队”，不要说“某位客服正在处理”；有人确认接手，才显示接手人和预计的下一次更新方式。若队列满了或系统异常，保留工单待办并告警，不能把客户丢在机器人和人工之间。接手人也能把处理结果、缺失字段和纠错反馈写回交接卡，供后续评测和知识修复。

**领导：**转接时 Agent 还在生成，客服接了之后它又补一句，会不会把人说的话顶掉？

**小陈：**会，所以转接是一次所有权切换。工单系统接收转人请求，先把 Agent 的当前草稿冻结成版本 3；客服接手时确认版本 3 的交接卡，系统把对客发送权交给客服。此后 Agent 只可补充内部查证建议，不能继续自动外发。若客服接手前发现订单状态变了，交接卡标“证据已更新”，生成版本 4 等待确认，不悄悄覆盖客服正在看的版本。发送权与卡片版本都由系统校验，不靠两边“自觉别抢”。

队列也可能把卡交丢：入队请求成功但回执超时，不能立刻再建一张新单。先按工单 ID 查询队列里是否已有待办；存在就补记回执，不存在且确认未建才用同一业务键重试；仍不明就交值班人核对。客户看到的仍是同一张工单和下一次更新承诺，不会因为后台重试收到三条“已为您转人工”。

小陈给交接过程定了三个回执。第一，**生成回执**：交接卡写入工单，能查到版本和来源，失败就保留 Agent 侧待办并告警。第二，**入队回执**：人工队列接受工单，返回队列 ID 与预期值班组，尚无人接手时保持待办状态。第三，**接手回执**：具体客服确认，并获得对客回复权。客服在接手页能一键指出“订单证据已过期”“缺少客户诉求”“下一步没有负责人”；这不是抱怨按钮，而是让交接质量变成可统计的修复任务。

**领导：**客户刚转人工又来一句“其实是另一张订单”，卡不是瞬间过期了吗？

**小陈：**新消息继续挂原工单，但标记“交接后新增”。它不会抹掉卡片版本 3；客服接手页显示差异，提醒重新核订单归属。如果新订单属于另一位客户或另一件事，先核身份再分单，不能直接把新订单塞进旧卡。交接卡是一份带时间戳的快照，不是永远正确的圣旨。

验收让一位**没参与前半段对话**的客服接手：不再追问已核验的订单号，能在卡上找到现行规则和未决项；如证据链接失效或身份未核验，卡片必须显眼标出，不能假装已查。再故意让人工队列无人接，确认工单不会消失，并按时升级给班次负责人。客户能少讲一遍，客服才真算接到单。

## 先把“交接”两个字拆开

**领导：**技术同学说框架里已经有 `handoff`，你是不是又造轮子？

**小陈：**得看看那只轮子装在哪辆车上。多 Agent 框架里的 handoff，通常指一个 Agent 把当前任务交给另一个 Agent，运行时决定下一位由谁继续生成。这个能力很有用，但它不知道我们的客服何时上班、哪个队列能接签收争议、工单是否成功入队，也不会自动把客户的服务承诺记成待办。把一次模型控制权转移当作人工接手，就像把会议邀请发出去便宣布会议已开完。

在业务系统里，至少有四件独立的事：**形成可复核的交接资料、把资料和原工单绑定、让人工队列承认自己收到了、让具体的人取得处理权**。其中任何一步失败，处理方式都不同。摘要生成失败，可以用原始会话与工具记录补写；工单写入失败，不能假装人工看到了；队列入队失败，必须保留待处理任务并触发值班告警；无人领取，则要按服务时限升级，而不是让模型再写一段“非常抱歉”。

**领导：**所以“转人工”也要像支付那样认真？

**小陈：**客户等结果的心情，未必比等退款轻松。我们不一定要上复杂的分布式事务，但必须知道每一步是“请求已发出”“对方已确认”还是“结果仍未知”。如果只有一个布尔值 `transferred=true`，它装不下这些区别，故障来了只能靠客服凭空找单。

以 0823 为例，系统先产生 `handoff_requested`，写入卡片版本和关联工单；工单服务返回持久化回执后，才发 `queue_submission_requested`；队列回执带 `queue_item_id`；客服领取时产生 `human_accepted` 和 `owner_id`。这几项事件可以异步发生，但工单页必须能用同一个 `case_id` 串起来。对外展示的话术只依据已确认状态，绝不依据“按钮点击成功”的前端提示。

## 交接卡不是作文，是有类型的证据包

**领导：**卡片字段看着挺全。让模型直接把聊天记录压缩成一段，不也能看？

**小陈：**一段话最容易把三种东西搅在一起。客户说“快递没来”，订单系统只说“已签收”，模型可能补成“快递员疑似代签”。前两句分别是陈述和工具结果，第三句是猜想。摘要写得越流畅，客服越容易把猜想当事实。所以每条信息除了内容，还要有**来源、发生时间、核验状态和权限范围**。

一张可落库的卡，可以先用下面的结构表达。字段名只是示意，关键在含义：

```json
{
  "case_id": "0823",
  "card_version": 3,
  "customer_claims": [
    {"text": "显示签收但未收到", "message_id": "m-201", "at": "16:00"}
  ],
  "verified_facts": [
    {"text": "订单状态为已签收", "tool_receipt": "q-781", "at": "16:02"}
  ],
  "policy_refs": [{"rule_id": "delivery-dispute", "version": "v4"}],
  "unresolved": ["签收人是谁", "是否有投递照片", "退款条件是否满足"],
  "actions_done": [{"type": "customer_reply", "receipt": "r-087"}],
  "next_action": {"type": "check_delivery_proof", "owner_queue": "物流争议"},
  "transfer_reason": "订单状态与客户陈述冲突",
  "privacy_level": "客服工单可见"
}
```

这份结构不是让前台客服读 JSON，而是让系统检查有没有把关键字段漏掉。展示层仍可是一屏自然语言，点击事实能跳到原始回执，点击规则能看到当前有效版本。消息 ID 和回执 ID 是内部索引；对跨组人员只展示其权限允许的内容。订单地址如果用于核验，只保存“已核验”和对应凭证的受控链接，不能把完整地址复制到每张流转卡里。

**领导：**模型把“客户说”塞进 `verified_facts` 怎么办？

**小陈：**结构化输出只能解决格式，不能自动保证事实。入库前做两道校验：`verified_facts` 必须带能访问的工具回执，`policy_refs` 必须带版本；缺任意一个就降为“待核实”，并在卡上亮出来。再抽样回放原消息，核对诉求有没有被摘要改意。客户一句“先查一下，暂时别退款”，如果压缩成“要求退款”，客服照着办就会闯祸。对高风险意图，宁可附一段短原文让客服看，也不要追求摘要优雅。

时效也要写进去。16:02 的签收状态到了 17:40 未必还有效；客服接手前可以重查关键工具，若状态变成“签收异常复核中”，旧事实保留为历史，新增事实进入版本 4。系统展示“旧卡生成于 16:03，订单状态已在 17:40 更新”，而不是覆盖掉旧记录。这样以后有人追问“当时为什么这么判断”，还能回到当时的证据。

## 一条签收争议，跑完整个接力

**领导：**别光讲字段，0823 到底怎么走？

**小陈：**16:00 客户说没收到货；Agent 确认工单归属，查询订单状态，记录 `q-781`。它发现“系统已签收”和“客户未收到”冲突，规则 v4 又要求查凭证，所以停止自动建议退款，产生转接原因。16:03，卡片版本 3 写入工单，工单服务返回 `card_saved`。16:04，队列返回 `queued` 和队列号。此时客户看到的是“已提交客服团队核查，下一次更新将在本班服务时段内发出”，不是“客服正在查”，因为还没有人领取。

16:06 客户补一句：“是尾号 731 的订单，刚才那单我记错了。”这句话作为新消息附在原工单事件流里，并把卡片标为“可能失效”。系统不要替客服静默改掉旧订单，也不要让 Agent 自行把新订单合并进去。先核对尾号 731 是否属于当前已验证身份；若属于且确为同一签收争议，生成版本 4 并标出差异；若不属于，走身份确认或新建案件。16:08 客服领取，看到的是版本 3、待确认的新消息和明确的“订单归属待核”，而不是一段看似确定的结论。

客服接手后先看凭证，不需要再问已核实的订单号。如果凭证里的收件人确实不是客户授权的人，客服按规则走物流调查；如果照片只是门口包裹，客服不能因为系统显示签收就断言客户收到了。调查提交后，工单记录处理动作和下次更新时间。离班时，未结单要交给下一班次或负责人，客户承诺跟着案件走，不跟着某个客服的在线状态消失。

**领导：**听着流程挺顺。故障一定不会这么配合。

**小陈：**那就故意挑三种不配合的场景来验。第一，卡片写入成功但响应超时；按 `case_id + transfer_attempt` 查询已有版本，不能重试出两张版本 3。第二，入队返回超时；先查队列，查不到再用同一幂等键重试，仍无法确认就通知值班人，客户仍留在原工单。第三，客服点击领取时另一位客服也在点；工单服务用版本条件更新，只给一人发送权，另一人收到“已由某某领取”，而不是两个人都给客户发结论。

再加一个最容易漏的：转接触发后 Agent 的流式输出还没结束。如果前端只在聊天窗口关掉机器人按钮，后台任务仍可能把“可以退款”写出去。因此所有对客发送命令都要带当前所有权版本，消息服务在真正发送前核对。所有权不匹配时拒发并记审计事件。UI 禁用只是给人看的，服务端校验才防得住并发。

## 接手人的责任，从哪一秒开始算

**领导：**客服领了单，过半小时不看，也算交接成功？

**小陈：**从技术上看“已领取”，从服务上看还没“已处理”。所以指标要分层。`queue_wait` 是入队到领取的时间；`first_human_action` 是领取到首次有效查看、询证或回复的时间；`customer_update_delay` 是承诺时间到实际更新的偏差。这三个不能合并成一个“转人工耗时”。如果只盯领取速度，客服可能先抢单占坑，客户仍在原地等。

归属同样不能靠一句“转给人工”。接手事件要写 `owner_id`、班次、队列和版本。客服休假或下班时，案件可以换人，但必须有新的领取回执和未完成动作列表。转出者撤销权限，转入者承接客户承诺；案件没有确认新负责人前，原负责人或值班队列仍负责升级。这样才能避免“我以为他接了，他以为我还在看”的经典夹缝。

**领导：**那交接卡缺字段，是阻止转人，还是先让人看？

**小陈：**看缺什么。`case_id`、转接原因、当前诉求、所有权和已做动作缺失，接手人根本无法安全继续，应该阻止“交接完成”并走人工兜底入口。签收照片暂时查不到，却恰恰是转人的理由，不能因为缺照片就不让转。卡上标“待核实”并指定下一步责任人即可。把“必须有答案”设成硬门槛，会逼模型编答案；把“必须明确不知道什么”设成硬门槛，才是可执行的质量要求。

## 怎么知道客户真的少讲了一遍

**领导：**你要向我汇报效果，别拿“卡片生成率 99%”糊弄。

**小陈：**我会看五项。**空白卡率**：接手时缺关键字段的比例；**重复提问率**：客服在接手后再次询问卡上已有且仍有效的信息的比例；**接手确认时长**：入队到明确负责人领取的分布，不只平均值；**失约率**：下一次更新超出承诺窗口的比例；**错证据率**：抽样检查“已核事实”是否真能追到回执。这五项还要按队列、渠道、问题类型切开，不能让简单咨询冲淡签收争议的失败。

重复提问也不能一刀切。有时客户报的订单号和系统归属不一致，客服重问是安全核验；这类问题应标记原因，而不是算交接失败。反过来，客服没重问但照着错误摘要处理，也不是成功。抽样要把客户原话、工具回执、卡片版本和客服动作放在同一条时间线上，让质检人员判断“该问的有没有问，不该问的有没有重复问”。

上线前，小陈会拿四组样本做盲测：正常签收争议、工具状态随后变化、客户补充另一订单、人工队列无人领取。让没参与前半段的客服只凭卡片和允许访问的证据处理，记录他们是否能说出“目前确定什么、还缺什么、我下一步做什么”。如果答不出来，先修卡片和路由，不是催客服“主动一点”。

## 领导的面试题，小陈当场答

**领导：**第一题，摘要和交接卡有什么区别？

**小陈：**摘要为了快速阅读，交接卡为了**继续执行**。后者必须有案件 ID、证据来源、未决项、已做动作、下一步责任和版本；摘要漂亮但没有回执，遇到争议就无法复核。

**领导：**第二题，队列调用超时，直接重试行不行？

**小陈：**先确认结果未知还是明确失败。未知时先按业务键查已有队列项，再用相同幂等键重试；确认失败才新发，且保留原工单待办。否则一个客户可能被三个客服同时联系。

**领导：**第三题，框架自带 Agent handoff，为何还要工单状态机？

**小陈：**框架解决模型运行时谁继续处理；工单状态机解决客户案件是否被持久化、哪支团队接收、谁拥有对客发送权、承诺何时到期。两者可以协作，但业务回执不能由模型控制流替代。

**领导：**第四题，交接后客户又补信息，旧卡删掉重做？

**小陈：**不删。旧卡记录当时判断依据，新消息触发差异提示和新版本。客服确认新版本后继续执行；若涉及另一个身份或案件，先核验再分流。保留版本才能解释为何前后动作不同。

**领导：**第五题，怎样防止机器人和客服一起回复？

**小陈：**对客发送权要有服务端所有权版本。客服领取后，Agent 的自动发送命令即使已经排队，发送前也会因版本不符被拒；内部建议可以继续生成，但不能越过客服发给客户。

**领导：**行。以后谁再把一个“转人工成功”的绿色勾给我看，我就问他：客服收到的到底是接力棒，还是白纸？

**小陈：**还要问“接力棒上写的是谁的事”。一个客户可能同时咨询物流和发票，交接卡不能把两个诉求压成一句“售后问题”。主工单若拆成两个子任务，物流由售后队列接，发票由财务队列接，各自有负责人、回执和期限；对客户仍保留一个可查询的进度入口。任何子任务卡住，主单负责人要负责解释下一次更新，而不能说“已经转给别的部门，我也没办法”。这也是为什么交接卡要记录**下一步由谁做**，而不只是“建议联系某部门”。

上线后还要看权限审计。客服能打开证据链接，意味着该客服对当前案件有访问权，不意味着整支队列都能浏览客户的订单历史。转组时系统重新计算可见范围，已过期的临时链接失效；质检回放用脱敏副本。交接资料越完整，越要防止它变成一份随处转发的客户档案。让接手人少问一次，与让不相干的人多看一眼，不能划等号。
