**领导：**会议纪要已经有了。让 Agent 给所有参会人自动发跟进邮件，省得销售忙忘。

**小陈：**如果照现在这份草稿发，客户会问“你哪位”。它把甲公司的会议内容发给了乙公司一个同名联系人，附件还是上个月作废的报价。省下十分钟，换来十封解释邮件。

**领导：**收件人邮箱总不会认错吧？

**小陈：**邮箱是地址，不是联系理由，也不能证明附件该给这个人。我们把生成、核对、批准、发送、送达状态和 CRM 记录拆开。先做一封能审得懂的邮件，再讨论批量化。

文中的客户、联系人、商机、邮件与附件均为教学虚构。真实对外联系的许可、名单使用、客户偏好和数据处理方式必须由企业按所在地区规则和内部制度确认；这里讲的是技术和业务控制点。

## 邮件开头很热情，客户根本没来过这场会

虚构销售团队刚结束系统对接会。Agent 从会议邀请里抓到“王工”，又在 CRM 里搜到同名联系人。它把邮件正文写得颇有温度：“感谢您今天分享仓库改造需求。”问题是 CRM 里的王工属于乙公司的另一个商机；真正参会的王工在甲公司邮箱，刚入职，尚未关联 CRM。Agent 还从附件库拿了文件名最像“方案报价”的旧版 PDF。销售只看到正文像回事，没展开收件人和附件，点了“全部发送”。乙公司王工回了一句“你哪位”，甲公司客户则还在等清单。

**领导：**这不是模型匹配差？换个模型。

**小陈：**换模型不能替我们决定谁有资格收什么。姓名相同、集团共用邮箱域、参会人转发邀请、客户中途换岗，都不是靠语言理解就能稳定消失的歧义。发送前要拿到“邮件收件地址如何关联本场会议和商机”的证据。找不到，就先列候选让账户负责人确认。附件也要有版本和适用客户范围，不能按文件名相似度直接挑。

第一步做收件人解析。会议系统给出地址，CRM 给出联系人 ID，账户和商机给出关系。只有会议与客户记录关联明确、地址与授权联系人一致，才能进入“待发”候选。若邮件地址不在 CRM，却确实出现在会议里，可由销售手工确认其身份和联系原因，创建或关联联系人；系统不能自行给一个新邮箱加上“采购决策人”标签。若地址属于多人共享邮箱，则正文中的称呼和敏感信息必须重新审查。尤其要查抄送：有时销售只想发给采购负责人并抄送我方方案组，Agent 却把全部参会者包括外部供应商一起带上。

## 个性化不是把名字填进模板里

**领导：**那就给每个人加一句“上次沟通很愉快”，总不会错。

**小陈：**没沟通过的人更想问“上次是哪次”。个性化不是插变量，而是说明这封信与对方什么事情有关。参加接口讨论的人可以收到清单与待确认问题；只参加采购环节的人不一定需要逐项技术字段；未参加会议却负责审批的人，需要由销售解释为什么转给他，而不是 Agent 假装他也在场。

正文每句关键事实都绑定来源。比如“按今天会议约定，我方周四发送字段映射清单”，要能定位到会议纪要里我方确实答应的时间；若会议只说“尽快”，不能替双方约成周四。对“您的团队已经确认方案”，要找客户明确确认的话；找不到就改为“我们整理了一版方案，供您核对”。语气自然可以灵活，事实与承诺不能弹性伸缩。要引用客户行业或新闻，也要确认与本次需求有关且不过期；如果只是为了让模板显得“懂你”，不如不写。

附件单独过一遍，不与正文共用“审核通过”四个字。文件名相同不代表内容相同，链接指向的云文档也可能在审批后被人修改。系统记录固定版本或内容指纹、文件所有者、允许分享的客户范围、下载链接的权限与有效期。方案草稿可以给技术联系人看，不代表底价表也能给采购、顾问或全体参会人看。若附件链接过期，客户收到的是一封看似完成交付、实则打不开的信；发送前至少检查可访问性，发送后客服或销售要能处理“打不开”的反馈。若使用临时链接，不能因为测试账号能打开就断言客户账号能打开，必要时由业务负责人用受限视角验证。

**领导：**附件版本都锁了，报价出了新版怎么办？

**小陈：**旧草稿退回待审。系统把新旧附件的版本、关键价格字段和适用日期列成差异，不自动把最新版替换进已批准邮件。客户此前收到的旧报价也不会因我们更新文件而自行消失；那是另一篇要处理的错误外发事故。今天先保证每一次对外发送到底带了哪一版，事后能说清楚。

发送目标也要具体。跟进邮件可能是交付会中答应的清单、请求客户补资料、确认下一次会议、解释范围变化。不同目标对应不同附件和提问。系统先从会议行动项挑一件事，再生成一封围绕它的邮件。若一封信同时催合同、推新产品、索要预算、补技术资料，客户可能只回最不重要的一项，销售还以为全部推进了。对于没有明确跟进事项的会议，允许“不发”，但要在销售待办里提醒核对，而不是为了达到“自动化发送率”硬造一封邮件。

微软 [Sales agent 的邮件草稿说明](https://learn.microsoft.com/en-us/microsoft-sales-copilot/email-reply-premium)展示的交互是先生成建议，用户可查看、保留、编辑后再发送，并描述了草稿对关联 CRM 记录的依赖。小陈借鉴的是草稿与发送分离；实际产品的字段范围、许可和支持语言都应以企业使用版本为准。我们自己的流程还需把收件关系、附件版本和审批记录并排呈现，不把“生成建议”误写成“系统已安全发送”。

## 审核界面若藏了收件人，领导点得再认真也没用

小陈设计了一张发送审核卡。最上面不是模型写的漂亮开头，而是完整的 To、Cc、Bcc 列表，每个地址后写“来源：本次会议邀请/CRM 联系人/销售手工补入”。旁边显示账户与商机 ID、联系人状态、历史退订或不联系偏好。中间才是正文，标注哪些句子引用会议原话、哪些是销售自写的说法。下方是附件名称、版本、文件指纹、所属客户范围与共享权限，最后显示邮件发送目标。审批人能一眼看出“乙公司王工”混进了甲公司的信，点驳回时系统保留原因。

**领导：**把收件人列这么长，销售还不是直接一路点通过？

**小陈：**可以减少需要人审的量，却不能藏关键字段。对既有线程内、同一已确认联系人、无敏感附件、正文只答复一个明确问题的低风险回复，规则可以更轻；首次联系、批量外联、价格或合同附件、跨账户抄送，一律要更严格。审核界面把变化突出：新收件人、新附件、从草稿上次确认后改过的句子。人要审的是差异与风险，而不是每次从头读相同的页脚。

批准回执绑定草稿版本与内容指纹，包括收件人、主题、正文、附件 ID 和附件版本。销售点通过后，如果系统发现附件被更新、地址被改、会议关联变了，原批准失效。不能拿一张“批准发送邮件”的空白通行证，给稍后由 Agent 改写的任何内容盖章。外发服务在真正调用邮件 API 之前再检查审批回执是否有效、账户权限是否仍在、客户偏好是否变化。审批是一个具体版本的授权，不是对模型未来全部输出的信任。

**领导：**可是销售要给十位客户发十封相似邮件，能不能一次批准十封？

**小陈：**可以一次看一个批次，但批次不能只有一段通用正文。审核页要逐行列出十个账户、实际 To 与 Cc、对应联系理由、附件差异和每封信里引用的事实。批量批准的是这十个具体版本的集合，系统保存批次指纹和单封指纹。只要其中一封加入新收件人、换附件或正文出现未经核实的客户承诺，这一封就退回待审，其他九封不必陪它重写。若审批人只看到“预计发送十封”，他审的不是邮件，是一张数量报表。

批量外联还要处理发送节奏与撤销窗口。系统把批准和排队分开，已批准不代表立即投递；正式排队前再次查客户是否刚刚回复、销售是否手动发过同主题邮件、是否已有退订或联系偏好更新。客户上午回复“资料收到了”，下午 Agent 再发“您还没收到吧”，显得系统比人更健忘。排队中的任务可取消；一旦邮件系统已受理，撤销能力受实际供应商限制，不能给销售一个写着“撤回”却仅删除本地记录的按钮。界面必须说清动作到哪一步还能停。

## “邮件 API 返回成功”不等于客户收到了

**领导：**发信接口返回成功，CRM 不就记“已联系”了吗？

**小陈：**得看接口所谓成功是哪一层。以 Microsoft Graph 的 [sendMail 接口文档](https://learn.microsoft.com/en-us/graph/api/user-sendmail?tabs=http&view=graph-rest-1.0)为例，成功的 <code>202 Accepted</code>表示请求已被接受，不表示处理完成或最终投递。邮件系统后续可能限流、退信、被收件端拒绝。CRM 若在接口受理瞬间记“客户已收到并阅读”，是把三种状态折成一个。我们分别记“待发送”“请求已受理”“发送系统确认”“投递失败/退信”“客户已回复”，没有证据的状态不往前跳。

对于 Microsoft Graph，我们还要核对发件邮箱、发送权限、是否保存到已发送邮件、消息 ID 如何查询。Gmail 的[发送 API](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/send)会返回消息资源；那同样只能作为系统侧发送记录，不能证明收件人已读。不同供应商的回执语义不完全一样，所以 CRM 的统一字段不应只叫“成功=true”。保留供应商原始状态、请求关联 ID、业务发送意图 ID，再由适配层映射到内部状态，遇到不明确时标“待核”，而不是自己脑补最后一步。

最难的是超时。系统调用发信接口后网络断了：邮件可能已发，调用方没收到回执。此时盲目重试可能让客户收到两封一模一样的“亲切跟进”，第二封甚至被看成催促。小陈给每次发送意图一个稳定 ID，先查邮件系统的已发送记录、消息 ID 和可能的退信，再决定是否人工确认或补发。邮箱 API 没有承诺业务幂等时，不能假设相同请求重复提交一定只发一封。对于未知状态，销售后台清楚显示“发送结果待核查”；系统不把它标已发，也不自动再发。销售可结合邮箱、日志和客户回复处理，所有核查动作都留记录。

## 发送之后，还要把真相写回去

**领导：**邮件发出后，把正文和时间同步到 CRM 就好了。

**小陈：**同步也要带来源和状态。先把业务发送意图、审批回执、邮件系统消息 ID、收件人快照、正文与附件版本关联到同一条活动。客户如果回复，活动能回连原信；如果退信，销售的跟进任务应转成“联系渠道失效”，而不是继续按已联系客户计数。若外部邮箱和 CRM 同步暂时中断，不能为了仪表盘好看，先伪造一条“已联系”。可以保留待同步队列，恢复后按业务 ID 去重写入，并对账发件箱与 CRM 是否一致。

对客户偏好也要有回流。若客户说“请只发给采购邮箱”，后续系统应更新联系限制，经有权人员确认后应用；不能只在这封邮件里礼貌道歉，下次换个活动又群发。若客户说“我不负责这个项目”，联系人与商机的关联要复核，错误关系标为有争议，不把这次错误接触当作有效触达。客户回应是更新关系图的证据，但仍要核对身份，避免一个外部回复自动修改整个账户的负责人。

**领导：**如果客户回了信，CRM 却没同步，下一轮 Agent 会不会再追一遍？

**小陈：**会，所以自动外联不能只读 CRM 里的上次接触时间。它要能查当前邮箱线程或在邮箱事件进入 CRM 前暂停同一收件人的新任务。邮箱与 CRM 的同步是最终一致的，短时间不一致很正常；系统要有一条“待同步、禁止重复追”的状态。重新运行任务时先按业务意图 ID、收件地址和线程关联查重，再核对内容和时间。查到已发但客户未回，可以按策略提醒销售；查到客户已回，先消化答复。查不到邮箱权限时，宁可把这一封交销售判断，也不按旧 CRM 盲发。

客户回应的自动分类也不能越界。一个“收到，谢谢”确认的是收到，不是认可报价；“我转给同事看看”确认的是转发意图，不是同事已经批准。销售系统可把这些句子变成待跟进提示，但必须保留原话，不能在客户画像里自动写“价格已接受”。S06 那套说话人和承诺状态，到了邮件线程同样有用：对方是谁、回复的是哪一封、引用了哪个附件版本、表达的是事实还是可能性。跨场景复用的是证据原则，不是把上篇的纪要模板照搬过来。

小陈给领导看一份追责轨迹：上午十点 Agent 从哪场会议产生跟进意图；十点零二分选了哪些收件人、依据是什么；十点零三分销售审核的是哪个正文和附件版本；十点零五分邮件 API 返回什么；十点十分 CRM 写入哪条活动；下午客户若说“你哪位”，能把整条链拉出来。轨迹给内部复盘，不把客户隐私贴进全员群。没有这条链，就只能找销售、运营和开发互相猜“到底是谁点的”。

## 批量发送怎么试，才不会拿客户当测试数据

**领导：**我们的目标是规模化，难道每封都审一遍？

**小陈：**先分层回放，不拿真实客户做第一批。拿历史会议和邮箱记录构成脱敏测试集，故意放入同名联系人、跨公司域名、过期附件、客户要求换收件地址、抄送里有外部顾问、无会议关联、销售已经手工发过一封、接口超时但其实已发送。每例检查四件事：系统选对联系人和联系理由了吗；正文里的关键事实和承诺能回原话吗；附件版本和权限对吗；故障时会不会重复外发。只看邮件“像真人写的”没有意义，外发风险恰好藏在看起来流畅的句子里。

试点先用“仅生成内部草稿”，销售在原有邮箱里发送，记录改写原因与审核耗时。若草稿常因联系人错而被驳回，就先修身份关联；若正文常编承诺，就回到会议证据抽取；若附件常过期，就修文档版本管理。每个错误找对应环节，不能一律调温度或多写几句提示词。经过足够回放后，可选一个明确边界尝试更自动化，如只对已确认账户的既有邮件线程回复、不含报价附件、只交付会中已答应的公开资料。高风险场景继续人审，自动化范围写进配置，不藏在某人的脑子里。

评估不只数“发出多少封”，还要看错收件率、承诺越界率、附件错误率、客户纠正与投诉、发送未知状态解决时间、重复发送、销售审核耗时。批量外联如果把客户关系弄坏，发得再快也没有商业价值。具体目标由企业现有基线和风险承受能力确定；虚构案例不提供一个万能的“合格率”。审查者要能从指标下钻到单封邮件和对应证据，避免只看漂亮曲线。

## 那封错发的邮件怎么收场

小陈先停止这次批量任务，按发送意图和邮箱回执确定影响范围，不依赖 CRM 的“已联系”字段判断谁真的收到了。乙公司王工那封已经外发，无法靠删草稿或改 CRM 抹掉。账户负责人核对内容是否包含甲公司的敏感信息，按企业事件流程决定通知和处理；销售向错收件人说明来意并更正，不让 Agent 自动用模板再道一次可能更错的歉。甲公司客户本该收到的接口清单，由销售确认正确联系人和附件版本后单独发送，不拿“刚才群发过”当完成承诺。

**领导：**这一套下来，自动化省的时间好像没想象多。

**小陈：**第一阶段省的是查会中承诺、整理草稿和对照来源的时间。外发决定暂时留给销售。等身份关系、附件版本、审批和回执跑顺，低风险场景再逐步放权。比起一晚上发出一千封邮件，第二天客户都回“你哪位”，慢一点的正确更便宜。

最后领导把“全部自动发送”改成“先生成有证据的待审草稿”。销售点开第一张审核卡，没先读文采，先看到乙公司王工的地址被标红。他点了驳回，系统把身份冲突转给账户负责人，甲公司的清单则继续由正确联系人确认后发送。那封“你哪位”，这次留在测试集里，没有进客户邮箱。

下次要扩大自动发送，领导先看三张表：谁被错误匹配过、哪些附件因版本不明被拦、发送结果未知的邮件多久查清。三张表都能下钻到具体发送意图，而不靠“本月发信量创新高”自我鼓励。真正的规模化，得让错误在发送前就有名字。
