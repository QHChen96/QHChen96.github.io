**领导：**客户问“我们集团新买一百套能用去年的八折吗”，销售 Agent 回“可以，合同写了”。你看，法务库和 CRM 都接上了，它这回挺能干。

**小陈：**我把它引用的合同打开了。八折属于“青杉科技有限公司”去年那批续约，客户这次下单的是“青杉云服务有限公司”，两家公司名称相近，却不是同一个合同主体。CRM 里只写“青杉集团”，Agent 搜到第一份八折条款就停了。它不是没查到资料，是没把“谁买、买什么、合同何时有效”连成一条完整证据链。

**领导：**合同都在，为什么不让它多搜几次？

**小陈：**可以多搜，但先把要补的缺口写出来。它需要确认提问人的客户实体、采购产品和数量，再查该实体的有效合同与价格政策；有例外审批还要查批准记录。每一步留下查询、结果、权限和未解决的问题，证据不齐就停在“待销售与法务确认”，不能为了让回答看起来完整，替公司把另一个法人的折扣送出去。

本文的客户、公司、折扣、合同和日志均为教学虚构。跨语料检索服务可帮助分解复杂问题、选资料源和返回活动记录；本文描述的实体匹配、合同效力与对客承诺闸门仍由业务系统与责任人定义。Azure AI Search 与 Google 的相关能力包含预览或区域限制，后文会明确使用边界。

## 第一份“证据”为什么看着真，结论却错得很具体

小陈在屏幕上放出 Agent 的原始轨迹。输入是“青杉集团新买一百套还能八折吗”。检索器对“青杉 八折 合同”查询法务库，返回一份《2025 年度续约补充协议》，页面上真有“订阅续约享八折”。模型摘出这句，回答“可以”。整个过程没有虚构文件，也没有凭空编数字；错误在于没查合同主体、产品、采购类型和期限。对于一个通用问答题，引用一段相关合同也许能算有用；对于报价承诺，相关不等于适用。

**领导：**这两家公司不都属于同一个集团？

**小陈：**“集团关系”不等于“合同权利可自动转给子公司”。有的协议写明关联企业适用，有的要求另签订单，有的只限原主体续约。机器可以从合同原文抽出条款，但不能从名字像、企业关系近，就替法务推定合同覆盖。先查 CRM 的法人实体 ID 和这次商机的采购主体，再查与该实体对应的合同；如果有“关联公司适用”条款，还要看定义、时间和产品范围。没有明确条款就交合同负责人确认，不能靠“集团”两个字穿透法律实体。

小陈给问题建了一个最小证据对象：<code>account_id</code> 是 CRM 客户记录，<code>legal_entity_id</code> 是签约主体，<code>opportunity_id</code> 指向本次商机，<code>product_sku</code> 和数量确定采购对象，<code>contract_id</code> 指向协议，<code>clause_id</code> 定位折扣条款，<code>effective_from/to</code> 标生效期，<code>approval_id</code> 指向例外审批。回答不是把这些字段全念给客户，而是让系统有能力证明“这句可以八折”同时满足谁、何物、何时、何条件。缺一个关键字段，结论就要降级。

## 问题拆小，资料源才知道各自该回答哪一半

**领导：**把法务库、CRM、价格表都合到一个搜索框，不就不用路由了？

**小陈：**一个框能统一入口，不能消除资料的职责。CRM 对“这次商机是谁、购买什么”有权威；法务库对“签了什么条款”有权威；价格系统对“现行标准价和折扣审批”有权威。把三份内容全向量化后一起搜索，排名第一的片段不一定是整题最关键的片段。我们要把总问题拆成子问题，再给每个子问题选合适的数据源，最后按实体和时间连接。这个连接是业务判断，不是把三个 Top 1 片段用逗号拼起来。

小陈写下四条查询。第一条到 CRM：本次商机对应的法人实体与采购产品是什么？第二条到法务库：该实体是否有覆盖新购、该产品、一百套数量的有效折扣条款？第三条到价格系统：现行价格和折扣审批限制是什么？第四条只在前三条提示有例外时查审批记录：是否真的批准了这笔交易的特殊折扣？每条查询都在用户当前授权下运行。销售不能读的法务内部意见不会因为“Agent 帮忙”被随手塞进最终回答；需要法务判断时返回任务和引用定位给有权限的人。

**领导：**这是不是就是“Agentic Retrieval”？名字这么时髦，能不能直接买一个？

**小陈：**它描述的是让检索器规划子查询、选择资料源、按结果判断要不要继续的一类做法。比如 [Azure AI Search 的官方概览](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-overview)说明，多查询检索可以拆问题、并行查资料源、合并结果，并返回引用和活动记录；其中 LLM 查询规划等能力按文档处于预览。[Google 的跨语料检索文档](https://docs.cloud.google.com/gemini-enterprise-agent-platform/build/rag-engine/cross-corpus-retrieval)也描述了按语料说明选择库、评估上下文是否足够再检索的流程，同时标明公开预览与区域限制。这些工具能帮忙做搜索计划，不能替我们定义“两个法人能不能共用合同”或“谁有权答价格”。先把业务证据要求写清，再选实现。

## 多轮检索不是“直到模型觉得自己很懂”

小陈把每一步写成一个可检查的状态：待查实体、待查合同、待查现行价格、待查审批、证据齐、证据冲突、证据不足。最初 Agent 只有客户自然语言和商机号；查到 CRM 后才能知道具体法人 ID，进而查正确合同。若合同正文指向附件，下一步只查那份附件；若条款明确不适用新购，就停止继续找八折的理由，直接给销售内部提示“旧协议不适用这单”。如果两份有效合同冲突，系统保留两边来源并交法务，不能按排序选一份。每一轮都有“为什么再查”的缺口，不是无止境地换关键词。

**领导：**多查几轮会不会慢到客户挂电话？

**小陈：**给路线设上限。可以并行查互不依赖的标准价格和合同目录；必须等 CRM 法人 ID 出来才能做的合同精查则顺序执行。单次问题限制资料源数、查询轮数、总耗时和模型预算；超过上限时返回“目前还缺哪一项，已转给谁核实”，不能把半套证据包装成全套。对销售内部助手，先给一份“可引用事实＋待确认项”比三十秒后给一个自信错误报价更有用。紧急对客回复可以先说“我会核实合同适用范围”，而不是先把八折放出去再追认。

**领导：**系统怎么判断“证据齐”？它还是模型在说自己查够了吧。

**小陈：**不是一句自由文本。结论需要的槽位有明确约束：同一法人 ID、同一产品或可证明的产品映射、采购类型一致、日期落在有效期、审批状态足够、来源可读。每个槽位记录来源 ID、版本和原文位置；若模型抽取了“关联公司适用”，还要指向相应条款并让规则检查其覆盖范围。模型可以提出“我认为这些证据够”，应用层仍用这些结构化条件验一遍。不能自动判的法律解释，状态就叫“需法务确认”，不把不确定性挤进一个看似精确的置信度小数里。

## 一份能复盘的查询轨迹，比最后一句漂亮话重要

做实体匹配时，小陈没有把公司名的相似度当主键。CRM 可能有“青杉集团”“青杉云”“青杉云服务有限公司”三个别名，合同页上又可能出现历史名称。检索先拿自然语言找候选客户，再由 CRM 的稳定实体 ID 连接商机与法律主体；合同系统若没有同一 ID，就维护一张经审核的映射表，记录统一社会信用代码或公司注册号、名称变更记录、映射生效时间和维护人。仅凭字符串“青杉”召回的合同只能进候选集，不能直接进入适用结论。遇到同名不同主体、集团合并或客户主数据正在清洗的情况，系统把两个候选都摆出，让销售运营确认，而不是挑一个搜索分最高的。

**领导：**合同里写的“关联公司”也得做映射？

**小陈：**至少得弄清条款是列举具体子公司、定义某种控制关系，还是要求另行书面通知。有些合同允许关联方使用产品，却没说能继承价格；有些折扣只给指定订单，不给后续新购。Agent 可以把合同中的定义条款、价格条款和订单条款一起找出来，标出可能相关的限制；若需要法律解释，交法务确认。业务上不能先用 CRM 的组织树得出“关联”，再悄悄把它等同于“合同权利可转移”。两个系统分别描述关系，合同授予何种权利仍看合同文本。

小陈给条款解析做了一个约束表。维度依次是主体、产品、交易类型、数量、价格、时间、条件和审批。每个维度有三种结果：匹配、不匹配、未知。只要有明确不匹配，比如“仅续约”对“新购”，就不能使用该条款；有未知，比如“关联方须获书面同意”但没找到同意书，就保持待确认；全部匹配才进入可用候选，且对外承诺仍需价格审批。不能把八个维度求一个平均分，得到“七项都差不多，所以总体 87.5% 可以八折”。一项关键条件失败，合同适用就可能归零；数字化分数只能帮排序，不能替代合取条件。

**领导：**价格系统里已经有一条八折审批，能不能跳过合同？

**小陈：**先看审批对象。它可能针对同一集团的另一张商机，也可能只限上个月的采购数量。审批记录应绑定商机 ID、主体、产品、额度、有效期和审批状态；若其中任一关键字段不匹配，不能拿它补合同缺口。确有针对本次商机的有效特价审批时，合同标准折扣不一定是唯一依据，但回复要说清“本次价格来自特价审批”，不能继续谎称“旧合同自动适用”。不同证据可能支持同一个数字，所代表的责任和期限却完全不同。Agent 应给出最准确的依据，不能只挑最容易向客户解释的一份。

检索规划也要防“空结果带来的假确定”。按准确法人 ID 搜不到合同，可能是真的没有，也可能索引缺页、连接器权限不足或同步未完成。小陈要求每个资料源返回查询范围、索引更新时间、失败状态和命中数量；合同库若只同步到昨天，今天刚签的补充协议不能被它否定。否定性结论“没有适用合同”比肯定性结论更难证明，需要确认覆盖范围。系统可以说“在当前已同步且有权限的合同库中未找到”，同时列待核路径，不能简化为“贵司没有合同”。这种限定语不是故作谨慎，而是把搜索系统的观察范围交代清楚。

再看多轮查询的停止条件。若先查到一份明确“不适用新购”的合同，且没有任何其他有效协议或审批候选，系统可以停止“继续找八折”，转而查标准价与申请路径；若合同库返回多个候选但有资料源超时，不能因其中一份看似匹配就立刻承诺。小陈把继续查询写成一个问题：“剩余的不确定性有没有机会改变结论？”有，就在预算内继续查；没有，比如主体已确定不符、价格审批也不存在，就停下。超时则把尚未验证的分支写进输出，交人接棒。这样既避免无限搜，也避免第一段相关文字就让 Agent 收工。

**领导：**这听起来像做了一套小数据库查询，Agent 还有啥用？

**小陈：**结构化字段帮我们守住不会错的边界，Agent 帮我们处理用户口语、合同措辞、资料源选择和缺口归纳。两者各做擅长的事。让模型从一句“我们集团买一百套”识别可能的客户与意图，再用 CRM 确定身份；让模型找合同里可能涉及关联方的段落，再用条款条件和审核确认它能不能用。纯规则难覆盖所有写法，纯模型又容易跳过关键条件。高风险承诺让二者配合，比争谁“更智能”有用。

小陈没有只测这一张青杉商机。他把题集分成同名不同法人、改名后续约、关联方条款存在但产品不符、价格审批过期、合同库超时和权限不足六组，每组保存应查的源与不能说出的结论。评测时同时记正确证据覆盖率、错误承诺数、平均查询轮次、尾部耗时和人工接手比例。若新规划器把平均轮次从两轮变成六轮，却只把“看起来完整”的回答增加了，不能算进步；若它少查一轮就漏掉法务库，也不能只看延迟下降。选型以本公司这批真实形式的题为准，产品文档给的是能力边界，不替公司保证成绩。

小陈把这次错误轨迹改成表：第 0 步接到“青杉集团”这个模糊称谓；第 1 步 CRM 返回本次商机法人为青杉云服务有限公司；第 2 步法务库按该法人 ID 检索，找到现行主合同，无八折新购条款；第 3 步相似名称的青杉科技有限公司旧续约协议被检索到，但主体不符、采购类型不符，标“排除”；第 4 步价格系统显示标准价和申请特别折扣的路径；第 5 步生成内部答复，说明不能依据旧协议承诺八折，若销售希望申请特价需走审批。每一步记请求身份、时间、来源版本、结果和排除理由。客户不需要看这张表，销售和法务却要靠它避免下一次重演。

**领导：**那旧协议被搜出来，算不算检索失败？

**小陈：**检索到相似材料不等于失败，错在把相似材料当适用证据。候选召回可以宽一点，后面的实体匹配和条款判断要严。若一开始就只用公司全称做关键词，可能漏掉合同里写的曾用名；若只用向量相似度，又会把同集团不同法人混在一起。先用 CRM 的结构化 ID 做精确连接，再用别名表辅助找可能的合同，最后人工或规则核对合同主体。这里的“多轮”是逐渐收窄证明对象，不是多抽几段相关文字来堆引用数。

查询服务还要区分错误来源。CRM 接口超时，是身份尚未确定；法务库返回 206 部分结果，是合同证据不完整；审批系统拒绝访问，是用户没有权限；合同索引落后一天，是时效未知。这四种都不能被模型统一翻译成“没找到合同”。Azure 的[检索 API 文档](https://learn.microsoft.com/en-us/azure/search/agentic-retrieval-how-to-retrieve)提到活动记录和部分内容响应可以暴露资料源失败等情况；应用应把这些状态纳入停止条件。一个库正常返回、另一个库失败时，答案只能基于已确认部分说明缺口，不能让合并器把成功的那一半当全局事实。

## 领导现场追加四道题，小陈让系统把话说到边界

第一题：“青杉科技有限公司去年续约可以八折吗？”如果合同仍有效且条款、产品、数量都匹配，系统可以给内部销售显示可用依据与限制，并要求最终报价按审批流程确认。第二题：“青杉云服务有限公司本次新购可以八折吗？”旧协议不能支持，应明确不能据此承诺，给特价申请路径。第三题：“两家是关联公司，能不能共用？”没有明确关联方条款时，系统列出需要法务判断的具体段落，不自行解释。第四题：“客户已经收到八折口头承诺怎么办？”这不是检索题，进入销售承诺纠错流程，记录谁说了什么、何时说、是否需要客户更正与审批。Agent 不因查到旧合同就替公司追认错误承诺。

**领导：**如果数据都齐，它能直接给客户回信吗？

**小陈：**资料齐只解决事实依据，对外报价还牵涉授权和动作审批。系统可以生成附依据的内部草稿，价格、合同适用和有效期由相应负责人核对；发送工具还要检查审批回执。对客动作与知识检索是两个闸门，前者不因后者“引用充分”而自动打开。查得准是一项能力，代表公司承诺是另一项权限。我们前面已经为错价外发单独做过补救，这里先确保检索层不把别人的合同送上谈判桌。

验收时，领导没有只看一句“不能用八折”。他随机抽轨迹里的法人 ID，看 CRM 是否真对应本次商机；打开被排除的旧协议，确认主体和采购类型确实不同；模拟法务库超时，看系统是否停止推定；换一个没有合同权限的销售账号，检查受限片段是否根本没进入模型；把查询预算压到一轮，检查结果是否明确写“未完成核查”。五个动作都留下证据，才算解决“查一次就自由发挥”。小陈总结：“跨库问题不是搜得越多越聪明，是每一块证据都认清自己能证明什么。”

领导又抽了一条名字完全不像的合同，问为什么它没进候选。小陈展示路由记录：那份合同的法人 ID 与商机无映射，产品也不符，系统在结构化预筛时排除了它；如果客户主数据将来新增已审核的名称变更关系，它才会重新进入候选。检索排除要有原因和版本，不能只是模型一句“我觉得不相关”。这样漏查时可以修映射或源数据，而不是反复调提示词碰运气。
