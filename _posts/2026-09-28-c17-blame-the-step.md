**领导：**客户收到一句“可以直接退款”，结果政策根本不支持。模型又抽风了？

**小陈：**我按工单 0823 的轨迹倒查。输入是“已签收但未收到”；检索命中的是三个月前的“未发货可取消”FAQ；订单工具返回“已签收”；草稿却引用旧 FAQ 写“可以退款”；审核人改过语气，没改结论；发送服务照着批准版本发了。

**领导：**所以到底是谁的锅？

**小陈：**至少有两处具体故障：知识库让失效文件进入候选，答复生成又把“不适用条款”套进本单。审核环节也没拦住。说“模型不行”无法告诉工程师改哪里，更无法证明明天不会重演。

**领导：**下次别让你手工翻半天。

**小陈：**每次运行留一条可关联的轨迹，但不留客户明文隐私：

| 阶段 | 至少记录什么 |
| --- | --- |
| 输入 | 工单关联 ID、请求时间、脱敏后的问题类型 |
| 检索 | 文档 ID、版本、生效状态、引用片段定位 |
| 工具 | 工具名、权限判定、请求关联 ID、状态码、耗时 |
| 决策与草稿 | 走哪条路、依据的事实 ID、草稿版本、未核实项 |
| 审核与发送 | 审核人、批准版本、收件人关联 ID、渠道回执 |

**小陈：**查错按顺序来：先看发送了哪版，再看审核是否改稿；然后核对模型用的证据与工具返回；最后追检索准入和原始输入。每步要能跳到前一步的关联 ID。[OpenAI Agents SDK 的追踪文档](https://openai.github.io/openai-agents-python/tracing/)列出了模型调用、工具调用、交接等轨迹单元，但业务规则版本、审批与发送回执还得自己接上。

**领导：**客户这单怎么收尾？

**小陈：**先由客服核实并纠正外发结论，记录影响范围；同时下架旧 FAQ 的检索资格，增加“已签收争议不能引用未发货取消条款”的回放样本。验收是抽一张错单，在约定的排查时限内能找出规则版本、工具返回和最终发送内容；日志导出给排查人时，手机号和地址仍应遮盖。

## 先救客户，再争论“谁的锅”

**领导：**分析可以慢慢做，客户已经收到“可以退款”了，先怎么办？

**小陈：**先让授权客服核对这张单的真实规则和已发生动作。若退款根本没提交，不能继续让客户以为钱在路上；客服要给出准确更正、解释后续核查路径，记录对客户作过的错误承诺。若同一发布版本可能影响更多工单，暂时关闭相同题型的自动外发或退回人工审核，按引用旧 FAQ 的运行记录找影响范围。先止血、核影响、纠正客户，再做根因归属。复盘不是为了找到一个人背锅，而是为了让同类错答不再出去。

0823 这单的轨迹有七站：客户输入、检索、订单工具、生成、审核、发送、客户后续反馈。我们从最后一站倒推，因为客户看到的是真正发出去的版本，不是开发者以为生成的版本。先取得发送回执 `M-19` 和批准草稿版本，核对这句话是否原样发出；再看审核记录是否只改了语气；再看生成时引用的片段和订单工具回执；最后看旧 FAQ 为何进入可用检索集合。这样查会发现至少三个薄弱点，而不是用一句“模型幻觉”结束会议。

**领导：**既然旧文件是根因，把它删了不就完？

**小陈：**删旧文件能止一部分血，不能解释它为什么进索引，也不能保证同类规则错用不再发生。知识条目的状态、生效时间、渠道与问题类型应作为检索过滤条件；当前样本里“已签收但未收到”与“未发货可取消”有词面相似，却业务条件相反。检索层要排失效版本，生成层要校验本单条件与条款适用条件，审核层要把退款承诺当高风险结论检查。每层都能挡一次，才不把命运押在某个审稿人那天有没有喝咖啡。

## 一条轨迹需要哪些键，才串得起来

**领导：**研发说 OpenAI Agents SDK 已经有 trace。直接开开关不行？

**小陈：**框架轨迹能记录模型生成、工具调用、交接与护栏等运行单元，这很有帮助；但业务链还要接上工单、知识版本、审批和渠道回执。以 0823 为例，`trace_id` 串起一次 Agent 运行；`case_id` 把运行挂到工单；`release_id` 指明提示词、模型、知识索引与工具配置是哪版；`document_id + version` 指出引用了哪份 FAQ；`tool_receipt` 指出订单系统何时返回什么；`draft_version` 和 `approval_id` 连到人工审核；`message_id` 连到外发回执。缺最后一环，我们只知道模型说过什么，不知道客户收到什么。

一次工单可能有多次运行：客户上午发问、下午补充、第二天重开。不要把整张工单硬塞进一个巨大 trace，也不要每次运行只有独立 ID、查不到同案关系。工单 ID 关联多条运行轨迹，运行内部用父子 span 看检索、工具与生成的时间顺序；涉及跨系统异步事件，就用业务关联 ID 接续。按时间线还原时标注事件发生时间与系统接收时间，避免回调晚到被误解成动作晚发生。

**领导：**轨迹是不是要把模型看到的全文都存起来？

**小陈：**不要默认这么做。为了排查“哪份规则被引用”，记录文档 ID、版本、片段位置和内容哈希，必要时由有权限的人回到受控知识系统看正文；订单只记受控回执与状态类别，客户手机号和地址不进通用追踪。模型输入输出若含客户私事，要按数据策略配置采集、脱敏与访问，而不是因为 SDK 默认方便就全部导出。官方追踪文档本身也单列敏感数据处理，企业必须决定哪些 span 可保存、送到哪里、谁能看、多久清。故障排查需要关联性，不等于需要复制客户整段人生。

## 追责之前先做“第一处错误”定位

**领导：**旧 FAQ 进来了，模型也用错了，审核也没看出。报告到底写一个根因还是三个？

**小陈：**写一条因果链，不抢“唯一根因”帽子。**触发点**是失效 FAQ 被检索返回；**生成错误**是没有校验“未发货可取消”与“已签收争议”的适用条件；**逃逸点**是审核只改语气没核退款结论；**客户影响**是发送服务把批准版本发出。这四层都要有修复项。若只修检索，下一份状态错误的条款可能继续被误用；若只教育审核员，自动发送场景仍无护栏；若只换模型，旧规则仍在索引里。

排查顺序还要识别“工具真实返回错”与“模型误读工具”。订单工具回执写“已签收”，Agent 写成“未发货”，错误在解释；订单适配器把另一张单的“未发货”返回，错误在身份和工具层。两种修法完全不同。运行轨迹中的工具请求参数、授权结果和回执 ID 必须可查，但对排查人员按角色开放，不暴露无关客户信息。

**领导：**能不能让模型自动给自己写根因分析？

**小陈：**可以让它整理时间线和候选原因，但结论要能点回证据。模型说“检索召回旧 FAQ”，就要给出文档版本和当时索引状态；说“审核漏检”，就要指出审核人看到的是哪版草稿、审核规则要求什么。没有证据的“建议优化提示词”只是把锅重新刷了漆。事故负责人最终确认因果与修复，模型做助手，不做陪审团主席。

## 从一张错单扩大到一批，影响范围怎么圈

**领导：**我最怕不是 0823 一张，而是周末有一百张。

**小陈：**先按 `release_id` 和旧 FAQ 的 `document_id + version` 查引用该片段的运行，再交叉看哪些草稿包含“可退款”承诺、哪些经审核、哪些真正外发、哪些客户已收到。不能把“检索到旧 FAQ”都算成客户被误告，也不能只统计客户投诉的三张。影响表按“可能接触错误证据／生成错误草稿／已批准／已发出／需主动更正”分层，每层有工单 ID、负责人和处理状态。这样客服知道该联系谁，工程知道哪道防线失守，领导知道影响究竟到哪一步。

如果日志只留模型最终文本，没有文档版本，就无法精确圈范围，只能扩大人工抽查。这个代价会反过来告诉团队：该保留的是**证据标识和版本**，不是客户原文。轨迹保留策略要覆盖事故发现窗口，过早清掉版本映射会让我们无法解释上周的错答；但也不能无限期保存敏感载荷。保留元数据与保护私密内容可以同时做到。

**领导：**发错以后回滚知识库，过去的轨迹还会变吗？

**小陈：**不能。轨迹必须指向当时真正读到的版本，旧文档即使从对客索引下架，也应在受控审计系统留必要版本记录。否则周一回滚后回看周五运行，页面只显示“当前规则 v4”，大家会误以为 Agent 当时也读了 v4。历史证据和当前可用知识是两套用途：前者用来解释与复盘，后者决定下一次答复能引用什么。

## 修完之后怎么证明真的修到了那一步

**领导：**三个修复项都写了，验收总不能再挑一张同样的工单看运气。

**小陈：**做四组回归。第一组，失效 FAQ 与生效规则标题很像，检索候选里不能把失效文件当可用证据；第二组，检索到了相邻但不适用的条款，生成不能套到已签收争议；第三组，生成故意写“可直接退款”，审核或发送前校验应拦住并要求证据；第四组，故障恢复后重新发布索引，线上仍不能返回旧条款。每组至少有正例和反例：真正的未发货可取消题不能被“一律禁用退款”误杀。

同时演练排查时限：给值班同学一个虚构客户投诉和发送回执，要求他在约定时间内找到运行版本、旧 FAQ、订单回执、草稿、审批和发送记录，判定影响范围。若必须找五个工程师分别查数据库，说明关联键和工作台还没做好。验收报告记录“哪一层发生了错误、哪一层挡住了、客户是否受影响”，不只报“模型回答正确率提高”。

**领导：**技术面试问 trace 和 log 区别，你怎么说？

**小陈：**trace 用关联 ID 和父子 span 表示一次请求跨步骤的因果与耗时，log 记录各处事件详情；两者可以互相链接。客服业务还要工单事件与外发回执，因为模型运行结束不等于客户案件结束。为了排错，记录足够的版本、状态和回执；为了隐私，少记原始个人内容。找到第一处错误，修具体的门，再用故障回放证明门真的关上。这比全场齐喊“模型不行”省时间，也更对得起客户。

## 工程师再追问：轨迹要精细到什么程度

**领导：**你把七站都记了，会不会每天产生海量日志？

**小陈：**要区分**轻量常态轨迹**与**受控调查材料**。常态轨迹记录每站开始结束时间、结果状态、版本、回执 ID、错误码和必要的数值指标；不默认保存完整输入、模型长篇输出、订单原文。抽样或事故调查时，授权人员可以通过工单系统回看必要内容，并记录访问。高风险动作如退款提交、人工审批和对客发送应保留更强的业务审计，而普通检索未必需要每次存全文。保留策略按调查窗口与数据要求制定，不能因为存储便宜就无限复制客户内容。

一个运行可以有 `trace_id`，每次检索有 `span_id` 与 `parent_span_id`，文档候选记录 ID、版本、过滤原因、分数和是否被引用。这里的“分数”只是检索线索，不是条款适用性结论。订单工具 span 记录工具名、受控订单引用、权限结果、状态码、耗时、回执 ID；生成 span 记录模型配置、提示模板版本、引用的证据 ID、输出草稿 ID；审核事件记录批准人、决定、草稿版本；发送事件记录渠道回执。这样我们能从客户投诉逆向跳转，也能从某个错误文档正向找受影响工单。

**领导：**如果模型生成了答案，但 trace 导出失败，工单还能继续吗？

**小陈：**核心业务动作不能只靠追踪系统存活。工单、审批、发送回执要落在各自的业务系统；追踪导出故障会降低可观测性，应告警并视风险决定是否暂停自动外发。尤其高风险路径，若无法记录证据与批准版本，宁可退回人工，不要发生了退款却查不到是谁批准的。追踪系统不是业务事实仓，但关键业务事实必须可审计。事后补轨迹时要标“补录”与来源，不能伪造成当时实时记录。

## 再看一次 0823，分清“相关”和“因果”

**领导：**旧 FAQ 在候选列表里，是否就能证明它造成了错答？

**小陈：**不能。候选可能有十篇，模型最终引用的是另一篇；也可能没引用任何文档而凭记忆回答。我们要看检索候选、实际入上下文的片段、草稿引用和生成内容之间的链。如果旧 FAQ 仅在候选里、被过滤掉了，根因不在它；如果它被送进上下文但模型明确拒绝使用，说明生成护栏挡住了一次；如果它被引用并形成错误承诺，因果链才闭合。排查报告不能因为“日志里出现旧文件”就把所有问题推给知识团队。

同理，审核人按“已批准”也不意味着他看到了所有证据。工作台若只显示最终文案，不显示引用规则版本和订单回执，审核人可能根本无法判断“可退款”依据是否有效。改进不能只要求审核员更仔细，还要给他能审核的材料；高风险结论旁显示证据和适用条件，缺失时按钮应禁用或要求升级。人审是防线，但防线也要有视野。

**领导：**如果模型根本没引用旧 FAQ，却依旧说能退款呢？

**小陈：**那要看提示词、上下文其他材料和输出约束。可能旧规则被写死在提示模板里，也可能某段客户输入伪装成政策，还可能模型自行推断。轨迹能把这些候选分开。修复可能是移除过期提示、加强资料来源隔离、增加“退款结论必须附批准依据”的结构化输出校验。先定位第一处错误，才不会把知识索引翻修一遍，结果真正的旧提示仍在上班。

## 把“事故后补救”写成值班流程

**领导：**周六半夜再发生一次，值班人按什么顺序做？

**小陈：**第一步，从客户提供的消息或渠道回执找到具体工单和发送版本，确认错误是否真的对外；第二步，暂停相同发布版本或题型的自动发送，避免继续扩大；第三步，按文档版本、发布版本和危险措辞圈出候选影响工单；第四步，让业务负责人确定正确处理与客户更正方式；第五步，工程师沿轨迹定位第一处错误与逃逸点，修规则、检索、生成或审核；第六步，用错单和相邻反例回放，通过后小范围恢复。每一步有负责人和回执，不能因为模型一时答对重跑样本就跳过影响客户的处理。

这个流程有两个时间目标：**止血时间**从确认对外错误到相关自动路径暂停，**定位时间**从拿到工单到明确第一处错误及其证据。不要只量“平均排障耗时”，极端慢的一次可能代表关键回执缺失。周报可列无法定位的错单数、轨迹缺字段比例、旧政策误引次数、审核挡住的危险草稿数和已发错后纠正完成率。数字最终要指向修复队列，不是用来评比谁背锅背得快。

**领导：**客户隐私怎么兼顾排查？

**小陈：**常态轨迹用受控标识，敏感原文仍在客服系统；调查者按角色、案件和时限获取必要内容，导出样本脱敏，并留访问审计。测试时用虚构手机号、地址和订单号验证正常与报错轨迹都不泄露。若为了排错把全量提示和附件送进无人管理的监控平台，事故还没查完就造出第二个事故。排查的专业性，也包括知道哪些数据根本不该出现在自己的屏幕上。

小陈在复盘会上放出两条对照轨迹。第一条是修复前：旧 FAQ 进入可用候选，生成器引用，审核页没显示版本，错误文案外发。第二条是修复后：同样输入仍可能在搜索原始结果里看到旧 FAQ，但生效过滤把它挡在模型上下文之外；即使人为注入错误草稿，发送前的高风险校验也要求有效规则和审批。两条轨迹并排，大家才看见防线具体移动到了哪里。

**领导：**这比写“提升模型理解能力”麻烦，但我终于知道钱花在哪了。

**小陈：**知道哪一步出错，下一次就能只修那一步；知道哪道门没挡住，下一次就能把门装牢。若复盘报告只写“加强培训、持续优化”，客户收到的下一句“可以退款”可能仍来自同一份旧文件。值班手册里留下的是可查的 ID、版本、回执和负责人，周末接班的人不必靠猜公司上周发生了什么。

这张工单的结论也留在原案：客户是否收到更正、是否仍需要人工处理、何时复核。技术修复上线了，不代表客户那张错误答复就自动消失。

**领导：**追踪里只有模型输出和最终短信，中间缺工具授权记录，还能归因吗？

**小陈：**只能缩小怀疑范围，不能编造缺失的事实。先从订单服务与发送平台补回执，确认实际读取和外发；缺的关联链明确记为观测缺口，修追踪传播后再复测。日志不能为了完整而复制客户全文，关键是用同一工单和调用 ID 串起授权、证据、草稿、审核与发送。缺一环时报告不确定性，比指着模型截图定责可靠。
