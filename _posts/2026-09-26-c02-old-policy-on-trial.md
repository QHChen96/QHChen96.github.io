**领导：**知识库里两份退款规定都写着“公司发布”。Agent 引用旧的那份，是它不认真吧？

**小陈：**旧文件标题叫“最终版”，新文件叫“最终版2”。人看了都想请假，模型又不是档案室主任。

**领导：**那给它一句提示：“永远用最新文件”。

**小陈：**日期最新也未必适用。还得问：哪个业务线、哪个地区、哪类订单，以及按下单日还是售后申请日判定。您给我这张虚构的工单 0823，我把两份文件摆上桌。

| 文件 | 文件名看起来 | 台账里真正要有的字段 | 本单处理 |
| --- | --- | --- | --- |
| A：旧版 FAQ | “退款规定最终版” | 文档 ID、版本、适用范围、生效与失效时间、责任人 | 已失效，不能作为本单答复依据 |
| B：现行签收争议规则 | “售后补充说明” | 同上，另附条款位置和批准记录 | 若适用范围匹配，先核对签收记录，再交售后判断 |
| C：待发布草案 | “最新修订” | 状态为草案、计划生效日 | 没正式生效，不能抢跑 |

**领导：**所以“最新文件”这招，连草案也会捞上来？

**小陈：**会。更麻烦的是跨区规则、活动期规则。我们让**政策责任人**先定准入，入库时把草案和失效文件隔离；检索时按工单业务、地区和适用日期过滤；生成草稿时把文档 ID、版本和条款一同展示给客服。索引只是加速找资料，没资格替政策负责人宣布生效。

**领导：**要是 A 和 B 都写着有效，但内容打架？

**小陈：**停止给退款结论，记录冲突的两个文档 ID，派给政策责任人。别让 Agent 开“谁的措辞更像领导签过字”的辩论赛。责任人解决冲突、发布版本、重建索引后，再用原工单回放。政策更新期间，相关问题宁可走人工。

**领导：**我想看的是成果，不是“资料治理很重要”六个字。

**小陈：**交付三件。第一，规则台账每份文件都有状态、适用范围、生效与失效条件、责任人；第二，工单 0823 的检索记录只返回适用条款，旧版和草案被拦下；第三，故意让两份有效条款冲突，答复必须标“规则待确认”并转人工。工程实现可以用文档元数据做过滤，检索系统的设计也要保留来源和权限信息，[Azure AI Search 的 RAG 文档](https://learn.microsoft.com/en-us/azure/search/retrieval-augmented-generation-overview?tabs=docs)对内容准备与检索元数据有具体说明。

**领导：**行。以后文件名再写“最终版3”，我先找发布人。

## “最新”是哪一种新，先把四只钟摆出来

**小陈：**文件上传时间、审批时间、业务生效时间、客户订单对应的适用时间，是四只不同的钟。旧 FAQ 可能昨天重新上传，上传时间很新，内容仍是三年前政策；新草案可能今天审批完成，但计划下周生效；现行条款可能半年前发布，却仍是这类订单唯一有效的依据。所以“按文件更新时间倒序”只能找最近改过的文件，不能决定客户有没有退款资格。

0823 的客户说“系统显示已签收，但我没收到”。要判断适用规则，至少确认业务线、地区、商品或订单类型、客户提出争议的时间，以及规则规定采用哪一个时间点。某些政策按下单日，某些按售后申请日，具体由业务负责人定；技术实现不能自己挑对 Agent 最容易的日期。台账里不仅写 `effective_from` 与 `effective_to`，还要写 `applicability_basis`，例如“按售后申请时间判定”，并有审批记录。否则日期字段齐了，执行仍可能错。

**领导：**客户问的是现在能不能退，为什么还要保留旧版？

**小陈：**旧版不能进入当前不适用的对客检索，但它可能需要解释历史决策。去年按 v2 给客户的书面承诺，今天不能被 v4 的文本覆盖得无影无踪。知识系统分**当前可用集合**和**受控历史档案**：前者供 Agent 回答当前问题，后者供有权限的人复盘当时依据。撤下旧版不是物理删除所有历史；保留旧版也不等于允许它继续参与今天的答案。两套用途分开，才能同时避免旧政策误答与历史无据可查。

## 文件名不做裁判，规则台账才是门卫

**领导：**规则负责人要填哪些字段，才算一条能上线的政策？

**小陈：**最小台账包含 `policy_id`、版本、状态、审批人和审批回执、生效与失效时间、适用业务线、地区、渠道、客户或订单类型、判定日期基准、条款位置、例外条件、复核日期和责任人。还要有冲突关系：新版本替代了哪版，是否只替代部分地区。文件正文可以是 PDF 或网页，但这些字段要能被系统检验。空白的适用范围不是“全球通用”，应是“不能进入自动对客集合，等负责人补齐”。

状态可以简单些：`草案`、`待批准`、`已批准待生效`、`生效`、`失效`、`撤回`。上传文件只到草案；批准有审批回执；到了生效时间，索引也确认构建完，才对适用问题可检索。若审批后来撤回，索引和缓存都要更新并验证线上查不到撤回版。数据库状态改成“失效”但搜索服务仍给 Agent 返回正文，门卫只是把胸牌翻了面，门还开着。

**领导：**有两条政策部分重叠，怎么办？

**小陈：**发布前做重叠检测。同一业务线、地区、渠道、订单类型与时间窗，如果两条生效规则都声称管同一条件，却给不同结论，系统要标冲突，交政策负责人裁决。若一条是通用规则、一条是明确例外，台账要写优先关系和例外条件，不让模型凭措辞猜“特别规定优于普通规定”。对 0823，若签收争议规则与活动期退款规则重叠，先由负责人确定优先与适用范围，再发布机器可识别的关系。

## 三道闸口，挡在回答前与发送前

**领导：**只在入库时检查不够吗？

**小陈：**不够。第一道是**发布准入**：没有审批、适用字段不完整、冲突未解决的文件不能进入可用知识集合。第二道是**检索过滤**：以工单的业务条件和规则时间点为输入，先筛掉草案、失效、不适用地区与类型的条款，再在剩余集合里按文本相似度排序。第三道是**答复校验**：Agent 的关键结论必须引用当前适用的文档 ID、版本和条款；发送前再核一次生效状态和案件条件，防止检索之后规则被撤回或工单事实更新。

“检索后再让模型判断是否适用”不够稳。把旧版和草案都放进模型上下文，再提示“请只用现行规则”，相当于把过期菜和新鲜菜放同一个锅，让厨师靠眼力挑。确定能用结构化条件过滤的部分，应在模型看见前就完成；模型只负责理解客户问法和解释适用条款，不负责宣布哪份文件有法律或业务效力。

**领导：**如果条件缺了，例如客户没说地区？

**小陈：**先从已授权的工单字段读取；仍缺就问必要的澄清问题，或转人工。不能把缺省地区默认为公司总部，也不能拿全国通用条款覆盖有地区例外的场景。检索结果可以给出“候选规则需要地区字段”，对客户的答复是“需要确认您的订单所属地区后才能判断”，而非“您可以退”。缺条件是一个明确状态，不是鼓励模型发挥想象力的空白。

## 0823 的实战：三份文件如何被淘汰

**领导：**你把 A、B、C 跑给我看，别只讲闸门名字。

**小陈：**客户诉求进入工单，系统确认订单属于当前客户，查询到订单显示已签收。路由器判为“签收争议”，业务线为线上零售，地区与售后申请时间从工单受控字段得到。检索过滤先看状态：A 已失效，C 未生效，只有 B 留下。再看 B 的地区、订单类型和日期条件，确认适用后把条款片段交给 Agent。B 的结论是“先核对签收记录，再由售后判断”，因此草稿只能说需要核查，不能直接承诺退款。

随后小陈故意制造第二份生效条款 D，写着“活动期所有订单可直接退款”，但适用地区字段为空。发布闸口应拒绝 D 对客可用，要求负责人补地区；如果误入索引，检索过滤应标适用范围不明并停止；如果模型仍写出“可以直接退款”，发送前的引用校验应挡住。测试不是为了证明模型特别聪明，而是证明一处人手漏填不会立即变成客户承诺。

**领导：**政策负责人修完，旧工单怎么办？

**小陈：**新版本发布后，尚未外发的草稿要重新核对适用规则；已经外发的答复保留当时引用，并根据新规则的生效说明判断是否要主动更正。若新规则只对新申请生效，不能把老工单全部批量改判；若业务宣布追溯适用，则按受影响工单清单处理。技术系统提供版本和影响查询，是否追溯由业务责任人批准。不能让索引重建这一技术动作悄悄改写客户权利。

## 发布失败与规则冲突，怎么恢复

**领导：**规则已批准，索引却没建出来。你要让客服都停工？

**小陈：**不用停整个客服。受影响的退款判断题退到人工核查或已验证的固定流程，其他题仍可服务。发布任务记录审批版本、索引构建 ID 和线上查询回执；构建超时先查任务状态，不再复制出“最终版4”。若已构建但线上仍返回旧版，检查缓存与索引别名，并在恢复前保持相关自动答复关闭。技术上“文档已上传”与“对客可用”必须是两个状态。

若两份生效条款内容冲突，Agent 不做投票。冲突记录包含文档 ID、版本、重叠条件、冲突句子、发现时间和受影响问题类型；政策负责人裁决是撤回、拆适用范围还是发布新版本；工程重建索引后用原工单与相邻反例回放。客服可以在人工模式按负责人临时书面指引处理，但临时指引也要留版本和有效期，不能在群里一句“先按老办法”让系统无法追溯。

**领导：**怎么衡量规则台账有没有效果？

**小陈：**看旧版进入可用候选的次数、草案抢跑次数、适用条件缺失而被正确停答的次数、规则冲突从发现到裁决的时长、已发答复引用有效条款的比例。还要抽样看“没有误引但答非所问”的工单，因为版本正确不代表证据适用。上线前回放旧版、草案、地区例外、活动期与生效临界点；上线后监控每个发布版本的错引与客户复联。一个百分比“知识命中率”无法替代这些问题。

## 领导最后考小陈：规则比检索多管哪一步

**领导：**向量检索已经能把最像的条款排第一，为什么还需要台账？

**小陈：**相似度只回答“文字像不像”，台账回答“这份规则在这个时间、地区、订单上有没有权威”。两者是不同问题。先用确定性条件限定合法候选，再在候选里搜索，最后核答复能否被条款支持。把排序分数当政策效力，旧 FAQ 标题写得越像客户问题，就越容易让系统自信地答错。

**领导：**规则改了，为什么不能只更新向量索引？

**小陈：**还要更新状态、缓存、适用范围、提示与回放样本，确认线上查询返回新版本。旧版历史保留供审计，但不进当前对客集合。索引是加速器，不是发布审批系统。

**领导：**没找到适用规则时，Agent 要说什么？

**小陈：**说清目前无法依据现行规则判断，保留已核实的订单事实，把待确认的适用条件或冲突交给负责人，并给客户下一次更新方式。没证据时不编结论，客户少走一次错误退款流程，比听到一段漂亮却无效的承诺更实用。

## 台账落库以后，查询条件长什么样

**领导：**研发说抽象原则听懂了，缺一份能照着建的示例。

**小陈：**可以把 B 条规则的元数据写成示意对象：

```json
{
  "policy_id": "delivery-dispute",
  "version": "v4",
  "status": "effective",
  "business_line": "online-retail",
  "regions": ["示例地区A"],
  "order_types": ["regular"],
  "applicability_basis": "after_sale_request_at",
  "effective_from": "2026-09-20T00:00:00+08:00",
  "effective_to": null,
  "approved_by": "售后规则负责人",
  "approval_receipt": "approval-041",
  "supersedes": ["delivery-dispute:v3"],
  "source_section": "签收争议/核对凭证"
}
```

字段值与日期都是虚构示范。系统接到 0823 时，从已授权工单读业务线、地区、订单类型和售后申请时间；过滤器判断每个条件，不满足的条款给出明确原因，比如 `expired`、`draft`、`region_mismatch`、`basis_time_missing`。检索团队看到“没命中”时，能知道是没有文档、条件过滤掉了，还是关键词没召回。没有过滤原因的黑箱，只会把运营同事逼去上传第四份“最终版”。

**领导：**为什么时间里写了时区？

**小陈：**政策若约定“九月二十日零点生效”，系统得知道以哪个时区的零点算。跨地区客户、跨境订单和定时索引任务可能使用不同时区；把日期只存成字符串，临界点最容易出错。若规则按自然日而非精确时刻生效，也要在业务配置里写明时区与包含边界。测试 23:59、00:00 和跨地区时刻，确认同一单不会因服务部署在哪台机器而得到不同答案。

还有两类时间要分清：规则说“业务上何时适用”，系统说“我何时得知这份规则”。假如负责人周一补录一条上周五已生效的政策，今天的查询要按业务有效时间判断，但复盘周六 Agent 为什么没用它时，也要知道当时系统还未录入。历史记录既有业务生效时间，也有系统记录时间，这种双时间视角能解释事后补录和追溯修正。具体是否追溯影响已处理客户，仍由业务负责人决定。

## 从“最终版2”迁移过来，先别一夜把库洗白

**领导：**我们现在几百份老 PDF，没有这些字段。要全补完才能用 Agent？

**小陈：**先限定试点范围，比如签收争议与退款资格这两类高频题，找规则负责人确认现行权威文件和适用条件，把旧版、草案隔离。迁移工具可帮忙从 PDF 提取标题、日期和条款位置，但“是否生效、覆盖哪个地区、谁批准”必须有权的人确认。未整理的资料可留在受控历史区供人工查，不进入自动对客检索。这样不需要一夜治理全库，也不让未经核实的几百份 PDF 决定客户权益。

迁移过程中让新旧检索并行作内部对照：同一批虚构或脱敏工单，旧系统会返回哪些文件，新过滤器为何排除；业务负责人抽查被排除和新纳入的样本。不要把“召回文件数下降”当故障，过滤掉旧版正是目的；也别把“只返回一篇”当成功，若现行规则被误排，Agent 同样没依据。对照表要有适用条款召回、误引率、冲突停答和人工接手结果。

**领导：**发布负责人休假，遇到冲突怎么办？

**小陈：**台账里要有代理责任人和升级路径。冲突工单停在“规则待确认”，客户得到真实进度，值班客服根据公司已批准的临时流程处理，不私自宣布退款；紧急裁决也要留下审批记录、适用范围和到期时间。规则治理不是让一个人守着 PDF 盖章，而是把谁能裁决、裁决何时有效、系统如何执行写清。领导要的“今天能用”，就靠这条可追责的应急路，而不是让模型猜老板睡醒会怎么想。

## 最后用六张反例，试出“永远用最新”有多不靠谱

**小陈：**第一张，新上传旧内容，检查上传时间不会压过业务失效状态；第二张，最新草案，检查未到生效日不会进入对客候选；第三张，通用规则与地区例外同时有效，检查地区匹配后只用适用结论；第四张，售后申请刚跨零点，检查时区和边界；第五张，两份有效规则同范围冲突，检查系统停答并交有权负责人；第六张，已答复的老工单跨政策更新，检查历史引用仍可追溯，后续新决定按负责人批准的追溯规则执行。

每张反例不仅看 Agent 最终说了什么，还看过滤日志：哪些条款进入候选、哪些被挡、原因是什么、生成用了哪个版本、发送前有没有再次核验。这样查错时能区分“元数据填错”“索引没更新”“检索排序不对”“模型越过条款”四种问题。只用一条漂亮答案验收，下一次“最终版4”仍会趁夜上岗。

**领导：**这么一套下来，客服要不要每天背版本号？

**小陈：**不用。工作台直接展示当前适用条款的标题、版本、生效范围和来源链接；客服点开能看审批与例外。系统负责拦不适用的文档，人负责裁决业务上仍有争议的条件。客户不需要听我们解释索引，只需要得到按当时规则可执行的答复。如果规则还不明确，就告诉他谁在核查、何时更新，而不是让一份名字叫“最终版”的旧 PDF 替公司做决定。

这次交付后，小陈把“最终版”“最终版2”都移出自动回答集合，只让经过责任人确认的条款进入测试。领导说：“看来文件名最该加的不是数字，是负责人的名字和生效日期。”
