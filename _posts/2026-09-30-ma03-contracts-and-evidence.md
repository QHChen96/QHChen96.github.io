**领导：**合同 Agent 说可以九折，客户研究 Agent 说去年谈过八五折，服务 Agent 说投诉还没处理。我让汇总 Agent 综合一下，它写成“建议八五折并承诺优先解决”。综合能力不错啊。

**小陈：**它把三条不同地位的信息搅成了一杯价格特调。去年谈过不等于今年获批，现行规则允许不等于这个客户适用，工单待处理更不等于我们已经承诺完成日期。先把证据的身份写清楚，再让它综合。

本篇沿用**教学虚构**的星河制造续约准备。目标是把三路研究的结果收成一份可核验资料，而非让几个角色投票选一个最顺耳的说法。所有协议字段和冲突案例由作者为教学设计；引用的框架能力只用于说明相应机制，不代表它已经替应用解决了业务一致性。

## 一、先把一条回传分成四层

**领导：**研究结果就是一段文本，还有什么层？

**小陈：**第一层是运输身份：哪次运行、哪项任务、哪次尝试发来的。第二层是执行状态：成功、缺资料、权限不足、超时还是失败。第三层是业务内容：查到了什么事实和证据。第四层是决定建议：下一步可以考虑什么。四层混成一句“已完成，建议八五折”，接收方没法安全处理。

运输身份解决“这条东西能不能进入当前运行”。执行状态解决“它有没有满足这项工作的交付要求”。业务内容解决“这个主张由什么支持”。决定建议只是待讨论产物，不可以自动进入权威事实区。主流程可以从消息里取建议，却要根据事实和审批状态决定是否使用。模型表达得肯定，不会提高证据权限。

还有一个经常被忽略的字段：逻辑任务与尝试必须分开。合同任务`contract`第一次读取接口超时，第二次成功；第一次的晚到回传可能在第二次之后到达。系统要依据授权的有效尝试与任务状态判断是否接受，不能因为“最近到达”就覆盖合格结果。消息时间也不能单独证明哪份合同更新；到达时间与资料生效时间是两套钟。

下面是一份**教学结果信封**。状态值属于业务设计，字段类型应在应用中用 schema 校验：

```json
{
  "run_id": "renewal-042",
  "task_id": "contract",
  "attempt": 2,
  "customer_id": "customer-17",
  "status": "succeeded",
  "schema_version": 1,
  "artifact_ref": "evidence/contract-v4",
  "claims": [{
    "claim_id": "renewal-discount-rule",
    "kind": "policy_fact",
    "value": "九折需要满足规则并取得适用审批",
    "source_id": "policy-2026-09",
    "source_version": "4",
    "locator": "section-3.2",
    "effective_at": "2026-09-01",
    "uncertainty": "本客户尚无审批记录"
  }]
}
```

`artifact_ref`让完整证据保存在受控工件中，信封只带必要摘要；接收方展开时仍要检查权限。`source_version`不是装饰，后续来源更新可据此找到依赖它的草稿。`locator`应定位到文档段落、记录字段或工单事件，不能只有一个主页链接。`uncertainty`保留缺口，不让下一位在润色时把它抹掉。哈希可以检查内容是否变化，却不能证明内容正确或当前用户有权读它。

## 二、消息合法不等于证据成立

**领导：**JSON 校验通过，就能放心合并了吧？

**小陈：**只是结构过关。字符串字段里完全可以放“我猜客户已经获批”。我们至少还有身份校验、来源校验和语义校验。它们的失败原因要区分，才能知道修的是协议、数据还是判断。

身份校验核对运行、任务、尝试、客户、租户和来源能力。不是当前预期任务的回传要拒绝或隔离；另一个客户的工单即使内容相关，也不能进入这轮证据。来源校验确认文档存在、可访问、版本有效、定位能找到，引用不是模型编出来的 ID。语义校验则判断原文是否真的支持主张，有没有遗漏条件或把历史事实写成现行政策。

这三个步骤应尽量由不同的证据支撑。主键和权限通过业务服务判断，版本通过登记表判断，数值计算通过代码判断；需要语言解释的部分再用模型或人工复核。让原研究 Agent 自己再回答一次“我的引用是真的吗”，很可能重复同一个误读。分层检查还能减少模型成本：明显不属于当前客户的结果，根本不必进入昂贵的语义审核。

**领导：**模型返回一个高置信度呢？

**小陈：**那是它报告的分数，除非我们在目标分布上校准并验证过，否则不能当真实概率。它可以帮助排查或排序，但“零点九八”不能抵消版本过期。尤其是缺少来源时，高置信度只会让错误更像一份正式文件。

## 三、事实、假设和建议必须分账

星河制造去年的销售笔记写着“客户提出八五折，待审批”。合同政策写着“符合条件时可申请九折”。客户投诉记录写着“希望优先修复报表问题”。三者分别是历史谈判记录、现行规则和用户诉求。把它们合并后，我们可以写“续约前需核对折扣资格并确认服务计划”，却不能写“已批准八五折并保证本周修复”。

我们让证据条目带`kind`。事实条目记录已核实状态；假设条目记录基于事实的推断以及待验证条件；建议条目记录可选动作与理由；批准条目必须来自受控审批记录，不接受模型自己生成。类型本身也要验证，模型把猜测标成`fact`不能直接放行。可靠的类型体系来自数据来源与业务检查，schema 只是表达载体。

写作时只允许把事实改成易懂表述，不允许改变地位。若需要把假设写入草稿，就使用清晰措辞并列出条件；若建议涉及价格或承诺，明确“待审核”。事实缺失不能靠其他 Agent 的认可补足。多个角色重复一条主张，只会增加文本副本，不会增加独立来源数量。统计证据覆盖时，应按来源链去重，别把同一合同被引用三次算成三票。

**领导：**这会不会让文章太啰嗦？

**小陈：**客户看到的稿件可以简洁，系统里的证据关系必须完整。我们可以把来源放成简短标记，把详细证据留在内部附件；销售点开即可核对。少写无关推理，多保留影响决定的条件。简洁与可追溯可以同时存在，前提是压缩表达没有压掉关键限制。

## 四、为什么共享一个字典，最后最容易谁快谁赢

多个分支各自返回状态更新时，默认覆盖是最危险的简化。客户研究写`risk="low"`，服务研究写`risk="high"`；谁最后写入，主流程就显示谁的结果。运行速度发生变化，业务结论也变了。这不是智能波动，是状态设计把事实裁决交给了调度时序。

我们应先存有归属的分支结果，再单独计算汇总视图。`results[task_id]`保存每项任务被接受的输出，`claims[claim_id]`保存主张与来源集合，`conflicts`保存未解决矛盾。字段写入所有权也要明确：合同分支可以提交合同证据，不能覆盖客户身份；写作分支可以提交草稿，不能修改权威审批状态。主流程的决定字段只由决定步骤写入。

合并函数常被称为 reducer。它规定旧状态和新写入如何形成下一状态。拼接列表容易实现，但重复消息会重复追加；简单按键覆盖容易实现，却会吞掉版本冲突。并行重放环境中应明确合并是否对重复、乱序和分批写入稳定。我们经常希望满足幂等、交换或结合等性质，但这些不是每个业务字段都天然具备。金额余额例如不能靠随意合并文本恢复，应该由业务账本管理。

下面是**简化 reducer 伪代码**，展示重复结果与不同内容的区别；身份和权限在进入它之前已校验：

```python
def merge_results(old, incoming):
    merged = dict(old)
    for task_id, result in incoming.items():
        previous = merged.get(task_id)
        if previous is None:
            merged[task_id] = result
        elif previous["artifact_hash"] == result["artifact_hash"]:
            continue
        else:
            raise ResultConflict(task_id)
    return merged
```

相同工件哈希表示相同内容的重复提交，直接忽略；同一逻辑任务出现不同工件则交给冲突策略，不做无声覆盖。生产实现还要比较有效尝试、结果版本、取消状态和业务修订号。若允许一次新尝试正式替换旧结果，应由编排器先发布明确的替换授权，并保留历史引用；不能让任何晚到消息凭一个更大的自报编号取代当前结果。

列表是否适用，也要看用途。运行事件适合追加并按事件 ID 去重；当前合同事实适合有版本的对象；多个候选建议可以存集合等待评审。不能把一套 reducer 套给所有字段。LangGraph 的状态归并机制能承接这类设计，但具体归并规则仍由应用定义；它不能替我们决定哪份业务材料具有权威性。

## 五、两个专家意见不同，先判断它们是否真的在说同一件事

**领导：**那九折和八五折就是冲突，挑更新的一份。

**小陈：**先确认对象、时间、条件与信息类型。去年申请八五折与今年九折规则，未必是两个同时有效的价格事实。直接挑更新，可能把历史谈判价值删掉，也可能把当前政策误当成已经获批的报价。

冲突检测至少对齐四个维度：是否同一客户和合同、是否同一属性、是否同一生效范围、是否都在陈述可比的事实。只有对齐以后，才判断它们互斥。不同时间的使用指标可以一起保留形成趋势；同一时刻的两份生效合同版本则必须查权威登记。模型可以帮助发现潜在矛盾，确定处理流程最好由版本与业务规则驱动。

处理顺序可以这样落实。先排除错客户、错范围和失效来源；再按业务登记确认权威文档与适用期；若只是不同粒度，把原始指标与派生统计保留为不同字段；若事实仍无法一致，产出冲突记录并阻断相关承诺。冲突记录写两方主张、来源定位、影响的决定以及需要谁确认。这样销售拿到的是“缺合同适用确认”，而不是一句令人绝望的“系统异常”。

**领导：**可以让第三个专家当裁判吗？

**小陈：**可以让它辅助整理争议，但裁判也必须读取原始来源和权威规则。只读两份摘要再投票，就是用第三次压缩去裁决前两次压缩的损失。裁决结果要留下依据；无法确认时保留未知，不把“有了裁判”当成“有了事实”。

## 空值、单位和时间窗口，也要进入证据契约

**领导：**客户研究返回使用量零，服务研究返回工单数量空，写成“客户没在用，也没有问题”行不行？

**小陈：**零是测得的数值，空可能是没权限、接口失败、尚未采集或不适用。我们让指标同时带值、单位、统计窗口、采集状态和来源。没有成功观测就不能用零填充；没有工单记录也要确认查询范围与返回完整性。否则一次接口故障会被写成客户流失证据。

时间窗口尤其容易串。一个分支统计过去七天活跃账号，另一个统计自然月付费账号，数字不能直接相减。账号、席位、登录次数也不是同一单位。先由定义表指定口径，再让研究者提取；需要换算时保留原值和计算过程。来源系统使用不同时间区间或时区，要在归并前统一边界并注明限制。可复算的派生值属于计算结果，不冒充原始观测；缺失数据可能影响哪些建议，也在证据条目里关联。协议认真处理这些小字段，比让汇总者猜一个“总体趋势”可靠得多。

## 六、上下文裁剪：把该带的带过去，不要每次搬家公司

给每个 Agent 复制全部会话有两个后果：成本扩大，任务重点变模糊。合同研究只需要当前客户、合同入口、核对目标和允许来源，不需要客户研究的全部网页，也不需要模型内部反复改稿的文本。服务研究需要相关工单与产品范围，不需要商业折扣讨论。越界的信息即使与任务沾边，也不能因为“方便理解”就顺手传播。

上下文包可以分三层。固定指令说明角色、输出结构与禁止动作；任务输入携带当前对象和具体问题；证据入口提供授权引用，按需检索原文。把大量可重取内容留在工件里，把不可丢的确认事实、未解决条件和版本放在轻量摘要中。摘要要保留反例和未知，否则后续单元只看到一个过度乐观的任务背景。

裁剪也不能只看 token。将合同例外条款删掉可以立即省输入，却可能让核心结论错误。先按决策需要选证据，再按长度压缩；关键规则保留准确定位与适用条件。读取引用时若权限已变、来源已更新，要重新确认，不把“上一次能读到”当永久通行证。摘要缓存应绑定客户、资料版本与访问范围，不能只按问题文字命中。

**领导：**共享记忆是不是让大家永远不用重复查了？

**小陈：**记忆是带有效期的资料，不是事实的退休保险。客户偏好、上次已确认身份、历史处理计划有不同的保留期限。每条记忆要有来源、形成时间、适用范围和失效规则。存进去的摘要若本来就错，共享得越广，错误越便宜。

## 七、共享记忆与广播，分别解决什么

线程内状态保存当前运行进度，跨运行记忆保存以后仍可能有用的信息，工件库保存具体产物，知识库保存经过管理的资料。它们可以使用同一存储服务，却不应混成同一种语义。运行失败的临时推测不能自动写进客户长期画像，待审草稿也不能自动成为下次检索的权威政策。

[LangGraph Persistence 文档](https://docs.langchain.com/oss/python/langgraph/persistence)区分线程范围的 checkpointer 与跨线程的 store。这个技术区别可以帮助组织状态，但存储键与访问控制仍由应用设计。跨线程并不等于跨租户公开。键名可以包含租户与客户范围，读取时还要有服务端权限校验；仅把租户 ID 拼进字符串，不能证明不会越权。

广播解决消息分发，不解决信息合法性。[AgentScope Java 的 MsgHub](https://java.agentscope.io/v1/en/docs/task/msghub)让参与者的回复自动被其他参与者观察，减少手工传递。它适合明确范围内的讨论。但如果三位专家有不同数据权限，默认互相广播可能让合同敏感信息进入不该看到它的上下文。先定义参与范围与可传播内容，再选择广播能力。

**领导：**我只广播摘要，总安全吧？

**小陈：**摘要可能包含客户身份、价格、投诉和推断，同样是数据。派生信息的权限至少要继承来源限制，不能因为换成中文短句就降低访问要求。工件引用也要在读取时授权，不让一个能猜出路径的 Agent绕过检查。我们可以广播“任务完成、证据引用可请求”，再由各自的权限决定能展开什么。

## 八、更新一份资料，为什么三份草稿都要重新看

续约草稿中的一句话可能依赖合同政策和工单状态两份材料。只记录最后一份摘要，会失去依赖关系。我们应让主张关联证据 ID，证据关联来源版本，草稿关联所使用的主张版本。来源更新后，从这条依赖链找出受影响的结论，再决定局部重查、重新写作或撤销待审状态。

不需要一开始就建复杂知识图谱。用三张明确的关联表就能起步：证据到来源、主张到证据、产物到主张。版本更新事件能查询这些关系，标记受影响产物。若只是标题修正且不影响主张，可以保留验证结果；若折扣条件改变，则原审核不能继续有效。是否影响决定要有规则与记录，不让模型随口说“变化不大”。

过期失效和物理删除也不同。当前业务视图可以停止使用旧证据，审计所需历史应按保留政策保存；敏感数据依法或按组织要求删除时，还要处理派生摘要与缓存。对外不需要展示一整套版本技术，但内部必须能回答“这份稿子当时依据了什么，后来何时不再适用”。这直接关系到错误更正和恢复。

## 九、把混乱资料收成今天能用的交付

| 检查层 | 本案例的规则 | 不通过的结果 |
| --- | --- | --- |
| 任务身份 | 属于本次运行和当前有效尝试 | 隔离晚到或无关回传 |
| 客户范围 | 客户、租户和合同关联一致 | 阻断合并并记录归属错误 |
| 来源版本 | 权威登记确认有效资料 | 返回失效或待核对 |
| 主张支持 | 原文支持结论与条件 | 保留缺口，不进入确定事实 |
| 冲突处理 | 对齐对象与时间后按规则裁决 | 阻断受影响商业承诺 |
| 草稿依赖 | 每项关键主张可追到证据版本 | 退回改稿而非直接批准 |

**领导：**所以最终怎么写那句折扣？

**小陈：**写“当前政策允许符合条件的申请进入九折审批；该客户是否符合以及最终价格尚待确认。去年八五折诉求保留为谈判背景，不作为现行批准。未解决服务问题另列处理确认项。”销售一眼知道哪些能说、哪些还不能说，不用在三份摘要里找谁嗓门最大。

**领导：**消息协议为什么还要版本？

**小陈：**因为团队会改字段。旧工单 Agent 用`open`表示所有未完成状态，新版本把等待客户与内部处理分开；没有 schema 版本，汇总器可能把状态解释错。升级时要保留兼容读取或明确拒绝旧格式，回放历史也要使用对应解释。协议变更是接口变更，不是一句提示词润色。

这篇的交付是结果信封、分层校验、冲突记录与证据依赖关系。下一篇用它们开始调度：任务已经分对、结果能收住，为什么并发一调大，系统反而排队更久、账单更厚。
