**领导：**我看流程图挺完整：消息进工单系统，n8n 调 Agent，Agent 查订单，客服审核，然后自动回写。怎么客户明明收到了回复，后台还显示“无人处理”？

**小陈：**因为图里全是箭头，没有“谁说了算”。n8n 看到任务成功，是工作流运行成功；Agent 生成了草稿，是查证和起草成功；渠道返回已发送，是一条消息发成功。**这三件事都不等于工单已经解决。**

小陈打开虚构的 0823 号工单。客户说“显示签收，没收到货”。Agent 查到“已签收”，草稿写“我们继续核查签收凭证”。客服批准并发出。n8n 收到成功回执后把流程标成绿色，可工单还需要物流调查。第二天客户追问，队列里却没有责任人。图上漏掉的不是一个节点，是业务上的“谁继续管”。

## 先定唯一的账本，再定每段谁有权动笔

**领导：**把所有状态都放 n8n 不就统一了？

**小陈：**编排工具可以调度，但工单的权威状态仍放在工单系统。原因很实在：客服换班、客户再次来信、审计抽查和人工改派，最后都要在同一张工单上看得到。n8n 可以被替换，工单历史不能跟着消失。

| 组件 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 工单系统 | 工单 ID、客户关联、责任人、状态、时限、最终结案 | 让模型自己决定业务事实 |
| n8n 或其他编排层 | 接事件、调服务、重试可安全重试的步骤、记录运行关联 | 代替工单系统宣告“已解决” |
| Agent 服务 | 在授权范围内查证、引用规则、生成内部草稿和未决项 | 直接改客户身份、审批、发送或结案 |
| 审批与发送服务 | 绑定草稿、收件人和批准人；发送并记渠道回执 | 猜测业务后续已完成 |
| 客服／物流负责人 | 接下调查、处理例外、确认解决 | 为没有证据的自动答复背书 |

**领导：**接口上怎么保证这些箭头不是“画着好看”？

**小陈：**给每张单一个稳定的 `ticket_id`，每次触发再有 `event_id` 和 `run_id`。工单事件只带必要字段：事件类型、工单版本、渠道、授权范围和关联 ID；客户原文由有权限的服务按需读取，别把地址复制进每个 Webhook。下游写回要带工单版本：如果客服在 Agent 思考时已改派或结案，旧运行的写回要被拒绝并进入冲突队列，不能覆盖人的更新。

接口契约可以长这样。这里的 ID 与版本是示例，重点是**事件唯一、业务版本明确、敏感内容不随事件广播**：

```json
{
  "event_id": "evt-0823-04",
  "event_type": "ticket.evidence_requested",
  "ticket_id": "0823",
  "ticket_version": 7,
  "run_id": "run-9f2",
  "channel": "app",
  "allowed_tools": ["read_current_order", "read_active_policy"]
}
```

编排层接到事件，先用 `event_id` 去重；调用 Agent 时把授权范围从服务端带过去，而不是让 Agent 自己根据客户原话决定能看什么。Agent 返回的是**提议**，工单系统检查 `ticket_version` 仍为 7 才能写草稿。若客服此时已把工单推进版本 8，编排层把冲突放进待核队列，不能悄悄用旧证据覆盖新处理。发布到生产前还要演练“工作流重启后重放同一事件”，看它会不会重复建子任务。

一次正常流转是这样：工单系统发“待查证”事件；编排层接到事件后去重并调用 Agent；Agent 返回**证据引用、草稿、未决项**；工单系统保存内部草稿；客服审批；发送服务核对批准版本后外发；渠道回执回写“已回复”；工单仍归物流核查负责人，直到有签收调查结果和客户问题的处理结论，才能走结案审核。

**领导：**万一 n8n 那段掉了？

**小陈：**掉了也不能丢单。事件写入工单侧待处理表，编排成功与否另记运行状态；超时进入有主的重试或人工队列。重放同一 `event_id` 不再多发一条消息；若发送结果未知，先查渠道回执。[n8n 官方文档](https://docs.n8n.io/build/flow-logic/handle-errors-gracefully)提供错误处理和错误工作流能力，但业务去重、工单所有权和“已回复不等于已解决”的规则要我们自己实现。

领导问：“n8n 的执行记录不是也能查吗？”小陈把两个记录并排放：n8n 记录“节点 6 成功”，工单记录“物流还未回执、客服小陈负责”。前者帮助工程师定位哪一步断了，后者告诉业务下一步该找谁。运行记录清理或更换编排产品，不应清掉工单的待办。反过来，工单只写“失败”也不够排障，要能从工单关联 ID 点回那次运行的错误节点与重试次数。

## 为什么“画了箭头”仍会丢单：跨系统有三类不同的写入

**领导：**既然有 `ticket_id`，每个系统都回写同一张单，不就一致了吗？

**小陈：**关键不是 ID 一样，而是谁有权改什么。工单系统的“责任人从 A 改到 B”是业务命令；编排层发出的“我查证完了”是运行事件；Agent 的“建议回复”是候选内容。三者若都能直接把工单状态写成“已解决”，就会发生最后写入的人赢：客服刚标“待物流”，Agent 的旧运行延迟十秒返回，把状态盖成“已回复已结案”。这不是模型语气问题，是多写者竞争。

我们给接口分两类。**查询接口**按当前工单授权读取订单状态、规则版本和已发消息，返回最小必要字段；**业务命令接口**由工单系统校验状态转换、操作者、版本和审批记录。Agent 不能持有能直接改工单状态的通用 API 密钥。它提交 `ProposeDraft`，工单系统决定是否接受为内部草稿；客服点击批准，审批服务生成绑定内容与收件人的批准记录；发送服务用批准记录执行外发。业务状态变化由明确的命令驱动，运行成功只能作为证据之一。

小陈拿一个竞态做演示：08:00 Agent 在工单版本 7 上开始查证；08:01 客服发现客户给错了订单号，把工单改成版本 8；08:02 Agent 还用旧订单号生成草稿并请求写回。写入时带 `expected_ticket_version=7`，工单系统发现现值是 8，返回冲突。编排层不把冲突当普通网络失败盲目重试，而是重新读取版本 8，确认旧草稿是否仍适用；不适用就废弃并记录原因。这个乐观并发校验比“谁最后写谁赢”多一步，却能挡住一类很难在演示里看见的错单。

## 事件发不出去怎么办：业务数据与通知要一起落地

**领导：**工单系统刚写成“待查证”就崩了，事件没发给 n8n，谁知道还要跑 Agent？

**小陈：**这叫双写问题：数据库更新成功，事件通知失败。可用事务性 outbox 的思路，在同一个数据库事务里保存工单状态和一条待发布事件；后台发布器再把事件送出，成功后标记已送。发布器可能重复发送，所以消费端仍按 `event_id` 去重。[AWS 的事务性 outbox 指南](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)专门解释了数据库写入与消息通知之间的不一致风险。这里不是要求一定装某个消息中间件，而是要求“工单已进入待查证”与“这件事待通知”不能只靠两个互不相关的按钮。

反过来，n8n 已经调用了 Agent，但写回工单超时，也不能立即再次生成并外发。先查工单里有没有同一个 `run_id` 的草稿或发送动作；有就继续后续步骤，没有且能确认未写才重试；状态不明时给人一个待核任务。**至少一次投递 + 消费端幂等**比口头承诺“消息只会来一次”更符合分布式系统现实。出站消息还要有业务唯一键，例如 `ticket_id + draft_version + channel + recipient_ref`，避免同一运行重放后给客户发两封信。

**领导：**那是不是所有失败都交人工？

**小陈：**不是。只读订单查询超时可以在总时限内有限重试；知识检索服务短暂故障可以降级为“证据不足，转客服查”；工单状态版本冲突应重新核对事实，不应机械重试；发送结果未知必须查渠道回执或人工对账。我们按“动作是否可安全重复”和“结果是否可确认”分支，不让平台默认的重试按钮一视同仁。退款更是高风险写操作，未知结果要按业务幂等键查流水，不能由 n8n 跳回上一个节点再点一次。

## 用一张单跑完全程，再故意把每根线拔掉

小陈把 0823 号工单画成时间线。09:00 客户消息入站，渠道给 `source_event_id`；09:01 工单系统核身份、建单并保存待查证事件；09:02 编排层收到事件，按授权范围调用 Agent；09:03 Agent 查本单订单和现行签收规则，返回“已签收但客户称未收到、需要物流核查”，只生成内部草稿；09:04 客服审核并把物流子任务指给负责人；09:05 批准给客户发“已启动核查”，发送服务拿到渠道回执；09:06 工单状态仍是“待内部处理”，而不是“已解决”。第二天物流回执回来，客服继续处理同一张单。

在这条线上，小陈准备四种故障注入：

| 拔掉哪根线 | 预期可观察结果 | 不允许发生什么 |
| --- | --- | --- |
| 工单写库后断开事件发送 | outbox 待发布事件仍在，恢复后送达 | 工单永久静默 |
| 同一事件送三次 | 消费端只建立一项有效查证任务 | 三份草稿、三封外发 |
| 客服改派后旧运行返回 | 版本冲突进入待核 | 旧草稿覆盖新负责人决定 |
| 发送成功但回执超时 | 查渠道与本地发送记录，未知时挂起 | 盲目换键重发 |

**领导：**这不就是测试吗？文章为什么要写这么细？

**小陈：**因为平台演示通常只跑第一条全绿路线，而生产问题往往卡在第 2 次投递、第 8 分钟的超时和交班后的无主工单。只有把故障注入写成验收条件，采购或开发时才知道要向平台、工单系统和业务团队分别要什么。否则“支持自动化”四个字谁都能说，出了事却没人能回答“这张单现在哪儿”。

## 观测与容量：技术值班看运行，客服值班看待办

每次运行至少关联 `ticket_id`、`event_id`、`run_id`、发布版本和步骤耗时。技术轨迹记录工具名、状态码、错误类型和必要的脱敏引用；客服工作台显示当前负责人、未决事实、待办到期时间、最近一次对客承诺。技术人员不必读客户完整地址就能定位失败节点；客服也不必去 n8n 后台猜哪个节点变红。原始附件和敏感订单信息仍由业务系统按权限展示，运行日志只留最小诊断信息。

**领导：**大促时一小时进来十倍工单，谁先崩？

**小陈：**先看每段容量。入口可以先接事件并排队，不要让客户请求一直等 Agent 运行完；编排层限制并发，避免同时打爆订单系统；Agent 服务限制每单步数和模型预算；人工队列有容量与超时升级。积压时优先保证工单创建和有主待办，非紧急的摘要生成可延后。n8n 官方有[队列模式](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode)与[并发控制](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/control-concurrency)文档，但具体负载阈值要在本公司的接口限流和客服班次条件下测试。排队 20 分钟仍没人接，不是“系统处理成功”，应在工单侧显示和告警。

## 领导顺手考了五个原理问题

**领导：**第一问，为什么工单系统是事实来源，n8n 不能当唯一账本？

**小陈：**工单承载客户、责任人、状态、审批和结案依据，跨班次和跨工具都要稳定；n8n 的执行记录承载一次自动化运行的节点状态。业务事实与技术运行生命周期不同，换编排组件不应让客户问题失去主人。

**领导：**第二问，`event_id` 和 `run_id` 为什么不能合一个？

**小陈：**同一业务事件可能因超时重投，触发多次技术运行尝试；`event_id` 用于识别“这是同一件业务事”，`run_id` 用于定位“这次具体跑了什么”。合起来就难以区分重复投递与真正的新事件，也难以排障。

**领导：**第三问，事务性 outbox 解决了什么，没解决什么？

**小陈：**它解决工单状态写库成功而事件通知丢失的双写窗口；不保证下游只收到一次，不代替消费端幂等，也不决定客服该不该结案。发送渠道的未知结果仍要单独对账。

**领导：**第四问，为什么 Agent 只提交草稿，不直接调用“完成工单”？

**小陈：**模型擅长整理证据和生成提议，但业务状态转换需要权限、版本、结案依据和责任人校验。把通用写权限交给它，客户一句提示注入或一条旧规则就可能触发越权结案。

**领导：**第五问，如何证明“转人工成功”？

**小陈：**至少分入队和接手两个回执，队列有值班人，具体客服确认后工单责任人才切换；超时未接要升级。编排节点返回 200 只说明请求被接受，不说明有人开始处理。

## 把接口责任写到字段，不让“已完成”有四种解释

小陈把四种最容易混淆的返回值贴在会议室墙上。`agent_completed` 表示 Agent 结束一次查证，产物可能只是“证据不足”；`draft_approved` 表示某人批准某版内容，但还没发；`message_delivered` 表示渠道确认消息送达，不代表客户同意；`ticket_resolved` 才表示业务结案条件满足。接口返回值不能都叫 `success=true`，否则集成的人会把绿色勾误译成“客户的问题解决了”。每个事件都带时间、操作者或服务身份、工单版本与关联证据，其他系统只消费自己需要的部分。

| 事件 | 写入方 | 必要约束 | 工单侧结果 |
| --- | --- | --- | --- |
| `evidence_ready` | Agent 服务 | 工具与规则引用存在，当前工单版本仍匹配 | 新增内部查证卡，不自动外发 |
| `approval_recorded` | 审批服务 | 批准人有权，草稿哈希与收件人绑定 | 草稿进入可发送候选 |
| `delivery_confirmed` | 发送服务 | 渠道回执与业务幂等键匹配 | 记录已回复，但保留未决待办 |
| `investigation_closed` | 物流或人工负责人 | 有调查回执和处理结论 | 由工单状态机判断能否结案 |

**领导：**如果客服先批准，规则版本随后更新，旧草稿还能发吗？

**小陈：**这取决于发布策略，但不能默默照发。审批记录保存起草时的规则版本和订单查询时间；发送前检查是否出现会改变结论的更新。若新政策已生效、订单状态变化或收件人变化，旧批准失效并回到审核；若只是无关的措辞版本更新，可按事先批准的规则处理。关键是**让状态变化显式化**，而不是让编排层拿着昨天的绿色回执继续跑。对于运行中的工单，我们固定发布版本或明确中止重启，避免前半程按旧规则、后半程按新规则。

小陈还把交班事故写成值班剧本。晚班客服接到 0823，发现编排运行仍在等待外部接口；她可在工单侧点击“人工接管”，系统撤销 Agent 的对客发送权，保留已有轨迹与草稿。若 Agent 此后迟到返回，只能作为内部建议，不能覆盖晚班已经发出的处理决定。接管人、时间和原因写入工单历史。这个设计让业务真正能在自动化卡住时继续工作，也让事故复盘能分清“系统未完成”和“人已接手”。

最后，一张单的验收报告要分两份。技术报告回答消息是否重复、接口如何超时、运行轨迹是否完整、积压到多少；业务报告回答客户是否得到准确解释、还有什么待办、谁负责、是否按时接手。只交技术报告，领导会看到全绿却仍被客户追着问；只交业务报告，工程师又无法定位哪根线断了。两份用同一个 `ticket_id` 关联，才算端到端闭环。

**领导：**假如周一 n8n 整体不可用，客服是不是连工单都打不开？

**小陈：**不应该。工单创建、查看历史、人工分配和批准发送是核心业务路径，编排层故障时应能切到人工处理；只是自动查证暂时停用，并在工作台标明“自动化不可用”。待发布事件保留，恢复后按工单当前状态逐项判断是否仍需执行，不能一股脑补跑：已经由人处理完的单不再生成过期草稿，更不能补发旧回复。恢复脚本要有“模拟运行”清单，让值班人先看会影响哪些工单。这样 n8n 是帮客服省步骤的组件，而不是客户服务唯一的电源开关。

接口契约还要有版本。今天 `evidence_ready` 只有规则 ID，明天新增规则生效范围，旧消费者若忽略新字段可能照样放行不适用条款。发布时先让接收方兼容新字段，再逐步切发送方；不兼容的重大变化换事件版本并重跑回归工单。变更记录里写清“谁改了接口、影响哪些消费者、如何回退”，工单系统、编排层和 Agent 才能在不同升级节奏下继续认同一套事实。客服端也要看到版本变更提示，避免继续审核按旧字段生成的草稿。这样线上事故才能定位到具体一次发布，而不是把责任笼统推给“自动化偶发”。发布单里还应列明旧消费者何时下线、兼容期内谁监控异常事件，以及发现字段缺失时如何暂停对客发送。

## 交给领导的不是四张截图，是一条闭合链

**小陈：**上线验收用一张工单跑四次：正常回复后保留物流负责人；编排中途失败后待办仍在；客服抢先改派时旧运行不能覆盖；客户再次回复能回到原单且看到上次查证。每次都从工单系统点开：谁负责、谁批准、发了什么、还欠什么。若客服必须在四个后台拼图，这套集成还没做完。

**领导：**所以 n8n 该不该用？

**小陈：**可用来编排重复步骤和接异构系统，[Webhook](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook)和[错误处理](https://docs.n8n.io/build/flow-logic/handle-errors-gracefully)都有官方说明。它不该成为唯一业务账本。今天先把责任表和接口契约定下，再换哪款编排工具都不会把工单主人换没了。

**领导：**n8n 节点显示执行成功，工单系统却没建待办，谁负责补？

**小陈：**按业务请求 ID 查工单系统回执；编排平台节点成功可能只代表请求已发，不能证明待办落库。结果未知时挂异常队列，由值班人核对，避免新建一张重复工单。接口契约要写成功语义、错误码、重试与去重，监控同时看节点状态和业务完成状态。客户关心的是有人继续处理，不是画布上哪块变绿。
