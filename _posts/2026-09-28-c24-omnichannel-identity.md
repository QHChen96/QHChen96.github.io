**领导：**这个客户在微信说“包裹没收到”，App 又问了一遍，网页再投诉一次。系统建了三张单，三个 Agent 给了三种承诺。能不能按手机号一键合并？

**小陈：**先别点。微信聊天里的手机号可能是客户手填的，网页表单可能是家人代填的；同一个手机号也可能对应两个不同账户。错分三张单会烦人，错合成一张单可能把 A 的订单状态讲给 B 听。

小陈把三条消息排在同一张桌上。微信消息带平台会话 ID，没有登录身份；App 消息带已登录客户 ID；网页投诉带订单号和联系人手机号。它们都说“没收到”，但**相似内容不是同一个人，也不一定是同一件事**。先做关联，再决定是否合并，操作要留原始消息和撤销路径。

## 统一的是事件格式，不是把原文扔进一个大桶

**领导：**三个渠道进来，总得先有一套共同字段。

**小陈：**对。入口先生成不可变的渠道事件：`source`、`source_event_id`、接收时间、渠道会话 ID、已验证的客户 ID（若有）、本渠道可见的订单引用、附件引用、原始消息存放位置。后续再有 `ticket_id` 和 `case_link_id`。一条渠道事件只处理一次；重复投递不会再创建一张新单。原始聊天保留在各渠道的受控存储，统一事件只保存必要引用。

身份关联分三档。第一档，已登录 App 的客户 ID 与工单归属一致，可以自动挂到此客户的工单；第二档，客户提供订单号但身份尚未核验，只能作为“疑似相关”，不能展示该订单详情；第三档，只有相似话术或手机号，进入人工核实，不自动合并。跨渠道同案还要看事件时间、诉求、订单与当前处理状态：同一个人今天问发票和昨天投诉签收，不该挤成一张单。

**领导：**客户微信说的也是 0823 号订单，为什么还不能自动并？

**小陈：**订单号是线索，不是通行证。小陈拿两条假消息演示：微信用户甲说“0823 没收到”，App 登录用户乙也有 0823——如果订单号是公开运单截图里拍到的，甲可能只是代问或冒用。系统应先核渠道身份能否映射到订单有权人。核不出来，给客服一个“可能同案”提示，并挡住订单详情回显。确认甲是有权人后，再建立 `case_link`，写明证据、确认人、确认时间；若之后发现误判，撤销的是这条关联，不删除原来的渠道事件。

渠道事件还要处理时间乱序：客户先在 App 投诉，微信消息因为接口延迟半小时才到。不能按“最后到达”决定哪条是最新诉求，得同时保存客户发出时间与系统接收时间。若较晚收到的是更早的旧消息，Agent 不得用它覆盖刚刚已经批准的处理结论。附件也只保留渠道来源和授权引用，跨渠道展示前再次校验可见性。

**领导：**那三个 Agent 已经各说了一句，怎么避免继续打架？

**小陈：**确认同案后，工单系统定一个主工单和一个当前负责人；其他渠道消息作为带来源的事件挂上去。主工单里显示每个渠道已发的原话、批准人和回执，Agent 起草新回复前要先看已有承诺。若微信上已经说“正在核查”，App 不能又说“已经退款”。发送服务仍按渠道和收件人单独审批，不能因为合单就跨渠道乱发。相关但不能合并的单，用“关联工单”保留线索，不共享敏感内容。

小陈在客服页加了一个“承诺栏”：每条已外发承诺列出渠道、内容版本、发出时间、审批人和后续责任人。客服准备给 App 回答时，先看到微信那句“正在核查”，再决定是补充进展还是纠正旧话。跨渠道统一视图的目的，是让处理连续，不是把三个渠道的隐私边界抹平。

**领导：**误合了还能拆吗？

**小陈：**必须能撤销关联，恢复原事件与责任人，并审计误合期间有没有信息外泄。像 [Zendesk 官方的工单合并说明](https://support.zendesk.com/hc/en-us/articles/4408882445594-Merging-tickets)所展示的，合并在实际客服产品里也不是一个没有后果的按钮；我们自己的方案更应该先用“关联”代替不可逆的物理揉合。

## 第一关：同一个人，和同一个问题，是两种不同的判断

**领导：**客户已经登录 App，又在微信发来同一个订单号，还不能自动连起来？

**小陈：**要先问微信身份怎么核。App 登录态告诉我们 App 这一侧是谁；微信会话 ID 只告诉我们“这条微信消息来自同一个微信会话”，不自动证明它就是 App 里的客户。可以通过客户主动在已登录 App 内发起绑定、客服按既定身份核验流程确认，或业务系统已有可信渠道映射来建立身份关系。只凭手机号、昵称、头像和相似说话习惯不能放开订单资料。手机号可以被家人共用，昵称可重复，订单号可能来自截图。把“匹配概率高”当“可以查订单”的那一刻，全渠道视图就变成跨客户信息出口。

就算身份确认是同一个人，也要再判断是否同一问题。客户今天问包裹 0823 的签收争议，晚上在微信问同一包裹“物流调查到哪了”，可挂到同一案例；明天问 0917 号包裹的发票，应该另开案例。反过来，一个网页表单写“0823 没收到、0917 发票错了”，前端可能只创建了一张平台工单，业务分析却应识别两个诉求，分别有负责人和结案依据。**身份是“谁”，案例是“哪件事”，工单是“系统怎样分配工作”**，三者关系不能用一列手机号代替。

小陈把关联候选写成三类：`confirmed` 表示身份和业务对象都核实，系统可把事件挂到主案例；`suspected` 表示有相似线索但不足以共享敏感信息，只供有权限客服看提示；`rejected` 表示确认不是同案，留下拒绝原因避免模型下次又提同一条错误关联。候选可以升级或撤销，但每次变更都保留操作者、证据和时间。Agent 只能用 `confirmed` 的关联读取历史，不能把 `suspected` 当上下文直接喂给模型。

## 第二关：入口事件要去重，也要保留时间与来源

**领导：**微信平台已经有消息 ID，为什么还要我们的 `source_event_id`？

**小陈：**因为不同渠道的 ID 作用域不同，甚至同一个渠道重试时会再次投递同一事件。我们把唯一键写成“渠道 + 渠道事件 ID”，进站时先查是否处理过；处理过就返回原处理结果，不再建新工单、不再启动 Agent。新事件则保存原始 ID、发生时间、入库时间和原始内容引用。渠道消息可能先发后到，不能拿数据库插入顺序当客户对话顺序。附件另有来源与访问范围，不把照片原件复制到所有渠道和模型日志。

一个教学用标准事件可以写成：

```json
{
  "source": "wechat",
  "source_event_id": "wx-20260928-771",
  "channel_conversation_id": "conv-19",
  "verified_customer_id": null,
  "claimed_order_ref": "0823",
  "occurred_at": "2026-09-28T18:00:00+08:00",
  "ingested_at": "2026-09-28T18:03:10+08:00",
  "content_ref": "vault-msg-771"
}
```

`verified_customer_id` 留空就是留空，不能因为 `claimed_order_ref` 有值就自动补上。身份核验成功后，新增一条映射记录指向可信客户 ID，记录核验方式和有效范围；原渠道事件仍保持原貌。这样以后发现冒用，能撤销映射、重建案例关系和追查哪些答复可能已经泄露，而不必猜当初微信消息究竟带了什么。

**领导：**如果同一条微信消息先被系统处理，半小时后身份才核实，会不会再发一遍回复？

**小陈：**不会。身份映射更新是“关联状态变化”，不是新的客户来信。发送服务仍以业务动作键去重，并检查当前案例的已发承诺。客服可在核验后补充准确答复，但必须是新草稿、新批准和明确的新发送动作，不能让旧事件自动重跑导致第二封矛盾回复。

## 第三关：合并、关联、拆分，各自解决什么问题

**领导：**那我们永远不合并工单，只关联，会不会客服工作台一团乱？

**小陈：**关联不是拒绝整理，而是把整理分成可审查的步骤。第一步保留原渠道记录，建立主案例视图；第二步选一个当前负责人，其他渠道入口都能找到他；第三步把待办、已发承诺和证据按时间线展示。客服看到的是一张主案例卡，底下可以展开微信、App、电话原始记录。若平台必须做物理工单合并，要先确认产品的不可逆后果和权限变化。Zendesk 官方文档就明确写明其工单合并是永久且不能撤销的，因此不能把“误合再拆”当作普遍可用的逃生门。本文采用可撤销的**关联层**，是为了在身份复杂时保留纠错能力。

拆分也有明确条件：一位客户提出两个独立业务诉求，或原来被误认的两位客户；拆分后分别建立负责人、状态、发送对象和结案依据。已发出的错误承诺无法通过拆分擦掉，仍要按渠道回执追踪，必要时由客服批准纠正。技术上撤销一条 `case_link` 很简单，业务上要清点它带来的可见范围和对外信息，这部分不能省。

**领导：**如果 App 负责人与微信负责人同时准备回复，谁说了算？

**小陈：**主案例必须有一个处理责任人；两边的草稿提交前都要读最新的承诺栏和案例版本。App 客服先批准“物流调查中”，微信客服的旧草稿还写“已安排退款”，提交时案例版本不匹配，应被挡回重审。外发审批绑定渠道和收件人，不能把 App 对客户甲的批准拿去微信给一个尚未核身的账户发。这是跨渠道的并发控制，不是一句“团队注意协作”。

## 第四关：指标别奖励系统把错误藏进新工单

小陈让数据同事做两张报表。第一张是运营负担：同一案例用了几个渠道、建了几张工单、客服触碰了几次、有没有相互矛盾的承诺。第二张是关联质量：确认同案被系统漏连的比例、错误自动合并的次数、疑似候选等待人工确认的时间、撤销关联后的影响范围。**错合比漏合更危险**，因为它可能把他人订单暴露出来，所以自动关联阈值应偏谨慎；漏合造成重复处理，也要给客服明确的合案提示和验证入口。

**领导：**你这听起来会让自动合并率很低。

**小陈：**低一点可以接受，前提是疑似同案能被及时人工确认，客户不必讲三遍。我们不拿“自动合并率”单独当 KPI，否则系统会被鼓励大胆猜身份。更好的组合是：跨渠道同案重复承诺下降、误合并为零或符合已批准红线、人工确认等待可控、客户同案复联得到连续处理。数字旁必须标识身份覆盖率：有多少跨渠道事件根本无法核实客户，避免把一大片未知数据藏在分母外。

验收时故意放五组边界样本：同一客户同一订单跨渠道；同一客户不同订单；两位客户共用手机号；家人代问但没有授权；微信旧消息延迟到达而 App 新处理已批准。每组检查三个结果：是否正确关联或停在疑似、工具是否只返回当前有权字段、对外承诺是否仍唯一且可追溯。仅最后一句回复“看着对”不算过，运行轨迹和渠道回执也要对上。

## 领导最后给了四道面试题

**领导：**第一题，去重和合案有什么区别？

**小陈：**去重处理的是同一渠道事件被重复投递，按事件唯一键只处理一次；合案处理的是多个不同事件是否属于同一业务诉求，需要身份与业务对象证据。把两者混在一起，可能把客户真正的新追问当重复丢掉。

**领导：**第二题，为什么同一手机号不一定同一客户？

**小陈：**手机号可能共用、变更、代填，也可能尚未验证。它可作为候选线索，不替代已验证的客户 ID 和订单归属。对客取数时必须按当前渠道身份再校验。

**领导：**第三题，为什么保留 `occurred_at` 和 `ingested_at` 两个时间？

**小陈：**前者表示客户何时发，后者表示系统何时收到。接口延迟和重投会让两者差很多；只按入库顺序排列，旧消息可能覆盖最新处理。两者还能帮助排查渠道延迟与时限问题。

**领导：**第四题，误合以后最先做什么？

**小陈：**先停止关联带来的跨客户可见与自动回复，撤销错误映射并保留审计；再查误合期间哪些人或模型读过数据、哪些消息已外发，交客服和隐私负责人处理影响。统计层随后重算，不能只把界面拆开就宣布修复。

## 两个容易骗过匹配器的现场，必须人工看一眼

第一个现场是“同号不同人”。甲在 App 登录并查询 0823，乙在网页投诉也填了甲的手机号，因为甲是代收人。两条记录手机号一致，订单却分别属于不同账户。系统若把“手机号相同”设为最高权重，会把乙的投诉、甲的订单和两人的附件聚在一页；客服稍不留神就可能向乙解释甲的订单。正确路径是网页记录先留独立工单，手机号只触发候选提示；客服按公司核身流程确认乙对哪张订单有权，再决定是授权代办、另建诉求还是拒绝透露。匹配算法的分数不能越过权限服务。

第二个现场是“同人不同事”。甲在 App 说 0823 没收到，半小时后电话里说 0917 发票金额错。系统通过登录和来电核验确认同一客户，但两个诉求有不同的负责团队、规则和结案依据。若为了减少工单数强行合并，物流调查结束后可能一键把发票问题也结了。主客户视图可以同时看到两个案例的存在，工单处理必须分别推进。一个人有多件事，比一个平台有多张单正常得多。

**领导：**算法是不是给每条候选算一个相似度，超过 0.8 自动并？

**小陈：**相似度可用于排序人工待核候选，不能单独做自动合并开关。把特征分成“强证据”和“弱线索”：已验证客户 ID 与订单归属是强证据；同一手机号、相近时间、相似文本是弱线索。自动关联的前提必须是强证据齐备且没有冲突，弱线索只提高候选优先级。一旦出现不同客户 ID、不同订单归属或不同诉求对象的冲突，直接停到人工，不因为其他相似特征多就凑平均分。这个规则简单但可解释，客服能看到“为什么提示我可能同案”，也能指出错在哪里。

为了检验规则，测试集不只放正常合并，还要故意放“家人共用手机”“同名客户”“截图里有他人运单”“同客户两张订单”“渠道延迟半小时”“重复事件投递”。人工标注每组正确的客户和业务案例关系，分别算**漏关联**与**错关联**，并把错关联按是否发生越权展示分级。若某次规则更新让自动关联率从 70% 涨到 90%，但错关联也增加，就先回滚；不能只看节省了多少客服点击。

**领导：**旧工单很多，新规则上线后能不能一夜之间自动补连？

**小陈：**先影子计算候选，不直接改历史权限与工单责任人。抽样看错关联，分批让客服确认；已结案的单尤其谨慎，关联用于分析客户旅程不代表要把旧附件突然展示给新负责人。历史回填要记录规则版本和执行时间，能按批次撤销。新规则若影响服务质量看板，重算前后的数据差异单独说明，不能让上个月的“机器人解决率”无声无息改成另一数值。

跨渠道承诺还要有一条“先读后写”的规则。客服或 Agent 准备外发时，发送服务检查主案例最新版本与承诺栏；如果另一渠道刚刚批准了不同结论，当前草稿必须回审。客户在微信说“我接受补发”后，App 端旧草稿仍写“等待客户选择”，不能半小时后自动发出。两条渠道消息即使都经过各自客服批准，也可能在业务上互相矛盾；主案例版本校验让系统把冲突显露给负责人。发错的消息不能靠事后合案抹掉，必须查渠道回执、向客户更正并记录是谁批准的哪一版。

小陈把“同案处理成功”写成可验收的一句话：核过身份的客户换渠道追问同一订单时，接手人看得到先前已核事实和已发承诺，客户不用重新讲关键经过；身份不足或诉求不同的消息不会读到别人的资料，也不会被强行结在旧单里。技术上的关联数只是过程指标，客户少解释一次、没有收到相互打架的答复，才是这项集成的业务结果。

验收用两组故意相像的样本：A 客户从微信和 App 追同一订单，核验后只留一个负责的主单，不重复承诺；A、B 共用联系人手机号但订单归属不同，系统只能给人工一个候选提示，任何一方看不到另一方订单。再重复投递微信事件三次，主工单里只出现一次。三关都过，才谈全渠道“看起来是一张单”。
