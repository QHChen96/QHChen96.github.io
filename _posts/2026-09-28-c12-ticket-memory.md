**领导：**昨天客服已经核过签收记录，今天 Agent 又问客户“您有订单号吗”。不是说它有记忆？

**小陈：**“有记忆”这四个字，比“稍后处理”还容易让人误会。我们缺的是这张工单的交接记录，不是让模型把所有聊天永远背下来。

**领导：**那就把整段对话存着，下次全喂进去。

**小陈：**整段太长，还可能带地址、手机号；换了客户要是拿错线程，就成了大型认亲现场。我给 0823 号工单写一页交接簿：

| 栏目 | 这单写什么 | 谁能改 |
| --- | --- | --- |
| 已核实事实 | 订单归属已核验；签收系统返回“已签收”，查询时间 16:02 | 订单工具写入，客服可标注异议 |
| 未解决的问题 | 客户称未收到；签收凭证尚待人工核查 | 客服／审核流程 |
| 当前状态 | 等待物流核查；未批准退款，未向客户承诺退款 | 工单状态机 |
| 下一步与责任人 | 客服小陈跟进物流回执，截止下班前 | 工单负责人 |

**领导：**对话摘要呢？

**小陈：**只保留对处理有用的事实和客户诉求，不把模型的猜测写成“已核实”。摘要由当前工单 ID 绑定；跨天恢复时先读工单状态，再读摘要；有冲突以业务系统和最新人工记录为准。长期知识库只放可复用的现行政策，不存某位客户的私事。[LangGraph 的持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)说明了按线程保存检查点的技术机制；业务上仍要自己定工单归属、访问控制和过期规则。

**领导：**怎么证明没串单？

**小陈：**做两次回放：重新打开 0823，Agent 应接着“等物流核查”处理，不再索要已核验的订单号；切到另一位客户的工单，任何 0823 的摘要、订单状态和附件都读不到。工单关闭后，工作记忆按批准的期限清理；若有人重新开单，只能通过授权的工单关联查到必要历史，不能靠模糊相似度捞别人的记录。验收记录把访问失败也记下来，这比一句“模型应该不会”值钱。

## “记忆”不是一个抽屉，先拆成四本账

**领导：**我只想让它别忘了昨天那单。你怎么又要四本账？

**小陈：**因为这四类东西的真相来源、有效期和访问权都不同。第一本是**工单业务状态**：谁负责、订单归属、物流子任务、退款审批、客户承诺。这些由工单和业务系统写，模型不能把一句对话当成状态变更。第二本是**本次运行状态**：Agent 查到哪一步、哪个工具请求仍在等、当前草稿版本。它用于中断后继续执行，通常跟一次运行或线程绑定。第三本是**对话摘要**：客户说过什么、已经解释过什么、还有什么没弄清，它帮助客服少问一遍，但可能过时或有误。第四本是**可复用知识**：现行签收争议规则、商品政策、客服操作指南，应由知识团队发布，不存进某个客户的私人记忆。

这四本账不能互相冒充。Agent 的摘要写“客户已收到包裹”，但物流状态和客户最新消息都说未收到，摘要要被纠正；运行检查点记着“准备申请退款”，不等于退款系统真的受理；知识库里说“签收争议先查凭证”，也不说明 0823 的凭证已经查过。把所有文字放进一个向量库按相似度检索，模型也许能找到一句像答案的话，却不知道那句话对哪个客户、哪一天、哪个业务状态有效。

**领导：**技术团队说给 Agent 加了 checkpoint，不就能接着昨天跑？

**小陈：**检查点确实有用。以 LangGraph 为例，官方文档把线程内的图状态检查点与跨线程的 store 分开：前者帮助对话继续、中断恢复和故障容错，后者保存应用定义的持久数据。可技术上能恢复线程，不意味着业务上能相信线程里所有内容。恢复时仍要根据当前登录身份、工单归属和权限检查，重新读取关键业务事实；否则昨天的状态可能在今天已被客服、物流或客户更新。

一个简单规则是：**谁有权写，就从谁那里读事实**。订单状态从订单系统读，退款结果从退款系统读，客服承诺从工单事件读，客户原话从当前案件的会话记录读，模型摘要只作导航。检查点记录的是“当时 Agent 看到什么、准备做什么”，不是“世界现在是什么”。它能帮我们定位停在哪一步，也可能带着已经过期的证据，继续前必须复核。

## 昨天的 16:02，到了今天早上还算数吗

**领导：**给我看 0823 跨班到底怎么接。

**小陈：**昨天 16:02，订单工具返回“已签收”；16:05，客服查不到投递照片，建物流子任务；16:10，客服告诉客户“我们正在核查，明天上午更新”；17:50 客服下班。夜里物流回了“签收人名字与收件人不一致”，客户又补一句“门卫说没代收”。今天早上 Agent 若只读昨天的聊天摘要，很可能继续说“等待物流核查”，甚至重复问订单号。正确的恢复顺序是：验证当前会话身份与工单权限 → 读取工单最新版本和未完成动作 → 拉取夜间新增事件 → 只把仍有效的摘要片段放进上下文 → 再决定回复或交接。

交接簿里每条重要事实要有来源、时间和状态。`订单已签收` 是昨天 16:02 的工具回执，并不等于客户实际收到；`客户称未收到` 是客户陈述，不是系统核验；`物流回执签收人不符` 是今天的新证据；`明天上午更新` 是客服给客户的承诺，需要有人履行。小陈把这四条分开，Agent 才能说“订单系统曾显示已签收，但新的物流核查发现签收人信息不一致，我们继续由专员处理”，不会一句“系统显示签收”把新证据盖掉。

**领导：**摘要有新有旧，怎么自动合并？

**小陈：**不靠模型把两段话糊成一段。每次新事件进来，摘要可以生成新版本，但要保留差异和出处。字段如 `verified_facts`、`customer_claims`、`open_questions`、`actions_done`、`promises`、`next_owner` 分开；新事实若与旧事实冲突，标 `conflict`，交给客服或规则处理。摘要可以写“原签收状态被新物流回执质疑”，不能直接把“已签收”改成“未签收”。那会抹掉案件为什么进入争议处理的轨迹。

把摘要每次重写成越来越短的一句话，还会发生**摘要漂移**。最早客户说“先核查，不要退款”，三次压缩后可能变成“客户要求退款”；客服接班照着摘要执行就闯祸。对关键约束和承诺保留原话短引用与消息 ID，定期用原事件回放核对摘要。摘要节省阅读时间，不应代替原始证据。

## 跨客户串单，比“忘事”更危险

**领导：**Agent 总不会故意把 0823 给别人看吧？

**小陈：**串单通常不是“故意”，是键用错了。开发者把 `thread_id` 设成浏览器会话 ID，客服一台电脑切换两位客户，旧线程还在；或者把用户手机号当唯一键，家庭共用号码时两张单被合并；或者向量检索只按“签收争议”相似度找摘要，找到隔壁客户的订单。每种实现都可能让模型读到无权看的资料。模型最后有没有说出来不是唯一风险，**读取本身**就越界。

业务入口应先由服务端确定 `tenant_id`、已认证的 `customer_id`、`case_id` 和授权范围，再把允许读取的本单资料交给 Agent。工具查询必须按这些范围过滤；不能让模型传一个任意工单号就得到内容。线程 ID 只是运行定位键，不是访问许可证。跨班客服也一样：接手人获得工单权限后才可读必要历史；未接手者即使知道工单 ID，也不能靠 API 拼接访问。

**领导：**如果客户在新渠道来问，没带原工单号，怎么找回历史？

**小陈：**先完成该渠道的身份核验，再用业务规则做同案关联。订单号、问题类型、时间窗和客户确认可作为线索，不能单凭一句“没收到货”就相似度合并。候选可能有两张单时，让客服确认；关联后记录谁合并、依据是什么，并保留拆分能力。关联是业务决定，记忆检索只负责提供候选。宁可多核一步，也不要让一个客户看到另一个客户的签收照片。

本单资料也有最小化边界。Agent 为了提醒明天上午更新，只需要工单承诺时间和负责人，不需要完整聊天、地址和历史所有订单。需要查签收凭证时再按权限取对应附件。按需加载比把“客户完整画像”一次塞进上下文更省成本，也减少误用旧信息的机会。

## 进程重启、版本冲突、删除：三种恢复都要试

**领导：**你讲隔离，研发会说“我们已接数据库”。有数据库就不会失忆了吧？

**小陈：**得看接的是什么。官方文档也提醒内存型检查点进程重启后会丢，生产要用持久化方案；但用了持久化数据库也会有写入失败、并发覆盖和版本迁移。测试要在 Agent 已查订单、尚未生成答复时重启进程：恢复后先确认工具调用是否已有回执，不能盲目再执行可能有副作用的动作；读取工单新版本，不能继续拿旧规则给客户答。检查点让“跑到哪一步”可见，业务幂等与权限校验让“继续跑”安全。

换班时两个客服可能同时编辑交接簿。客服甲把状态改成“等待物流”，客服乙刚收到物流结果，要改为“待客户告知”。写入应带预期版本；乙的更新如果基于旧版，要看到冲突和新事件，重新决定，不让后写覆盖先写。摘要同理，新版基于哪个工单事件序号要写清楚；若落后于最新事件，展示“摘要待刷新”，不要伪装成实时真相。

删除更不能只清聊天窗口。工单按批准的期限归档或删除时，要处理运行检查点、摘要、搜索索引、缓存和派生样本；长期知识库若错误混入客户资料，也要定位条目和索引副本。不同系统保留期可能不同，先盘数据流和业务要求，再执行清理并留回执。工单重新打开时，只能在仍合法可用的记录里按权限恢复，不能把已清除的私人信息从模型“长期记忆”里捞回来。

**领导：**要是数据库暂时读不了，Agent 就说“我失忆了”？

**小陈：**它应停止依赖缺失记忆的自动处理，保留客户当前消息并告知需要核查；系统把案件交给有权限的客服或待恢复队列。恢复后依据工单真实状态补读，不能让模型凭对话猜昨天答应了什么。读不到状态和读到“没有状态”是两件事，错误码必须区分。前者要重试或升级，后者可能是新单，绝不能都当成“空白，可以从头开始”。

## 交接簿怎么验收，别拿“它记得名字”当成绩

**领导：**给我一套能让测试同事执行的验收。

**小陈：**第一组是**连续性**：昨天已核验订单，今天同一授权客服接手，不重复问；新物流回执出现，回复必须反映新增证据；客户承诺到期，工作台提醒负责人。第二组是**隔离性**：换客户、换租户、换客服权限、同一手机号关联不同订单、同一浏览器切换账号，均不能读到 0823。第三组是**准确性**：摘要里故意放一条过时事实，恢复时以业务系统和新事件为准，并标示冲突。第四组是**故障恢复**：进程重启、数据库超时、并发编辑、队列重放，工单不丢、动作不重复、无权信息不泄露。第五组是**生命周期**：关闭、重开、到期清理与删除后，检查每类派生数据的状态。

指标也别只叫“记忆命中率”。要分别量重复提问率、过期事实引用率、跨案件拒绝访问成功率、恢复后重复工具动作数、未履行承诺数。重复提问有时是必要核验，抽样时要看原因；过期事实即使没引发投诉，也要算质量问题；跨案件访问即使模型没输出，也要作为权限事件记录。测试用虚构工单与假客户，不把真实客户聊天拿来随意演示。

**领导：**最后来个面试题。短期记忆、长期记忆、业务状态，一句话分清。

**小陈：**短期记忆帮助这次运行或这个线程续上；长期记忆保存经业务允许、跨线程复用的应用数据；业务状态由订单、工单、审批等系统维护，是执行动作的真相来源。框架提供存取机制，业务系统决定谁能读、何时过期、冲突时信谁。真正的“记住客户”，不是把他所有话永远塞给模型，而是在他有权继续处理这张单时，准确接住还没办完的事。

## 研发要建表，小陈给出最小数据契约

**领导：**研发在群里问：“到底存哪几个字段？”你别回一句“按需设计”。

**小陈：**交接簿的最小记录可以是 `tenant_id`、`case_id`、`case_version`、`summary_version`、`source_event_range`、`verified_facts`、`customer_claims`、`open_questions`、`actions_done`、`promises`、`next_owner`、`updated_at`。每条 `verified_fact` 必须指向工具或人工确认回执，客户陈述指向消息 ID，承诺指向对客发送回执与到期时间。系统不必把所有聊天复制到这张表；需要原文时按权限回到原事件。`source_event_range` 标明这份摘要覆盖到哪条事件，后续有新消息就能提示“摘要落后两条”。

运行检查点单独保存 `run_id`、`thread_id`、当前节点、待确认工具调用、模型配置版本和检查点时间。检查点引用 `case_id`，却不把工单状态复制成第二套可写真相。重启恢复时先读运行检查点，再读取工单最新版本；若工具请求状态未知，先查业务回执或人工核对，不能凭检查点中的“准备执行”就重做退款。跨线程的长期 store 若保存客户偏好，也必须有来源、范围、到期与删除机制，不能把“客户上次抱怨物流慢”自动变成永久标签。

**领导：**这些字段会不会让摘要变成一本厚书？

**小陈：**存储结构可以细，展示要短。客服接班页面只显示当前诉求、已经核实的三五项、还缺的证据、下一步与截止时间；点开才看来源和时间线。Agent 的上下文也按当前问题选取：问物流就加载物流相关状态和政策，问发票就加载发票规则。超过上下文预算时，优先保留未完成动作、客户明确限制和最新回执，旧闲聊可以不放。压缩是为了少读废话，不是为了删掉责任。

## 两次真实感更强的串单测试

**小陈：**第一场：客服坐席在同一个浏览器标签先处理 0823，退出后登录另一位客户，打开 0917。测试脚本保留原浏览器缓存、旧线程参数和搜索历史。后端应以新登录身份和新 `case_id` 重新授权，旧线程即使被前端带上，也只能返回拒绝并记录安全事件；页面不能闪出上一位客户的摘要。只做“清空前端状态”的测试不够，因为生产事故常发生在旧参数漏清的时候。

第二场：同一位客户同时有一张签收争议单和一张发票单，描述里都提到“昨天的订单”。系统可以在有权限时展示候选，但不能把签收照片塞进发票 Agent 的上下文，除非任务确实需要且工单关联经确认。相同客户也不等于所有案件都能混用；客户希望查发票入口，不代表授权 Agent 顺手重读投诉和退款历史。隔离测试不仅防跨人泄露，也防同一客户的无关资料被滥用。

如果这两场测试有一次失败，先冻结相关记忆检索和跨单自动关联，把服务降级为当前单的受控读取与人工接手。修复要落在服务端授权、键设计和索引过滤，不是给模型加一句“不要泄露”。模型看见了就已进入风险区，拦住输出只是最后一道门。

**领导：**还有一个问题。昨天的摘要引用签收规则 v3，今天规则更新成 v4；工单继续处理时听谁的？

**小陈：**摘要记录“昨天按 v3 查过”，这是历史事实；今天要作新决定，先查 v4 的生效时间、适用范围和是否影响存量工单，再由业务规则确定。不能把知识库的最新版无脑套到已经形成的承诺上，也不能因为摘要里存了 v3 就一直用旧规则。若新旧规则适用边界不清，暂停自动结论，交业务负责人裁决并把裁决记入工单。长期知识更新与工单历史连续性并不冲突，前提是每条结论都有版本和时间。

**领导：**那“记忆”能不能直接给客户展示？

**小陈：**可以展示客户应知的进度，不把内部猜测和风险标签当事实告诉客户。比如“物流核查已收到新的签收人信息，专员将在今天更新”，前提是相关回执真实存在、时间承诺有人负责。内部摘要可能写“疑似错投”，这仍是推断，不能变成“您的包裹已错投”。对客措辞要基于已核事实和批准规则，发送前再查工单最新版本，避免客服接班期间状态已变化。

要验收这点，小陈会在测试里故意让物流回执与客户补充消息在同一分钟到达，再让 Agent 生成草稿。草稿要同时看见两条新事件；若读取时摘要还没刷新，系统应标“摘要过期”，直接拉取原事件或转人工。所谓记性好，不是背得牢，而是知道手里的笔记何时已经过时。

**领导：**换班后的 Agent 记得一句“客户已同意”，就能接着发消息吗？

**小陈：**不能。状态要指明客户同意的是哪版内容、哪个渠道、何时给出，有原消息或审批回执；换班时重新核工单版本与当前收件人。若客户后来撤回或补充信息，旧同意失效。摘要能让接手人知道发生过什么，不能替具体动作的授权记录签字。
