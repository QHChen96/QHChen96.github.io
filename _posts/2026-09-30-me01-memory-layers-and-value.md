**领导：**销售助手别每次都问客户情况。加个记忆，让它永远记得客户，最好比销售本人还熟。

**小陈：**可以先记有用的。它现在已经很熟了，熟到把去年没批的八五折当今年承诺，一开口就帮公司少收钱。记忆的目标是下次做事更准确，不是把说过的话都供起来。

本专题延续多 Agent 协作里的**教学虚构**案例：星河制造即将续约，助手查询 CRM、合同政策和工单，生成附证据的内部草稿。当前联系人林女士要求“工作沟通先发邮件，不要直接电话”；后来她可能改口，也可能换了联系人。我们需要记住适用的偏好、任务进度和已核验背景，同时保证价格、权限和服务状态仍从权威系统确认。所有人物、数据和状态名用于教学。

## 一、模型能看见、应用有存档、下次能找回，是三件事

**领导：**聊天记录明明在页面上，为什么助手说不知道？

**小陈：**页面存着不等于这轮请求带着。模型只能利用实际收到的上下文。应用可以保存一万条消息，但这次只发最后五条，它不会隔空翻我们的数据库；反过来，这轮发过的资料，如果应用没有保存与索引，换个会话又可能找不到。

一次模型调用的输入由指令、当前问题、部分历史、工具说明和检索材料组成。这些内容共同消耗上下文空间。模型利用它们生成下一步输出，而不是自动把所有内容永久写进自己的参数。我们通常讨论的 Agent 记忆，是应用在模型外部建立的写入、存储、读取与更新机制。是否还另有模型训练或服务商数据处理，是不同问题，不能拿“有记忆功能”一句话包办。

保存历史解决可回看，检索解决能找回，组织上下文解决当前能利用。三层任何一层失误，都可能表现成“忘了”。用户偏好从未提取是写入问题；提取正确但客户 ID 错了是归属问题；找到了却没有注入当前请求是组装问题；注入了大量无关消息掩盖关键条件，是利用问题。诊断先找到丢失位置，才知道是否需要更大上下文或新的记忆服务。

**领导：**把全部历史塞进去总能解决吧？

**小陈：**先遇到容量与费用，再遇到旧新冲突。历史里既有客户原话，也有助手猜测、过期规则和已经推翻的方案。全量输入不自动告诉模型哪条现在有效。它还要从长文本里找出具体对象和时间条件；扩大窗口只能缓解容量，不能替我们维护事实版本与权限。

## 二、六个抽屉，各自保存不同的真相

| 层 | 回答的问题 | 星河制造例子 | 使用方式 |
| --- | --- | --- | --- |
| 当前上下文 | 这轮需要看什么 | 当前续约目标与相关证据 | 按任务临时组装 |
| 会话历史 | 双方实际说过什么 | 林女士提出先邮件沟通 | 保存原话与说话者 |
| 工作状态 | 这件事办到哪一步 | 合同核验完成，工单仍待确认 | 结构化状态持续更新 |
| 检查点与工件 | 停下后从哪里恢复 | 当前阶段、草稿版本与证据引用 | 按运行身份恢复 |
| 长期记忆 | 以后可能再次有用什么 | 当前联系人的沟通偏好 | 按范围和有效期检索 |
| 权威业务资料 | 现在究竟是什么 | 生效合同、价格审批、工单状态 | 从业务系统核实 |

抽屉之间可以关联，但不能互相冒充。会话里说“已经发出报价”只证明有人说了，动作回执才证明提交或投递；记忆里写“客户偏好邮件”能帮助准备联系，不证明当前地址仍正确；检查点记着上次批准，实际发送前还要核对批准绑定的版本与期限。清楚地保存不同来源，比一张什么都装的向量表更容易追查。

**领导：**长期记忆里也可以存合同吧？

**小陈：**可以存合同相关背景与定位，但要保留版本和失效规则。它不能成为脱离合同登记的第二个权威系统。生效状态、最终价格与工单处理结果变化快，需要使用时核对。我们可以缓存事实，但必须知道缓存何时失效、核对失败时如何收窄结论。

## 三、长期记忆可以有三种内容，别都写成客户画像

语义记忆保存可复用事实与偏好，例如林女士偏好先邮件。事件记忆保存一次具体经历，例如九月某次沟通中客户提出报表问题，关联当时背景、行动和结果。流程知识保存经过验证的做事方法，例如该客户验收前需要先由技术联系人确认报表口径。三类内容用途不同，组织方式也不同。

**领导：**“客户很难伺候”，算哪一种？

**小陈：**那是评价，通常不应该直接进长期事实。可以记“在九月会议中，客户要求报价先注明服务范围”，并附来源。把具体要求变成负面标签，会污染下次判断，也没有可靠验收。事件能保留细节，语义事实要有依据，流程经验还要验证适用条件。

[LangMem 的概念指南](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)也讨论 semantic、episodic 与 procedural 等类型。这里借用的是应用设计分类，不表示软件记忆等同于人的神经机制。一个数据库可以存三类记录，区别来自字段、验证与读取策略，未必需要三套技术平台。

流程知识尤其要防止从一次经历推成永恒规则。某个工单通过人工例外批准，不意味着以后都能走例外路径；某次工具调用失败，可能只是暂时服务故障，不应该永久写成“此工具不可用”。把经验表示为适用环境、前提、行动与验证结果，下次先核对前提，再考虑采用。能力提升来自可检验经验，不来自把模型自评“这次做得不错”记进制度。

## 四、记忆的主体是谁，比记了多少更重要

林女士是一位联系人，星河制造是一家公司，当前续约是一个任务，销售团队又有自己的表达规则。四个层级不能混在同一个`user_id`里。林女士不希望直接电话，是她的沟通偏好，不能推成集团所有员工都不接电话；当前销售要求草稿简洁，是应用用户偏好，也不能覆盖客户对合同信息完整性的要求。

我们为记忆定义租户、主体类型、主体 ID、应用或项目、可见范围与用途。对象来自业务解析和授权，不由模型随便编一个名字。个人偏好、客户共享背景、团队流程知识分开命名空间。关系可以关联联系人属于公司，但关联不自动扩大可见范围，也不意味着偏好会沿组织树继承。

**领导：**以后换销售接手，旧偏好还用不用？

**小陈：**看交接授权与是否仍适用。客户级背景可以按组织规则交接，个人用户自己的写作习惯不一定要跟着走；联系人换了，旧联系人的偏好不再指导新联系人。系统应根据业务身份查当前关系，再检索对应范围。所谓跨会话，是同一授权范围的延续，不是全公司随时共享所有人的聊天。

主体解析不确定时，先不入权威记忆。例如一句“王总还是喜欢微信”里，王总可能指客户负责人，也可能指我们自己的主管；“还是”说明历史延续，却没有给出足够身份。保留候选并等待确认，比把错误归属持久化便宜得多。后面写入篇会把这种不确定变成明确状态，而不是让它躲在一个置信度小数里。

## 五、什么值得记：看未来用途，不是看今天说得响不响

**领导：**既然存储便宜，全部留着以后慢慢筛。

**小陈：**存原始历史和提取长期记忆是两项决定。原始历史按用途与保留策略保存，长期记忆只提取以后确实可能有用的内容。每条记忆都要付维护、检索、验证和错误传播成本，不能只算硬盘钱。

判断可以使用四个条件：是否有明确未来用途，是否有可靠来源，是否有稳定主体与范围，是否有更新或失效办法。林女士明确提出先邮件，能影响下次沟通，主体清楚，可以写成可修订偏好；“今天好累”可能只是即时情绪，未必有长期用途；“也许下季度换产品”属于尚未确认计划，应带条件与期限，不能写成已决定迁移。

业务敏感度影响写入门槛。语气偏好可以在用户明确表达后直接保存；价格、权限、身份关系和商业承诺要从相应系统或批准记录验证。模型推测可以短期辅助分析，不能自动升级为长期事实。没有用途的敏感资料尽量不形成额外副本；如果任务只需要知道“已通过资格检查”，未必需要长期保留全部原始证明。

重要性分数可以帮排序，不能绕过这四个条件。销售在群里重复八次同一个错误报价，重复只提高出现频率，不提高权威性。模型自己生成的判断也不能因为“很重要”直接入库。先决定合法与可信，再讨论值得占多少上下文。

## 六、一条记忆最小应该长什么样

下面是**教学结构**，不是某个 SDK 的固定对象：

```json
{
  "memory_id": "contact-17-channel",
  "tenant_id": "tenant-a",
  "subject_type": "contact",
  "subject_id": "contact-17",
  "kind": "preference",
  "predicate": "preferred_contact_channel",
  "value": "email_first",
  "source_ref": "conversation-31/message-8",
  "source_actor": "contact-17",
  "status": "active",
  "revision": 1,
  "valid_from": "2026-09-30",
  "review_after": "2026-12-30",
  "purpose": "renewal_communication"
}
```

`memory_id`标识逻辑记忆，`revision`区分修订；主体与租户确定它描述谁，`predicate`说明哪种属性，`value`保存值。来源定位证明这条偏好出自谁、在哪次对话。`valid_from`表示适用开始，`review_after`提醒何时复核，不一定等于物理删除日。偏好被改口时创建新修订并使旧值停止用于当前沟通，历史根据保留策略处理。

文本也可以是记忆，但关键约束别只藏在自然语言里。租户、主体、类型、状态、有效期和权限尽量结构化，便于过滤与验证；内容保留易读表述与证据定位。若以后引入向量索引，向量是搜索辅助，结构记录仍保存真实版本与状态。模型不用从一段长摘要里猜“这是谁的、还有效吗”。

空值要有语义。“未记录偏好”与“用户明确没有偏好”不同；“尚未确认联系人”与“当前没有联系人”不同。缺失不等于否定。写入结构包含观测状态和未知，读取时就能决定是否需要再次确认，而不会默认一个看似方便的值。

## 七、当前资料与记忆，怎样在回答时汇合

生成续约草稿之前，应用先解析任务对象与权限，再读取当前联系人偏好、相关历史承诺及工作状态，同时查询生效合同和未关闭工单。两条资料路径在上下文组装处汇合，但保留不同地位：偏好帮助决定怎么沟通，合同决定可以陈述什么，批准记录决定允许承诺什么。

**领导：**客户以前说过愿意续约，为什么还要问现在状态？

**小陈：**历史意向提供背景，不保证今天仍有效。我们可以写“上次沟通表达了续约意向，当前仍需确认”，不能直接写“已确认续约”。时间敏感性由属性决定。长期稳定的表达习惯、短期计划与实时业务状态，需要不同的复核策略。

上下文里可以明确分区：当前目标与硬约束、已核验当前事实、带日期的历史事件、适用偏好、未解决问题。把记忆放在数据区，不将客户原话变成系统级指令。假如一条记忆写“客户要求跳过审批”，它描述一个请求，不授予任何权限；系统仍按业务规则审批。程序解释记忆地位，模型处理内容，职责才能分开。

输入预算不足时，优先保留影响本次决定的约束与必要事实。不是所有记忆都要每轮出现，甚至稳定偏好也可以按任务类型选择；计算合同金额时不需要把“客户喜欢简洁称呼”反复塞给模型。记忆被检索到与被使用分开记录，以后才知道哪些内容只是热闹陪跑。

## 八、存成文件、关系表还是向量，先看访问方式

**领导：**别人都用向量库，我们只用数据库是不是落后？

**小陈：**已知客户、已知属性的查询，直接按主键查表更准；“客户上次为什么反对升级”这种语义问题，才需要搜索历史事件和相关证据。短小的团队规则可以用版本化文件或受控配置。关系复杂、时间变化多时再评估图。存储形态由访问与维护要求决定。

文件便于阅读、版本审查与随代码维护，但要管理共享写入、权限和发布；关系表适合类型、版本、事务和确定查询；向量索引适合相似内容召回，单靠它难以表达精确撤销与当前版本；图可以表达实体、关系与时间，但会增加抽取、实体合并与一致性成本。组合是常态，不能用一种数据库名称代替整个记忆方案。

架构最初可以只有三块：消息与事件存档，结构化记忆表，按需组装上下文的服务。先验证偏好、更新和范围隔离，再加入语义召回。技术选择可替换，记忆身份、来源和状态语义要保持稳定。否则换供应商会让所有历史记录都变成一段无法解释的字符串。

## 九、把一次完整续约走完，看看六个抽屉怎样配合

**领导：**分类我听懂了，真做事时不还是一起塞给模型？

**小陈：**我们顺着一件事走，先看看每个阶段要拿什么。收到“帮星河准备续约草稿”时，任务状态保存目标、客户身份、允许读的系统与草稿交付要求。先解析当前联系人，再查她的有效沟通偏好。历史消息保留原话，长期记忆只提供经确认的邮件优先规则；这里还没有查询价格，也没有批准任何动作。

合同工具返回生效版本后，工作状态保存合同引用与核验结果，工件区保存可追溯的证据摘录。草稿引用这版合同，不能引用某条记忆里的旧价格。工单服务暂时不可用时，状态记录核验未完成，草稿把服务风险标为待确认。模型为了让话漂亮写出“问题已全部解决”，应用的证据检查要挡住它，不能让这句漂亮话再被记忆抽取器保存成客户事实。

如果这时运行停止，恢复靠任务阶段、证据版本与检查点，重新确认失效的工具观测；长期偏好不能告诉我们草稿到底审到哪里。下一次新会话只问“怎么联系林女士”，读取她当前偏好即可，没必要恢复整份续约检查点。两种读取入口对应两种问题，少走一条无关路径，也少引入一批旧状态。

**领导：**那最后需要总结什么？

**小陈：**保存可复用的已核验背景与本次事件结果。比如她要求后续方案注明报表口径，可以形成带来源的沟通要求；本次草稿已完成则是任务结果。未经外部回执确认的“发送成功”不写成事实，仍未解决的问题也不为了结项好看改成已解决。下一轮能找到这些记录，还要解释它们来自哪次事件、是否仍适用。

记录的粒度也在这个流程里决定。联系人偏好是一条可单独修订的属性，会议纪要是一组带来源的事件，项目进度是一份结构状态。若把三者塞进同一段画像，客户改了联系方式就得重写整段文字，重写时容易顺手丢掉未关闭工单；拆成独立对象后，更新哪种事实就触碰哪种对象，审计也能定位。

## 十、画像与事件集合，怎样组合才不越记越胖

短画像适合直接查当前值：称呼、当前沟通偏好、已确认的角色。事件集合适合按问题找经历：为什么反对上一版方案、哪次会谈提出数据口径问题。画像快，但容易把多来源条件揉没；事件完整，但检索与版本判断更复杂。我们的组合是当前属性保持结构化，原始经历保留证据链，按本轮问题生成临时背景。

画像里的每个值最好还能指回组成它的有效记录。用户在管理界面改偏好时，修改的是逻辑属性与修订，不能只是把展示文字改掉；展示、检索与实际生成读取同一份当前状态。允许用户看见“来源是你上次明确提出的要求”，也能发现模型把同事的意见记到了自己头上，形成低成本纠错入口。

维护成本不能只看记录数量。某条偏好每轮都读取，却从没影响决定，可能范围过宽；某条重要条件只有特定任务要用，可以在条件触发时检索；长期没人使用的历史事件也未必该立刻删除，可能还有审计用途。使用统计帮助判断价值，实际留存仍按用途与策略，不凭点击频率处理所有资料。

**领导：**能不能让 Agent 自己学出公司的最佳流程？

**小陈：**可以整理候选经验，发布仍要看适用环境和验证结果。销售沟通的措辞建议容易检查，绕过报价审批的“经验”不能发布。我们把经验发现和规则生效分开，既让记忆积累有用方法，又让公司流程保持有负责人、有版本、有撤回办法。这样记得越久，系统应当更稳，而不是越来越有自己的主意。

## 十一、“记性好”的验收，先拿这五种情况试

| 场景 | 合格表现 | 常见假成功 |
| --- | --- | --- |
| 换窗口问沟通方式 | 取回当前联系人有效偏好 | 复述另一个人的习惯 |
| 客户改口 | 使用新值并停用旧值 | 两个值一起塞入提示 |
| 合同更新 | 查现行版本，不凭历史报价 | 熟练复述旧政策 |
| 研究任务重启 | 恢复合法进度与证据 | 只恢复聊天语气 |
| 撤回一条偏好 | 当前检索与上下文停止使用 | 只删界面显示记录 |

这些测试预期不是已经取得的生产成绩。项目按真实业务样本执行，观察信息从源消息、写入记录、检索候选到最终产物经过哪几步。尤其不要只测试“你记得我叫什么吗”：名字容易精确匹配，跨主体更新、权限和真实决定才暴露工程问题。

**领导：**那你这次交什么？

**小陈：**交六层职责图、记忆字段、写入资格表与验收场景。先只启用当前联系人的明确沟通偏好和可核验业务背景，价格与动作仍由原系统确认。我们要的是下次少问重复问题、少犯历史错误，不是让助手像退休同事一样把十年前每件事都讲一遍。

下一篇展开写入：客户一句“以后先电话”，怎样从原话变成新修订，旧邮件偏好又怎样停止被检索，而不是越存越多、越记越矛盾。
